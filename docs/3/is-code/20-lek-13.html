01База, которую можно отправить письмом

Администратор ИС «Склад+» ООО «Северный склад» копирует файл sklad.db на флешку и передаёт разработчику. В файле 4800 товарных позиций, 12 категорий, четыре площадки и остатки по ним. Разработчик открывает файл на ноутбуке, выполняет запрос и видит те же данные, что на складе. Никакого сервера, службы Windows и строки подключения к localhost при этом нет.

Так работает SQLite. Это не сервер, который принимает подключения по сети, а библиотека, встроенная в программу. Приложение вызывает функции библиотеки, а библиотека читает и пишет один файл. В Python модуль sqlite3 входит в стандартную поставку, поэтому первый запрос можно выполнить без установки чего-либо.

SQLite хранит целую базу в одном файле и обеспечивает целостность через транзакции и ограничения. Файл это не просто набор таблиц. Внутри есть заголовок, страницы данных, индексы, служебные структуры и журнал изменений. Именно поэтому база переживает сбой питания и не превращается в текст, который можно испортить одной неверной записью.

Дальше разберём, из чего состоит файл, как читать схему, зачем нужен индекс, что делает транзакция и какие ограничения проверяет сама база, а не программа.

02Что лежит внутри одного файла

Файл базы делится на страницы. По умолчанию размер страницы 4096 байт. Первая страница содержит заголовок файла и корень служебной таблицы sqlite_master. В ней описана схема: какие таблицы, индексы и представления существуют и каким оператором они созданы. После создания учебных таблиц запрос к служебной таблице возвращает их список.

import sqlite3

conn = sqlite3.connect(".../sklad-plus/data/sklad.db")

for row in conn.execute(
    "SELECT type, name, tbl_name FROM sqlite_master ORDER BY type, name"
):
    print(row)

('index', 'sqlite_autoindex_categories_1', 'categories')
('index', 'sqlite_autoindex_products_1', 'products')
('index', 'sqlite_autoindex_stock_1', 'stock')
('index', 'sqlite_autoindex_warehouses_1', 'warehouses')
('table', 'categories', 'categories')
('table', 'products', 'products')
('table', 'stock', 'stock')
('table', 'warehouses', 'warehouses')

Запрос показывает две вещи. Первая: схема сама является данными, её можно прочитать обычным SELECT. Вторая: некоторые индексы созданы автоматически. sqlite_autoindex_products_1 появился из-за ограничения UNIQUE на артикул, sqlite_autoindex_stock_1 из-за составного первичного ключа. Это не отдельные таблицы, а структуры ускорения и проверки уникальности.

Данные таблицы хранятся в B-дереве. Каждая строка имеет внутренний идентификатор rowid, если таблица не объявлена без него. Для таблицы с целочисленным первичным ключом INTEGER PRIMARY KEY этот ключ и есть rowid, поэтому отдельный столбец не создаётся. Отсюда правило: не добавляйте AUTOINCREMENT без необходимости, он добавляет служебную таблицу и замедляет вставку, а уникальность целочисленного ключа обеспечивается и без него.

Кроме таблиц и индексов, в файле есть список свободных страниц. Когда строку удаляют, место не возвращается операционной системе сразу, а помечается свободным и используется следующей вставкой. Поэтому размер файла после массового удаления может не уменьшиться. Команда VACUUM перестраивает файл и возвращает свободное место, но требует дополнительного места на диске и блокирует запись.

Режим журнала определяет, как фиксируются изменения. В режиме DELETE рядом с базой на время транзакции создаётся отдельный файл журнала, а после фиксации он удаляется. В режиме WAL изменения сначала пишутся в файл -wal, а читатели видят прежнюю версию, пока новая не зафиксирована. Новый файл открывается в режиме DELETE, а переключение выполняет команда PRAGMA journal_mode = WAL, которая возвращает новое значение режима.

03Схема учебной базы

Схема это договор о данных, записанный на языке SQL. Она задаёт таблицы, столбцы, типы и правила. Для склада достаточно четырёх таблиц: площадки, категории, товары и остатки.

conn = sqlite3.connect(".../sklad-plus/data/sklad.db")
conn.execute("PRAGMA foreign_keys = ON")

conn.executescript(
    """
    CREATE TABLE warehouses (
        id    INTEGER PRIMARY KEY,
        code  TEXT NOT NULL UNIQUE,
        title TEXT NOT NULL
    );

    CREATE TABLE categories (
        id    INTEGER PRIMARY KEY,
        title TEXT NOT NULL UNIQUE
    );

    CREATE TABLE products (
        id          INTEGER PRIMARY KEY,
        sku         TEXT NOT NULL UNIQUE,
        title       TEXT NOT NULL,
        category_id INTEGER NOT NULL REFERENCES categories(id)
    );

    CREATE TABLE stock (
        warehouse_id INTEGER NOT NULL REFERENCES warehouses(id),
        product_id   INTEGER NOT NULL REFERENCES products(id),
        qty          INTEGER NOT NULL CHECK (qty >= 0),
        PRIMARY KEY (warehouse_id, product_id)
    );
    """
)

conn.executemany(
    "INSERT INTO warehouses (code, title) VALUES (?, ?)",
    [("MSK", "Москва"), ("TVR", "Тверь"), ("TUL", "Тула"), ("KLG", "Калуга")],
)

titles = [
    "Крепёж", "Электрика", "Сантехника", "Инструмент", "Спецодежда", "Упаковка",
    "Хозтовары", "Метизы", "Лакокраска", "Стройматериалы", "Перчатки", "Плёнка",
]
conn.executemany("INSERT INTO categories (title) VALUES (?)", [(t,) for t in titles])

conn.executemany(
    "INSERT INTO products (sku, title, category_id) VALUES (?, ?, ?)",
    [(f"SKU-{1000 + i}", f"Товар {i}", i % 12 + 1) for i in range(4800)],
)
conn.executemany(
    "INSERT INTO stock (warehouse_id, product_id, qty) VALUES (?, ?, ?)",
    [((i % 4) + 1, i + 1, (i * 7) % 250 + 10) for i in range(4800)],
)
conn.commit()

Четыре площадки и 12 категорий заданы явно, а 4800 товаров и 4800 строк остатка созданы генератором, чтобы не вставлять их вручную. Номера артикулов идут от SKU-1000 до SKU-5799, категория выбирается остатком от деления, склад распределяется по кругу. Такие данные удобны для проверки запросов, но не заменяют реальный справочник.

После загрузки файл занимает около 102 страниц по 4096 байт, то есть примерно 400 КБ. Для 4800 товаров и 4800 строк остатка это немного. Компактность достигается за счёт того, что SQLite не держит отдельный процесс, буферы сервера и журналы фиксированного размера. Индекс, который мы создадим дальше, добавит ещё около 48 КБ.

Проверить размеры можно командами PRAGMA page_size и PRAGMA page_count: их произведение даёт размер файла без учёта журнала.

Разберём ограничения по строкам.

PRIMARY KEY задаёт уникальный идентификатор строки. В таблице warehouses это целое число, которое удобно использовать как внешний ключ. В таблице stock первичный ключ составной: пара «площадка и товар» уникальна, потому что один товар хранится на площадке одной строкой остатка.

UNIQUE запрещает повторение значения. Артикул товара уникален, код площадки тоже. SQLite создаёт для такого столбца автоматический индекс, поэтому проверка уникальности не требует полного перебора.

NOT NULL требует, чтобы значение было задано. Без него в столбец можно записать NULL, и программа получит ошибку позже, при чтении.

REFERENCES объявляет внешний ключ. Он говорит, что category_id должен указывать на существующую строку в categories. Но одного объявления мало: SQLite по умолчанию не проверяет внешние ключи. Проверка включается отдельной командой PRAGMA foreign_keys = ON для каждого соединения. Об этом ниже.

CHECK задаёт условие на значение. CHECK (qty >= 0) не даст записать отрицательный остаток. Это пример правила, которое лучше держать в базе, а не только в коде: база защищает данные от любой программы, включая ручной запрос и будущий скрипт импорта.

Посмотреть схему конкретной таблицы можно через PRAGMA table_info.

for row in conn.execute("PRAGMA table_info(stock)"):
    print(row)

(0, 'warehouse_id', 'INTEGER', 1, None, 1)
(1, 'product_id', 'INTEGER', 1, None, 2)
(2, 'qty', 'INTEGER', 1, None, 0)

Второй столбец вывода это имя, третий объявленный тип, четвёртый признак NOT NULL, шестой позиция в первичном ключе. У warehouse_id и product_id позиции 1 и 2, значит ключ составной. У qty позиция 0, значит в ключ он не входит.

Связи между таблицами удобно читать по внешним ключам. products.category_id ведёт в categories.id. stock.warehouse_id ведёт в warehouses.id, а stock.product_id в products.id. Получается звезда: товар связан с категорией, остаток связывает товар и площадку. Такая схема устраняет дублирование: название категории хранится один раз, а не в каждой строке остатка.

04Индекс: как поиск перестаёт быть перебором

Индекс это отдельное B-дерево, в котором хранятся значения столбца и ссылки на строки. Если индекс есть, база находит нужные строки по дереву, а не просматривает таблицу целиком. Разница видна в плане запроса.

for row in conn.execute(
    "EXPLAIN QUERY PLAN SELECT sku FROM products WHERE category_id = 3"
):
    print(row)

(2, 0, 216, 'SCAN products')

SCAN означает полный просмотр таблицы. Для 4800 строк это ещё терпимо, для миллиона строк уже заметно. Создадим индекс по столбцу категории.

conn.execute("CREATE INDEX idx_products_category ON products(category_id)")

for row in conn.execute(
    "EXPLAIN QUERY PLAN SELECT sku FROM products WHERE category_id = 3"
):
    print(row)

(3, 0, 61, 'SEARCH products USING INDEX idx_products_category (category_id=?)')

SEARCH означает поиск по индексу. Третье число в выводе этой версии SQLite это оценка стоимости плана: 216 против 61. Оценка не гарантирует реальное время, но показывает, что план изменился.

Индекс ускоряет чтение и замедляет запись: при каждой вставке, изменении и удалении базы нужно обновить и дерево индекса. Поэтому индексы создают под конкретные запросы, а не на все столбцы подряд. Для внешнего ключа индекс особенно полезен: при удалении родительской строки база проверяет дочерние, и без индекса каждая проверка превращается в полный просмотр.

Порядок столбцов в составном индексе важен. Индекс (warehouse_id, product_id) ускоряет поиск по площадке и по паре «площадка и товар», но не ускоряет поиск только по товару. Если запросы идут по обоим столбцам отдельно, нужны два индекса или один с другим порядком.

Индекс не обязан хранить все столбцы. Если запрос выбирает только артикул и категорию, индекс по этим двум столбцам может ответить без обращения к таблице. Такой индекс называют покрывающим. Он экономит чтение страниц, но занимает больше места.

Проверять план нужно после изменения данных и запросов. Планировщик SQLite использует статистику, которую собирает команда ANALYZE. Без статистики он может выбрать неверный индекс или не выбрать ни одного. В учебном проекте ANALYZE запускают после массовой загрузки, а не после каждой вставки.

05Транзакция: всё или ничего

Транзакция объединяет несколько изменений в одну операцию. Либо база применит все изменения, либо ни одного. Это свойство называют атомарностью. Второе свойство, согласованность, означает, что после транзакции выполняются все ограничения. Третье, изолированность, скрывает незафиксированные изменения от других читателей. Четвёртое, долговечность, гарантирует, что зафиксированные данные переживут сбой питания.

В SQL транзакция начинается командой BEGIN, завершается COMMIT или ROLLBACK. В Python модуль sqlite3 умеет управлять транзакцией через контекстный менеджер соединения.

try:
    with conn:
        conn.execute(
            "UPDATE stock SET qty = qty - 10 WHERE product_id = 1 AND warehouse_id = 1"
        )
        conn.execute(
            "UPDATE stock SET qty = -1 WHERE product_id = 2 AND warehouse_id = 2"
        )
except sqlite3.IntegrityError as error:
    print("транзакция отменена:", error)

print(
    "остаток после отмены:",
    conn.execute(
        "SELECT qty FROM stock WHERE product_id = 1 AND warehouse_id = 1"
    ).fetchone()[0],
)

транзакция отменена: CHECK constraint failed: qty >= 0
остаток после отмены: 10

Первая команда уменьшила остаток с 10 до 0 и была бы применена, если бы транзакция завершилась успешно. Вторая команда нарушила CHECK, потому что остаток не может быть отрицательным. Контекстный менеджер откатил обе команды, и остаток вернулся к 10. Без транзакции первая команда осталась бы в базе, и склад потерял бы 10 единиц товара без документа.

Важно: with conn управляет транзакцией, но не закрывает соединение. Закрывать его нужно отдельно, обычно в конце работы программы или через contextlib.closing.

SQLite обеспечивает сериализуемую изоляцию транзакций: читатель не видит незафиксированные изменения, а писатель блокирует других писателей. Один писатель в каждый момент времени, несколько читателей параллельно. Для склада с 120 сотрудниками это обычно достаточно, если транзакции короткие.

Долгая транзакция держит блокировку и мешает другим. Если программа открыла транзакцию, изменила строку и ушла на обед, остальные получат ошибку database is locked. Лечение простое: не держать транзакцию во время ввода пользователя, сетевых запросов и ожидания. Сначала соберите данные, затем откройте транзакцию, выполните изменения и сразу зафиксируйте.

Для ожидания блокировки используют PRAGMA busy_timeout. Значение задаётся в миллисекундах: база подождёт указанное время, прежде чем вернуть ошибку.

conn.execute("PRAGMA busy_timeout = 5000")

Пять секунд это разумный запас для учебного проекта. Бесконечное ожидание опасно: программа зависнет, и пользователь не поймёт причину.

06Ограничения целостности

Ограничения это правила, которые база проверяет сама. Программа может забыть проверить поле, ручной запрос может обойти код, но ограничение сработает в обоих случаях.

Начнём с внешнего ключа. По умолчанию SQLite не проверяет его, даже если он объявлен в схеме. Это историческое решение для совместимости. Включать проверку нужно для каждого соединения.

conn.execute("PRAGMA foreign_keys = ON")

try:
    conn.execute(
        "INSERT INTO stock (warehouse_id, product_id, qty) VALUES (1, 99999, 5)"
    )
except sqlite3.IntegrityError as error:
    print("внешний ключ:", error)

внешний ключ: FOREIGN KEY constraint failed

Товара с идентификатором 99999 нет, поэтому вставка отклонена. Если убрать PRAGMA, строка с несуществующим товаром попадёт в таблицу, и отчёт по остаткам начнёт ссылаться на пустое место. Ошибка проявится позже и в другом месте, что всегда дороже.

Проверить, включена ли проверка, можно запросом.

print(conn.execute("PRAGMA foreign_keys").fetchone())

(1,)

Единица означает, что проверка включена. Ноль означает, что внешние ключи игнорируются.

Ограничение UNIQUE тоже проверяется базой.

try:
    conn.execute(
        "INSERT INTO products (sku, title, category_id) VALUES ('SKU-1000', 'Дубль', 1)"
    )
except sqlite3.IntegrityError as error:
    print("уникальность:", error)

уникальность: UNIQUE constraint failed: products.sku

Артикул SKU-1000 уже существует, поэтому вставка отклонена. Без ограничения в базе появились бы два товара с одним артикулом, и остаток разделился бы между ними.

CHECK проверяет условие на строку. NOT NULL проверяет наличие значения. Внешний ключ проверяет существование родительской строки. Вместе они образуют тот минимум, который защищает данные от случайной порчи.

Поведение при удалении родительской строки задают через ON DELETE. По умолчанию это NO ACTION: удаление категории, на которую ссылаются товары, будет отклонено. Вариант CASCADE удаляет дочерние строки вместе с родительской. Для справочника категорий CASCADE опасен: одна команда удалит товары. Для строк заказа, наоборот, каскад уместен. Выбор зависит от смысла связи, а не от удобства.

Отложенная проверка DEFERRABLE INITIALLY DEFERRED позволяет нарушить внешний ключ внутри транзакции и восстановить согласованность до COMMIT. Это нужно при переносе данных, когда родитель и потомок вставляются в неудобном порядке. В обычной работе достаточно немедленной проверки.

07Типы, даты и деньги

SQLite использует гибкую типизацию. Объявленный тип столбца задаёт сходство, но не запрещает хранить значение другого вида. В столбец INTEGER можно записать строку '48', и база попытается преобразовать её к числу. Если преобразование невозможно, значение сохранится как текст.

Такое поведение удобно при импорте, но опасно для расчётов. Строгий режим включается словом STRICT в объявлении таблицы.

CREATE TABLE stock_strict (
    warehouse_id INTEGER NOT NULL,
    product_id   INTEGER NOT NULL,
    qty          INTEGER NOT NULL CHECK (qty >= 0),
    PRIMARY KEY (warehouse_id, product_id)
) STRICT;

В строгой таблице тип проверяется при вставке: строка 'сорок' и дробь 48.5 будут отклонены, а '48' по-прежнему станет целым 48, потому что такое преобразование не теряет данные. Для новой схемы лучше выбирать STRICT, а старые таблицы оставлять как есть, если их читает несколько программ.

Дат в SQLite нет отдельного типа. Их хранят строкой в формате ISO 8601 (2026-10-05) или целым числом секунд. Строка удобна для чтения и сортировки, но требует единого формата. Если одна программа пишет 05.10.2026, а другая 2026-10-05, сравнение и сортировка дадут неверный результат. Договор о формате даты так же важен, как договор о формате CSV.

Деньги нельзя хранить в REAL. Двоичная дробь не представляет копейки точно, и сумма из тысяч строк накопит расхождение. В учебном проекте цену хранят целым числом копеек или строкой с фиксированной точностью и преобразуют в Decimal на границе приложения. В SQLite для денег чаще выбирают целое число копеек: сложение и сравнение работают точно.

Логические значения хранят как 0 и 1 в столбце INTEGER. Отдельного типа BOOLEAN нет, но CHECK (flag IN (0, 1)) делает правило явным.

08SQLite из C

В .NET для SQLite используют пакет Microsoft.Data.Sqlite. Код открывает соединение, создаёт команду с параметрами и читает результат.

using Microsoft.Data.Sqlite;

using var connection = new SqliteConnection("Data Source=.../sklad-plus/data/sklad.db");
connection.Open();

using var command = connection.CreateCommand();
command.CommandText = """
    SELECT w.title, SUM(s.qty)
    FROM stock AS s
    JOIN warehouses AS w ON w.id = s.warehouse_id
    GROUP BY w.title
    ORDER BY SUM(s.qty) DESC
    """;

using var reader = command.ExecuteReader();
while (reader.Read())
{
    Console.WriteLine($"{reader.GetString(0)}: {reader.GetInt64(1)}");
}

Параметры задаются через command.Parameters.AddWithValue("@id", value), а не склейкой строки. Склейка открывает путь для SQL-инъекции и ломается на апострофе в названии товара. В Python для того же служат знаки вопроса в запросе и кортеж значений вторым аргументом execute.

Строка подключения Data Source=... указывает на файл. Если файла нет, SQLite создаст пустую базу. Это удобно для первого запуска и опасно при опечатке в пути: программа молча создаст новую пустую базу вместо существующей. Проверяйте путь до открытия соединения.

09Где SQLite ломается

Забытый PRAGMA foreign_keys. Симптом: в дочерней таблице появляются ссылки на несуществующие строки. Причина: проверка выключена по умолчанию. Лечение: включать при каждом соединении и проверять значение.

Долгая транзакция. Симптом: database is locked у других программ. Причина: писатель держит блокировку, пока ждёт пользователя или сеть. Лечение: короткие транзакции и busy_timeout.

Отсутствие индекса на внешнем ключе. Симптом: удаление категории или отчёт по площадке выполняется заметно дольше. Причина: проверка дочерних строк и соединение идут полным просмотром. Лечение: индекс по столбцу внешнего ключа.

Деньги в REAL. Симптом: сумма отчёта отличается на копейки. Причина: двоичная погрешность. Лечение: целое число копеек или Decimal на границе.

Разные форматы даты. Симптом: часть операций не попадает в отчёт за месяц. Причина: строки 05.10.2026 и 2026-10-05 сравниваются как текст. Лечение: единый ISO 8601 и проверка при вставке.

Копирование файла во время записи. Симптом: копия базы не открывается или теряет последние изменения. Причина: файл скопирован без учёта журнала. Лечение: команда .backup или API резервного копирования, а не копирование средствами проводника.

База на сетевой папке. Симптом: случайные ошибки блокировки и повреждение файла. Причина: блокировки SQLite рассчитаны на локальную файловую систему. Лечение: хранить файл локально, а общий доступ строить через сервер приложений.

Общее соединение между потоками. Симптом: ошибка SQLite objects created in a thread can only be used in that same thread. Причина: одно соединение передано в другой поток. Лечение: отдельное соединение на поток или явная настройка, если библиотека её поддерживает.

AUTOINCREMENT без необходимости. Симптом: лишняя служебная таблица и замедление вставки. Причина: ключевое слово добавлено по привычке. Лечение: INTEGER PRIMARY KEY достаточно, если не требуется гарантия, что идентификатор никогда не будет повторно использован.

Хранение больших файлов в базе. Симптом: база растёт до гигабайтов и медленно копируется. Причина: сканы накладных записаны в BLOB. Лечение: хранить файлы отдельно, а в базе держать путь и контрольную сумму.

10Итоги

  • SQLite это библиотека, а не сервер: вся база лежит в одном файле, а приложение работает с ней через модуль или пакет.
  • Схема хранится в sqlite_master и читается обычным запросом, включая автоматические индексы ограничений.
  • Индекс меняет план с SCAN на SEARCH, ускоряет чтение и замедляет запись, поэтому его создают под конкретный запрос.
  • Транзакция применяет все изменения или ни одного, а with conn откатывает работу при нарушении ограничения.
  • Внешние ключи включаются командой PRAGMA foreign_keys = ON для каждого соединения.
  • Ограничения PRIMARY KEY, UNIQUE, NOT NULL, CHECK и REFERENCES защищают данные от ошибок любой программы.
  • Даты хранят в едином формате ISO 8601, деньги в целом числе копеек, а большие файлы держат вне базы.

01Чем SQLite отличается от серверной СУБД?

SQLite встраивается в программу и не требует отдельного процесса.

02Что делает команда PRAGMA foreign_keys = ON?

Проверка внешних ключей в SQLite по умолчанию выключена.

03Какие признаки указывают на долгую транзакцию?

Писатель блокирует других писателей на всё время транзакции.

04Зачем создают индекс по столбцу внешнего ключа?

Индекс ускоряет поиск дочерних строк по значению ключа.

05Как называется ограничение, которое запрещает повторение значения в столбце?

UNIQUE создаёт автоматический индекс и не даёт записать дубль.

06Что означает SCAN products в плане запроса?

SCAN показывает перебор строк без использования индекса.

07Что делает режим WAL?

Читатели видят прежнюю версию, пока новая не зафиксирована.

08Какие правила помогают хранить даты и деньги без расхождений?

Единый формат даты и точное представление денег убирают расхождения.

09Какое свойство транзакции означает «всё или ничего»?

Атомарность не позволяет применить часть изменений.

10Где хранится описание схемы базы SQLite?

Схема является данными и читается запросом к sqlite_master.

11Какая команда включает проверку внешних ключей в SQLite?

Команду выполняют для каждого соединения, потому что по умолчанию проверка выключена.

12Что произойдёт при нарушении CHECK внутри блока with conn?

Контекстный менеджер откатывает транзакцию при исключении.

13Какие ограничения проверяет сама база SQLite?

База проверяет объявленные ограничения, а не смысл данных.

14Что произойдёт, если открыть соединение с несуществующим файлом базы?

Поэтому путь к файлу проверяют до открытия.

15Почему деньги не стоит хранить в столбце REAL?

Для точных сумм используют целое число копеек или Decimal.
