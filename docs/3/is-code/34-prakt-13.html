03Краткие теоретические сведения

Вход в систему состоит из двух разных действий. Аутентификация проверяет, кто пришёл: логин и пароль должны совпасть с учётной записью. Авторизация решает, что этому пользователю разрешено: кладовщик создаёт приёмку на своей площадке, менеджер смотрит отчёты, администратор меняет роли. Смешивать их нельзя: верный пароль не даёт прав на любую операцию.

Пароль не хранят в открытом виде. В базе лежит хеш, полученный медленной функцией с солью. Соль делает одинаковые пароли разными, а большое число итераций удорожает перебор. Для проверки берут введённый пароль, повторяют вычисление с сохранённой солью и сравнивают результат за постоянное время. Функция hmac.compare_digest не выдаёт по времени, на каком символе строки произошло расхождение.

Число итераций выбирают так, чтобы одна проверка занимала заметное, но приемлемое время. Сто двадцать тысяч итераций SHA-256 на учебном компьютере дают около шестидесяти миллисекунд, и вход остаётся быстрым. Увеличение до миллиона замедлит и вход, и перебор, поэтому значение подбирают под оборудование и фиксируют в формате хеша. Если число итераций хранится рядом с солью, старые хеши можно пересчитать постепенно, не сбрасывая пароли всем пользователям.

Открытый пароль не должен попадать ни в журнал, ни в текст ошибки, ни в тело ответа. Даже при отладке достаточно вывести логин и результат проверки. Это правило понадобится на следующем занятии, когда в сервис добавят журнал событий.

После успешного входа сервер выдаёт токен. Подписанный токен содержит идентификатор пользователя и срок действия, а подпись не даёт изменить содержимое. Клиент присылает токен в заголовке Authorization: Bearer <токен>. Сервер проверяет подпись и срок, затем берёт пользователя из токена. Пароль при каждом запросе не передают.

Токен отличается от серверной сессии. Сессия хранится на сервере, а клиент носит только её идентификатор; отозвать такую сессию легко, достаточно удалить запись. Подписанный токен хранит данные у клиента, и сервер не помнит о его выдаче. Поэтому срок жизни токена делают коротким, а для немедленного запрета доступа проверяют признак блокировки в базе. В учебном сервисе достаточно срока в тридцать минут и проверки пользователя по идентификатору из токена.

Валидация полей отвечает за то, чтобы в базу не попало значение, которое нарушает контракт. Проверяют обязательность, тип, формат, диапазон и допустимый список значений. Нарушения собирают в список и возвращают с кодом 400. У каждого нарушения есть имя поля, машинный код и текст для человека. Клиент подсвечивает поле по имени, не разбирая сообщение.

Коды ответа разделяют причины отказа. 400 означает неверные данные клиента, 401 отсутствующий или неверный токен, 403 запрет для известного пользователя, 409 конфликт с существующей записью. Если смешать эти коды, клиент не поймёт, исправлять данные, входить заново или обращаться к администратору.

Хеш считают один раз при создании учётной записи, а не при каждом входе. Ниже функции на Python, которые понадобятся и в скрипте заполнения, и в маршруте входа. Формат строки включает имя алгоритма, число итераций и соль, поэтому его можно проверить без дополнительных колонок.

import hashlib
import hmac
import secrets

ITERATIONS = 120_000


def hash_password(password: str) -> str:
    salt = secrets.token_hex(16)
    digest = hashlib.pbkdf2_hmac(
        "sha256", password.encode("utf-8"), bytes.fromhex(salt), ITERATIONS
    )
    return f"pbkdf2_sha256${ITERATIONS}${salt}${digest.hex()}"


def verify_password(password: str, stored: str) -> bool:
    algorithm, iterations, salt, expected = stored.split("$")
    if algorithm != "pbkdf2_sha256":
        return False
    digest = hashlib.pbkdf2_hmac(
        "sha256", password.encode("utf-8"), bytes.fromhex(salt), int(iterations)
    )
    return hmac.compare_digest(digest.hex(), expected)

Проверка функций на одном пароле даёт такой результат:

формат: pbkdf2_sha256$120000$32a3acf88...
верный пароль: True
неверный пароль: False
другая соль: True

Шаг 2. Реализуйте проверку пары логин и пароль

Маршрут входа принимает JSON с полями login и password. Сервер ищет пользователя по логину, проверяет пароль и только потом смотрит на блокировку. Такой порядок не даёт отличить заблокированную запись от несуществующей, если пароль неверен: обе получают 401.

Шаг 3. Выдайте подписанный токен

Токен собирают из идентификатора пользователя и роли. Срок действия задают при проверке, а не при выдаче: один и тот же токен можно принимать 30 минут или 8 часов в зависимости от настроек маршрута. Секрет подписи берут из переменной окружения, а не из исходного кода. Перед запуском задайте SKLAD_SECRET; без этой переменной приложение не стартует.

import os
from itsdangerous import BadSignature, SignatureExpired, URLSafeTimedSerializer

SECRET = os.environ["SKLAD_SECRET"]
serializer = URLSafeTimedSerializer(SECRET, salt="sklad-plus-auth")


def issue_token(user):
    return serializer.dumps({"user_id": user["id"], "role": user["role"]})


def read_token(token, max_age=1800):
    try:
        return serializer.loads(token, max_age=max_age)
    except SignatureExpired:
        return None
    except BadSignature:
        return None

URLSafeTimedSerializer кладёт в токен время выдачи и подпись. При проверке max_age сравнивает текущее время с временем выдачи. Просроченный токен и токен с изменённой подписью дают None, и маршрут отвечает 401.

Проверьте три случая: свежий токен принимается, токен с изменённым последним символом отклоняется, токен старше срока отклоняется. Для третьего случая можно временно вызвать read_token(token, max_age=1) и подождать две секунды, не меняя код приложения.

Шаг 4. Закройте маршрут проверкой токена

Закрытый маршрут не должен повторять разбор заголовка в каждом обработчике. Проверку выносят в декоратор, который кладёт данные пользователя в g и вызывает исходную функцию только после успешной проверки.

from functools import wraps
from flask import g, jsonify, request


def require_token(view):
    @wraps(view)
    def wrapper(*args, **kwargs):
        header = request.headers.get("Authorization", "")
        if not header.startswith("Bearer "):
            return jsonify({"error": "unauthorized", "message": "Нужен токен"}), 401
        payload = read_token(header.removeprefix("Bearer ").strip())
        if payload is None:
            return jsonify({"error": "unauthorized", "message": "Токен неверен или истёк"}), 401
        g.user = payload
        return view(*args, **kwargs)

    return wrapper

Подключите декоратор к маршруту списка остатков. Запрос без заголовка получает 401, запрос с рабочим токеном получает 200 и данные. Проверьте оба ответа и запишите их в таблицу сценариев.

HTTP 401 {'error': 'unauthorized', 'message': 'Нужен токен'}
HTTP 200 {'user_id': 1, 'rows': 4800}

Добавьте проверку роли: список остатков доступен кладовщику и менеджеру, а изменение ролей только администратору. Если роль не подходит, верните 403 с кодом forbidden. Роль берут из токена, а не из тела запроса, иначе клиент сможет назвать себя кем угодно.

Разделяйте два отказа. 401 означает, что сервер не знает, кто пришёл: заголовка нет, подпись неверна или срок истёк. 403 означает, что пользователь известен, но операция ему запрещена. Клиент по коду понимает, что делать: получить новый токен или прекратить попытки. Если на запрет роли отвечать 401, клиент зациклится на повторном входе.

Шаг 6. Верните 400 со списком полей

Маршрут создания приёмки сначала вызывает валидатор, потом сохраняет запись. Если список ошибок не пуст, запись не сохраняется вообще: ни одна строка из документа не попадает в базу. Ответ содержит общий код ошибки и массив нарушений.

@app.post("/api/acceptance")
@require_token
def acceptance():
    data = request.get_json(silent=True) or {}
    errors = validate_position(data)
    if errors:
        return jsonify({"error": "validation_failed", "fields": errors}), 400
    return jsonify({"status": "created", "sku": data["sku"].strip().upper()}), 201

Проверка неверной позиции даёт такой ответ:

HTTP 400 {'error': 'validation_failed', 'fields': [{'field': 'sku', 'code': 'format', 'message': 'Артикул вида SKU-1001'}, {'field': 'qty', 'code': 'range', 'message': 'Количество от 1 до 10000'}, {'field': 'site', 'code': 'choice', 'message': 'Площадка: Москва, Тверь, Тула или Калуга'}]}

Обратите внимание, что сервер вернул три нарушения сразу, а не остановился на первом. Проверьте, что при пустом списке ошибок запись сохраняется и ответ имеет код 201. Отдельно проверьте, что при неверном поле в базу не добавилось ни одной строки: сравните количество записей до и после запроса.

Сохранение документа выполняйте одной транзакцией. Если приёмка состоит из нескольких позиций и одна из них не прошла проверку, не должно остаться половины документа. Сначала проверяются все позиции, затем одной операцией записываются все строки и только после успешной записи фиксируется результат. При ошибке транзакция откатывается, и база остаётся в прежнем состоянии.

08Критерии оценки

Оценка выставляется по шкале от 1 до 5. - 5: вход проверяет пару логин и пароль, пароли хранятся в виде хеша с солью, токен подписан и имеет срок, закрытый маршрут возвращает 401 без токена и 200 с токеном, все поля приёмки проверены, ответ 400 содержит имена полей и коды, восемь сценариев прогнаны и записаны. - 4: работа выполнена полностью, но одно поле проверено не по всем правилам, в таблице сценариев не хватает одного случая или не проверен срок действия токена. - 3: вход работает, но пароль сравнивается без хеша или без соли, токен не проверяется на срок, ответ 400 содержит общий текст без имён полей, часть сценариев не прогнана. - 2: работа не выполнена. - 1: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
