01Цель работы

Провести рецензию пул-реквеста в учебном проекте sklad-plus, найти дефект, которого не заметили тесты, и оставить замечания так, чтобы автор мог исправить их без переписки. После исправления собрать релизную версию приложения и проверить артефакт в отдельной папке.

Результат работы это заполненная рецензия с решением по пул-реквесту, подтверждение исправления и файл sklad-plus-1.0.0.pyz с контрольной суммой. Рецензия показывает ход проверки, а не только итоговую оценку «одобрить» или «отклонить».

Работа идёт в двух ролях. Сначала вы рецензент: читаете diff, запускаете тесты, проверяете границы и формулируете замечания. Затем вы автор релиза: применяете исправление, собираете артефакт и проверяете, что он запускается на чистой папке. Обе роли нужны, потому что рецензия без проверки исправления и сборка без проверки артефакта оставляют риск.

Материалы к работе · скачать и приступить Шаблон отчёта · DOCX Данные и шаблоны · ZIP

Шаблон отчёта заполняется по ходу работы. В архиве сырые данные каталога, поставок и журнала, готовых решений нет.

02Оборудование и программное обеспечение

  • Персональный компьютер с Python 3.11 или новее.
  • Git версии 2.28 или новее.
  • VS Code с расширением Python и встроенным терминалом.
  • Пакет pytest, установленный в виртуальное окружение проекта.
  • .NET SDK 10 и Visual Studio 2022 с рабочей нагрузкой .NET desktop для сборки C#-части.
  • Текстовый редактор для отчёта, например Word или LibreOffice Writer.

Внешние архивы и готовые шаблоны не нужны. Ветка с пул-реквестом, файлы проекта и данные для проверки приведены в тексте. Все команды выполняются в терминале из корня проекта .../sklad-plus.

03Краткие теоретические сведения

Пул-реквест это предложение слить изменения рабочей ветки в общую. Он содержит описание задачи, список коммитов, изменённые файлы и diff. Рецензент читает diff, сверяет изменение с критериями приёмки, запускает тесты и оставляет замечания. Решение бывает трёх видов: одобрить, запросить изменения или оставить комментарий без решения.

Замечание должно быть применимым. В нём указывают файл и строку, уровень серьёзности, что происходит, почему это проблема и что сделать. Уровни помогают автору понять, что обязательно, а что можно обсудить. Блокирующее замечание связано с дефектом, потерей данных, обходом прав или неверным расчётом. Nit это необязательная мелочь.

Релизная сборка отличается от запуска из рабочей папки. В рабочей папке рядом лежат .env, локальная база, кеш и тесты. В релизный артефакт должны попасть только файлы приложения и его зависимости. Артефакт проверяют в отдельной папке, где нет исходников, и сравнивают контрольную сумму с записью в релизной заметке.

Контрольная сумма это значение, вычисленное по содержимому файла. Если файл изменился хотя бы на один байт, сумма тоже изменится. Она не доказывает, что файл безопасен, но показывает, что на сервер поехала именно собранная версия, а не другая копия.

Diff читают в три прохода. Сначала смотрят список файлов и размер изменения: не появилось ли файла, которого не должно быть. Затем читают описание и коммиты: совпадает ли заявленная цель с тем, что видно в строках. Только после этого разбирают отдельные фрагменты и открывают файл целиком, чтобы увидеть функцию в контексте.

Элемент diff Что означает На что смотреть
diff --git a/... b/... начало блока файла неожиданный файл в списке
@@ -7,7 +7,7 @@ фрагмент начинается с седьмой строки сколько строк затронуто
строка с минусом было в базовой версии что удалили и зачем
строка с плюсом стало в новой версии что добавили и как это работает
строка без знака контекст вокруг изменения в какой функции находится правка

Замечание без уровня серьёзности автор понимает как требование. Если рецензент написал «переименуй переменную», автор может решить, что без этого пул-реквест не примут, и потратит время на мелочь. Уровень снимает неопределённость: блокирующее исправляют обязательно, nit обсуждают по желанию.

Решение по пул-реквесту принимают по критериям приёмки, а не по количеству комментариев. Пул-реквест может содержать десять замечаний о стиле и ни одного дефекта: тогда его одобряют, а стиль правят отдельно. Обратная ситуация опаснее: одно блокирующее замечание при десяти одобрениях всё равно требует изменений.

Шаг 1. Прочитайте описание и diff пул-реквеста

Шаг 2. Запустите тесты и найдите непроверенный случай

Установите зависимости и запустите набор:

python -m pytest -q

..                                                                       [100%]
2 passed in 0.01s

Оба теста проходят. Это не значит, что код правильный: тесты проверяют только те случаи, которые в них записаны. Посмотрите на новый тест и определите, какой параметр в нём равен нулю.

Подробный прогон показывает имена проверок:

python -m pytest -v

tests/test_stock.py::test_available_is_stock_minus_reserved PASSED       [ 50%]
tests/test_stock.py::test_reserve_reduces_stock PASSED                   [100%]

Имя test_reserve_reduces_stock обещает проверку уменьшения остатка, но вход 40, 0, 10 не содержит резерва. Такой тест проходит и на правильной, и на сломанной функции, потому что при нулевом резерве оба варианта дают одинаковый результат. Это не проверка поведения, а подтверждение одного удачного примера.

Заполните таблицу проверок. Первая строка дана как образец, остальные добавьте сами: удачный случай, нулевой резерв, резерв больше нуля, запрос больше свободного остатка.

Проверка Вход Ожидаемый результат Фактически
Остаток без резерва 40, 0, 10 30 30

Сформулируйте, почему зелёный набор не доказывает сохранение поведения. Ответ должен опираться на конкретный вход, а не на общее утверждение «тесты неполные».

Шаг 3. Проверьте граничные значения вручную

Запустите функцию на двух наборах, где резерв больше нуля. Первый запрос больше свободного остатка, второй меньше.

python -c "from src.stock import reserve; print(reserve(40, 30, 25))"
python -c "from src.stock import reserve; print(reserve(40, 30, 5))"

reserve: stock=40, requested=25
15
reserve: stock=40, requested=5
35

На складе 40 перфораторов, 30 уже зарезервированы, свободно 10. Первый вызов должен завершиться ошибкой, потому что 25 больше 10. Второй должен вернуть 5, потому что после резервирования пяти единиц из десяти свободных остаётся пять.

Заполните таблицу наблюдений.

Вход Свободно Ожидалось Получено Вывод
40, 0, 10 40 30 30

Сравните ожидание и факт. Если расхождение есть, дефект подтверждён. Запишите, в какой строке функции он находится и какое выражение нужно изменить. Пока не исправляйте код: на этом шаге вы только собираете доказательства для рецензии.

Шаг 4. Пройдите по чек-листу

Проверьте пул-реквест по списку. В столбце результата поставьте «да», «нет» или «не проверено», в последнем столбце запишите конкретное наблюдение. Первая строка дана как образец.

Пункт Что проверить Результат Наблюдение
Соответствие задаче все критерии приёмки выполнены
Размер изменения не больше 400 строк, одна задача 3 файла, +10 -4 правки по теме
Границы расчёта нулевой резерв, резерв больше нуля, нехватка
Обработка ошибок понятный тип и сообщение
Тесты есть проверка, которая упадёт при дефекте
Отладочный вывод нет print, console.log, временных файлов
Секреты нет паролей, токенов, строк подключения
Читаемость понятные имена, одна ответственность функции
Документация описание соответствует поведению

Чек-лист не заменяет чтение кода. Он напоминает, что проверить, но решение принимает рецензент. Если пункт нельзя проверить по diff, откройте файл целиком или запустите программу.

Пункты идут от риска к оформлению. Соответствие задаче и границы расчёта важнее читаемости, потому что дефект в расчёте меняет данные, а неудачное имя только затрудняет чтение. Отладочный вывод и секреты проверяют до слияния: после слияния print попадёт в журнал сервера, а токен останется в истории.

Если пункт чек-листа вызывает сомнение, запишите вопрос, а не догадку. «Не проверено, нужен запуск с резервом больше нуля» полезнее, чем «вроде нормально». Автор увидит, что именно осталось проверить, и не будет считать рецензию формальной.

Шаг 5. Оставьте замечания

Каждое замечание оформляйте по шаблону. Шаблон нужен, чтобы автор видел место, причину и направление правки.

Файл и строка:
Уровень: блокирующее / серьёзное / незначительное / nit
Что происходит:
Почему это проблема:
Что сделать:

Ниже пример замечания, которое не относится к дефекту и показывает форму. Оно не заменяет ваши замечания по существу.

README.md:5, nit: строка описывает функцию, но не показывает пример вызова.
Не блокирует. Можно добавить один пример reserve(40, 0, 10).

Подготовьте не меньше трёх замечаний: одно блокирующее по расчёту, одно по тестам и одно по отладочному выводу или документации. Заполните таблицу.

Файл и строка Уровень Что происходит Почему проблема Что сделать

Проверьте формулировки. В замечании не должно быть оценки личности автора, слов «ужасно», «опять», «никто так не пишет». Вместо них укажите строку, входные данные и ожидаемое поведение.

Плохая формулировка Что с ней не так Как переписать
«Тут всё сломано» нет места и причины «src/stock.py:11, при 40, 30 и 25 возвращается 15 вместо ошибки»
«Зачем этот print?» вопрос без направления «src/stock.py:10, незначительное: вывод останется в журнале, убрать»
«Тесты не проверяют ничего» оценка без факта «tests/test_stock.py:9, вход с нулевым резервом не ловит дефект»
«Переделай по-нормальному» нет критерия готовности «Указать, какое значение сравнивается с запросом и что возвращается после проверки»

Формулировка должна позволять проверить исправление. Если после правки нельзя запустить конкретный вход и увидеть ожидаемый результат, замечание сформулировано расплывчато.

Шаг 6. Примите решение по пул-реквесту

Рецензия заканчивается решением. Одобрять пул-реквест с блокирующим дефектом нельзя, даже если тесты зелёные. Запросить изменения можно и при одном блокирующем замечании: остальные замечания автор исправит по желанию.

Решение Когда выбирают Что сообщают автору
Одобрить блокирующих замечаний нет, проверки прошли что проверено и что можно улучшить
Запросить изменения есть дефект, потеря данных, слабый тест список блокирующих пунктов
Комментировать вопрос или обсуждение без решения вопрос и контекст

Запишите выбранное решение и обоснование на три-пять предложений. В обосновании должны быть критерий приёмки, который нарушен, и входные данные, на которых это видно.

Ошибка рецензента Симптом Как исправить
Одобрение по зелёным тестам дефект доходит до пользователя проверить границы вручную
Поток придирок автор правит стиль, дефект остаётся сначала расчёт и данные
Замечание без строки переписка вместо правки указать файл и строку
Оценка автора конфликт вместо разбора говорить о коде и данных
Проверка после слияния замечание некуда применить проверять до слияния

Рецензия не должна заканчиваться словами «вроде нормально». Решение формулируют явно: что проверено, что осталось, что блокирует слияние. Автор должен понять, можно ли сливать ветку сейчас или нужно внести правку.

Шаг 7. Проверьте исправление автора

Автор исправил функцию и добавил два теста: на нехватку свободного остатка и на границу, когда запрос равен свободному остатку. В ветке появился новый коммит Исправить расчёт свободного остатка. Проверьте только то, что изменилось после ваших замечаний, и повторите проверки.

Ожидаемое поведение после исправления:

reserve(40, 30, 25) -> ValueError
reserve(40, 30, 5) -> 5
pytest -q -> 4 passed

Запустите тесты и оба вызова. Заполните таблицу повторной проверки.

Замечание Что изменилось Проверка Результат

Если после исправления появились новые изменения, не связанные с замечаниями, попросите вынести их в отдельный пул-реквест. Рецензия не должна разрастаться до размера исходной задачи.

Шаг 8. Соберите релизную версию

Соберите Python-часть в один файл. Сначала подготовьте папку build/app и положите в неё только файлы приложения: app.py и stock.py. Не копируйте .env, sklad.db, tests, __pycache__ и .venv: они не должны попасть в артефакт.

Файл app.py для сборки печатает версию и свободный остаток:

from stock import available


def main() -> None:
    print("sklad-plus 1.0.0")
    print("Свободный остаток:", available(4800, 1200))


if __name__ == "__main__":
    main()

Соберите архив командой zipapp. Она упаковывает каталог в исполняемый файл .pyz, а флаг -m задаёт точку входа.

python -m zipapp build/app -m "app:main" -o dist/sklad-plus-1.0.0.pyz -c

Флаг -c сжимает содержимое. Проверьте состав архива, чтобы в нём не оказалось лишнего:

python -m zipfile -l dist/sklad-plus-1.0.0.pyz

File Name                                             Modified             Size
app.py                                         2026-10-31 11:41:56          191
stock.py                                       2026-10-31 11:41:56           85
__main__.py                                    2026-10-31 11:42:04           46

Размеры зависят от содержимого файлов, поэтому сравнивать нужно список имён, а не число байтов. В архиве должны быть только файлы приложения и точка входа.

Вычислите контрольную сумму:

Get-FileHash dist/sklad-plus-1.0.0.pyz -Algorithm SHA256

Для C#-части выполните публикацию в конфигурации Release. Команда создаёт папку с готовыми файлами, которые можно перенести на другую машину без исходного проекта.

dotnet publish src/SkladPlus.Api -c Release -o dist/api

Проверьте, что в dist/api есть сборка приложения, файл настроек и зависимости. Заполните таблицу артефактов.

Артефакт Команда сборки Что проверить
sklad-plus-1.0.0.pyz
dist/api

Шаг 9. Проверьте артефакт на чистой папке

Создайте папку .../release-check и скопируйте туда только файл sklad-plus-1.0.0.pyz. Запустите его из этой папки:

python sklad-plus-1.0.0.pyz

sklad-plus 1.0.0
Свободный остаток: 3600

Приложение не должно искать файлы в рабочей папке проекта. Если запуск требует .env, базы или тестов, артефакт собран неверно: в него попали не все зависимости или он зависит от окружения разработчика.

Симптом Вероятная причина Что сделать
ModuleNotFoundError зависимость не попала в сборку добавить пакет или собрать с зависимостями
архив содержит __pycache__ сборка из рабочей папки собрать из чистой build/app
архив содержит .env файл лежал рядом с кодом убрать из папки сборки и сменить секрет
вывод отличается от ожидаемого собрана другая версия кода проверить коммит и хэш
сумма не совпадает файл изменён или повреждён пересобрать и сравнить заново

Проверьте, что в архиве нет секретов и лишних файлов. Команда python -m zipfile -l показывает список, а Get-FileHash подтверждает, что файл не изменился при копировании. Сравните сумму с той, что записана после сборки.

Шаг 10. Оформите рецензию и релизную заметку

Соберите документ рецензии по структуре: номер пул-реквеста, автор, ветка, что проверено, таблица замечаний, решение, подтверждение исправления. В отдельном разделе опишите релиз: версию, дату, коммит, команду сборки, состав артефакта и контрольную сумму.

Релизная заметка отвечает на вопросы, которые возникнут при переносе. Что изменилось в версии 1.0.0? Какие зависимости нужны? Как проверить, что артефакт не повреждён? Что делать, если приложение не запускается? Ответы должны быть короткими и проверяемыми.

Поле заметки Что записать Зачем
Версия 1.0.0 связать артефакт с изменением
Дата и коммит дата сборки и короткий хэш найти исходное состояние
Изменения что вошло в версию понять, что проверять
Зависимости файл замка и версия Python повторить окружение
Артефакт имя файла и контрольная сумма проверить целостность
Проверка команда запуска и ожидаемый вывод убедиться, что работает

Релизная заметка не пересказывает весь пул-реквест. В ней только то, что нужно для установки и проверки. Подробности остаются в рецензии и истории коммитов.

05Требования к отчёту

Отчёт оформляется в Word или LibreOffice Writer на 5-7 страниц. В нём должны быть цель работы, описание пул-реквеста, таблица разбора файлов, результаты прогона тестов, таблица граничных значений, чек-лист, замечания с уровнями, решение по пул-реквесту и подтверждение исправления.

Отдельный раздел отведите релизной сборке: команды, состав артефакта, контрольная сумма и проверка запуска в чистой папке. Приложите снимок списка файлов архива и снимок запуска, на котором видны версия приложения и свободный остаток.

06Что сдать

  • заполненную рецензию пул-реквеста с тремя замечаниями и решением;
  • таблицу проверки граничных значений с ожидаемым и фактическим результатом;
  • подтверждение исправления: прогон тестов и два вызова функции;
  • файл sklad-plus-1.0.0.pyz и его контрольную сумму;
  • релизную заметку с версией, составом артефакта и порядком проверки;
  • отчёт на 5-7 страниц с таблицами и снимками проверки.

08Критерии оценки

Оценка выставляется по шкале от 1 до 5.

  • 5: дефект найден по diff и подтверждён граничным входом; замечания содержат файл, строку, уровень, причину и предложение; решение по пул-реквесту обосновано критерием приёмки; исправление проверено тестами; релизный артефакт собран из чистых файлов, запускается вне проекта, содержит только нужные файлы, контрольная сумма совпадает; отчёт полный.
  • 4: дефект найден и исправление проверено, но одно замечание сформулировано без строки или уровня; артефакт собран и запускается, однако состав архива проверен не полностью.
  • 3: дефект найден чтением кода, но не подтверждён граничным входом; замечания описывают проблему общими словами; релизная сборка выполнена, но артефакт не проверен в отдельной папке или содержит лишние файлы.
  • 2: работа не выполнена или рецензия не содержит решения по пул-реквесту.
  • 1: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
