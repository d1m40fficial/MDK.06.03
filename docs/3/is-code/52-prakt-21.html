01Цель работы

Спроектировать базу индивидуального проекта по заявке: выделить четыре-шесть таблиц, назначить первичные и внешние ключи, добавить ограничения и справочники. Затем создать базу скриптом, заполнить справочники и тестовых пользователей, реализовать вход с хешированием пароля и проверить его на верных, неверных и заблокированных учётных записях.

Результат работы это schema.sql, скрипт заполнения, модуль src/auth.py, заполненная таблица проверок входа и протокол проверки ограничений. Схема и вход считаются готовыми не тогда, когда таблицы существуют, а тогда, когда база создаётся с нуля, ограничения отклоняют неверные данные, а вход различает успех и отказ.

03Краткие теоретические сведения

Схема базы это описание таблиц, полей, ключей и связей. Сущность из заявки становится таблицей, атрибут становится полем, связь между сущностями становится внешним ключом. Схема отвечает не только на вопрос «где лежат данные», но и на вопрос «какие данные допустимы».

Первичный ключ уникально определяет строку. В учебном проекте удобен суррогатный ключ id INTEGER PRIMARY KEY AUTOINCREMENT: он не зависит от предметных значений и не меняется при переименовании. Естественный ключ, например инвентарный номер, тоже может быть уникальным, но его изменение ломает связи.

Внешний ключ связывает строку с записью другой таблицы. Он не даёт создать выдачу для несуществующего оборудования и не даёт удалить категорию, на которую ссылаются товары. Внешний ключ защищает связь на уровне базы, а не на уровне интерфейса, поэтому работает и для программы, и для ручного запроса.

Ограничения описывают допустимые значения. NOT NULL требует значение, UNIQUE запрещает дубли, CHECK задаёт диапазон или список, DEFAULT подставляет значение по умолчанию. Чем больше правил записано в схеме, тем меньше способов записать мусор остаётся у любой программы.

Ограничение Что защищает Пример нарушения
PRIMARY KEY уникальность строки повтор того же id
UNIQUE уникальность логина или номера второй пользователь с тем же логином
NOT NULL обязательное значение пустое название
CHECK диапазон или список значений отрицательная цена
FOREIGN KEY ссылку на существующую запись выдача для удалённого оборудования

Справочник это небольшая таблица с устойчивым набором значений: категории, статусы, единицы измерения. Справочник выносят отдельно, чтобы не хранить один и тот же текст в каждой строке и чтобы опечатка не создавала новую категорию. Связь с справочником задают внешним ключом.

Схему создают скриптом, а не набором ручных команд в графическом редакторе. Скрипт хранится в репозитории, повторяется на любой машине и показывает историю изменений. Если таблицу добавили вручную, на другой машине её не будет, и проект не запустится.

В SQLite внешние ключи по умолчанию выключены. Команда PRAGMA foreign_keys = ON включает их только для текущего соединения. Это значит, что её выполняют при каждом подключении, а не один раз в файле схемы. Если забыть про неё, база молча примет ссылку на несуществующую запись.

Пароль не хранят в открытом виде. В таблице пользователей лежит хеш, полученный медленной функцией с солью. Соль делает одинаковые пароли разными, а число итераций удорожает перебор. Формат строки включает алгоритм, число итераций и соль, поэтому проверка не зависит от дополнительных колонок.

Проверка входа выполняется в определённом порядке. Сначала ищут пользователя по логину, затем проверяют пароль, и только потом смотрят на признак блокировки. Такой порядок не даёт отличить заблокированную запись от несуществующей, если пароль неверен: обе получают одинаковый отказ. Заблокированная запись с верным паролем получает отдельный отказ, потому что пользователь доказал, что знает секрет.

Сценарий Что проверяют Ожидаемый результат
верный логин и пароль успешный вход пользователь и его роль
верный логин, неверный пароль отказ в проверке пароля invalid_credentials
неизвестный логин отсутствие записи invalid_credentials
заблокированная запись, верный пароль признак блокировки blocked
пустой пароль пустое значение invalid_credentials

Ограничения проверяют попыткой их нарушить. Если вставка дубля логина завершилась ошибкой UNIQUE constraint failed, ограничение работает. Если вставка прошла, значит, ограничения нет или оно не включено. Ошибка в этом случае является доказательством, а не сбоем.

Шаг 3. Напишите schema.sql

Создайте файл .../project/db/schema.sql. Ниже три таблицы: пользователи, справочник категорий и оборудование. Четвёртую таблицу выдачи добавьте сами по описанию после кода.

PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    login TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    role TEXT NOT NULL CHECK (role IN ('admin', 'manager', 'user')),
    is_blocked INTEGER NOT NULL DEFAULT 0 CHECK (is_blocked IN (0, 1)),
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS categories (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL UNIQUE
);

CREATE TABLE IF NOT EXISTS equipment (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    inventory_no TEXT NOT NULL UNIQUE,
    title TEXT NOT NULL,
    category_id INTEGER NOT NULL REFERENCES categories(id),
    price REAL NOT NULL CHECK (price > 0)
);

INTEGER PRIMARY KEY AUTOINCREMENT создаёт целочисленный ключ, который база заполняет сама. TEXT NOT NULL UNIQUE требует строку и запрещает повтор. CHECK (role IN (...)) ограничивает роль тремя значениями. REFERENCES categories(id) связывает оборудование с категорией. DEFAULT (datetime('now')) подставляет дату создания.

Добавьте таблицу issues со столбцами id, equipment_id, user_id, issued_on, due_on, returned_on. Требования: внешние ключи на equipment и users, дата выдачи обязательна, срок возврата не раньше даты выдачи, дата фактического возврата может быть пустой. Для проверки дат используйте CHECK.

Типы выбирайте по смыслу. Целые числа и признаки храните в INTEGER, текст и даты в формате ГГГГ-ММ-ДД в TEXT, деньги и размеры в REAL. Даты в текстовом формате сравниваются как строки, поэтому формат должен быть единым.

INSERT OR IGNORE пропускает строку, если она нарушает UNIQUE. Поэтому повторный запуск заполнения не создаёт дубликаты. Если нужно изменить существующую строку, одного IGNORE мало: понадобится UPDATE или пересоздание базы.

Шаг 5. Реализуйте модуль входа

Создайте .../project/src/auth.py. Модуль содержит три функции: хеширование пароля, проверку пароля и вход по логину.

import hashlib
import hmac
import secrets

ITERATIONS = 120_000


def hash_password(password: str) -> str:
    salt = secrets.token_hex(16)
    digest = hashlib.pbkdf2_hmac(
        "sha256", password.encode("utf-8"), bytes.fromhex(salt), ITERATIONS
    )
    return f"pbkdf2_sha256${ITERATIONS}${salt}${digest.hex()}"


def verify_password(password: str, stored: str) -> bool:
    algorithm, iterations, salt, expected = stored.split("$")
    if algorithm != "pbkdf2_sha256":
        return False
    digest = hashlib.pbkdf2_hmac(
        "sha256", password.encode("utf-8"), bytes.fromhex(salt), int(iterations)
    )
    return hmac.compare_digest(digest.hex(), expected)


def authenticate(connection, login: str, password: str) -> dict:
    row = connection.execute(
        "SELECT id, login, password_hash, role, is_blocked FROM users WHERE login = ?",
        (login,),
    ).fetchone()
    if row is None or not verify_password(password, row["password_hash"]):
        return {"ok": False, "reason": "invalid_credentials"}
    if row["is_blocked"]:
        return {"ok": False, "reason": "blocked"}
    return {"ok": True, "user": {"id": row["id"], "login": row["login"], "role": row["role"]}}


if __name__ == "__main__":
    sample = hash_password("Admin-2026")
    print("формат:", sample[:30] + "...")
    print("верный пароль:", verify_password("Admin-2026", sample))
    print("неверный пароль:", verify_password("admin-2026", sample))

secrets.token_hex(16) создаёт соль из 16 случайных байт и возвращает 32 шестнадцатеричных символа. hashlib.pbkdf2_hmac считает хеш с указанным числом итераций. hmac.compare_digest сравнивает строки за постоянное время, чтобы по задержке нельзя было подбирать значение по байтам.

Функция authenticate принимает соединение с базой, логин и пароль. Запрос использует параметр ?, поэтому логин не может изменить текст SQL. Сначала проверяется пара логин и пароль, затем признак блокировки. Результат возвращается словарём: успех содержит пользователя и роль, отказ содержит причину. Функция ожидает, что соединение настроено на доступ по имени столбца (row_factory = sqlite3.Row); это делает вызывающий код.

Проверьте функции отдельно от базы. Запустите модуль как программу: он посчитает хеш для учебного пароля и сравнит его с верным и неверным значением. Соль при каждом запуске новая, поэтому начало строки будет меняться.

python -m src.auth

формат: pbkdf2_sha256$120000$d8e655723...
верный пароль: True
неверный пароль: False

Шаг 6. Заполните пользователей хешами

Создайте .../project/src/seed_users.py. Скрипт считает хеш для каждого учебного пароля и вставляет запись в таблицу. Пароли нужны только для проверки входа; в рабочей системе их задают отдельно и не хранят в файле данных.

import sqlite3

from src.auth import hash_password

USERS = [
    ("admin", "Admin-2026", "admin", 0),
    ("lab_1", "Lab-2026", "manager", 0),
    ("student_1", "Student-2026", "user", 0),
    ("student_2", "Student-2026", "user", 1),

Проверьте таблицу без хешей. Запрос должен показать логины, роли и признак блокировки, но не столбец password_hash.

Если повторно запустить заполнение, количество строк не изменится. INSERT OR IGNORE не обновляет существующую запись, поэтому смена пароля в списке не изменит хеш в базе. Для учебной проверки проще удалить файл базы и создать его заново.

Шаг 7. Проверьте сценарии входа

Создайте .../project/src/login_check.py. Скрипт открывает базу, включает построчный доступ по имени столбца и проверяет четыре пары логин и пароль.

import sqlite3

from src.auth import authenticate

connection = sqlite3.connect("db/project.db")
connection.row_factory = sqlite3.Row
checks = [
    ("admin", "Admin-2026"),
    ("admin", "admin-2026"),
    ("unknown", "Admin-2026"),
    ("student_2", "Student-2026"),
]
for login, password in checks:
    result = authenticate(connection, login, password)
    if result["ok"]:
        print(f"{login}: вход выполнен, роль {result['user']['role']}")
    else:
        print(f"{login}: отказ, причина {result['reason']}")
connection.close()

Запустите проверку. Вывод показывает, что верная пара пускает пользователя, неверный пароль и неизвестный логин дают одинаковый отказ, а заблокированная запись с верным паролем получает отдельную причину.

python -m src.login_check

admin: вход выполнен, роль admin
admin: отказ, причина invalid_credentials
unknown: отказ, причина invalid_credentials
student_2: отказ, причина blocked

Заполните таблицу проверок. Первая строка дана как образец, остальные заполните по фактическому выводу. В последней колонке запишите, что именно подтверждает результат.

Сценарий Логин Пароль Ожидаемый результат Фактический результат
Верный вход admin Admin-2026 вход, роль admin
Неверный пароль admin admin-2026 invalid_credentials
Неизвестный логин unknown Admin-2026 invalid_credentials

Пустой пароль проверяется отдельно: verify_password получит пустую строку и посчитает хеш, который не совпадёт с сохранённым. Отдельная ветка для пустого значения не нужна, но результат должен быть отказом, а не ошибкой программы.

Шаг 8. Проверьте ограничения схемы

Ограничение считается работающим только после попытки его нарушить. Создайте .../project/src/check_constraints.py. Скрипт включает внешние ключи, пробует три неверные вставки и печатает тип ошибки. После каждой попытки выполняется откат, чтобы база осталась чистой.

import sqlite3

connection = sqlite3.connect("db/project.db")
connection.execute("PRAGMA foreign_keys = ON")
checks = [
    "INSERT INTO users (login, password_hash, role) VALUES ('admin', 'x', 'admin')",
    "INSERT INTO equipment (inventory_no, title, category_id, price) VALUES ('INV-002', 'Мышь', 1, -10)",
    "INSERT INTO issues (equipment_id, user_id, issued_on, due_on) VALUES (999, 1, '2026-10-01', '2026-10-02')",
]
for sql in checks:
    try:
        connection.execute(sql)
        print("вставка прошла")
    except sqlite3.IntegrityError as error:
        print(type(error).__name__ + ":", error)
    connection.rollback()
connection.close()

python -m src.check_constraints

IntegrityError: UNIQUE constraint failed: users.login
IntegrityError: CHECK constraint failed: price > 0
IntegrityError: FOREIGN KEY constraint failed

Три ошибки подтверждают три правила: логин уникален, цена положительна, ссылка на оборудование существует. Если вместо ошибки появилось сообщение «вставка прошла», проверьте ограничение в схеме и команду PRAGMA foreign_keys = ON в текущем соединении. Внешние ключи в SQLite не запоминаются в файле базы: их включает каждая программа при подключении.

Запросы в скрипте написаны под схему из шага 3. Если в таблице есть обязательные поля сверх показанных, добавьте их в запрос с корректными значениями, чтобы ошибка возникала именно на проверяемом ограничении, а не на пропущенном поле. Если имена таблиц или столбцов другие, замените их в запросах, сохранив смысл проверки.

Шаг 9. Проверьте схему на чистой базе

Удалите файл базы и повторите создание с нуля. Это проверяет, что в схеме нет таблиц, созданных вручную, и что заполнение не зависит от старых данных.

После повторного создания вход должен работать так же, как до удаления. Если появилась ошибка отсутствующей таблицы, значит, schema.sql не содержит нужную таблицу или init_db.py не выполнил файл целиком.

05Требования к отчёту

Отчёт содержит таблицу сущностей, текстовую схему связей, текст schema.sql, данные справочника, код src/auth.py, таблицу проверок входа и протокол проверки ограничений.

На снимке терминала должны быть видны команда создания базы, её вывод и отсутствие ошибок. На снимке таблицы пользователей должны быть видны логины, роли и признак блокировки; столбец с хешем в отчёт не копируют. На снимке проверки входа должны быть видны четыре строки с разными результатами.

В выводе ответьте на три вопроса: почему выбранные ключи обеспечивают связи; что произойдёт при попытке вставить дубль логина; почему проверка пароля стоит перед проверкой блокировки.

08Критерии оценки

Оценка выставляется по шкале от 1 до 5.

  • 5: схема содержит четыре-шесть таблиц с первичными и внешними ключами, ограничения NOT NULL, UNIQUE и CHECK использованы по делу, справочник заполнен, база создаётся с нуля, пароли хранятся хешами, проверены пять сценариев входа и три нарушения ограничений, отчёт содержит доказательства.
  • 4: работа выполнена полностью, но одно ограничение отсутствует или один сценарий входа не проверен.
  • 3: таблицы созданы без внешних ключей или проверок, справочник заполнен частично, вход работает только для верного пароля, ограничения не проверялись.
  • 2: работа не выполнена или база не создаётся.
  • 1: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
