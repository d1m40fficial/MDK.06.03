01Цель работы

Собрать консольное приложение на C#, которое рассчитывает заказ по минимальному остатку для двенадцати позиций склада. Программа получает остатки, минимумы и кратность упаковки, считает количество к заказу по каждой позиции, выводит итог и число позиций, которым нужен заказ.

Работа проверяет три умения. Первое: объявить метод с параметрами и возвращаемым типом и вызвать его из точки входа. Второе: разложить программу на несколько методов и файлов так, чтобы данные, расчёт и вывод не мешали друг другу. Третье: собрать проект, прочитать предупреждения компилятора и убрать их, не отключая проверки.

Результат это папка проекта, которая собирается командой dotnet build без предупреждений, запускается командой dotnet run и выдаёт отчёт по данным склада.

Проверка работы идёт по трём признакам. Первый: программа считает заказ для всех двенадцати позиций, а не для одной. Второй: каждый метод можно вызвать отдельно и получить предсказуемый результат. Третий: сборка не содержит предупреждений, потому что предупреждение это непрочитанное сообщение компилятора о возможной ошибке.

03Краткие теоретические сведения

Метод это именованный блок кода с параметрами и возвращаемым значением. Объявление метода содержит уровень доступа, тип возврата, имя, список параметров и тело. В консольной программе методы обычно объявляют статическими: они принадлежат классу и не требуют создания объекта.

Параметр это имя входного значения внутри метода, аргумент это значение при вызове. В C# у каждого параметра указан тип, поэтому компилятор проверяет, что в метод не передали строку вместо числа. Параметры передаются по значению: метод получает копию числа и не может изменить переменную вызывающего кода. Исключение составляют ссылочные типы, например массивы: метод видит тот же массив и может изменить его элементы.

Возвращаемое значение задаётся типом перед именем. Тип void означает, что метод ничего не возвращает. Тип int обязывает вернуть целое число на каждом пути выполнения. Если ветка if возвращает значение, а else нет, компилятор выдаст ошибку.

Перегрузка это несколько методов с одним именем и разными параметрами. Компилятор выбирает вариант по числу и типам аргументов. Перегрузка удобна, когда одна операция имеет короткую и полную форму, например описание количества с единицей измерения и без неё.

Сборка проекта проходит в два шага. Компилятор превращает исходный код в сборку, а затем среда выполнения запускает её. Предупреждение не мешает сборке, но указывает на место, где код скорее всего содержит ошибку: неиспользуемую переменную, недостижимую строку, неявное преобразование. Предупреждения нужно разбирать, а не отключать.

Проект C# это набор файлов .cs и файл .csproj с настройками. Команда dotnet build собирает проект, команда dotnet run собирает и сразу запускает. Промежуточные файлы попадают в каталог obj, готовая сборка в bin. Пространство имён группирует классы и защищает от совпадения имён: два класса Program в разных пространствах имён допустимы, а в одном нет.

Целочисленное деление в C# отбрасывает дробную часть. Для округления вверх до целой упаковки к делимому добавляют packSize - 1, а затем делят на packSize. Для дефицита 28 и упаковки 10 получается (28 + 9) / 10, то есть 3 коробки.

04Ход работы

Шаг 1. Создайте проект и запустите шаблон

Команда dotnet new console создаёт консольный проект по шаблону. Ключ -n задаёт имя проекта, ключ -o указывает папку. Выполните в терминале:

dotnet new console -n SkladCalc -o .../sklad-plus.calc

Перейдите в созданную папку и запустите проект:

dotnet run

Шаблон печатает Hello, World!. Рядом с файлом проекта появятся каталоги obj и bin: в первом лежат промежуточные файлы сборки, во втором готовая сборка. Эти каталоги не редактируют и не включают в отчёт.

Точка входа программы это метод Main. Среда выполнения начинает работу с него, поэтому вызовы других методов должны находиться внутри Main или внутри методов, которые он вызывает. Слово static означает, что метод принадлежит классу, а не объекту. Пока объектов в программе нет, статического метода достаточно.

Откройте Program.cs и замените приветствие на строку Склад+: расчёт заказа. Сохраните файл и снова выполните dotnet run. Убедитесь, что вывод изменился.

Сделайте снимок терминала, на котором видны команда dotnet run и новая строка вывода. На снимке должно быть понятно, из какой папки запущена команда.

Шаг 2. Объявите первый метод

В том же файле Program.cs объявите метод расчёта. Он принимает остаток, минимум и кратность упаковки, а возвращает количество к заказу.

static int ReorderQuantity(int quantity, int minQuantity, int packSize)
{
    if (quantity >= minQuantity)
    {
        return 0;
    }
    int missing = minQuantity - quantity;
    int packs = (missing + packSize - 1) / packSize;
    return packs * packSize;
}

Разберите формулу на примере. Остаток 12, минимум 40, упаковка 10. Дефицит равен 28. Добавка packSize - 1 превращает 28 в 37, деление на 10 даёт 3 коробки, заказ равен 30. Без добавки деление 28 на 10 дало бы 2 коробки и 20 штук, чего не хватает до минимума.

Метод возвращает число, а не печатает его. Это важно для дальнейшей работы: тот же метод понадобится отчёту, API и проверке, и каждому нужен свой способ вывода. Если метод печатает сам, повторный вызов добавит лишнюю строку в консоль и в журнал.

Вызовите метод из Main:

Console.WriteLine(ReorderQuantity(12, 40, 10));

Запустите программу. В консоли должно появиться 30. Добавьте ещё два вызова: ReorderQuantity(96, 60, 12) и ReorderQuantity(0, 25, 5). Запустите и запишите результат в таблицу.

Остаток Минимум Упаковка Ожидаемый заказ Фактический заказ
12 40 10 30
96 60 12
0 25 5

Первая строка дана как образец. Остальные заполните до запуска, затем сравните с выводом.

Шаг 3. Добавьте проверки входа

Метод должен отказывать, если остаток или минимум отрицательные, а упаковка равна нулю. Добавьте проверки в начало метода:

if (quantity < 0 || minQuantity < 0)
{
    throw new ArgumentOutOfRangeException("quantity", "Остаток и минимум не могут быть отрицательными");
}
if (packSize <= 0)
{
    throw new ArgumentOutOfRangeException("packSize", "Кратность упаковки должна быть больше нуля");
}

throw создаёт исключение и прерывает выполнение метода. Для неверного входа это правильное поведение: программа не должна молча возвращать ноль, иначе склад решит, что заказ не нужен.

Проверки стоят до расчёта и называются защитными условиями. Сначала отсекается невозможный вход, и только потом выполняется формула. Если поставить проверку после деления, при нулевой упаковке программа упадёт с другим сообщением, и причина будет неочевидна.

Проверьте отказ. Временно добавьте в Main вызов ReorderQuantity(12, 40, 0), запустите программу и скопируйте сообщение об ошибке в отчёт. После проверки удалите этот вызов, чтобы программа снова завершалась нормально.

Сделайте снимок терминала с сообщением об ошибке. На снимке должна быть видна строка с именем параметра и текстом проверки.

Шаг 4. Посчитайте итог по массиву

Одна позиция проверена, теперь нужен расчёт по набору. Массив в C# хранит значения одного типа и имеет длину Length. Метод принимает три массива одинаковой длины и возвращает сумму заказов.

static int TotalToOrder(int[] quantities, int[] minimums, int[] packs)
{
    if (quantities.Length != minimums.Length || quantities.Length != packs.Length)
    {
        throw new ArgumentException("Массивы должны быть одинаковой длины");
    }
    int total = 0;
    for (int i = 0; i < quantities.Length; i++)
    {
        total += ReorderQuantity(quantities[i], minimums[i], packs[i]);
    }
    return total;
}

Проверка длины стоит до цикла. Если массивы разной длины, программа должна отказать сразу, а не падать на середине обхода.

Вызовите метод с пятью значениями:

int[] quantities = { 12, 96, 0, 7, 3 };
int[] minimums = { 40, 60, 25, 7, 30 };
int[] packs = { 10, 12, 5, 1, 6 };
Console.WriteLine(TotalToOrder(quantities, minimums, packs));

Запустите программу и запишите итог. Затем самостоятельно добавьте метод CountToOrder, который принимает массивы остатков и минимумов и возвращает число позиций, где остаток ниже минимума. Вызовите его на тех же данных. Ожидаемое число позиций равно трём, проверьте, что метод даёт именно его.

Шаг 5. Добавьте перегрузку метода

Вернитесь к выводу. Сейчас программа печатает голое число, а в отчёте нужна единица измерения. Объявите два метода с одним именем:

static string Describe(int quantity)
{
    return quantity + " ед.";
}

static string Describe(int quantity, string unit)
{
    return quantity + " " + unit;
}

Вызов Describe(85) вернёт 85 ед., вызов Describe(85, "шт.") вернёт 85 шт.. Компилятор выбирает вариант по числу аргументов.

Перегрузка работает, пока варианты отличаются числом или типами параметров. Два метода с одинаковыми типами, но разными именами параметров, компилятор не различает: имена в сигнатуре для выбора не участвуют. Если варианты неоднозначны, сборка завершится ошибкой, и это полезно: неоднозначность видна сразу, а не в момент вызова.

Добавьте третий вариант, который принимает количество, единицу и артикул и возвращает строку вида SKU-1042: 30 шт.. Вызовите все три варианта и проверьте, что каждый вернул свою строку. Запишите в отчёт, по какому признаку компилятор отличает перегрузки.

Шаг 6. Разбейте программу на файлы

Пока весь код лежит в Program.cs, файл растёт и в нём смешаны данные, расчёт и вывод. Разделите ответственность на три файла в папке проекта.

Файл StockData.cs хранит исходные данные:

namespace SkladCalc

    {
        public static readonly string[] Skus =
        {
            "SKU-1042", "SKU-2087", "SKU-3310", "SKU-4155", "SKU-5201", "SKU-6034",
            "SKU-7118", "SKU-8246", "SKU-9073", "SKU-1120", "SKU-2244", "SKU-3367"
        };

        public static readonly int[] Minimums = { 40, 60, 25, 7, 30, 18, 20, 50, 12, 45, 24, 10 };
        public static readonly int[] Packs = { 10, 12, 5, 1, 6, 4, 10, 6, 4, 15, 8, 3 };

Файл ReorderCalculator.cs хранит методы расчёта. Перенесите в него ReorderQuantity, TotalToOrder, CountToOrder и перегрузки Describe, добавив using System; и пространство имён SkladCalc.

Файл Program.cs оставьте точкой входа: в нём останутся только вызовы методов и вывод. Подключите пространство имён:

using System;
using System.Text;

namespace SkladCalc
{
    public static class Program
    {
        public static void Main()
        {
            Console.OutputEncoding = Encoding.UTF8;
            Console.WriteLine("Позиций в справочнике: " + StockData.Skus.Length);
            Console.WriteLine("К заказу: " + ReorderCalculator.CountToOrder(StockData.Quantities, StockData.Minimums));
            Console.WriteLine("Всего единиц: " + ReorderCalculator.TotalToOrder(StockData.Quantities, StockData.Minimums, StockData.Packs));

Строка Console.OutputEncoding = Encoding.UTF8; нужна, чтобы кириллица в консоли Windows не превращалась в вопросительные знаки. Без неё отчёт может выглядеть правильно в редакторе и неправильно в терминале.

Соберите проект командой dotnet build и запустите dotnet run. Проект сам включает все файлы .cs из папки, поэтому добавлять их в файл проекта вручную не нужно.

Шаг 7. Соберите проект и уберите предупреждения

Выполните сборку:

dotnet build

В выводе найдите строки Warning(s) и Error(s). Ноль ошибок обязателен, ноль предупреждений это цель работы. Предупреждение не останавливает сборку, но означает, что компилятор заметил подозрительное место.

Чтобы увидеть предупреждение своими глазами, добавьте в начало Main строку int unused = 0;. Соберите проект и найдите сообщение CS0219: переменная назначена, но её значение никогда не используется. Удалите строку и соберите снова.

Сообщение компилятора состоит из кода, текста и места. Код CS0219 полезно запомнить: он почти всегда означает забытую переменную. Читайте вывод сверху вниз: первая ошибка часто вызывает следующие, и после её исправления часть сообщений исчезает.

Теперь включите строгий режим:

dotnet build -warnaserror

Ключ -warnaserror превращает каждое предупреждение в ошибку. Сборка должна пройти без замечаний. Если появилось предупреждение о неиспользуемой переменной, неиспользуемом using или недостижимой строке, уберите причину, а не отключайте проверку.

Сделайте снимок терминала с результатом dotnet build -warnaserror. На снимке должны быть видны итоговые строки с нулём предупреждений и нулём ошибок.

Шаг 8. Проверьте граничные случаи

Обычные данные не показывают, как программа ведёт себя на краях. Проверьте шесть случаев и запишите фактический результат. Для ошибок фиксируйте текст сообщения, а не только слово «ошибка».

Случай Вход Ожидание Факт
Остаток равен минимуму 7, 7, 1 0
Нулевой остаток 0, 25, 5 25
Упаковка из одной штуки 12, 40, 1 28
Пустые массивы три массива длины 0 0
Отрицательный остаток -3, 40, 10 сообщение об ошибке
Нулевая упаковка 12, 40, 0 сообщение об ошибке

Первая строка дана как образец. Остальные заполните после запуска. Для пустых массивов вызовите TotalToOrder(new int[0], new int[0], new int[0]). Для ошибочных входов вызывайте метод по одному разу, чтобы сообщение относилось к нужной проверке.

Исключение это не сбой программы, а предусмотренный отказ. Программа сообщает, что вход неверен, и останавливает расчёт, вместо того чтобы выдать правдоподобное, но неправильное число. Поэтому в таблице для отрицательного остатка и нулевой упаковки ожидается именно сообщение, а не ноль.

Отдельно проверьте несовпадение длин: передайте в TotalToOrder массивы длины 3 и 4. Программа должна выдать ArgumentException, а не IndexOutOfRangeException. Разные сообщения помогают понять, какая именно проверка сработала.

Соберите документ по структуре: титульный лист, цель работы, дерево файлов проекта, сигнатуры методов, таблица обычных вызовов, таблица граничных случаев, вывод сборки, заключение.

В разделе с сигнатурами укажите для каждого метода имя, параметры с типами и возвращаемый тип. Например, ReorderQuantity(int quantity, int minQuantity, int packSize) возвращает int. Для перегрузок покажите все варианты и объясните, чем они отличаются.

В заключении ответьте на два вопроса. Первый: какие методы пришлось выделить и почему. Второй: какое предупреждение компилятора встретилось и как его убрали. Ответ на второй вопрос должен содержать код предупреждения.

05Требования к отчёту

Отчёт оформляется в DOCX. Титульный лист содержит название работы, дисциплину, фамилию и группу. Далее идут цель работы и перечень использованного программного обеспечения.

Оформление по единому шаблону: A4, поля 3 см слева, 1,5 см справа, по 2 см сверху и снизу, Times New Roman 14 пт, интервал 1,5, отступ первой строки 1,25 см. Заголовки оформляются стилями Heading 1 и Heading 2, таблицы стилем Table Grid с шапкой по центру и названием под таблицей.

Основная часть содержит дерево файлов проекта, сигнатуры всех методов, таблицу обычных вызовов с ожидаемым и фактическим результатом и таблицу граничных случаев. Для каждого метода укажите, что он принимает и что возвращает.

В отчёт вставьте снимки терминала: запуск шаблона, сообщение проверки входа, результат dotnet build -warnaserror. На каждом снимке должна быть видна команда и её вывод, а не только итоговая строка.

Таблицы оформляйте с шапкой и подписью под таблицей. В таблице обычных вызовов столбцы: остаток, минимум, упаковка, ожидаемый заказ, фактический заказ, совпадение. В таблице граничных случаев добавьте столбец с текстом ошибки. Единицы измерения указывайте в шапке, а не в каждой клетке.

Снимок вставляйте после абзаца, который его описывает, и подписывайте: что именно проверялось. Снимок без подписи через месяц ничего не докажет ни автору, ни проверяющему.

Завершает отчёт заключение на пять-семь предложений: какие методы выделены, где пришлось добавить проверку, какое предупреждение компилятора встретилось и как его устранили.

08Критерии оценки

Оценка выставляется по шкале от 1 до 5. Балл снижается за пропущенную проверку, а не за длину отчёта или число страниц. Главное это работающий проект и понятные результаты его запуска.

  • 5: проект собирается без предупреждений и ошибок, методы имеют понятные имена и типы, данные и расчёт разнесены по файлам, обычные и граничные случаи проверены, отчёт содержит все таблицы и снимки, заключение объясняет решения.
  • 4: проект собирается без ошибок, но остаётся одно предупреждение или одна граничная проверка не выполнена, таблицы заполнены с одним расхождением, отчёт полный.
  • 3: программа работает на обычных данных, но методы собраны в один файл, проверки входа отсутствуют, граничные случаи не проверены, отчёт неполный.
  • 2: работа не выполнена или программа не собирается.
  • 1: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
