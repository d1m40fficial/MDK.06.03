01Что представляет собой работа

Работа состоит из шести заданий, которые связаны одним набором документов. В папке варианта лежат заказ покупателя, заказ на производство, спецификация, цены, справочник заказчиков в JSON и заметки сотрудников в JSON. Из этих документов нужно собрать информационную систему небольшого предприятия: нарисовать модель данных, создать базу, посчитать стоимость заказа, сделать приложение, разработать API и заполнить документацию.

На выполнение отводится 210 минут. Работа оценивается в 75 баллов. Уровень базовый: проверяют не изящную архитектуру, а работающую и объяснимую систему, каждый шаг которой можно показать на экране. Все задания идут в одном порядке и опираются друг на друга. Модель данных задаёт таблицы базы, база питает запрос, приложение и API, а документация описывает то, что уже работает.

Главное правило работы: пока текущее задание не доведено до сдаваемого файла, следующее не начинается. Исключение одно: если задание заблокировано чужой ошибкой, например не запускается MySQL, зафиксируйте проблему и перейдите к тому, что от неё не зависит, но обязательно вернитесь.

02Шесть заданий и их результаты

№ Задание Что нужно сделать Что сдаётся
1 ER-диаграмма Выделить сущности, атрибуты, ключи и связи, привести модель к 3НФ PDF с читаемой диаграммой
2 База данных Создать таблицы и ограничения, импортировать заказчиков, загрузить заказ и цены SQL-скрипт и выгрузка базы
3 Запрос стоимости Соединить заказ, спецификацию, ресурсы и цены, сложить материалы и операции SQL-запрос и его результат
4 Приложение Сделать вход, роли, пазл, блокировку и управление пользователями Проект приложения и протокол проверки
5 API Отдать заметки в JSON с нужными полями и кодами 200, 400, 500 Проект API и коллекция Postman
6 Документация Заполнить шаблон DOCX по фактическому API DOCX, OpenAPI JSON и примеры

Три задания работают с данными: модель, база, запрос. Два задания создают программы: приложение и API. Последнее описывает то, что уже сделано. Такое деление удобно держать в голове при планировании: сначала данные, потом поведение, потом описание.

Один и тот же заказ проходит через все задания. Если в заказе два изделия, то в модели это шапка заказа и две строки, в базе две записи, в запросе две строки стоимости, в приложении список заказов, в API связанные заметки, а в документации пример ответа. Поэтому ошибка в модели видна далеко не сразу, но стоит дорого.

03Из чего состоит вариант

Документы заказчика устроены как обычные бумажные формы. У каждой формы есть шапка с номером и датой и табличная часть с повторяющимися строками. Это главный признак, по которому в модели появляются отдельные таблицы.

Заказ покупателя. В шапке номер, дата, срок, изготовитель и заказчик. В табличной части изделие, единица, количество, цена, скидка и сумма. Код заказчика связывает заказ со справочником контрагентов.

Заказ на производство. В шапке номер производственного заказа и дата запуска. В табличной части продукция к выпуску и плановый расход ресурсов с единицами измерения. Этот документ показывает, что предприятие не только продаёт, но и производит.

Спецификация. Описывает, из чего состоит изделие и какие операции нужны. В табличной части ресурс, вид, единица, норма расхода и часы на единицу. Норма это расход на одну единицу готовой продукции.

Цены. Справочник цен с датой начала действия. Одна и та же позиция может иметь несколько цен, поэтому ключ получается составным: ресурс и дата. Так старый заказ считается по старым ценам.

Заказчики.json. Массив объектов с ключами id, name, inn, addres, phone, type. Код записан строкой из десяти цифр и содержит ведущие нули. Если преобразовать его в число, 0000000002 станет 2, и связь с заказом потеряется. Ключ адреса в источнике записан с опечаткой addres, а в таблице поле называется address; это сопоставление нужно зафиксировать, а не исправлять файл заказчика.

Заметки.json. Пять записей с заголовком, логином автора, содержанием и датой создания. Эти данные понадобятся в задании 5: логин нужно сопоставить с пользователем, а дату привести к формату ДД.ММ.ГГГГ.

Ключевая идея

Документ не равен сущности. Одна бумажная форма часто превращается в две таблицы: шапку и строки. Одна строка спецификации может стать отдельной таблицей, если у неё есть свои свойства, например количество и норма времени.

04Программы и стенд

Стенд фиксирован. Не нужно выбирать инструменты, нужно уверенно работать в тех, что есть. Перед началом проверьте каждую программу, чтобы не искать причину сбоя в середине работы.

Программа Где открыть Для чего
Браузер Ярлык на рабочем столе draw.io, phpMyAdmin, Swagger UI
draw.io https://app.diagrams.net/ ER-диаграмма
XAMPP Control Panel Пуск, затем XAMPP Запуск Apache и MySQL
phpMyAdmin http://localhost/phpmyadmin База, SQL, импорт и экспорт
Visual Studio 2022 Пуск, затем Visual Studio 2022 Приложение и API
.NET SDK 10 Проверка командой dotnet --version Сборка проекта
Postman Пуск, затем Postman Коллекция запросов и тесты
Word Пуск, затем Word Документация API

Проверка стенда занимает несколько минут.

  1. Откройте XAMPP Control Panel и нажмите Start у Apache и MySQL. Оба статуса должны стать Running.
  2. Откройте браузер и перейдите по адресу http://localhost/phpmyadmin. Должна открыться страница входа. Пользователь root, пароль пустой, если его не меняли.
  3. Откройте новую вкладку и проверьте https://app.diagrams.net/. Должен загрузиться редактор диаграмм.
  4. Откройте командную строку и выполните dotnet --version. Команда должна вернуть номер версии 10.
  5. Запустите Visual Studio 2022 и убедитесь, что доступен шаблон Windows Forms App.
  6. Запустите Postman и создайте пустую коллекцию. Если программа требует вход, используйте локальный профиль без синхронизации.
Типичная ошибка

Если Apache не запускается, phpMyAdmin не откроется, хотя MySQL может работать. Если MySQL не запускается, проверьте, не занят ли порт 3306 другой службой. Не переустанавливайте XAMPP в середине работы, сначала прочитайте сообщение об ошибке.

05Рабочая папка и имена файлов

Создайте одну папку на рабочем столе, например Экзамен_Фамилия. Внутри сделайте подпапки по заданиям. Такой порядок экономит время на сдаче: проверяющий видит комплект, а вы не ищете файл по всему диску.

Экзамен_Фамилия/
  variant/          исходные документы варианта
  task1/            ER_Фамилия.drawio, ER_Фамилия.pdf, keys.docx
  task2/            schema.sql, dkip2027.sql, import-notes.txt
  task3/            cost.sql, cost-result.csv
  task4/            Dkip.WinForms/ (проект)
  task5/            Dkip.Api/ (проект), postman.json
  task6/            API_документация.docx, openapi.json

Имена файлов должны быть короткими и латинскими, без пробелов. Кириллица в именах допустима, но иногда ломает пути в командной строке и в архивах. Если преподаватель требует русское имя, используйте его только для итогового документа.

06Порядок выполнения и контрольные точки

Порядок заданий не случайный. Он совпадает с направлением данных: от документов к модели, от модели к базе, от базы к запросу и приложению, от приложения к API и документации.

  1. Задание 1. Прочитайте документы, выпишите сущности и связи, постройте диаграмму, проверьте 3НФ и экспортируйте PDF.
  2. Задание 2. Создайте базу по своей диаграмме, выполните SQL, импортируйте заказчиков и загрузите заказ. Сделайте выгрузку и проверьте восстановление.
  3. Задание 3. Напишите запрос стоимости, проверьте его на контрольном примере и сохраните результат.
  4. Задание 4. Создайте приложение, подключите его к базе, реализуйте вход, пазл, роли и блокировку.
  5. Задание 5. Реализуйте API заметок, проверьте ответы в браузере и Postman, соберите коллекцию с тестами.
  6. Задание 6. Заполните шаблон документации по фактическим ответам API, сверьте его с OpenAPI.

Контрольные точки удобно записать на листке и отмечать по мере готовности.

  • PDF с диаграммой открывается и читается без увеличения.
  • В базе есть все таблицы, ключи и шесть заказчиков с ведущими нулями.
  • SQL-запрос возвращает материалы и операции отдельными строками и общую сумму.
  • Приложение запускается, входит под администратором и пользователем, блокирует запись после трёх ошибок.
  • API отвечает 200 на обычный запрос, пустым массивом на пустую выборку, 400 на неверный параметр и 500 при сбое базы.
  • Коллекция Postman импортируется на другом компьютере и проходит тесты.
  • DOCX заполнен по шаблону, примеры в нём совпадают с реальными ответами.

07Что сдаётся и как оценивается

Баллы начисляют не за задания, а по десяти критериям, которые описывают виды деятельности.

Критерий Баллы
Администрирование отдельных компонент серверов 6
Выявление технических проблем при эксплуатации баз данных 11
Сбор исходных данных для проектной документации 6
Разработка модулей информационной системы по техническому заданию 10
Разработка подсистем безопасности 8
Разработка проектной документации по требованиям заказчика 6
Поиск, анализ и интерпретация информации 3
Разработка тестовых наборов и сценариев 9
Интеграция модулей в программное обеспечение 15
Отладка программного модуля 1
Итого 75

Самый весомый критерий это интеграция модулей, 15 баллов. Второй по весу это выявление технических проблем, 11 баллов. Вместе они дают больше трети всех баллов и требуют, чтобы система работала целиком. Поэтому сквозной сценарий собирайте как можно раньше и проверяйте после каждого изменения.

Артефакт, вспомогательный файл и доказательство это разные вещи. Артефакт без задания не существует: нет PDF, значит нет задания 1. Вспомогательный файл нужен вам: исходник draw.io, черновик SQL, журнал проверок. Доказательство убеждает проверяющего: скриншот списка таблиц, вывод запроса, ответ API. Скриншот становится доказательством только тогда, когда на нём виден результат шага, а не шапка отчёта и не открытое меню.

08Частые ошибки

  • Начать с приложения и оставить диаграмму с базой на конец.
  • Рисовать ER-диаграмму по памяти, не сверяя реквизиты с документами.
  • Забыть, что таблицы пользователей и заметок тоже входят в модель.
  • Импортировать заказчиков как числа и потерять ведущие нули.
  • Посчитать стоимость в уме и не показать запрос.
  • Сделать пазл картинкой, которая не проверяется.
  • Возвращать 500 там, где по смыслу нужен 400.
  • Описать в документации методы, которых в сервисе нет.

Первая ошибка стоит дороже остальных, потому что тянет за собой все следующие. Остальные объединяет одно свойство: каждая из них видна проверяющему за минуту, но почти незаметна автору, который смотрел на свою работу весь день.

09Чек-лист перед началом

  • Папка работы создана, подпапки по заданиям готовы.
  • Исходные документы варианта скопированы в variant/ и не редактируются.
  • XAMPP запускает Apache и MySQL, phpMyAdmin открывается.
  • draw.io открывается в браузере, вход в редактор не требуется.
  • Visual Studio 2022 создаёт проект Windows Forms, dotnet --version возвращает 10.
  • Postman запускается, коллекция создаётся.
  • Word открывает шаблон DOCX из папки reports.
  • Есть чистый лист или файл для контрольных точек.
