01Что делаем

Мебельный цех за неделю принял пять заказов: стеллажи и столы для ООО «Альфа», шкаф и полки для ООО «Бета», мебель для колледжа и для ИП Волкова. Бухгалтер считает выручку в Excel и получает то 249 000 рублей, то 579 000. Арифметика тут ни при чём. Во втором случае к заказам присоединили таблицу норм расхода, у стеллажа оказалось три материала, и каждая позиция заказа размножилась на три строки.

JOIN не склеивает таблицы в одну длинную, он составляет все допустимые пары строк по условию. Пять заказов и девять позиций дают девять пар, а те же девять позиций с нормами расхода дают двадцать две пары. Поэтому главный навык этой работы не в синтаксисе, а в умении заранее ответить, сколько строк появится после каждого соединения.

Соберём учебную базу из пяти таблиц и напишем шесть запросов. Стоимость заказов, потребность в материалах, топ продуктов, заказы выше среднего, продукты без норм и доля каждого материала в затратах. Каждый результат сверим с ручным расчётом и с планом выполнения.

Результат работы: файл базы orders.db, скрипт с шестью запросами, таблица ожиданий и фактов, скриншоты и заполненный отчёт. Числа, которые должны получиться: пять заказов на 249 000 рублей, 382 единицы крепежа, 96 единиц дерева, 30 единиц металла, три заказа дороже среднего чека 49 800.

Что считается готовым результатом

Все шесть запросов выполняются без ошибок и дают осмысленные числа. Сумма по заказам совпадает с ручным расчётом, в запросе потребности нет задвоенных строк, пропуск в данных найден через LEFT JOIN, план запроса до и после индекса отличается, отчёт содержит скриншоты и вывод.

Цены в схеме объявлены как REAL, поэтому SQLite покажет сумму как 65000.0. Это то же число, что 65 000 рублей: .0 означает вещественный тип, а не копейки.

03Задание 1. Схема и данные

В скрипте пять таблиц. Разберитесь в связях до первого запроса: от схемы зависит, какие соединения вообще допустимы.

Таблица Что хранит Ключи и ограничения
products Готовая продукция: код, название, цена PRIMARY KEY product_id, UNIQUE code, CHECK price >= 0
materials Материалы: код, название, цена за единицу PRIMARY KEY material_id, UNIQUE code, CHECK price >= 0
norms Норма расхода материала на единицу продукта Составной ключ (product_id, material_id), оба поля внешние, CHECK qty > 0
orders Заказы: заказчик, дата, статус PRIMARY KEY order_id, CHECK status IN ('new', 'paid', 'done')
order_items Позиции заказа: сколько единиц продукта заказано Составной ключ (order_id, product_id), оба поля внешние, CHECK qty > 0

Два составных ключа решают главную проблему будущих запросов. В norms пара «продукт и материал» встречается один раз, поэтому у стеллажа не может быть двух строк с металлом. В order_items пара «заказ и продукт» тоже единственная: нельзя добавить стеллаж в заказ двумя отдельными строками. Пока это ограничение действует, число строк в соединении предсказуемо.

Проверьте, что данные загрузились полностью:

SELECT
  (SELECT COUNT(*) FROM products)    AS products,
  (SELECT COUNT(*) FROM materials)   AS materials,
  (SELECT COUNT(*) FROM norms)       AS norms,
  (SELECT COUNT(*) FROM orders)      AS orders,
  (SELECT COUNT(*) FROM order_items) AS items;

Должно получиться 4, 4, 10, 5, 9. Если число позиций меньше девяти, скрипт выполнился не до конца. Если таблиц вообще нет, вы смотрите на другой файл базы: проверьте, что подключение открывает orders.db из папки практики.

04Задание 2. Стоимость заказа

Стоимость заказа это сумма произведений цены продукта на количество в позиции. Цена лежит в products, количество в order_items, номер заказа в orders. Значит, нужны все три таблицы и соединение по внешним ключам.

SELECT o.order_id, o.customer, SUM(p.price * oi.qty) AS total
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.order_id
JOIN products AS p ON p.product_id = oi.product_id
GROUP BY o.order_id, o.customer
ORDER BY total DESC;
order_id customer total
5 ООО Альфа 65 000
4 ИП Волков 64 000
1 ООО Альфа 56 000
2 ООО Бета 36 000
3 Колледж 28 000

Пять строк это пять заказов, и это не совпадение: соединение идёт от orders, у каждого заказа есть хотя бы одна позиция, а группировка склеивает позиции обратно в заказ. Сумма всех пяти чисел равна 249 000.

В GROUP BY перечислены оба неагрегированных столбца, order_id и customer. SQLite разрешает указать только order_id и молча возьмёт любое значение заказчика из группы, но стандарт SQL такой запрос отклонит, и при переносе в другую СУБД он не выполнится. Пишите полный список сразу, пока таблица маленькая.

Лишняя таблица в группировке завышает сумму

Добавьте в запрос JOIN norms AS n ON n.product_id = p.product_id и выполните его снова. Заказ 5 вырастет с 65 000 до 160 000, заказ 1 с 56 000 до 136 000, а общая сумма станет 579 000. Причина простая: у шкафа три нормы, у полки две, поэтому каждая позиция превратилась в две или три строки, а SUM сложила цену несколько раз. Нормы к стоимости заказа отношения не имеют, поэтому в этом запросе им делать нечего.

Правило звучит так: прежде чем добавить таблицу в запрос с GROUP BY, ответьте, добавляет она к группе одну строку или много. Справочник по внешнему ключу, у которого ключ уникален, даёт одну строку. Таблица-детализация даёт столько строк, сколько у неё записей на этот ключ, и любая сумма после неё считается по размноженным данным.

05Задание 3. Потребность в материалах

Теперь обратная задача: сколько материала уйдёт на все заказы. Норма расхода задана на единицу продукта, значит, для каждой позиции нужно умножить норму на количество и сложить по материалу.

SELECT m.code, m.name, SUM(n.qty * oi.qty) AS required
FROM order_items AS oi
JOIN norms AS n ON n.product_id = oi.product_id
JOIN materials AS m ON m.material_id = n.material_id
GROUP BY m.material_id, m.code, m.name
ORDER BY required DESC;
code name required
M-04 Крепёж 382
M-02 Дерево 96
M-01 Металл 30

Строк три, а материалов в справочнике четыре. Краска не попала в результат, потому что её нет ни в одной норме: JOIN выбрасывает материал, для которого не нашлось пары. Иногда это правильно, но здесь нужно увидеть весь склад, поэтому запрос переписывают от materials:

SELECT m.code, m.name, COALESCE(SUM(n.qty * oi.qty), 0) AS required
FROM materials AS m
LEFT JOIN norms AS n ON n.material_id = m.material_id
LEFT JOIN order_items AS oi ON oi.product_id = n.product_id
GROUP BY m.material_id, m.code, m.name
ORDER BY required DESC, m.code;

Теперь строк четыре, у краски стоит 0, и это честный ответ: материал есть на складе, но в заказах не используется. COALESCE заменяет NULL на ноль, потому что NULL в отчёте читается как «неизвестно», а не как «ноль единиц».

Умножать агрегаты нельзя

Соблазн записать SUM(n.qty) * SUM(oi.qty) выглядит логично, но считает не то. Для крепежа в заказе 1 правильный ответ 88: две единицы стеллажа по 20 креплений плюс четыре стола по 12, то есть 2*20 + 4*12. Через произведение сумм получается 192: (20+12) * (2+4). Умножать нужно построчно, внутри SUM, иначе суммы разных строк перемножаются между собой.

Задвоений здесь нет, и это можно доказать по ключам. Пара (order_id, product_id) встречается в order_items один раз, пара (product_id, material_id) в norms тоже один раз, поэтому каждая позиция встречается с каждой своей нормой ровно один раз. Если бы в norms не было составного ключа, сумма выросла бы, и никакая проверка этого бы не заметила.

06Задание 4. Топ продуктов и заказы выше среднего

Выручка продукта считается так же, как стоимость заказа, только группировка идёт по продукту. Топ задаётся сортировкой и ограничением числа строк.

SELECT p.code, p.name, SUM(p.price * oi.qty) AS revenue
FROM order_items AS oi
JOIN products AS p ON p.product_id = oi.product_id
GROUP BY p.product_id, p.code, p.name
ORDER BY revenue DESC, p.code
LIMIT 3;
code name revenue
P-02 Стол 112 000
P-04 Полка 56 000
P-03 Шкаф 45 000

Стол на первом месте не из-за цены, а из-за количества: 14 единиц против 3 стеллажей. Полка с ценой 3 500 обогнала стеллаж за 12 000 по той же причине, её заказали в количестве 16 единиц. Выручка всегда зависит от объёма, поэтому «дорогой» и «прибыльный» это разные слова.

Второй ключ сортировки p.code нужен для устойчивости: при равной выручке без него порядок строк не определён, и два запуска могут дать разные тройки.

Заказ выше среднего ищут через подзапрос, который считает средний чек, и HAVING, который фильтрует уже готовые группы:

SELECT o.order_id, o.customer, SUM(p.price * oi.qty) AS total
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.order_id
JOIN products AS p ON p.product_id = oi.product_id
GROUP BY o.order_id, o.customer
HAVING SUM(p.price * oi.qty) > (
  SELECT AVG(total) FROM (
    SELECT SUM(p2.price * oi2.qty) AS total
    FROM order_items AS oi2
    JOIN products AS p2 ON p2.product_id = oi2.product_id
    GROUP BY oi2.order_id
  )
)
ORDER BY total DESC;

Средний чек равен 49 800, выше него оказались три заказа: 65 000, 64 000 и 56 000. Заказ на 36 000 и заказ на 28 000 остались за чертой.

WHERE здесь не подошёл бы: он выполняется до группировки, когда суммы ещё не существует. HAVING работает после GROUP BY и видит агрегат. SQLite разрешает написать HAVING total > ... по псевдониму, но стандарт SQL этого не гарантирует, поэтому в шаблоне использован повтор суммы: запрос переносится в другую СУБД без правок.

07Задание 5. Пропуски

LEFT JOIN сохраняет все строки левой таблицы, даже если пары в правой не нашлось. Проверим, у каждого ли продукта есть нормы расхода:

SELECT p.code, p.name
FROM products AS p
LEFT JOIN norms AS n ON n.product_id = p.product_id
WHERE n.product_id IS NULL;

Запрос вернёт пустой результат, и это правильный ответ: нормы есть у всех четырёх продуктов. Пустая таблица не означает, что запрос сломан, она означает, что пропусков нет. Проверить это утверждение можно, только создав пропуск.

Добавьте продукт без норм и повторите запрос:

INSERT INTO products (product_id, code, name, price)
VALUES (5, 'P-05', 'Табурет', 2500);

Теперь результат содержит одну строку P-05, Табурет, а количество продуктов стало пять. После проверки удалите тестовую строку, чтобы база вернулась в исходное состояние:

DELETE FROM products WHERE product_id = 5;

Условие IS NULL проверяет столбец правой таблицы. Если написать WHERE p.product_id IS NULL, результат всегда будет пустым: слева строки есть по определению, иначе они не попали бы в соединение. Вторая частая ошибка это условие на правую таблицу в WHERE, например WHERE n.qty = 8. Оно отбрасывает строки с NULL и превращает LEFT JOIN обратно в INNER JOIN, только менее заметно.

Та же логика у заказов. Запрос 1 начинает с orders и соединяется с позициями через JOIN, поэтому заказ без единой позиции в результат не попадёт. Проверьте, есть ли такие:

SELECT COUNT(*) AS empty_orders
FROM orders AS o
LEFT JOIN order_items AS oi ON oi.order_id = o.order_id
WHERE oi.order_id IS NULL;

Сейчас ответ 0, и это ожидаемо. Если менеджер создаст заказ и ещё не добавит в него позиции, при INNER JOIN заказ исчезнет из отчёта, а при LEFT JOIN останется с нулевой стоимостью.

08Задание 6. Проверка

Первую цифру проверим руками. Заказ 1 это два стеллажа по 12 000 и четыре стола по 8 000: 2*12000 + 4*8000 = 56 000. Совпало. Крепёж по всем заказам: 2*20 + 4*12 + 1*30 + 6*4 + 1*20 + 2*12 + 8*12 + 2*30 + 10*4 = 382. Тоже совпало, значит, соединение не размножило позиции.

Второй инструмент это подсчёт разных значений. Если строки задвоились, COUNT(*) вырастет, а COUNT(DISTINCT ...) нет:

SELECT COUNT(*) AS rows_total,
       COUNT(DISTINCT order_id) AS orders,
       COUNT(DISTINCT product_id) AS products,
       SUM(qty) AS units
FROM order_items;

Получится 9, 5, 4, 36: девять позиций, пять заказов, четыре разных продукта, тридцать шесть единиц товара. Девять позиций на четыре продукта это нормально, один продукт может стоять в нескольких заказах. А вот если COUNT(DISTINCT order_id) окажется больше пяти, соединение точно что-то размножило.

Третий инструмент это проверочный запрос на долю материала в затратах. Он собирается в два шага: сначала потребность, потом её стоимость.

WITH need AS (
  SELECT n.material_id, SUM(n.qty * oi.qty) AS qty
  FROM order_items AS oi
  JOIN norms AS n ON n.product_id = oi.product_id
  GROUP BY n.material_id
)
SELECT m.code, m.name,
       COALESCE(need.qty, 0) AS qty,
       ROUND(COALESCE(need.qty, 0) * m.price, 0) AS cost,
       ROUND(100.0 * COALESCE(need.qty, 0) * m.price
             / (SELECT SUM(qty * p.price)
                FROM need JOIN materials AS p ON p.material_id = need.material_id), 1) AS share
FROM materials AS m
LEFT JOIN need ON need.material_id = m.material_id
ORDER BY cost DESC;
code name qty cost share
M-02 Дерево 96 67 200 53.1
M-04 Крепёж 382 45 840 36.2
M-01 Металл 30 13 500 10.7
M-03 Краска 0 0 0.0

Сумма затрат 126 540, сумма долей 100.0. Если доли не дают в сумме сотню, ошибка в знаменателе: в него попали не все материалы или попали дважды.

Четвёртый инструмент это план выполнения. Он показывает, как SQLite собирается читать таблицы, и ничего не выполняет:

EXPLAIN QUERY PLAN
SELECT * FROM order_items WHERE product_id = 3;

До индекса план состоит из одной строки SCAN order_items: база читает таблицу целиком. Создайте индекс и повторите:

CREATE INDEX idx_order_items_product ON order_items(product_id);

EXPLAIN QUERY PLAN
SELECT * FROM order_items WHERE product_id = 3;

Теперь в плане SEARCH order_items USING INDEX idx_order_items_product (product_id=?). Слово SCAN означает полный перебор, SEARCH означает поиск по индексу. Строка USE TEMP B-TREE FOR ORDER BY в плане запроса 1 говорит о сортировке во временной структуре, а не о чтении таблицы. На девяти строках разницы по времени нет, и это нормально: индекс нужен не для учебной таблицы, а для таблицы, которая растёт.

Отдельно про автоматические индексы. В плане запроса 2 может появиться USING AUTOMATIC COVERING INDEX: SQLite строит временный индекс сам, на время одного запроса. Такой индекс не сохраняется в файле и не помогает следующему запросу, поэтому явный CREATE INDEX всё равно полезен.
