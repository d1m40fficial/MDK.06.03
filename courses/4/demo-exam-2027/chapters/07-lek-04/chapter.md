## Одна идея

В заказе покупателя №1 от 22 апреля 2026 года два кухонных стола «Самобранка». Продажная сумма строки равна `26828.00`: два изделия по `14120.00` минус скидка `1412.00`. В файле `Расчет стоимости.xlsx` стоит другая сумма, `11448.12`. Нормативный расчёт по спецификации и прайсу даёт третье число, `14374.28`. Все три величины описывают один заказ, но отвечают на разные вопросы.

**Стоимость заказа это вычисляемая величина, а не столбец, который кто-то заполнил вручную.** Её получают из количества изделий, норм расхода материалов, норм времени операций и цен ресурсов. Запрос должен соединить эти сведения так, чтобы каждый ресурс участвовал в сумме ровно один раз.

Формулировка задания 3 приведена в [КИМ](reports/KIM_09.02.07-5-2027.pdf). В задании перечислены количество продукции, стоимость всех материалов и технологических операций с учётом нормы расхода. Продажная цена и скидка в расчёт себестоимости не входят.

## Что дано

Заказ хранится в двух таблицах. `customer_order` содержит номер, дату, заказчика и исполнителя. `customer_order_line` содержит изделие, количество, продажную цену и скидку. В нашем заказе одна строка: изделие с внутренним ключом `1`, код документа `ФР-00000034`, количество `2`, цена `14120.00`, скидка `1412.00`.

Спецификация хранится отдельно. `specification` связывает изделие с его составом и указывает `output_qty`, то есть сколько изделий получается по приведённым нормам. В учебном наборе `output_qty` равно `1`, поэтому нормы относятся к одному столу. Если бы спецификация описывала партию из десяти столов, нормы пришлось бы делить на десять.

`specification_component` содержит строки состава. У каждой строки есть ресурс `item_id`, количество `qty` и норма времени `time_norm`. Для материала `qty` означает норму расхода, а `time_norm` равна единице. Для операции `qty` равна единице, а `time_norm` содержит норму времени в часах. Такое соглашение позволяет хранить материалы и операции в одной таблице и считать их одной формулой.

Цены лежат в `price`. Ключ `(item_id, valid_from)` задаёт историю: у ресурса может быть несколько цен с разными датами действия. Для заказа от 22 апреля 2026 года нужна цена, которая действовала на эту дату, а не самая новая цена вообще.

## Формула

Стоимость одной строки состава:

```text
количество изделий / output_qty × qty × time_norm × цена
```

Для материалов `time_norm` равна единице, поэтому остаётся количество изделий × норма расхода × цена. Для операций `qty` равна единице, поэтому остаётся количество изделий × норма времени × тариф. Общая стоимость заказа это сумма строк состава.

Посчитаем один стол по учебным данным.

| Ресурс | Вид | Норма | Цена | Стоимость |
|---|---|---|---|---|
| Столешница корпус | материал | 1.000 | 3250.00 | 3250.00 |
| Кромка ПВХ 0,4х20 | материал | 2.000 | 95.00 | 190.00 |
| Кромка ПВХ 2х20 | материал | 4.000 | 140.00 | 560.00 |
| Евровинт 7х50 | материал | 0.012 | 595.00 | 7.14 |
| Опора | материал | 4.000 | 220.00 | 880.00 |
| Сборка кухни | операция | 0.750 | 1400.00 | 1050.00 |
| Распиловка, кромление, присадка | операция | 1.500 | 450.00 | 675.00 |
| Упаковка | операция | 0.500 | 950.00 | 475.00 |

Материалы дают `4987.14`, операции `2200.00`, вместе `7187.14` на одно изделие. Для двух изделий сумма удваивается: `14374.28`. Именно это число должен вернуть запрос.

```sql
SELECT 2 * 1 * 3250 AS tabletops,
       2 * 0.012 * 595 AS screws,
       2 * 0.75 * 1400 AS assembly;
```

## JOIN и удвоение строк

Соединение начинается с заказа и идёт по ключам: заказ → строки заказа → спецификация → состав → цена. Каждый переход добавляет столбцы, но не должен размножать строки состава. Это главное правило запроса стоимости.

Соблазн выглядит так: соединить `specification_component` с материалами через одно условие, а с операциями через второе. Тогда каждая материальная строка соединится с каждой операционной. При пяти материалах и трёх операциях получится пятнадцать строк вместо восьми. Сумма посчитает материалы три раза, а операции пять раз.

Проверим на числах. Если материалы `4987.14` умножить на три, получится `14961.42`. Если операции `2200.00` умножить на пять, получится `11000.00`. Вместе `25961.42` на одно изделие, то есть почти вдвое больше правильного ответа. Для двух изделий ошибка станет ещё заметнее.

Правильный путь один: читать `specification_component` как единый список ресурсов, а вид ресурса брать из `item.kind`. Материал и операция отличаются видом и значениями норм, но не требуют отдельных соединений. Одна строка состава даёт одну строку результата.

```sql
SELECT
  o.id AS order_id,
  ROUND(SUM(l.qty / s.output_qty * c.qty * c.time_norm * p.amount), 2) AS total_cost
FROM customer_order o
JOIN customer_order_line l ON l.order_id = o.id
JOIN specification s ON s.product_id = l.product_id
JOIN specification_component c ON c.specification_id = s.id
JOIN price p ON p.item_id = c.item_id
  AND p.valid_from = (
    SELECT MAX(p2.valid_from)
    FROM price p2
    WHERE p2.item_id = c.item_id
      AND p2.valid_from <= o.doc_date
  )
WHERE o.id = 1
GROUP BY o.id;
```

Разберём соединения по одному. `customer_order_line` даёт количество изделий. `specification` находит состав изделия по `product_id`. `specification_component` перечисляет ресурсы. `price` даёт цену ресурса на нужную дату. Если убрать любое соединение, часть суммы исчезнет.

`WHERE o.id = 1` ограничивает расчёт одним заказом. Без него запрос посчитает все заказы, и `GROUP BY o.id` вернёт по строке на каждый. Для отчёта это тоже полезно, но проверять контрольный пример удобнее на одном заказе.

## Цена на дату и агрегация

История цен требует условия по дате. Нельзя соединять `price` только по `item_id`: если у ресурса три цены, каждая строка состава размножится на три. Нельзя брать и `MAX(valid_from)` без ограничения сверху: тогда для старого заказа подставится будущая цена.

Правильное условие выбирает последнюю цену, которая уже действовала на дату заказа:

```sql
p.valid_from = (
  SELECT MAX(p2.valid_from)
  FROM price p2
  WHERE p2.item_id = c.item_id
    AND p2.valid_from <= o.doc_date
)
```

Подзапрос коррелированный: для каждой строки состава он ищет свой ресурс и свою дату. Первичный ключ `(item_id, valid_from)` обслуживает этот поиск, поэтому отдельный индекс не нужен. В учебных данных цена `2026-04-01` действует на `2026-04-22`, и подставляется именно она.

`SUM` складывает стоимости строк, `GROUP BY o.id` собирает их в одну строку на заказ. `ROUND(..., 2)` округляет итог до копеек. Округлять нужно итог, а не каждую строку: иначе ошибки округления накопятся. В учебном примере строка евровинта на одно изделие даёт ровно `7.14`, но при других нормах разница может составить копейки.

Деньги считают в `DECIMAL`, а не в `FLOAT`. Двоичная дробь не хранит 0,1 точно, и сумма из многих строк может дать `14374.279999`. `DECIMAL(14,2)` хранит копейки точно, а `ROUND` приводит результат к двум знакам.

Проверить строки до агрегации можно отдельным запросом. Он показывает ресурс, норму, цену и вклад каждой строки.

```sql
SELECT i.name, i.kind, c.qty, c.time_norm, p.amount,
       ROUND(l.qty / s.output_qty * c.qty * c.time_norm * p.amount, 2) AS line_cost
FROM customer_order o
JOIN customer_order_line l ON l.order_id = o.id
JOIN specification s ON s.product_id = l.product_id
JOIN specification_component c ON c.specification_id = s.id
JOIN price p ON p.item_id = c.item_id
  AND p.valid_from = (
    SELECT MAX(p2.valid_from)
    FROM price p2
    WHERE p2.item_id = c.item_id
      AND p2.valid_from <= o.doc_date
  )
WHERE o.id = 1
ORDER BY i.kind, i.id;
```

Восемь строк этого запроса в сумме дают `14374.28`. Если строк семь или девять, состав и цены не совпадают с ожиданием.

## Полнота данных и допущения

Если у ресурса нет подходящей цены, соединение с `price` не найдёт строку, и `SUM` молча занизит итог. Это опаснее ошибки: запрос вернёт число, и его примут за правильное. Поэтому перед расчётом проверяют полноту.

```sql
SELECT i.id, i.name
FROM specification_component c
JOIN item i ON i.id = c.item_id
WHERE c.specification_id = 1
  AND NOT EXISTS (
    SELECT 1
    FROM price p
    WHERE p.item_id = c.item_id
      AND p.valid_from <= '2026-04-22'
  );
```

Запрос должен вернуть ноль строк. Если он вернул ресурс, цену добавляют в `price` с датой, которая не позже даты заказа, и повторяют расчёт. Заменять отсутствующую цену нулём нельзя: ноль означает бесплатный ресурс, а не неизвестную цену.

Отдельно проверяют наличие спецификации у каждого изделия заказа.

```sql
SELECT l.id
FROM customer_order_line l
WHERE NOT EXISTS (
  SELECT 1
  FROM specification s
  WHERE s.product_id = l.product_id
);
```

Тоже ноль строк. Если спецификации нет, изделие не участвует в сумме, и заказ выглядит дешевле.

Теперь о допущениях. В исходных документах есть расхождения, и запрос не должен их скрывать. Единицы евровинта и опоры в заказе на производство расходятся со спецификацией. Для расчёта приняты единицы спецификации: евровинт в тысячах штук, опора в штуках. Тариф операции отнесён к часу, норма времени берётся из спецификации, упаковка тоже считается операцией. Цена `2026-04-01` действует на дату заказа. Эти решения записывают рядом с запросом, потому что при другом толковании итог изменится.

| Допущение | Значение | Почему |
|---|---|---|
| Единицы евровинта | тыс. шт | так указано в спецификации |
| Единицы опоры | шт | так указано в спецификации |
| Тариф операции | за час | в прайсе нет единицы тарифа |
| Упаковка | операция | входит в состав |
| Дата цены | 2026-04-01 | действует на 2026-04-22 |
| `output_qty` | 1 | нормы даны на одно изделие |

Продажная сумма `26828.00` не равна стоимости `14374.28`, и это нормально. Первая величина включает цену продажи и скидку, вторая описывает затраты по нормам. Файл `Расчет стоимости.xlsx` даёт `11448.12`, и это число не согласуется с текущими нормами и прайсом. Подгонять запрос под него нельзя: в пояснении фиксируют расхождение и выбранный источник.

## Итоги

- Стоимость заказа вычисляют из количества, норм и цен, а не берут из продажной суммы.
- Материалы и операции читают из одной таблицы состава, иначе соединения перемножают строки.
- Цену выбирают на дату заказа, а не самую новую.
- Перед `SUM` проверяют, что у каждого ресурса есть цена и спецификация.
- Итог округляют один раз, после суммирования, и сравнивают с ручным контрольным примером.

## Проверьте себя

> [!CHECK] Почему после двух JOIN по видам ресурсов сумма стала больше?
> Каждая материальная строка соединилась с каждой операционной. Материалы посчитались столько раз, сколько операций, а операции столько раз, сколько материалов.

> [!CHECK] Что вернёт запрос, если у одного ресурса нет цены?
> Соединение с price не найдёт строку, и SUM занизит итог. Поэтому сначала выполняют проверку NOT EXISTS и только потом считают сумму.

> [!CHECK] Почему 26828 и 14374.28 не должны совпадать?
> 26828 это продажная сумма со скидкой, а 14374.28 это нормативная стоимость по спецификации и прайсу. Это разные величины.

Q: Из чего складывается полная стоимость заказа?
+ Количество изделий, нормы расхода и цены ресурсов
- Только продажная цена и скидка
- Только стоимость материалов
- Только тариф рабочих операций
! В сумму входят и материалы, и технологические операции с учётом норм.

Q: Как считается вклад строки состава?
+ Количество изделий / output_qty × qty × time_norm × цена
- Количество изделий × цена продажи
- Цена ресурса / количество изделий
- Сумма всех цен без норм
! Формула учитывает количество выпуска, норму и цену.

Q: Почему материалы и операции нельзя соединять двумя отдельными JOIN?
+ Строки перемножатся и сумма удвоится
- Запрос не выполнится из-за синтаксиса
- Пропадёт кодировка utf8mb4
- Цена станет нулевой
! Каждая материальная строка соединится с каждой операционной.

Q: Что делает GROUP BY o.id?
+ Собирает строки состава в один итог по заказу
- Сортирует ресурсы по названию
- Удаляет повторные цены
- Создаёт внешний ключ
! Группировка нужна для SUM по заказу.

Q: Как выбрать цену, действовавшую на дату заказа?
+ MAX(valid_from) с условием valid_from <= дата заказа
+ Подзапрос по item_id и дате
- Самую новую цену без ограничения даты
- Среднюю цену всех периодов
! Нужна последняя цена, которая уже действовала на дату заказа.

Q: Что произойдёт, если у ресурса нет цены на дату заказа?
+ Строка выпадет из соединения, и SUM занизит итог
- Цена автоматически станет нулевой
- Запрос вернёт ошибку синтаксиса
- Сервер создаст цену сам
! Поэтому перед расчётом проверяют полноту через NOT EXISTS.

Q: Зачем нужен output_qty?
+ Показывает, на сколько изделий даны нормы
- Задаёт скидку на заказ
- Хранит номер спецификации
- Определяет валюту
! Если нормы даны на партию, их делят на размер партии.

Q: Что хранит time_norm у операции?
+ Норму времени в часах
- Цену операции
- Количество изделий
- Код ресурса
! Тариф умножается на норму времени.

Q: Почему деньги считают в DECIMAL?
+ DECIMAL хранит копейки точно
- DECIMAL быстрее FLOAT
- FLOAT не поддерживает рубли
- DECIMAL автоматически округляет до целого
! FLOAT хранит двоичную дробь и накапливает ошибку.

Q: Какие данные нужны для запроса стоимости?
+ Строки заказа с количеством
+ Спецификация с нормами
+ Цены ресурсов на дату
+ Вид ресурса
- Пароль пользователя базы
- Цвет интерфейса
! Нужны количество, нормы, цены и различие материалов и операций.

Q: Что проверить перед выполнением SUM?
+ Наличие спецификации у изделия
+ Наличие цены у каждого ресурса
+ Число строк соединения
- Порядок строк в JSON
- Имя пользователя Windows
! Проверка полноты не даёт занизить итог.

Q: Что означает число 14374.28?
+ Нормативную стоимость двух изделий
- Продажную сумму заказа
- Скидку по заказу
- Стоимость одной операции
! Это сумма материалов и операций для двух столов.

Q: Почему продажная сумма 26828 не равна стоимости?
+ Она включает цену продажи и скидку, а не нормы затрат
- Она посчитана в другой валюте
- Она не включает количество
- Она относится к другому заказу

= количество изделий / output_qty * qty * time_norm * цена
= l.qty / s.output_qty * c.qty * c.time_norm * p.amount
