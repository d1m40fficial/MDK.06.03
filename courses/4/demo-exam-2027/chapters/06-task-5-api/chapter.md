## Что требуется

Нужно сделать небольшой HTTP-сервис, который читает заметки сотрудников из базы и отдаёт их в JSON. Сервис не рисует окон и не показывает таблиц: у него есть адрес, по которому браузер или Postman отправляет запрос, и есть ответ с данными или с описанием ошибки.

Требования короткие и все проверяются на экране.

- В базе есть таблица `notes` с тремя или пятью записями.
- У таблицы есть внешний ключ `notes.id_user` на `users.id`.
- Сервис отвечает на `GET /notes` или на `GET /api/notes`.
- В ответе у каждой заметки ровно четыре поля: `id`, `title_user`, `content`, `formatted_date`.
- Поле `title_user` собирается из заголовка и логина автора, между ними дефис с пробелами.
- Поле `content` передаётся без изменений.
- Поле `formatted_date` приходит в формате ДД.ММ.ГГГГ.
- Обычный запрос даёт код 200 и массив объектов.
- Запрос без подходящих записей даёт код 200 и пустой массив `[]`.
- Неверный параметр даёт код 400 и JSON с полем `error`.
- Сбой базы даёт код 500 и JSON с полем `error`.
- Коллекция Postman содержит запросы и исполняемые проверки для 200, 400 и 500.

Сдаются четыре вещи: проект API, SQL-скрипт таблицы `notes` с тестовыми записями, экспортированная коллекция Postman и короткий протокол проверки. Протокол это таблица, где напротив каждой проверки записан фактический код и фактическое тело ответа.

Отдельно обратите внимание на слово «контракт». Это список договорённостей: имена полей, их типы и смысл каждого кода. Если сервис вернул правильные данные, но назвал поле `titleUser` вместо `title_user`, клиент сломается.

## Как устроено задание

Разберём путь одного запроса. Браузер отправляет `GET http://127.0.0.1:5271/notes`. Процесс API принимает запрос, открывает соединение с MySQL, выполняет `SELECT`, получает строки, превращает каждую строку в объект с четырьмя полями и отправляет массив обратно. Браузер показывает JSON как обычный текст.

В этом пути три участника. Клиент отправляет запрос и ничего не знает про таблицы. Сервер решает, что вернуть. База хранит строки. Ошибка может возникнуть у каждого, и код ответа говорит, где искать причину.

| Код | Кто виноват | Что делать клиенту | Тело ответа |
|---|---|---|---|
| 200 | Никто, всё прошло | Читать массив | Массив объектов или `[]` |
| 400 | Клиент | Исправить параметры запроса | Объект с полем `error` |
| 500 | Сервер | Повторить позже, сообщить разработчику | Объект с полем `error` |

Код 200 означает успешную обработку, а не наличие данных. Пустой массив это нормальный ответ: запрос корректен, записей просто нет. Код 404 здесь был бы неправдой, потому что адрес `/notes` существует и отвечает.

Код 400 ставят, когда клиент прислал то, что сервер не может разобрать. В учебном сервисе есть необязательный параметр `user_id`, и он даёт удобный повод для проверки: строка `abc`, ноль, повтор параметра и неизвестное имя параметра приводят к 400. Код 500 ставят, когда сбой произошёл на сервере: база недоступна, запрос упал, соединение оборвалось.

Теперь про поля ответа. Два из четырёх в таблице не хранятся.

| Поле | Тип | Откуда берётся |
|---|---|---|
| `id` | число | Столбец `id` таблицы `notes` |
| `title_user` | строка | Заголовок, дефис с пробелами, логин автора |
| `content` | строка | Столбец `content` без изменений |
| `formatted_date` | строка | Столбец `created_at`, приведённый к виду ДД.ММ.ГГГГ |

Хранить `title_user` и `formatted_date` в таблице нельзя. Логин автора может измениться, и сохранённая строка устареет. Дата в базе имеет один тип, а клиенту нужен другой вид. Оба значения вычисляются в момент ответа, поэтому в таблице их нет и искать там нечего.

Сервис удобно делать на минимальном API ASP.NET Core. В этом стиле нет контроллеров и папок с классами: маршрут и обработчик описываются прямо в `Program.cs`. Для одного метода этого достаточно, а читать такой файл проще, чем три отдельных.

### Шаг 1. Проверьте таблицу users

Откройте phpMyAdmin, выберите слева базу `dkip2027_course` и найдите таблицу `users`. Она появилась в задании с приложением и ролями. Если таблицы ещё нет, создайте её тем же скриптом, что и в задании 4. Он безопасен для существующей таблицы: `IF NOT EXISTS` ничего не меняет, а `INSERT IGNORE` добавляет только недостающих сотрудников.

```sql
CREATE TABLE IF NOT EXISTS users (
  id INT AUTO_INCREMENT PRIMARY KEY,
  login VARCHAR(64) NOT NULL UNIQUE,
  password_hash VARBINARY(32) NOT NULL,
  salt VARBINARY(16) NOT NULL,
  role ENUM('admin','user') NOT NULL DEFAULT 'user',
  failed_attempts INT NOT NULL DEFAULT 0,
  is_locked BOOLEAN NOT NULL DEFAULT FALSE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

INSERT IGNORE INTO users (login, password_hash, salt, role) VALUES
('manager', UNHEX('00'), UNHEX('00'), 'user'),
('technologist', UNHEX('00'), UNHEX('00'), 'user'),
('master', UNHEX('00'), UNHEX('00'), 'user');
```

Хеш и соль здесь нулевые, потому что для задания 5 нужен только логин автора. Настоящие пароли сотрудников задаются в приложении из задания 4. Если вы ещё не делали приложение, эти записи всё равно подойдут: API не проверяет пароль.

Выполните проверку и запомните номера:

```sql
SELECT id, login FROM users ORDER BY id;
```

В результате должно быть три строки с разными номерами. Эти номера понадобятся при вставке заметок. Если логины называются иначе, используйте свои, но тогда поменяйте и данные в `INSERT` на следующем шаге.

### Шаг 2. Создайте таблицу notes

Откройте вкладку `SQL`, вставьте скрипт и нажмите `Выполнить` справа внизу.

```sql
USE dkip2027_course;

CREATE TABLE IF NOT EXISTS notes (
  id INT AUTO_INCREMENT PRIMARY KEY,
  title VARCHAR(120) NOT NULL,
  content TEXT NOT NULL,
  id_user INT NOT NULL,
  created_at DATE NOT NULL,
  CONSTRAINT fk_notes_user FOREIGN KEY (id_user) REFERENCES users(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

Разберём строки. `id` это первичный ключ, он различает заметки и растёт сам. `title` хранит заголовок, ограничение `NOT NULL` запрещает пустое значение. `content` имеет тип `TEXT`, потому что текст заметки может быть длинным. `id_user` хранит номер автора. `created_at` имеет тип `DATE`, а не `DATETIME`: в задании нужна дата без времени, и лишние часы только создают повод для ошибки формата.

Последняя строка задаёт внешний ключ. Она не даёт вставить заметку с номером пользователя, которого нет в `users`. Без этого ограничения `JOIN` молча потеряет строку, и заметка исчезнет из ответа без сообщения об ошибке.

Проверьте связь: попробуйте вставить заметку с несуществующим автором.

```sql
INSERT INTO notes (title, content, id_user, created_at)
VALUES ('Проверка ключа', 'Такой автор не должен существовать', 999, '2027-03-16');
```

MySQL должен отказать с сообщением о нарушении внешнего ключа. Запись не появилась, и это правильный результат.

### Шаг 4. Проверьте чтение через JOIN

API нужен логин автора, а он лежит в `users`. Соедините таблицы тем запросом, который потом попадёт в код.

```sql
SELECT n.id, n.title, u.login, n.content, n.created_at
FROM notes n
JOIN users u ON u.id = n.id_user
ORDER BY n.id;
```

У каждой строки должны быть и заголовок, и логин. Сортировка по `id` делает ответ предсказуемым: без `ORDER BY` порядок строк не гарантирован, и тест, сравнивающий первый элемент, может пройти сегодня и упасть завтра.

### Шаг 7. Напишите Program.cs

Откройте `Program.cs` в редакторе, удалите всё содержимое и вставьте код ниже. Он полный, ничего дописывать не нужно.

```csharp
using System.Globalization;
using MySqlConnector;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();
var app = builder.Build();

app.UseSwagger();
app.UseSwaggerUI();

// Блок 1. Строка подключения. Значение берём из переменной окружения,
// чтобы пароль не попадал в исходники.
string connectionString =
    Environment.GetEnvironmentVariable("DKIP_CONNECTION")
    ?? "Server=127.0.0.1;Database=dkip2027_course;User ID=root;Password=;Character Set=utf8mb4";

// Блок 2. Общий перехват исключений. Любой сбой превращается в 500 и короткий JSON.
app.Use(async (context, next) =>
{
    try
    {
        await next();
    }
    catch (Exception ex)
    {
        app.Logger.LogError(ex, "Ошибка обработки API");
        context.Response.StatusCode = 500;
        await context.Response.WriteAsJsonAsync(new
        {
            error = "Ошибка подключения к базе данных или обработки запроса"
        });
    }
});

// Блок 3. Чтение заметок. Один запрос, преобразование каждой строки в объект.
List<object> ReadNotesFromDatabase(int? userId)
{
    var result = new List<object>();

    using var connection = new MySqlConnection(connectionString);
    connection.Open();

    string sql = """
        SELECT n.id, n.title, u.login, n.content, n.created_at
        FROM notes n
        JOIN users u ON u.id = n.id_user
        """;

    if (userId is not null)
        sql += " WHERE n.id_user = @userId";

    sql += " ORDER BY n.id";

    using var command = new MySqlCommand(sql, connection);
    if (userId is not null)
        command.Parameters.AddWithValue("@userId", userId);

    using var reader = command.ExecuteReader();
    while (reader.Read())
    {
        string title = reader.GetString("title");
        string login = reader.GetString("login");

        result.Add(new
        {
            id = reader.GetInt32("id"),
            title_user = title + " - " + login,
            content = reader.GetString("content"),
            formatted_date = reader.GetDateTime("created_at")
                .ToString("dd.MM.yyyy", CultureInfo.InvariantCulture)
        });
    }

    return result;
}

// Блок 4. Проверка параметров и ответ.
IResult HandleGetNotes(HttpRequest request)
{
    int? userId = null;

    if (request.Query.Keys.Any(key => key != "user_id"))
    {
        return Results.BadRequest(new
        {
            error = "Неизвестный параметр. Допустим user_id."
        });
    }

    if (request.Query.ContainsKey("user_id"))
    {
        if (request.Query["user_id"].Count != 1
            || !int.TryParse(request.Query["user_id"], out int parsed)
            || parsed <= 0)
        {
            return Results.BadRequest(new
            {
                error = "user_id должен быть положительным целым числом"
            });
        }

        userId = parsed;
    }

    return Results.Ok(ReadNotesFromDatabase(userId));
}

// Блок 5. Два адреса ведут к одному обработчику.
app.MapGet("/notes", HandleGetNotes);
app.MapGet("/api/notes", HandleGetNotes);

// Короткий адрес для файла описания: удобно открывать и указывать в документации.
app.MapGet("/openapi.json", () => Results.Redirect("/swagger/v1/swagger.json"));

app.Run();
```

Разберём блоки по порядку.

**Блок 1.** `WebApplication.CreateBuilder` готовит приложение, `Build` собирает его. Строка подключения читается из переменной окружения `DKIP_CONNECTION`. Если переменной нет, берётся значение по умолчанию для локального стенда.

**Блок 2.** `app.Use` вставляет обработчик в начало цепочки. Он вызывает `next`, то есть пропускает запрос дальше, и ловит любое исключение. Без него ASP.NET Core вернёт 500 с пустым телом или страницей разработчика, и проверка «JSON ошибки» не пройдёт. Подробности пишутся в консоль сервера, клиент получает общую фразу без строки подключения.

**Блок 3.** `MySqlConnection` открывает соединение, `MySqlCommand` выполняет запрос, `MySqlDataReader` читает строки по одной. Условие `WHERE` добавляется только при наличии фильтра. Значение передаётся через `AddWithValue`, а не склейкой текста: параметр отделяет данные от команды и работает при любом вводе.

Внутри цикла строка превращается в анонимный объект. Имена свойств становятся именами полей JSON, поэтому здесь нельзя ошибиться в регистре: `title_user` и `TitleUser` дадут разные ответы. Дата приводится к виду `dd.MM.yyyy` с `CultureInfo.InvariantCulture`. Без инвариантной культуры на другой машине разделитель может стать другим.

**Блок 4.** Сначала проверяются параметры, потом идёт обращение к базе. Неизвестное имя параметра даёт 400. Повтор, нечисловое значение и ноль тоже дают 400. Если параметра нет, `userId` остаётся пустым и возвращается весь список. `Results.Ok` с пустым списком сам отдаёт `[]`, отдельная ветка для пустого результата не нужна.

**Блок 5.** `MapGet` связывает адрес с обработчиком. Два вызова дают два рабочих адреса с одинаковым поведением. Если в задании достаточно одного, второй можно убрать, но тогда его не должно быть и в документации.

**Swagger.** Четыре строки в начале файла включают описание API. `AddEndpointsApiExplorer` собирает сведения о маршрутах, `AddSwaggerGen` строит из них документ OpenAPI, `UseSwagger` отдаёт его по адресу `/swagger/v1/swagger.json`, а `UseSwaggerUI` открывает страницу `/swagger`. Эта страница понадобится в задании 6: на ней видно пути, параметры и коды, а кнопка `Try it out` отправляет настоящий запрос.

### Шаг 9. Проверьте успешный ответ и пустой массив

Откройте в браузере `http://127.0.0.1:5271/notes`. Ответ должен начинаться с квадратной скобки и содержать пять объектов.

```json
[
  {
    "id": 1,
    "title_user": "Заказ принят - manager",
    "content": "Заказ V01-01: Фартук поварской, 12 ед.; срок 22.03.2027.",
    "formatted_date": "16.03.2027"
  }
]
```

Сверьте каждое поле. `id` совпадает с номером строки в таблице. `title_user` содержит заголовок, дефис с пробелами и логин. `content` совпадает с текстом в базе посимвольно, включая точку с запятой. `formatted_date` содержит точки и не содержит часов.

Затем проверьте пустой результат. Откройте `http://127.0.0.1:5271/notes?user_id=999`. Такого автора в базе нет, поэтому ответом должен быть код 200 и тело `[]`. В браузере тело видно сразу, код можно посмотреть в Postman или во вкладке `Сеть` инструментов разработчика.

Если приходит 404, обработчик не зарегистрирован по этому адресу. Если приходит 500, смотрите консоль сервера: чаще всего неверно имя базы или не запущен MySQL. Если приходит `null`, вместо списка возвращается пустое значение, и это ошибка контракта.

### Шаг 12. Создайте коллекцию Postman

Откройте Postman. Нажмите `New`, затем `Collection`. Введите имя `Dkip API заметки` и нажмите `Create`.

Откройте коллекцию и перейдите на вкладку `Variables`. Добавьте две переменные.

| Переменная | Начальное значение | Зачем |
|---|---|---|
| `base_url` | `http://127.0.0.1:5271` | Рабочий экземпляр |
| `error_url` | `http://127.0.0.1:5281` | Экземпляр с неверным подключением |

Переменные наследуются всеми запросами коллекции. Если вписать адрес в каждый запрос отдельно, при смене порта придётся править четыре места и легко пропустить одно.

Теперь добавьте запросы. Нажмите правой кнопкой по имени коллекции, выберите `Add request`. В открывшейся вкладке задайте метод `GET` и адрес `{{base_url}}/notes`. Сохраните запрос по `Ctrl+S` и дайте ему имя `Список заметок`.

Сделайте так же ещё три запроса.

| Имя запроса | Метод и адрес | Ожидание |
|---|---|---|
| Список заметок | `GET {{base_url}}/notes` | 200, массив из пяти объектов |
| Пустой список | `GET {{base_url}}/notes?user_id=999` | 200, `[]` |
| Неверный параметр | `GET {{base_url}}/notes?user_id=abc` | 400, поле `error` |
| Сбой подключения | `GET {{error_url}}/notes` | 500, поле `error` |

Нажмите `Send` в первом запросе. В нижней части окна появятся вкладки с результатом. `Body` показывает тело, `Headers` заголовки, `Test Results` результаты проверок. Пока проверок нет, эта вкладка пуста.

### Шаг 13. Добавьте проверки во вкладку Tests

В новых версиях Postman вкладка называется `Scripts`, а нужный раздел внутри неё `Post-response`. В более старых версиях это отдельная вкладка `Tests`. Смысл один: код выполняется после получения ответа.

Откройте запрос `Список заметок`, перейдите в `Tests` и вставьте код.

```javascript
pm.test("Статус 200", () => pm.response.to.have.status(200));

const body = pm.response.json();

pm.test("Ответ это массив", () => pm.expect(body).to.be.an("array"));

pm.test("Поля заметки", () => {
    body.forEach(note => {
        pm.expect(note).to.have.all.keys("id", "title_user", "content", "formatted_date");
        pm.expect(note.id).to.be.a("number");
        pm.expect(note.title_user).to.be.a("string");
        pm.expect(note.content).to.be.a("string");
    });
});

pm.test("Формат даты", () => {
    body.forEach(note =>
        pm.expect(note.formatted_date).to.match(/^\d{2}\.\d{2}\.\d{4}$/));
});
```

Разберём строки. `pm.test` объявляет проверку с понятным именем. `pm.response.to.have.status(200)` сравнивает код. `pm.response.json()` разбирает тело и заодно убеждается, что это валидный JSON: если сервер вернул HTML, тест упадёт уже здесь. `all.keys` требует ровно четыре поля и ловит лишние. Регулярное выражение проверяет две цифры, точку, две цифры, точку и четыре цифры.

Для запроса `Пустой список` проверки короче.

```javascript
pm.test("Статус 200", () => pm.response.to.have.status(200));
pm.test("Пустой массив", () => {
    const body = pm.response.json();
    pm.expect(body).to.be.an("array");
    pm.expect(body).to.have.lengthOf(0);
});
```

Для запроса `Неверный параметр`:

```javascript
pm.test("Статус 400", () => pm.response.to.have.status(400));
pm.test("JSON с полем error", () => {
    pm.expect(pm.response.json()).to.have.property("error");
});
```

Для запроса `Сбой подключения`:

```javascript
pm.test("Статус 500", () => pm.response.to.have.status(500));
pm.test("JSON с полем error", () => {
    pm.expect(pm.response.json()).to.have.property("error");
});
```

Нажмите `Send` в каждом запросе и откройте `Test Results`. Все проверки должны быть зелёными. Вкладка показывает пройденные и упавшие проверки.

Проверьте, что тесты умеют падать. Временно уберите разделитель в коде API, замените `title + " - " + login` на `title + login`, перезапустите сервер и отправьте запрос снова. Тест полей упадёт. Верните разделитель и повторите запуск.

## Частые ошибки

**500 на пустом списке.** Пустой результат принимают за сбой и возвращают ошибку. Клиент видит аварию там, где данных просто нет. Правильный ответ это 200 и `[]`.

**Дата в формате ISO.** `ToString()` без шаблона даёт `2027-03-16T00:00:00`. Нужен явный шаблон `dd.MM.yyyy` и `CultureInfo.InvariantCulture`, иначе на другой машине появится другой разделитель.

**Склейка без разделителя.** `title_user` получается слитным, например `Заказ принятmanager`. Проверка формата не проходит, а глазами ошибку легко пропустить.

**Лишние поля.** В ответ попадают `id_user`, `created_at` или `login`. Контракт нарушен, хотя данные верные. Проверка `all.keys` ловит это сразу.

**Заглушка вместо базы.** API возвращает заранее записанный массив и не читает `notes`. Проверка с новой записью сразу это показывает: добавьте заметку в phpMyAdmin и обновите страницу.

**Тесты только на 200.** Коллекция не воспроизводит 400 и 500, поэтому половина требований не подтверждена. В коллекции должно быть четыре запроса, а не один.

**Один объект вместо массива.** При одной записи возвращают объект, при нескольких массив. Клиент ломается на первом же изменении данных. Ответ всегда массив, даже если в нём ноль или один элемент.

**Адрес вписан в каждый запрос.** При смене порта часть запросов уходит на старый адрес, и половина тестов падает без причины. Используйте переменную `base_url`.
