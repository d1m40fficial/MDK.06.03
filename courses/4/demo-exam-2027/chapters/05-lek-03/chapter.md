## Одна идея

ER-диаграмма описывает данные на бумаге. Сервер базы данных делает те же правила обязательными: он не примет строку без обязательного поля, не позволит сослаться на несуществующего заказчика и сохранит код с ведущими нулями, если столбец объявлен текстовым. Задание 2 проверяет именно это: не рисунок таблиц, а работающую базу, в которую импортированы данные из файла `Заказчики.json`.

**База данных это набор таблиц вместе с ограничениями, которые сервер проверяет при каждой записи.** Таблица без первичного ключа, внешнего ключа и проверок остаётся хранилищем строк, но не моделью предприятия. Ограничения дороже на этапе проектирования и дешевле на этапе эксплуатации: они не дают ошибке попасть в данные.

Формулировка задания 2 и перечень документов приведены в [КИМ](reports/KIM_09.02.07-5-2027.pdf). В работе участвуют те же файлы, что и в задании 1: заказ покупателя, спецификация, цены, расчёт стоимости и JSON заказчиков.

## Сервер, клиент и phpMyAdmin

MySQL это отдельная служба. Она слушает порт 3306 и хранит данные в своих файлах. phpMyAdmin это веб-приложение на PHP, которое открывается в браузере по адресу `http://localhost/phpmyadmin` и передаёт команды серверу. Ему нужен Apache, потому что PHP выполняется веб-сервером. Поэтому в XAMPP запускают обе службы: Apache для phpMyAdmin, MySQL для данных.

Если MySQL не поднимается, Control Panel показывает занятый порт и кнопку `Netstat`. Второй сервер на том же порту запускать не нужно. Если Apache не поднимается, phpMyAdmin не откроется, хотя база при этом может быть доступна из консольного клиента. Это разные отказы, и лечатся они по-разному.

На учебном стенде `root` входит без пароля. Для задания 2 этого достаточно: студент создаёт схему и импортирует данные. Для приложения из следующего задания так делать нельзя, потому что `root` не ограничен ни одной базой. Учётную запись приложения заводят отдельно и выдают ей только нужные права.

В сборке XAMPP сервер собран на MariaDB. Команды MySQL и типы данных работают так же, но версия сервера и некоторые коды ошибок отличаются от MySQL 8. Поэтому в протоколе указывают версию, которую вернул `SELECT VERSION();`, а не предполагаемую.

## База и кодировка

База создаётся один раз, до таблиц. Имя `dkip2027_course` выбрано так, чтобы его было легко узнать в списке и в строке подключения.

```sql
CREATE DATABASE dkip2027_course
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

SHOW CREATE DATABASE dkip2027_course;
```

`utf8mb4` это полный UTF-8 до четырёх байт на символ. Старое имя `utf8` в MySQL означает три байта и не вмещает часть символов. На учебных данных разница не видна, пока в наименовании не появится редкий символ, но исправлять кодировку после импорта придётся вместе с данными. Сравнение `utf8mb4_unicode_ci` не различает регистр и правильно сортирует кириллицу. Сравнение `utf8mb4_general_ci` быстрее, но менее точно; главное, чтобы оно было одинаковым у базы, таблиц и соединения.

<figure class="diagram">

Кодировка задаётся на трёх уровнях: сервер, база и соединение. База задаёт значение по умолчанию для новых таблиц. Соединение объявляет кодировку клиента. Если клиент прислал однобайтовый текст, сервер перекодирует его и вернёт знаки вопроса. Поэтому в строке подключения указывают `Character Set=utf8mb4`, а не полагаются только на настройку базы.

## Таблицы и типы

Схема задания 2 повторяет ER-диаграмму. В учебном наборе семь основных таблиц: контрагенты, ресурсы, цены, спецификация, состав спецификации, заказ и строки заказа. Этого достаточно, чтобы импортировать заказчиков и посчитать стоимость заказа в следующем задании. Производственные таблицы, пользователи и заметки добавляются, когда появляются соответствующие документы и модули.

| Сущность | Первичный ключ | Внешние ключи | Что хранит |
|---|---|---|---|
| `counterparty` | `id` | нет | заказчики, исполнители, поставщики |
| `item` | `id` | нет | продукция, материалы, операции |
| `price` | `item_id`, `valid_from` | `item_id` | историю цен ресурса |
| `specification` | `id` | `product_id`, `manufacturer_id` | состав изделия |
| `specification_component` | `specification_id`, `item_id` | `specification_id`, `item_id` | нормы расхода и времени |
| `customer_order` | `id` | `customer_id`, `executor_id` | шапку заказа |
| `customer_order_line` | `id` | `order_id`, `product_id` | строки заказа |

Тип выбирают по смыслу, а не по удобству. Деньги хранят в `DECIMAL(14,2)`, количество и нормы времени в `DECIMAL(14,3)`. `FLOAT` и `DOUBLE` хранят двоичную дробь, поэтому 0,1 в них не равно 0,1, и сумма из сотни строк может разойтись с ручным расчётом. `DATE` хранит дату без времени, `VARCHAR` текст ограниченной длины, `INT` целое.

Отдельно решается судьба кода заказчика. В JSON коды выглядят как `00000001`, `00000008`, `00000010`. Если объявить столбец целым, ведущие нули исчезнут: `00000008` станет `8`. Если объявить `VARCHAR(32)`, код сохранится символ в символ. Текстовыми также делают ИНН и телефон: ИНН может начинаться с нуля, телефон содержит плюс, а арифметика над ними не нужна.

```sql
CREATE TABLE counterparty (
  id VARCHAR(32) NOT NULL,
  name VARCHAR(255) NOT NULL,
  inn VARCHAR(20) NOT NULL,
  address VARCHAR(500) NOT NULL,
  phone VARCHAR(64) NOT NULL,
  party_type VARCHAR(24) NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE item (
  id INT AUTO_INCREMENT NOT NULL,
  code VARCHAR(64) UNIQUE NOT NULL,
  name VARCHAR(255) NOT NULL,
  kind VARCHAR(16) NOT NULL,
  unit VARCHAR(16) NOT NULL,
  PRIMARY KEY (id),
  CONSTRAINT ck_item_kind CHECK (kind IN ('product', 'material', 'operation'))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`AUTO_INCREMENT` подходит для внутренних ключей, которые создаёт сама база. Внешний код из документа лучше не делать автоинкрементным: его значение задаёт источник, а не сервер.

## Ограничения

Ограничение это правило, которое сервер проверяет до записи. Основные виды перечислены в таблице.

| Ограничение | Что запрещает | Пример |
|---|---|---|
| `PRIMARY KEY` | повтор ключа и пустое значение | `id` различает строки |
| `FOREIGN KEY` | ссылку на отсутствующую строку | строка заказа ссылается на заказ |
| `NOT NULL` | пустое значение | имя заказчика обязательно |
| `UNIQUE` | повтор значения | код ресурса не повторяется |
| `CHECK` | значение вне диапазона | количество больше нуля |
| `DEFAULT` | отсутствие значения | дата создания по умолчанию |

Первичный ключ может быть составным. В `price` ключ `(item_id, valid_from)` означает, что у ресурса не может быть двух цен с одной даты, но может быть много цен с разными датами. В `specification_component` ключ `(specification_id, item_id)` не даёт дважды указать один ресурс в одной спецификации. Это не формальность: без такого ключа запрос стоимости посчитает ресурс дважды.

Внешний ключ связывает строку с родителем. По умолчанию MySQL запрещает удалить родителя, пока на него ссылаются, и запрещает вставить ребёнка с несуществующим родителем. Это поведение `RESTRICT`. `ON DELETE CASCADE` удаляет детей вместе с родителем и подходит только там, где дети не имеют самостоятельного смысла. Для заказа и строк заказа лучше запретить удаление, чем потерять документ.

```sql
CREATE TABLE price (
  item_id INT NOT NULL,
  valid_from DATE NOT NULL,
  amount DECIMAL(14,2) NOT NULL,
  PRIMARY KEY (item_id, valid_from),
  CONSTRAINT fk_price_item FOREIGN KEY (item_id) REFERENCES item(id),
  CONSTRAINT ck_price_amount CHECK (amount >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE customer_order_line (
  id INT AUTO_INCREMENT NOT NULL,
  order_id INT NOT NULL,
  product_id INT NOT NULL,
  source_code VARCHAR(64) NOT NULL,
  qty DECIMAL(14,3) NOT NULL,
  sale_price DECIMAL(14,2) NOT NULL,
  discount DECIMAL(14,2) NOT NULL,
  PRIMARY KEY (id),
  CONSTRAINT fk_line_order FOREIGN KEY (order_id) REFERENCES customer_order(id),
  CONSTRAINT fk_line_product FOREIGN KEY (product_id) REFERENCES item(id),
  CONSTRAINT ck_line_qty CHECK (qty > 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Порядок создания важен: сначала родительские таблицы `counterparty`, `item`, `customer_order`, потом зависимые `price`, `specification`, `specification_component`, `customer_order_line`. Сервер не может проверить внешний ключ на таблицу, которой ещё нет.

Проверки `CHECK` работают в MySQL начиная с версии 8.0.16, в MariaDB начиная с 10.2. В более старых сборках они принимаются синтаксически, но не выполняются. Поэтому в протоколе фиксируют версию сервера и проверяют ограничение реальной попыткой вставить неверное значение.

Движок `InnoDB` указывают явно. Только он даёт транзакции, внешние ключи и блокировки строк. Старый `MyISAM` принимает объявление внешнего ключа, но не проверяет его, поэтому схема с ним выглядит правильной и не защищает данные.

## Импорт JSON

Файл `Заказчики.json` содержит массив объектов. У каждого объекта шесть ключей: `id`, `name`, `inn`, `addres`, `phone`, `type`. Ключ `addres` записан с опечаткой в источнике. Исправлять файл нельзя, поэтому программа импорта читает `addres`, а записывает в столбец `address`. Это отображение фиксируют в пояснении.

```json
[
  {
    "id": "00000001",
    "name": "ООО \"Поставка\"",
    "inn": "",
    "addres": "г. Пятигорск",
    "phone": "+79198634592",
    "type": "Поставщик"
  },
  {
    "id": "00000008",
    "name": "ООО \"Новый JDTO\"",
    "inn": "26320045111",
    "addres": "г. Железноводск",
    "phone": "+79884581555",
    "type": "Покупатель"
  }
]
```

В файле шесть записей. Порядок в файле не совпадает с порядком кодов: после `00000002` идёт `00000008`, затем `00000003`. Поэтому проверочный запрос всегда содержит `ORDER BY id`, а не рассчитывает на порядок строк в файле.

| Код | Наименование | ИНН | Тип |
|---|---|---|---|
| `00000001` | ООО «Поставка» | пусто | Поставщик |
| `00000002` | ООО «Кинотеатр Квант» | `26320045123` | Покупатель |
| `00000003` | ООО «Ромашка» | `4140784214` | Поставщик |
| `00000008` | ООО «Новый JDTO» | `26320045111` | Покупатель |
| `00000009` | ООО «Ипподром» | `5874045632` | Поставщик |
| `00000010` | ООО «Ассоль» | `2629011278` | Покупатель |

phpMyAdmin умеет импортировать CSV, SQL и XML, но не сопоставляет произвольный массив объектов со столбцами готовой таблицы. Кнопка `Импорт` не знает, какой ключ объекта соответствует какому столбцу. Поэтому JSON читает отдельная программа: консольное приложение на C# с драйвером `MySqlConnector`. Она разбирает массив, сопоставляет поля и выполняет `INSERT` с параметрами.

```csharp
using System.Text.Json;
using MySqlConnector;

var cs = Environment.GetEnvironmentVariable("DKIP_CONNECTION")
    ?? "Server=127.0.0.1;Database=dkip2027_course;User ID=root;Password=;Character Set=utf8mb4";

await using var conn = new MySqlConnection(cs);
await conn.OpenAsync();
await using var tx = await conn.BeginTransactionAsync();

using var doc = JsonDocument.Parse(await File.ReadAllTextAsync("Заказчики.json"));
var imported = 0;

foreach (var x in doc.RootElement.EnumerateArray())
{
    await using var cmd = new MySqlCommand("""
        INSERT INTO counterparty (id, name, inn, address, phone, party_type)
        VALUES (@id, @name, @inn, @address, @phone, @type)
        """, conn, tx);

    cmd.Parameters.AddWithValue("@id", x.GetProperty("id").GetString());
    cmd.Parameters.AddWithValue("@name", x.GetProperty("name").GetString());
    cmd.Parameters.AddWithValue("@inn", x.GetProperty("inn").GetString());
    cmd.Parameters.AddWithValue("@address", x.GetProperty("addres").GetString());
    cmd.Parameters.AddWithValue("@phone", x.GetProperty("phone").GetString());
    cmd.Parameters.AddWithValue("@type", x.GetProperty("type").GetString());

    await cmd.ExecuteNonQueryAsync();
    imported++;
}

await tx.CommitAsync();
Console.WriteLine($"Импортировано записей: {imported}");
```

Три решения в этом коде важнее остальных. `GetString()` читает код как текст, поэтому ведущие нули не теряются. Параметры `@id`, `@name` и другие не склеивают SQL со значениями, поэтому кавычка в названии не ломает команду. Транзакция записывает всех заказчиков целиком или ни одного: при ошибке на третьей записи первые две не останутся в таблице.

После импорта проверяют не число строк вообще, а шесть исходных записей. Служебные контрагенты `DOC-CUSTOMER` и `DOC-MAKER` добавляются отдельно для документов, где заказчик и исполнитель не совпадают с JSON. Поэтому условие `id NOT LIKE 'DOC-%'` отделяет исходные данные от дополнений.

```sql
SELECT COUNT(*) AS json_rows
FROM counterparty
WHERE id NOT LIKE 'DOC-%';

SELECT id, name, inn, phone, party_type
FROM counterparty
WHERE id NOT LIKE 'DOC-%'
ORDER BY id;

SELECT id, CHAR_LENGTH(id) AS id_len
FROM counterparty
WHERE id NOT LIKE 'DOC-%'
ORDER BY id;
```

Ожидается шесть строк, длина каждого кода восемь символов, значения совпадают с JSON. Если `COUNT(*)` вернул шесть, а `id_len` у части строк равен одному, значит код где-то был прочитан как число. Если название пришло с `\"`, значит строка собиралась вручную и экранирование не снято.

<figure class="diagram">
<img src="reports/screens/mysql/db-import.png" alt="Таблица counterparty после импорта JSON">

Пустой ИНН у первой записи это пустая строка, а не `NULL`. Столбец объявлен `NOT NULL`, поэтому `NULL` был бы отвергнут, а пустая строка допустима. Если бизнес-правило требует ИНН у каждого покупателя, добавляют отдельную проверку, но менять исходное значение нельзя.

## Ссылочная целостность

Ссылочная целостность означает, что каждая ссылка указывает на существующую строку. Проверяют её не описанием схемы, а попыткой нарушить правило. Внешний ключ `customer_order.customer_id` ссылается на `counterparty.id`. Заказ с кодом `99999999` должен быть отвергнут.

```sql
START TRANSACTION;

INSERT INTO customer_order (doc_no, doc_date, customer_id, executor_id)
VALUES ('TEST-FK', '2026-04-22', '99999999', 'DOC-MAKER');

ROLLBACK;
```

Сервер возвращает ошибку 1452 с текстом `Cannot add or update a child row: a foreign key constraint fails`. Строка не появляется. В MariaDB номер может отличаться, но текст содержит имя ограничения и таблицы. Если вставка прошла, внешний ключ не создан или создан на другой столбец.

Обратная проверка ищет строки, которые уже потеряли родителя. Для исправной базы запрос возвращает ноль строк.

```sql
SELECT l.id
FROM customer_order_line l
LEFT JOIN customer_order o ON o.id = l.order_id
WHERE o.id IS NULL;
```

Проверить все связи сразу можно через `information_schema`, не открывая каждую таблицу.

```sql
SELECT table_name, constraint_name, referenced_table_name
FROM information_schema.KEY_COLUMN_USAGE
WHERE table_schema = 'dkip2027_course'
  AND referenced_table_name IS NOT NULL
ORDER BY table_name, constraint_name;
```

`SET FOREIGN_KEY_CHECKS = 0` отключает проверки на время сессии. Этим пользуются при восстановлении дампа, но не для того, чтобы «починить» ошибку. Если импорт проходит только с отключёнными ключами, данные содержат битые ссылки, и их нужно исправлять, а не скрывать.

## Выгрузка и восстановление

Проверка выгрузки это восстановление в другую пустую базу. Создают `dkip2027_restore`, открывают `Импорт`, выбирают файл и выполняют его. Затем сравнивают не только список таблиц, но и данные: число контрагентов, коды с ведущими нулями, а если представление `order_cost` уже создано, и результат стоимости.

```sql
SELECT COUNT(*) AS all_rows FROM counterparty;
SELECT id, name FROM counterparty WHERE id NOT LIKE 'DOC-%' ORDER BY id;
-- если представление order_cost уже создано
SELECT * FROM order_cost;
```

В восстановленной базе восемь контрагентов, шесть из них исходные. Если представление `order_cost` уже создано, оно возвращает `14374.28`. Если таблицы есть, а данные пусты, при экспорте не включили данные. Если внешние ключи пропали, при экспорте не включили структуру или выбрали неверный формат.

## Итоги

- База это таблицы и ограничения, которые сервер проверяет при каждой записи.
- Коды заказчиков, ИНН и телефоны хранят текстом, иначе ведущие нули и плюс теряются.
- Внешний ключ проверяют реальной попыткой вставить несуществующую ссылку, а не чтением схемы.
- JSON импортируют программой с параметрами и транзакцией, потому что phpMyAdmin не сопоставляет ключи объекта со столбцами.
- Выгрузка считается готовой только после восстановления в пустую базу и сверки данных.

## Проверьте себя

> [!CHECK] Почему код заказчика объявлен VARCHAR, хотя выглядит как число?
> Ведущие нули являются частью кода. Целое число их не хранит, поэтому `00000008` превратится в `8` и перестанет совпадать с документом.

> [!CHECK] Что проверить после импорта, кроме числа строк?
> Коды с ведущими нулями, совпадение наименований, ИНН и телефонов с JSON, отсутствие лишних записей среди исходных шести.

> [!CHECK] Как доказать, что внешний ключ работает?
> Попробовать вставить заказ с несуществующим кодом заказчика и получить ошибку 1452. Затем найти потерянные ссылки запросом с `LEFT JOIN`.

::quiz
Q: Что произойдёт при вставке строки заказа с несуществующим customer_id?
+ Сервер отклонит строку из-за внешнего ключа
- Строка сохранится с пустым заказчиком
- Сервер создаст нового заказчика автоматически
- Строка сохранится, но запрос её не покажет
! Внешний ключ требует, чтобы родительская строка уже существовала.

Q: Зачем код заказчика хранят в VARCHAR?
+ Чтобы сохранить ведущие нули и буквенные коды
- Чтобы ускорить арифметику
- Чтобы автоматически проверять ИНН
- Чтобы запретить сортировку
! Код `00000008` является текстом, а не числом 8.

Q: Какая команда создаёт базу в utf8mb4?
+ CREATE DATABASE dkip2027_course CHARACTER SET utf8mb4;
- CREATE TABLE dkip2027_course CHARSET utf8;
- USE dkip2027_course;
- ALTER DATABASE dkip2027_course;
! Кодировка задаётся при создании базы или меняется отдельной командой ALTER.

Q: Чем utf8mb4 отличается от старого utf8 в MySQL?
+ Хранит до четырёх байт на символ
- Хранит только латиницу
- Не поддерживает кириллицу
- Всегда использует сравнение без регистра
! Старое имя utf8 ограничено тремя байтами.

Q: Что делает PRIMARY KEY?
+ Различает строки и запрещает повтор ключа
- Разрешает повтор строк
- Создаёт резервную копию
- Связывает две таблицы
! Первичный ключ уникален и не может быть пустым.

Q: Что означает ошибка 1062 Duplicate entry?
+ Попытку вставить повтор значения уникального ключа
- Отсутствие таблицы
- Неверный пароль
- Синтаксическую ошибку в SELECT
! Уникальный ключ уже содержит такое значение.

Q: Зачем импорт выполняют в транзакции?
+ Чтобы при ошибке не осталось части записей
- Чтобы ускорить чтение
- Чтобы отключить внешние ключи
- Чтобы изменить кодировку
! Транзакция фиксирует все вставки вместе или отменяет их.

Q: Почему phpMyAdmin не импортирует JSON напрямую?
+ Он не сопоставляет ключи объекта со столбцами таблицы
- Он не поддерживает кодировку utf8mb4
- JSON запрещён в MySQL
- Для JSON нужен отдельный сервер
! Форматы CSV и SQL описывают строки иначе, чем массив объектов.

Q: Что означает ошибка 1452?
+ Ссылку на отсутствующую родительскую строку
- Повтор первичного ключа
- Пустое обязательное поле
- Нарушение CHECK
! Внешний ключ не нашёл родителя с указанным значением.

Q: Какие ограничения нужно проверить в схеме?
+ PRIMARY KEY
+ FOREIGN KEY
+ NOT NULL
+ CHECK
- AUTOCOMMIT
- INDEX_ONLY
! Это основные правила целостности таблицы.

Q: Что проверяют после импорта заказчиков?
+ Число исходных записей равно шести
+ Коды сохранили ведущие нули
+ Значения совпадают с JSON
- Порядок строк совпадает с файлом
- Все ИНН заполнены
! Порядок в файле не гарантирован, а пустой ИНН допустим.

Q: Какие значения правильно хранить текстом?
+ Код заказчика
+ ИНН
+ Телефон
- Количество изделий
- Цену материала
! Коды, ИНН и телефоны не участвуют в арифметике.

Q: Какая команда показывает внешние ключи базы?
+ Запрос к information_schema.KEY_COLUMN_USAGE
- SHOW TABLES
- SELECT VERSION()
- SHOW DATABASES
! В KEY_COLUMN_USAGE есть ссылки на родительские таблицы.

Q: Какая команда создаёт базу dkip2027_course в utf8mb4?
= CREATE DATABASE dkip2027_course CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
= CREATE DATABASE dkip2027_course CHARACTER SET utf8mb4;
= CREATE DATABASE dkip2027_course CHARSET utf8mb4;
! Кодировку задают при создании базы.

= шесть
! В файле шесть объектов, служебные записи DOC- считаются отдельно.
