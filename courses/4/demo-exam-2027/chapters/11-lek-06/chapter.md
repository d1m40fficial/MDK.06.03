## Одна идея

Заказчик открывает адрес API в браузере и видит строку `"formatted_date":"2026-04-22T00:00:00"`. Формально дата есть, фактически её нельзя показать в отчёте: заказчик ждал 22.04.2026. Рядом лежит поле `"title_user":"Планы на неделюadmin"`, потому что заголовок склеили с логином без разделителя.

**Ответ API это контракт, а не удобный дамп таблицы.** Поля называются так, как записано в задании, дата приходит в согласованном формате, а лишние служебные столбцы в ответ не попадают. Клиент не обязан знать, как устроена база, и не должен разбирать внутренние типы даты.

Дальше разбирается задание 5 из КИМ 09.02.07-5-2027: API заметок с четырьмя полями, кодами 200, 400, 500 и пустым массивом, а также коллекция Postman с исполняемыми проверками. Требования приведены в Приложении 2, полный текст лежит в `reports/KIM_09.02.07-5-2027.pdf`.

## Что требуется от API

Требования короткие и все проверяются:

- таблица `notes` с тремя или пятью записями;
- внешний ключ `notes.id_user` на `users.id`;
- метод `GET /notes` или `GET /api/notes`;
- ответ содержит `id`, `title_user`, `content`, `formatted_date`;
- `title_user` собирается как заголовок, дефис с пробелами, логин;
- `content` передаётся без изменений;
- `formatted_date` в формате ДД.ММ.ГГГГ;
- код 200 и массив записей при успехе;
- код 200 и пустой массив, если записей нет;
- код 400 при неверном запросе;
- код 500 и JSON ошибки при внутреннем сбое;
- коллекция Postman с проверками 200, 500 и валидного JSON.

Слово «валидный JSON» означает не только синтаксис. Ответ должен разбираться как массив объектов, а каждое поле иметь ожидаемый тип. Строка `"error"` вместо массива при успехе ломает клиента, даже если код 200.

## Таблица notes

```sql
CREATE TABLE notes (
  id INT AUTO_INCREMENT PRIMARY KEY,
  title VARCHAR(120) NOT NULL,
  content TEXT NOT NULL,
  id_user INT NOT NULL,
  created_at DATE NOT NULL,
  CONSTRAINT fk_notes_user FOREIGN KEY (id_user) REFERENCES users(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`created_at` хранится как `DATE`, а не `DATETIME`: в задании нужна дата без времени, и лишние часы только создают повод для ошибки формата. Поля `title_user` и `formatted_date` в таблице отсутствуют. Это вычисляемые значения ответа, и хранить их нельзя: при смене логина автора сохранённая строка устареет.

Внешний ключ не даёт создать заметку для несуществующего пользователя. Без него `JOIN` молча потеряет строку, и заметка исчезнет из ответа без сообщения об ошибке.

Записей должно быть от трёх до пяти. Одна запись не показывает сортировку и не позволяет отличить пустой ответ от единственной строки. Десять записей усложняют проверку вручную.

## Чтение данных через JOIN

API нужен логин автора, а он лежит в `users`. Запрос соединяет две таблицы:

```sql
SELECT n.id, n.title, u.login, n.content, n.created_at
FROM notes n
JOIN users u ON u.id = n.id_user
ORDER BY n.id;
```

`JOIN` оставляет только заметки с существующим автором. Если нужна диагностика потерянных строк, временно используют `LEFT JOIN` и ищут записи с пустым логином. В рабочем запросе достаточно внутреннего соединения: внешний ключ уже гарантирует автора.

## Контракт ответа

Ответ собирается в объект с четырьмя полями. Порядок полей в JSON не важен, важны имена и типы.

```json
[
  {
    "id": 1,
    "title_user": "Планы на неделю - admin",
    "content": "Проверить заказ № 1 и подготовить отчёт.",
    "formatted_date": "22.04.2026"
  }
]
```

`title_user` собирается из двух значений и разделителя. Разделитель это дефис с пробелами с обеих сторон. Если склеить без пробелов, получится `Планы на неделюadmin`, и проверка формата не пройдёт.

`formatted_date` формируется из `created_at` с шаблоном `dd.MM.yyyy`. В C# это выглядит так:

```csharp
string titleUser = title + " - " + login;
string formattedDate = createdAt.ToString("dd.MM.yyyy", CultureInfo.InvariantCulture);
```

`CultureInfo.InvariantCulture` обязателен. В русской локали разделитель даты тоже точка, но в других настройках он станет косой чертой или дефисом, и ответ изменится на чужой машине.

Порядок полей в JSON не фиксируется, поэтому тест проверяет наличие ключей, а не текст ответа целиком. Сравнение строки целиком ломается от любого изменения порядка и не показывает, какое поле испорчено.

`content` передаётся без обрезки, замены переносов и экранирования вручную. Сериализатор сам экранирует кавычки и переводы строк. Ручная замена ломает текст, который заказчик ввёл.

## Коды ответов и JSON ошибки

Код отвечает на вопрос «что произошло», тело ответа уточняет подробности.

| Код | Когда | Тело |
|---|---|---|
| 200 | записи найдены или список пуст | массив объектов |
| 400 | неверный параметр запроса | объект с полем `error` |
| 500 | сбой базы или обработки | объект с полем `error` |

Пустой список это нормальный результат: в базе просто нет подходящих записей. Клиент получает 200 и `[]`, показывает «Заметок пока нет» и продолжает работать. Код 404 здесь означал бы, что не существует сам адрес, а он существует.

Код 400 ставят, когда клиент прислал то, что сервер не может разобрать. В учебном API есть необязательный параметр `user_id`, и он даёт удобный повод для проверки:

- `?user_id=abc` не число;
- `?user_id=0` не положительное;
- `?user_id=1&user_id=2` повтор параметра;
- `?limit=10` неизвестный параметр.

Во всех случаях ответ содержит 400 и понятное поле `error`, а не пустой массив. Пустой массив на неверный запрос скрывает ошибку клиента.

Проверка параметра стоит до обращения к базе. Иначе неверный запрос всё равно откроет соединение, а при недоступной базе вернёт 500 вместо 400, и клиент будет искать ошибку в своих данных.

```json
{ "error": "Ошибка подключения к базе данных или обработки запроса" }
```

Строка подключения, имя пользователя базы и текст исключения в ответ не попадают. Это не только вопрос безопасности: клиент всё равно не сможет исправить сервер, а лишние подробности уводят его от правильного действия.

## Проект ASP.NET Core minimal API

Minimal API не требует контроллеров: маршрут и обработчик описываются в `Program.cs`. Для одного метода этого достаточно.

```csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.Use(async (context, next) =>
{
    try { await next(); }
    catch (Exception ex)
    {
        app.Logger.LogError(ex, "Ошибка обработки API");
        context.Response.StatusCode = 500;
        await context.Response.WriteAsJsonAsync(
            new { error = "Ошибка подключения к базе данных или обработки запроса" });
    }
});

IResult ReadNotes(HttpRequest request)
{
    int? userId = null;
    if (request.Query.Keys.Any(k => k != "user_id"))
        return Results.BadRequest(new { error = "Неизвестный параметр. Допустим user_id." });
    if (request.Query.ContainsKey("user_id"))
    {
        if (request.Query["user_id"].Count != 1
            || !int.TryParse(request.Query["user_id"], out var parsed)
            || parsed <= 0)
            return Results.BadRequest(new { error = "user_id должен быть положительным целым числом" });
        userId = parsed;
    }
    return Results.Ok(Notes.Read(userId));
}

app.MapGet("/notes", ReadNotes);
app.MapGet("/api/notes", ReadNotes);
app.Run();
```

Промежуточный обработчик ловит исключение до того, как оно дойдёт до клиента. Без него ASP.NET Core вернёт 500 с пустым телом или страницей разработчика, и проверка «JSON ошибки» не пройдёт.

`Results.Ok` с пустым списком сам отдаёт `[]`. Отдельная ветка для пустого результата не нужна и часто пишется неправильно: вместо массива возвращают `null`, и клиент получает `null` с кодом 200.

## Коллекция и переменные

Коллекция объединяет запросы и проверки. Вместо адреса, вписанного в каждый запрос, задают переменную `base_url`. Тогда переезд с порта 5271 на другой порт не требует правки всех запросов.

Переменные коллекции:

| Переменная | Значение | Назначение |
|---|---|---|
| `base_url` | `http://127.0.0.1:5271` | рабочий экземпляр |
| `error_url` | `http://127.0.0.1:5281` | экземпляр с неверным подключением |

Коллекция содержит минимум четыре запроса: список заметок, пустой результат, неверный параметр и сбой подключения. Импорт коллекции через `Import` показывает, что файл читается и переменные подхватились.

## Тесты в Postman

Тест выполняется после получения ответа. Вкладка Scripts, раздел Post-response, содержит код на JavaScript.

```javascript
pm.test("Статус 200", () => pm.response.to.have.status(200));

const body = pm.response.json();

pm.test("Ответ это массив", () => pm.expect(body).to.be.an("array"));

pm.test("Поля заметки", () => {
    body.forEach(note => {
        pm.expect(note).to.have.all.keys("id", "title_user", "content", "formatted_date");
        pm.expect(note.id).to.be.a("number");
        pm.expect(note.title_user).to.be.a("string");
        pm.expect(note.content).to.be.a("string");
    });
});

pm.test("Формат даты", () => {
    body.forEach(note =>
        pm.expect(note.formatted_date).to.match(/^\d{2}\.\d{2}\.\d{4}$/));
});
```

`pm.response.json()` разбирает тело и заодно проверяет, что это валидный JSON. Если сервер вернул HTML или обрезанный текст, тест падает на разборе, а не на первом поле.

Проверка `all.keys` ловит лишние поля. Иногда студенты добавляют `login` и `title` рядом с `title_user`, и клиент начинает сомневаться, какое поле главное. Контракт содержит ровно четыре поля.

Для сбоя отдельный запрос и отдельные тесты:

```javascript
pm.test("Статус 500", () => pm.response.to.have.status(500));
pm.test("JSON с полем error", () => {
    pm.expect(pm.response.json()).to.have.property("error");
});
```

Тест без запроса бесполезен, запрос без теста тоже: коллекция должна позволять другому человеку нажать Send и увидеть результат. Поэтому в коллекцию кладут и запросы, и скрипты, и сохранённые примеры ответов.

Сохранённые примеры помогают читать коллекцию без запуска сервиса. Пример не заменяет тест: он показывает ожидаемое тело, но не проверяет фактическое.

## Пустой массив как отдельный сценарий

Пустой результат воспроизводят фильтром по несуществующему пользователю: `?user_id=999`. Ответ должен быть 200 и `[]`.

Фильтр удобнее удаления строк: данные остаются на месте, а сценарий воспроизводится одной правкой параметра. Удалять записи ради проверки опасно, потому что после неё нужно восстанавливать тестовый набор.

Проверка:

```javascript
pm.test("Статус 200", () => pm.response.to.have.status(200));
pm.test("Пустой массив", () => {
    const body = pm.response.json();
    pm.expect(body).to.be.an("array");
    pm.expect(body).to.have.lengthOf(0);
});
```

Если API возвращает 404 или 500, клиент воспримет отсутствие данных как аварию и покажет ошибку вместо пустого списка. Разница принципиальная: «данных нет» и «сервис сломан» требуют разных действий.

## Сбой на отдельном экземпляре

Проверка 500 не должна останавливать рабочую базу. Запускают второй экземпляр API с заведомо неверным портом базы:

```powershell
$env:DKIP_STACK='mysql'
$env:DKIP_CONNECTION='Server=127.0.0.1;Port=1;Database=dkip2027_course;User ID=demo;Connection Timeout=1'
dotnet run --project Api --urls http://127.0.0.1:5281
```

Запрос к `error_url` даёт 500 и JSON ошибки, запрос к `base_url` продолжает давать 200. Подробности исключения остаются в консоли второго экземпляра.

## Типичные ошибки

**500 на пустом списке.** Пустой результат принимают за сбой. Клиент получает ошибку там, где данных просто нет.

**Дата в формате ISO.** `ToString()` без шаблона даёт `22.04.2026 0:00:00` или `2026-04-22T00:00:00`. Нужен явный шаблон и инвариантная культура.

**Склейка без разделителя.** `title_user` получается слитным, и проверка формата не проходит.

**Лишние поля.** В ответ попадают `id_user`, `created_at` или `login`. Контракт нарушен, хотя данные верные.

**Реквизиты базы в ошибке.** Клиент видит строку подключения и имя пользователя. Это утечка и одновременно бесполезная для него информация.

**Заглушка вместо базы.** API возвращает заранее записанный массив и не читает `notes`. Проверка с новой записью сразу это показывает.

**Тесты только на 200.** Коллекция не воспроизводит 400 и 500, поэтому половина требований не подтверждена.

**Ответ не массив.** При одной записи возвращают объект, при нескольких массив. Клиент ломается на первом же изменении данных.

## Итоги

- Контракт ответа задаёт четыре поля, их имена, типы и форматы.
- `title_user` и `formatted_date` вычисляются при ответе и не хранятся в таблице.
- Пустой список это 200 и `[]`, а не ошибка.
- 400 означает неверный запрос, 500 означает сбой сервера, оба возвращают JSON с полем `error`.
- Коллекция Postman содержит запросы и исполняемые проверки для успеха, пустого списка и ошибок.

- Успешный ответ
- Запрос перенаправлен
! Код 400 ставят, когда параметры не разбираются или недопустимы.

Q: Что означает код 500?
+ Сбой на стороне сервера
- Ошибку в параметрах запроса
- Успешное создание записи
- Отсутствие прав у клиента
! Код 500 сообщает о внутренней проблеме, которую клиент не исправит.

Q: Что делают с подробностями исключения при коде 500?
+ Пишут в консоль сервера, клиенту отдают общий текст
- Отправляют клиенту вместе со строкой подключения
- Сохраняют в поле title_user
- Удаляют без записи
! Подробности нужны разработчику, клиенту они не помогают и раскрывают устройство.

Q: Где хранится значение formatted_date?
+ Нигде, оно вычисляется при формировании ответа
- В столбце таблицы notes
- В отдельной таблице дат
- В переменной окружения
! Вычисляемое поле не хранят, иначе оно устареет при изменении данных.

Q: Что проверяет вызов pm.response.to.have.status(200)?
+ Код ответа
- Длину массива
- Формат даты
- Имя поля
! Проверка статуса это первое, что делает тест после получения ответа.

Q: Какие коды нужно воспроизвести в коллекции?
+ 200
+ 400
+ 500
- 301
! Коллекция подтверждает успех, неверный запрос и внутренний сбой.

Q: Что проверяют тесты коллекции для успешного ответа?
+ Статус 200
+ Валидный JSON и состав полей
+ Формат даты
- Скорость интернет-соединения
! Проверки касаются контракта ответа, а не сети.

Q: Какие ошибки ломают приёмку API?
+ Код 500 на пустом списке
+ Дата в формате ISO
+ Тесты только на успешный ответ
- Чтение данных из таблицы notes
! Контракт нарушается в поведении и в проверках, а не в источнике данных.

Q: Какое поле ответа содержит заголовок и логин автора?
= title_user
! Поле собирается из заголовка, дефиса с пробелами и логина.

Q: Какой параметр запроса позволяет отфильтровать заметки по автору?
= user_id
! Необязательный параметр user_id принимает положительное целое число.
