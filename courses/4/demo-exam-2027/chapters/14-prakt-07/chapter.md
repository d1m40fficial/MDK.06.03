## Цель работы

Заполнить шаблон документации API для собственного сервиса заметок, описать все реализованные методы, параметры, коды 200, 400 и 500, привести примеры из реальных ответов и сверить документ с OpenAPI и Swagger UI.

Результат работы это заполненный файл DOCX, файл `openapi.json` и сохранённые примеры ответов. Документ должен позволить другому человеку повторить запрос, не открывая исходный код.

## Оборудование и программное обеспечение

- Windows 10 или 11 и PowerShell.
- XAMPP 8.5.12 с запущенными Apache и MySQL, база `dkip2027_course`.
- .NET SDK 10 и Visual Studio 2022 Community.
- Проект API из практики 6, собирающийся командой `dotnet build`.
- Postman и браузер с установленным Swagger UI.
- Microsoft Word и шаблон `reports/API_документ_шаблон.docx`.
- Файл `reports/openapi.json` как образец структуры.

## Краткие теоретические сведения

Документация API описывает контракт: адрес, метод, параметры, формат ответа и коды. В задании форма сдачи задана шаблоном, поэтому структура документа не обсуждается. Шаблон содержит строку «Базовый URL», таблицу методов с четырьмя столбцами и таблицу кодов ответов HTTP.

Один контракт живёт в трёх местах. Код задаёт фактическое поведение, `openapi.json` фиксирует его для инструментов, Swagger UI показывает человеку и отправляет запросы. DOCX переводит тот же контракт на язык шаблона. Расхождение между источниками это дефект, который нужно устранить до сдачи.

Базовый URL это схема, хост и порт без пути метода: `http://127.0.0.1:5271`. Параметр `user_id` передаётся в строке запроса, необязателен, принимает целое число не меньше единицы. Без параметра сервис возвращает все заметки, с несуществующим автором возвращает пустой массив с кодом 200.

Главное правило работы: **пример берут из ответа, который только что пришёл от сервиса**. Придуманный пример проверяется первым же запросом и подводит автора документа.

## Ход работы

### Шаг 1. Подготовьте рабочую папку и копию шаблона

Создайте папку практики и скопируйте туда шаблон под новым именем. Шаблон скачайте со страницы занятия кнопкой из блока материалов:

```powershell
New-Item -ItemType Directory -Force C:\DKIP\practice-07 | Out-Null
Set-Location C:\DKIP\practice-07
Copy-Item "$env:USERPROFILE\Downloads\API_документ_шаблон.docx" .\api.docx
```

Оригинал шаблона не редактируйте. Если он испорчен, восстановить структуру по памяти не получится, а эксперт сверяет документ именно с приложением.

Откройте `api.docx` и убедитесь, что видны три части: поле базового URL, таблица методов и таблица кодов. Сделайте снимок пустого шаблона: он доказывает, что работа начата с исходной формы, а не с самодельной таблицы.

### Шаг 2. Запустите API и проверьте адрес

Сервис из практики 6 читает подключение из переменных окружения. Откройте PowerShell в папке проекта и задайте те же значения, что использовали раньше:

```powershell
$env:DKIP_STACK='mysql'
$env:DKIP_CONNECTION='Server=127.0.0.1;Database=dkip2027_course;User ID=root;Password=;Character Set=utf8mb4'
dotnet run --project Api --urls http://127.0.0.1:5271
```

Окно оставьте открытым: закрытие процесса останавливает сервис. Во втором окне проверьте адрес:

```powershell
curl.exe -s -i "http://127.0.0.1:5271/notes"
```

В ответе должны быть строка состояния `HTTP/1.1 200 OK`, заголовок `Content-Type: application/json` и массив заметок. Если пришёл код 500, смотрите консоль сервиса: чаще всего неверен пароль или имя базы.

Запишите в черновик фактический адрес и порт. Дальше он понадобится в трёх местах: в документе, в командах проверки и в коллекции Postman.

### Шаг 3. Соберите реальные ответы

Выполните четыре запроса и сохраните тела в папку `examples`. Первый запрос возвращает все заметки, второй только заметки автора, третий пустой результат, четвёртый ошибку параметра:

```powershell
$base = "http://127.0.0.1:5271"
curl.exe -s "$base/notes" -o .\examples\notes-200.json
curl.exe -s "$base/notes?user_id=2" -o .\examples\notes-filter.json
curl.exe -s "$base/notes?user_id=2147483647" -o .\examples\notes-empty.json
curl.exe -s -i "$base/notes?user_id=abc" -o .\examples\notes-400.txt
```

Проверьте каждый файл в редакторе, а не только код ответа. В первом должно быть столько объектов, сколько строк в таблице `notes`. Во втором только записи выбранного автора. В третьем ровно `[]`. В четвёртом код 400 и объект с полем `error`.

Те же два случая удобно показать в Swagger UI: успешный список и пустой массив. Снимки делайте после нажатия «Execute», когда видны адрес запроса, код и тело.

Ошибку 500 воспроизводят отдельно, чтобы не останавливать рабочий сервис. Во втором окне PowerShell задайте неверный порт базы и другой порт API:

```powershell
$env:DKIP_CONNECTION='Server=127.0.0.1;Port=1;Database=dkip2027_course;User ID=root;Password=;Connection Timeout=3'
dotnet run --project Api --urls http://127.0.0.1:5281
```

В третьем окне отправьте запрос и сохраните ответ:

```powershell
curl.exe -s -i "http://127.0.0.1:5281/notes" -o .\examples\notes-500.txt
```

В файле должны быть код 500 и объект `{"error": "..."}` без строки подключения и без трассировки. После проверки закройте только тестовый процесс.

### Шаг 4. Заполните базовый URL и таблицу методов

В строку «Базовый URL» запишите `http://127.0.0.1:5271`. Путь метода сюда не входит: иначе читатель сложит два адреса и получит `/notes/notes`.

В таблице методов заполните по строке на каждый работающий маршрут. Если сервис отвечает и на `/notes`, и на `/api/notes`, опишите оба и укажите, что результат одинаков.

| Название метода | Параметры | Описание метода | Формат ответа |
|---|---|---|---|
| GET /notes | `user_id`, необязательное целое от 1, query | Возвращает список заметок, при параметре только записи автора | JSON, массив объектов: `id`, `title_user`, `content`, `formatted_date` |
| GET /api/notes | те же | Второй маршрут к тому же обработчику | Тот же JSON |

Столбец «Название метода» содержит и метод, и путь. Запись `GET` без пути бессмысленна: читатель не знает, куда обращаться. Запись `/notes` без метода тоже неполна.

В ячейке «Параметры» перечислите имя, тип, обязательность и расположение. Формулировка «есть параметр user_id» не отвечает на вопрос, можно ли его пропустить.

### Шаг 5. Опишите параметры и формат ответа

Для каждого параметра укажите пять сведений. У сервиса заметок параметр один, поэтому строка короткая, но полная:

| Имя | Где | Тип | Обязательный | Ограничение |
|---|---|---|---|---|
| `user_id` | query | integer | нет | от 1 до 2147483647 |

В столбце «Формат ответа» перечислите поля и объясните их происхождение. Одного слова «JSON» мало: читателю нужны имена полей и типы.

- `id` это целое число, идентификатор заметки.
- `title_user` это строка из заголовка, дефиса и логина автора.
- `content` это текст заметки без изменений.
- `formatted_date` это дата в формате ДД.ММ.ГГГГ.

Обязательно отметьте, что `title_user` и `formatted_date` вычисляются при выдаче. В таблице базы таких столбцов нет, и без пояснения читатель ищет их в схеме и не находит.

Вставьте пример одного элемента из файла `notes-200.json`. Полный список не нужен, но пометьте, что в ответе пять объектов. Дату и логин берите из сохранённого файла, а не из памяти.

### Шаг 6. Заполните коды ответов и примеры

В таблице «Коды ответов HTTP» заполните три строки. Для каждого кода укажите условие возникновения и пример тела.

| Код | Описание |
|---|---|
| 200 | Успех. Массив заметок, в том числе пустой. Пример: `GET /notes?user_id=2147483647` даёт `[]` |
| 400 | Неверный параметр. Пример: `GET /notes?user_id=abc` даёт объект `error` |
| 500 | Сбой базы или обработки. Пример: запрос к тестовому процессу с неверным портом базы |

Пустой массив относится к коду 200, а не к 404. Запрос корректен, ресурс существует, подходящих записей нет. Если записать пустой результат под 404, документ будет утверждать, что сервис теряет адрес при отсутствии данных.

Для 400 и 500 приведите тело целиком и условие воспроизведения. Без условия читатель не сможет повторить ошибку и решит, что пример выдуман.

Проверьте, что в документе нет пароля, строки подключения и полного текста исключения. Документация уходит в отчёт, а сведения о подключении туда попадать не должны.

Если значения разошлись, исправляйте источник, а не примечание. Устаревший документ правят по фактическому ответу. Если расходится сам сервис, дефект описывают в отчёте: что запросили, что ожидали, что получили.

В конце попросите соседа открыть ваш DOCX и назвать адрес и метод для получения заметок. Если он справляется без подсказок, документ готов. Сохраните DOCX, `openapi.json`, файлы из папки `examples` и снимки ответов.

## Что сдать

- Заполненный файл `api.docx` без изменений структуры шаблона.
- Файл `openapi.json`, совпадающий с документом по путям, параметрам и кодам.
- Пять сохранённых ответов: список, фильтр, пустой массив, ошибка 400 и отдельно ответ 500.
- Таблицу сверки документа, OpenAPI и фактического поведения.
- Скриншоты шаблона, ответов 200 и `[]`, раздела `paths` и заполненного документа.
- Краткий вывод: какие расхождения найдены и как устранены.

## Критерии оценки

| Критерий | Баллы | Что проверяется |
|---|---|---|
| Структура документа | 15 | Шаблон не изменён, все ячейки заполнены |
| Методы и параметры | 25 | Описаны все работающие пути, у параметра есть тип и обязательность |
| Коды и примеры | 25 | 200, 400, 500 и пустой массив, примеры совпадают с ответами |
| Сверка с OpenAPI | 20 | Шесть пунктов проверены, расхождения объяснены |
| Оформление и вывод | 15 | Нет секретов, текст понятен, вывод содержит решение |
