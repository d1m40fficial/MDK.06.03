## Одна идея

В понедельник преподаватель принимает работу. Студент показывает вход: неверный пароль даёт сообщение, верный открывает окно. Потом преподаватель просит ошибиться три раза подряд, закрыть приложение и войти с правильным паролем. Вход проходит. Блокировки нет, потому что счётчик неудач жил в переменной формы, а форма создаётся заново при каждом запуске.

**Защита приложения это состояние в базе, а не поведение окна.** Пароль, пазл, счётчик ошибок, признак блокировки и роль хранятся в таблице `users`. Интерфейс показывает результат проверки, но не хранит его.

Дальше разбирается задание 4 из КИМ 09.02.07-5-2027: приложение с авторизацией, двумя ролями, пазлом, блокировкой после трёх ошибок и управлением пользователями. Требования к заданию приведены в Приложении 1, полный текст лежит в `reports/KIM_09.02.07-5-2027.pdf`.

## Что требуется от приложения

Список требований короткий, но каждое проверяется отдельно:

- вход по логину и паролю;
- роли Администратор и Пользователь;
- пазл из фрагментов изображения, который проверяется вместе с паролем;
- блокировка учётной записи после трёх подряд ошибок пароля или пазла;
- управление пользователями: добавление, изменение, снятие блокировки;
- проверка обязательных полей и дублей логина;
- понятные сообщения об ошибках и обработка исключений;
- недоступность управления учётными записями обычному пользователю.

Три подряд ошибки означают, что счётчик обнуляется при успешном входе. Если человек ошибся дважды, вошёл, вышел и ошибся ещё раз, счёт начинается заново. Ошибка пароля и ошибка пазла считаются одинаково: это одна неудачная попытка входа.

Слово «подряд» важно и для проверки. Эксперт смотрит не на сообщение о блокировке, а на поведение после перезапуска: признак блокировки должен остаться в базе. Поэтому в работе ценится не красивый диалог, а сохранённое состояние.

## Таблица users как единственный источник состояния

```sql
CREATE TABLE users (
  id INT AUTO_INCREMENT PRIMARY KEY,
  login VARCHAR(64) NOT NULL UNIQUE,
  password_hash VARBINARY(32) NOT NULL,
  salt VARBINARY(16) NOT NULL,
  role ENUM('admin','user') NOT NULL DEFAULT 'user',
  failed_attempts INT NOT NULL DEFAULT 0,
  is_locked BOOLEAN NOT NULL DEFAULT FALSE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`UNIQUE` на `login` это единственная надёжная защита от дублей: проверка в коде может пропустить две одновременные попытки, ограничение базы не пропустит. Поля `failed_attempts` и `is_locked` не украшение схемы: именно они переживают перезапуск приложения и перезагрузку компьютера.

Роль хранится строкой из двух значений. Логическая модель может быть богаче, но ролей в задании ровно две, и лишние уровни усложняют проверку. Значение по умолчанию `user` защищает от ошибки, когда пользователя создали и забыли указать роль: он получит минимальные права, а не максимальные.

## Форма входа

В окне есть подпись «Логин», поле логина, подпись «Пароль», поле пароля со скрытыми символами, пазл и кнопка «Войти». Имена `LoginInput` и `PasswordInput` нужны не для красоты: по ним проверяют доступность и автоматические тесты. Свойство `AccessibleName` даёт экранному диктору понятную подпись.

```csharp
readonly TextBox login = new() { Name = "LoginInput", AccessibleName = "Логин", Width = 440 };
readonly TextBox password = new() { Name = "PasswordInput", AccessibleName = "Пароль",
    UseSystemPasswordChar = true, Width = 440 };
```

Обработчик кнопки выполняет шаги в строгом порядке: проверяет заполненность полей, проверяет пазл, вызывает проверку входа, открывает рабочее окно. Любое исключение превращается в сообщение, приложение остаётся открытым.

## Пазл из четырёх фрагментов

Изображение `1.png` масштабируется до 200 на 200 и режется на четыре части по 100 на 100. В левой части окна показывается образец, в правой сетка 2 на 2. Первое нажатие выбирает фрагмент, второе меняет его местами с выбранным.

Состояние пазла это массив `order` из четырёх чисел. Собранное состояние это последовательность 0, 1, 2, 3. Проверка занимает одну строку:

```csharp
public bool IsSolved() => order.SequenceEqual(new[] { 0, 1, 2, 3 });
```

Перемешивание не должно случайно давать собранную картинку, поэтому `Shuffle` повторяет выбор, пока `IsSolved` истинно. Иначе часть студентов получит уже собранный пазл и не поймёт, что от них требуется.

## Пароль, соль и хеш

Пароль не хранится и не шифруется обратимо. Хранится хеш PBKDF2 с индивидуальной солью. При входе из введённого пароля и сохранённой соли вычисляют хеш и сравнивают с сохранённым. Совпадение хешей означает верный пароль, восстановить сам пароль из хеша нельзя.

Соль нужна, чтобы одинаковые пароли у двух пользователей давали разные хеши. Без соли таблица с хешами уязвима к заранее посчитанным словарям: злоумышленник один раз считает хеши популярных паролей и находит совпадения во всей таблице.

Число итераций PBKDF2 задаёт стоимость перебора. Для учебной работы достаточно значения по умолчанию в библиотеке, но фиксировать его в коде полезно: при смене библиотеки поведение не должно измениться незаметно.

## Три ошибки и блокировка

Проверка входа должна менять состояние атомарно. Между чтением счётчика и его записью не должно быть окна, в котором другая копия приложения прочитает старое значение.

```csharp
using var tx = connection.BeginTransaction();
var select = new MySqlCommand(
  "SELECT id, password_hash, salt, role, failed_attempts, is_locked " +
  "FROM users WHERE login = @login FOR UPDATE", connection, tx);
```

`FOR UPDATE` блокирует строку до конца транзакции. Дальше возможны три ветки:

1. `is_locked` истинно: сообщение о блокировке, счётчик не меняется;
2. пароль и пазл верны: `failed_attempts = 0`, вход разрешён;
3. пароль или пазл неверны: `failed_attempts + 1`, при достижении трёх `is_locked = true`.

Третья ошибка ставит признак блокировки в той же транзакции, что и счётчик. Если записать счётчик и упасть до записи признака, блокировка потеряется, а пользователь получит четвёртую попытку.

<figure class="diagram">
<img src="reports/screens/mysql/locked.png" alt="Сообщение о блокировке учётной записи">
<figcaption>Третья подряд ошибка закрывает вход: признак блокировки записан в базу.</figcaption>

Проверка пазла входит в ту же ветку, что и пароль. Неверно собранный пазл при верном пароле это неудачная попытка. Это прямо написано в требовании и часто пропускается: студенты проверяют пазл отдельным сообщением и не считают его ошибкой.

## Сообщения об ошибках

Сообщение должно помогать своему пользователю и не помогать чужому. Рабочие формулировки выглядят так:

- «Введите логин и пароль» при пустых полях;
- «Соберите изображение» при несобранном пазле;
- «Неверный логин или пароль» при несовпадении, без уточнения, что именно неверно;
- «Учётная запись заблокирована. Обратитесь к администратору» при `is_locked`;
- «Не удалось подключиться к базе данных. Проверьте MySQL и строку подключения» при исключении соединения.

Последнее сообщение не раскрывает тайну, а даёт диагностику: без него студент ищет причину в пароле, хотя база просто не запущена.

## Роли и разграничение доступа

Роль `admin` открывает вкладку «Пользователи», роль `user` её не видит. Скрытая вкладка это удобство, а не защита: проверка должна быть и в методах, которые меняют данные.

```csharp
public static void RequireAdmin(Account actor)
{
    if (actor.Role != "admin")
        throw new InvalidOperationException("Недостаточно прав для управления пользователями");
}
```

Метод `Save` вызывает `RequireAdmin` первой строкой. Тогда даже при ошибке в интерфейсе обычный пользователь не изменит чужую учётную запись. Проверка роли по имени пользователя, а не по логину, важнее: логин можно сменить, роль хранится в записи.

## Управление пользователями

Администратор видит таблицу с полями `id`, `login`, `role`, `failed_attempts`, `is_locked`. Хеш и соль не выводятся.

Добавление требует логина, пароля и роли. Проверяются обязательность полей, длина логина и допустимая роль. Уникальность логина обеспечивает ограничение базы, а приложение переводит ошибку ограничения в понятное сообщение «Логин уже занят».

Изменение начинается с выбора строки: поля заполняются текущими значениями. Пустой новый пароль означает сохранение прежнего. Иначе администратор, меняя роль, случайно сбросит пароль и заблокирует человеку вход.

Снятие блокировки устанавливает `failed_attempts = 0` и `is_locked = false`. После сохранения пользователь входит с прежним паролем, менять его не нужно.

<figcaption>Администратор снимает блокировку: счётчик ошибок обнуляется, вход снова разрешён.</figcaption>

Операции записи выполняются параметризованными командами. Склейка строки запроса с логином открывает путь к подстановке SQL и ломается на фамилии с апострофом.

## Валидация и дубли логина

Валидация делится на два уровня. Интерфейс не даёт отправить пустое поле и показывает сообщение. База не даёт записать дубль и нарушить ссылочную целостность.

Проверять уникальность запросом перед вставкой недостаточно: между проверкой и вставкой строку может создать другой администратор. Поэтому вставка выполняется сразу, а ошибку дубликата обрабатывают отдельно.

```csharp
catch (MySqlException ex) when (ex.Number == 1062)
{
    throw new InvalidOperationException("Логин уже занят");
}
```

Код 1062 означает нарушение уникального ключа в MySQL. Ловить общее исключение и писать «Ошибка» нельзя: студент не поймёт, что исправить, и будет менять пароль вместо логина.

## Чек-лист приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Пустые поля | сообщение, окно не закрывается |
| Неверный пароль | сообщение, счётчик увеличился |
| Несобранный пазл при верном пароле | сообщение, счётчик увеличился |
| Третья ошибка | `is_locked = true`, вход запрещён |
| Перезапуск приложения | блокировка сохранилась |
| Вход администратора | вкладка «Пользователи» доступна |
| Вход пользователя | вкладки «Пользователи» нет |
| Новый пользователь | создан, вход работает |
| Повтор логина | сообщение о дубле |
| Снятие блокировки | вход снова возможен |

Эту таблицу заполняют результатами, а не галочками: напротив каждой строки пишут, что именно увидели на экране и что стало в базе.

## Типичные ошибки

**Счётчик в памяти.** Блокировка исчезает после перезапуска. Лечится хранением в `users`.

**Пазл проверяется отдельно.** Неверный пазл не считается ошибкой, и блокировка не наступает.

**Проверка роли только в интерфейсе.** Вкладка скрыта, но метод сохранения доступен.

**Хеш в таблице.** Администратор видит служебные поля, которых видеть не должен.

**Открытый пароль.** Пароль хранится строкой, и любой, кто открыл базу, читает его.

**Молчаливое исключение.** При недоступной базе приложение закрывается без сообщения.

**Проверка уникальности запросом.** Дубль появляется при двух одновременных сохранениях.

**Пароль в строке подключения на экране.** Сообщение об ошибке не должно показывать строку подключения целиком.

## Итоги

- Состояние защиты хранится в базе: счётчик, блокировка, роль, хеш и соль.
- Пароль и пазл проверяются вместе, ошибка любого из них увеличивает счётчик.
- Третья ошибка ставит блокировку в той же транзакции, что и счётчик.
- Роль проверяется и в интерфейсе, и в методах изменения данных.
- Уникальность логина обеспечивает ограничение базы, а приложение объясняет ошибку.

! Без блокировки две копии приложения могут прочитать один и тот же счётчик.

Q: Какое ограничение базы защищает от двух одинаковых логинов?
+ UNIQUE на столбце login
- NOT NULL на столбце role
- DEFAULT у столбца is_locked
- PRIMARY KEY на столбце id
! Уникальный ключ не пропустит дубль даже при одновременном сохранении.

Q: Что хранится вместо самого пароля?
+ Хеш PBKDF2 с индивидуальной солью
- Пароль в зашифрованном виде с общим ключом
- Первые восемь символов пароля
- Контрольная сумма длины пароля
! Хеш нельзя обратить, а соль делает одинаковые пароли разными.

Q: Кому доступна вкладка управления пользователями?
+ Администратору
- Любому вошедшему пользователю
- Только тому, кто знает пароль root
- Всем, кто открыл приложение
! Роль user не должна видеть и вызывать операции управления учётными записями.

Q: Что означает пустой новый пароль при изменении пользователя?
+ Прежний пароль сохраняется
- Пароль становится пустым
- Учётная запись блокируется
- Пользователь удаляется
! Иначе смена роли случайно ломала бы вход человеку.

Q: Что должно произойти при недоступной базе данных?
+ Появится сообщение об ошибке, приложение останется открытым
- Приложение закроется без сообщения
- Пароль будет принят без проверки
- Учётная запись заблокируется навсегда
! Исключение соединения это отдельный случай с собственной диагностикой.

Q: Чем проверяется собранность пазла?
+ Сравнением порядка фрагментов с последовательностью 0, 1, 2, 3
- Совпадением числа нажатий
- Размером изображения
- Цветом рамки выбранного фрагмента
! Пазл собран, когда каждый фрагмент стоит на своём месте.

Q: Какие ошибки считаются неудачной попыткой входа?
+ Неверный пароль
+ Несобранный пазл при верном пароле
- Пустое поле логина
- Неверно выбранная роль
! Пустые поля отсекаются до обращения к базе и не тратят попытку.

Q: Какие поля не показывают в таблице администратора?
+ password_hash
+ salt
- login
- is_locked
! Служебные поля защиты не нужны для управления и раскрывают устройство системы.

Q: Что должно быть в приложении по требованиям задания?
+ Авторизация по логину и паролю
+ Роли Администратор и Пользователь
+ Пазл и блокировка после трёх ошибок
- Экспорт списка пользователей в Excel
! Перечисленные модули проверяются отдельно, экспорт в задании не требуется.

Q: Какой алгоритм используется для хеширования пароля?
= PBKDF2
! PBKDF2 с индивидуальной солью даёт необратимый хеш и замедляет перебор.

= 4
