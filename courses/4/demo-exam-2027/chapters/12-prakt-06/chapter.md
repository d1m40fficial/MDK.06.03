## Цель работы

Сервис, который отвечает только на правильный запрос, нельзя считать готовым. Нужно показать, что он читает базу, отдаёт согласованные поля, различает ошибку клиента и сбой сервера и подтверждает всё это исполняемыми проверками.

Цель работы: реализовать API заметок по контракту, воспроизвести успешный ответ, пустой массив, ошибку 400 и сбой 500, собрать коллекцию Postman с тестами и сдать её вместе с протоколом.

## Краткие теоретические сведения

**API** это соглашение о запросах и ответах. Клиент вызывает адрес, сервер читает данные и возвращает JSON. Клиент не знает структуру таблиц и не должен знать: он опирается только на имена и типы полей ответа.

**Контракт** фиксирует четыре поля: `id`, `title_user`, `content`, `formatted_date`. Заголовок и логин склеиваются через дефис с пробелами, дата приводится к формату ДД.ММ.ГГГГ. Вычисляемые значения не хранятся в таблице.

**Код ответа** сообщает класс результата. 200 означает успех, в том числе пустой список. 400 означает, что клиент прислал недопустимый параметр. 500 означает сбой на сервере. Тело ответа при ошибке содержит поле `error` и не содержит реквизитов подключения.

**Разделение 400 и 500** помогает клиенту понять, кто виноват. При 400 он исправляет запрос, при 500 ждёт восстановления сервиса и не меняет параметры. Один и тот же код на оба случая сбивает поддержку и скрывает настоящую причину.

**Коллекция Postman** хранит запросы, переменные и скрипты проверки. Проверки пишут на JavaScript в разделе Post-response, результаты видны во вкладке Test Results.

**Отдельный экземпляр для сбоя.** Чтобы воспроизвести 500, запускают второй процесс API с неверным портом базы. Рабочий экземпляр при этом продолжает отвечать 200.

### Шаг 1. Проверьте таблицу и тестовые записи

Убедитесь, что таблица создана и содержит от трёх до пяти записей.

```sql
USE dkip2027_course;

SELECT n.id, n.title, u.login, n.content, n.created_at
FROM notes n
JOIN users u ON u.id = n.id_user
ORDER BY n.id;
```

Если записей меньше трёх, добавьте их с разными датами и авторами. Одинаковые даты не показывают, что формат не зависит от значения, а один автор скрывает ошибку соединения таблиц.

```sql
INSERT INTO notes (title, content, id_user, created_at) VALUES
('Планы на неделю', 'Проверить заказ № 1 и подготовить отчёт.', 1, '2026-04-22'),
```

Проверьте внешний ключ: попытка вставить заметку с несуществующим `id_user` должна завершиться ошибкой.


### Шаг 2. Соберите чтение данных

Метод чтения выполняет один запрос и преобразует строки в объекты ответа.

```csharp
public static List<object> Read(int? userId)
{
    var result = new List<object>();
    using var connection = Database.Open();
    var cmd = new MySqlCommand(
        "SELECT n.id, n.title, u.login, n.content, n.created_at " +
        "FROM notes n JOIN users u ON u.id = n.id_user " +
        (userId is null ? "" : "WHERE n.id_user = @userId ") +
        "ORDER BY n.id", connection);
    if (userId is not null) cmd.Parameters.AddWithValue("@userId", userId);
    using var reader = cmd.ExecuteReader();
    while (reader.Read())
    {
        string title = reader.GetString("title");
        string login = reader.GetString("login");
        result.Add(new
        {
            id = reader.GetInt32("id"),
            title_user = title + " - " + login,
            content = reader.GetString("content"),
            formatted_date = reader.GetDateTime("created_at")
                .ToString("dd.MM.yyyy", CultureInfo.InvariantCulture)
        });
    }
    return result;
}
```

Проверьте, что при `userId = null` возвращается весь список, а при существующем номере только записи автора. Поле `content` не обрезайте и не заменяйте переносы строк.

Параметр добавляется в команду только при наличии значения. Склейка условия через конкатенацию открыла бы путь к подстановке SQL, а параметр передаёт значение отдельно от текста запроса и работает при любом вводе.

### Шаг 3. Создайте проект API

```powershell
dotnet new web -n Api
cd Api
dotnet add package MySqlConnector
```

В `Program.cs` зарегистрируйте маршрут и промежуточный обработчик исключений.

```csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.Use(async (context, next) =>
{
    try { await next(); }
    catch (Exception ex)
    {
        app.Logger.LogError(ex, "Ошибка обработки API");
        context.Response.StatusCode = 500;
        await context.Response.WriteAsJsonAsync(
            new { error = "Ошибка подключения к базе данных или обработки запроса" });
    }
});

IResult ReadNotes(HttpRequest request)
{
    int? userId = null;
    if (request.Query.Keys.Any(k => k != "user_id"))
        return Results.BadRequest(new { error = "Неизвестный параметр. Допустим user_id." });
    if (request.Query.ContainsKey("user_id"))
    {
        if (request.Query["user_id"].Count != 1
            || !int.TryParse(request.Query["user_id"], out var parsed)
            || parsed <= 0)
            return Results.BadRequest(new { error = "user_id должен быть положительным целым числом" });
        userId = parsed;
    }
    return Results.Ok(Notes.Read(userId));
}

app.MapGet("/notes", ReadNotes);
app.MapGet("/api/notes", ReadNotes);
app.Run();
```

Маршрут `MapGet` отвечает только на чтение. Попытка отправить POST на этот адрес должна вернуть 405, а не изменить данные.

### Шаг 5. Проверьте успешный ответ и пустой массив

Откройте в браузере `http://127.0.0.1:5271/notes`. Ответ должен быть массивом объектов с четырьмя полями.

```json
[
  {
    "id": 1,
    "title_user": "Планы на неделю - admin",
    "content": "Проверить заказ № 1 и подготовить отчёт.",
```


### Шаг 7. Проверьте сбой 500

Рабочую базу не останавливайте. Запустите второй экземпляр API с неверным портом подключения в отдельном окне.

```powershell
$env:DKIP_STACK='mysql'

dotnet run --project Api --urls http://127.0.0.1:5281
```

Запрос к `http://127.0.0.1:5281/notes` должен вернуть 500 и короткое сообщение об ошибке. Убедитесь, что в ответе нет строки подключения и имени пользователя базы. Рабочий экземпляр на порту 5271 при этом продолжает отвечать 200.

Второй экземпляр читает те же исходники, но другую строку подключения. Поэтому сбой воспроизводится без остановки MySQL и без риска испортить данные: первый процесс продолжает обслуживать запросы.

### Шаг 8. Соберите коллекцию Postman

Создайте коллекцию и две переменные: `base_url` со значением `http://127.0.0.1:5271` и `error_url` со значением `http://127.0.0.1:5281`.

Добавьте четыре запроса:

| Запрос | Адрес | Ожидание |
|---|---|---|
| Список заметок | `{{base_url}}/notes` | 200, массив |
| Пустой список | `{{base_url}}/notes?user_id=999` | 200, `[]` |
| Неверный параметр | `{{base_url}}/notes?user_id=abc` | 400, поле `error` |
| Сбой подключения | `{{error_url}}/notes` | 500, поле `error` |

Переменные коллекции наследуются всеми запросами. Если адрес вписан в каждый запрос отдельно, при смене порта придётся править четыре места и легко пропустить одно.

В разделе Post-response первого запроса добавьте проверки.

```javascript
pm.test("Статус 200", () => pm.response.to.have.status(200));

const body = pm.response.json();

pm.test("Ответ это массив", () => pm.expect(body).to.be.an("array"));

pm.test("Поля заметки", () => {
    body.forEach(note => {
        pm.expect(note).to.have.all.keys("id", "title_user", "content", "formatted_date");
        pm.expect(note.id).to.be.a("number");
        pm.expect(note.title_user).to.be.a("string");
    });
});

pm.test("Формат даты", () => {
    body.forEach(note =>
        pm.expect(note.formatted_date).to.match(/^\d{2}\.\d{2}\.\d{4}$/));
});
```

Для запроса с ошибкой 500 добавьте свои проверки.

```javascript
pm.test("Статус 500", () => pm.response.to.have.status(500));
pm.test("JSON с полем error", () => {
    pm.expect(pm.response.json()).to.have.property("error");
});
```

Запустите коллекцию кнопкой Send по каждому запросу и приложите скриншот вкладки Test Results.

Проверки должны падать на реальной ошибке. Чтобы убедиться в этом, временно уберите разделитель в `title_user` и запустите запрос снова: тест формата покажет ошибку. Затем верните код и повторите запуск. Коллекция, которая проходит всегда, ничего не подтверждает.

### Шаг 9. Сверьте ответ с контрактом

Сравните фактический ответ с таблицей требований.

| Поле | Тип | Пример | Проверка |
|---|---|---|---|
| `id` | число | 1 | совпадает с записью в базе |
| `title_user` | строка | `Планы на неделю - admin` | есть разделитель |
| `content` | строка | текст заметки | совпадает без изменений |
| `formatted_date` | строка | `22.04.2026` | шаблон ДД.ММ.ГГГГ |

Расхождение хотя бы в одном поле означает, что контракт нарушен, даже если код ответа 200.

Сверку выполняют до заполнения протокола. Если поле нарушено, тест покажет это на фактическом ответе, а сохранённый пример останется красивым и неверным.
