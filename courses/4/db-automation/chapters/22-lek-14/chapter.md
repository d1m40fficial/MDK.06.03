## Одна идея

В пятницу вечером приложение деканата начинает отвечать за полторы секунды вместо двухсот миллисекунд. Администратор видит загрузку процессора двенадцать процентов: железо свободно. В понедельник на диске `C:` заканчивается место: binary log вырос втрое, а временные таблицы писались на диск.

Мониторинг отвечает не на вопрос «сколько сейчас процессора», а на два других: **что с базой происходит прямо сейчас** и **что с ней будет через неделю, если ничего не менять**. Первый вопрос обслуживает инцидент, второй планирование. Панель, которая умеет только первый, работает как пожарная сигнализация без огнетушителя.

> [!KEY]
> Метрика без истории отвечает только на вопрос «сейчас». Чтобы ответить на вопрос «через неделю», значение сравнивают с базовой линией, то есть с тем, как эта же база вела себя в обычные дни.

## Три слоя наблюдения

Наблюдение идёт на трёх уровнях. Сверху приложение показывает, что чувствует пользователь: время ответа, ошибки, очередь. В середине сервер объясняет, на что уходит время: соединения, запросы, ожидания, блокировки. Внизу система говорит, какого ресурса не хватает: процессор, память, диск, место.

Разбор идёт сверху вниз. Если ответы быстрые, высокая загрузка процессора это рабочий режим, а не инцидент. Потом ищут запрос, создавший симптом, и только затем ресурс: рост дисковых операций ничего не значит, пока не видно, кто их вызвал.

## Счётчики сервера

`SHOW GLOBAL STATUS` возвращает несколько сотен строк «имя, значение». Это счётчики с момента запуска, поэтому смысл имеет прирост за интервал.

```sql
SHOW GLOBAL STATUS WHERE Variable_name IN (
  'Uptime', 'Threads_connected', 'Threads_running', 'Max_used_connections',
  'Questions', 'Slow_queries', 'Aborted_connects', 'Created_tmp_disk_tables',
  'Innodb_buffer_pool_reads', 'Innodb_buffer_pool_read_requests'
);
```

| Показатель | Переменная | О чём говорит |
|---|---|---|
| Соединения | `Threads_connected` | сколько клиентов держат сессию |
| Активные | `Threads_running` | сколько запросов выполняется сейчас |
| Пик соединений | `Max_used_connections` | приближались ли к пределу |
| Поток запросов | `Questions` | прирост даёт запросы в секунду |
| Медленные | `Slow_queries` | сколько запросов превысили порог |
| Отказы | `Aborted_connects` | неверный пароль, нет прав, обрыв сети |
| Временные таблицы | `Created_tmp_disk_tables` | сортировка не помещается в память |

Если `Questions` вырос на шесть тысяч за минуту, база обслуживает около ста запросов в секунду. `Threads_running` выше числа ядер означает очередь за процессором.

## Кто работает прямо сейчас

Список сессий даёт `SHOW FULL PROCESSLIST` или представление `information_schema.PROCESSLIST`: второе удобнее, к нему добавляют условие и сортировку.

```sql
SELECT id, user, host, db, command, time, state, LEFT(info, 80) AS query
FROM information_schema.PROCESSLIST
WHERE command <> 'Sleep' AND time > 5
ORDER BY time DESC;
```

Поле `time` показывает секунды в текущем состоянии, а не общее время запроса. Сессии `Sleep` держат соединение и ничего не делают: их много, когда приложение не возвращает подключение в пул.

## performance_schema

`performance_schema` это таблицы с инструментированными событиями: выполнения запросов, ожидания, блокировки, чтения файлов. Проверить сбор можно запросом `SELECT @@performance_schema;`. Если вернулся ноль, в `C:\xampp\mysql\bin\my.ini` добавляют строку `performance_schema=ON` и перезапускают MySQL.

```sql
SELECT DIGEST_TEXT,
       COUNT_STAR AS calls,
       ROUND(SUM_TIMER_WAIT / 1e12, 1) AS total_s,
       ROUND(AVG_TIMER_WAIT / 1e9, 1) AS avg_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 5;
```

`TIMER_WAIT` хранится в пикосекундах, поэтому деление на `1e12` даёт секунды. Сортировка по суммарному времени, а не по среднему, показывает, что оптимизировать: частый запрос на две миллисекунды нагружает базу сильнее редкого на две секунды.

Долгие запросы ищут в `events_statements_current`, транзакции в `INNODB_TRX`, ожидания в `INNODB_LOCK_WAITS`, а в MySQL 8 то же даёт `performance_schema.data_locks`. Взаимные блокировки разбирают по разделу `LATEST DETECTED DEADLOCK` команды `SHOW ENGINE INNODB STATUS`.

## Доступность, соединения, репликация

Доступность проверяют снаружи, запросом `SELECT 1` из того места, откуда ходит приложение: внутри всё может быть исправно, а порт 3306 закрыт.

Предел соединений задаёт `max_connections`. Когда `Threads_connected` подходит к нему, новые клиенты получают отказ. Лечится это пулом соединений и короткими транзакциями.

Отставание реплики показывает `SHOW SLAVE STATUS`, в новых версиях `SHOW REPLICA STATUS`. Поле `Seconds_Behind_Master` измеряет задержку применения журнала: пока оно растёт, читать с реплики опасно.

## Диск и binary log

Место кончается с постоянной скоростью, поэтому вопрос «что будет через неделю» здесь практичный.

```sql
SHOW VARIABLES LIKE 'datadir';
SHOW VARIABLES LIKE 'log_bin';
SHOW BINARY LOGS;
```

В XAMPP файлы лежат в `C:\xampp\mysql\data\` и называются `mysql-bin.000001`, `mysql-bin.000002`. Чистят журнал командой `PURGE BINARY LOGS BEFORE DATE_SUB(NOW(), INTERVAL 7 DAY);` или настройкой `binlog_expire_logs_seconds`. Перед очисткой проверяют свежую копию: без binary log базу между дампами не восстановить.

## Buffer pool

InnoDB держит страницы таблиц и индексов в буферном пуле. Доля попаданий считается по двум счётчикам: `Innodb_buffer_pool_read_requests` это обращения к странице, `Innodb_buffer_pool_reads` это обращения, ушедшие на диск.

```sql
SHOW STATUS LIKE 'Innodb_buffer_pool_read%';
SHOW STATUS LIKE 'Innodb_buffer_pool_pages%';
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
```

Отношение числа обращений, обслуженных памятью, к общему числу обращений даёт коэффициент попаданий. Значение около `0.99` означает, что почти все чтения обслужены памятью, но высокий коэффициент не гарантирует быстрых ответов: промахи могут приходиться на частые запросы.

Чтение статусов вынесено в отдельный метод: он открывает соединение, читает две колонки и складывает числовые значения в словарь. Строки вроде `Ssl_cipher` не числа, поэтому разбор идёт через `TryParse`.

```csharp
using MySqlConnector;

static async Task<Dictionary<string, long>> ReadStatusAsync(string cs)
{
    var raw = new Dictionary<string, long>();
    await using var conn = new MySqlConnection(cs);
    await conn.OpenAsync();
    await using var cmd = new MySqlCommand("SHOW GLOBAL STATUS", conn);
    await using var reader = await cmd.ExecuteReaderAsync();
    while (await reader.ReadAsync())
        if (long.TryParse(reader.GetString(1), out var value))
            raw[reader.GetString(0)] = value;
    return raw;
}
```

Обработчик таймера считает скорость и обновляет список строк. Таймер останавливают на время запроса: иначе медленный ответ наложится на следующий тик.

```csharp
private readonly BindingList<MetricRow> _rows = new();
private Dictionary<string, long> _prev = new();
private DateTime _prevAt = DateTime.UtcNow;

private async void timer_Tick(object? sender, EventArgs e)
{
    _timer.Stop();
    try
    {
        var raw = await ReadStatusAsync(_connectionString);
        var seconds = (DateTime.UtcNow - _prevAt).TotalSeconds;
        double Rate(string key) => _prev.TryGetValue(key, out var was) && seconds > 0
            ? (raw[key] - was) / seconds : 0;

        _rows.Clear();
        _rows.Add(new MetricRow("Запросов в секунду", Rate("Questions")));
        _rows.Add(new MetricRow("Активных сессий", raw["Threads_running"]));
        _rows.Add(new MetricRow("Медленных запросов", raw["Slow_queries"]));
        _prev = raw;
        _prevAt = DateTime.UtcNow;
    }
    finally { _timer.Start(); }
}

private sealed record MetricRow(string Metric, double Value);
```

Строку подключения приложение берёт из переменной окружения, а не из кода. Пользователь `dean_app` получает `SELECT` на `performance_schema` и `PROCESS`, но не право менять данные.

## Базовая линия и пороги

Порог нельзя назначить на глаз: одинаковых баз не бывает. Сначала собирают базовую линию, две-четыре недели значений по часам и дням недели: в понедельник нагрузка выше, чем в субботу.

Линию строят по процентилям, а не по среднему. Девяносто пятый процентиль означает, что девяносто пять процентов запросов были быстрее этого значения, а среднее скрывает редкие медленные запросы, которые как раз и портят работу.

| Метрика | Внимание | Тревога |
|---|---|---|
| Занятые соединения | 70% от предела | 85% дольше пяти минут |
| Свободное место | меньше 25% | меньше 10% |
| Отставание реплики | больше 10 секунд | больше 60 секунд |
| Запрос дольше порога | больше 30 секунд | больше пяти минут |
| Доля попаданий в пул | ниже 0.99 | ниже 0.95 |

Числа калибруют по своей базе: для одной норма это сто соединений, для другой тревога уже на тридцати. Порог ставят там, где заканчивается нормальная работа.

> [!PITFALL] Оповещение без действия
> Правило, на которое никто не реагирует, хуже отсутствия правила: оно приучает игнорировать канал. У каждого оповещения должен быть владелец и короткая инструкция, что проверить первым.

::/gate

::gate Как разобрать инцидент и где чаще всего ошибаются?

## Разбор инцидента

1. **Зафиксировать картину.** Записать время начала, что видят пользователи, какие метрики выросли, и сохранить снимок `PROCESSLIST`.
2. **Остановить изменения.** Не выпускать миграции и не менять настройки, пока причина не найдена.
3. **Сузить слой.** Если ответы медленные, а соединения в норме, идти в запросы. Если соединения на пределе, идти в пул.
4. **Найти ожидание.** Посмотреть `state` активных сессий, `INNODB_TRX` и `INNODB_LOCK_WAITS`.
5. **Действовать минимально.** Отменить один зависший запрос, а не перезапускать сервер: перезапуск стирает следы.

После устранения отвечают на два вопроса: почему сломалось и почему заметили поздно. Второй важнее: если оповещение сработало через сорок минут, чинить нужно и порог.

## Типичные ошибки

- **Смотреть только на процессор.** Свободный процессор не означает здоровую базу: узкое место часто в диске.
- **Нет базовой линии.** Без истории любое число выглядит нормальным или тревожным произвольно.
- **Слишком много оповещений.** Двадцать правил, из которых пятнадцать срабатывают ежедневно, прячут настоящее событие.
- **Среднее вместо процентиля.** Среднее время ответа остаётся красивым, пока часть пользователей ждёт секундами.
- **Опрос без остановки таймера.** Второй запрос стартует до завершения первого, и приложение показывает собственную очередь.

## Проверьте себя

> [!CHECK] Свободное место 30%, и оно уменьшается на 2% в сутки. Это инцидент?
> Пока нет, но это задача на неделю: место кончится примерно через две недели. Правильное действие не тревога, а проверка, что именно растёт.

> [!CHECK] Время ответа выросло, процессор свободен, соединений мало. Где искать причину?
> В ожиданиях и запросах. Смотрят `Threads_running`, `state` активных сессий и `INNODB_LOCK_WAITS`. Ожидание блокировки указывает на чужую транзакцию, а рост `Created_tmp_disk_tables` на сортировку, которой не хватило памяти.

> [!CHECK] Почему оповещение «среднее время запроса выше 100 мс» плохо ловит проблему?
> Среднее сглаживает редкие выбросы. Если один запрос из ста идёт пять секунд, среднее вырастет незначительно, а пользователь ждёт очень долго. Процентиль показывает хвост распределения, где и живут проблемы.

## Итог

- Мониторинг отвечает на два вопроса: состояние сейчас и тренд на неделю вперёд.
- Наблюдают три слоя: приложение даёт симптом, сервер даёт причину, система даёт ресурс.
- `SHOW GLOBAL STATUS` даёт счётчики, `PROCESSLIST` сессии, `performance_schema` историю запросов.
- Порог ставят по базовой линии и процентилям, а не по среднему.
- WinForms опрашивает сервер по таймеру и показывает приросты, а не абсолютные значения.

! Questions это счётчик, поэтому смысл имеет прирост, делённый на интервал.

Q: Где видно, какие запросы выполняются прямо сейчас?
+ В information_schema.PROCESSLIST
- В таблице mysql.user
- В файле my.ini
- В журнале ошибок Apache
! PROCESSLIST показывает по строке на каждую сессию с текущим запросом.

Q: В каких единицах performance_schema хранит TIMER_WAIT?
+ В пикосекундах
- В секундах
- В миллисекундах
- В микросекундах
! Поэтому деление на 1e12 даёт секунды, а на 1e9 миллисекунды.

Q: Что показывает Threads_running?
+ Число запросов, которые выполняются в этот момент
- Число запросов, ожидающих подключения
- Общее число сессий с момента запуска
- Количество временных таблиц на диске
! Если значение выше числа ядер, запросы стоят в очереди за процессором.

Q: Почему в events_statements_summary_by_digest сортируют по SUM_TIMER_WAIT?
+ Так находят запросы, которые суммарно съедают больше всего времени
- Так находят самый длинный одиночный запрос
- Так проверяют права пользователей
- Так считают свободное место на диске
! Частый короткий запрос нагружает базу сильнее редкого длинного.

Q: О чём говорит растущее значение Seconds_Behind_Master?
+ Реплика отстаёт и читать с неё опасно
- Основная база переполнена соединениями
- В буферном пуле закончилась память
- Binary log отключён в my.ini
! Поле измеряет задержку применения журнала.

Q: Зачем в приложении WinForms останавливают таймер на время опроса?
+ Чтобы следующий опрос не начался до завершения предыдущего
- Чтобы уменьшить размер журнала MySQL
- Чтобы приложение не закрылось
- Чтобы отключить буферный пул
! Иначе обработчики конкурируют за соединение.

Q: Что проверяют перед очисткой binary log?
+ Что есть свежая резервная копия базы
- Что все пользователи отключились
- Что буферный пул заполнен
- Что Apache остановлен
! Без binary log нельзя восстановить базу между дампами.

Q: Какие метрики относятся к слою сервера MySQL, а не к операционной системе?
+ Число активных соединений
+ Время выполнения запросов
+ Ожидания на блокировках
- Загрузка процессора
- Свободное место на разделе
! Соединения, запросы и ожидания видны в представлениях MySQL.

Q: Какие признаки говорят о проблеме с соединениями?
+ Число соединений приблизилось к max_connections

+ Много сессий в состоянии Sleep
- Размер базы вырос за месяц
- Увеличилось число строк в students
! Предел соединений, отказы и спящие сессии создают риск.

Q: Что входит в разбор инцидента?
+ Фиксация картины и времени начала
+ Поиск ожиданий у активных сессий
+ Запись хронологии действий
- Немедленный перезапуск сервера
- Удаление журналов до выяснения причины
! Снимок и хронология сохраняют следы для разбора.

= доля попаданий
