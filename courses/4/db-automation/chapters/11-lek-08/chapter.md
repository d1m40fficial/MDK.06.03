## Одна идея

Отчёт по успеваемости группы собирается восемь секунд. `EXPLAIN` показывает `type: ALL`: MySQL читает все двести тысяч записей `enrollments`, чтобы найти двадцать нужных. Добавляем индекс по двум столбцам, и тот же отчёт отвечает за три сотые секунды. Через неделю выясняется, что загрузка новых ведомостей замедлилась почти втрое.

**Индекс InnoDB это отдельная структура, которая хранит значения столбцов в порядке, удобном для поиска.** Он ускоряет чтение, избавляя от просмотра всей таблицы, и замедляет запись, потому что изменение нужно отразить и в индексе. Хороший индекс это компромисс под конкретные запросы, а не украшение схемы.

## Дерево, по которому ищут строку

InnoDB хранит данные в B+tree. В корне и внутренних страницах лежат ключи и ссылки на следующие страницы, в листьях лежат сами записи. Поиск начинается с корня, на каждой странице делит диапазон пополам и за три или четыре шага доходит до нужного листа. Для миллиона строк это три или четыре чтения страниц вместо миллиона.

На рисунке корень хранит только границы, страницы первого уровня сужают диапазон, а записи лежат в листьях. Стрелки между листьями позволяют прочитать `WHERE id BETWEEN 9 AND 27` одним проходом, не поднимаясь обратно к корню.

У InnoDB два вида индексов. **Кластерный индекс** один: это сама таблица, разложенная по первичному ключу. **Вторичный индекс** хранит столбцы индекса и значение первичного ключа, поэтому поиск идёт в два прохода: сначала ключ, потом строка в кластерном индексе.

| Свойство | Кластерный индекс | Вторичный индекс |
|---|---|---|
| Сколько их | один, это таблица | сколько объявили |
| Что хранит в листе | всю строку | столбцы индекса и первичный ключ |
| Сколько проходов | один | два, если нужны другие столбцы |
| Влияние ключа | ширина ключа раздувает таблицу | ширина ключа раздувает все индексы |

Отсюда правило: первичный ключ делают коротким и растущим. `AUTO_INCREMENT` дописывает строки в конец, а случайный UUID разбрасывает их по дереву и вызывает расщепление страниц.

## Составной индекс и порядок столбцов

Составной индекс это дерево, отсортированное сначала по первому столбцу, потом по второму. Для `(group_id, full_name)` все студенты группы 2 стоят рядом, а внутри группы фамилии идут по алфавиту.

```sql
CREATE INDEX idx_students_group_name ON students (group_id, full_name);
```

Правило левого префикса: индекс работает, только если условие опирается на его начало. Проверим:

| Запрос | Использует индекс | Почему |
|---|---|---|
| `WHERE group_id = 2` | да | первый столбец известен |
| `WHERE group_id = 2 ORDER BY full_name` | да, без сортировки | внутри группы фамилии уже упорядочены |
| `WHERE full_name = 'Иванов'` | нет | второго столбца без первого недостаточно |
| `WHERE full_name LIKE 'Ив%' AND group_id = 2` | да | равенства можно переставить местами |
| `WHERE group_id > 1 ORDER BY full_name` | частично | диапазон ломает общий порядок, нужна сортировка |

Последняя строка показывает, почему порядок важен: после `>` дерево не отдаёт глобальный порядок по второму столбцу.

Правило: сначала равенство, затем диапазон, затем сортировка. Индекс `(group_id, enrolled_at)` обслуживает отчёт по группе, а `(enrolled_at, group_id)` отчёт по всем группам, но не наоборот.

## Селективность

**Селективность** показывает, какую долю строк отсекает значение: отношение числа различных значений к числу строк. У `email` в таблице `students` десять различных значений на десять строк, селективность единица. У `group_id` три значения на десять строк, селективность 0,3.

```sql
SELECT
  COUNT(DISTINCT group_id) / COUNT(*) AS group_sel,
  COUNT(DISTINCT email) / COUNT(*) AS email_sel
FROM students;
```

Чем выше селективность, тем меньше строк остаётся после первого шага и тем полезнее индекс. Столбец `status` с тремя значениями на миллион строк отсекает треть таблицы, и оптимизатор часто выбирает сканирование.

Низкая селективность не приговор: если все запросы фильтруют по `group_id`, индекс с него начинается и работает. Плохо строить индекс на редкий столбец с малым числом значений и ждать ускорения всех запросов.

## Покрывающий индекс

Если индекс содержит все столбцы запроса, серверу не нужно идти в таблицу. Такой индекс называют **покрывающим**, а в `EXPLAIN` появляется `Using index`.

```sql
CREATE INDEX idx_enroll_cover ON enrollments (student_id, course_id, grade);

SELECT course_id, grade
FROM enrollments
WHERE student_id = 7;
```

Запрос читает только индекс: находит студента и забирает пару столбцов из листа, не обращаясь к таблице. На больших таблицах это сокращает чтение в разы.

Цена та же, что у любого индекса: каждая запись обновляет ещё одно дерево. Широкий индекс может ускорить один отчёт и замедлить вставку. `SELECT *` покрывающий индекс ломает: появился столбец вне индекса, и сервер идёт в таблицу.

## Частичного индекса нет, но есть префиксный

В MySQL нельзя написать `CREATE INDEX ... WHERE status = 'active'`: частичных индексов здесь нет. Вместо них есть три приёма.

**Префиксный индекс** индексирует начало длинной строки:

```sql
CREATE INDEX idx_courses_title ON courses (title(20));
```

Он помогает поиску `WHERE title LIKE 'Информа%'` и экономит место. Но префикс не покрывает запрос, не годится для сортировки по полному значению и теряет селективность, если начала строк совпадают. Глубину проверяют запросом:

```sql
SELECT COUNT(DISTINCT LEFT(title, 20)) / COUNT(*) AS prefix_sel FROM courses;
```

**Функциональный индекс** появился в MySQL 8.0.13 и индексирует выражение:

```sql
CREATE INDEX idx_students_email_lower ON students ((LOWER(email)));
```

Запрос `WHERE LOWER(email) = 'ivanov@example.ru'` теперь может использовать индекс. В MariaDB такого синтаксиса нет, там берут **генерируемый столбец**:

```sql
ALTER TABLE students
  ADD email_norm VARCHAR(128) AS (LOWER(email)) STORED,
  ADD INDEX idx_email_norm (email_norm);
```

Третий приём это составной индекс, где признак стоит первым: `(status, created_at)` обслуживает выборку активных записей за период. Он индексирует все строки, но запросы с равенством по `status` получают нужный порядок.

::gate Во сколько обходится лишний индекс при записи?

## Стоимость записи

Каждый вторичный индекс это отдельное дерево. `INSERT` в таблицу с пятью индексами обновляет шесть деревьев: кластерное и пять вторичных. Каждое обновление это поиск страницы, запись в redo и undo log, а при заполненной странице ещё и расщепление.

При расщеплении заполненная страница делится на две, и половина записей переезжает. На диске это случайные операции, в буферном пуле новая страница вытесняет старую. Чем больше индексов и случайнее ключи, тем чаще это происходит.

Цену проверяют замером: загрузить пятьдесят тысяч строк без индексов и с ними, сравнить время и счётчик:

```sql
SHOW GLOBAL STATUS LIKE 'Innodb_rows_inserted';
```

Разница в разы на учебном стенде нормальна. В рабочей системе добавляются блокировки и репликация, поэтому лишний индекс бьёт по всему конвейеру записи.

> [!TRADEOFF] Индекс под отчёт или под запись
> Индекс `(student_id, course_id, grade)` ускоряет отчёт и замедляет каждую вставку оценки. Если отчёт запускают раз в день, а оценки ставят сотни раз, широкий индекс может стоить дороже пользы. Сначала измеряют, потом добавляют.

## SHOW INDEX и EXPLAIN

`SHOW INDEX` показывает, что реально построено:

```sql
SHOW INDEX FROM enrollments;
```

В выводе важны `Key_name`, `Seq_in_index`, `Column_name` и `Cardinality`. Если `Seq_in_index` у `group_id` равно 1, а у `full_name` равно 2, индекс начинается с группы, и запрос только по фамилии его не использует.

`EXPLAIN` показывает, как сервер собирается выполнять запрос:

```sql
EXPLAIN SELECT s.full_name, e.grade
FROM students s
JOIN enrollments e ON e.student_id = s.id
WHERE s.group_id = 2;
```

Смотрят на `type`, `key`, `rows` и `Extra`. `ALL` это полное сканирование, `ref` поиск по индексу, `eq_ref` одна строка по уникальному ключу. `Extra` сообщает о `Using index`, `Using where`, `Using filesort` или `Using temporary`.

`EXPLAIN` не выполняет запрос и показывает оценку. Точные числа даёт `EXPLAIN ANALYZE` в MySQL 8.0.18 и новее, а в MariaDB `ANALYZE SELECT`.

## ANALYZE TABLE

Оптимизатор выбирает индекс по статистике, а это оценки, а не точные знания. После массовой загрузки они устаревают, и план остаётся прежним, хотя данные другие.

```sql
ANALYZE TABLE enrollments;
```

Команда пересчитывает распределение ключей и обновляет `Cardinality` в `SHOW INDEX`. В InnoDB статистика по умолчанию хранится на диске (`innodb_stats_persistent=ON`) и обновляется автоматически после заметной доли изменений, но ручной запуск после большой загрузки всё равно полезен.

Запускать `ANALYZE TABLE` перед каждым запросом бессмысленно: это чтение страниц. Достаточно делать это после массового импорта, миграции или когда `EXPLAIN` показывает странный план при подходящем индексе.

## Типичные ошибки

- **Индекс на каждый столбец.** Пять одиночных индексов не заменяют один составной: сервер выберет один, а запись подорожает в пять раз. Нужен индекс под запрос, а не набор по всем полям.
- **Неверный порядок столбцов.** Индекс `(enrolled_at, group_id)` не помогает запросу `WHERE group_id = 2 AND enrolled_at > '2026-09-01'` так, как помог бы обратный порядок.
- **Индекс не используется.** Функция над столбцом, сравнение строки с числом, шаблон с ведущим процентом, `OR` по разным столбцам. Индекс существует, но план показывает `ALL`.
- **Дубли и перекрытия.** Индекс `(a)` полностью покрыт индексом `(a, b)`. Держать оба значит платить за запись дважды.
- **Вера в имя вместо плана.** Индекс создан, значит работает, думает разработчик. Проверять нужно `EXPLAIN`, а не список индексов.
- **Забытая статистика.** После импорта план остался прежним, и виноват не индекс, а устаревшие оценки.

> [!PITFALL] Функция в условии
> `WHERE DATE(paid_at) = '2026-10-27'` не использует индекс по `paid_at`: функция применяется к каждой строке, и сравнивать нечего. Диапазон `paid_at >= '2026-10-27' AND paid_at < '2026-10-28'` возвращает индекс в работу.

## Проверьте себя

> [!CHECK] Запрос фильтрует по `full_name`, а индекс построен на `(group_id, full_name)`. Почему индекс не помогает?
> Дерево отсортировано сначала по группе. Без условия по `group_id` нужные фамилии разбросаны по всем группам, и сервер не может отсечь диапазон. Нужен отдельный индекс на `full_name` или другой порядок столбцов.

> [!CHECK] Отчёт стал быстрее, а загрузка ведомостей замедлилась. Что проверить?
> Число индексов на таблице и их ширину. Каждая вставка обновляет все деревья, а широкий покрывающий индекс добавляет больше страниц и расщеплений. Стоит убрать неиспользуемые индексы и сравнить замеры до и после.

> [!CHECK] `EXPLAIN` показывает `Using index`. Что это значит и чего лишает запрос?
> Все нужные столбцы нашлись в индексе, и сервер не читает таблицу. Это быстрее, но запрос с `SELECT *` или с новым столбцом вне индекса сразу потеряет это преимущество.

## Итог

- Индекс это B-tree, который ускоряет поиск и требует обновления при каждой записи.
- Составной индекс работает по левому префиксу, поэтому порядок столбцов задаёт, какие запросы он обслужит.
- Селективность показывает пользу индекса, но низкая селективность первого столбца допустима, если по нему фильтруют все запросы.
- Покрывающий индекс убирает чтение таблицы, частичного индекса в MySQL нет, его заменяют префикс, выражение или генерируемый столбец.
- `SHOW INDEX`, `EXPLAIN` и `ANALYZE TABLE` показывают, что построено, что выбрано и на какой статистике.

## Тест по лекции

::quiz
Q: Что делает индекс InnoDB?
+ Ускоряет чтение и замедляет запись
- Ускоряет и чтение, и запись
- Замедляет чтение и ускоряет запись
- Не влияет на запись
! Каждое изменение нужно отразить в дереве индекса, поэтому запись дорожает.

Q: Что хранится в листе вторичного индекса InnoDB?
+ Столбцы индекса и значение первичного ключа
- Вся строка таблицы
- Только первичный ключ
- Указатель на файл таблицы
! По ключу сервер находит строку в кластерном индексе, поэтому нужен второй проход.

Q: Какой запрос использует индекс (group_id, full_name)?
+ WHERE group_id = 2
+ WHERE group_id = 2 ORDER BY full_name
+ WHERE full_name = 'Иванов' AND group_id = 2
- WHERE full_name = 'Иванов'
- WHERE full_name LIKE 'Ив%'
! Индекс работает по левому префиксу, а равенства оптимизатор переставляет сам.

Q: Что показывает селективность столбца?
+ Долю различных значений среди всех строк
- Число индексов на таблице
- Среднюю длину строки
- Скорость вставки
! Чем выше селективность, тем меньше строк остаётся после первого шага поиска.

Q: Какой индекс называют покрывающим?
+ Тот, который содержит все столбцы запроса
- Тот, который покрывает всю таблицу
- Тот, который построен на первичном ключе
- Тот, который занимает всю страницу
! Серверу не нужно обращаться к таблице, и в EXPLAIN появляется Using index.

Q: Есть ли в MySQL частичный индекс с условием WHERE?
+ Нет, вместо него используют префикс, выражение или составной индекс
- Да, синтаксис CREATE INDEX WHERE
- Да, но только для InnoDB
- Да, только для текстовых столбцов
! Частичных индексов нет, ближайшие замены это префиксный и функциональный индекс.

Q: Что делает ANALYZE TABLE?
+ Пересчитывает статистику распределения ключей
- Перестраивает все индексы
- Удаляет дубли строк
- Сжимает таблицу
! Оптимизатор опирается на статистику, и после массовой загрузки её нужно обновить.

Q: Что означает type: ALL в EXPLAIN?
+ Полное сканирование таблицы
- Поиск по уникальному ключу
- Поиск по индексу
- Чтение только индекса
! ALL означает, что сервер собирается прочитать все строки.

Q: Почему случайный UUID в первичном ключе хуже AUTO_INCREMENT?
+ Вставки разбрасываются по дереву и вызывают расщепление страниц
- UUID занимает меньше места
- UUID нельзя индексировать
- AUTO_INCREMENT запрещён в InnoDB
! Растущий ключ дописывает строки в конец, случайный ломает порядок вставки.

Q: Какие условия мешают использовать индекс?
+ Функция над столбцом в WHERE
+ Шаблон LIKE '%Иванов'
+ Сравнение строкового столбца с числом
+ Условие OR по разным столбцам
- Равенство по первому столбцу индекса
- Сортировка по второму столбцу после равенства
! Индекс теряет работу, когда значение столбца преобразуется или диапазон не определён.

Q: Какие утверждения о составном индексе верны?
+ Порядок столбцов влияет на применимость
+ Равенства оптимизатор может переставить
+ Диапазон по первому столбцу ломает сортировку по второму
+ Индекс (a, b) работает для запроса по a
- Индекс (a, b) покрывает запрос только по b
- Порядок столбцов не важен
! Дерево отсортировано по первому столбцу, поэтому всё решает левый префикс.

Q: Что даёт покрывающий индекс?
+ Меньше чтений таблицы
+ Короткий путь до нужных столбцов
+ В EXPLAIN появляется Using index
- Ускоряет вставку
- Уменьшает число индексов
! Запрос обслуживается индексом целиком, но запись от этого не ускоряется.

Q: Что показывает Seq_in_index в SHOW INDEX?
+ Позицию столбца внутри индекса
- Число различных значений
- Тип индекса
- Размер страницы
! Порядок столбцов определяет, какие запросы используют левый префикс.

Q: Как называется индекс, который содержит все столбцы запроса?
= покрывающий
= covering
! Покрывающий индекс избавляет от второго прохода в таблицу.

Q: Какая команда пересчитывает статистику таблицы?
= ANALYZE TABLE
= analyze table
! ANALYZE TABLE обновляет оценки распределения ключей для оптимизатора.
