## Одна идея

Запрос «покажи студентов группы ИС-21 по алфавиту» на десяти строках выполняется мгновенно. Через год в базе десять тысяч студентов, и тот же запрос читает всю таблицу, сортирует её и только потом отдаёт двадцать строк. Администратор добавляет индекс, запрос ускоряется в сто раз, а через месяц жалуется оператор: массовая загрузка оценок стала вдвое медленнее.

**Индекс это отсортированный указатель, который ускоряет чтение и замедляет запись.** Каждая вставка, обновление и удаление обязаны поддерживать в индексе порядок, поэтому за скорость `SELECT` платят скоростью `INSERT`. Хороший индекс строится не «на всякий случай», а под конкретный запрос с конкретным условием.

Отсюда правило: сначала находят медленный запрос и его план, потом решают, какой индекс ему нужен. Индекс, созданный до анализа запросов, часто оказывается лишним грузом.

## Как устроен B-tree

B-tree, или сбалансированное дерево, это тип индекса по умолчанию. В корне и внутренних узлах лежат ключи, которые направляют поиск в нужную ветвь, а в листьях хранятся ключи и ссылки на строки таблицы. Листья связаны между собой, поэтому диапазон читается последовательно, без возврата к корню.

Высота дерева растёт логарифмически. Для миллиона строк это обычно три или четыре уровня, то есть три или четыре страницы вместо тысяч страниц таблицы. Именно поэтому индекс находит строку за считанные обращения к диску.

B-tree поддерживает равенство, диапазоны, `BETWEEN`, `IN`, `IS NULL`, сортировку и поиск по префиксу `LIKE 'ИС%'`. Он не помогает при `LIKE '%21'`, потому что шаблон не задаёт начало ключа.

Другие типы решают другие задачи:

- **hash** хранит только хеш ключа и годится для равенства, диапазоны и сортировку он не ускоряет;
- **GIN** работает с составными значениями: `jsonb`, массивами, полнотекстовым поиском;
- **GiST** обслуживает геометрию, диапазоны и поиск ближайших соседей;
- **BRIN** хранит минимум и максимум по блокам и занимает килобайты на большой таблице с физически упорядоченными данными.

```sql
CREATE INDEX idx_audit_details ON audit_log USING gin (details);
CREATE INDEX idx_audit_at_brin ON audit_log USING brin (at);
```

GIN здесь ускоряет поиск по полям JSON, BRIN подходит журналу, который только дописывается: значения времени растут вместе с номерами блоков. На маленькой таблице BRIN бесполезен, потому что вся она читается быстрее, чем окупается индекс.

## Составной индекс и порядок столбцов

Составной индекс строится по нескольким столбцам, и порядок в нём не случаен. Индекс работает как телефонный справочник: найти фамилию можно, найти имя без фамилии нельзя.

```sql
CREATE INDEX idx_students_group_name ON students (group_id, full_name);
```

Этот индекс обслуживает запрос `WHERE group_id = 2 ORDER BY full_name`, потому что условие равенства задаёт первый столбец, а сортировка идёт по второму. Он же помогает запросу `WHERE group_id = 2 AND full_name LIKE 'А%'`.

Запрос `WHERE full_name = 'Иванов Иван'` этим индексом не воспользуется: первый столбец не задан. Так работает правило левого префикса: индекс читается слева направо, и пропустить столбец нельзя.

Порядок выбирают по правилу: сначала столбцы равенства, потом диапазон, потом сортировка. Для запроса с условием по курсу и периоду правильный индекс выглядит так:

```sql
CREATE INDEX idx_enrollments_course_date ON enrollments (course_id, enrolled_at);
```

Обратный порядок `(enrolled_at, course_id)` для условия `WHERE course_id = 5` почти бесполезен: диапазон времени стоит первым, а курс вторым, и без времени в условии индекс не сужает поиск.

## Селективность

Селективность это доля строк, которую возвращает условие. Чем меньше доля, тем полезнее индекс.

- `email` уникален: условие возвращает одну строку из десяти тысяч, индекс незаменим.
- `group_id` принимает три значения: условие возвращает треть таблицы, и последовательное чтение может оказаться дешевле.
- `grade` принимает четыре значения: индекс по оценке редко нужен для чтения, зато бывает полезен как частичный.

Планировщик знает распределение по статистике и сравнивает стоимость вариантов. Если индекс должен прочитать треть таблицы, а потом ещё и саму таблицу, последовательное сканирование выигрывает. Поэтому индекс на низкоселективный столбец не «не работает», а просто не окупается.

```sql
ANALYZE students;
SELECT attname, n_distinct, correlation
FROM pg_stats
WHERE tablename = 'students';
```

`n_distinct` показывает число различных значений, `correlation` близость физического порядка к логическому. Высокая корреляция помогает BRIN и подсказывает, что данные лежат кучно.

## Покрывающий и частичный индексы

Обычный индекс находит строку, но за остальными столбцами приходится идти в таблицу. Покрывающий индекс хранит нужные столбцы прямо в листьях, и запрос отвечает, не читая таблицу.

```sql
CREATE INDEX idx_enrollments_student_grade
ON enrollments (student_id) INCLUDE (grade);

SELECT grade FROM enrollments WHERE student_id = 7;
```

Столбец `grade` не участвует в поиске, он только хранится. В плане появляется `Index Only Scan`, и число чтений таблицы падает до нуля. Работает это при одном условии: карта видимости должна показывать, что строки не изменялись после последней очистки. Поэтому `VACUUM` важен не только для места на диске.

Частичный индекс строится не по всей таблице, а по строкам, которые удовлетворяют условию.

```sql
CREATE INDEX idx_enrollments_bad
ON enrollments (student_id) WHERE grade = 2;
```

Он занимает меньше места и обновляется реже, потому что остальные строки в него не попадают. Запрос обязан содержать то же условие, иначе планировщик индекс не применит.

Частичный индекс удобен для «горячей» части данных: непроверенные заявки, неоплаченные счета, активные записи. В учебной базе это долги по оценке два или платежи без подтверждения.

## Стоимость записи

Каждый индекс это отдельная структура, которую нужно обновлять. Вставка строки в таблицу с пятью индексами порождает пять вставок в индексы и пять записей в журнал.

```sql
INSERT INTO enrollments (student_id, course_id, grade)
SELECT s.id, 1, 4 FROM students s;
```

Если на `enrollments` висят индексы по `student_id`, `course_id`, `grade`, `enrolled_at` и составной, одна команда обновит пять структур. На десяти строках это незаметно, на массовой загрузке становится заметной потерей времени.

Обновление иногда обходится дешевле. Если ни один индексированный столбец не меняется и на странице есть место, PostgreSQL делает HOT-обновление: новая версия строки остаётся на той же странице, индексы не трогаются. Параметр `fillfactor` оставляет место на странице именно для таких случаев.

Со временем индекс раздувается: удалённые строки оставляют пустые места, страницы заполняются неравномерно. Раздутый индекс читается дольше и занимает больше диска.

```sql
REINDEX INDEX CONCURRENTLY idx_students_group_name;
```

`REINDEX` перестраивает индекс, `CONCURRENTLY` не блокирует запись на время работы. Обычный `REINDEX` быстрее, но останавливает изменения таблицы. Для рабочей базы выбирают конкурентный вариант и следят за местом на диске: старая и новая копии существуют одновременно.

## Статистика и наблюдение за индексами

Индекс, который никто не использует, это чистый расход. PostgreSQL считает обращения к каждому индексу.

```sql
SELECT indexrelname, idx_scan, idx_tup_read
FROM pg_stat_user_indexes
WHERE relname = 'students'
ORDER BY idx_scan;
```

`idx_scan` это число сканирований индекса. Ноль после месяца работы означает, что индекс не нужен запросам, но продолжает замедлять запись. Перед удалением проверяют, не используется ли он редким отчётом, и смотрят на размер.

```sql
SELECT indexname, pg_size_pretty(pg_relation_size(indexname::regclass)) AS size
FROM pg_indexes
WHERE tablename = 'students';
```

Удаление лишнего индекса освобождает место и ускоряет запись. Это одна из самых дешёвых оптимизаций, потому что не требует менять код приложения.

## Статистика для планировщика

Индекс помогает только тогда, когда планировщик верит в его пользу. Веру даёт статистика, собранная `ANALYZE` и автоочисткой.

```sql
ANALYZE enrollments;
```

Если данные загрузили массово и не проанализировали, планировщик считает, что строк мало, и выбирает последовательное чтение. Запрос работает медленно, а индекс остаётся нетронутым.

Для столбцов с неравномерным распределением точность повышают настройкой:

```sql
ALTER TABLE students ALTER COLUMN group_id SET STATISTICS 500;
ANALYZE students;
```

`default_statistics_target` по умолчанию равен 100. Большее значение даёт более подробную гистограмму, но увеличивает время анализа и размер каталога.

## Типичные ошибки

- **Индекс на всё.** Десяток индексов ускоряет редкие отчёты и замедляет каждую загрузку. Индексы добавляют под конкретные запросы, а не под столбцы.
- **Неверный порядок столбцов.** Индекс `(enrolled_at, course_id)` не помогает условию только по курсу. Столбцы равенства ставят первыми.
- **Индекс не используется.** Причины разные: функция над столбцом (`lower(email)`), несовпадение типов, `LIKE '%текст'`, `OR` по разным столбцам, устаревшая статистика.
- **Забыли `VACUUM`.** Покрывающий индекс не даёт `Index Only Scan`, пока карта видимости не обновлена.
- **Индекс создан без `CONCURRENTLY`.** `CREATE INDEX` на большой таблице блокирует запись на всё время построения.

> [!PITFALL] Индекс по функции
> `WHERE lower(email) = 'ivanov@mail.ru'` не использует обычный индекс по `email`. Нужен либо индекс по выражению `CREATE INDEX ... ON students (lower(email))`, либо запрос с приведением, которое сохраняет сравнение по столбцу.

## Проверьте себя

> [!CHECK] Запрос фильтрует по `course_id` и сортирует по `enrolled_at`. Какой индекс построить?
> Составной `(course_id, enrolled_at)`. Столбец равенства идёт первым и сужает поиск, второй столбец обеспечивает порядок и избавляет от сортировки.

> [!CHECK] Почему индекс по `grade` почти не ускоряет выборку двоек, хотя двоек мало?
> Если двоек немного, частичный индекс `WHERE grade = 2` будет маленьким и полезным. Полный индекс по `grade` хранит все оценки, а планировщик для условия `grade = 2` может предпочесть чтение таблицы, если статистика покажет большую долю строк.

> [!CHECK] Вставка тысячи строк стала вдвое медленнее после добавления индексов. Что проверить?
> Число индексов на таблице и их использование. Каждый лишний индекс добавляет работу при вставке. Индексы с `idx_scan = 0` удаляют, а массовую загрузку по возможности выполняют до создания индексов.

## Итоги

- Индекс ускоряет чтение и замедляет запись, поэтому строится под запрос.
- B-tree закрывает равенство, диапазоны и сортировку; GIN, GiST и BRIN решают особые задачи.
- В составном индексе сначала идут столбцы равенства, затем диапазон и сортировка.
- Покрывающий индекс экономит чтение таблицы, частичный уменьшает размер.
- Лишние индексы находят по `idx_scan` и удаляют, раздутые перестраивают через `REINDEX CONCURRENTLY`.

- Индекс перестроен

+ Перестроить раздутый или повреждённый индекс

- Удалить неиспользуемый индекс
- Создать слот репликации
! Перестройка возвращает индексу компактность и целостность структуры.

Q: Что происходит при вставке строки в таблицу с несколькими индексами?
+ Обновляется каждый индекс таблицы
- Обновляется только первичный ключ
- Индексы перестраиваются целиком
- Индексы блокируются до конца дня
! Каждый индекс получает новую запись, поэтому их число влияет на скорость записи.

+ GIN
- BRIN
- Hash
- B-tree без изменений
! GIN работает с составными значениями: jsonb, массивами, полнотекстовым поиском.

Q: Что необходимо для Index Only Scan?
+ Обновлённая карта видимости после VACUUM
- Отключённый autovacuum
- Индекс типа hash
- Частичный индекс по всем строкам
! Без карты видимости PostgreSQL не знает, что версия строки видна всем, и идёт в таблицу.

Q: Что ускоряет индекс B-tree?
+ Равенство по столбцу
+ Диапазон значений
+ Сортировку по индексированному столбцу
+ Поиск по префиксу LIKE 'ИС%'
- Поиск по шаблону LIKE '%21'
- Арифметику над столбцом в условии
! B-tree хранит ключи в порядке, поэтому равенство, диапазон, сортировка и префикс используют его.

Q: Когда дополнительный индекс вредит?
+ При частых массовых вставках
+ Когда индексов на таблице уже много
+ Когда столбец имеет низкую селективность
- Когда запросы выполняются редко
- Когда нужна уникальность значений
! Каждый индекс добавляет работу записи и занимает место, а низкая селективность не окупает чтение.

Q: Почему индекс может не использоваться?
+ Условие содержит функцию над столбцом
+ Типы сравниваемых значений не совпадают
+ Статистика устарела после массовой загрузки
+ Таблица мала, и последовательное чтение дешевле
- Индекс создан через CREATE INDEX
- Индекс имеет тип B-tree
! Планировщик не применяет индекс, если условие не совпадает с ключом или стоимость плана выше.

Q: Что относится к обслуживанию индексов?
+ Перестройка раздутых индексов
+ Наблюдение за idx_scan
+ Удаление неиспользуемых индексов
- Ежедневное пересоздание всех индексов
- Отключение autovacuum
! Обслуживание это контроль размера и пользы, а не постоянная перестройка всего.

Q: Какой тип индекса создаётся по умолчанию?
= btree
= b-tree
! По умолчанию PostgreSQL строит B-tree, если тип не указан явно.

Q: Какая команда перестраивает индекс без блокировки записи?
= REINDEX INDEX CONCURRENTLY
= REINDEX CONCURRENTLY
! Ключ CONCURRENTLY позволяет перестроить индекс, не останавливая изменения таблицы.
