## Цель работы

Индекс ускоряет не базу, а конкретный запрос: тот же индекс, полезный для одного условия, остаётся мёртвым грузом для другого. Цель работы: увидеть это на данных, где разница заметна, и научиться принимать решение по плану, а не по привычке.

Вы наполняете `payments` миллионом строк, снимаете планы пяти запросов до индексов, затем строите B-tree, составной, частичный и покрывающий индекс. После каждого шага вы повторяете замер и заполняете таблицу: план, время, прочитанные буферы. Итог: вывод, какой индекс под какой запрос подходит и чем каждый из них стоит для записи.

## Оборудование и программное обеспечение

- Виртуальная машина Ubuntu Server с PostgreSQL 16 и базой `dean`.
- Не менее 2 ГБ свободного места: миллион строк с индексами занимает сотни мегабайт.
- Клиент `psql` с включённым `\timing`.
- Табличный редактор для таблицы замеров.
- Копия базы, снятая в практике 3: объём данных вырастет, и откатить его будет нечем.

## Краткие теоретические сведения

**Полное сканирование** (`Seq Scan`) читает все страницы таблицы, потому что другого способа найти строки нет. Его стоимость растёт линейно с объёмом, зато чтение идёт подряд и не требует спуска по дереву. Для условия, которое отбирает половину таблицы, это часто самый дешёвый план.

**B-tree** хранит ключи в порядке возрастания и находит диапазон за несколько страниц. Индекс годится для равенства, сравнений `>`, `<`, `BETWEEN`, `IN` и для сортировки по индексированному столбцу. Для `LIKE '%текст'` обычный B-tree бесполезен: шаблон с ведущим процентом не задаёт границу поиска.

**Составной индекс** строится по нескольким столбцам, и порядок в нём не случаен. Сначала ставят столбец, по которому проверяют равенство, затем столбец диапазона. Индекс `(student_id, paid_at)` обслуживает запрос с фильтром только по `student_id` и запрос с обоими условиями, а индекс `(paid_at, student_id)` для фильтра только по `student_id` не подходит: поиск в дереве начинается с первого столбца.

**Частичный индекс** содержит только строки, попавшие под условие `WHERE` в его определении. Он меньше полного и обслуживает запросы, условие которых совместимо с этим `WHERE`. Планировщик применит его, только если докажет, что условие запроса не шире условия индекса.

**Покрывающий индекс** содержит все столбцы, которые нужны запросу, через `INCLUDE`. Тогда сервер отвечает по индексу и не обращается к таблице, это `Index Only Scan`. Обращений к таблице не будет, только если карта видимости показывает, что страницы очищены: её обновляет `VACUUM`.

**Статистика** это основа выбора плана. `ANALYZE` собирает распределение значений, и планировщик оценивает, сколько строк вернёт условие. Без свежей статистики оценка врёт, и индекс может остаться неиспользованным даже при правильном определении.

**Цена индекса** платится на записи: каждая вставка, обновление и удаление поддерживает все индексы таблицы. Индекс занимает место и требует обслуживания. Поэтому индекс, у которого `idx_scan` равен нулю, это кандидат на удаление, а не запас на будущее.

## Ход работы

### Шаг 1. Наполните таблицу

Работайте в базе `dean` после того, как копия из практики 3 проверена. Индексы создаёт владелец таблиц, поэтому подключитесь как `postgres` и переключитесь на `dean_owner`.

```bash
sudo -u postgres psql -d dean
```

```sql
SET ROLE dean_owner;
SELECT 'Иванов ИС-41' AS student;
\timing on

INSERT INTO payments (student_id, amount, paid_at)
SELECT 1 + (g % 10),
       (500 + (g % 50) * 100)::numeric(10,2),
       timestamptz '2025-09-01' + make_interval(days => (g % 365)::int)
FROM generate_series(1, 1000000) AS g;
```

Сеанс с `SET ROLE dean_owner` сохраняйте до конца работы: от имени приложения индексы создать нельзя, оно не владелец таблиц.

```sql
SELECT count(*) AS rows_total,
       pg_size_pretty(pg_total_relation_size('payments')) AS total_size
FROM payments;

ANALYZE payments;
```

`generate_series` даёт миллион значений, остаток от деления распределяет строки по десяти студентам и пятидесяти суммам, а дата сдвигается в пределах года. `ANALYZE` обязателен: без него планировщик опирается на старую статистику и оценивает строки неверно.

Сделайте скриншот числа строк и размера таблицы.

### Шаг 2. Снимите планы до индексов

Выполните пять запросов с `EXPLAIN (ANALYZE, BUFFERS)` и сохраните вывод. Перед каждым планом печатайте строку с фамилией и группой. Первый запрос берёт неделю августа, второй группирует её по студентам, третий добавляет условие по студенту, четвёртый отбирает крупные суммы, пятый готовится к покрывающему индексу.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, student_id, amount, paid_at
FROM payments
WHERE paid_at >= '2026-08-01' AND paid_at < '2026-08-08';

EXPLAIN (ANALYZE, BUFFERS)
SELECT student_id, sum(amount) AS total
FROM payments
WHERE paid_at >= '2026-08-01' AND paid_at < '2026-08-08'
GROUP BY student_id
ORDER BY total DESC;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount, paid_at
FROM payments
WHERE student_id = 7
  AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08'
ORDER BY paid_at DESC;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, student_id, amount
FROM payments
WHERE amount > 4000
  AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08';

EXPLAIN (ANALYZE, BUFFERS)
SELECT student_id, paid_at, amount
FROM payments
WHERE student_id = 7
  AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08';
```

До индексов все пять планов опираются на `Seq Scan`. Запишите время выполнения и число прочитанных буферов в таблицу замеров. Скриншот плана первого запроса приложите к отчёту.

### Шаг 3. Постройте B-tree по дате

```sql
CREATE INDEX payments_paid_at_idx ON payments (paid_at);
ANALYZE payments;
```

Повторите первый и второй запросы. В плане появится `Index Scan` или `Bitmap Heap Scan`, число буферов упадёт. Если планировщик всё равно выбрал `Seq Scan`, проверьте диапазон: широкий интервал читать подряд действительно дешевле, и это правильное решение, а не ошибка.

### Шаг 4. Постройте составной индекс

```sql
CREATE INDEX payments_student_paid_idx ON payments (student_id, paid_at DESC);
ANALYZE payments;
```

Повторите третий запрос. Условие равенства по `student_id` стоит первым, диапазон по `paid_at` вторым, поэтому индекс отбирает строки одного студента за нужную неделю. Порядок `DESC` в определении совпадает с `ORDER BY paid_at DESC` и избавляет от отдельной сортировки.

Проверьте обратный порядок столбцов отдельным индексом и сравните планы.

```sql
CREATE INDEX payments_wrong_order_idx ON payments (paid_at, student_id);
ANALYZE payments;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, amount, paid_at
FROM payments
WHERE student_id = 7;

DROP INDEX payments_wrong_order_idx;
```

Для фильтра только по `student_id` индекс `(paid_at, student_id)` не помогает: первый столбец не ограничен, и дерево пришлось бы читать целиком. Удалите его, чтобы не платить за него на записи.

### Шаг 5. Постройте частичный индекс

```sql
CREATE INDEX payments_large_idx ON payments (paid_at) WHERE amount > 4000;
ANALYZE payments;
```

Повторите четвёртый запрос. Частичный индекс меньше полного, потому что хранит только крупные платежи, и подходит запросу, где условие `amount > 4000` присутствует явно. Если убрать это условие из запроса, планировщик частичный индекс не применит.

Сравните размеры индексов.

```sql
SELECT indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE relname = 'payments'
ORDER BY indexrelname;
```

### Шаг 6. Постройте покрывающий индекс

```sql
CREATE INDEX payments_cover_idx
  ON payments (student_id, paid_at) INCLUDE (amount);

VACUUM (ANALYZE) payments;
```

Повторите пятый запрос. В плане должен появиться `Index Only Scan`, а в строке `Heap Fetches` стоять `0`. Если обращений к таблице много, `VACUUM` ещё не успел обновить карту видимости: повторите очистку и замер.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT student_id, paid_at, amount
FROM payments
WHERE student_id = 7
  AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08';
```

Сделайте скриншоты планов до и после для этого запроса и скриншот `\d payments`.

### Шаг 7. Заполните таблицу замеров

Каждый запрос выполните три раза подряд и возьмите медианное время: первый запуск читает данные с диска, следующие попадают в кэш. В таблицу вносите фактические числа вашего стенда, а не ожидания из текста.

| Запрос | План до | Время до, мс | Индекс | План после | Время после, мс | Буферы до и после |
|---|---|---|---|---|---|---|
| Неделя по `paid_at` | `Seq Scan` | | `payments_paid_at_idx` | | | |
| Сумма по студентам | `Seq Scan` | | `payments_paid_at_idx` | | | |
| Студент и неделя | `Seq Scan` | | `payments_student_paid_idx` | | | |
| Крупные суммы | `Seq Scan` | | `payments_large_idx` | | | |
| Покрывающий запрос | `Seq Scan` | | `payments_cover_idx` | | | |

Ниже добавьте строку для запроса с индексом `(paid_at, student_id)`: запишите план, который получили до его удаления, и вывод, почему он не помог.

### Шаг 8. Оцените цену индексов

```sql
SELECT pg_size_pretty(pg_relation_size('payments')) AS table_size,
       pg_size_pretty(pg_indexes_size('payments')) AS indexes_size;

SELECT indexrelname, idx_scan, idx_tup_read
FROM pg_stat_user_indexes
WHERE relname = 'payments'
ORDER BY indexrelname;

\d payments
```

Сделайте скриншот `\di+ payments` и времени выполнения запроса из шага 6. Индекс с нулевым `idx_scan` после всех замеров, это кандидат на удаление: он занимает место и замедляет вставку, но не участвует ни в одном плане.

### Требования к отчёту

Отчёт содержит SQL-скрипт наполнения и всех индексов, таблицу замеров с планами и временем, скриншоты планов до и после, `\d payments`, `\di+` и вывода времени. В выводе ответьте, какой индекс вы оставили бы для каждого из пяти запросов, от какого отказались и почему, и как изменится скорость вставки при пяти индексах вместо одного.

## Что сдать

- SQL-скрипт наполнения таблицы и создания индексов.
- Таблицу замеров: план, время и буферы до и после для каждого запроса.
- Скриншоты `EXPLAIN (ANALYZE, BUFFERS)` до и после, `\d payments`, `\di+`.
- Вывод о выборе индексов и их цене для записи.
- Файл отчёта с титульной шапкой и данными студента.
