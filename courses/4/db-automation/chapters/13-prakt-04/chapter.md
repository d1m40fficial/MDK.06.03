## Цель работы

Индекс ускоряет не базу, а конкретный запрос: тот же индекс, полезный для одного условия, остаётся мёртвым грузом для другого. Цель работы: увидеть это на данных, где разница заметна, и принять решение по плану, а не по привычке.

Вы наполняете `payments` миллионом строк, снимаете планы пяти запросов до индексов, затем строите B-tree, составной и покрывающий индекс. После каждого шага повторяете план и замер и заполняете таблицу. Итог: вывод, какой индекс под какой запрос подходит и чем каждый из них стоит для записи.

## Оборудование и программное обеспечение

- Табличный редактор для таблицы замеров.

## Краткие теоретические сведения

**Полное сканирование** в `EXPLAIN` помечено `type=ALL`: сервер читает все страницы таблицы, потому что другого способа найти строки нет. Стоимость растёт линейно с объёмом, зато чтение идёт подряд. Для условия, которое отбирает половину таблицы, это часто самый дешёвый план.

**B-tree** хранит ключи в порядке возрастания и находит диапазон за несколько страниц. Индекс годится для равенства, сравнений `>`, `<`, `BETWEEN`, `IN` и для сортировки по индексированному столбцу. Для `LIKE '%текст'` он бесполезен: шаблон с ведущим процентом не задаёт границу поиска.

**Составной индекс** строится по нескольким столбцам, и порядок в нём не случаен. Сначала ставят столбец равенства, затем столбец диапазона. Индекс `(student_id, paid_at)` обслуживает запрос с фильтром только по `student_id` и запрос с обоими условиями, а `(paid_at, student_id)` для фильтра только по `student_id` не подходит: поиск в дереве начинается с первого столбца. Это правило левого префикса.

**Покрывающий индекс** содержит все столбцы, которые нужны запросу. В MySQL нет ключевого слова `INCLUDE`, нужные столбцы добавляют в конец ключа: `(student_id, paid_at, amount)`. Тогда в `Extra` появляется `Using index`, и сервер отвечает по индексу, не обращаясь к таблице.

**Статистика** это основа выбора плана. `ANALYZE TABLE` собирает распределение значений, и планировщик оценивает, сколько строк вернёт условие. Без свежей статистики оценка врёт, и индекс может остаться неиспользованным даже при правильном определении. `SHOW INDEX` показывает кардинальность: сколько разных значений сервер видит в столбце.

**Цена индекса** платится на записи: каждая вставка и удаление поддерживают все индексы таблицы. Индекс занимает место и требует обслуживания. Индекс, который не участвует ни в одном плане, это кандидат на удаление, а не запас на будущее.

## Ход работы

### Шаг 1. Наполните таблицу

Индексы создаёт администратор: у `dean_app` нет права `ALTER`. Подключитесь под `root` к базе `dean`.

```powershell
& "C:\xampp\mysql\bin\mysql.exe" -u root dean
```

```sql
SELECT 'Иванов ИС-41' AS student;
```

Наполнение идёт циклом по 1000 строк: рекурсивный CTE даёт номера, `WHILE` повторяет порцию.

```sql
DROP PROCEDURE IF EXISTS fill_payments;
DELIMITER $$
CREATE PROCEDURE fill_payments(IN rows_total INT)
BEGIN
  DECLARE done INT DEFAULT 0;
  WHILE done < rows_total DO
    INSERT INTO payments (student_id, amount, paid_at)
    WITH RECURSIVE seq (n) AS (
      SELECT 1
      UNION ALL
      SELECT n + 1 FROM seq WHERE n < 1000
    )
    SELECT 1 + ((done + n) % 10),
           500 + ((done + n) % 50) * 100,
           TIMESTAMP('2025-09-01') + INTERVAL ((done + n) % 365) DAY
    FROM seq;
    SET done = done + 1000;
  END WHILE;
END$$
DELIMITER ;

CALL fill_payments(1000000);
```

Глубина рекурсии 1000 выбрана не случайно: в MySQL это предел по умолчанию (`cte_max_recursion_depth`), в MariaDB ограничение задаёт `max_recursive_iterations`. Порция в 1000 строк не упирается ни в то, ни в другое.

```sql
SELECT COUNT(*) AS rows_total FROM payments;
ANALYZE TABLE payments;
```

Сделайте скриншот числа строк.

### Шаг 2. Снимите планы и время до индексов

Клиент `mysql` печатает время после каждой команды, поэтому отдельный таймер не нужен. Сначала планы.

```sql
EXPLAIN SELECT id, student_id, amount, paid_at
FROM payments
WHERE paid_at >= '2026-08-01' AND paid_at < '2026-08-08';

EXPLAIN SELECT student_id, SUM(amount) AS total
FROM payments
WHERE paid_at >= '2026-08-01' AND paid_at < '2026-08-08'
GROUP BY student_id
ORDER BY total DESC;

EXPLAIN SELECT id, amount, paid_at
FROM payments
WHERE student_id = 7
  AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08'
ORDER BY paid_at DESC;

EXPLAIN SELECT id, student_id, amount
FROM payments
WHERE amount > 4000
  AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08';

EXPLAIN SELECT student_id, paid_at, amount
FROM payments
WHERE student_id = 7
  AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08';
```

Теперь те же пять запросов без `EXPLAIN` и замер вставки.

```sql
SELECT id, student_id, amount, paid_at FROM payments
WHERE paid_at >= '2026-08-01' AND paid_at < '2026-08-08';

SELECT student_id, SUM(amount) AS total FROM payments
WHERE paid_at >= '2026-08-01' AND paid_at < '2026-08-08'
GROUP BY student_id ORDER BY total DESC;

SELECT id, amount, paid_at FROM payments
WHERE student_id = 7 AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08'
ORDER BY paid_at DESC;

SELECT id, student_id, amount FROM payments
WHERE amount > 4000 AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08';

SELECT student_id, paid_at, amount FROM payments
WHERE student_id = 7 AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08';

INSERT INTO payments (student_id, amount, paid_at) VALUES (3, 1500.00, NOW());
```

До индексов все пять планов опираются на `type=ALL`. Запишите время и число строк из `rows` в таблицу замеров, отдельно сохраните время вставки. Скриншот плана первого запроса приложите к отчёту.

### Шаг 3. Постройте B-tree по дате

```sql
CREATE INDEX payments_paid_at_idx ON payments (paid_at);
ANALYZE TABLE payments;
```

Повторите первый и второй запросы. В плане появится `type=range` и `key=payments_paid_at_idx`, время упадёт. Если планировщик всё равно выбрал `ALL`, проверьте диапазон: широкий интервал читать подряд действительно дешевле, и это правильное решение, а не ошибка.

### Шаг 4. Постройте составной индекс

```sql
CREATE INDEX payments_student_paid_idx ON payments (student_id, paid_at);
ANALYZE TABLE payments;
```

Повторите третий запрос. Условие равенства по `student_id` стоит первым, диапазон по `paid_at` вторым, поэтому индекс отбирает строки одного студента за нужную неделю. Проверьте обратный порядок столбцов отдельным индексом.

```sql
CREATE INDEX payments_wrong_order_idx ON payments (paid_at, student_id);
ANALYZE TABLE payments;

EXPLAIN SELECT id, amount, paid_at FROM payments WHERE student_id = 7;

DROP INDEX payments_wrong_order_idx ON payments;
```

Для фильтра только по `student_id` индекс `(paid_at, student_id)` не помогает: первый столбец не ограничен. План покажет либо `ALL`, либо `type=index`, то есть чтение всего индекса. Удалите его, чтобы не платить за него на записи.

### Шаг 5. Постройте покрывающий индекс

```sql
CREATE INDEX payments_cover_idx ON payments (student_id, paid_at, amount);
ANALYZE TABLE payments;

EXPLAIN SELECT student_id, paid_at, amount
FROM payments
WHERE student_id = 7
  AND paid_at >= '2026-08-01' AND paid_at < '2026-08-08';
```

В строке `Extra` должно появиться `Using index`: сервер отвечает по индексу и не читает строки таблицы. Столбец `id` в индекс добавлять не нужно, InnoDB и так хранит первичный ключ в каждом вторичном индексе.

Сделайте скриншоты планов до и после для этого запроса.

### Шаг 6. Проверьте индексы и размеры

```sql
SHOW INDEX FROM payments;

SELECT table_name,
       ROUND(data_length / 1024 / 1024, 1) AS data_mb,
       ROUND(index_length / 1024 / 1024, 1) AS index_mb
FROM information_schema.tables
WHERE table_schema = 'dean' AND table_name = 'payments';
```

`SHOW INDEX` показывает кардинальность и порядок столбцов в каждом индексе. Сделайте скриншот вывода: по нему видно, что индексов стало больше, чем запросов.

### Шаг 7. Заполните таблицу замеров

Каждый запрос выполните три раза подряд и возьмите медианное время: первый запуск читает данные с диска, следующие попадают в кэш. Вносите фактические числа своего стенда, а не ожидания из текста.

| Запрос | План до | Время до, с | Индекс | План после | Время после, с |
|---|---|---|---|---|---|
| Неделя по `paid_at` | `ALL` | | `payments_paid_at_idx` | | |
| Сумма по студентам | `ALL` | | `payments_paid_at_idx` | | |
| Студент и неделя | `ALL` | | `payments_student_paid_idx` | | |
| Крупные суммы | `ALL` | | `payments_paid_at_idx` | | |
| Покрывающий запрос | `ALL` | | `payments_cover_idx` | | |

Ниже добавьте строку для индекса `(paid_at, student_id)`: запишите план, который получили до его удаления, и вывод, почему он не помог.

### Шаг 8. Оцените цену записи

Повторите ту же вставку, что в шаге 2, и сравните время.

```sql
INSERT INTO payments (student_id, amount, paid_at) VALUES (3, 1500.00, NOW());
```

Пока индексов не было, вставка обновляла только таблицу. Теперь она обновляет таблицу и три индекса, поэтому время растёт. Сделайте скриншот обоих замеров: времени вставки до индексов и после.

### Шаг 9. Сформулируйте вывод

Для каждого из пяти запросов назовите индекс, который его обслуживает, и план, который получился. Отдельно ответьте, какой индекс дублирует другой: `payments_cover_idx` начинается с тех же столбцов, что `payments_student_paid_idx`, и после его создания второй индекс можно удалить. Посчитайте, сколько индексов осталось бы у вас в рабочей базе и почему.

### Требования к отчёту

Отчёт содержит SQL-скрипт наполнения и всех индексов, таблицу замеров с планами и временем, скриншоты планов до и после, `SHOW INDEX` и времени вставки. В выводе объясните, почему индекс `(paid_at, student_id)` не помог, от какого индекса вы отказались и как изменится скорость вставки при трёх индексах вместо одного. Скриншоты шапки отчёта и текста теории не нужны.
