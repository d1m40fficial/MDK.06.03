## Одна идея

Студент поставил PostgreSQL, подключился с хоста, всё работает. Через неделю он меняет `shared_buffers`, перезапускает сервер и получает отказ в подключении. Потом правит `pg_hba.conf`, но ничего не меняется. Потом выясняется, что он редактировал файл в каталоге данных, а сервер читает совсем другой.

**Настройка PostgreSQL это не список команд, а последовательность проверяемых решений.** Каждый параметр отвечает на конкретный вопрос: где слушать, сколько памяти дать, как проверять пароль, кого пускать. После каждого изменения есть способ убедиться, что сервер его принял.

В этой лекции мы пройдём путь от установки пакетов до проверки параметров в работающем сервере и разберём, почему одна и та же правка иногда требует перезапуска, а иногда достаточно перечитать файл.

## Установка и кластер

В Ubuntu Server PostgreSQL ставится из штатного репозитория. Отдельный установщик не нужен, права администратора Windows тоже: всё происходит внутри виртуальной машины.

```bash
sudo apt update
sudo apt install postgresql postgresql-contrib
```

Пакет `postgresql` ставит сервер и создаёт кластер, пакет `postgresql-contrib` добавляет полезные расширения и утилиты. Версия зависит от выпуска Ubuntu: в 24.04 это PostgreSQL 16.

**Кластер** в терминах Debian и Ubuntu это не «несколько серверов», а один каталог данных вместе с файлами настроек и портом. На одной машине может быть несколько кластеров: например, версия 16 на порту 5432 и версия 15 на порту 5433. Список кластеров показывает утилита `pg_lsclusters`:

```bash
pg_lsclusters
```

Она выводит версию, имя кластера, порт, состояние, владельца, каталог данных и файл журнала. Типичная строка выглядит так: версия 16, кластер `main`, порт 5432, состояние `online`, владелец `postgres`, каталог `/var/lib/postgresql/16/main`.

Управлять кластером можно двумя способами. Через systemd: `systemctl status postgresql@16-main`. Или через обёртку `pg_ctlcluster 16 main restart`. Оба способа делают одно и то же, но `pg_ctlcluster` удобнее, когда кластеров несколько.

## postgresql.conf

Основной файл настроек в Ubuntu лежит отдельно от данных: `/etc/postgresql/16/main/postgresql.conf`. Каталог данных находится в `/var/lib/postgresql/16/main`, и файла настроек там может не быть вовсе. Это первая ловушка: правка файла в каталоге данных ни на что не влияет.

Файл большой, но для начала достаточно шести параметров.

**`listen_addresses`** задаёт интерфейсы, на которых сервер ждёт подключения. Значение `'localhost'` означает только петлевой адрес, то есть подключения с самой машины. Значение `'*'` означает все интерфейсы.

**`port`** задаёт номер порта, по умолчанию 5432.

**`shared_buffers`** задаёт размер кэша страниц в разделяемой памяти. По умолчанию 128 мегабайт. Разумная отправная точка это четверть оперативной памяти машины, но для учебной VM с двумя гигабайтами не стоит выходить за 512 мегабайт.

**`work_mem`** ограничивает память одной операции сортировки или соединения. По умолчанию 4 мегабайта. Увеличение помогает тяжёлым запросам, но умножается на число одновременных операций.

**`maintenance_work_mem`** задаёт память для обслуживания: `VACUUM`, `CREATE INDEX`, `ALTER TABLE`. По умолчанию 64 мегабайта.

**`wal_level`** определяет, сколько информации попадает в журнал. По умолчанию `replica`, и этого достаточно для архивации и репликации. Значение `minimal` уменьшает журнал, но лишает возможности восстанавливаться на момент времени.

**`max_connections`** задаёт предел одновременных соединений, по умолчанию 100.

Значения с единицами измерения пишут явно: `512MB`, `16MB`, `1GB`. PostgreSQL понимает и `mb`, и `MB`, но лучше придерживаться одного стиля.

## pg_hba.conf

Файл `pg_hba.conf` отвечает на вопрос «кому можно». Он лежит рядом с `postgresql.conf` и читается сверху вниз, причём срабатывает первое подходящее правило. Порядок строк важнее их количества.

```
# TYPE  DATABASE  USER  ADDRESS       METHOD
local   all       all                 peer
host    all       all   127.0.0.1/32  scram-sha-256
host    all       all   ::1/128       scram-sha-256
```

Строка `local` относится к Unix-сокету, строка `host` к TCP. Метод `peer` доверяет имени операционной системы: пользователь `postgres` в Linux может войти как роль `postgres` без пароля. Метод `scram-sha-256` требует пароль и современную схему его проверки.

Пароль должен быть сохранён именно в формате SCRAM. С версии 14 параметр `password_encryption` по умолчанию равен `scram-sha-256`, поэтому достаточно задать пароль заново:

```sql
alter role dean_app with login password 'uchebnyi-parol';
```

Если роль создана давно и пароль хранится в старом формате, смена пароля перезапишет хеш. Проверить формат можно по префиксу `SCRAM-SHA-256$` в системном каталоге, но читать его может только суперпользователь.

Для учебной VM с пробросом порта соединение с хоста приходит в гостевую систему с адресом шлюза NAT, обычно `10.0.2.2`. Поэтому одного правила для `127.0.0.1` мало: нужно добавить строку для этого адреса. Если в журнале появилось сообщение об отказе, в нём обычно указан настоящий адрес клиента, и правило правят по факту, а не по догадке.

## Перезагрузка, перечитывание и журнал

Не всякое изменение требует перезапуска. Параметры делятся на группы по способу применения.

| Параметр | Как применяется |
|---|---|
| `shared_buffers` | перезапуск кластера |
| `port`, `listen_addresses` | перезапуск кластера |
| `max_connections`, `wal_level` | перезапуск кластера |
| `work_mem`, `maintenance_work_mem` | перечитывание файла |
| `pg_hba.conf` | перечитывание файла |
| `log_min_duration_statement` | перечитывание файла |

Перечитывание делается командой `select pg_reload_conf();` или через `pg_ctlcluster 16 main reload`. Перезапуск: `sudo systemctl restart postgresql` или `pg_ctlcluster 16 main restart`.

Журнал сервера в Ubuntu лежит в `/var/log/postgresql/postgresql-16-main.log`. Туда попадают запуск, остановка, ошибки подключения и медленные запросы, если включён `log_min_duration_statement`. Читать журнал нужно после каждой правки: именно там видно, принял ли сервер настройку и почему отказал клиенту.

```bash
sudo tail -n 50 /var/log/postgresql/postgresql-16-main.log
sudo systemctl restart postgresql
pg_isready -h 127.0.0.1 -p 5432
```

## Проброс порта в VirtualBox

Чтобы подключаться к базе с хоста, в настройках виртуальной машины включают проброс порта. В VirtualBox это раздел «Сеть», адаптер NAT, «Дополнительно», «Проброс портов». Правило выглядит так: протокол TCP, адрес хоста `127.0.0.1`, порт хоста 5432, адрес гостя можно оставить пустым, порт гостя 5432.

Адрес хоста `127.0.0.1` важен. Если указать `0.0.0.0`, база станет доступна всей локальной сети, а это уже другая история безопасности.

Внутри гостя сервер тоже должен слушать не только петлевой адрес, иначе проброшенное соединение не дойдёт. Поэтому `listen_addresses` расширяют до адреса NAT-интерфейса или до `'*'`, а доступ ограничивают правилом `pg_hba.conf` для конкретного адреса. Открыть порт и разрешить вход кому угодно это две разные ошибки, и делать их вместе нельзя.

## Проверка после изменения

Проверка это часть настройки, а не отдельный этап. Есть три надёжных способа увидеть, что сервер принял параметр.

Первый: `pg_isready` проверяет, принимает ли сервер соединения. Код возврата 0 значит «принимает», 1 значит «отклоняет», 2 значит «не отвечает».

Второй: `SHOW` показывает действующее значение в текущем сеансе. `SHOW shared_buffers;` вернёт `512MB`, если параметр применился. Полный список доступен в представлении `pg_settings`, где есть и значение по умолчанию, и источник.

Третий: тестовое подключение от той роли, для которой настраивали доступ. Проверять нужно именно ей, а не суперпользователем: суперпользователь проходит там, где обычная роль получает отказ.

```sql
show listen_addresses;
show shared_buffers;
select name, setting, source from pg_settings where name = 'work_mem';
```

## Что не стоит менять без понимания

Некоторые параметры ускоряют работу ценой сохранности. Их изменение допустимо на стенде и недопустимо на рабочей базе.

- **`fsync = off`.** Ускоряет запись, но подтверждённый `COMMIT` может исчезнуть после сбоя питания. База перестаёт быть надёжной.
- **`full_page_writes = off`.** Экономит журнал, но повреждённая страница после сбоя может остаться повреждённой.
- **`autovacuum = off`.** Отключает очистку мёртвых строк. Таблицы раздуваются, а счётчик транзакций приближается к переполнению.
- **`wal_level = minimal`** при включённой архивации. Архив перестаёт работать, и восстановление на момент времени становится невозможным.
- **`max_connections` в тысячу.** Каждый backend это процесс, память и переключения контекста. Часто проблему решает пул соединений, а не новый предел.

Есть и менее очевидные вещи. `shared_buffers` больше оперативной памяти не ускорит ничего, а `work_mem` в гигабайт при сотне соединений уведёт сервер в своп. Настройка это компромисс между памятью, диском и нагрузкой, а не поиск максимального значения.

## Типичные ошибки

**Правка не того файла.** Студент находит `postgresql.conf` в каталоге данных, меняет его и перезапускает сервер. Симптом: `SHOW` показывает старое значение. Лечение: смотреть путь в `pg_lsclusters` и помнить, что в Ubuntu настройки лежат в `/etc/postgresql/16/main`.

**Забыли перечитать `pg_hba.conf`.** Правило добавлено, сервер работает, но клиент по-прежнему получает отказ. Симптом: в журнале старое сообщение, а в файле новая строка. Лечение: `select pg_reload_conf();` и повторная проверка.

**Перезапуск вместо перечитывания.** Правка `work_mem` сопровождается полным перезапуском, хотя достаточно перечитать файл. Это лишний простой. И наоборот: `shared_buffers` меняют с расчётом на перечитывание и удивляются, что значение не изменилось.

**Порт открыт всем.** `listen_addresses = '*'` и правило `host all all 0.0.0.0/0 trust` ставят на учебной VM «чтобы работало». Симптом: база доступна любому в сети без пароля. Лечение: узкий адрес и `scram-sha-256`, а `trust` только на одноразовом стенде.

**Пароль задан до смены схемы шифрования.** Роль создана, когда `password_encryption` ещё был `md5`, и после перехода на SCRAM вход не работает. Лечение: задать пароль заново после смены параметра.

## Проверьте себя

> [!CHECK] Вы поменяли `shared_buffers` и выполнили `select pg_reload_conf();`. Значение в `SHOW` не изменилось. Почему?
> `shared_buffers` относится к параметрам, которые применяются только при запуске сервера. Перечитывание файла их не меняет, нужен перезапуск кластера.

> [!CHECK] Клиент с хоста получает «no pg_hba.conf entry». Сервер слушает порт и отвечает на `pg_isready`. Что проверять?
> Правило для адреса, с которого приходит соединение. При пробросе порта это адрес шлюза NAT, а не `127.0.0.1`. Нужно добавить строку `host` для этого адреса и перечитать файл.

> [!CHECK] Почему проверять доступ нужно от имени обычной роли, а не `postgres`?
> Суперпользователь обходит многие ограничения и проходит там, где приложение получит отказ. Проверка от его имени ничего не говорит о реальных правах `dean_app`.

## Итог

- Установка в Ubuntu создаёт кластер `main`; список кластеров показывает `pg_lsclusters`.
- Настройки лежат в `/etc/postgresql/16/main`, данные в `/var/lib/postgresql/16/main`.
- `postgresql.conf` задаёт сеть, память и журнал, `pg_hba.conf` задаёт правила доступа.
- Часть параметров требует перезапуска, часть достаточно перечитать.
- Проверка после правки это `pg_isready`, `SHOW` и тестовое подключение нужной ролью.

Q: Что проверить, если подключение с хоста не работает?
+ Слушает ли сервер нужный адрес
+ Есть ли подходящее правило в pg_hba.conf
+ Настроен ли проброс порта в VirtualBox
+ Запущена ли служба PostgreSQL
- Выбрана ли тёмная тема сайта
! Отказ возникает на одном из четырёх шагов пути подключения.

Q: Какие настройки опасны на рабочей базе?
+ fsync = off
+ autovacuum = off
+ wal_level = minimal при включённой архивации
- log_min_duration_statement = 500
- work_mem = 8MB
! Эти значения ускоряют работу ценой сохранности или ломают обслуживание.

Q: Что показывает pg_lsclusters?
+ Версию PostgreSQL
+ Порт кластера
+ Состояние кластера
+ Каталог данных
- Список таблиц учебной базы
! Утилита описывает кластеры, а не содержимое баз.

Q: Какой файл задаёт правила доступа клиентов к серверу?
= pg_hba.conf
! Именно pg_hba.conf решает, кому и с какого адреса разрешено подключение.

Q: Какой параметр задаёт предельное число одновременных соединений?
= max_connections
! max_connections ограничивает число backend-процессов.

Q: Как называется утилита проверки готовности сервера принимать соединения?
= pg_isready
! pg_isready проверяет доступность сервера и возвращает код состояния.
