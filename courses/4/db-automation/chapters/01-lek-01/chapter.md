## Одна идея

Понедельник, восемь сорок, деканат. Секретарь открывает ведомость, приложение отвечает ошибкой, а в журнале MySQL появляется строка о недоступной базе. В пятницу кто-то поправил оценки прямо в phpMyAdmin, в субботу на диск с данными записали учебные видео, а копия делалась один раз перед началом семестра и ни разу не восстанавливалась. Формально сервер работал все выходные. Фактически базу никто не администрировал.

**Администрирование базы это ответственность за три вещи: кто имеет доступ, целы ли данные и успевает ли база отвечать.** В MySQL это учётные записи и привилегии, резервные копии и журналы, буферный пул и индексы. Автоматизация выполняет повторяющийся шаг быстрее и с одинаковым результатом, но решение о том, какой шаг и когда запускать, остаётся за человеком.

## Чем администратор отличается от разработчика

Разработчик меняет поведение системы: добавляет таблицы, пишет запросы, собирает приложение на C#. Администратор отвечает за состояние сервера: чтобы приложение могло подключиться, данные пережили сбой, а запрос уложился в разумное время.

| Вопрос | Разработчик | Администратор |
|---|---|---|
| Что меняет | код и схему под задачу | состояние сервера и данные |
| Критерий успеха | функция работает | данные доступны и целы |
| Инструмент | Visual Studio 2022, миграции | phpMyAdmin, mysql, mysqldump |
| Цена ошибки | неверный результат | потеря данных или доступа |

Граница проходит не по командам, а по последствиям. Разработчик пишет `ALTER TABLE students ADD COLUMN phone VARCHAR(20)`. Администратор спрашивает, сколько времени таблица будет заблокирована, есть ли копия, что делать при откате, хватит ли места на диске. Синтаксис один и тот же, но за простой и целостность отвечает администратор.

В небольшой организации обе роли совмещает один человек. Разница не исчезает: пока он пишет код, он оптимизирует доставку функции, а когда проверяет копию, он оптимизирует выживание данных.

1. **Проект.** Определяют данные и ограничения деканата: группы, студенты, курсы, записи, платежи. Внешний ключ, добавленный позже, придётся заполнять вручную.

3. **Ввод в работу.** Создают базу `dean` в `utf8mb4`, таблицы, пользователя приложения, копирование и наблюдение.

6. **Вывод.** База работает только на чтение, затем последняя копия, архив и удаление.

## Регламентные операции MySQL

Регламент это список операций, у каждой из которых есть период, команда, проверка результата и ответственный. Без проверки регламент превращается в ритуал: скрипт запускается, файл появляется, а восстанавливать из него нечего.

| Операция | Команда | Период | Что проверяем |
|---|---|---|---|
| Логический дамп | `mysqldump` | ежедневно | файл восстанавливается в тестовую базу |
| Статистика индексов | `ANALYZE TABLE` | после массовой загрузки | `EXPLAIN` видит новые оценки |
| Пересборка таблицы | `OPTIMIZE TABLE` | после удаления большой доли строк | размер файла и `CHECK TABLE` |
| Проверка целостности | `mysqlcheck` | еженедельно | статус `OK` у всех таблиц |
| Журналы | error log, slow log | постоянно | ошибки и долгие запросы |
| Метрики | `SHOW STATUS` | каждые несколько минут | соединения, диск, блокировки |

Копия это не файл, а проверенная процедура. Команды для учебной базы выглядят так:

```bash
"mysqldump" -u dean_backup -p --single-transaction --routines --triggers --default-character-set=utf8mb4 --result-file=backup/dean.sql dean
"mysql" -u root -e "ANALYZE TABLE dean.students, dean.enrollments;"
"mysqlcheck" -u root --check dean
```

`ANALYZE TABLE` пересчитывает распределение значений в индексах. На эту статистику опирается оптимизатор, когда выбирает порядок соединения таблиц. Если после загрузки десяти тысяч студентов статистика устарела, `EXPLAIN` может показать сканирование всей таблицы вместо поиска по индексу. Операция дешёвая, её запускают после каждой крупной загрузки.

`OPTIMIZE TABLE` в InnoDB пересобирает таблицу и возвращает освободившееся место файловой системе. Операция тяжёлая: она переписывает все страницы, требует свободного места примерно на размер таблицы и на время пересборки ограничивает запись. Её применяют после удаления большой доли строк, а не ежедневно «для порядка».

Журналы отвечают на вопрос, что случилось, когда приложение уже не отвечает. В XAMPP журнал ошибок лежит в `.../xampp/mysql/data\mysql_error.log`. Журнал медленных запросов включается переменными `slow_query_log` и `long_query_time`. Двоичный журнал хранит изменения данных и нужен для восстановления на момент сбоя; его включают в `my.ini` строками `log-bin=mysql-bin` и `server-id=1`.

## Что автоматизировать

Автоматизация переносит риск, а не убирает его. Скрипт, который каждую ночь делает дамп и не смотрит на код возврата, может месяц создавать пустые файлы, а отчёт об успешной копии уже отправлен.

Операцию стоит автоматизировать, если она проходит четыре проверки:

- **Повторяется.** Шаг выполняется по расписанию или после каждого события.
- **Детерминирована.** При одинаковых входных данных получается одинаковый результат.
- **Проверяема.** Успех подтверждается запросом, размером файла или кодом возврата.
- **Безопасна.** Ошибка не уничтожает данные мгновенно, либо перед опасным шагом стоит копия.

Под эти критерии попадают дамп, восстановление в отдельную базу, `ANALYZE TABLE`, ротация журналов, сбор метрик и сверка числа строк. Не попадают операции, где неверный параметр необратим: `DROP DATABASE`, восстановление поверх рабочей базы, изменение схемы на живой базе, выдача прав. Их можно готовить скриптом, но запускать должен человек, который видит контекст.

Простейший каркас автоматизации на C# выглядит так:

```csharp
using System.Diagnostics;

var dump = "mysqldump";
var cnf = Environment.GetEnvironmentVariable("DEAN_DB_CNF") ?? @".../backup/dean.cnf";
var args = $"--defaults-extra-file={cnf} --single-transaction --routines " +
           "--triggers --default-character-set=utf8mb4 --result-file=.../backup/dean.sql dean";
var p = Process.Start(new ProcessStartInfo(dump, args) { UseShellExecute = false });
if (p is null) return;
p.WaitForExit();
if (p.ExitCode != 0) Environment.Exit(p.ExitCode);
```

Пароль не передают аргументом: его видно в списке процессов и в истории команд. Для этого у `mysqldump` есть файл параметров, который подключают через `--defaults-extra-file`. Приложение берёт путь к нему из переменной `DEAN_DB_CNF`, а сам файл лежит вне репозитория. В файле `dean.cnf` в секции `[client]` указаны пользователь и пароль.

## Инструменты учебного стенда

| Инструмент | Для чего | Ограничение |
|---|---|---|
| XAMPP Control Panel | запуск MySQL и Apache, порт, журнал, `my.ini` | не умеет расписание |
| phpMyAdmin | просмотр таблиц, SQL, экспорт, пользователи | ручная работа, не для регламента |
| mysql CLI | точный вывод, скрипты, коды возврата | требует знания синтаксиса |
| Visual Studio 2022 | проект C#, отладка, WinForms | не заменяет CLI при аварии |

XAMPP Control Panel запускает сервер и показывает, занят ли порт 3306. phpMyAdmin удобен, когда нужно посмотреть таблицу или выполнить одну команду. Консольный клиент `mysql` даёт тот же результат, но его вывод можно сохранить в файл и сравнить, а код возврата использовать в скрипте. Visual Studio 2022 и .NET SDK 10 нужны для приложения обслуживания: одно и то же решение собирают в графической среде или командами в терминале.

```powershell
dotnet --list-sdks
& "mysql" --version
& "mysql" -u root -e "SELECT VERSION(), @@character_set_server;"
```

Сервер в сборке XAMPP собран на MariaDB и совместим с MySQL 8 по основным командам дисциплины. Версия в выводе будет выглядеть как `10.4.x-MariaDB`, и это нормально: `CREATE USER`, `GRANT`, `mysqldump` и `binary log` работают так же.

Дамп сделан в 02:00, сбой произошёл в 14:20. Без двоичного журнала восстановление вернёт базу к 02:00, и деканат потеряет 12 часов 20 минут работы. С журналом база восстанавливается из дампа, а затем журнал проигрывается до 14:19: потеря около одной минуты.

RTO считается по всей процедуре. Восстановление дампа заняло 12 минут, проигрывание журнала 4 минуты, проверка counts и связей 10 минут. Итого 26 минут, и это укладывается в требование вернуть деканат за час. Если бы проверка не была отрепетирована, двадцать шесть минут превратились бы в неопределённость.

| Вариант копирования | RPO | RTO | Где годится |
|---|---|---|---|
| Дамп раз в сутки без журнала | до 24 часов | часы | учебная база |
| Дамп раз в сутки плюс binary log | минуты | десятки минут | рабочая база деканата |
| Реплика плюс binary log | секунды | минуты | система без простоя |

## Типичные ошибки

**root без пароля.** В XAMPP учётная запись `root` создаётся без пароля. Для учебного компьютера это удобно, но приложение, которое подключается как `root`, получает право удалить любую базу. Ошибка в коде или SQL-инъекция в таком приложении означает полный контроль над сервером. Рабочая настройка начинается с отдельного пользователя `dean_app` и пароля.

**Ручные правки в phpMyAdmin.** `UPDATE students SET group_id = 3;` без условия `WHERE` меняет всех студентов. Подтверждение проходит одним нажатием, транзакция не открывается, аудита нет. Если правка нужна, её оформляют скриптом с условием, проверкой `SELECT` до и после и записью в журнал.

**Копии без проверки.** Файл существует, весит два мегабайта и открывается в блокноте. Это не значит, что из него можно восстановить базу: дамп мог оборваться, кодировка могла не совпасть. Копия считается сделанной только после восстановления в отдельную базу и сверки числа строк.

**Копия на том же диске.** Диск с данными и диск с копиями не должны отказывать одновременно. Папка `.../backup` лежит на другом носителе или в облачном хранилище, а не рядом с `.../xampp/mysql/data`.

**Нет двоичного журнала.** Без него нельзя восстановить базу на момент сбоя, только на момент последнего дампа. Журнал включают заранее, задним числом он не появляется.

> [!PITFALL] Успешный запуск не равен успешной копии
> Скрипт вернул код 0, файл создан, отчёт отправлен. Через месяц выясняется, что в дампе нет таблицы `payments`, потому что у `dean_backup` не было на неё прав. Проверка восстанавливает копию в `dean_restore` и сравнивает counts по всем таблицам.

## Проверьте себя

> [!CHECK] Приложение работает, запросы идут, ошибок нет. База введена в эксплуатацию?
> Нет. Пока нет проверенной копии и наблюдения, первый сбой диска или ошибочный `DELETE` окажется необратимым.

> [!CHECK] Почему `OPTIMIZE TABLE` не ставят в ежедневный регламент?
> Операция пересобирает таблицу целиком, требует свободного места и ограничивает запись. Её применяют после удаления большой доли строк, когда нужно вернуть место.

> [!CHECK] Дамп делается каждые 15 минут, RTO равно часу. Этого достаточно?
> Нет. Частота дампа задаёт только RPO. RTO зависит от времени восстановления, и его нужно измерить на проверке.

## Итоги

- Администратор отвечает за доступ, сохранность и скорость данных, разработчик за поведение приложения.
- Регламент MySQL включает дампы, статистику, проверку таблиц, журналы и метрики, и у каждого шага есть проверка.
- Автоматизируют повторяемые, детерминированные, проверяемые и безопасные операции.
- RPO задаёт допустимую потерю данных, RTO задаёт время восстановления, оба числа проверяются на практике.

- Написание бизнес-логики на C#
- Вёрстка отчёта в WinForms
! Администратор отвечает за доступ, сохранность и работоспособность базы.

Q: Какой этап жизненного цикла нельзя завершить без проверенной копии?
+ Ввод в эксплуатацию
- Проектирование схемы
- Установка XAMPP
- Вывод из эксплуатации

Q: Какие операции относятся к регламентным в MySQL?
+ Логический дамп через mysqldump
+ Обновление статистики через ANALYZE TABLE
+ Проверка журнала ошибок
- Перезапуск Apache по расписанию
- Ручное редактирование строк в phpMyAdmin
! Регламент включает копии, статистику, проверки и наблюдение.

Q: Что делает ANALYZE TABLE?
+ Обновляет статистику индексов для оптимизатора
- Пересобирает таблицу и освобождает место
- Создаёт резервную копию базы
- Удаляет дублирующиеся строки
! ANALYZE TABLE пересчитывает распределение значений для EXPLAIN.

Q: Чем OPTIMIZE TABLE отличается от ANALYZE TABLE?
+ Пересобирает таблицу, а не только пересчитывает статистику
- Работает только с таблицами MyISAM
- Не требует свободного места на диске
- Выполняется мгновенно на любой таблице
! OPTIMIZE TABLE переписывает страницы и возвращает место файловой системе.

Q: По каким признакам операцию стоит автоматизировать?
+ Она повторяется по расписанию
+ Результат можно проверить запросом или файлом
+ Параметры не меняются от запуска к запуску
- Она удаляет данные без возможности отмены
- Решение требует оценки ситуации человеком
! Автоматизируют повторяемые, детерминированные и проверяемые шаги.

Q: Что означает показатель RPO?
+ Допустимый объём данных, который можно потерять при сбое
- Время, за которое база вернётся к работе
- Размер файла дампа
- Число одновременных соединений
! RPO измеряется временем до сбоя и задаёт допустимую потерю.

Q: Дамп сделан в 02:00, сбой в 14:20, binary log не включён. Чему равен RPO?
+ 12 часов 20 минут
- 20 минут
- 2 часа
- 0 минут
! Без журнала восстановление вернёт базу к моменту дампа.

- Цвет вывода в консоли
- Число строк в самом скрипте
- Версию Apache
! Копия считается сделанной только после восстановления и сверки.

Q: Почему root без пароля в XAMPP опасен даже на учебном компьютере?
+ Любой клиент на этом компьютере получает полный доступ
- MySQL перестаёт запускаться
- phpMyAdmin не открывается
- Дампы становятся больше
! Пустой пароль root даёт локальному клиенту полный контроль над сервером.

Q: Что произойдёт, если хранить единственную копию на диске с данными?
+ При отказе диска пропадут и база, и копия
- Копия станет создаваться быстрее
- MySQL автоматически сделает вторую копию
- Восстановление ускорится
! Копия должна пережить отказ носителя с данными.
