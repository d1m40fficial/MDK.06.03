## Одна идея

Один и тот же запрос `SELECT * FROM students WHERE id = 42` вчера выполнялся за две миллисекунды, а сегодня за две секунды. Текст не изменился, данные тоже. Изменилось состояние сервера: нужная страница вытеснилась из памяти, запрос ждал метаданные таблицы или вырос журнал, который сервер теперь сбрасывает на диск.

**MySQL это не файл с таблицами, а процесс, который держит данные в памяти, пишет журналы и только потом возвращается к диску.** Понимание этого устройства объясняет, почему база быстрая, почему она переживает отключение питания и почему копировать её файлы «на лету» нельзя.

## Клиент и сервер

MySQL работает по клиент-серверной модели. Клиент открывает соединение, отправляет текст запроса и получает строки результата. Сервер `mysqld` принимает соединение, проверяет пользователя, разбирает запрос, выбирает план и выполняет его.

Клиентом может быть консольный `mysql`, phpMyAdmin в браузере или приложение на C# с библиотекой MySqlConnector. Все они говорят по одному протоколу, обычно через порт 3306. Для сервера важно не имя программы, а учётная запись и права, с которыми пришло соединение.

Каждое соединение это отдельная сессия со своими переменными, временными таблицами и транзакцией. Посмотреть, кто сейчас подключён, можно командой `SHOW PROCESSLIST`. Параметр `max_connections` ограничивает число одновременных сессий; в MySQL 8 по умолчанию это 151. Приложение на C# держит не одно соединение, а пул: открыть соединение дорого, поэтому библиотека переиспользует уже установленные.

Пул объясняет частую ошибку в приложении. Строка подключения задаёт минимальный и максимальный размер пула, и если максимум больше, чем допускает `max_connections`, под нагрузкой часть клиентов получит отказ. В учебной работе достаточно небольшого пула: несколько параллельных запросов, а не сотня. Наблюдать за реальным числом сессий полезнее, чем увеличивать лимит наугад.

## Что делает InnoDB

InnoDB это движок хранения по умолчанию. Он отвечает за то, как строки лежат на диске, как проверяются ограничения и как транзакция фиксируется. Верхние слои MySQL не знают, где именно находится строка: они просят движок прочитать или изменить её.

Данные InnoDB хранит в табличных пространствах. Системное пространство `ibdata1` существует всегда, а при включённом `innodb_file_per_table` каждая таблица получает свой файл `.ibd`. Внутри пространства данные разбиты на страницы по 16 КБ. Страница это минимальная единица чтения с диска: даже одна строка вытягивает целую страницу.

Таблица InnoDB организована как кластерный индекс по первичному ключу. Строки физически упорядочены по `id`, а листья вторичного индекса хранят не адрес строки, а значение первичного ключа. Отсюда два следствия. Короткий первичный ключ экономит место во всех индексах. Поиск по вторичному индексу требует второго шага: сначала найти ключ, потом спуститься по кластерному индексу.

```sql
SHOW TABLE STATUS FROM dean LIKE 'students';
SHOW VARIABLES LIKE 'innodb_page_size';
```

## Буферный пул

Буферный пул это область памяти, где сервер держит прочитанные страницы. Когда запросу нужна страница, InnoDB сначала ищет её в пуле. Попадание в память стоит микросекунды, чтение с диска на порядок дороже. Поэтому первый запрос после запуска сервера медленнее, а повторный по тем же данным быстрее.

Изменение тоже начинается в памяти. Сервер меняет страницу в пуле, помечает её грязной и записывает изменение в журнал. Сама страница отправится на диск позже, при сбросе (checkpoint). Такая схема позволяет не ждать диск на каждую строку, но создаёт вопрос: что будет, если питание пропадёт до записи страницы.

Размер пула задаётся параметром `innodb_buffer_pool_size`. В MySQL 8 по умолчанию 128 МБ, для рабочей базы этого мало: пул должен вмещать горячие данные и индексы. Проверить настройку и попадания можно так:

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW STATUS LIKE 'Innodb_buffer_pool_read_requests';
SHOW STATUS LIKE 'Innodb_buffer_pool_reads';
```

Отношение `reads` к `read_requests` показывает долю чтений, ушедших на диск. Если она заметно выше нуля на прогретой базе, пул мал для рабочего набора.

## Журналы

Три журнала решают три разные задачи, и путать их нельзя.

| Журнал | Что записывает | Кто читает | Зачем |
|---|---|---|---|
| redo log | изменения страниц на физическом уровне | сервер при восстановлении | повторить работу после сбоя |
| undo log | прежние версии строк | транзакция и читатели | откат и согласованное чтение |
| binary log | зафиксированные изменения в логическом виде | реплика и администратор | репликация и восстановление на момент |

**Redo log** работает по принципу записи вперёд: изменение сначала попадает в журнал, потом в страницу на диске. При отключении питания сервер при запуске проигрывает журнал и получает согласованное состояние. Параметр `innodb_flush_log_at_trx_commit=1` требует сбрасывать журнал на диск при каждом коммите: медленнее, но зафиксированная транзакция не теряется.

**Undo log** хранит прежние версии строк. Он нужен, чтобы откатить транзакцию по `ROLLBACK` и чтобы другие читатели видели старое состояние, пока новая версия не зафиксирована. Долгая транзакция не даёт очистить старые версии, и undo растёт, занимая диск.

**Binary log** ведёт сам сервер, а не движок. В него попадают изменения данных и схемы, причём в логическом виде. Этот журнал нужен реплике и восстановлению на момент времени. Он не заменяет резервную копию: в нём нет начального состояния таблиц.

При коммите сервер сначала пишет redo, затем binary log, и только после этого подтверждает успех клиенту. Если между этими шагами произойдёт сбой, при запуске согласованность восстанавливается по журналам.

## Autocommit и транзакции

По умолчанию `autocommit=1`: каждая команда это отдельная транзакция, и она фиксируется сразу. `INSERT INTO payments ...` без `START TRANSACTION` становится видимой другим сразу после выполнения.

Явная транзакция нужна, когда несколько изменений должны пройти вместе:

```sql
START TRANSACTION;
INSERT INTO payments (student_id, amount) VALUES (7, 4500.00);
INSERT INTO audit_log (db_user, action, table_name, row_id)
VALUES (CURRENT_USER(), 'insert', 'payments', LAST_INSERT_ID());
COMMIT;
```

Если вторая вставка нарушит ограничение, `ROLLBACK` вернёт базу к состоянию до `START TRANSACTION`. Деньги не спишутся без записи в аудит.

Важная особенность MySQL: команды `CREATE`, `ALTER`, `DROP` вызывают неявную фиксацию. Миграцию схемы нельзя обернуть в транзакцию и отменить одной командой. Для неё готовят обратный скрипт и копию.

## MVCC: как читатели не мешают писателям

InnoDB хранит в каждой строке служебные поля: номер транзакции, которая изменила версию, и ссылку на прежнюю версию в undo. Когда транзакция начинает читать, она получает снимок (read view) со списком активных транзакций. Строки, изменённые незафиксированными транзакциями, для неё невидимы: она берёт старую версию из undo.

Это и есть многоверсионность (MVCC). Читатель не блокирует писателя, писатель не блокирует читателя. Уровень изоляции по умолчанию `REPEATABLE READ`: повторный `SELECT` в той же транзакции видит тот же снимок, даже если другие уже зафиксировали изменения.

Если нужно увидеть самые свежие данные и заблокировать строку, используют `SELECT ... FOR UPDATE`. Такой запрос ждёт освобождения блокировки, поэтому его применяют точечно.

Долгая транзакция с открытым снимком держит старые версии и мешает очистке undo. На учебной базе это легко заметить: сессия забыла `COMMIT`, а таблица растёт. Найти такие транзакции помогает `information_schema.INNODB_TRX`.

Проверим на двух сессиях. Первая выполняет `START TRANSACTION; SELECT grade FROM enrollments WHERE id = 5;` и не завершается. Вторая меняет ту же строку и фиксирует изменение. Первая сессия при повторном чтении всё равно увидит прежнюю оценку: её снимок создан раньше. Как только она выполнит `COMMIT`, следующая транзакция увидит новое значение. Пока первая открыта, undo хранит обе версии строки.

## Файловая и серверная СУБД

Разница видна, если сравнить MySQL с настольной базой вроде SQLite или Access.

| Свойство | Файловая СУБД | Серверная СУБД MySQL |
|---|---|---|
| Доступ | локальный файл | много клиентов по сети |
| Пользователи | обычно нет | учётные записи и привилегии |
| Блокировки | файл или таблица | строки и транзакции |
| Журналы | минимальные | redo, undo, binary |
| Копия | копия файла | дамп или согласованный снимок |

В файловой базе достаточно скопировать файл, когда приложение закрыто. В серверной базе файлы постоянно меняются: страницы в пуле грязные, журналы пишутся, соединения работают. Копия файла на работающем сервере почти наверняка окажется несогласованной.

## Как это влияет на копирование и восстановление

Логический дамп `mysqldump` читает таблицы через транзакцию с согласованным снимком. Параметр `--single-transaction` как раз и создаёт такой снимок для InnoDB: дамп видит базу на один момент, хотя работа продолжается. Ограничение одно: во время дампа нельзя менять структуру таблиц. Команда `ALTER TABLE`, выполненная в этот момент, ломает снимок, и дамп может завершиться ошибкой или собрать несогласованные данные. Поэтому миграции не запускают одновременно с копированием.

Физическая копия требует либо остановить сервер, либо заблокировать запись через `FLUSH TABLES WITH READ LOCK`, либо использовать специальную утилиту, которая умеет читать журналы. Простое копирование `.ibd` на работающем сервере даёт «рваную» копию.

При восстановлении сначала импортируют дамп, затем проигрывают binary log до нужного момента. После аварийного запуска сервер сам проигрывает redo и откатывает незавершённые транзакции по undo. Поэтому журналы это не украшение, а часть механизма восстановления.

## Проверьте себя

> [!CHECK] Почему второй такой же запрос обычно быстрее первого?
> Первый читает страницы с диска и кладёт их в буферный пул. Второй находит их в памяти, если пул достаточно велик и страницы не вытеснены.

> [!CHECK] Можно ли восстановить базу только из binary log, без дампа?
> Нет. Binary log содержит изменения, но не начальное состояние. Нужен дамп, на который последовательно накладывают журнал.

> [!CHECK] Что произойдёт с незавершённой транзакцией после отключения питания?
> При запуске сервер проиграет redo для зафиксированных изменений, а незавершённые версии откатит по undo. Клиент увидит разрыв соединения, но база останется согласованной.

## Итоги

- Клиент отправляет SQL, сервер разбирает его, строит план и обращается к InnoDB.
- InnoDB хранит данные страницами по 16 КБ в табличных пространствах и организует таблицу вокруг первичного ключа.
- Буферный пул ускоряет чтение и запись, а redo, undo и binary log обеспечивают восстановление, откат и репликацию.
- Копировать файлы работающего сервера нельзя: нужен согласованный снимок или дамп.

! Коммит фиксирует изменение в журналах и только потом подтверждает клиенту.

Q: Чем серверная СУБД отличается от файловой?
+ Поддерживает много клиентов по сети
+ Проверяет учётные записи и привилегии
+ Использует транзакции и журналы
- Не хранит данные на диске
- Не требует резервного копирования
! Серверная СУБД рассчитана на параллельных пользователей и восстановление.

Q: Почему нельзя копировать файлы .ibd на работающем сервере?
+ Копия может оказаться несогласованной из-за незавершённых записей
- Файлы .ibd зашифрованы паролем root
- InnoDB не хранит данные в файлах
- Копирование запрещено лицензией
! Страницы и журналы меняются во время копирования, поэтому нужен снимок.
