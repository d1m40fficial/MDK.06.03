## Цель работы

Транзакция даёт одно обещание: набор изменений применяется целиком или не применяется вовсе, а параллельная сессия не видит половину работы. Ошибка начинается там, где два человека одновременно меняют одну строку или читают таблицу, пока другой её дописывает.

Цель работы: проверить это обещание на базе `dean` в MySQL из XAMPP. Вы увидите фиксацию и откат, точку сохранения, неповторяющееся чтение, фантом, взаимную блокировку и ожидание по `innodb_lock_wait_timeout`. Каждый сценарий заканчивается записью в таблицу наблюдений: что сделала каждая сессия, что увидела и почему.

## Краткие теоретические сведения

**Транзакция** это последовательность операторов, которую сервер выполняет как единое целое. Четыре буквы ACID означают атомарность (всё или ничего), согласованность (ограничения выполняются после фиксации), изолированность (параллельные транзакции не мешают друг другу) и долговечность (зафиксированное переживает сбой).

**Фиксация** (`COMMIT`) делает изменения видимыми и пишет их в журнал упреждающей записи. **Откат** (`ROLLBACK`) отменяет всё, что сделано после `START TRANSACTION`. **Точка сохранения** (`SAVEPOINT`) отменяет часть работы, не теряя транзакцию: `ROLLBACK TO SAVEPOINT` возвращает состояние на момент точки, `RELEASE SAVEPOINT` убирает её из стека.

**Автофиксация.** В MySQL оператор вне транзакции фиксируется сразу, потому что `autocommit` включён. `CREATE`, `ALTER`, `DROP` и `TRUNCATE` вызывают неявную фиксацию, откатить их нельзя.

**Уровень изоляции** определяет, какие изменения чужих транзакций видит ваша. По умолчанию в InnoDB стоит `REPEATABLE READ`. На `READ COMMITTED` каждый оператор берёт новый снимок и видит только зафиксированные строки. На `REPEATABLE READ` снимок берётся при первом чтении и живёт до конца транзакции, поэтому повторный запрос возвращает те же строки. `SERIALIZABLE` превращает обычные чтения в блокирующие.

**Аномалии.** Неповторяющееся чтение даёт разные значения в двух одинаковых запросах одной транзакции. Фантом добавляет строки, и повторный `COUNT(*)` меняется. Потерянное обновление теряет результат одной из двух транзакций.

**Блокировки.** Изменение строки берёт монопольную блокировку до конца транзакции, поэтому второй `UPDATE` той же строки ждёт. InnoDB блокирует и промежуток в индексе (next-key lock), иначе фантом вернулся бы через вставку. Цикл ожидания сервер находит сам и отменяет одну транзакцию с ошибкой 1213.

**Ожидание.** Параметр `innodb_lock_wait_timeout` задаёт предел ожидания в секундах, по умолчанию 50. Истёкшее ожидание даёт ошибку 1205. Транзакции видны в `information_schema.INNODB_TRX`, а отчёт о последней взаимной блокировке в разделе `LATEST DETECTED DEADLOCK` команды `SHOW ENGINE INNODB STATUS`.

## Ход работы

### Шаг 1. Откройте две сессии и подпишите вывод

Откройте два окна командной строки и в каждом запустите клиент на базе `dean`.

В сессии A напечатайте подпись, номер соединения и уровень изоляции.

Строка с фамилией попадает в вывод первой, поэтому на скриншоте видно, чья это работа. Повторяйте её перед каждым сценарием и запишите номера соединений обеих сессий.

### Шаг 2. Проверьте фиксацию, откат и точку сохранения

В сессии A выполните откат.

```sql
SELECT 'Иванов И.И., ИС-41' AS student;
START TRANSACTION;
UPDATE payments SET amount = amount + 100 WHERE id = 1;
SELECT amount FROM payments WHERE id = 1;
ROLLBACK;
SELECT amount FROM payments WHERE id = 1;
```

Сумма после `ROLLBACK` вернулась к исходной. Теперь повторите с фиксацией и точкой сохранения.

```sql
START TRANSACTION;
UPDATE payments SET amount = amount + 100 WHERE id = 1;
SAVEPOINT before_second;
UPDATE payments SET amount = amount + 200 WHERE id = 1;
ROLLBACK TO SAVEPOINT before_second;
COMMIT;
SELECT amount FROM payments WHERE id = 1;
```

Прибавка составила 100, а не 300: откат до точки убрал второе изменение, но сохранил первое. Запишите оба результата.

### Шаг 3. Воспроизведите неповторяющееся чтение

На `READ COMMITTED` каждый оператор берёт новый снимок, поэтому повторный запрос видит чужую фиксацию.

```sql
SELECT 'Иванов И.И., ИС-41' AS student;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT amount FROM payments WHERE id = 1;
```

```sql
SELECT 'Петров П.П., ИС-41' AS student;
UPDATE payments SET amount = amount + 50 WHERE id = 1;
```

Вернитесь в сессию A, повторите запрос и зафиксируйте транзакцию.

```sql
SELECT amount FROM payments WHERE id = 1;
COMMIT;
```

Второе значение отличается от первого. Это неповторяющееся чтение: внутри одной транзакции данные изменились, потому что `READ COMMITTED` не обещает стабильный снимок, он обещает отсутствие грязного чтения.

### Шаг 4. Повторите сценарий на REPEATABLE READ

Снимок теперь берётся при первом чтении и живёт до конца транзакции.

```sql
SELECT 'Иванов И.И., ИС-41' AS student;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT amount FROM payments WHERE id = 1;
```

Сессия B снова прибавляет 50. Запрос в сессии A возвращает прежнее значение.

```sql
SELECT amount FROM payments WHERE id = 1;
COMMIT;
```

Разница между шагами 3 и 4 и есть цена уровня изоляции: `REPEATABLE READ` даёт стабильное чтение, но приложение работает с устаревшими числами.

### Шаг 5. Покажите фантом на двух уровнях

Фантом проверяется по множеству строк. Считайте платежи студента с `id = 3`.

```sql
SELECT 'Иванов И.И., ИС-41' AS student;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
SELECT COUNT(*) AS payments_before FROM payments WHERE student_id = 3;
```

```sql
SELECT 'Петров П.П., ИС-41' AS student;
INSERT INTO payments (student_id, amount) VALUES (3, 500);
```

Повторите счёт в сессии A и зафиксируйте транзакцию.

```sql
SELECT COUNT(*) AS payments_after FROM payments WHERE student_id = 3;
COMMIT;
```

На `READ COMMITTED` второй счёт больше первого. Повторите сценарий на `REPEATABLE READ`: обычный `SELECT COUNT(*)` покажет прежнее число, потому что транзакция читает снимок. Добавьте блокирующее чтение и убедитесь, что строки всё равно видны.

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT COUNT(*) AS snapshot_count FROM payments WHERE student_id = 3;
SELECT COUNT(*) AS locking_count FROM payments WHERE student_id = 3 FOR UPDATE;
COMMIT;
```

Второе число больше первого. Фантом не исчез, он скрыт от согласованного чтения: `FOR UPDATE` читает последнюю версию и блокирует промежуток индекса, поэтому чужая вставка в диапазон будет ждать. Запишите оба числа.

### Шаг 6. Вызовите взаимную блокировку

Каждая сессия захватывает свою строку, затем просит строку другой. Цикл сервер находит сам.

```sql
SELECT 'Иванов И.И., ИС-41' AS student;
START TRANSACTION;
UPDATE students SET full_name = full_name WHERE id = 1;
```

```sql
SELECT 'Петров П.П., ИС-41' AS student;
START TRANSACTION;
UPDATE students SET full_name = full_name WHERE id = 2;
```

Теперь поменяйте порядок: в сессии A обновите строку 2, в сессии B строку 1. Выполняйте по очереди: сначала команду в A, затем в B.

```sql
UPDATE students SET full_name = full_name WHERE id = 2;
```

```sql
UPDATE students SET full_name = full_name WHERE id = 1;
```

Одна сессия получит `ERROR 1213 (40001): Deadlock found when trying to get lock`, и её транзакция будет отменена целиком. Вторая продолжит работу после `COMMIT`. Запишите, какая сессия стала жертвой. Обновление без изменения значения тоже берёт блокировку.

### Шаг 7. Ограничьте ожидание через innodb_lock_wait_timeout

Сессия A держит блокировку строки и не завершает транзакцию.

```sql
START TRANSACTION;
UPDATE students SET full_name = full_name WHERE id = 1;
```

В сессии B задайте предел ожидания и попробуйте обновить ту же строку.

```sql
SELECT 'Петров П.П., ИС-41' AS student;
SET SESSION innodb_lock_wait_timeout = 5;
UPDATE students SET full_name = full_name WHERE id = 1;
```

Через пять секунд запрос завершится ошибкой `ERROR 1205 (HY000): Lock wait timeout exceeded`. После `COMMIT` в сессии A повторите запрос в сессии B: он пройдёт. Параметр действует на текущую сессию.

Приложите скриншот ошибки 1205: на нём видно, что ожидание ограничено.

### Шаг 8. Найдите причину в INNODB STATUS и INNODB_TRX

Пока сессия A держит строку, откройте третье окно и посмотрите активные транзакции.

```sql
SELECT 'Иванов И.И., ИС-41' AS student;
SELECT trx_id, trx_state, trx_started, trx_mysql_thread_id,
       trx_isolation_level, trx_rows_locked, LEFT(trx_query, 60) AS query_text
FROM information_schema.INNODB_TRX
ORDER BY trx_started;
```

Строка со старым `trx_started` и есть долгая транзакция. Посмотрите, кто кого ждёт.

```sql
SELECT * FROM information_schema.INNODB_LOCKS;
SELECT * FROM information_schema.INNODB_LOCK_WAITS;
```

В MySQL 8 таблицы `INNODB_LOCKS` и `INNODB_LOCK_WAITS` пусты: данные перенесены в `performance_schema`.

```sql
SELECT OBJECT_SCHEMA, OBJECT_NAME, INDEX_NAME, LOCK_TYPE,
       LOCK_MODE, LOCK_STATUS, LOCK_DATA
FROM performance_schema.data_locks
WHERE OBJECT_SCHEMA = 'dean';
```

Строка с `LOCK_STATUS = 'WAITING'` это ожидание. Наконец, откройте полный отчёт сервера.

```sql
SHOW ENGINE INNODB STATUS\G
```

В разделе `LATEST DETECTED DEADLOCK` найдите транзакции, их запросы и строку, на которой возник цикл. В разделе `TRANSACTIONS` видны активные транзакции и удерживаемые блокировки. Приложите скриншот обоих разделов.

### Шаг 9. Заполните таблицу наблюдений

Одна строка на сценарий. В последнем столбце объясните причину, а не перескажите результат.

| Сценарий | Уровень | Действие A | Действие B | Что увидела A | Аномалия | Вывод |
|---|---|---|---|---|---|---|
| Откат | по умолчанию | `UPDATE`, затем `ROLLBACK` | нет | Исходное значение | нет | Откат убирает изменение целиком |
| Точка сохранения | по умолчанию | Два `UPDATE`, `ROLLBACK TO` | нет | Только первая прибавка | нет | Точка отменяет часть работы |
| Повторное чтение | `READ COMMITTED` | Два `SELECT` | `UPDATE` и автофиксация | Значение изменилось | Неповторяющееся чтение | Новый снимок на каждый оператор |
| Повторное чтение | `REPEATABLE READ` | Два `SELECT` | `UPDATE` и автофиксация | Значение прежнее | нет | Снимок на всю транзакцию |
| Фантом | `READ COMMITTED` | Два `COUNT(*)` | `INSERT` | Счёт вырос | Фантом | Новые строки попадают в снимок |
| Фантом и блокировка | `REPEATABLE READ` | `COUNT(*)`, затем `FOR UPDATE` | нет | Числа различаются | Фантом скрыт | Блокирующее чтение видит новые строки |
| Взаимная блокировка | по умолчанию | Строка 1, затем 2 | Строка 2, затем 1 | `ERROR 1213` | Взаимная блокировка | Сервер отменил одну транзакцию |
| Ожидание | по умолчанию | Держит строку | `innodb_lock_wait_timeout = 5` | `ERROR 1205` | нет | Ожидание ограничено параметром |

Скриншоты делайте только как доказательства: две подписанные сессии, ошибка 1205 при ожидании, ошибка 1213 и раздел `LATEST DETECTED DEADLOCK`. Шапка отчёта и текст теории в кадр не нужны.
