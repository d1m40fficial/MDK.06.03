## Цель работы

Транзакция даёт одно обещание: набор изменений применяется целиком или не применяется вовсе, а параллельные сессии не видят половину работы. На словах это просто. Ошибка начинается там, где два человека одновременно меняют одну строку или читают таблицу, пока другой её дописывает.

Цель работы: проверить обещание транзакции на учебной базе `dean`. Вы увидите фиксацию и откат, точку сохранения, неповторяющееся чтение на `Read Committed`, фантом, конфликт на `Serializable`, взаимную блокировку и ожидание по `lock_timeout`. Каждый сценарий заканчивается записью в таблицу наблюдений: что сделала каждая сессия, что она увидела и почему.

## Оборудование и программное обеспечение

- Персональный компьютер с VirtualBox и учебной Ubuntu Server.
- PostgreSQL 16 в виртуальной машине, база `dean` с учебными данными.
- Два окна терминала или tmux с двумя панелями для параллельных сессий.
- Роль `dean_owner` или `dean_write` с правом изменения таблиц `students`, `payments` и `enrollments`.
- Клиент `psql` версии 16.
- Текстовый редактор для SQL-скриптов и табличный редактор для отчёта.
- Каталог `~/transactions` для скриптов и скриншотов.

## Краткие теоретические сведения

**Транзакция** это последовательность операторов, которую сервер выполняет как единое целое. Свойства транзакции описывают четыре буквы ACID: атомарность (всё или ничего), согласованность (ограничения выполняются после фиксации), изолированность (параллельные транзакции не мешают друг другу) и долговечность (зафиксированное переживает сбой).

**Фиксация** (`COMMIT`) делает изменения видимыми и записывает их в журнал упреждающей записи. **Откат** (`ROLLBACK`) отменяет всё, что сделано после `BEGIN`. **Точка сохранения** (`SAVEPOINT`) позволяет отменить часть работы, не теряя транзакцию целиком: `ROLLBACK TO SAVEPOINT` возвращает состояние на момент точки, а `RELEASE SAVEPOINT` убирает её из стека.

**Уровень изоляции** определяет, какие изменения чужих транзакций видит ваша. В PostgreSQL три практических уровня. `Read Committed` (по умолчанию) видит только зафиксированные строки и берёт новый снимок на каждый оператор. `Repeatable Read` берёт снимок на всю транзакцию, поэтому повторный запрос возвращает те же строки. `Serializable` добавляет проверку зависимостей и может прервать транзакцию, если её результат нельзя объяснить последовательным выполнением.

**Аномалии.** Неповторяющееся чтение: два одинаковых запроса в одной транзакции дают разные значения. Фантомное чтение: между запросами появляются новые строки, и повторный `count(*)` меняется. Потерянное обновление: две транзакции читают одно значение и записывают результат, один результат теряется. Ошибка сериализации (`SQLSTATE 40001`) это не сбой, а требование повторить транзакцию.

**Блокировки.** Изменение строки берёт монопольную блокировку до конца транзакции, поэтому второй `UPDATE` той же строки ждёт. Если две транзакции ждут ресурсы друг друга, сервер находит цикл и отменяет одну с сообщением `deadlock detected` (`SQLSTATE 40P01`). Параметр `lock_timeout` ограничивает ожидание и превращает его в ошибку `canceling statement due to lock timeout`. Состояние блокировок видно в `pg_locks`, а сессии и их запросы в `pg_stat_activity`.

### Шаг 2. Проверьте фиксацию, откат и точку сохранения

В сессии A выполните откат.

```sql
\echo 'Иванов И.И., ИС-41'
BEGIN;
UPDATE payments SET amount = amount + 100 WHERE id = 1;
SELECT amount FROM payments WHERE id = 1;
ROLLBACK;
SELECT amount FROM payments WHERE id = 1;
```

Сумма после `ROLLBACK` вернулась к исходной. Теперь повторите с фиксацией и точкой сохранения.

```sql
BEGIN;
UPDATE payments SET amount = amount + 100 WHERE id = 1;
SAVEPOINT before_second;
UPDATE payments SET amount = amount + 200 WHERE id = 1;
ROLLBACK TO SAVEPOINT before_second;
COMMIT;
SELECT amount FROM payments WHERE id = 1;
```

Прибавка составила 100, а не 300: откат до точки сохранения убрал второе изменение, но сохранил первое. Запишите оба результата в таблицу наблюдений.

### Шаг 3. Воспроизведите неповторяющееся чтение

Уровень `Read Committed` берёт новый снимок на каждый оператор, поэтому повторный запрос видит чужую фиксацию.

| Шаг | Сессия A | Сессия B |
|---|---|---|
| 1 | `BEGIN ISOLATION LEVEL READ COMMITTED;` | |
| 2 | `SELECT amount FROM payments WHERE id = 1;` | |
| 3 | | `BEGIN; UPDATE payments SET amount = amount + 50 WHERE id = 1; COMMIT;` |
| 4 | `SELECT amount FROM payments WHERE id = 1;` | |
| 5 | `COMMIT;` | |

```sql
\echo 'Иванов И.И., ИС-41'
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT amount FROM payments WHERE id = 1;
```

```sql
\echo 'Петров П.П., ИС-41'
BEGIN;
UPDATE payments SET amount = amount + 50 WHERE id = 1;
COMMIT;
```

Вернитесь в сессию A, повторите запрос и зафиксируйте транзакцию.

```sql
SELECT amount FROM payments WHERE id = 1;
COMMIT;
```

Второе значение отличается от первого. Это неповторяющееся чтение: внутри одной транзакции данные изменились. Причина в том, что `Read Committed` не обещает стабильный снимок, он обещает отсутствие грязного чтения.

### Шаг 4. Повторите сценарий на Repeatable Read

Снимок теперь берётся на всю транзакцию. Повторите шаги 3 с другим уровнем.

```sql
\echo 'Иванов И.И., ИС-41'
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT amount FROM payments WHERE id = 1;
```

Сессия B снова прибавляет 50 и фиксирует изменение. Запрос в сессии A возвращает прежнее значение.

```sql
SELECT amount FROM payments WHERE id = 1;
COMMIT;
```

Добавьте проверку записи: начните транзакцию `REPEATABLE READ`, прочитайте строку, измените её в сессии B, а затем попробуйте обновить ту же строку в сессии A. Сервер вернёт `could not serialize access due to concurrent update` и отменит транзакцию. Это защита от потерянного обновления: молча перезаписать чужую работу PostgreSQL не даёт.

### Шаг 5. Покажите фантом на двух уровнях

Фантом проверяется не по одной строке, а по множеству. Считайте платежи студента с `id = 3`.

```sql
\echo 'Иванов И.И., ИС-41'
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT count(*) FROM payments WHERE student_id = 3;
```

```sql
\echo 'Петров П.П., ИС-41'
INSERT INTO payments (student_id, amount) VALUES (3, 500);
```

Повторите счёт в сессии A и зафиксируйте транзакцию.

```sql
SELECT count(*) FROM payments WHERE student_id = 3;
COMMIT;
```

На `Read Committed` второй счёт больше первого. Повторите сценарий на `Repeatable Read`: второй счёт останется прежним, потому что транзакция работает со снимком. Запишите оба результата.

### Шаг 6. Получите ошибку сериализации на Serializable

На уровне `Serializable` сервер проверяет, можно ли объяснить результат последовательным выполнением транзакций.

| Шаг | Сессия A | Сессия B |
|---|---|---|
| 1 | `BEGIN ISOLATION LEVEL SERIALIZABLE;` | `BEGIN ISOLATION LEVEL SERIALIZABLE;` |
| 2 | `SELECT sum(amount) FROM payments;` | `SELECT sum(amount) FROM payments;` |
| 3 | `INSERT INTO payments (student_id, amount) VALUES (1, 10);` | `INSERT INTO payments (student_id, amount) VALUES (2, 10);` |
| 4 | `COMMIT;` | `COMMIT;` |

Одна из транзакций завершится ошибкой `could not serialize access due to read/write dependencies among transactions`. Откатите её через `ROLLBACK` и повторите: на повторном запуске конфликт исчезает. Запишите, какая сессия стала жертвой и на каком шаге.

### Шаг 7. Вызовите взаимную блокировку

Каждая сессия захватывает свою строку, затем просит строку другой стороны. Цикл ожидания сервер находит сам.

```sql
\echo 'Иванов И.И., ИС-41'
BEGIN;
UPDATE students SET full_name = full_name WHERE id = 1;
```

```sql
\echo 'Петров П.П., ИС-41'
BEGIN;
UPDATE students SET full_name = full_name WHERE id = 2;
```

Теперь поменяйте порядок: в сессии A обновите строку 2, в сессии B строку 1.

```sql
UPDATE students SET full_name = full_name WHERE id = 2;
```

```sql
UPDATE students SET full_name = full_name WHERE id = 1;
```

Через `deadlock_timeout` одна сессия получит `ERROR: deadlock detected`, и её транзакция будет отменена. Вторая продолжит работу после `COMMIT`. Обратите внимание: даже обновление без изменения значения берёт блокировку, потому что сервер создаёт новую версию строки.

### Шаг 8. Ограничьте ожидание через lock_timeout

Сессия A держит блокировку строки и не завершает транзакцию.

```sql
BEGIN;
UPDATE students SET full_name = full_name WHERE id = 1;
```

В сессии B задайте предел ожидания и попробуйте обновить ту же строку.

```sql
\echo 'Петров П.П., ИС-41'
SET lock_timeout = '2s';
UPDATE students SET full_name = full_name WHERE id = 1;
```

Запрос завершится ошибкой `canceling statement due to lock timeout`. После `COMMIT` в сессии A повторите запрос в сессии B: он пройдёт. Параметр действует на текущую сессию и сбрасывается через `RESET lock_timeout`.

### Шаг 9. Посмотрите блокировки и ожидающие запросы

Пока сессия A держит строку, откройте третью сессию или используйте B после ошибки.

```sql
SELECT a.pid, a.application_name, a.state,
       now() - a.xact_start AS xact_age,
       l.locktype, l.mode, l.granted,
       l.relation::regclass AS object
FROM pg_locks l
JOIN pg_stat_activity a ON a.pid = l.pid
WHERE l.relation IS NOT NULL
ORDER BY a.pid, l.granted DESC;
```

Строка с `granted = false` это ожидание. Найдите, кто кого блокирует.

```sql
SELECT pid, application_name, state,
       pg_blocking_pids(pid) AS blocked_by,
       left(query, 60) AS query
FROM pg_stat_activity
WHERE datname = 'dean' AND cardinality(pg_blocking_pids(pid)) > 0;
```

Столбец `blocked_by` содержит PID держателя блокировки. Приложите скриншот обоих запросов: на нём видно, что ожидание относится к вашей паре сессий.

| Сценарий | Уровень | Действие A | Действие B | Что увидела A | Аномалия | Вывод |
|---|---|---|---|---|---|---|
| Откат | Read Committed | `UPDATE`, затем `ROLLBACK` | нет | Исходное значение | нет | Откат убирает изменение целиком |
