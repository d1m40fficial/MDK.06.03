## Одна идея

Отчёт «средний балл по курсам» выполняется сорок секунд. Администратор добавляет индекс по `course_id`, запускает снова и получает те же сорок секунд. Тогда он открывает план и видит: индекс действительно используется, но внутри вложенного цикла на каждую строку выполняется ещё один проход по таблице платежей.

**Медленный запрос лечится по плану, а не по догадкам.** План показывает, какие узлы работают, сколько строк через них проходит и где время тратится на самом деле. Индекс, добавленный без плана, часто лечит не ту операцию.

Порядок работы простой: найти тяжёлый запрос, снять план до правки, понять узкое место, изменить запрос или схему, снять план после и сравнить. Каждый шаг опирается на измерение, а не на веру.

## EXPLAIN и EXPLAIN ANALYZE

Команда `EXPLAIN` показывает выбранный план, но не выполняет запрос. `EXPLAIN ANALYZE` выполняет и добавляет фактическое время и число строк.

```sql
EXPLAIN
SELECT c.title, round(avg(e.grade), 2) AS avg_grade
FROM enrollments e
JOIN courses c ON c.id = e.course_id
GROUP BY c.title;
```

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.title, round(avg(e.grade), 2) AS avg_grade
FROM enrollments e
JOIN courses c ON c.id = e.course_id
GROUP BY c.title;
```

План читают снизу вверх: нижние узлы поставляют строки верхним. У каждого узла есть оценка стоимости `cost=начало..итог`, оценка числа строк `rows` и ширина строки в байтах `width`. Стоимость измеряется не в секундах, а в условных единицах: чтение страницы с диска принято за единицу, случайное чтение дороже, обработка строки дешевле.

С `ANALYZE` появляются `actual time`, `actual rows` и `loops`. Время указано на один цикл узла, поэтому при `loops` больше единицы его умножают. Если узел выполнялся тысячу раз по миллисекунде, это секунда, а не миллисекунда.

`BUFFERS` добавляет работу с памятью и диском. `shared hit` это страницы, найденные в кэше, `shared read` прочитанные с диска, `temp read` и `temp written` обращения к временным файлам. Именно буферы объясняют, почему запрос с одинаковым временем может быть хорошим в тесте и плохим на рабочей базе.

> [!PITFALL] ANALYZE выполняет запрос
> `EXPLAIN ANALYZE` для `UPDATE` или `DELETE` действительно меняет данные. На рабочей базе такой запрос оборачивают в транзакцию и завершают её откатом, иначе объяснение плана станет изменением таблицы.

## Операторы плана

Узлы плана называют операторами, и каждый из них отвечает за свою стратегию доступа или соединения.

- **Seq Scan** читает все страницы таблицы. Это нормально для маленькой таблицы или выборки в треть строк.
- **Index Scan** идёт по индексу к строкам и читает их по одной. Хорош для точных условий.
- **Index Only Scan** отвечает по индексу, не заглядывая в таблицу.
- **Bitmap Index Scan** с **Bitmap Heap Scan** сначала собирает ссылки на строки, сортирует их по страницам и читает таблицу крупными кусками.
- **Nested Loop** берёт строки внешнего набора и для каждой ищет совпадения во внутреннем. Хорош, когда внешних строк мало и внутренний поиск идёт по индексу.
- **Hash Join** строит хеш по меньшему набору и проверяет по нему больший. Хорош для больших неотсортированных наборов.
- **Merge Join** сливает два отсортированных потока и хорош, когда сортировка уже есть.
- **Sort** сортирует строки в памяти или на диске.

Опасные признаки видны сразу. `Seq Scan` на большой таблице с условием, возвращающим десяток строк, означает отсутствующий или неприменимый индекс. `Nested Loop` с большим числом циклов означает, что внешний набор оказался больше ожидаемого. `Sort Method: external merge Disk: 24576kB` означает, что сортировка не поместилась в `work_mem` и ушла на диск.

```sql
SET work_mem = '64MB';
```

`work_mem` ограничивает память на одну операцию, а не на соединение. Увеличение помогает сортировкам и хеш-соединениям, но при сотне одновременных запросов память умножается на их число. Настройку меняют осознанно, а не «на максимум».

## Sargable-условия

Условие называется sargable, если по нему можно пройти по индексу. Функция над столбцом ломает эту возможность: индекса по `paid_at` недостаточно, чтобы найти `date_trunc('month', paid_at) = '2026-04-01'`.

```sql
SELECT count(*) FROM payments
WHERE date_trunc('month', paid_at) = DATE '2026-04-01';
```

Переписанное условие становится диапазоном, и индекс по `paid_at` работает:

```sql
SELECT count(*) FROM payments
WHERE paid_at >= DATE '2026-04-01'
  AND paid_at < DATE '2026-05-01';
```

То же с арифметикой. `WHERE amount * 1.2 > 100` заставляет считать выражение для каждой строки, а `WHERE amount > 83.33` позволяет искать по индексу.

Приведение типа тоже бывает лишним. `WHERE student_id::text = '7'` превращает число в текст и отключает индекс, а `WHERE student_id = 7` работает. Причина в том, что сравнение идёт по вычисленному значению, а не по столбцу.

`LIKE '%ов'` не может использовать обычный B-tree: шаблон не задаёт начало строки. Для таких поисков нужен индекс GIN с расширением `pg_trgm` или отдельное решение, а не ещё один B-tree.

## SELECT * и лишние соединения

`SELECT *` тянет все столбцы, даже если нужны два. Это увеличивает чтение, передачу по сети и мешает покрывающему индексу: `Index Only Scan` возможен только тогда, когда все нужные столбцы есть в индексе.

Соединение, добавленное только ради фильтра, часто заменяется на `EXISTS`.

```sql
SELECT s.full_name
FROM students s
WHERE EXISTS (
  SELECT 1 FROM enrollments e
  WHERE e.student_id = s.id AND e.grade = 2
);
```

`EXISTS` останавливается на первой подходящей строке и не размножает результат. Обычный `JOIN` с той же таблицей вернёт студента столько раз, сколько у него двоек, и кто-то добавит `DISTINCT`, скрыв настоящую причину.

Соединение двух таблиц «многие к одному» искажает и суммы. Если соединить `enrollments` и `payments` по студенту, каждая оценка повторится для каждого платежа, и `avg(grade)` посчитается по раздутому набору. Агрегаты считают по каждой таблице отдельно или через `LATERAL`.

## CTE и материализация

Общее табличное выражение (`WITH`) задаёт именованный подзапрос. До PostgreSQL 12 оно всегда материализовалось: результат вычислялся отдельно и дальше использовался как готовая таблица. Сейчас обычное CTE, использованное один раз, встраивается в основной запрос, и условие может примениться к нему целиком.

```sql
WITH bad AS (
  SELECT * FROM enrollments WHERE grade = 2
)
SELECT student_id, count(*) FROM bad GROUP BY student_id;
```

Если встроить это выражение, индекс по `grade` может отфильтровать строки до соединения. Если материализовать, сначала будет прочитана вся таблица. Управлять поведением можно явно:

```sql
WITH bad AS MATERIALIZED (
  SELECT * FROM enrollments WHERE grade = 2
)
SELECT student_id, count(*) FROM bad GROUP BY student_id;
```

`MATERIALIZED` запрещает встраивание и полезен, когда подзапрос действительно должен выполниться один раз, например с `LIMIT` или дорогой функцией. `NOT MATERIALIZED` заставляет встроить выражение. Выбор делают по плану, а не по привычке.

## Пагинация

`LIMIT` с большим `OFFSET` читает и выбрасывает все пропущенные строки. Страница номер тысяча стоит столько же, сколько чтение тысячи страниц.

```sql
SELECT id, full_name FROM students
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;
```

Ключевая пагинация запоминает последнюю строку и продолжает с неё.

```sql
SELECT id, full_name FROM students
WHERE (created_at, id) < ('2026-04-01 10:00:00+03', 500)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Условие по паре столбцов требует составного индекса `(created_at, id)`. Зато стоимость страницы не растёт с её номером: каждая следующая начинается с известного места.

## pg_stat_statements

Искать медленные запросы вручную тяжело: их сотни. Расширение `pg_stat_statements` собирает статистику по нормализованным запросам.

```
shared_preload_libraries = 'pg_stat_statements'
```

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT calls,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       round(total_exec_time::numeric, 1) AS total_ms,
       rows,
       left(query, 60) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

Нормализация заменяет конкретные значения на параметры, поэтому одинаковые запросы с разными аргументами считаются вместе. Сортировка по `total_exec_time` находит запрос, который съедает больше всего времени в сумме, даже если каждый вызов быстрый.

## Статистика и проверка результата

Планировщик выбирает план по статистике. Если оценки строк расходятся с фактическими в десятки раз, виновата не «плохая база», а устаревшие или слишком грубые данные о распределении.

```sql
ANALYZE enrollments;

CREATE STATISTICS st_students_group_specialty (dependencies)
ON group_id, specialty FROM students;
ANALYZE students;
```

Расширенная статистика помогает, когда два столбца связаны: группа почти всегда относится к одной специальности, и планировщик без подсказки умножает вероятности и занижает результат.

Сравнивать правку нужно честно. Берут те же данные и параметры, прогревают кэш несколькими прогонами, снимают `EXPLAIN (ANALYZE, BUFFERS)` до и после и смотрят не только время, но и число прочитанных страниц, оценку строк и выбранные узлы. Один замер на холодной базе ничего не доказывает.

> [!TRADEOFF] Запрос или схема
> Иногда дешевле переписать запрос, иногда добавить индекс, иногда изменить модель данных. Начинают с запроса, потому что это не требует миграции и не замедляет запись. Индекс добавляют, когда план показывает повторяющийся доступ по одному условию.

## Типичные ошибки

- **Смотреть только время.** Запрос на десять секунд может быть быстрым для своей задачи, а запрос на сто миллисекунд съедать половину ресурсов сервера. Время без плана и числа строк ничего не объясняет.
- **Менять запрос без плана.** Переписанный запрос может стать красивее и медленнее. Сначала план, потом правка, потом новый план.
- **Забыть статистику.** После массовой загрузки `ANALYZE` не выполнен, оценки строк неверны, и планировщик выбирает соединение, рассчитанное на десять строк вместо десяти тысяч.
- **Проверять на других данных.** На учебной базе из двадцати строк любой план работает мгновенно. Решение принимают на объёме, близком к рабочему.

## Проверьте себя

> [!CHECK] План показывает Seq Scan по таблице на двадцать тысяч строк, а условие возвращает пять. Что проверить?
> Наличие индекса по столбцу условия, его применимость (нет ли функции или приведения типа), статистику и фактическое число строк. Если индекс есть и подходит, сравните `rows` оценки и `actual rows`: расхождение указывает на устаревшую статистику.

> [!CHECK] Почему запрос с JOIN и DISTINCT может считать неверные средние?
> Соединение размножает строки: одна оценка повторяется для каждого платежа или курса. `DISTINCT` убирает повторы строк результата, но не восстанавливает правильный вес. Агрегат считают по таблице отдельно или через `LATERAL`.

> [!CHECK] Чем ключевая пагинация лучше OFFSET на большой таблице?
> `OFFSET` читает и отбрасывает все предыдущие строки, поэтому поздние страницы стоят всё дороже. Ключевая пагинация начинает с известной позиции по индексу и не зависит от номера страницы.

## Итоги

- План выполнения показывает, где запрос тратит время, и заменяет догадки.
- `EXPLAIN ANALYZE` добавляет фактические строки, время и буферы.
- Функция или приведение типа над столбцом отключают индекс; условие переписывают в диапазон.
- `SELECT *` и лишние соединения увеличивают чтение и размножают строки.
- `pg_stat_statements` находит тяжёлые запросы, а `ANALYZE` даёт планировщику верные оценки.

::quiz
Q: Чем EXPLAIN ANALYZE отличается от EXPLAIN?
+ Он выполняет запрос и показывает фактическое время и строки
- Он строит индекс для запроса
- Он сохраняет план в таблицу
- Он отключает планировщик
! EXPLAIN только показывает выбранный план, ANALYZE выполняет запрос и добавляет фактические измерения.

Q: Что означает loops в узле плана?
+ Сколько раз узел выполнялся
- Сколько строк вернул узел
- Сколько страниц прочитано с диска
- Сколько индексов использовано
! Время узла указано на один цикл, поэтому при loops больше единицы его умножают на число циклов.

Q: Какой узел читает все страницы таблицы?
+ Seq Scan
- Index Only Scan
- Bitmap Index Scan
- Nested Loop
! Последовательное сканирование читает таблицу целиком и не использует индекс.

Q: Что показывает строка Buffers: shared read?
+ Страницы, прочитанные с диска
- Страницы, найденные в кэше
- Временные файлы сортировки
- Число изменённых строк
! shared hit это кэш, shared read это чтение с диска.

Q: О чём говорит Sort Method: external merge Disk?
+ Сортировка не поместилась в work_mem и ушла на диск
- Сортировка выполнена в индексе
- Данные повреждены
- Запрос отменён
! Недостаток памяти заставляет сортировать во временных файлах, что заметно медленнее.

Q: Как переписать условие date_trunc('month', paid_at) = '2026-04-01' для использования индекса?
+ Заменить на диапазон paid_at >= '2026-04-01' AND paid_at < '2026-05-01'
- Добавить ORDER BY paid_at
- Заменить date_trunc на extract
- Обернуть условие в подзапрос
! Диапазон сравнивает сам столбец, поэтому индекс по paid_at применим.

Q: Что делает MATERIALIZED в объявлении CTE?
+ Запрещает встраивание и вычисляет результат отдельно
- Ускоряет любой запрос
- Создает временную таблицу на диске
- Отключает статистику
! MATERIALIZED фиксирует поведение старой версии: подзапрос выполняется как отдельный шаг.

Q: Чем плох OFFSET 100000 при пагинации?
+ Читает и отбрасывает все предыдущие строки
- Блокирует таблицу на запись
- Требует прав суперпользователя
- Удаляет старые строки
! Стоимость поздней страницы растёт вместе с её номером, поэтому используют ключевую пагинацию.

Q: Что показывает pg_stat_statements?
+ Суммарное и среднее время выполнения нормализованных запросов
- Размер таблиц и индексов
- Настройки репликации
- Права ролей
! Расширение собирает статистику по запросам и помогает найти самые тяжёлые.

Q: Какие признаки в плане указывают на проблему?
+ Оценка rows сильно расходится с actual rows
+ Seq Scan большой таблицы при точном условии
+ Sort с записью на диск
+ Nested Loop с большим числом циклов
- Index Only Scan
- Bitmap Heap Scan
! Эти признаки говорят о плохой статистике, неприменимом индексе, нехватке памяти или неудачном соединении.

Q: Какие условия можно переписать, чтобы индекс заработал?
+ Функцию над столбцом заменить диапазоном
+ Приведение столбца к тексту убрать
+ Арифметику перенести в правую часть сравнения
+ Вместо JOIN для фильтра использовать EXISTS
- Добавить SELECT *
- Увеличить OFFSET
! Условие должно сравнивать сам столбец, а не вычисленное выражение.

Q: Что помогает при неточной оценке числа строк?
+ Выполнить ANALYZE
+ Создать расширенную статистику по связанным столбцам
+ Повысить statistics target для столбца
- Отключить autovacuum
- Удалить все индексы
! Планировщик опирается на статистику, и её нужно поддерживать в актуальном виде.

Q: Как корректно сравнить запрос до и после оптимизации?
+ Снять EXPLAIN (ANALYZE, BUFFERS) до и после
+ Использовать одинаковые данные и параметры
+ Прогреть кэш и повторить замер несколько раз
- Сделать один замер на холодной базе
- Сравнивать только общее время без плана
! Сравнение имеет смысл при одинаковых условиях и с учётом буферов и оценок строк.

Q: Какая команда показывает план запроса, не выполняя его?
= EXPLAIN
= explain
! EXPLAIN строит план и оценки стоимости, но сам запрос не запускает.

Q: Какая настройка ограничивает память одной операции сортировки или хеширования?
= work_mem
= work_mem = '64MB'
! work_mem задаёт память на операцию, а не на всё соединение с базой.
