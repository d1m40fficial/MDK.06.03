## Одна идея

Отчёт о задолженностях идёт двенадцать секунд. Разработчик добавляет `LIMIT`, потом меняет `JOIN` на подзапрос, потом переписывает всё на временную таблицу. Время не меняется, потому что причина не в форме запроса: `EXPLAIN` показывает `type: ALL` по `enrollments` и `Using temporary; Using filesort`, а индекс по `student_id` просто отсутствует.

**Медленный запрос лечится планом и статистикой, а не перебором вариантов.** `EXPLAIN` показывает, что сервер собирается делать, статистика объясняет, почему он выбрал именно это, а замер до и после доказывает, что стало лучше. Без плана любая правка это лотерея.

## План запроса

`EXPLAIN` ставится перед запросом и возвращает таблицу с одной строкой на каждый шаг плана. Читать её нужно сверху вниз, но решение принимают по четырём столбцам.

| Столбец | Что показывает | На что смотреть |
|---|---|---|
| `type` | способ доступа к таблице | `ALL` и `index` подозрительны на большой таблице |
| `key` | выбранный индекс | `NULL` значит, что индекс не используется |
| `rows` | оценка числа просмотренных строк | сравнивают с числом нужных строк |
| `Extra` | дополнительные операции | `Using temporary`, `Using filesort`, `Using join buffer` |

`possible_keys` перечисляет доступные индексы, `key_len` показывает, сколько байт индекса задействовано, `filtered` даёт долю строк после условия. Оценка стоимости учитывает `rows` и `filtered`, и её оптимизатор старается уменьшить.

```sql
EXPLAIN SELECT s.full_name, COUNT(*) AS courses
FROM students s
JOIN enrollments e ON e.student_id = s.id
WHERE e.grade IS NULL
GROUP BY s.full_name;
```

`EXPLAIN` не выполняет запрос. Фактические числа даёт `EXPLAIN ANALYZE` в MySQL 8.0.18 и новее: реальное время и строки на каждом шаге. Расхождение оценки и факта говорит об устаревшей статистике. В MariaDB ту же роль играет `ANALYZE SELECT`.

## Соединения

MySQL соединяет таблицы вложенными циклами: берёт строку внешней таблицы и ищет соответствия во внутренней. Если во внутренней таблице есть индекс по столбцу соединения, поиск занимает несколько страниц. Если индекса нет, для каждой внешней строки читается вся внутренняя таблица.

```sql
CREATE INDEX idx_enroll_student ON enrollments (student_id);
```

Десять студентов и двести тысяч записей без индекса дают два миллиона чтений. С индексом это десять поисков по дереву. `EXPLAIN` в первом случае покажет `ALL`, во втором `ref`, а при уникальном ключе `eq_ref`.

Порядок соединения выбирает оптимизатор: внешней обычно становится таблица, которая сильнее сужает результат. Подсказка `STRAIGHT_JOIN` это крайняя мера, потому что она переживает данные, под которые её писали.

С MySQL 8.0.18 при равенстве без индекса работает хеш-соединение: сервер строит хеш-таблицу и помечает план `Using join buffer (hash join)`. Это лучше полного сканирования, но индекс по столбцу соединения остаётся основным приёмом.

## Сортировка и группировка

`ORDER BY` может обойтись без сортировки, если индекс уже отдаёт строки в нужном порядке. Построим составной индекс и проверим:

```sql
CREATE INDEX idx_enroll_student_date ON enrollments (student_id, enrolled_at);

SELECT enrolled_at, grade
FROM enrollments
WHERE student_id = 7
ORDER BY enrolled_at;
```

Строки студента 7 лежат в индексе подряд и упорядочены по дате, поэтому `Extra` пуст. Без условия по `student_id` порядок по дате собирается заново, и появляется `Using filesort`.

`GROUP BY` устроен похоже: группировка по началу индекса читает строки группами и не строит временную таблицу. Иначе появляются `Using temporary` и `Using filesort`, а большая временная таблица уходит на диск.

`Using filesort` не всегда приговор: сортировка двадцати строк в памяти дешевле чтения индекса. Плохо, когда она стоит на пути к сотням тысяч строк и повторяется в каждом отчёте.

## Sargable-условия

Условие называют **sargable**, если сервер может превратить его в диапазон по индексу. Функция над столбцом, арифметика над столбцом и шаблон с ведущим процентом эту возможность отнимают.

| Плохо | Хорошо | Почему |
|---|---|---|
| `WHERE YEAR(paid_at) = 2026` | `paid_at >= '2026-01-01' AND paid_at < '2027-01-01'` | функция считается для каждой строки |
| `WHERE amount * 2 > 1000` | `amount > 500` | арифметику переносят на константу |
| `WHERE title LIKE '%Информ%'` | `title LIKE 'Информ%'` | ведущий процент не даёт диапазона |
| `WHERE code = 123` при `code VARCHAR` | `WHERE code = '123'` | приведение типов превращает столбец в выражение |
| `WHERE a = 1 OR b = 2` | два запроса с `UNION ALL` | `OR` по разным столбцам редко даёт один диапазон |

Правило: слева от сравнения стоит голый столбец, справа константа или параметр. Всё, что навешено на столбец, выполняется построчно и отменяет индекс.

```sql
SELECT COUNT(*) FROM payments
WHERE paid_at >= '2026-10-01' AND paid_at < '2026-11-01';
```

Такой запрос читает по индексу только нужный месяц, а не всю таблицу платежей.

## SELECT * и лишние соединения

`SELECT *` тянет все столбцы, включая ненужные. Это лишний трафик, лишняя сборка строк и ловушка при изменении схемы: новый столбец незаметно попадает в ответ.

Главная потеря в другом. Покрывающий индекс работает только тогда, когда все нужные столбцы есть в индексе. `SELECT *` обычно выводит запрос из покрытия и заставляет сервер идти в таблицу за каждой строкой.

Лишнее соединение даёт похожий эффект: таблица, присоединённая ради неиспользуемого столбца, только размножает строки. Если после него появляется `DISTINCT`, значит соединение добавило веер строк.

```sql
SELECT DISTINCT s.full_name
FROM students s
JOIN enrollments e ON e.student_id = s.id
WHERE e.grade = 5;
```

Здесь `DISTINCT` скрывает веер: у студента несколько оценок, и он появляется столько же раз. Честнее спросить, есть ли хотя бы одна такая оценка:

```sql
SELECT s.full_name
FROM students s
WHERE EXISTS (
  SELECT 1 FROM enrollments e
  WHERE e.student_id = s.id AND e.grade = 5
);
```

`EXISTS` останавливается на первом совпадении и не размножает строки. Список столбцов внутри `EXISTS` не важен, поэтому `SELECT 1` здесь нормален, в отличие от `SELECT *` в основном запросе.

## Подзапросы

Подзапрос в `IN` MySQL 8 часто превращает в полусоединение: берёт значения и ищет совпадения по индексу. Переписывать такой план руками не нужно, а увидеть его можно по `select_type` со значением `SEMI` или шагу `Materialize`.

Опасен коррелированный подзапрос: он выполняется для каждой строки внешнего запроса:

```sql
SELECT s.full_name,
       (SELECT COUNT(*) FROM enrollments e WHERE e.student_id = s.id) AS cnt
FROM students s;
```

На десяти студентах это десять подсчётов, на тысяче тысяча. Тот же результат даёт соединение с группировкой, которое выполняется один раз. Коррелированный подзапрос в списке столбцов почти всегда переписывают.

Отдельная ловушка это `NOT IN` с `NULL` в подзапросе: сравнение даёт неизвестность, и результат пуст, хотя строки есть. `NOT EXISTS` предсказуем и обычно быстрее.

## Статистика и замер

Оптимизатор выбирает план по статистике. После массового импорта оценки устаревают, и `EXPLAIN` может показать `ALL` там, где индекс уже создан.

```sql
ANALYZE TABLE enrollments;
```

Команда пересчитывает распределение ключей. В MySQL 8 можно построить гистограмму по столбцу с неравномерными значениями:

```sql
ANALYZE TABLE payments UPDATE HISTOGRAM ON amount WITH 32 BUCKETS;
```

Гистограмма помогает там, где кардинальности мало: большинство платежей мелкие, а несколько очень крупных.

Замер делают по счётчикам сессии, а не только по секундомеру:

```sql
FLUSH STATUS;
SELECT COUNT(*) FROM enrollments WHERE grade = 5;
SHOW SESSION STATUS WHERE Variable_name IN
  ('Handler_read_key', 'Handler_read_next', 'Handler_read_rnd_next',
   'Select_scan', 'Created_tmp_disk_tables', 'Sort_merge_passes');
```

`Handler_read_rnd_next` растёт при полном сканировании, `Select_scan` считает запросы со сканом. `Created_tmp_disk_tables` и `Sort_merge_passes` показывают, что временная таблица и сортировка ушли на диск. `Innodb_rows_read` в `SHOW GLOBAL STATUS` даёт число прочитанных строк, а `Last_query_cost` оценку последнего запроса.

Медленные запросы ищут и через журнал: `slow_query_log=ON` и `long_query_time=1` записывают всё, что дольше секунды. Сводка по типам запросов лежит в `performance_schema.events_statements_summary_by_digest`, где одинаковые запросы с разными параметрами сгруппированы в один шаблон.

## Проверка до и после

Сравнение должно быть честным, иначе легко доказать что угодно.

1. **Те же данные.** Замер на копии с тем же объёмом, а не на пустой таблице.
2. **Тот же прогрев.** Первый запуск читает с диска, следующие из буферного пула. Сравнивают установившийся режим и три запуска.
3. **Тот же план.** Перед замером смотрят `EXPLAIN`: если план не изменился, время могло измениться по другой причине.
4. **Те же счётчики.** `Handler_read_rnd_next` и `Innodb_rows_read` показывают объём работы, а не только её длительность.

| Метрика | До | После |
|---|---|---|
| Время отчёта | 12,4 с | 0,08 с |
| `type` по `enrollments` | `ALL` | `range` |
| `Innodb_rows_read` | 214 000 | 1 850 |
| `Created_tmp_disk_tables` | 1 | 0 |

Такая таблица убеждает лучше фразы «стало быстрее»: изменился объём работы, а не удача с кешем.

::gate Почему запрос остаётся медленным после правки?

## Типичные ошибки

- **Смотреть только время.** Секундомер не говорит, где узкое место. Два разных плана могут дать одинаковое время на малой таблице и разойтись на большой.
- **Менять запрос без плана.** Переписывание «на глаз» часто убирает одно сканирование и добавляет два. Сначала `EXPLAIN`, потом правка, потом снова `EXPLAIN`.
- **Забыть статистику.** Индекс создан, а план прежний, потому что `ANALYZE TABLE` не запускали после импорта.
- **Оптимизировать пустую таблицу.** На десяти строках любой план быстрый, и выводы переносятся на рабочий объём без оснований.
- **Лечить `filesort` сортировкой в приложении.** Сервер отдаёт строки в другом порядке, приложение сортирует всё в памяти, и нагрузка переезжает с базы на клиент.
- **Верить `LIMIT` без `ORDER BY`.** Запрос вернёт любые строки, и сравнение времени будет бессмысленным.

> [!PITFALL] `NOT IN` и NULL
> Если в подзапросе есть хотя бы один `NULL`, `NOT IN` вернёт пустой результат. Это не ошибка MySQL, а логика трёхзначного сравнения. Для проверки отсутствия связи используют `NOT EXISTS` или добавляют условие `IS NOT NULL` по столбцу связи.

## Проверьте себя

> [!CHECK] `EXPLAIN` показывает `type: ALL`, `rows: 200000`, а нужны двадцать строк. С чего начать?
> С условий запроса и индексов: есть ли индекс по столбцам фильтра и соединения, не навешана ли на столбец функция. Затем проверить `ANALYZE TABLE` и повторить `EXPLAIN`. Только после этого менять форму запроса.

> [!CHECK] Запрос с `ORDER BY` использует индекс, но всё равно показывает `Using filesort`. Почему?
> Индекс отдаёт порядок только при равенстве по его ведущим столбцам. Если по первому столбцу стоит диапазон или условия нет, порядок по второму собирается заново. Помогает составной индекс с равенством впереди или сортировка по тому столбцу, с которого начинается индекс.

> [!CHECK] Чем `EXISTS` лучше `DISTINCT` после соединения?
> `EXISTS` проверяет наличие хотя бы одной строки и останавливается на первом совпадении, не размножая результат. `DISTINCT` сначала строит все пары соединения, а потом убирает дубли, то есть делает лишнюю работу.

## Итог

- Медленный запрос начинают с `EXPLAIN`, а не с переписывания.
- `type`, `key`, `rows` и `Extra` показывают способ доступа, индекс, объём и лишние операции.
- Индекс по столбцу соединения превращает полное сканирование в поиск, а составной индекс может убрать сортировку и временную таблицу.
- Sargable-условие оставляет столбец слева голым, а `SELECT *` и лишние соединения добавляют работу.
- Замер до и после опирается на одинаковые данные, план и счётчики, а статистику обновляют после массовых изменений.

- Handler_read_first
- Handler_read_next
! Handler_read_rnd_next считает чтения строк без индекса.

Q: Какие условия мешают использовать индекс?
+ Функция над столбцом
+ Арифметика над столбцом
+ Шаблон с ведущим процентом
+ Сравнение строкового столбца с числом
- Диапазон по голому столбцу
- Равенство по первому столбцу индекса
! Индекс теряется, когда столбец превращается в выражение.

Q: Какие шаги входят в честное сравнение до и после?
+ Одинаковые данные и объём
+ Проверка плана до и после
+ Несколько запусков и установившийся режим
+ Счётчики Handler и Innodb_rows_read
- Замер только на пустой таблице
- Один запуск на прогретом кеше
! Сравнивать нужно одинаковые условия и объём работы, а не только секунды.

Q: Какие утверждения о подзапросах верны?
+ IN часто превращается в полу соединение
+ Коррелированный подзапрос выполняется для каждой строки
+ NOT IN с NULL возвращает пустой результат
+ EXISTS останавливается на первом совпадении
- Подзапрос всегда быстрее соединения
- NOT IN безопасен при NULL
! Форма подзапроса влияет на план, а NULL ломает логику NOT IN.

Q: Что показывает Last_query_cost?
+ Оценку стоимости последнего запроса
- Точное время последнего запроса
- Число строк в таблице
- Размер буферного пула
! Это оценка оптимизатора, а не измеренное время.

Q: Какая команда показывает план выполнения запроса?
= EXPLAIN
= explain
! EXPLAIN выводит план, а EXPLAIN ANALYZE ещё и выполняет запрос.

Q: Какой счётчик показывает чтения строк без использования индекса?
= Handler_read_rnd_next
= handler_read_rnd_next
! Рост этого счётчика означает полное сканирование таблицы.
