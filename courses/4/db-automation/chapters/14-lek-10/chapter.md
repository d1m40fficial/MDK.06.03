## Одна идея

На курс осталось одно место. Двое студентов нажимают «Записаться» в одну и ту же секунду. Приложение каждого сначала считает свободные места запросом, видит единицу, потом вставляет строку в `enrollments`. Если база выполнит обе вставки независимо, на курс попадут двое, а мест было одно.

**Транзакция** это единица работы, которая применяется целиком или не применяется вовсе. **Блокировка** это очередь: пока одна транзакция меняет строку, вторая ждёт или получает отказ. Одно без другого не работает. Транзакция без блокировки не мешает двоим перезаписать одно значение, а блокировка без транзакции держится до конца отдельной команды и не даёт откатить группу изменений.

В MySQL за то и другое отвечает InnoDB. Дальше речь о двух вещах сразу, потому что на практике они неразделимы: как оформить группу команд в транзакцию и как понять, кто кого ждёт, когда запрос завис.

## Что обещает ACID

Четыре свойства транзакции отвечают на четыре вопроса администратора.

| Свойство | Что гарантирует | Что случится без него |
|---|---|---|
| Атомарность | все команды применяются или ни одна | после сбоя останется половина оплаты |
| Согласованность | ограничения выполнены к моменту фиксации | в таблице появится оценка 7 или дубль |
| Изолированность | параллельные транзакции не видят чужой незавершённой работы | двое прочитают одно и то же место |
| Долговечность | зафиксированное переживает сбой питания | после перезапуска пропадут платежи |

Разберём на базе `dean`. Студент оплачивает курс: в `payments` появляется строка, в `enrollments` меняется оценка. Для деканата это одна операция. Атомарность не даст базе остановиться между двумя командами. Согласованность означает, что к моменту `COMMIT` работают внешние ключи и проверка `grade BETWEEN 2 AND 5`. Изолированность не покажет бухгалтеру платёж, который деканат ещё не подтвердил. Долговечность означает, что после ответа `COMMIT` данные уже в redo-журнале и переживут выключение компьютера.

> [!KEY]
> `COMMIT` это точка, после которой работа считается завершённой. Всё остальное InnoDB делает сама через журналы.

## Как выглядит транзакция

Транзакция начинается с `START TRANSACTION` и заканчивается `COMMIT` или `ROLLBACK`. Между ними работает обычный SQL, но его результаты видит только эта сессия.

```sql
START TRANSACTION;
UPDATE courses SET hours = hours + 8 WHERE id = 3;
INSERT INTO enrollments (student_id, course_id, grade) VALUES (7, 3, 4);
COMMIT;
```

Если вторая команда оказалась лишней, её место занимает `ROLLBACK`, и таблицы возвращаются к состоянию до `START TRANSACTION`. Откат возможен потому, что InnoDB пишет старые версии строк в undo-журнал: `ROLLBACK` не отменяет изменения, а восстанавливает прежние версии.

### Savepoint: откат части работы

Иногда нужно отменить не всю транзакцию, а последний шаг. Для этого служит `SAVEPOINT`: он ставит метку внутри транзакции, к которой можно вернуться.

```sql
START TRANSACTION;
UPDATE courses SET hours = hours + 8 WHERE id = 3;
SAVEPOINT after_course;
INSERT INTO enrollments (student_id, course_id, grade) VALUES (7, 3, 4);
ROLLBACK TO SAVEPOINT after_course;
INSERT INTO enrollments (student_id, course_id, grade) VALUES (7, 3, 5);
COMMIT;
```

После `ROLLBACK TO SAVEPOINT` первое изменение остаётся, а неудачная вставка исчезает. Метку можно снять явно через `RELEASE SAVEPOINT`, хотя `COMMIT` делает это сам.

Здесь MySQL ведёт себя иначе, чем многие ожидают. Ошибка в команде отменяет только эту команду, а транзакция остаётся открытой. Опечатка в имени таблицы не требует начинать заново: исправленный запрос выполняется в той же транзакции, а `ROLLBACK TO SAVEPOINT` убирает часть работы.

## Уровни изоляции MySQL

Когда транзакций две и больше, база должна решить, что каждая из них видит. Это решение задаёт **уровень изоляции**. Чем он строже, тем меньше странностей видит запрос и тем больше работы у сервера.

Сначала назовём аномалии, от которых защищаются уровни.

- **Грязное чтение.** Транзакция видит строку, которую другая ещё не зафиксировала и может откатить.
- **Неповторяющееся чтение.** Два одинаковых `SELECT` внутри одной транзакции возвращают разные значения.
- **Фантом.** Повторный запрос возвращает новый набор строк, потому что кто-то вставил запись.
- **Потерянное обновление.** Двое прочитали одно значение, каждый прибавил своё, последняя запись затёрла первую.

| Уровень | Что видит транзакция | Когда применять |
|---|---|---|
| READ UNCOMMITTED | незафиксированные изменения других сессий | почти никогда |
| READ COMMITTED | свежий снимок на каждую команду | экранные формы и короткие операции |
| REPEATABLE READ | один снимок на всю транзакцию | отчёты и расчёты по нескольким таблицам |
| SERIALIZABLE | чтение берёт разделяемые блокировки | денежные операции и строгие правила |

По умолчанию в MySQL и MariaDB стоит **REPEATABLE READ**. Это не случайность: для InnoDB такой уровень дешевле, чем кажется, потому что чтение идёт по снимку, без блокировок.

```sql
SELECT @@transaction_isolation;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

В MariaDB из XAMPP та же настройка называется `tx_isolation`, поэтому перед проверкой стоит выполнить `SELECT @@version;` и выбрать нужное имя переменной.

Важная деталь: снимок создаётся не в момент `START TRANSACTION`, а при первой команде чтения. Если между началом транзакции и первым `SELECT` другая сессия успела зафиксировать изменение, оно попадёт в снимок. Для администратора это значит, что «транзакция видит состояние на момент старта» не совсем точно.

## Неповторяющееся чтение и фантом

Проследим на числах. В базе `dean` двадцать записей в `enrollments`. Сессия A начинает транзакцию и считает строки по курсу 3, получает 8. Тем временем сессия B добавляет девятую запись и фиксирует её. Сессия A повторяет тот же `SELECT`.

При `READ COMMITTED` второй запрос берёт новый снимок и вернёт 9: это неповторяющееся чтение. При `REPEATABLE READ` второй запрос увидит тот же снимок и вернёт 8, хотя в таблице уже девять строк. Для отчёта это хорошо: все его шаги смотрят на одно состояние.

```sql
START TRANSACTION;
SELECT COUNT(*) FROM enrollments WHERE course_id = 3;
SELECT COUNT(*) FROM enrollments WHERE course_id = 3;
COMMIT;
```

С фантомом та же картина, но речь о наборе строк, а не о значении. Запрос «студенты без оценки по курсу 3» при повторном выполнении может вернуть новую строку, которой в первом ответе не было.

Разница между уровнями видна и в блокировках. В `REPEATABLE READ` InnoDB блокирует не только найденные строки, но и промежутки между ними, поэтому вставка нового значения в диапазон ждёт. Это **next-key lock**. В `READ COMMITTED` промежутки не блокируются, зато фантом при повторном чтении возможен.

`SERIALIZABLE` идёт дальше: обычный `SELECT` превращается в чтение с разделяемой блокировкой, и параллельная вставка в тот же диапазон ждёт завершения транзакции. Результат эквивалентен последовательному выполнению, но пропускная способность падает.

> [!TRADEOFF] Строгость и очередь
> Повышение уровня изоляции убирает аномалии, но добавляет ожидания и ошибки сериализации. Начинают с умолчания, а уровень меняют там, где конкретная операция требует большего: денежный перевод, распределение мест, нумерация документов.

Потерянное обновление уровнем изоляции не лечится. Его причина в схеме «прочитать, посчитать в приложении, записать». Правильное решение: считать в базе одной командой `UPDATE courses SET hours = hours + 8 WHERE id = 3`, либо взять строку под блокировку заранее.

```sql
SELECT id, hours FROM courses WHERE id = 3 FOR UPDATE;
SELECT id, hours FROM courses WHERE id = 3 FOR SHARE;
```

`FOR UPDATE` ставит исключительную блокировку, `FOR SHARE` разделяемую: читать можно многим, менять нельзя никому до фиксации.

## Блокировки строк и таблиц

InnoDB блокирует не «строку вообще», а запись в индексе. Если условие не опирается на индекс, сервер просматривает таблицу целиком и блокирует всё просмотренное.

```sql
UPDATE students SET email = 's7@example.ru' WHERE full_name = 'Иванов Иван';
```

Столбец `full_name` в схеме `dean` не индексирован. В `REPEATABLE READ` такая команда заблокирует все строки таблицы, и параллельная запись встанет в очередь. С индексом по `full_name` заблокированы были бы только подходящие записи и промежуток вокруг них.

Виды блокировок, которые важно различать:

- **Запись (record lock)** держит конкретную индексную запись.
- **Промежуток (gap lock)** держит пространство между двумя записями и мешает вставке.
- **Next-key lock** объединяет запись и промежуток перед ней; это обычная блокировка InnoDB в `REPEATABLE READ`.
- **Намерение вставки (insert intention)** показывает, что транзакция собирается вставить строку в промежуток.
- **Разделяемая и исключительная (S и X)** различаются тем, разрешают ли они другим читать или менять запись.
- **Метаданные (MDL)** защищают структуру таблицы: пока идёт `ALTER TABLE`, запросы к таблице ждут, и наоборот.

Табличные блокировки InnoDB ставит как намерения (`IS`, `IX`), а не как запрет на всю таблицу. Отдельный `LOCK TABLES` в InnoDB нужен редко: команда, которая обошла индексы, и без него блокирует все просмотренные строки.

## Где смотреть, кто кого ждёт

Первая команда при разборе зависания это `SHOW ENGINE INNODB STATUS`. Она отдаёт текстовый отчёт с разделами о последней взаимной блокировке, активных транзакциях и ожиданиях.

```sql
SHOW ENGINE INNODB STATUS\G
```

В отчёте ищите раздел `LATEST DETECTED DEADLOCK`: там записаны обе транзакции, их последние команды и строка, из-за которой возник цикл. Раздел `TRANSACTIONS` показывает, кто держит блокировки и сколько строк уже изменил.

Второй источник это таблица активных транзакций. Она отвечает на вопрос «что сейчас открыто и как давно».

```sql
SELECT trx_id,
       trx_state,
       trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_s,
       trx_rows_locked,
       trx_rows_modified,
       trx_mysql_thread_id,
       trx_query
FROM information_schema.INNODB_TRX
ORDER BY trx_started;
```

Столбец `age_s` важнее остальных: транзакция, которая живёт двадцать минут и изменила одну строку, почти всегда означает забытый `COMMIT` в приложении или в консоли.

Третий источник это таблицы ожиданий. Они показывают пару «кто просит» и «кто держит».

```sql
SELECT w.requesting_trx_id,
       w.blocking_trx_id,
       l.lock_table,
       l.lock_index,
       l.lock_mode,
       l.lock_data
FROM information_schema.INNODB_LOCK_WAITS AS w
JOIN information_schema.INNODB_LOCKS AS l
  ON l.lock_id = w.requested_lock_id;
```

В MariaDB из XAMPP эти таблицы есть. В MySQL 8 их убрали, и те же сведения лежат в `performance_schema.data_locks` и `performance_schema.data_lock_waits`. Смысл столбцов тот же: `lock_table`, `lock_index`, `lock_mode` и данные записи.

## Deadlock

Взаимная блокировка возникает, когда две транзакции берут одни и те же ресурсы в разном порядке. Сессия A меняет студента 1, потом студента 2. Сессия B делает наоборот.

```sql
START TRANSACTION;
UPDATE students SET email = 'a1@example.ru' WHERE id = 1;
UPDATE students SET email = 'a2@example.ru' WHERE id = 2;
COMMIT;
```

```sql
START TRANSACTION;
UPDATE students SET email = 'b2@example.ru' WHERE id = 2;
UPDATE students SET email = 'b1@example.ru' WHERE id = 1;
COMMIT;
```

A держит строку 1 и ждёт строку 2, B держит строку 2 и ждёт строку 1. Цикл не разорвётся сам, поэтому InnoDB его находит и откатывает одну транзакцию целиком. Вторая продолжает работу. Приложение получает ошибку 1213 `Deadlock found when trying to get lock; try restarting transaction`.

Это не сбой базы, а штатная защита. Лечится она тремя приёмами: брать строки в одном порядке во всех операциях, держать транзакции короткими и повторять операцию после ошибки 1213. Повтор обязателен: без него пользователь увидит отказ там, где достаточно было попробовать ещё раз.

## Долгие транзакции и innodb_lock_wait_timeout

Ожидание блокировки не бесконечно. Параметр `innodb_lock_wait_timeout` задаёт предел в секундах, по умолчанию 50.

```sql
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
SET SESSION innodb_lock_wait_timeout = 5;
```

Когда предел истекает, команда падает с ошибкой 1205 `Lock wait timeout exceeded; try restarting transaction`, а транзакция остаётся открытой. Для экранной формы пятьдесят секунд ожидания бессмысленны: пользователь уже ушёл. Разумнее поставить несколько секунд и показать понятное сообщение.

Долгая транзакция дорога не только ожиданием. Пока она открыта, undo-журнал растёт, очистка старых версий отстаёт, а `ALTER TABLE` ждёт метаданных и блокирует очередь запросов. На реплике такая транзакция задерживает применение изменений.

Завершить зависшую работу можно двумя командами. `KILL QUERY` прерывает текущий запрос, но оставляет соединение. `KILL` закрывает соединение целиком и откатывает его транзакцию.

```sql
KILL QUERY 42;
KILL 42;
```

Номер соединения берут из `trx_mysql_thread_id` или из `SHOW PROCESSLIST`.

## Типичные ошибки

- **Транзакция вокруг ожидания пользователя.** Приложение открывает транзакцию, читает строку, показывает форму и ждёт ввода. Строка заблокирована всё это время, а `COMMIT` придёт через минуты. Транзакцию открывают после ввода и держат только на время команд.
- **Нет таймаута.** Запрос ждёт пятьдесят секунд по умолчанию и всё равно падает. На экранных операциях ставят короткий `innodb_lock_wait_timeout` и повторяют попытку.
- **Забытый `COMMIT` в консоли.** После `SET autocommit = 0` сессия держит блокировки до закрытия окна. `SHOW PROCESSLIST` показывает `Sleep`, а таблица при этом заблокирована.
- **DDL внутри транзакции.** `ALTER TABLE` и `CREATE TABLE` вызывают неявную фиксацию. Миграция не откатывается одной транзакцией, поэтому нужен обратный скрипт и копия.
- **`SELECT ... FOR UPDATE` без индекса.** Блокируются все просмотренные строки, а не одна. Условие должно опираться на индекс.
- **Нет повтора после 1213.** Взаимная блокировка это сигнал «повтори», а не повод показать ошибку пользователю.

> [!PITFALL] Проверка «на своей машине»
> В одиночной сессии конфликтов не бывает, поэтому ошибки блокировок всплывают только на групповой работе. Проверять транзакции нужно в двух окнах `mysql` одновременно, иначе поведение кажется идеальным.

## Проверьте себя

> [!CHECK] Транзакция прочитала строку, а потом ждала ввода две минуты. Что увидят другие сессии?
> Строка останется заблокированной до `COMMIT` или `ROLLBACK`, если чтение шло через `FOR UPDATE` или строка уже менялась. Обычный `SELECT` в `REPEATABLE READ` блокировок не ставит, поэтому конфликт возникает не от чтения, а от записи и блокирующего чтения.

> [!CHECK] Почему `REPEATABLE READ` не спасает от потерянного обновления?
> Уровень изоляции управляет видимостью, а не последовательностью «прочитать, посчитать, записать». Оба приложения читают одно значение и записывают результат, и последняя запись затирает первую. Помогает атомарная команда `UPDATE` или блокировка строки через `FOR UPDATE`.

> [!CHECK] Запрос упал с ошибкой 1205. Транзакция закрылась?
> Нет. Истёк таймаут ожидания, команда отменена, но транзакция осталась открытой и держит то, что успела изменить. Её нужно завершить через `COMMIT` или `ROLLBACK`, иначе блокировки останутся.

## Итоги

- Транзакция применяется целиком или не применяется, а блокировка решает, кто меняет строку.
- `START TRANSACTION`, `COMMIT`, `ROLLBACK` и `SAVEPOINT` задают границы работы.
- По умолчанию MySQL работает на `REPEATABLE READ` со снимком на первую команду чтения.
- InnoDB блокирует индексные записи и промежутки, а не строки «вообще».
- `SHOW ENGINE INNODB STATUS` и `INNODB_TRX` показывают, кто кого ждёт.
- Взаимная блокировка лечится порядком захвата, короткими транзакциями и повтором.

## Тест по лекции

::quiz
Q: Что гарантирует атомарность транзакции?
+ Все команды применяются вместе или не применяются вовсе
- Зафиксированные данные переживают сбой питания
- Параллельные транзакции не видят чужих изменений
- Ограничения проверяются при каждом чтении
! Атомарность не даёт базе остановиться на половине работы.

Q: Какая команда фиксирует изменения транзакции?
+ COMMIT
- ROLLBACK
- SAVEPOINT
- START TRANSACTION
! COMMIT завершает транзакцию и делает изменения видимыми другим сессиям.

Q: Какой уровень изоляции MySQL использует по умолчанию?
+ REPEATABLE READ
- READ UNCOMMITTED
- READ COMMITTED
- SERIALIZABLE
! InnoDB по умолчанию работает на REPEATABLE READ и читает по снимку.

Q: Что означает ошибка 1213 в MySQL?
+ Взаимная блокировка, одну из транзакций откатили
- Превышено время ожидания блокировки
- Неверный пароль пользователя
- Дубликат уникального ключа
! Код 1213 это deadlock, после него операцию повторяют.

Q: Что делает ROLLBACK TO SAVEPOINT?
+ Отменяет команды после метки и оставляет транзакцию открытой
- Закрывает соединение с базой
- Фиксирует часть работы до метки
- Удаляет метку вместе со всей транзакцией
! Откат к метке возвращает состояние на момент SAVEPOINT.

Q: Какая настройка задаёт предел ожидания блокировки в секундах?
+ innodb_lock_wait_timeout
- wait_timeout
- lock_wait_timeout
- innodb_flush_log_at_trx_commit
! По умолчанию предел равен 50 секундам, его меняют на уровне сессии.

Q: Где видно активные транзакции и их длительность?
+ information_schema.INNODB_TRX
- information_schema.TABLES
- mysql.user
- performance_schema.setup_instruments
! В INNODB_TRX есть время старта, число заблокированных строк и текст запроса.

Q: Что произойдёт с транзакцией при выполнении ALTER TABLE?
+ Изменения зафиксируются неявно, транзакция завершится
- Транзакция продолжит работу и откатится целиком
- ALTER TABLE выполнится только после COMMIT
- База вернёт ошибку синтаксиса
! DDL в MySQL вызывает неявную фиксацию, поэтому миграцию откатывают скриптом.

Q: Что делает KILL QUERY?
+ Прерывает текущий запрос и оставляет соединение открытым
- Закрывает соединение и откатывает транзакцию
- Снимает все блокировки таблицы
- Перезапускает сервер MySQL
! KILL без слова QUERY закрывает соединение целиком.

Q: Какие аномалии устраняет REPEATABLE READ в InnoDB?
+ Неповторяющееся чтение при обычном чтении
+ Грязное чтение
+ Фантом для блокирующего чтения диапазона
- Потерянное обновление при схеме «прочитать и записать»
! Снимок на транзакцию убирает разные ответы на один запрос, но не лечит логику чтения и записи.

Q: Какие причины приводят к взаимной блокировке?
+ Разный порядок захвата одних и тех же строк
+ Долгие транзакции, которые держат строки
+ Условие без индекса, из-за которого блокируются лишние строки
- Использование COMMIT после каждой команды
! Цикл возникает, когда транзакции берут ресурсы в противоположном порядке.

Q: Что помогает сократить ожидания на блокировках?
+ Держать транзакцию короткой
+ Задавать короткий innodb_lock_wait_timeout для экранных операций
+ Повторять операцию после ошибки 1213
- Открывать транзакцию до ввода пользователя
! Короткая транзакция освобождает строки быстро, а повтор переживает редкий конфликт.

Q: Что показывает SHOW ENGINE INNODB STATUS?
+ Раздел LATEST DETECTED DEADLOCK с командами обеих транзакций
+ Список активных транзакций и их блокировок
+ Ожидания одной транзакции на блокировке другой
- Содержимое таблиц базы dean
! Отчёт описывает последнюю взаимную блокировку и текущие транзакции.

Q: Какая команда начинает транзакцию в MySQL?
= START TRANSACTION
= BEGIN
! START TRANSACTION и BEGIN открывают явную транзакцию.

Q: Какой код ошибки возвращает MySQL при взаимной блокировке?
= 1213
= Deadlock found when trying to get lock
! InnoDB откатывает одну из транзакций и возвращает ошибку 1213.

::/gate
