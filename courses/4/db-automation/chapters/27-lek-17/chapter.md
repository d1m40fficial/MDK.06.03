## Сорок минут блокировки

В понедельник выпустили миграцию: новый столбец и индекс к нему. Столбец добавился за миллисекунды, индекс на таблице `enrollments` строился сорок минут, и всё это время таблица не принимала записи. Очередь запросов росла, приложение начало отдавать ошибки по таймауту, а миграция при этом считалась успешной: скрипт завершился без ошибки.

**Миграция** это изменение схемы на работающей базе с сохранением данных. У неё три требования, и все три обязательны. Изменение должно быть **предсказуемым**: заранее известно, сколько оно займёт и какие блокировки возьмёт. Оно должно быть **обратимым**: есть способ вернуть схему в прежнее состояние. И оно должно быть **проверяемым**: после запуска можно доказать, что данные на месте, а схема соответствует замыслу.

Схема это тоже код. У неё есть версия, история изменений и автор. Пока схему меняют вручную через `psql`, версии не существует, и два администратора, запустившие разные команды, получают две разные базы с одинаковым именем.

> [!KEY]
> Миграция это не «выполнить ALTER». Это выпуск изменения: версия, прямой скрипт, обратный скрипт, проверка на копии и порядок отката.

## Версия схемы

Версию хранят в самой базе, в отдельной таблице. Каждая применённая миграция оставляет в ней строку.

```sql
create table schema_version (
  version int primary key,
  name text not null,
  applied_at timestamptz not null default now()
);
```

Файлы миграций нумеруют по порядку: `001_add_phone.up.sql`, `002_students_email_index.up.sql`. Номер задаёт порядок, имя объясняет смысл. Применённая миграция никогда не переписывается: если в ней нашлась ошибка, выпускают следующую, которая её исправляет.

Одной строки «текущая версия» недостаточно. История показывает, что и когда применялось, и позволяет ответить на вопрос, почему база на стенде отличается от базы на рабочем сервере. Полезно хранить и контрольную сумму файла: тогда правка уже применённой миграции становится заметной.

Номер версии растёт монотонно, а пропуски недопустимы: если `003` применили раньше `002`, база окажется в состоянии, которого не описывает ни один файл.

```sql
alter table schema_version add column checksum text;
```

Те же идеи лежат в готовых инструментах миграций: Flyway, Liquibase, Alembic. Для учебной базы достаточно скрипта и таблицы версий, но принципы те же.

Расхождение схем это отдельная проблема. На стенде миграцию применили вручную, на рабочем сервере забыли, и приложение работает по-разному в двух местах. Таблица версий делает расхождение видимым: достаточно сравнить две строки. Поэтому миграции применяют только скриптами, а не командами из истории оболочки, и сверяют версию перед выпуском приложения.

## Прямой и обратный скрипт

У каждой миграции два файла. Прямой переводит схему из версии `N` в `N+1`, обратный возвращает из `N+1` в `N`.

```sql
-- 001_add_phone.up.sql
alter table students add column phone text;
```

```sql
-- 001_add_phone.down.sql
alter table students drop column phone;
```

Обратный скрипт пишут и проверяют **до** запуска прямого. Причина проста: во время инцидента думать некогда, а придумывать откат под давлением пользователей почти невозможно. Если откат написан заранее, он уже проверен на копии и запускается одной командой.

> [!PITFALL] Откат схемы не откатывает данные
> Обратный скрипт возвращает структуру, но не возвращает значения. Если миграция заполнила новый столбец, а потом он удаляется, заполненные данные исчезают. Поэтому перед миграцией, которая меняет или переносит данные, делают копию, а не надеются на `down.sql`.

Не всякое изменение обратимо. Удаление столбца теряет данные безвозвратно, слияние двух столбцов в один не восстанавливает исходное распределение. В таких случаях вместо отката планируют **исправляющую миграцию**: новую версию, которая приводит схему к нужному виду. Это честнее, чем делать вид, что откат возможен.

Обратный скрипт проверяют на копии так же, как прямой. Применили миграцию, применили откат, сравнили схему с исходной и убедились, что приложение снова работает. Откат, который ни разу не запускали, считается несуществующим.

## Транзакционный DDL

PostgreSQL поддерживает изменение схемы внутри транзакции. Если команда упала, откатывается вся транзакция, и база остаётся в прежнем состоянии.

```sql
begin;
alter table students add column phone text;
alter table students add constraint students_phone_len
  check (length(phone) <= 20);
commit;
```

Это большое преимущество: половина применённой миграции не остаётся в базе. Но не всё можно выполнить в транзакции. `create index concurrently`, `vacuum`, `create database` и `alter system` работают вне транзакционного блока. Если поместить их внутрь, сервер вернёт ошибку.

Поэтому инструмент миграций должен знать, где ставить границы транзакции. Практическое правило: одна миграция это одна логическая операция, и если в ней есть `concurrently`, транзакцию вокруг неё не открывают.

Отдельная тонкость это `create index concurrently`. Он не блокирует запись, но при сбое оставляет индекс в состоянии `invalid`, который занимает место и не используется планировщиком. Такой индекс удаляют и строят заново, поэтому команду запускают отдельной миграцией, чтобы её результат был виден в журнале и в версии схемы.

## Блокировки и окно обслуживания

Почти каждое изменение схемы берёт блокировку `ACCESS EXCLUSIVE`: пока идёт `alter table`, таблицу нельзя ни читать, ни менять. `create index` без `concurrently` берёт `SHARE`: читать можно, писать нельзя.

Опаснее всего не сама блокировка, а очередь. Если `alter table` ждёт долгий `select`, то все новые запросы встают за `alter` и тоже ждут, даже те, которым нужна только одна строка.

Отсюда главный приём безопасного изменения схемы:

```sql
set lock_timeout = '3s';
set statement_timeout = '30s';
alter table students add column phone text;
```

Если блокировку не удалось взять за три секунды, команда завершается ошибкой и ничего не ломает. Её повторяют позже, когда долгий запрос закончился. Без `lock_timeout` миграция может ждать часами, а вместе с ней ждёт вся база.

Перед запуском полезно посмотреть, кто держит таблицу, и не начинать, пока в базе есть долгая транзакция.

```sql
select pid, state, now() - xact_start as tx_age, left(query, 60) as query
from pg_stat_activity
where xact_start is not null
order by tx_age desc
limit 5;
```

Отдельно учитывают реплики. Изменение схемы передаётся через журнал предзаписи, и долгая перезапись таблицы задерживает применение на ведомых узлах. Если ведомый используется для чтения, отставание на время миграции может стать заметным, и это тоже часть плана.

Иногда без окна обслуживания не обойтись. Смена типа столбца с перезаписью таблицы, массовая чистка, восстановление из копии требуют остановки записи. Тогда окно объявляют заранее, приложение переводят в режим только чтения, а после работ проверяют данные и снимают режим.

## Добавление колонки

Простое добавление столбца в PostgreSQL почти бесплатно: меняется только каталог, файлы таблицы не переписываются. Столбец с постоянным значением по умолчанию тоже добавляется быстро, начиная с версии 11 значение хранится отдельно и подставляется при чтении.

Проблемы начинаются в двух случаях. Первый это изменчивое значение по умолчанию вроде `now()` или `random()`: оно вычисляется для каждой строки, и таблица переписывается целиком. Второй это `not null` на столбце, где уже есть пустые значения: сервер обязан проверить все строки.

Безопасный порядок такой: сначала добавить столбец без ограничения, потом заполнить его порциями, потом навесить ограничение.

Значение по умолчанию выбирают осторожно. Постоянная строка или число подставляются без перезаписи, а выражение, зависящее от времени или случайности, заставляет сервер вычислить его для каждой строки. Если нужно именно такое значение, столбец добавляют пустым, заполняют порциями и уже потом задают `default` для новых строк.

```sql
alter table students add column phone text;
```

## Заполнение порциями

Заполнение миллионов строк одной командой создаёт миллионы мёртвых строк, раздувает таблицу, пишет огромный объём журнала и держит блокировки до конца. Поэтому данные заливают порциями, с паузами и с возможностью повторить запуск.

```sql
do $$
declare
  max_id int;
  cur int := 0;
  step int := 1000;
begin
  select max(id) into max_id from students;
  while cur < max_id loop
    update students
       set phone = 'не указан'
     where id > cur and id <= cur + step
       and phone is null;
    cur := cur + step;
    perform pg_sleep(0.05);
  end loop;
end $$;
```

Условие `phone is null` делает операцию идемпотентной: повторный запуск не тронет уже заполненные строки. Пауза даёт автовакууму и реплике догнать изменения. Размер порции подбирают по нагрузке: тысяча строк это отправная точка, а не правило.

За ходом следят по числу оставшихся пустых значений и по отставанию реплики. Если отставание растёт, паузу увеличивают.

## Ограничения без долгой блокировки

Обычное добавление `not null` или внешнего ключа проверяет все строки под сильной блокировкой. Для большой таблицы это простой. Обходной путь стандартный: сначала объявить ограничение как `not valid`, потом проверить его отдельной командой.

```sql
alter table students
  add constraint students_phone_nn check (phone is not null) not valid;

alter table students validate constraint students_phone_nn;
```

Первая команда выполняется мгновенно: она только регистрирует правило и не смотрит на данные. Вторая читает таблицу, но берёт слабую блокировку, при которой чтение и запись продолжаются.

Начиная с версии 12 проверенное ограничение `check` позволяет команде `alter column ... set not null` не перечитывать таблицу: сервер доверяет уже проверенному условию.

Типичная ошибка новичка это сделать всё в одном выпуске: добавить столбец, перенести данные, переключить чтение и удалить старый. В момент выпуска часть узлов ещё работает по старому коду, и он падает, потому что столбца больше нет.

Совместимость касается не только столбцов. Новое ограничение `not null` ломает старый код, который вставляет строки без этого поля. Поэтому ограничение вводят после того, как все узлы научились заполнять поле, иначе выпуск превращается в гонку между версиями.

::gate Что проверять после миграции?

## Порядок выпуска

Порядок действий фиксируют заранее, чтобы в момент работ не импровизировать.

1. **Проверить на копии.** Восстановить копию рабочей базы, применить миграцию, замерить время и блокировки, прогнать проверки приложения.
2. **Сделать свежую копию.** Миграция меняет схему, и откат данных возможен только из копии.
3. **Проверить обстановку.** Убедиться, что нет долгих транзакций и запросов, которые держат таблицу.
4. **Применить с `lock_timeout`.** Короткий таймаут превращает ожидание в ошибку, которую безопасно повторить.
5. **Проверить результат.** Сверить число строк, ограничения, планы запросов.
6. **Понаблюдать.** Посмотреть ошибки приложения, время ответа, отставание реплики.
7. **Записать версию.** Строка в `schema_version` появляется только после успешной проверки.

Проверка на копии отвечает на вопрос, который нельзя задать рабочей базе: сколько времени займёт изменение и что оно сломает. Копия должна быть по объёму такой же, как рабочая, иначе замеры ничего не значат.

У выпуска есть условие отката, и его формулируют до начала работ. Например: если время ответа выросло вдвое или появились ошибки ограничений, применяем обратный скрипт и останавливаем выпуск. Условие, придуманное по ходу, обычно звучит как «подождём ещё немного», и этим база живёт до утра.

## Проверка данных

После миграции проверяют не только отсутствие ошибки, но и результат. Скрипт завершился успешно, а данные могли потеряться: например, условие переноса не покрыло часть строк.

```sql
select count(*) as total,
       count(*) filter (where phone is null) as empty
from students;

select conname, convalidated
from pg_constraint
where conrelid = 'students'::regclass;
```

Первый запрос сравнивают с числом строк до миграции. Второй показывает, что ограничения не только объявлены, но и проверены: `convalidated = false` означает, что правило зарегистрировано, но данные под него ещё не сверяли.

Если миграция переносила значения, сверяют контрольные суммы по столбцу или выборочно сравнивают несколько строк с копией. Отдельно смотрят планы запросов: новый индекс может не использоваться, а старый, который убрали, мог быть нужен для быстрой выборки.

Проверку повторяют на ведомом узле: если данные пришли туда с отставанием, число строк там временно меньше. Это не ошибка миграции, но повод не запускать следующую, пока реплика не догнала ведущий.

::/gate

::gate Какие ошибки делают миграцию опасной?

## Типичные ошибки

- **Нет обратного скрипта.** Откат придумывают в момент аварии, когда думать некогда, и обычно он не работает.
- **DDL в час пик.** Изменение схемы запускают тогда, когда нагрузка максимальна, и простой замечают все.
- **Заполнение одной транзакцией.** Миллионы строк в одном `update` раздувают таблицу, журнал и блокировки.
- **Забыли ограничения.** Столбец добавили, данные залили, а `not null` и внешний ключ не поставили, и в базе остались пустые значения.
- **Удаление столбца в том же выпуске.** Старый код на части узлов обращается к столбцу, которого уже нет.
- **Правка применённой миграции.** Файл изменили, а база уже прошла эту версию, и контрольная сумма перестала совпадать.

## Проверьте себя

> [!CHECK] Почему create index без concurrently блокирует запись, а с concurrently нет?
> Обычное построение индекса берёт блокировку `SHARE`: читать таблицу можно, а вставлять, изменять и удалять нельзя, пока индекс не построен. `concurrently` строит индекс в несколько проходов по слабой блокировке и не мешает записи, но занимает больше времени и при сбое оставляет недействительный индекс, который нужно удалить и построить заново.

> [!CHECK] Миграция добавляет not null, но в таблице есть строки с пустым значением. Что делать?
> Сначала заполнить пустые значения, потом ставить ограничение. Можно пойти безопасным путём: добавить `check (phone is not null) not valid`, заполнить данные порциями, проверить ограничение командой `validate constraint` и только затем ставить `not null`. Отключать проверку данных ради прохождения миграции нельзя: это переносит ошибку в базу.

> [!CHECK] Зачем нужен lock_timeout, если миграция всё равно выполнится?
> Без таймаута изменение может ждать блокировку неограниченно долго, а все запросы, вставшие за ним, ждут вместе с ним. Короткий таймаут превращает ожидание в ошибку, которую безопасно повторить позже, и не даёт одному изменению схемы остановить всю базу.

## Итог

- Миграция это выпуск изменения: версия, прямой скрипт, обратный скрипт и проверка.
- Версия схемы хранится в таблице, а применённые файлы не переписываются.
- Обратный скрипт пишут заранее, но помнят, что он возвращает схему, а не данные.
- Блокировки опасны очередью, поэтому изменения делают с коротким `lock_timeout`.
- Большую таблицу меняют в три шага: добавить, заполнить порциями, ограничить.
- Старый и новый код должны работать одновременно, поэтому схему расширяют, переключают и только потом сжимают.

## Тест по лекции

::quiz
Q: Что такое миграция схемы?
+ Изменение структуры базы на работающих данных без их потери
- Полная переустановка сервера базы данных
- Копирование всех таблиц в другой файл
- Удаление старых журналов сервера
! Миграция меняет схему, сохраняя данные и работу приложения.

Q: Какие требования предъявляют к миграции?
+ Предсказуемость по времени и блокировкам
+ Возможность вернуть схему в прежнее состояние
+ Проверяемость результата
- Обязательное выполнение в час пик
- Отсутствие обратного скрипта
! Миграция должна быть предсказуемой, обратимой и проверяемой.

Q: Зачем нужна таблица schema_version?
+ Чтобы хранить историю применённых миграций
- Чтобы ускорить выполнение запросов
- Чтобы заменить резервную копию
- Чтобы хранить пароли ролей
! История версий показывает, что и когда применялось к базе.

Q: Когда пишут обратный скрипт миграции?
+ До запуска прямого скрипта
- После аварии на рабочей базе
- Только если миграция упала
- Вместо прямого скрипта
! Обратный скрипт готовят и проверяют заранее, пока есть время.

Q: Что делает команда validate constraint?
+ Проверяет ранее объявленное ограничение, не блокируя запись
- Удаляет ограничение из таблицы
- Пересоздаёт таблицу целиком
- Отключает проверку данных
! Ограничение, объявленное как not valid, проверяют отдельной командой со слабой блокировкой.

Q: Почему заполнение большой таблицы одной командой update опасно?
+ Создаёт много мёртвых строк и долго держит блокировки
- Не меняет данные вообще
- Требует прав суперпользователя
- Отключает журнал предзаписи
! Массовое изменение раздувает таблицу, журнал и мешает работе.

Q: Что означает схема из трёх выпусков при миграции?
+ Расширить схему, переключить код, затем убрать лишнее
- Сделать всё в одном выпуске
- Сначала удалить старый столбец
- Сначала отключить ограничения
! Старый и новый код должны работать одновременно, поэтому изменения разводят по выпускам.

Q: Какие команды нельзя выполнять внутри транзакционного блока?
+ create index concurrently
+ vacuum
+ create database
- alter table add column
- alter table add constraint
! Эти команды работают вне транзакции, и обёртка вокруг них завершится ошибкой.

Q: Что даёт короткий lock_timeout при изменении схемы?
+ Изменение отступает, если блокировку не удалось взять быстро
- Ускоряет построение индекса
- Отменяет необходимость в копии
- Разрешает обойти ограничения
! Таймаут не даёт изменению встать в очередь и остановить все запросы.

Q: Почему опасно удалять столбец в том же выпуске, где код перестал его использовать?
+ Часть узлов ещё работает по старому коду и обращается к столбцу
- Столбец нельзя удалить технически
- Удаление всегда занимает часы
- После удаления пропадают индексы
! Пока развёртывание идёт, старый код продолжает работать.

Q: Как называют файл или таблицу, где хранится номер применённой миграции?
= schema_version
! Таблица schema_version хранит версии, имена и время применения.

Q: Как называют операцию построения индекса без блокировки записи?
= concurrently
! create index concurrently строит индекс, не мешая вставке и изменению строк.

Q: Что проверяют на копии базы перед миграцией?
+ Время выполнения и блокировки
+ Работу приложения после изменения
+ Возможность отката
- Цвет темы оформления панели
- Число строк в журнале сервера
! Копия позволяет измерить миграцию и проверить откат без риска для рабочей базы.

Q: Какие данные нужно сверить после миграции?
+ Число строк в затронутых таблицах
+ Значения в новом столбце
+ Работу ограничений целостности
- Название виртуальной машины
- Версию ядра операционной системы
! Проверка доказывает, что данные перенесены полностью и корректно.

Q: Что делать, если в уже применённой миграции нашлась ошибка?
+ Выпустить следующую миграцию, которая её исправляет
- Отредактировать применённый файл
- Удалить строку из schema_version
- Откатить все миграции до первой
! Применённые файлы не переписывают, иначе история версий перестаёт быть достоверной.

::/gate
