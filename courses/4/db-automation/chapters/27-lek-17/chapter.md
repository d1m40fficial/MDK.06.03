## Одна идея

В деканате решили хранить телефон студента. Разработчик добавил колонку и одним запросом заполнил её значениями по умолчанию. На учебной базе из десяти строк всё прошло за секунду. На рабочей базе с сотней тысяч строк `ALTER TABLE` ждал открытую транзакцию, за ним выстроились остальные запросы, а заполнение одной транзакцией удерживало блокировки до вечера.

**Миграция** это изменение схемы, которое не теряет данные и не ломает работающее приложение. Она состоит не из одного `ALTER TABLE`, а из последовательности шагов: версия, копия, прямой скрипт, заполнение данных, обратный скрипт, проверка.

Главная мысль: миграцию проектируют с конца. Сначала решают, как откатиться и как проверить результат, а уже потом пишут `ALTER TABLE`.

> [!KEY]
> В MySQL команда `ALTER TABLE` фиксирует транзакцию неявно, поэтому откатить её вместе с данными нельзя. Надёжная страховка это копия базы и заранее написанный обратный скрипт.

## Версия схемы

Схема базы со временем меняется, и приложение должно знать, в какой версии оно работает. Для этого служит таблица `schema_version`: одна строка на применённую миграцию.

```sql
CREATE TABLE schema_version (
  version INT PRIMARY KEY,
  applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  description VARCHAR(200) NOT NULL
) ENGINE=InnoDB;
```

Скрипты нумеруют по порядку и хранят в репозитории: `V007__add_phone.sql` и рядом `U007__add_phone.sql` для отката. Перед запуском приложение читает `SELECT MAX(version) FROM schema_version` и применяет только те файлы, чей номер больше текущего.

## ALTER TABLE и неявная фиксация

`ALTER TABLE` в MySQL это DDL, а DDL вызывает неявную фиксацию. Если скрипт из трёх команд упал на второй, первая уже зафиксирована, и `ROLLBACK` её не вернёт. В MySQL 8 некоторые операции с InnoDB выполняются атомарно, но правило про фиксацию остаётся: смешивать DDL и DML в одной транзакции бессмысленно.

```sql
ALTER TABLE students
  ADD COLUMN phone VARCHAR(32) NULL;
```

Колонку добавляют в конец и допускают `NULL`. Оба решения не случайны. Добавление в середину поддерживается не всеми версиями и может вызвать перестройку таблицы, а `NOT NULL` без значения по умолчанию на непустой таблице сразу требует заполнения всех строк.

Перед изменением проверяют, что таблица не держит долгих транзакций. `ALTER TABLE` ждёт их завершения и всё это время держит метаданные таблицы, а за ним выстраиваются остальные запросы.

```sql
SELECT id, user, time, state, LEFT(info, 60) AS query
FROM information_schema.PROCESSLIST
WHERE state LIKE '%metadata lock%';
```

Ожидание ограничивают параметром `lock_wait_timeout`: если блокировку не удалось взять за отведённое время, команда завершается с ошибкой, а не висит сутки. Миграцию всё равно ставят в окно обслуживания, потому что даже короткое ожидание метаданных останавливает таблицу для всех.

Версию в `schema_version` записывают только после успешного выполнения скрипта. Если записать её заранее, упавшая миграция будет считаться применённой, и следующая попытка пропустит нужные изменения.

## Добавление колонки и backfill

Правильная последовательность для новой колонки выглядит так.

1. Добавить колонку, допускающую `NULL`, без значения по умолчанию.
2. Заполнить её данными частями, по нескольку тысяч строк.
3. Убедиться, что незаполненных строк не осталось.
4. Поставить `NOT NULL` и значение по умолчанию.
5. Выпустить код, который читает и пишет новую колонку.

Заполнение частями защищает от долгой транзакции. Один `UPDATE` на сто тысяч строк держит блокировки, растит undo log и отставание реплики, а при сбое откатывает всё целиком.

Если версия поддерживает, у `ALTER TABLE` указывают `ALGORITHM=INPLACE, LOCK=NONE`: тогда таблица остаётся доступной для чтения и записи. Но не все изменения так выполняются: смена типа или добавление колонки в середину может потребовать перестройки, и сервер вернёт ошибку вместо тихой блокировки.

Если новая колонка станет внешним ключом, сначала создают индекс, потом ограничение. Без индекса MySQL создаст его сам, но имя и состав могут оказаться не такими, как задумано, а отменить уже созданное ограничение сложнее.

```sql
UPDATE students
SET phone = ''
WHERE phone IS NULL
LIMIT 2000;
```

Команду повторяют, пока она не вернёт ноль изменённых строк. Между порциями дают паузу, чтобы другие запросы успевали работать. В приложении такой цикл пишут на C#: он выполняет `UPDATE`, получает число изменённых строк и останавливается, когда изменений не осталось.

```csharp
while (true)
{
    await using var cmd = new MySqlCommand(
        "UPDATE students SET phone = '' WHERE phone IS NULL LIMIT 2000", conn);
    var changed = await cmd.ExecuteNonQueryAsync();
    if (changed == 0) break;
    await Task.Delay(200);
}
```

## NOT NULL и DEFAULT

Когда пустых значений не осталось, колонку ужесточают. `NOT NULL` сообщает базе, что пропуск значения это ошибка, а `DEFAULT` даёт значение для новых строк, где колонку не указали.

```sql
ALTER TABLE students
  MODIFY COLUMN phone VARCHAR(32) NOT NULL DEFAULT '';
```

Порядок важен: если поставить `NOT NULL` до заполнения, команда упадёт на первой же пустой строке. Если поставить `DEFAULT` раньше времени, старые строки получат значение молча, и проверить, что именно записалось, будет труднее.

## Обратный скрипт

Обратный скрипт пишут вместе с прямым, а не после сбоя. Для добавления колонки откат простой:

```sql
ALTER TABLE students DROP COLUMN phone;
```

Но у отката есть цена. Если новый код уже записал в колонку данные, `DROP COLUMN` их уничтожит. Поэтому откат схемы и откат кода делают в обратном порядке: сначала возвращают старую версию приложения, потом откатывают схему. И только если данные в новой колонке не нужны, её удаляют.

Для переименования и смены типа обратный скрипт сложнее: нужно вернуть прежнее имя и тип, а данные могут не поместиться в старый тип. Такие миграции проверяют на копии с реальным объёмом данных.

::gate Как проверить миграцию до рабочей базы?

## Совместимость старого и нового кода

Пока миграция идёт, приложение работает. Значит, старый и новый код какое-то время смотрят на одну схему. Приём, который это обеспечивает, называют расширением и сжатием.

Сначала **расширяют** схему: добавляют колонку, которую старый код не замечает. Потом выпускают код, который пишет и в старую, и в новую колонку. Затем заполняют историю и переводят чтение на новую колонку. И только после этого **сжимают** схему: удаляют старую колонку.

```sql
ALTER TABLE students ADD COLUMN email_new VARCHAR(128) NULL;
UPDATE students SET email_new = email WHERE email_new IS NULL LIMIT 2000;
```

Такой порядок требует двух выпусков приложения, зато не останавливает работу. Обратный порядок, когда сначала удаляют колонку, а потом выпускают код, ломает приложение между двумя шагами.

## Проверка на копии

Рабочую базу для проверки не используют. Миграцию прогоняют на копии с тем же объёмом данных: восстанавливают дамп в `dean_test`, замеряют время, смотрят блокировки и сверяют результат.

```sql
SELECT COUNT(*) FROM students;
SELECT COUNT(*) FROM students WHERE phone IS NULL;
CHECK TABLE students;
SHOW CREATE TABLE students;
```

Счётчики до и после должны совпадать, пустых значений после заполнения быть не должно, а `SHOW CREATE TABLE` показывает, что тип, `NOT NULL` и `DEFAULT` применились так, как задумано. Время на копии умножают на запас: рабочая база обычно нагружена сильнее.

Сверяют не только количество, но и содержимое: контрольную сумму по ключевым колонкам до и после. Если суммы разошлись, заполнение затронуло не те строки или потеряло часть значений, и миграцию останавливают до выката кода.

## Типичные ошибки

- **Нет обратного скрипта.** Откат пишут в день сбоя, под давлением, и он удаляет данные. Обратный скрипт готовят вместе с прямым.
- **DDL в час пик.** `ALTER TABLE` держит метаданные и останавливает запросы. Изменение ставят в окно обслуживания.
- **Backfill одной транзакцией.** Один `UPDATE` на всю таблицу держит блокировки и откатывается целиком при сбое.
- **NOT NULL до заполнения.** Команда падает на пустых строках, а половина изменений уже зафиксирована.
- **Удаление колонки до выката кода.** Старое приложение обращается к отсутствующей колонке и падает.
- **Проверка только на десяти строках.** На реальном объёме время и блокировки выглядят иначе.

## Проверьте себя

> [!CHECK] Почему нельзя откатить ALTER TABLE командой ROLLBACK?
> DDL в MySQL вызывает неявную фиксацию: команда завершает текущую транзакцию до и после изменения. Поэтому откат делают обратным скриптом, а страховкой служит копия базы.

> [!CHECK] Колонку добавили с NOT NULL и DEFAULT сразу. Чем это хуже постепенного плана?
> База заполняет значением все существующие строки в одной операции, что на большой таблице означает перестройку и долгую блокировку. Постепенный план даёт контроль над порциями и позволяет проверить данные до ужесточения.

> [!CHECK] Зачем проверять миграцию на копии, если скрипт уже прошёл на учебной базе?
> На десяти строках не видно ни времени выполнения, ни блокировок, ни роста undo log. Копия с реальным объёмом показывает, сколько миграция займёт и что произойдёт с параллельными запросами.

## Итог

- Миграция это версия схемы, копия, прямой скрипт, заполнение, обратный скрипт и проверка.
- `schema_version` хранит применённые версии и не даёт выполнить скрипт дважды.
- `ALTER TABLE` фиксирует транзакцию неявно, поэтому откат возможен только обратным скриптом.
- Колонку добавляют как `NULL`, заполняют частями и только потом ставят `NOT NULL` и `DEFAULT`.
- Старый и новый код совмещают через расширение и сжатие схемы, а проверяют миграцию на копии.
