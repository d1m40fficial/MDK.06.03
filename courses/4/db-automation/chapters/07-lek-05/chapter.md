## Одна идея

В папке `C:\backup` лежит файл `dean.sql` за прошлую пятницу. Он весит два мегабайта, открывается в блокноте и даже содержит `CREATE TABLE`. В понедельник выясняется, что восстановить из него нельзя: дамп снят без транзакции, часть таблиц попала в разное состояние, а импорт обрывается на середине.

**Копия это не файл, а обещание восстановить базу за отведённое время.** Пока восстановление не проверено, файл остаётся надеждой. Поэтому в регламенте копирования есть не только создание, но и проверка, хранение и ротация.

## Логическая и физическая копия

Два вида копий решают разные задачи. Логическая выгружает структуру и данные в виде SQL-команд. Физическая копирует файлы данных и журналов.

| Свойство | Логическая | Физическая |
|---|---|---|
| Что получается | текстовый SQL-файл | копия каталога данных |
| Инструмент | `mysqldump`, phpMyAdmin | остановка сервера и копирование папки |
| Переносимость | между версиями и платформами | зависит от версии и ОС |
| Скорость восстановления | медленнее, команды выполняются по одной | быстрее, файлы возвращаются на место |
| Размер | обычно меньше | равен объёму данных |
| Когда выбирают | учебная база, перенос, отдельные таблицы | большая база, быстрый возврат |

Логическая копия читается человеком и не зависит от версии InnoDB. Физическая возвращает сервер быстрее, но требует согласованного состояния файлов: на работающем сервере страницы и журналы меняются, поэтому простое копирование даёт «рваную» копию.

В XAMPP физическую копию делают при остановленном MySQL: останавливают модуль, копируют папку `C:\xampp\mysql\data` целиком и запускают сервер снова. Папка содержит `ibdata1`, файлы `.ibd`, журналы и системные таблицы. Возврат выполняют в обратном порядке: остановить сервер, заменить папку, запустить. Для учебной базы способ годится, для рабочей он означает простой на всё время копирования.

## Дамп через mysqldump

`mysqldump` читает базу и пишет SQL-скрипт: `CREATE TABLE`, затем `INSERT` строками. Для базы `dean` команда выглядит так:

```bash
"C:\xampp\mysql\bin\mysqldump.exe" -u dean_backup -p --single-transaction --routines --triggers --events --default-character-set=utf8mb4 --result-file=C:\backup\dean.sql dean
```

Параметры отвечают за полноту и согласованность. `--single-transaction` снимает согласованный снимок InnoDB. `--routines` добавляет процедуры и функции, `--events` события планировщика, а `--triggers` включает триггеры, хотя по умолчанию они и так попадают в дамп. `--default-character-set=utf8mb4` сохраняет кириллицу. Без `--routines` и `--events` структура восстановится не полностью, и приложение упадёт на первом же вызове процедуры.

`--result-file` важен в Windows. Перенаправление `>` в PowerShell 5.1 пишет файл в UTF-16, и `mysql` не сможет его прочитать как обычный SQL. `--result-file` создаёт файл в нужной кодировке.

Большой дамп сжимают: `--compress` сжимает поток между клиентом и сервером, а архиватор уменьшает готовый файл. Сжатый файл нельзя проверить частично: сначала распаковка, потом импорт. Для учебной базы сжатие экономит место, для рабочей важнее скорость восстановления.

Пароль не указывают в командной строке. Для этого готовят файл параметров и подключают его первым аргументом:

```ini
[client]
user=dean_backup
password=Slozhnyi-parol-2026
```

```bash
"C:\xampp\mysql\bin\mysqldump.exe" --defaults-extra-file=C:\backup\dean.cnf --single-transaction --routines --triggers --events --default-character-set=utf8mb4 --result-file=C:\backup\dean.sql dean
```

Дамп одной базы не содержит команду `CREATE DATABASE` и не включает пользователей с их правами. При восстановлении базу создают заранее, а права выдаются отдельным скриптом.

Кроме данных, сохраняют учётные записи и настройки. Пользователи и права живут в базе `mysql`, поэтому их выгружают отдельно: дампом этой базы или скриптом из `SHOW GRANTS`. Файл `my.ini` и список событий планировщика тоже сохраняют, иначе после восстановления сервер поднимется с другими настройками.

Команда возвращает код 0 только при успехе. В расписании проверяют код и размер нового файла, а не факт наличия файла: старый дамп от прошлого запуска остаётся на месте, и его легко принять за свежий.

## Экспорт из phpMyAdmin

phpMyAdmin умеет то же самое через браузер. Выбирают базу `dean`, вкладку `Export`, режим `Custom`, формат `SQL`, включают структуру и данные, добавляют `DROP TABLE`, выбирают кодировку `utf8mb4` и при необходимости сжатие gzip.

Экспорт удобен для разовой операции: отдать копию преподавателю, перенести таблицу на другой компьютер, проверить структуру. Для ежедневного регламента он не годится: нет расписания, нет кода возврата, а большой файл браузер может оборвать по таймауту.

## InnoDB и согласованный снимок

`--single-transaction` начинает транзакцию с уровнем `REPEATABLE READ` и снимает снимок на момент старта. Все таблицы InnoDB читаются из этого снимка, поэтому дамп видит базу целиком на одно состояние, даже если приложение продолжает писать.

У снимка есть границы. Он работает для InnoDB, но не спасает таблицы MyISAM: для них согласованность даёт блокировка чтения, которая останавливает запись. Схему во время дампа менять нельзя: `ALTER TABLE` ломает снимок и может привести к ошибке или несогласованным данным. Поэтому миграции и копирование разводят по времени. В учебной базе все таблицы InnoDB, поэтому блокировка не нужна и запись не останавливается.

## Binary log и восстановление на момент

Дамп возвращает базу к моменту съёмки. Всё, что произошло после, теряется. Двоичный журнал закрывает этот разрыв: в него попадают изменения данных и схемы после включения `log-bin`.

Цепочка восстановления выглядит так: развернуть дамп, затем проиграть журнал до нужного момента. Журнал проигрывают утилитой `mysqlbinlog`:

```bash
"C:\xampp\mysql\bin\mysqlbinlog.exe" --start-datetime="2026-10-27 02:00:00" --stop-datetime="2026-10-27 14:19:00" --result-file=C:\backup\replay.sql C:\xampp\mysql\data\mysql-bin.000003
```

Перед дампом полезно выполнить `FLUSH LOGS` и запомнить позицию журнала: так понятно, с какого файла продолжать. Журналы хранят не бесконечно: старые удаляют по расписанию, но только после того, как они перестали быть нужны для восстановления.

Формат журнала в MySQL 8 обычно `ROW`: в нём записаны изменения строк, а не текст запроса. Для восстановления это удобнее, потому что результат не зависит от настроек сервера, на котором журнал проигрывают.

## Расписание, хранение и шифрование

Расписание строят от RPO и RTO. RPO показывает, сколько данных допустимо потерять, RTO показывает, за сколько база должна вернуться к работе. Если допустимая потеря данных измеряется минутами, одного ночного дампа мало: нужен непрерывный binary log. Если допустимо потерять сутки, хватит ежедневного дампа.

Расписание удобно ставить в Планировщик Windows: задание запускает командный файл с `mysqldump`, а код возврата и размер файла попадают в журнал. Задание должно падать громко: если дамп не создался, администратор узнаёт об этом в тот же день, а не через месяц.

Типовая схема хранения: семь ежедневных копий, четыре недельных и двенадцать месячных. Копии держат по правилу трёх: три экземпляра, на двух разных носителях, один вне компьютера. Папка `C:\backup` на том же диске, что и `C:\xampp\mysql\data`, правилу не соответствует.

Дампы содержат персональные данные, поэтому их шифруют и ограничивают доступ. Подойдёт BitLocker на диске с копиями или архив с паролем AES-256. Пароль хранят отдельно от архива, иначе шифрование защищает только от случайного человека.

| Что храним | Сколько | Зачем |
|---|---|---|
| Ежедневный дамп | 7 дней | быстрый возврат к вчерашнему состоянию |
| Недельный дамп | 4 недели | ошибка, замеченная позже |
| Месячный дамп | 12 месяцев | отчёты и проверки |
| Binary log | не меньше срока давности копий | восстановление на момент |

## Проверка копии восстановлением

Проверка это отдельная операция, а не открытие файла в блокноте. Дамп импортируют в другую базу и сравнивают результат с источником.

```bash
"C:\xampp\mysql\bin\mysql.exe" -u root -e "DROP DATABASE IF EXISTS dean_restore; CREATE DATABASE dean_restore CHARACTER SET utf8mb4;"
"C:\xampp\mysql\bin\mysql.exe" -u root dean_restore -e "source C:/backup/dean.sql"
"C:\xampp\mysql\bin\mysql.exe" -u root -e "CHECKSUM TABLE dean.students, dean_restore.students;"
```

`CHECKSUM TABLE` считает контрольную сумму строк. Если суммы совпали, данные перенеслись без искажений. Дополнительно сравнивают число строк по каждой таблице и выполняют `CHECK TABLE` для проверки страниц.

Восстановление всегда делают в отдельную базу. Импорт поверх рабочей базы с командами `DROP TABLE` из дампа уничтожит текущие данные, и откатить это будет нечем. Если проверка прошла, копия считается готовой, а результат проверки записывают в журнал.

Порядок восстановления фиксируют в инструкции: создать пустую базу, импортировать дамп, проиграть журнал, проверить counts и связи, только потом переключить приложение. Если шаги перепутать, приложение начнёт писать в базу, которую ещё восстанавливают.

Проверку повторяют по расписанию, а не один раз. Копия, которая работала полгода назад, может не восстановиться после смены версии сервера или кодировки. Результат проверки хранят вместе с копией: дата, размер, число строк и кто проверял.

## Типичные ошибки

**Копия на том же диске.** Отказ диска забирает и базу, и копии. Нужен другой носитель или внешнее хранилище.

**Нет проверки.** Файл создаётся, отчёт отправляется, а импорт падает. Проверка восстановлением выявляет это до аварии.

**Нет binary log.** Без журнала нельзя вернуться на момент сбоя, только к последнему дампу.

**Дамп без `--single-transaction`.** Запись во время дампа даёт несогласованные таблицы: платёж есть, а записи о студенте ещё нет.

**Пароль в командной строке.** Его видно в списке процессов и в истории. Используют файл параметров.

**Нет ротации.** Копии занимают весь диск, и очередной дамп падает из-за нехватки места.

## Проверьте себя

> [!CHECK] Дамп весит два мегабайта и открывается в блокноте. Можно ли считать копию готовой?
> Нет. Нужно восстановить её в отдельную базу и сверить суммы и число строк. Файл может быть обрезан или снят без согласованного снимка.

> [!CHECK] Зачем хранить binary log, если есть ежедневный дамп?
> Дамп возвращает базу к моменту съёмки. Журнал позволяет проиграть изменения после него и восстановить базу на нужную секунду.

> [!CHECK] Почему восстановление проверяют в dean_restore, а не в dean?
> Импорт поверх рабочей базы заменяет таблицы и уничтожает текущие данные. Отдельная база позволяет сравнить результат, не рискуя работой деканата.

## Итоги

- Логическая копия это SQL-скрипт, физическая это файлы данных; выбор зависит от объёма и требуемого времени восстановления.
- `mysqldump` с `--single-transaction` даёт согласованный снимок InnoDB, а `--result-file` избегает проблем с кодировкой в PowerShell.
- Binary log дополняет дамп и позволяет восстановить базу на момент сбоя.
- Копия считается готовой только после восстановления в отдельную базу и сверки данных.

- `--lock-tables`
- `--no-data`

- Данные таблиц
- Триггеры таблиц

+ Перенаправление пишет файл в UTF-16, и mysql его не читает

- `--result-file` сжимает файл
- `--result-file` удаляет старые копии
! Файл дампа должен быть в кодировке, понятной клиенту mysql.

Q: Что добавляет binary log к ежедневному дампу?
+ Изменения после момента съёмки
- Структуру таблиц
- Пароли пользователей
- Свободное место на диске
! Журнал позволяет восстановить базу на момент, а не только на время дампа.

Q: Как проверить копию базы?
+ Восстановить её в отдельную базу и сверить данные
- Открыть файл в блокноте
- Посмотреть размер файла
- Запустить SHOW TABLES на рабочей базе
! Проверка это восстановление и сравнение, а не просмотр файла.

Q: Где хранить резервную копию?
+ На другом носителе или вне компьютера
- В папке с данными MySQL
- На том же диске рядом с базой
- В буферной памяти сервера
! Копия должна пережить отказ диска с данными.

Q: Что сравнивает CHECKSUM TABLE?
+ Контрольную сумму строк таблицы
- Размер файла my.ini
- Число пользователей MySQL
- Версию сервера
! Совпадение сумм подтверждает перенос данных без искажений.

Q: Из чего состоит восстановление на момент времени?
+ Дамп базы
+ Binary log до нужного момента
+ Проверка данных после импорта
- Только файл my.ini
- Только список пользователей
! Сначала разворачивают дамп, затем проигрывают журнал и проверяют результат.

Q: Что должно входить в регламент копирования?
+ Расписание создания копий
+ Хранение и ротация
+ Проверка восстановлением
- Ручной экспорт из phpMyAdmin раз в месяц
- Хранение копии на диске с базой
! Регламент описывает создание, хранение, проверку и удаление копий.

Q: Какие ошибки делают копию бесполезной?
+ Хранение единственной копии на диске с данными
+ Отсутствие проверки восстановлением
+ Отсутствие binary log при требовании малого RPO
- Использование `--single-transaction`
- Указание кодировки utf8mb4
! Копия должна пережить отказ, восстанавливаться и покрывать нужный момент.

Q: Какая утилита создаёт логический дамп MySQL?
= mysqldump
= mysqldump.exe
! mysqldump выгружает структуру и данные в SQL-скрипт.

Q: Какая утилита проигрывает binary log?
= mysqlbinlog
= mysqlbinlog.exe
! mysqlbinlog читает двоичный журнал и превращает его в SQL-команды.

Q: Что произойдёт, если снять дамп без `--single-transaction` при активной записи?
+ Таблицы могут попасть в разное состояние
- Дамп станет меньше
- Сервер автоматически остановится
- Копия будет зашифрована
! Без снимка изменения во время дампа дают несогласованные данные.
