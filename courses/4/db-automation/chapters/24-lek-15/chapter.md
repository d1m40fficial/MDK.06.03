## Инцидент, который нельзя разобрать

В понедельник утром в таблице `payments` не хватает семи строк. Приложение платежи не удаляет, обновлений в выходные не выпускали, резервная копия есть, но непонятно, к какому моменту её применять: неизвестно, когда именно пропали данные. Если аудит был настроен, ответ находится за несколько минут: видно, какая роль, с какого адреса и в какое время выполнила удаление. Если аудита не было, остаётся гадать, и это худший вид разбора.

**Аудит** это запись действий с данными: кто, когда, откуда, что сделал и чем это закончилось. Он отвечает не на вопрос «как поживает база», а на вопрос «кто довёл её до такого состояния». Мониторинг и аудит дополняют друг друга: первый показывает рост мёртвых строк, второй называет сеанс, который их создал.

У аудита три практические цели. Первая это **разбор инцидента**: восстановить последовательность действий и понять, что именно испорчено. Вторая это **подотчётность**: сотрудник знает, что его действия записаны, и это само по себе меняет поведение. Третья это **проверка правил**: по журналу видно, ходит ли приложение в таблицы, к которым не должно, и не пользуется ли кто-то лишними правами.

Разберём событие на примере. В понедельник в 09:14 роль `dean_write` с адреса `10.0.2.15` через приложение `dean_app` выполнила удаление из `payments` по строке 42, и операция завершилась успешно. Здесь пять полей: субъект, время, действие, объект и результат. Если хотя бы одного не хватает, событие теряет смысл. Без времени непонятно, что было раньше; без объекта непонятно, что пострадало; без результата нельзя отличить попытку от свершившегося изменения.

> [!KEY]
> Аудит нужен не для того, чтобы записать всё. Он нужен для того, чтобы на любой вопрос «кто это сделал» был ответ, полученный за минуты, а не за день.

Журнал сервера отвечает на вопрос «что выполнялось». pgaudit отвечает на вопрос «кто и к каким объектам обращался». Триггерная таблица отвечает на вопрос «что стало со строкой». Для полного разбора обычно нужны два источника: журнал показывает попытку, таблица показывает результат.

## Журнал сервера

Сервер уже умеет писать в свой журнал, и часть событий включается настройками. Три параметра закрывают основную потребность.

```sql
alter system set log_statement = 'ddl';
alter system set log_connections = on;
alter system set log_disconnections = on;
alter system set log_line_prefix = '%m [%p] %q%u@%d/%a %r ';
select pg_reload_conf();
```

`log_statement` принимает четыре значения. `none` выключает запись команд, `ddl` пишет только изменения схемы, `mod` пишет `insert`, `update`, `delete`, `truncate` и `copy from`, а `all` пишет вообще всё, включая `select`. Значение `all` на рабочей базе почти всегда ошибка: объём журнала вырастает в десятки раз, а полезной информации добавляется немного.

`log_connections` и `log_disconnections` фиксируют вход и выход, включая неудачные попытки входа. Это первый источник при разборе подозрительной активности: видно, с какого адреса и под какой ролью пытались подключиться.

`log_line_prefix` задаёт шапку строки. В примере выше `%m` это время с миллисекундами, `%p` номер процесса, `%u` роль, `%d` база, `%a` имя приложения, `%r` адрес клиента. Без этой шапки журнал превращается в поток строк, по которому невозможно понять, кто именно действовал.

Все три параметра применяются перезагрузкой конфигурации, перезапуск сервера не нужен. Это важно: аудит можно включить на работающей базе, не останавливая приложение.

## pgaudit, если доступно

`pgaudit` это расширение, которое добавляет семантический аудит: оно понимает смысл команды и умеет группировать события по классам. Настраивается оно на уровне сервера.

```sql
alter system set shared_preload_libraries = 'pgaudit';
alter system set pgaudit.log = 'write, ddl, role';
alter system set pgaudit.log_relation = on;
alter system set pgaudit.log_catalog = off;
```

```sql
create extension if not exists pgaudit;
```

Классы задают, что именно попадает в журнал: `read` для чтения, `write` для изменений данных, `ddl` для схемы, `role` для ролей и привилегий, `function` для вызовов функций. Параметр `log_relation` добавляет имена таблиц, которых коснулась команда, а `log_catalog` стоит выключить, иначе служебные запросы к системному каталогу забьют журнал.

Расширение требует загрузки при старте, поэтому его включение означает перезапуск сервера. Зато дальше оно работает одинаково для всех приложений: приложение не может «забыть» записать событие, потому что записывает сам сервер.

> [!NOTE]
> pgaudit не создаёт таблицу. Он пишет в тот же журнал сервера, что и `log_statement`, только строки получаются структурированными и с указанием объектов.

## Триггерная таблица

Когда нужны значения полей, журнала мало: в нём есть текст команды, но нет строки до и после. Тогда ставят триггер, который пишет в таблицу `audit_log`.

```sql
create or replace function audit_row() returns trigger
language plpgsql
security definer
set search_path = public, pg_temp
as $$
begin
  insert into audit_log(db_user, action, table_name, row_id, details)
  values (session_user, tg_op, tg_table_name,
          coalesce(new.id, old.id)::text,
          jsonb_build_object('as', current_user,
                             'old', to_jsonb(old),
                             'new', to_jsonb(new)));
  return null;
end;
$$;

create trigger payments_audit
after insert or update or delete on payments
for each row execute function audit_row();
```

Здесь важна одна тонкость. Функция объявлена `security definer`, поэтому выполняется с правами владельца и может писать в `audit_log`, куда приложению вход закрыт. Но внутри такой функции `current_user` равен владельцу, а не тому, кто вызвал триггер. Автора действия берут из `session_user`, а `current_user` сохраняют отдельно, чтобы видеть, под какой ролью реально работала функция.

Триггер видит только то, что прошло через таблицу. Чтение он не фиксирует, изменения через `truncate` при построчном триггере тоже не увидит, а при массовой загрузке добавит заметную нагрузку на запись. Поэтому триггеры ставят на чувствительные таблицы: платежи, оценки, роли, а не на все подряд.

У аудита есть цена, и её считают заранее. Запись в журнал добавляет операций ввода-вывода, триггер добавляет работу в каждую изменяющую транзакцию, а хранение копий требует места. На учебной базе этим можно пренебречь. На рабочей базе аудит сначала включают на одной таблице, смотрят прирост времени записи и объём журнала за сутки, и только потом расширяют набор событий.

## Что писать и что не писать

Полный аудит всего подряд быстро превращается в свалку, которую никто не читает. Набор событий выбирают по риску.

- **Платежи и оценки.** Любое изменение суммы или оценки важно, потому что затрагивает человека и деньги.
- **Роли и привилегии.** Кто выдал право, кто создал суперпользователя, кто изменил пароль.
- **Схема.** Создание, изменение и удаление таблиц и столбцов.
- **Подключения.** Особенно неудачные и с необычных адресов.
- **Чтение секретных данных.** Только если этого требует политика: чтение журнала запросов дорого по объёму.

Не стоит писать каждый `select` к справочнику групп и служебные запросы самого мониторинга. Они не несут риска и только мешают искать нужное.

Набор событий пересматривают после каждого разбора. Если журнал не ответил на вопрос «кто это сделал», значит, нужного события в нём не было, и вывод касается настройки аудита, а не самого инцидента.

## Политика аудита

Набор событий и срок хранения это не техническое решение, а документ. В политике фиксируют, какие таблицы считаются чувствительными, какие действия по ним пишутся, кто читает журнал, сколько он хранится и по какому основанию из него делают выгрузку. Без такого документа настройки живут до первого спора: один администратор пишет всё, другой выключает аудит ради скорости, и оба считают, что правы.

Политика отвечает и на неудобный вопрос: что делать с персональными данными внутри журнала. Аудит изменений студентов сам содержит фамилии и адреса, то есть становится ещё одной копией чувствительных данных. Поэтому в `details` часто пишут идентификатор и изменившиеся поля, а не всю строку целиком, а доступ к журналу приравнивают к доступу к самим данным.

## Срок хранения и ротация

Срок хранения задаёт не администратор, а политика организации: сколько времени нужно, чтобы заметить проблему и доказать факт. Типичная отправная точка это три месяца в быстром доступе и год в архиве, но для финансовых данных срок может быть больше.

Журнал сервера растёт непрерывно, поэтому его обязательно ротируют. В учебной Ubuntu этим занимается `logrotate`: файл за сутки или за размер, сжатие, удаление по возрасту. Если ротации нет, диск кончится, и сервер остановится. Это не гипотетический риск: журнал с `log_statement = 'all'` на активной базе занимает гигабайты за дни.

Таблицу `audit_log` чистят иначе. Удаление миллионов строк одной командой надолго занимает диск и мешает автовакууму. Поэтому таблицу секционируют по месяцам и старые секции удаляют целиком.

```sql
create table audit_log (
  id bigint generated always as identity,
  at timestamptz not null default now(),
  db_user text,
  action text,
  table_name text,
  row_id text,
  details jsonb,
  primary key (id, at)
) partition by range (at);

create table audit_log_2026_03 partition of audit_log
  for values from ('2026-03-01') to ('2026-04-01');
```

Удаление секции это быстрая операция, а не построчная работа. Заодно секции удобно выгружать в архив по одной.

## Защита журнала от изменения

Аудит, который можно безнаказанно переписать, не аудит. Защита строится в три слоя.

**Права.** Читать `audit_log` должна только роль `auditor`. Приложение не получает ни `insert`, ни `update`, ни `delete`: запись делает функция с правами владельца.

```sql
revoke all on audit_log from public;
grant select on audit_log to auditor;
```

**Неизменяемость.** Триггер запрещает правку и удаление строк.

```sql
create or replace function audit_immutable() returns trigger
language plpgsql as $$
begin
  raise exception 'audit_log append only';
end;
$$;

create trigger audit_log_immutable
before update or delete on audit_log
for each row execute function audit_immutable();
```

**Копия вне сервера.** Это главный слой. Владелец таблицы может отключить триггер, а тот, кто получил доступ к серверу, может удалить и базу, и журнал. Настоящая защита появляется, когда копия уходит на другой узел.

Отправка через `syslog` настраивается параметром `log_destination` и правилами `rsyslog`. Для учебной базы достаточно второго узла в той же виртуальной сети, для рабочей это отдельный сервер с политикой хранения.

Есть и организационная мера: разделение обязанностей. Администратор базы настраивает аудит, но не должен быть единственным, кто читает журнал: иначе он проверяет сам себя. Роль `auditor` выдают человеку или службе, которые не меняют данные. В небольшой организации обе роли может совмещать один человек, но копию журнала всё равно смотрят отдельно от базы.

Полезен и хеш-контур: в таблицу добавляют столбцы `prev_hash` и `hash`, где `hash` считается от предыдущего хеша и содержимого строки. Тогда выборочная правка ломает цепочку и становится заметной. Но если злоумышленник может переписать всю цепочку, она не поможет, поэтому якорь хеша всё равно хранят вне сервера.

## Чтение и восстановление хода действий

Журнал читают по вопросу, а не целиком. Сначала сужают окно времени, потом объект, потом роль.

```sql
select at, db_user, action, table_name, row_id,
       details -> 'old' ->> 'amount' as old_amount,
       details -> 'new' ->> 'amount' as new_amount
from audit_log
where table_name = 'payments'
  and at between '2026-03-02 08:00+03' and '2026-03-02 12:00+03'
order by at;
```

Дальше собирают цепочку. События одного пользователя выстраивают по времени, смотрят первое подозрительное действие и проверяют, что происходило в следующие минуты. Если строки удалены, по `row_id` и `details` восстанавливают значения и сравнивают их с резервной копией: копия даёт состояние до, журнал даёт список того, что изменилось после.

Порядок разбора удобно держать в голове целиком. Сначала находят окно: последнее известное хорошее состояние и момент обнаружения пропажи. Потом выбирают все события в этом окне по нужному объекту. Затем выстраивают их по времени и по роли, отмечая первое действие, которого не должно было быть. После этого сверяют `row_id` с текущей таблицей и с копией: чего не хватает, что изменилось не так. И только потом выбирают точку восстановления.

Аудит сам данные не возвращает. Он говорит, что именно испорчено и за какой промежуток, а восстановление выполняют из копии, применяя журнал предзаписи до нужного момента. Без аудита непонятно, какой момент выбирать; с аудитом окно восстановления известно с точностью до секунды.

::/gate

::gate Какие ошибки делают аудит бесполезным?

## Типичные ошибки

- **Логировать всё без ротации.** `log_statement = 'all'` без `logrotate` заполняет диск за дни и останавливает сервер.
- **Хранить журнал рядом с базой.** Один и тот же доступ позволяет удалить и данные, и следы. Копия должна уходить на другой узел.
- **Нет доступа к журналу.** Аудит включён, но роль `auditor` не создана, и прочитать записи некому. Это аудит для отчёта, а не для работы.
- **Писать аудит в ту же транзакцию и ждать записи об откате.** Триггер пишет внутри транзакции, и при откате запись исчезает вместе с ней. Попытки, которые должны остаться в любом случае, фиксируют в журнале сервера.
- **Путать `current_user` и `session_user`.** В функции с правами владельца автор действия теряется, если брать не то поле.

## Проверьте себя

> [!CHECK] Приложение подключается как dean_app, а триггер объявлен security definer с владельцем dean_owner. Какая роль попадёт в поле db_user, если использовать current_user?
> Владелец функции, то есть dean_owner. Внутри security definer `current_user` подменяется на владельца, поэтому все записи выглядели бы одинаково и разбор стал бы невозможен. Автора берут из `session_user`, а фактическую роль исполнения сохраняют отдельно.

> [!CHECK] В журнале есть строка об удалении из payments, но таблица audit_log пуста. Как это объяснить?
> Триггер срабатывает на построчные изменения, а `truncate` его не вызывает. Кроме того, триггер мог быть отключён или отсутствовать на этой таблице. Журнал сервера фиксирует саму команду, поэтому он и остаётся единственным следом.

> [!CHECK] Зачем нужна копия журнала, если на таблице стоит запрет изменения?
> Запрет действует внутри базы и снимается владельцем таблицы. Тот, кто получил доступ к серверу, может отключить триггер, изменить записи или удалить каталог. Копия на отдельном узле не подчиняется этим правам, поэтому только она делает журнал доказательством.

## Итог

- Аудит отвечает, кто и что сделал с данными, и нужен для разбора, подотчётности и проверки правил.
- Источников три: журнал сервера, pgaudit и триггерная таблица; они видят разное и дополняют друг друга.
- Пишут не всё, а события с риском: платежи, оценки, роли, схему, подключения.
- Журнал ротируют, таблицу секционируют, срок хранения задаёт политика.
- Защита строится на правах, запрете изменения и копии вне сервера.

## Тест по лекции

::quiz
Q: Что фиксирует событие аудита?
+ Кто, когда, что сделал и чем это закончилось
- Только текст выполненных запросов
- Только число подключений к базе
- Только размер базы данных
! Событие описывает субъект, время, действие, объект и результат.

Q: Какие источники событий аудита есть в PostgreSQL?
+ Журнал сервера с log_statement
+ Расширение pgaudit
+ Триггерная таблица audit_log
- Файл pg_hba.conf
- Параметр max_connections
! Журнал, pgaudit и триггер дают разные срезы действий, а конфигурация доступа событиями не является.

Q: Что записывает log_statement со значением ddl?
+ Только команды изменения схемы
- Все запросы, включая select
- Только ошибки выполнения
- Только подключения и отключения
! Значение ddl ограничивает журнал командами создания, изменения и удаления объектов.

Q: Что нужно, чтобы pgaudit начал работать?
+ Прописать расширение в shared_preload_libraries и перезапустить сервер
- Выдать приложению право GRANT ALL
- Включить автовакуум
- Построить индекс на audit_log
! Расширение загружается при старте сервера, поэтому без перезапуска оно не включится.

Q: Что стоит записывать в аудит в первую очередь?
+ Изменения платежей и оценок
+ Изменения ролей и привилегий
+ Изменения схемы базы
- Каждый select к справочнику групп
- Служебные запросы системы мониторинга
! Аудит настраивают по риску, а не по принципу «записать всё».

Q: Почему внутри security definer функции нельзя брать current_user как автора действия?
+ current_user равен владельцу функции, а не тому, кто её вызвал
- current_user всегда пуст
- current_user меняется при каждом запросе
- current_user доступен только суперпользователю
! Роль исполнения подменяется владельцем, поэтому автора берут из session_user.

Q: Что произойдёт с записью аудита, сделанной триггером в той же транзакции, если транзакция откатится?
+ Запись тоже откатится
- Запись останется в таблице
- Запись попадёт в журнал сервера
- Запись станет недействительной, но останется
! Триггер пишет внутри транзакции, и откат убирает запись вместе с изменением.

Q: Как защитить журнал аудита от изменения?
+ Отправлять копию на отдельный узел
+ Запретить update и delete триггером
+ Выдать чтение только роли auditor
- Хранить журнал в той же таблице, что и данные
- Дать приложению права владельца таблицы
! Защита складывается из прав, запрета изменения и копии вне сервера.

Q: Как называется параметр, который задаёт формат строки журнала сервера?
= log_line_prefix
! log_line_prefix задаёт шапку строки: время, процесс, роль, база, приложение, адрес.

Q: Зачем нужна ротация журнала?
+ Чтобы журнал не заполнил диск и хранился заданный срок
- Чтобы ускорить выполнение запросов
- Чтобы зашифровать данные в таблицах
- Чтобы автоматически отменять транзакции
! Без ротации журнал растёт до отказа диска, а срок хранения не соблюдается.

Q: Что даёт секционирование audit_log по месяцам?
+ Старые секции удаляют целиком, не трогая остальные
- Ускоряет выборку из таблицы payments
- Отменяет необходимость в индексах
- Заменяет резервную копию базы
! Удаление секции это быстрая операция, а построчное удаление надолго занимает диск.

Q: Что нужно, чтобы восстановить ход действий по журналу?
+ Время события
+ Роль и адрес подключения
+ Объект и идентификатор строки
- Среднее время выполнения запроса
- Размер табличного пространства
! Без времени, субъекта и объекта события цепочку действий не выстроить.

Q: Почему журнал, лежащий только на том же сервере, что и база, плохо защищён?
+ Тот, кто получил доступ к серверу, может удалить журнал вместе с базой
- Он занимает слишком много оперативной памяти
- Его нельзя прочитать через SQL
- Он не поддерживает кодировку UTF-8
! Локальная копия подчиняется тем же правам, что и данные, поэтому её уносят на другой узел.

Q: Как называется расширение PostgreSQL для семантического аудита?
= pgaudit
! pgaudit группирует события по классам и пишет их в журнал сервера.

Q: Что означает запись аудита с действием UPDATE и заполненными old и new?
+ Строка была изменена, и сохранены значения до и после
- Строка была только прочитана
- Транзакция была отменена
- Пользователь подключился к базе
! Триггер на update сохраняет обе версии строки, и по ним видно, что именно изменилось.
