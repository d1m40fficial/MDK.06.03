## Одна идея

В понедельник в базе деканата у десяти студентов исчезают оценки по одному курсу. Приложение работает, ошибок не пишет, резервная копия есть, но она сделана в воскресенье. Администратор открывает журнал и видит только время запуска сервера и сообщения об ошибках: кто именно выполнил `DELETE`, неизвестно. Восстановить картину нечем.

**Аудит** это учёт действий: кто, когда, что и над какими данными сделал. Мониторинг из прошлой лекции отвечает, как себя чувствует база, а аудит отвечает, что с данными произошло и по чьей воле. Это разные вопросы, и решаются они разными средствами.

Главная мысль: журнал аудита проектируют заранее, вместе с правами и регламентом хранения. Журнал, включённый после инцидента, показывает только будущее, а вопрос обычно задают о прошлом.

> [!KEY]
> Аудит нужен не для наказания, а для восстановления картины. Если по журналу нельзя ответить «кто удалил строку 42 и когда», аудита нет, даже если файл журнала существует.

## Два журнала и две задачи

У аудита в MySQL два разных инструмента, и путать их дорого. **General log** записывает все команды, которые сервер получил от клиентов: подключения, запросы, изменения. Он даёт полную картину, но стоит дорого и быстро растёт. **Триггерная таблица** пишет только те изменения, которые важны для дела: кто поменял оценку, когда и на что.

Разница видна на примере. Если нужно понять, почему тормозит отчёт, смотрят general log за пять минут. Если нужно доказать, что оценку изменил конкретный сотрудник, смотрят триггерную таблицу за семестр. Первый инструмент тяжёлый и временный, второй лёгкий и постоянный.

Есть и третий источник, binary log. Он не является журналом аудита, но показывает изменения строк и позволяет восстановить данные до нужного момента. Аудит отвечает на вопрос «кто», binary log на вопрос «что вернуть».

::gate Чем general log отличается от триггерной таблицы?

## General log: включение

General log по умолчанию выключен. Включают его на время разбора или на короткий период наблюдения, а не навсегда.

```sql
SHOW VARIABLES LIKE 'general_log%';
SET GLOBAL log_output = 'TABLE';
SET GLOBAL general_log = ON;
```

`log_output` задаёт, куда писать: `FILE`, `TABLE`, `NONE` или их комбинацию через запятую. В XAMPP удобнее `TABLE`: события попадают в таблицу, и их можно читать обычным запросом из phpMyAdmin, не открывая файлы на диске. Файловый режим пишет в `.../xampp/mysql/data\` и требует доступа к каталогу.

Проверить, что журнал включён, можно так:

```sql
SELECT @@general_log, @@log_output, @@general_log_file;
```

Выключить журнал нужно сразу после разбора: каждая команда клиента добавляет строку, и за активный день таблица вырастает до сотен тысяч записей. Если нужен файловый режим, `log_output = 'FILE'` пишет в `general_log_file`, а команда `FLUSH GENERAL LOGS` закрывает текущий файл и начинает новый. Старые файлы удаляют вручную: MySQL не хранит их сам.

## Чтение mysql.general_log

Таблица `mysql.general_log` хранит колонки `event_time`, `user_host`, `thread_id`, `server_id`, `command_type` и `argument`. Последняя колонка содержит текст команды.

```sql
SELECT event_time, user_host, command_type, LEFT(argument, 120) AS cmd
FROM mysql.general_log
WHERE event_time > NOW() - INTERVAL 30 MINUTE
  AND command_type = 'Query'
ORDER BY event_time DESC
LIMIT 50;
```

Такой запрос отвечает на вопрос «что выполнялось в последние полчаса». Колонка `user_host` показывает учётную запись и адрес клиента, поэтому видно, пришла команда из приложения или из phpMyAdmin.

У общего журнала есть неприятное свойство: в него попадают и пароли. Команда `CREATE USER ... IDENTIFIED BY '...'` и `SET PASSWORD` записываются открытым текстом. Поэтому журнал читают ограниченным кругом лиц и не выкладывают в общий доступ.

::gate Что писать в журнал и сколько его хранить?

## Триггерная таблица audit_log

Общий журнал отвечает на вопрос «что было», но не даёт удобного ответа «кто изменил эту строку». Для этого служит таблица аудита, в которую пишут триггеры на рабочих таблицах.

```sql
CREATE TABLE audit_log (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  db_user VARCHAR(64),
  action VARCHAR(32),
  table_name VARCHAR(64),
  row_id VARCHAR(64),
  details JSON
) ENGINE=InnoDB;
```

Триггер на изменение студентов фиксирует старую и новую почту студента. `CURRENT_USER()` возвращает учётную запись, под которой прошла аутентификация, и это правильный источник для аудита: `USER()` показывает имя, которое клиент указал при подключении, и его легко подделать.

```sql
DELIMITER //
CREATE TRIGGER trg_students_au AFTER UPDATE ON students
FOR EACH ROW
BEGIN
  INSERT INTO audit_log (db_user, action, table_name, row_id, details)
  VALUES (CURRENT_USER(), 'UPDATE', 'students', OLD.id,
          JSON_OBJECT('email_old', OLD.email, 'email_new', NEW.email));
END//
DELIMITER ;
```

Для удаления нужен такой же триггер `AFTER DELETE` с `OLD`, для вставки `AFTER INSERT` с `NEW`. Триггеры срабатывают на каждую строку, поэтому массовое обновление на десять тысяч строк даст десять тысяч записей в журнале.

Триггеры не видят DDL: `ALTER TABLE`, `DROP TABLE` и `TRUNCATE` проходят мимо них. Поэтому изменения схемы отслеживают отдельно, по general log или по журналу миграций.

## Что писать и сколько хранить

В журнал попадает минимум: время, пользователь базы, действие, таблица, ключ строки и значимые поля до и после. Не стоит копировать всю строку целиком: журнал быстро вырастет, а разбирать его станет труднее.

Срок хранения определяют по задаче, а не по размеру диска. Для учебной базы достаточно семестра, для рабочей системы срок задаёт регламент организации. Хранение делят на два слоя: горячий журнал в базе за последний месяц и архив в отдельном файле или на отдельном сервере за более долгий срок.

```sql
DELETE FROM audit_log WHERE at < NOW() - INTERVAL 180 DAY;
```

Удаление старых записей делают по расписанию и только после выгрузки архива. Если удалять вручную и «когда вспомнят», журнал либо растёт без предела, либо теряет нужный период.

## Защита журнала

Журнал аудита ценен только пока ему можно доверять. Основные меры такие:

- **Отдельная база или схема.** `audit_log` держат не в `dean`, а в отдельной схеме, чтобы рабочая база не могла её очистить. В учебной базе таблицу можно оставить рядом, но в рабочей её выносят отдельно.
- **Только добавление.** Приложению дают `INSERT` на журнал и не дают `UPDATE` и `DELETE`. Читает журнал отдельная роль `auditor`.
- **Отдельный пользователь.** Триггер создаёт администратор, приложение не получает право `TRIGGER`.
- **Резервная копия.** Журнал включают в дамп вместе с рабочими таблицами, иначе после восстановления базы пропадёт и история.
- **Синхронизация времени.** Все серверы работают по одному источнику времени, иначе события нельзя сопоставить.

> [!PITFALL] Журнал рядом с данными
> Если `audit_log` лежит в той же базе, что и рабочие таблицы, то пользователь с правом `DROP` на базу может удалить и журнал. Защита начинается с разделения прав и места хранения, а не с пароля на файл.

Аудит проверяют заранее, а не в день инцидента. Раз в месяц выполняют тестовое изменение в учебной таблице и смотрят, появилась ли запись. Если записи нет, триггер мог быть удалён, заменён при миграции или направлен в другую таблицу. Такая проверка занимает минуту и спасает от обнаружения пустого журнала в самый неподходящий момент.

::gate Как восстановить ход действий и где чаще всего ошибаются?

## Восстановление хода действий

Разбор начинают с вопроса, а не с просмотра таблицы. «Кто изменил оценку студента 17 после пятницы» превращается в конкретный запрос.

```sql
SELECT at, db_user, action, details
FROM audit_log
WHERE table_name = 'students' AND row_id = '17'
ORDER BY at;
```

Если в журнале есть запись, видно пользователя, время и старые значения. Если записи нет, проверяют, был ли триггер на таблице и не менялись ли данные командами `TRUNCATE` или `LOAD DATA`, которые не вызывают построчных триггеров.

Дальше картину дополняют general log за узкий интервал и binary log. Общий журнал показывает команды, binary log показывает изменения на уровне строк и позволяет восстановить данные до нужного момента. Три источника вместе дают ответ: кто, когда, что и можно ли вернуть.

Полезно заранее договориться о формате ответа на вопрос разбора: время события, пользователь, действие, таблица, ключ строки, что было и что стало. Если журнал даёт все шесть полей, разбор занимает минуты. Если не даёт, картину восстанавливают по косвенным признакам, и часть выводов остаётся догадкой.

```sql
SELECT at, db_user, action, table_name, row_id
FROM audit_log
WHERE at BETWEEN '2026-10-20 08:00:00' AND '2026-10-20 12:00:00'
ORDER BY at;
```

## Типичные ошибки

- **Логировать всё без ротации.** General log, включённый навсегда, забивает диск и замедляет сервер. Его включают на время разбора.
- **Хранить журнал рядом с базой.** Пользователь с широкими правами удаляет журнал вместе с данными. Журнал держат отдельно и защищают правами.
- **Писать пароли в журнал.** General log фиксирует `IDENTIFIED BY` открытым текстом. Доступ к журналу ограничивают.
- **Триггеры только на одну таблицу.** Изменения в соседних таблицах остаются без следа. Состав таблиц аудита определяют по важным данным.
- **Нет срока хранения.** Журнал либо растёт бесконечно, либо удаляется без архива.
- **Журнал без синхронизации времени.** События с разных серверов не выстраиваются в цепочку.

## Проверьте себя

> [!CHECK] Нужно узнать, какой запрос выполнялся в 14:32 и кто его отправил. Что включить?
> General log с `log_output = 'TABLE'` на короткое время и запрос к `mysql.general_log` по интервалу вокруг 14:32. Колонка `user_host` покажет учётную запись и адрес клиента. После разбора журнал выключают.

> [!CHECK] Триггер на students есть, а записи об удалении строки нет. Что могло произойти?
> Строку удалили командой, которая не вызывает построчных триггеров: `TRUNCATE TABLE`, `DROP TABLE` или массовая загрузка. Проверяют general log и binary log, а также наличие триггера `AFTER DELETE`.

> [!CHECK] Почему нельзя дать приложению право UPDATE на audit_log?
> Тогда приложение или злоумышленник сможет переписать историю и скрыть следы. Журналу нужно только добавление, а чтение и удаление старых записей выполняет отдельная роль.

## Итог

- Аудит отвечает, кто и что сделал с данными, а мониторинг отвечает, как работает база.
- General log включают на время разбора: `log_output = 'TABLE'` и `general_log = ON`.
- События общего журнала лежат в `mysql.general_log`, читают их запросом по времени и пользователю.
- Триггерная таблица `audit_log` фиксирует изменения важных таблиц и хранит старые и новые значения.
- Журнал держат отдельно, дают только `INSERT`, включают в копию и чистят по регламенту.

- Удаляют таблицу students
- Отключают binary log
! Запись в журнал во время очистки мешает и может потерять события.

Q: Какие операции не вызывают построчных триггеров?
+ TRUNCATE TABLE
+ DROP TABLE
+ LOAD DATA
- UPDATE одной строки
- INSERT одной строки
! Триггеры срабатывают на построчные DML, а не на операции целиком.

+ Время события
+ Пользователя базы
+ Ключ изменённой строки
+ Старое и новое значение важного поля
- Пароль пользователя
- Всю таблицу целиком
! Журнал должен быть достаточным для разбора и не хранить секреты.

+ Отдельная схема хранения
+ Право только на INSERT
+ Отдельная роль для чтения
+ Включение журнала в резервную копию

- Хранение журнала в базе dean
! Журнал защищают правами, отдельным местом и копией.

Q: Какие ошибки типичны для аудита?
+ Включённый навсегда general log без ротации
+ Журнал лежит в той же базе
+ Пароли попадают в общий журнал
+ Нет срока хранения

- Синхронизация времени
! Постоянный журнал, общее место хранения и отсутствие регламента ломают аудит.

! При log_output = 'TABLE' события попадают в эту таблицу.

Q: Какое значение log_output направляет журнал в таблицу?
= TABLE
! Значение TABLE включает табличный вывод, FILE пишет в файл.

Q: Какая функция возвращает учётную запись, под которой прошла аутентификация?
= CURRENT_USER()
! Именно её указывают в журнале аудита, а не USER().
