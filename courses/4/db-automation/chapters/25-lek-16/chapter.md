## Одна идея

Приложение деканата подключено к MySQL под пользователем `root` без пароля: так было удобно на первом занятии. В строке подключения пароль не нужен, зато любой, кто открыл исходники или просто сидит за этим компьютером, получает полный доступ к базе. Однажды в поле поиска студента вводят `' OR '1'='1`, и приложение показывает всю таблицу вместо одной записи.

Обе проблемы из одного корня: **приложение получило больше прав, чем ему нужно, и передаёт в базу текст, который не проверило**. Безопасность MySQL и .NET складывается из трёх рубежей, и каждый закрывает свою дверь.

> [!KEY]
> Минимальные права, защищённая строка подключения и параметризованный запрос закрывают большинство реальных атак. Шифрование и аудит нужны, но они не спасают от запроса, который приложение собрало из пользовательского ввода.

## Три рубежа защиты

Первый рубеж отвечает на вопрос «кто ты»: пользователь базы, его host и привилегии. Второй рубеж отвечает «как ты подключаешься»: строка подключения, пароль, шифрование канала. Третий отвечает «что ты передаёшь»: проверка ввода и параметры запроса.

Рубежи не заменяют друг друга. Параметры не помогут, если приложение ходит под `root`: инъекция всё равно выполнится с полными правами. Шифрование не поможет, если пароль записан в коде и лежит в репозитории.

## Пользователи и host

В MySQL учётная запись задаётся парой «имя и host». `'dean_app'@'localhost'` и `'dean_app'@'127.0.0.1'` это разные пользователи с разными паролями и правами. Host ограничивает, откуда разрешено подключение: `localhost` для этого компьютера, `%` для любого адреса.

```sql
SELECT User, Host FROM mysql.user ORDER BY User, Host;
SHOW GRANTS FOR 'dean_app'@'localhost';
```

`SHOW GRANTS` показывает привилегии в виде команд `GRANT`. Это самый быстрый способ проверить, что приложение получило только `SELECT`, `INSERT`, `UPDATE` и `DELETE` на базу `dean`, и ничего больше.

В таблице `mysql.user` видно имя, host, плагин аутентификации и хеш пароля. Сам пароль там не хранится, поэтому «посмотреть пароль пользователя» невозможно, его можно только сменить.

Host `%` разрешает подключение с любого адреса, и для учебного стенда это лишний риск: база слушает только этот компьютер, поэтому достаточно `localhost`. Если приложение ходит по TCP на `127.0.0.1`, создают отдельную запись с этим host.

## root без пароля в XAMPP

XAMPP ставит `root` без пароля, чтобы первый запуск phpMyAdmin прошёл без настройки. Для учебного стенда это допустимо на время занятия, но приложение не должно работать под `root` ни при каких условиях.

Порядок действий такой: задать пароль `root`, обновить его в `.../xampp/phpMyAdmin/config.inc.php`, создать отдельного пользователя приложения и выдать ему минимальные права.

```sql
ALTER USER 'root'@'localhost' IDENTIFIED BY 'StrongRootPass!';
CREATE USER 'dean_app'@'localhost' IDENTIFIED BY 'AppPass!2026';
GRANT SELECT, INSERT, UPDATE, DELETE ON dean.* TO 'dean_app'@'localhost';
```

`FLUSH PRIVILEGES` нужен после ручного изменения таблиц прав, а после `GRANT` и `CREATE USER` сервер обновляет кеш сам. Пользователю приложения не нужны `DROP`, `ALTER`, `CREATE USER`, `FILE` и `SUPER`: каждое из этих прав расширяет ущерб от ошибки или атаки.

## Роли и минимальные права

Когда пользователей несколько, права удобнее выдавать ролям. Роль это набор привилегий, который выдают пользователю целиком.

```sql
CREATE ROLE 'dean_read';
GRANT SELECT ON dean.* TO 'dean_read';
GRANT 'dean_read' TO 'dean_app'@'localhost';
SET DEFAULT ROLE 'dean_read' TO 'dean_app'@'localhost';
```

`SET DEFAULT ROLE` делает роль активной при подключении, иначе пользователь её не получит автоматически. Проверяют результат тем же `SHOW GRANTS`, а ещё лучше делом: войти под `dean_app` и попробовать запрещённую операцию. Сообщение `Access denied` означает, что рубеж работает; успешное выполнение означает, что прав больше, чем нужно.

## SQL-инъекция

SQL-инъекция возникает, когда приложение склеивает команду из текста и пользовательского ввода. Ввод перестаёт быть данными и становится частью кода.

```csharp
var sql = "SELECT id, full_name FROM students WHERE email = '" + email + "'";
```

Если в поле почты ввести `x' OR '1'='1`, условие станет истинным для всех строк, и запрос вернёт всю таблицу. Если ввести `x'; DROP TABLE students; #`, к запросу добавится вторая команда. Опасен не сам апостроф, а то, что приложение доверило вводу управлять структурой команды.

## Параметры MySqlConnector

Правильное решение одно: запрос пишут один раз, а значения передают параметрами. Драйвер отправляет текст команды и данные отдельно, поэтому кавычки во вводе остаются кавычками внутри строки.

```csharp
await using var cmd = new MySqlCommand(
    "SELECT id, full_name FROM students WHERE email = @email", conn);
cmd.Parameters.AddWithValue("@email", email);
await using var reader = await cmd.ExecuteReaderAsync();
```

Параметры работают и в `INSERT`, и в `UPDATE`, и в `DELETE`. Значение параметра нельзя использовать как имя таблицы или колонки: для динамического выбора сортировки применяют белый список допустимых значений, а не подстановку из ввода.

Проверка ввода остаётся нужной, но у неё другая задача: не дать сохранить бессмысленные данные. Она не заменяет параметры, потому что проверку легко обойти, а параметр обойти нельзя.

## Пароли пользователей приложения

Пароли пользователей приложения это отдельная история. В таблице `students` не должно быть колонки с паролем в открытом виде: хранят только хеш, посчитанный медленной функцией вроде bcrypt или Argon2, и сравнивают хеши, а не исходные строки. MySQL для своих учётных записей тоже хранит хеш, поэтому восстановить забытый пароль нельзя, его только сбрасывают.

## Строка подключения и секреты

Пароль в коде это утечка, которая ждёт своего часа: он попадает в репозиторий, в историю git и в резервные копии исходников. Секрет берут из переменной окружения, файла вне репозитория или хранилища секретов.

```csharp
var password = Environment.GetEnvironmentVariable("DEAN_DB_PASSWORD")
    ?? throw new InvalidOperationException("Не задан DEAN_DB_PASSWORD");

var cs = new MySqlConnectionStringBuilder
{
    Server = "localhost",
    Port = 3306,
    Database = "dean",
    UserID = "dean_app",
    Password = password,
    CharacterSet = "utf8mb4",
    SslMode = MySqlSslMode.Preferred
}.ConnectionString;
```

`MySqlConnectionStringBuilder` собирает строку без ручной склейки, поэтому пароль со спецсимволами не сломает подключение. `SslMode = Preferred` включает шифрование, если сервер его поддерживает; в рабочей среде, где TLS настроен, ставят `Required`, чтобы соединение без шифрования не устанавливалось вовсе.

Строку подключения не пишут в журнал и не показывают в сообщении об ошибке. Если приложение падает, пользователю показывают короткий текст, а подробности с параметрами уходят в защищённый журнал.

## Дампы и шифрование

Дамп базы содержит все данные и часто лежит в папке загрузок или в общем каталоге. Доступ к нему должен быть не шире, чем к самой базе: отдельный каталог, права только у администратора, шифрование архива и хранение вне учебного компьютера.

```powershell
mysqldump -u dean_app -p --single-transaction `
  --routines --triggers --default-character-set=utf8mb4 dean > dean.sql
```

С ключом `-p` без значения команда спросит пароль интерактивно, и он не останется в истории команд. Файл `dean.sql` после создания шифруют и удаляют из временного каталога, а не оставляют «на всякий случай».

Дамп не должен лежать в папке, которую синхронизирует облачный диск или открывает веб-сервер: Apache в XAMPP отдаёт файлы из `htdocs`, и копия базы станет доступна по ссылке.

Шифрование бывает трёх видов, и путать их не стоит. **Канал** защищает данные в пути между приложением и сервером, для этого служит TLS. **Диск** защищает файлы базы и дампы, для этого служит шифрование тома. **Пароли пользователей приложения** хранят только в виде стойкого хеша, а не в открытом виде и не в MD5.

Зашифрован ли канал, проверяют по `SHOW STATUS LIKE 'Ssl_cipher'`: пустое значение означает, что соединение идёт открытым текстом.

## Типичные ошибки

- **Пароль в коде.** Секрет попадает в репозиторий и остаётся в истории git даже после удаления строки.
- **GRANT ALL.** Приложение получает право удалять и менять таблицы, хотя ему нужны только четыре операции с данными.
- **root для приложения.** Одна инъекция превращается в полный контроль над сервером.
- **Склейка запроса.** Параметры заменяют конкатенацию, а не дополняют её.
- **Дамп в общем каталоге.** Копия базы доступна всем, у кого есть доступ к папке.
- **Пароль в журнале.** Строка подключения попадает в лог приложения или в общий журнал MySQL.

## Проверьте себя

> [!CHECK] Приложение работает под `dean_app` с правами только на `dean`, но запрос всё равно склеен из ввода. Что может сделать атакующий?
> Прочитать, изменить или удалить данные в базе `dean`, потому что прав на это хватает. Он не сможет удалить другие базы или создать пользователя, но ущерб для деканата всё равно полный. Поэтому параметры нужны независимо от прав.

> [!CHECK] Почему `'dean_app'@'localhost'` не пустит приложение, если оно подключается к `127.0.0.1`?
> Это разные учётные записи: MySQL сравнивает и имя, и host. Для адреса `127.0.0.1` нужен отдельный пользователь или host `%`, выданный осознанно. Проверяют это `SELECT User, Host FROM mysql.user`.

> [!CHECK] Зачем нужен `SslMode = Required`, если база стоит на том же компьютере?
> На одном компьютере трафик не выходит в сеть, и TLS менее важен. В рабочей среде база часто стоит на отдельном сервере, и без шифрования пароль и данные идут по сети открытым текстом. `Required` запрещает незашифрованное подключение.

## Итог

- Безопасность держится на трёх рубежах: права, подключение и параметры запроса.
- Учётная запись MySQL задаётся парой «имя и host», а `SHOW GRANTS` показывает её привилегии.
- `root` без пароля допустим только на учебном стенде, приложение работает под отдельным пользователем.
- SQL-инъекция лечится параметрами `MySqlConnector`, а не экранированием кавычек.
- Секреты хранят вне кода, дампы защищают, канал и диск шифруют.
