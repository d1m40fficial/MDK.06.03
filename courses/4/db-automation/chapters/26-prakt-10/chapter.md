## Цель работы

Аудит нужен не для отчёта, а для ответа на вопрос, кто и что сделал с данными. Без журнала инцидент разбирают по догадкам, а доступ к журналу у приложения превращает защиту в формальность. Цель работы: включить аудит учебной базы «Деканат», собрать события по тестовым изменениям и проверить защиту доступа, секретов и самого журнала.

Результат работы это настройки аудита, выгрузка событий, доказательство запрета на изменение журнала и список рисков с мерами.

## Оборудование и программное обеспечение

- Персональный компьютер с VirtualBox и учебной виртуальной машиной Ubuntu Server.
- PostgreSQL 16 в гостевой системе, доступ `sudo` внутри машины.
- Клиент `psql`, текстовый редактор, табличный редактор.
- Учебная база `dean`, роли `dean_owner`, `dean_app`, `student_read`, `auditor`.
- Файл конфигурации `/etc/postgresql/16/main/pg_hba.conf`.

SQL-команды выполняются через `sudo -u postgres psql -d dean`, если в команде не указано другое подключение. Операции от имени приложения выполняются отдельной сессией `psql -U dean_app -h 127.0.0.1 -d dean`.

## Краткие теоретические сведения

### Три источника событий

Серверный журнал пишет то, что видит сервер: подключения, отключения, текст операторов, ошибки. Он включается параметрами `log_connections`, `log_disconnections` и `log_statement`. Журнал удобен для разбора инцидента, но не знает смысла изменения: в нём есть оператор, а не строка таблицы до и после.

Триггерный аудит пишет события в обычную таблицу. Триггер видит старые и новые значения строки, поэтому отвечает на вопрос, что именно изменилось. Таблица аудита живёт в базе, её можно выгрузить запросом и ограничить правами.

Третий источник это специализированное расширение `pgaudit`, которое задаёт политику по объектам и ролям. В учебной работе достаточно первых двух источников, но в списке рисков стоит указать, что политика аудита без расширения задаётся вручную.

| Источник | Что фиксирует | Где хранится | Ограничение |
|---|---|---|---|
| Серверный журнал | Подключения, операторы, ошибки | Файл в `/var/log/postgresql` | Нет старых и новых значений |
| Триггерная таблица | Изменения строк с деталями | Таблица `audit_log` | Нужен триггер на каждую таблицу |
| Расширение `pgaudit` | События по политике | Журнал сервера | Требует установки и настройки |

### Что делает событие пригодным для разбора

Событие отвечает на пять вопросов: кто, когда, что, над каким объектом, с каким результатом. Поэтому в таблице есть пользователь, время, действие, имя таблицы, идентификатор строки и подробности в `jsonb`. Запись без пользователя или без времени для разбора бесполезна.

### Защита журнала

Журнал аудита защищают тремя мерами. Первая: отдельная роль `auditor` только на чтение. Вторая: запрет `UPDATE` и `DELETE` для приложения и для владельца приложения. Третья: отсутствие прямого `INSERT` у приложения, запись идёт через функцию триггера с правами владельца. Если приложение может править журнал, аудит не доказывает ничего.

### Доступ, секреты и копии

`pg_hba.conf` задаёт, кто и с какого адреса подключается и каким методом проверяется пароль. Опасны строки с методом `trust`, широкие диапазоны вроде `0.0.0.0/0` и порядок строк: первое совпадение выигрывает. SSL защищает пароль и данные в сети. Файл `.pgpass` хранит пароль для автоматических запусков и должен иметь права `600`. Пароль в командной строке виден в списке процессов и в истории оболочки, поэтому это риск, а не удобство.

## Ход работы

Первой строкой каждого вывода печатайте фамилию и группу: в `psql` это `SELECT 'Иванов И.И., ИС-41' AS student;`, в оболочке `echo "Иванов И.И., ИС-41"`.

### Шаг 1. Включите серверный журнал

Задайте параметры через `ALTER SYSTEM`, чтобы они пережили перезапуск, и примените их перечитыванием конфигурации.

```sql
ALTER SYSTEM SET log_statement = 'all';
ALTER SYSTEM SET log_connections = on;
ALTER SYSTEM SET log_disconnections = on;
SELECT pg_reload_conf();
```

Проверьте значения. Параметр `log_statement = 'all'` пишет и текст операторов, поэтому не выполняйте при нём смену паролей: пароль попадёт в журнал открытым текстом.

```sql
SELECT name, setting
FROM pg_settings
WHERE name IN ('log_statement', 'log_connections', 'log_disconnections',
               'log_destination', 'logging_collector', 'log_directory');
```

Приложите скриншот результата. В кадре должны быть видны значения `all`, `on` и `on`, а не только имена параметров.

### Шаг 2. Прочитайте события подключения

Откройте новую сессию `psql`, выйдите из неё и найдите записи в журнале. На Ubuntu файл обычно лежит в `/var/log/postgresql/postgresql-16-main.log`; точное имя проверьте командой `sudo ls /var/log/postgresql/`.

```bash
sudo grep -E 'connection authorized|disconnection: session time' \
  /var/log/postgresql/postgresql-16-main.log | tail -n 10
```

Приложите скриншот двух событий: вход и выход. Сравните их с действиями, которые вы выполнили, и запишите, какие сведения о пользователе и базе даёт серверный журнал.

### Шаг 3. Создайте триггерную таблицу аудита

В базе уже есть таблица `audit_log`. Создайте функцию, которая пишет событие при изменении строки, и повесьте её на `students`. Функция объявлена с правами владельца, чтобы приложение не нуждалось в прямом `INSERT` в журнал. Выполните блок от имени владельца объектов, иначе функция получит права суперпользователя.

```sql
SET ROLE dean_owner;

CREATE OR REPLACE FUNCTION audit_students() RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
BEGIN
  INSERT INTO audit_log(db_user, action, table_name, row_id, details)
  VALUES (session_user, TG_OP, TG_TABLE_NAME,
          CASE WHEN TG_OP = 'DELETE' THEN OLD.id ELSE NEW.id END::text,
          jsonb_build_object(
            'old', CASE WHEN TG_OP IN ('UPDATE', 'DELETE') THEN to_jsonb(OLD) END,
            'new', CASE WHEN TG_OP IN ('INSERT', 'UPDATE') THEN to_jsonb(NEW) END));
  RETURN NULL;
END;
$$;

DROP TRIGGER IF EXISTS students_audit ON students;
CREATE TRIGGER students_audit
AFTER INSERT OR UPDATE OR DELETE ON students
FOR EACH ROW EXECUTE FUNCTION audit_students();

RESET ROLE;
```

В функции с правами владельца `current_user` вернул бы владельца функции, а не того, кто выполнил оператор. Поэтому журнал пишет `session_user`: это учётная запись, под которой установлено соединение.

Проверьте, что триггер создан: `SELECT tgname, tgrelid::regclass FROM pg_trigger WHERE NOT tgisinternal;`.

### Шаг 4. Выполните тестовые изменения

Сделайте три операции от имени приложения и прочитайте журнал. Для проверки нужен пользователь, у которого есть права на `students`, но нет права менять `audit_log`. Откройте сессию приложения.

```bash
psql -U dean_app -h 127.0.0.1 -d dean
```

```sql
INSERT INTO students(full_name, group_id, email)
VALUES ('Тестов Тест Тестович', 1, 'test.audit@example.ru');

UPDATE students SET email = 'test.audit2@example.ru'
WHERE email = 'test.audit@example.ru';

DELETE FROM students WHERE email = 'test.audit2@example.ru';
```

```sql
SELECT id, at, db_user, action, table_name, row_id,
       details->'new'->>'email' AS new_email
FROM audit_log
ORDER BY id DESC
LIMIT 10;
```

Приложите скриншот событий: в нём видны три действия `INSERT`, `UPDATE`, `DELETE` и значения `old` и `new` хотя бы для одного из них.

### Шаг 5. Защитите журнал от изменения

Отзовите у приложения все права на журнал и оставьте чтение только роли `auditor`.

```sql
REVOKE ALL ON audit_log FROM PUBLIC;
REVOKE ALL ON audit_log FROM dean_app;
GRANT SELECT ON audit_log TO auditor;
```

Проверьте запрет от имени приложения. Ошибка прав это и есть доказательство того, что мера работает.

```bash
psql -U dean_app -h 127.0.0.1 -d dean \
  -c "UPDATE audit_log SET action = 'x' WHERE id = 1;"
```

Приложите скриншот сообщения `permission denied for table audit_log`. Затем повторите `INSERT` в `students` от `dean_app` и убедитесь, что изменение прошло. Событие проверьте отдельной сессией `auditor` или `postgres`: приложение журнал уже не читает, а триггер не должен сломать обычную работу.

### Шаг 6. Проверьте роли и права

Соберите список ролей и их атрибутов. Суперпользователь, `CREATEDB` и `CREATEROLE` у прикладной роли это избыточные права.

```sql
SELECT rolname, rolsuper, rolcreatedb, rolcreaterole, rolbypassrls, rolcanlogin
FROM pg_roles
WHERE rolname !~ '^pg_'
ORDER BY rolname;
```

```sql
SELECT grantee, table_name,
       string_agg(privilege_type, ', ' ORDER BY privilege_type) AS privileges
FROM information_schema.role_table_grants
WHERE table_schema = 'public'
GROUP BY grantee, table_name
ORDER BY grantee, table_name;
```

Заполните таблицу ожиданий и сравните с фактическим результатом.

| Роль | Назначение | Ожидаемые права | Фактические права | Расхождение |
|---|---|---|---|---|
| `dean_read` | Чтение данных | `SELECT` на таблицы |  |  |
| `dean_write` | Изменение данных | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |  |  |
| `student_read` | Свои данные | `SELECT` на представление или таблицу |  |  |
| `auditor` | Разбор инцидентов | `SELECT` на `audit_log` |  |  |
| `dean_app` | Приложение | Только необходимые операции |  |  |

### Шаг 7. Проверьте правила подключения

Прочитайте `pg_hba.conf` без комментариев и пустых строк. Порядок строк важен: первое совпадение определяет метод проверки.

```bash
sudo grep -vE '^\s*(#|$)' /etc/postgresql/16/main/pg_hba.conf
```

Приложите скриншот файла. Отметьте в отчёте каждую строку с `trust`, с широким диапазоном адресов и с методом `md5`: первые две опасны, третья уступает `scram-sha-256`. Если в вашей машине есть строка `host all all 0.0.0.0/0 trust`, это критический риск, даже если база учебная.

### Шаг 8. Проверьте SSL

Убедитесь, что сервер принимает защищённые соединения. Локальное соединение через сокет SSL не использует, поэтому параметры шифрования проверяйте в TCP-сессии.

```sql
SHOW ssl;
```

Подключитесь с требованием шифрования и выполните запрос в этой же сессии.

```bash
psql "host=127.0.0.1 dbname=dean user=dean_app sslmode=require"
```

```sql
SELECT a.usename, s.ssl, s.version, s.cipher
FROM pg_stat_ssl s
JOIN pg_stat_activity a USING (pid)
WHERE a.pid = pg_backend_pid();
```

Если `ssl` равно `true`, пароль и данные идут по шифрованному каналу. Если соединение с `sslmode=require` падает, запишите это как риск передачи данных открытым текстом.

### Шаг 9. Настройте `.pgpass` и найдите секреты

Создайте файл паролей для автоматических запусков и закройте его правами `600`. Замените слово `пароль` на пароль роли `dean_app`; пароль в командной строке больше не нужен.

```bash
printf '%s\n' '127.0.0.1:5432:dean:dean_app:пароль' > ~/.pgpass
chmod 600 ~/.pgpass
ls -l ~/.pgpass
psql -h 127.0.0.1 -U dean_app -d dean -c "SELECT current_user;"
```

Найдите секреты в скриптах проекта. Ищите переменные с паролями, строки подключения и ключи.

```bash
find /opt/dean "$HOME" -name '*.sh' -exec grep -HniE 'PGPASSWORD|password|secret|token' {} +
```

Каждую находку внесите в список рисков. Если пароль хранится в скрипте открытым текстом, мера это переменная окружения из защищённого файла или `.pgpass`, а не переименование переменной.

### Шаг 10. Составьте список рисков

Сведите находки в таблицу. У риска есть источник, влияние, вероятность, мера и остаточный риск после меры. Мера без проверки не считается выполненной.

| Риск | Где обнаружен | Влияние | Вероятность | Мера | Остаточный риск |
|---|---|---|---|---|---|
| Избыточные права приложения | Список ролей | Изменение любых данных | Высокая | Отозвать лишние права | Низкий |
| Журнал доступен приложению | Права на `audit_log` | Сокрытие следов | Средняя | Запрет `UPDATE` и `DELETE` | Низкий |
| `trust` в `pg_hba.conf` | Файл правил | Вход без пароля | Высокая | Заменить на `scram-sha-256` | Низкий |
| Пароль в скрипте | Поиск секретов | Утечка при копировании | Средняя | `.pgpass` с правами `600` | Средний |
| Соединение без SSL | `pg_stat_ssl` | Перехват пароля | Средняя | `sslmode=require` | Низкий |
| Копии без защиты | Каталог копий | Утечка всей базы | Средняя | Шифрование и права на каталог | Средний |
| Журнал без ротации | Настройки сервера | Переполнение диска | Средняя | Ротация и срок хранения | Низкий |

### Требования к отчёту

Соберите отчёт из настроек аудита, определений функции и триггера, выгрузки событий, проверки прав, `pg_hba.conf`, SSL, `.pgpass` и списка рисков. Для каждого риска укажите, подтверждён он проверкой или остался предположением.

Скриншоты шапки отчёта, теории и пустых окон не нужны. Доказательствами служат кадры с настройками, событиями аудита, ошибкой доступа и файлом правил.

## Критерии оценки

| Критерий | Баллы | Что проверяется |
|---|---|---|
| Настройка аудита | 15 | Параметры включены и подтверждены запросом |
| Триггерный аудит | 20 | События содержат пользователя, действие и старые и новые значения |
| Защита журнала | 20 | Права ограничены, запрет доказан ошибкой доступа |
| Проверка ролей и доступа | 20 | Роли, права, `pg_hba.conf` и SSL проверены |
| Секреты | 10 | `.pgpass` с правами `600`, поиск находок выполнен |
| Список рисков | 15 | Риски подтверждены, меры конкретны, остаточный риск оценён |
| **Итого** | **100** | Зачёт от 60 баллов |
