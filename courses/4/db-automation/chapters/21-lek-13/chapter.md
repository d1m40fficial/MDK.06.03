## Одна идея

Администратор уходит в отпуск на две недели. Копии базы делает его ручная привычка: каждую пятницу после пар. Привычка уходит вместе с ним, и две недели база живёт без копии. Никто не замечает этого, пока в первую неделю после отпуска не падает диск.

**Обслуживание должно запускаться без человека.** Для этого есть два механизма, и они решают разные задачи. Планировщик заданий Windows запускает программы: `DeanAdmin.exe`, `mysqldump`, скрипт PowerShell. Планировщик событий MySQL запускает SQL внутри сервера: чистку, пересчёт, архивирование строк.

Соблазн выбрать один механизм на всё понятен, но он ведёт к костылям. Событие MySQL не умеет вызвать `mysqldump`, потому что это внешняя программа. Планировщик Windows не умеет работать с базой без программы, которую сам и запускает. Поэтому в рабочем регламенте почти всегда есть оба.

В графическом интерфейсе задание создают через «Создать задачу», а не через «Создать простую задачу»: простая форма не показывает ни рабочую папку, ни правило повторного запуска.

Порядок настройки:

1. **Общие.** Имя вида `Dean backup`, описание. Отметка «Выполнять вне зависимости от того, зарегистрирован ли пользователь» и, если нужно, «Выполнять с наивысшими правами».
2. **Триггеры.** Ежедневно в 23:00, отметка «Выполнить задачу как можно скорее после пропущенного запуска».
3. **Действия.** Программа `C:\DeanAdmin\publish\DeanAdmin.exe`, аргументы `backup`, рабочая папка `C:\DeanAdmin\publish`.
4. **Условия.** Снять отметку «Запускать только при питании от сети», иначе ноутбук не сделает копию от батареи.
5. **Параметры.** «Если задача уже выполняется, то: не запускать новый экземпляр», предел времени выполнения.

То же самое из командной строки:

```powershell
$action = New-ScheduledTaskAction -Execute "C:\DeanAdmin\publish\DeanAdmin.exe" `
  -Argument "backup" -WorkingDirectory "C:\DeanAdmin\publish"
$trigger = New-ScheduledTaskTrigger -Daily -At 23:00
$settings = New-ScheduledTaskSettingsSet -MultipleInstances IgnoreNew
Register-ScheduledTask -TaskName "Dean backup" -Action $action `
  -Trigger $trigger -Settings $settings -User "dean_task"
```

Регистрация через PowerShell требует прав администратора. Командлет создаёт задание в корне библиотеки, а имя с обратной косой чертой, например `Dean\Backup`, раскладывает задания по папкам. Проверить результат можно до наступления ночи.

```powershell
Get-ScheduledTask -TaskName "Dean backup" | Select-Object TaskName, State
```

Состояние `Ready` означает, что задание зарегистрировано и ждёт триггера. Состояние `Disabled` означает, что его выключили вручную или оно отключено политикой. Если задание не появилось, смотрят, от имени какого пользователя выполнялась регистрация: без прав администратора командлет вернёт отказ доступа.

## Почему ручной запуск работает, а задание падает

Причина почти всегда в окружении. Из консоли программа видит ваш профиль, вашу переменную `PATH`, ваш текущий каталог. Планировщик запускает её от другого пользователя и из другого каталога.

**Рабочая папка.** По умолчанию это `C:\Windows\System32`. Относительный путь `logs\dean-admin.log` окажется там, и искать его будут долго. Лечение: абсолютные пути в программе и поле «Рабочая папка» в задании.

**Переменная PATH.** У системной учётной записи другой набор путей, и `mysqldump` может не найтись. Лечение: полный путь `C:\xampp\mysql\bin\mysqldump.exe` вместо имени.

**Пользователь и права.** Задание от вашей учётной записи работает, пока вы вошли в систему. Отметка «вне зависимости от входа» требует пароля при регистрации и сохранённых учётных данных. Отдельный пользователь `dean_task` с правом читать каталог программы и писать в каталог копий решает обе задачи.

**Код возврата.** Планировщик показывает последний результат задания. Ноль это успех, всё остальное это сбой, и именно код связывает задание с журналом программы.

```powershell
Get-ScheduledTaskInfo -TaskName "Dean backup" |
  Select-Object LastRunTime, LastTaskResult, NextRunTime
```

`LastTaskResult` со значением `0x0` означает успех, `0x1` ошибку работы, `0x2` неверные аргументы. Эти же числа возвращает программа из прошлой лекции, поэтому отчёт читается без догадок.

> [!PITFALL] Задание выполнено, а копии нет
> Код 0 говорит, что программа дошла до конца, а не что файл появился. Проверяют размер файла, время изменения и строку журнала `backup file=... rows=...`. Пустой файл при коде 0 означает, что `mysqldump` не нашёлся и вывод оказался пустым.

## История и журнал задания

В свойствах задания есть вкладка «История». Она показывает запуски, длительность и код, но работает только при включённом журнале `Microsoft-Windows-TaskScheduler/Operational`. По умолчанию он выключен, поэтому вкладка пуста и создаёт ложное впечатление, что задание не запускалось.

Включить журнал можно в «Просмотре событий»: «Журналы приложений и служб», `Microsoft`, `Windows`, `TaskScheduler`, «Включить журнал». После этого история появляется и в Планировщике, и в событиях Windows.

Журнал задания отвечает на вопрос «запускалось ли», а журнал программы отвечает на вопрос «что получилось». Нужны оба. Первый показывает, что триггер сработал, второй показывает, сколько строк изменено.

## События MySQL

Событие это именованный SQL-код, который сервер выполняет по расписанию. Оно живёт внутри базы и не зависит от того, вошёл ли человек в Windows.

Планировщик событий включается параметром `event_scheduler`. Проверка:

```sql
SHOW VARIABLES LIKE 'event_scheduler';
```

Значение `ON` означает, что планировщик работает, `OFF` что выключен, `DISABLED` что его запрещено включать на ходу. Включение на время сессии сервера:

```sql
SET GLOBAL event_scheduler = ON;
```

Постоянное включение прописывают в `C:\xampp\mysql\bin\my.ini` в разделе `[mysqld]`:

```
event_scheduler=ON
```

После правки файла MySQL перезапускают из панели XAMPP: без перезапуска файл не прочитан и настройка не применится.

## Создание события

Событие задаёт расписание, момент начала и команду.

```sql
CREATE EVENT IF NOT EXISTS ev_cleanup_audit
ON SCHEDULE EVERY 1 DAY
STARTS '2026-04-01 23:30:00'
ON COMPLETION PRESERVE
ENABLE
DO
  DELETE FROM audit_log
  WHERE at < NOW() - INTERVAL 365 DAY;
```

`ON COMPLETION PRESERVE` оставляет событие в базе после выполнения. Без этой фразы событие удаляется, и расписание исчезает после первого срабатывания. `ENABLE` включает событие сразу, `DISABLE` создаёт его выключенным, что удобно для проверки.

Список событий смотрится двумя способами:

```sql
SHOW EVENTS FROM dean;

SELECT event_name, status, last_executed, starts,
       interval_value, interval_field, definer
FROM information_schema.EVENTS
WHERE event_schema = 'dean';
```

`last_executed` это главный столбец. Если он пуст, событие ни разу не срабатывало, и причина почти всегда в выключенном планировщике или в статусе `DISABLED`.

Перед включением тело события выполняют вручную: тот же `DELETE` запускают в phpMyAdmin и смотрят, сколько строк он затрагивает. Если число неожиданно большое, условие переписывают до включения события. После проверки событие включают и ждут первого срабатывания, чтобы увидеть `last_executed`.

Остановить событие можно, не удаляя его. `ALTER EVENT ev_cleanup_audit DISABLE;` выключает расписание, а `ENABLE` возвращает. Удаление через `DROP EVENT` стирает и расписание, и тело, поэтому перед удалением полезно сохранить текст из `SHOW CREATE EVENT ev_cleanup_audit;`.

Права на создание события выдаются отдельно:

```sql
GRANT EVENT ON dean.* TO 'dean_app'@'localhost';
```

Событие выполняется от имени того, кто его создал, то есть от `definer`. Если этого пользователя удалить или лишить прав, событие перестанет работать, хотя останется в списке. Поэтому события создают от служебной учётной записи, а не от личной.

> [!TRADEOFF] Событие или задание Windows
> Событие живёт рядом с данными и не требует программы, но умеет только SQL и не запускает внешние процессы. Задание Windows запускает что угодно, но зависит от учётной записи и путей. Копию делает задание, чистку делает событие.

## Окно обслуживания

**Окно обслуживания** это время, когда нагрузка минимальна и можно менять данные без помех пользователям. Для учебной базы это ночь, для рабочей системы время выбирают по статистике подключений.

Внутри окна задачи разносят по времени: копия в 23:00, чистка в 23:30, пересчёт отчётов в 00:00. Так они не конкурируют за блокировки и диск.

```sql
CREATE EVENT IF NOT EXISTS ev_refresh_stats
ON SCHEDULE EVERY 1 WEEK
STARTS '2026-04-05 00:00:00'
ON COMPLETION PRESERVE
DO
  ANALYZE TABLE students, enrollments, payments;
```

`ANALYZE TABLE` обновляет статистику, по которой планировщик строит планы. Без неё после массовой загрузки планы становятся неточными.

## Пересечение запусков

Две копии одной задачи опасны: они делят диск, мешают друг другу и создают два файла с одним именем. У Планировщика Windows правило задаётся явно: «не запускать новый экземпляр». У событий MySQL такой защиты нет.

Если событие не успело закончиться к следующему запуску, MySQL может запустить второй экземпляр. Лечится это именованной блокировкой.

```sql
DELIMITER $$

ALTER EVENT ev_cleanup_audit
DO
BEGIN
  IF GET_LOCK('dean_cleanup', 0) = 1 THEN
    DELETE FROM audit_log
    WHERE at < NOW() - INTERVAL 365 DAY;
    DO RELEASE_LOCK('dean_cleanup');
  END IF;
END$$

DELIMITER ;
```

`GET_LOCK` с нулевым таймаутом пытается взять блокировку один раз и сразу возвращает результат. Если блокировку уже держит предыдущий экземпляр, условие ложно, и второй запуск завершается, не трогая данные. `RELEASE_LOCK` освобождает имя сразу после удаления, чтобы следующий запуск не ждал конца сессии.

`DELIMITER` меняет разделитель команд для клиента, потому что внутри `BEGIN` и `END` встречаются точки с запятой. В phpMyAdmin то же самое делает поле «Разделитель» в форме создания события.

Для больших таблиц удаление делают порциями, чтобы не держать блокировку минутами.

```sql
DELETE FROM audit_log
WHERE at < NOW() - INTERVAL 365 DAY
ORDER BY id
LIMIT 5000;
```

Порция удаляется быстро, а остальное дочищается следующим запуском. Так окно обслуживания не растягивается на всю ночь.

## Проверка после настройки

Настроенное задание проверяют, не дожидаясь ночи. В Планировщике есть «Выполнить» в контекстном меню, а в PowerShell команда запуска.

```powershell
Start-ScheduledTask -TaskName "Dean backup"
```

После запуска смотрят три вещи: код возврата, строку в журнале программы и появившийся файл копии. Если что-то не совпало, разбор идёт по цепочке: сработал ли триггер, запустился ли процесс, дошёл ли он до базы, записался ли результат.

Для события проверка та же, но средствами SQL: `last_executed`, число строк до и после, отсутствие ошибок в журнале ошибок MySQL `C:\xampp\mysql\data\mysql_error.log`.

## Типичные ошибки

- **Запуск от пользователя без прав.** Задание от учётной записи, которая не может читать каталог программы или писать в каталог копий, падает с кодом доступа. Лечение: отдельный пользователь с точными правами.
- **Нет PATH.** `mysqldump` вызывается по имени, а у системной учётной записи такого пути нет. Лечение: полный путь к программе.
- **Нет лога.** Задание упало ночью, и причину восстановить нечем. Лечение: журнал программы плюс история задания.
- **Пересечение запусков.** Копия идёт дольше суток, и вторая начинается поверх первой. Лечение: правило «не запускать новый экземпляр» и именованная блокировка для событий.
- **Событие без `ON COMPLETION PRESERVE`.** После первого срабатывания расписание исчезает, и чистка больше не повторяется.
- **Выключенный `event_scheduler`.** Событие создано, но не выполняется ни разу. Лечение: проверить `SHOW VARIABLES` и прописать параметр в `my.ini`.
- **Событие от удалённого пользователя.** `definer` исчез, и событие падает при каждом запуске. Лечение: служебная учётная запись и проверка `information_schema.EVENTS`.

## Проверьте себя

> [!CHECK] Задание завершилось с кодом 0, но копия не появилась. Где искать причину?
> В журнале программы: есть ли строка о запуске `mysqldump`, какой код вернул процесс и какой размер файла получен. Код 0 у задания означает только, что `DeanAdmin.exe` завершился штатно. Частая причина это пустой путь к `mysqldump`, из-за которого вывод оказался пустым.

> [!CHECK] Событие создано, `last_executed` пуст. Что проверить в первую очередь?
> Значение `event_scheduler` и статус события. При `OFF` или `DISABLED` событие не запускается, хотя строка в `information_schema.EVENTS` есть. Второй подозреваемый это `definer`: если пользователь удалён, событие падает при каждом срабатывании.

> [!CHECK] Почему копию не делают событием MySQL?
> Событие выполняет только SQL внутри сервера и не запускает внешние программы. `mysqldump` это отдельный процесс, поэтому его запускает Планировщик Windows, а событие отвечает за чистку и пересчёт внутри базы.

## Итоги

- Задание Windows состоит из триггера, действия и параметров, и параметры ломаются чаще всего.
- Рабочая папка, `PATH` и учётная запись задают окружение, которого нет при ручном запуске.
- История задания включается отдельно, а журнал программы пишет результат.
- Событие MySQL живёт в базе, требует включённого `event_scheduler` и прав `EVENT`.
- `ON COMPLETION PRESERVE` сохраняет расписание после первого запуска.
- Окно обслуживания и защита от пересечения запусков берегут данные и диск.

! Триггер задаёт время, действие задаёт программу, параметры задают окружение.

Q: Какая рабочая папка используется по умолчанию при запуске задания?
+ C:\Windows\System32
- Каталог программы
- Домашний каталог пользователя
- Каталог MySQL
! Поэтому относительные пути в задании не находят файлы.

Q: Почему mysqldump может не найтись при запуске из задания?
+ У системной учётной записи другой набор путей PATH
- Программа mysqldump удаляется после установки
- Планировщик запрещает внешние программы
- MySQL не работает ночью
! Надёжнее указывать полный путь к исполняемому файлу.

Q: Что означает LastTaskResult со значением 0x0?
+ Задание завершилось успешно
- Задание не запускалось
- Задание выполняется сейчас
- Задание отключено
! Ноль это код успеха, остальные значения означают сбой.

Q: Какая настройка включает планировщик событий MySQL?
+ event_scheduler = ON
- event_scheduler = DISABLED
- autocommit = 1
- log_bin = ON
! Параметр проверяют через SHOW VARIABLES и прописывают в my.ini.

Q: Что делает ON COMPLETION PRESERVE в событии?
+ Сохраняет событие после выполнения
- Удаляет событие после первого запуска
- Отключает расписание
- Меняет definer события
! Без этой фразы событие исчезает после срабатывания.

Q: От чьего имени выполняется событие MySQL?
+ От пользователя, указанного в definer
- От пользователя root всегда
- От учётной записи Windows
- От пользователя, который первым подключился
! Если definer удалён, событие перестаёт работать.

Q: Что показывает столбец last_executed в information_schema.EVENTS?
+ Время последнего срабатывания события
- Время создания события
- Время следующего запуска
- Время последней ошибки
! Пустое значение означает, что событие не срабатывало.

Q: Зачем нужна именованная блокировка GET_LOCK в событии?
+ Чтобы второй экземпляр события не начал работу
- Чтобы ускорить удаление строк
- Чтобы событие работало от другого пользователя
- Чтобы включить планировщик событий
! События MySQL не защищены от параллельного запуска сами по себе.

Q: Что настраивают в свойствах задания Windows?
+ Правило при уже выполняющейся задаче
+ Предел времени выполнения
+ Условие запуска при питании от сети
- Пароль пользователя базы данных
! Эти параметры определяют, как именно выполняется задание.

Q: Какие задачи подходят для события MySQL?
+ Чистка старых записей
+ Обновление статистики через ANALYZE TABLE
+ Пересчёт сводной таблицы по расписанию
- Запуск mysqldump
! Событие выполняет только SQL внутри сервера.

Q: Какие причины объясняют пустую вкладку «История» задания?
+ Журнал Microsoft-Windows-TaskScheduler/Operational выключен
+ Задание ещё ни разу не запускалось
+ Журнал был очищен
- Программа вернула код 0
! История хранится в отдельном журнале событий Windows.

Q: Что входит в окно обслуживания?
+ Время с минимальной нагрузкой на базу
+ Разнесение задач по времени внутри окна
+ Ограничение длительности тяжёлых операций
- Обязательное отключение сервера MySQL
! Окно нужно, чтобы обслуживание не мешало пользователям.

Q: Какой параметр включает планировщик событий в файле my.ini?
= event_scheduler=ON
= event_scheduler = ON
! Настройка вступает в силу после перезапуска MySQL.

= SHOW EVENTS FROM dean
= SHOW EVENTS
! SHOW EVENTS выводит события текущей базы или указанной схемы.
