## Одна идея

Скрипт копирования проверен вручную: запустили из терминала, файл появился, размер правдоподобный. Его ставят в расписание, и через сутки выясняется, что копии нет. Причина не в скрипте, а в том, что планировщик запустил его **в другом окружении**: от другого пользователя, с другим `PATH`, без переменных из профиля и не в том каталоге.

**Планировщик** это не «кнопка, которая нажимает скрипт по времени». Это отдельная среда исполнения со своими правилами: кто запускает, что видит процесс, куда пишется вывод и что считается успехом. Поэтому расписание и права здесь важнее текста скрипта.

Главная мысль: задание проектируют с конца. Сначала решают, как узнать, что оно сработало, и что делать при сбое, а уже потом выбирают время запуска.

## cron и systemd timers

В учебной Ubuntu доступны два планировщика. Оба решают одну задачу, но по-разному.

| Свойство | cron | systemd timer |
|---|---|---|
| Запись расписания | строка из пяти полей | секция `OnCalendar` |
| Окружение | минимальное, из файла crontab | задаётся в unit |
| Журнал | почта или перенаправление в файл | journald автоматически |
| Пропущенный запуск | не догоняет | `Persistent=true` догоняет |
| Зависимости | нет | `After=`, `Requires=` |
| Проверка | `crontab -l`, `grep CRON` | `systemctl list-timers` |

cron старше и проще: одна строка, никаких файлов служб. Его достаточно для учебного стенда и для задач, которые не требуют сложной логики. systemd timer даёт журнал без дополнительных настроек, умеет догонять пропущенный запуск и связывать задание с другими службами, например ждать запуска PostgreSQL.

На практике удобно так: cron для простых периодических команд, systemd timer для ночного обслуживания базы, где важны журнал и порядок запуска.

## Синтаксис расписания

Строка cron состоит из пяти полей и команды. Поля отделяются пробелами, порядок фиксирован.

| Поле | Допустимые значения | Пример |
|---|---|---|
| минута | 0 до 59 | 0 |
| час | 0 до 23 | 3 |
| день месяца | 1 до 31 | * |
| месяц | 1 до 12 | * |
| день недели | 0 до 7, где 0 и 7 это воскресенье | 1 |

Несколько примеров:

```
0 3 * * *      каждый день в 03:00
*/15 * * * *   каждые пятнадцать минут
0 3 * * 1      каждый понедельник в 03:00
0 4 1 * *      первого числа каждого месяца в 04:00
```

Звёздочка означает «любое значение», `*/15` означает «каждое значение с шагом 15», а перечисление через запятую задаёт набор, например `0 3 * * 1,3,5` для понедельника, среды и пятницы.

У cron есть неочевидное правило: если ограничены **и** день месяца, **и** день недели, задание запускается при совпадении **любого** из них, а не обоих. Строка `0 3 1 * 1` сработает и первого числа, и в каждый понедельник. Это редко нужно, но ошибка встречается.

Время cron берёт из системного часового пояса. Проверить его можно командой `timedatectl`, а в systemd пояс указывают прямо в расписании: `OnCalendar=*-*-* 03:00:00 Europe/Moscow`.

## Пользователь и окружение

Самая частая причина «в терминале работает, в расписании нет» это окружение. Интерактивная оболочка читает профиль, подставляет `PATH`, псевдонимы и переменные. cron и systemd запускают команду без профиля и с минимальным набором переменных.

Что это значит на практике:

- `PATH` содержит только системные каталоги, поэтому `pg_dump` может не найтись, если он лежит в `/usr/lib/postgresql/16/bin`;
- у cron текущий каталог это домашний каталог пользователя, у systemd корень `/`, а не тот, где вы запускали скрипт;
- псевдонимы и функции оболочки не работают;
- переменные вроде `PGPASSWORD` из вашего профиля отсутствуют.

Лечится это явно: в скрипте задают `PATH`, все пути делают абсолютными, а каталог меняют через `cd` или указывают в аргументах.

```bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
export PATH
cd /var/lib/dean || exit 1
```

Запускать задание от `root` нельзя. Скрипт обслуживания базы не должен иметь прав менять систему, а ошибка в нём от root обойдётся дороже. Для задания создают отдельного пользователя, например `dean_job`, и дают ему только нужные права: чтение своего каталога, запись в каталог копий, доступ к базе через роль `dean_read` или `dean_app`.

Проверяют задание тем же способом, каким его запустит планировщик: от нужного пользователя и с пустым окружением.

```bash
sudo -u dean_job env -i HOME=/home/dean_job PATH=/usr/bin:/bin \
  /usr/local/bin/dean-backup.sh --db dean --dry-run
```

Если команда проходит так, скорее всего она пройдёт и из cron. Если работает только из вашего терминала, проблема в окружении, а не в базе.

## .pgpass для задания

Пароль задание берёт из файла `.pgpass` того пользователя, от имени которого оно работает. Это значит, что файл должен лежать в домашнем каталоге `dean_job`, принадлежать ему и иметь права `600`.

```bash
sudo install -d -o dean_job -g dean_job -m 750 /etc/dean
sudo install -o dean_job -g dean_job -m 600 /dev/null /etc/dean/pgpass
```

Строка внутри обычная: хост, порт, база, пользователь, пароль.

```
127.0.0.1:5432:dean:dean_app:secret
```

Если файл лежит не в домашнем каталоге, путь задают переменной `PGPASSFILE` в unit или в самой команде. Главное, чтобы эту переменную видел процесс задания, а не ваша интерактивная оболочка.

Права проверяют после каждого изменения: `psql` отказывается читать файл, доступный группе или остальным. Сообщение об этом попадает в журнал, и ночью его никто не видит, поэтому проверку делают заранее от имени `dean_job`.

На схеме видно, что таймер не знает о базе: он только передаёт управление службе, а результат работы уходит в журнал и, при ошибке, в оповещение.

```ini
# /etc/systemd/system/dean-backup.service
[Unit]
Description=Backup of the dean database
After=postgresql.service

[Service]
Type=oneshot
User=dean_job
Group=dean_job
Environment=PGPASSFILE=/etc/dean/pgpass
ExecStart=/usr/local/bin/dean-backup.sh --db dean
Nice=10
IOSchedulingClass=idle
```

`Type=oneshot` говорит, что служба выполняет одну команду и завершается. `User` и `Group` задают пользователя задания. `Environment` передаёт путь к файлу паролей. `Nice` и `IOSchedulingClass` снижают приоритет, чтобы копия не мешала рабочим запросам.

Таймер ссылается на службу и задаёт расписание.

```ini
# /etc/systemd/system/dean-backup.timer
[Unit]
Description=Nightly backup of the dean database

[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true
RandomizedDelaySec=300
Unit=dean-backup.service

[Install]
WantedBy=timers.target
```

`Persistent=true` означает: если машина была выключена в момент запуска, задание выполнится после включения. `RandomizedDelaySec=300` добавляет случайную задержку до пяти минут, чтобы несколько заданий не стартовали в одну секунду.

После создания файлов systemd нужно перечитать конфигурацию и включить таймер.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now dean-backup.timer
systemctl list-timers --all
```

`enable --now` включает автозапуск и сразу активирует таймер. `list-timers` показывает, когда задание сработает в следующий раз и когда сработало в прошлый.

## Журнал и коды возврата

У systemd журнал есть по умолчанию: всё, что служба пишет в стандартные потоки, попадает в journald.

```bash
systemctl status dean-backup.service
journalctl -u dean-backup.service --since today
```

`status` показывает последний запуск и код возврата, `journalctl` даёт полный вывод с временными метками. Если служба завершилась с ошибкой, в журнале видно, на какой команде это произошло.

Код возврата службы это код возврата скрипта. Ноль означает успех, ненулевое значение означает сбой. Поэтому скрипт обязан возвращать осмысленный код, а не `exit 0` в конце любой ценой.

Для cron журнала по умолчанию нет: вывод уходит почтой, а почта на учебном сервере обычно не настроена. Поэтому в строке cron вывод перенаправляют в файл явно. В файле `/etc/cron.d/dean-backup` пользователя указывают отдельным полем между расписанием и командой.

```
0 3 * * * dean_job /usr/local/bin/dean-backup.sh --db dean >> /var/log/dean/backup.log 2>&1
```

Без `>> ... 2>&1` сообщение об ошибке теряется, и остаётся только догадываться, почему копии нет.

## Повторные попытки и оповещения

Сбой задания нужно заметить. Есть три уровня реакции.

**Повтор.** Если ошибка временная (база занята, не хватило места на минуту), запуск имеет смысл повторить. В systemd у службы типа `oneshot` нельзя включить `Restart=on-failure`, поэтому повтор делают отдельным заданием или циклом внутри скрипта с ограниченным числом попыток.

**Оповещение.** Для этого у службы есть директива `OnFailure`. Она запускает другую службу, когда основная завершилась с ошибкой.

```ini
[Unit]
Description=Backup of the dean database
OnFailure=dean-alert.service
```

Служба `dean-alert` может отправить письмо, записать событие в отдельный журнал или создать файл-флаг, который проверяет мониторинг. Важно, чтобы оповещение не зависело от той же базы, которая упала.

**Разбор.** После сбоя смотрят код возврата, журнал и состояние базы. Если задание упало из-за долгой транзакции, повтор без её завершения приведёт к тому же результату.

Для временных ошибок удобен код 75: он говорит внешнему обработчику, что запуск имеет смысл повторить позже. Постоянные ошибки, например неверный пароль или отсутствующая база, повтором не лечатся.

## Окно обслуживания

**Окно обслуживания** это время, когда тяжёлые работы не мешают пользователям. Ночная копия, очистка, перестройка индексов и миграции должны попадать в это окно.

При выборе времени учитывают три вещи:

- нагрузку на базу: копия читает все данные и занимает диск;
- другие задания: копия и очистка не должны идти одновременно;
- длительность: окно должно быть больше самой долгой работы с запасом.

Пересечение запусков решают двумя способами. Первый это `flock` в скрипте: вторая копия видит занятую блокировку и выходит. Второй это разнесение по времени и `RandomizedDelaySec`, чтобы задания не стартовали в одну минуту.

Перед тяжёлой работой полезно проверить, нет ли долгих транзакций: они держат снимок и мешают очистке.

```sql
select pid, state, age(now(), xact_start) as age
from pg_stat_activity
where datname = 'dean' and age(now(), xact_start) > interval '10 minutes';
```

Если такие сессии есть, тяжёлую операцию лучше отложить или сначала разобраться с ними. Иначе очистка не освободит место, а перестройка индекса будет ждать.

## Типичные ошибки

- **Запуск от root.** Задание получает лишние права, а ошибка в скрипте может затронуть систему. Для обслуживания базы создают отдельного пользователя.
- **Нет PATH.** В cron и systemd окружение минимальное, и `pg_dump` не находится. Путь задают в скрипте или в unit.
- **Нет журнала.** Вывод уходит в никуда, и причину сбоя не восстановить. Для cron перенаправляют вывод в файл, для systemd читают journald.
- **Пересечение запусков.** Две копии идут одновременно и мешают друг другу. Помогают `flock`, разные окна и случайная задержка.
- **Неверный часовой пояс.** Задание срабатывает не в 03:00, а в другое время, потому что сервер живёт в UTC. Проверяют `timedatectl` и указывают пояс явно.
- **Скрипт не исполняемый.** Файл без права выполнения или с символами возврата каретки в конце строк. Симптом: `bad interpreter` или `\r: command not found`.
- **Неверные права на .pgpass.** Файл доступен группе, и psql отказывается его читать. Права проверяют от имени пользователя задания.
- **Ошибка в расписании.** Перепутаны поля минуты и часа, и задание идёт каждый час вместо раза в сутки. Расписание проверяют по `list-timers` или по журналу cron.

> [!PITFALL] «Проверю вручную, а расписание поставлю потом»
> Ручной запуск из своей оболочки не проверяет ни пользователя, ни окружение, ни права на файлы. Проверка должна идти от имени задания и с тем же набором переменных, иначе сбой обнаружится в самый неудобный момент.

## Проверьте себя

> [!CHECK] Задание настроено на `0 3 * * *`, но копия появляется в 06:00. Что проверить?
> Часовой пояс сервера и время запуска. cron использует системное время, а сервер может работать в UTC. Проверяют `timedatectl` и при необходимости указывают пояс в расписании systemd или переносят время.

> [!CHECK] Скрипт отлично работает от вашего пользователя, а служба с `User=dean_job` падает с ошибкой доступа к базе. В чём причина?
> У `dean_job` нет своего `.pgpass` или файл имеет неверные права и владельца. Пароль из вашего домашнего каталога служба не видит. Файл создают для `dean_job` с правами 600 и проверяют запуск от его имени.

> [!CHECK] Зачем в таймере `Persistent=true`, если расписание и так ежедневное?
> Без него пропущенный из-за выключения машины запуск не выполнится. С `Persistent=true` systemd запоминает время последнего запуска и догоняет пропущенное после включения.

## Итог

- Планировщик запускает задание в другом окружении, от другого пользователя и без профиля.
- cron задаёт расписание пятью полями, systemd timer описывает его в `OnCalendar`.
- Задание запускают от отдельного пользователя с минимальными правами, а не от root.
- `PATH`, текущий каталог и `.pgpass` задают явно, иначе ночью задание не найдёт ни команду, ни пароль.
- `Type=oneshot`, `User`, `Environment` и `ExecStart` описывают службу, а `OnCalendar` и `Persistent` описывают таймер.
- Журнал systemd читают через `journalctl -u`, журнал cron настраивают перенаправлением вывода.
- Сбой замечают по коду возврата и `OnFailure`, а не по отсутствию файла.
- Окно обслуживания защищают от пересечений через `flock` и разнесение запусков.

Q: Сколько полей содержит расписание cron перед командой?
+ Пять
- Три
- Четыре
- Шесть
! Поля задают минуту, час, день месяца, месяц и день недели.

Q: Когда запустится задание с расписанием 0 3 * * *?
+ Каждый день в 03:00
- Каждые три часа
- Каждые три минуты
- Только третьего числа каждого месяца
! Первое поле это минута, второе час, звёздочки означают любой день и месяц.

Q: От какого пользователя выполняется служба systemd с директивой User=dean_job?
+ От dean_job
- От root
- От пользователя, запустившего systemctl
- От postgres
! Директива User задаёт учётную запись, от имени которой работает служба.

Q: Почему скрипт может работать в терминале, но падать из cron?
+ У задания другое окружение и другой PATH
- cron запрещает запускать bash
- cron удаляет файлы скрипта
- В cron нельзя обращаться к базе
! Профиль и переменные интерактивной оболочки в cron не загружаются.

Q: Где смотреть журнал службы systemd?
+ journalctl -u имя.service
- crontab -l
- psql -l
- systemctl list-timers
! journalctl показывает вывод службы с временными метками.

Q: Что делает параметр Persistent=true в таймере?
+ Догоняет запуск, пропущенный из-за выключения машины
- Запускает задание при каждой загрузке
- Запрещает повторный запуск
- Хранит журнал задания
! systemd запоминает время последнего запуска и выполняет пропущенное.

Q: Зачем нужен RandomizedDelaySec в таймере?
+ Разносит запуски нескольких заданий по времени
- Ускоряет выполнение скрипта
- Отключает журналирование
- Меняет пользователя задания
! Случайная задержка снижает пик одновременных запусков.

Q: Кто должен владеть файлом .pgpass задания?
+ Пользователь, от имени которого работает задание
- Пользователь root
- Любой пользователь группы sudo
- Роль postgres в базе
! psql читает файл от имени процесса задания и требует права 600.

Q: Что задают в секции Service файла службы?
+ Пользователя задания
+ Команду запуска
+ Переменные окружения
- Расписание запуска
- Список таймеров
! Расписание задаёт таймер, а служба описывает, что и от кого выполняется.

Q: Какие ошибки типичны при настройке планировщика?
+ Запуск задания от root
+ Отсутствие PATH в окружении задания
+ Отсутствие журнала
+ Пересечение запусков
- Явное указание абсолютных путей
- Проверка запуска от имени задания
! Лишние права, пустое окружение, отсутствие журнала и наложение запусков ломают задание.

Q: Что проверяют при сбое задания?
+ Код возврата службы
+ Записи в журнале
+ Права на файлы и доступ к базе
+ Наличие долгих транзакций
- Цвет оформления терминала
- Число установленных шрифтов
! Причину находят по коду, журналу, правам и состоянию базы.

Q: Что помогает заданиям не пересекаться по времени?
+ Блокировка flock в скрипте
+ Разные окна запуска
+ Случайная задержка запуска
- Запуск всех заданий в одну минуту
- Отключение журнала
! Блокировка, разнесение по окнам и случайная задержка не дают работам мешать друг другу.

Q: Какая команда показывает список таймеров systemd и время следующего запуска?
= systemctl list-timers
! list-timers выводит активные таймеры и время следующего срабатывания.

Q: Какой параметр таймера заставляет systemd выполнить пропущенный запуск?
= persistent
! Persistent=true догоняет запуск после включения машины.

Q: Как называется утилита просмотра журнала systemd?
= journalctl
! journalctl читает журнал служб, включая вывод задания.
