## Одна идея

Приложение деканата подключается к базе под ролью `postgres`. Так проще: не нужно ничего выдавать, всё работает. Потом в коде появляется ошибка, и один запрос удаляет таблицу `payments`. В журнале видно только `postgres`, а кто именно запускал запрос, непонятно. Отозвать доступ у подрядчика тоже нельзя: он работает под той же учётной записью, что и система.

**Доступ строится не на людях, а на ролях: роль описывает работу, человек или программа получает роль.** Чем точнее роль описывает работу, тем меньше прав достаётся случайно. Принцип минимальных привилегий звучит скучно, но именно он отделяет ошибку в коде от потери данных.

В этой лекции мы соберём набор ролей для учебной базы, выдадим права на разные объекты и научимся проверять, что лишнего доступа ни у кого нет.

## Роль и логин

В PostgreSQL нет отдельного понятия «пользователь». Есть роль, и роль с атрибутом `LOGIN` может подключаться к серверу. Команда `CREATE USER` это просто сокращение для `CREATE ROLE ... LOGIN`.

```sql
create role dean_owner nologin;
create role dean_read nologin;
create role dean_write nologin;
create role dean_app login password 'uchebnyi-parol';
```

Роль без `LOGIN` нельзя использовать для входа, но можно сделать владельцем таблиц или выдать ей привилегии. Это удобно: права описывают работу, а вход в систему остаётся отдельным решением.

Роли можно вкладывать друг в друга. Если выдать роль `dean_read` роли `dean_app`, приложение получит все права `dean_read`. Такая роль-группа не требует отдельного пароля и не считается учётной записью.

```sql
grant dean_read to dean_write;
grant dean_write to dean_app;
```

По умолчанию членство наследуется: `dean_app` сразу пользуется правами `dean_write` и `dean_read`, без дополнительных команд. Атрибут `INHERIT` включён у новых ролей, поэтому вложенность работает как обычное наследование.

## Привилегии на объекты

Права выдаются на конкретные объекты и проверяются по цепочке. Чтобы прочитать строку из таблицы, роли нужны три вещи: право `CONNECT` на базу, право `USAGE` на схему и право `SELECT` на таблицу. Пропуск любого звена даёт ошибку `permission denied`.

Привилегии делятся по видам объектов.

| Объект | Привилегии |
|---|---|
| База данных | `CONNECT`, `CREATE`, `TEMPORARY` |
| Схема | `USAGE`, `CREATE` |
| Таблица | `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER` |
| Последовательность | `USAGE`, `SELECT`, `UPDATE` |
| Функция | `EXECUTE` |

Выдача выглядит почти одинаково для всех объектов:

```sql
grant connect on database dean to dean_read, dean_write;
grant usage on schema public to dean_read, dean_write;
grant select on all tables in schema public to dean_read;
grant insert, update, delete on all tables in schema public to dean_write;
grant usage, select on all sequences in schema public to dean_write;
```

Обратите внимание на последовательности. Право `SELECT` на таблицу не даёт права брать `nextval` из последовательности. Если приложение вставляет строку с `serial`, ему нужно `USAGE` на последовательность, иначе вставка упадёт с ошибкой прав.

Вторая тонкость: `GRANT ... ON ALL TABLES` действует на таблицы, которые уже существуют. Таблица, созданная завтра, прав не получит. Для будущих объектов есть отдельный механизм, о нём ниже.

Отзыв прав выполняется командой `REVOKE` с той же структурой:

```sql
revoke insert, update, delete on all tables in schema public from dean_read;
revoke create on schema public from public;
```

Слово `PUBLIC` здесь означает не «все пользователи базы», а «все роли, включая будущие». Права, выданные `PUBLIC`, действуют на всякого, кто подключится. Поэтому `GRANT ALL ... TO PUBLIC` это худшее, что можно сделать с базой.

## Владелец и переключение роли

У каждого объекта есть владелец. Владелец может менять объект, удалять его, выдавать права другим и передавать владение. Поэтому владелец это не «ещё одна роль для удобства», а самая сильная позиция в базе.

```sql
alter table students owner to dean_owner;
alter schema public owner to dean_owner;
```

Если приложение создаёт таблицы само, оно становится их владельцем. Тогда оно может их удалить, даже не имея права `DELETE` на строки. Отсюда правило: **схему и таблицы создаёт отдельная роль, а приложение только работает с данными.**

Переключение роли внутри сеанса делает `SET ROLE`. Это удобно для проверки: администратор входит под своей учётной записью и временно становится другой ролью, чтобы увидеть базу её глазами.

```sql
set role dean_app;
select * from students limit 3;
reset role;
```

`SET ROLE` работает, только если текущая роль является членом указанной. Суперпользователь может переключиться в любую роль, и это ещё одна причина не давать приложению суперпользователя.

## Права по умолчанию

Проблема с `GRANT ON ALL TABLES` решается через `ALTER DEFAULT PRIVILEGES`. Команда задаёт правила для объектов, которые будут созданы позже указанной ролью в указанной схеме.

```sql
alter default privileges for role dean_owner in schema public
  grant select on tables to dean_read;

alter default privileges for role dean_owner in schema public
  grant select, insert, update, delete on tables to dean_write;
```

Здесь важно каждое слово. `FOR ROLE dean_owner` значит, что правило сработает для объектов, созданных именно этой ролью. Если таблицу создаст другая роль, правило не применится. `IN SCHEMA public` ограничивает действие схемой.

Без этой команды администратор каждый раз после миграции выдаёт права вручную и рано или поздно забудет. С ней новая таблица сразу доступна тем, кому положено, и закрыта для остальных.

## Разделение обязанностей

Хорошая схема ролей повторяет разделение работы, а не список людей. В учебной базе оно выглядит так:

- **`dean_owner`** владеет таблицами и последовательностями, выполняет миграции схемы. Вход в систему ей не нужен.
- **`dean_app`** работает с данными: читает и меняет строки, но не меняет схему.
- **`dean_read`** читает данные для отчётов и не может ничего изменить.
- **`student_read`** видит только то, что положено студенту, и не видит платежи.
- **`auditor`** читает журнал `audit_log` и не трогает рабочие таблицы.

Проверить схему просто: для каждой роли выпишите, что она должна делать, и сравните с тем, что ей выдано. Если роль может больше, чем описано, это избыточная привилегия.

Отдельная тема это общие учётные записи. Если три человека работают под одним логином, журнал не различит их действия, а смена пароля выключит всех сразу. У каждого человека должна быть своя учётная запись, а права приходят через роли.

## Аудит прав

Права имеют свойство накапливаться. Роль выдали на время, потом задача закончилась, а роль осталась. Поэтому раз в несколько месяцев полезно смотреть, что выдано на самом деле.

Список ролей и их атрибутов лежит в `pg_roles`:

```sql
select rolname, rolsuper, rolcanlogin, rolcreatedb, rolcreaterole, rolbypassrls
from pg_roles
where rolname not like 'pg\_%'
order by rolname;
```

Флаг `rolsuper` означает полный обход всех проверок. `rolbypassrls` обходит политики защиты строк. `rolcreatedb` и `rolcreaterole` позволяют создавать базы и роли. Для приложения все эти флаги должны быть ложными.

Выданные права на таблицы видны в `information_schema.role_table_grants`:

```sql
select grantee, table_name, privilege_type
from information_schema.role_table_grants
where table_schema = 'public'
order by grantee, table_name;
```

Точечная проверка делается функцией `has_table_privilege`. Она отвечает на вопрос «может ли эта роль сделать это с этой таблицей» и учитывает наследование ролей.

```sql
select has_table_privilege('dean_app', 'public.students', 'SELECT');
select has_table_privilege('student_read', 'public.payments', 'SELECT');
```

Второй запрос должен вернуть `false`. Если он вернул `true`, студент видит платежи, и это надо исправлять.

Членство в ролях хранится в `pg_auth_members`, а проверить его можно функцией `pg_has_role`. Эти запросы стоит сохранить как готовый скрипт проверки и запускать после каждой смены прав.

## Типичные ошибки

**`GRANT ALL ON ALL TABLES`.** Так выдают права «чтобы точно работало». Симптом: роль чтения может удалять строки, а приложение может менять схему. Лечение: выдавать по видам операций и проверять через `has_table_privilege`.

**Права на таблицу без `USAGE` на схему.** Студент получает `SELECT` на таблицу и всё равно видит `permission denied for schema public`. Лечение: помнить про цепочку база, схема, таблица.

**Приложение под суперпользователем.** Ошибка в коде или SQL-инъекция получает полный доступ к кластеру. Симптом: в журнале одна и та же роль для всех действий. Лечение: отдельная роль с `LOGIN` и минимальным набором привилегий.

**Забыли `ALTER DEFAULT PRIVILEGES`.** Сегодня права выданы, завтра миграция создала таблицу, и приложение упало. Лечение: правила по умолчанию плюс проверка после миграции.

**Пароль в открытом виде.** Пароль записан в скрипте или в истории команд. Симптом: строка подключения лежит в репозитории. Лечение: файл `.pgpass` с правами только для владельца или переменные окружения, а пароль меняется при подозрении на утечку.

## Проверьте себя

> [!CHECK] Роль `dean_read` получила `SELECT` на таблицу `students`, но запрос всё равно падает. Чего не хватает?
> Права `USAGE` на схему `public` и, возможно, `CONNECT` на базу. Проверка идёт по цепочке, и отсутствие любого звена даёт отказ.

> [!CHECK] Почему `ALTER DEFAULT PRIVILEGES FOR ROLE dean_owner` не сработает для таблицы, созданной ролью `dean_app`?
> Правило привязано к роли, которая создаёт объект. Объект, созданный другой ролью, под это правило не попадает, и права на него нужно выдавать отдельно.

> [!CHECK] Как проверить, что студент не видит платежи, не заходя под его паролем?
> Вызвать `has_table_privilege('student_read', 'public.payments', 'SELECT')`. Функция учитывает наследование ролей и отвечает за роль так, как ответила бы сама база.

## Итог

- Роль это единица прав, `LOGIN` лишь разрешает вход.
- Роли вкладываются друг в друга, и членство по умолчанию наследуется.
- Доступ проверяется по цепочке: база, схема, объект.
- Владелец объекта сильнее обычной роли, поэтому приложение владельцем не делают.
- `ALTER DEFAULT PRIVILEGES` закрывает проблему прав на будущие таблицы, а `pg_roles` и `information_schema` помогают найти лишнее.

Q: Чем роль с атрибутом LOGIN отличается от роли без него?
+ Она может подключаться к серверу
- Она всегда является суперпользователем
- Она не может владеть таблицами
- Она обходит проверку пароля
! LOGIN разрешает вход, остальные права всё равно выдаются отдельно.

Q: Что означает атрибут INHERIT у роли?
+ Роль пользуется привилегиями ролей, в которые входит
- Роль наследует пароль другой роли
- Роль получает права владельца всех таблиц
- Роль может создавать новые базы

- CONNECT
- EXECUTE

- Только CONNECT на базу
- Роль суперпользователя
