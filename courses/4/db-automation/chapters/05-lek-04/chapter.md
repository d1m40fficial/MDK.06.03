## Одна идея

Приложение деканата должно читать студентов, добавлять платежи и исправлять оценки. Ему не нужно удалять таблицы, создавать пользователей или читать чужие базы. Если выдать ему `root`, оно получит всё это сразу, и любая ошибка в коде станет ошибкой администратора.

**Доступ в MySQL это учётная запись, роль и привилегия на конкретный объект, и каждая часть сужает предыдущую.** Учётная запись отвечает на вопрос «кто», роль собирает типовой набор прав, привилегия разрешает конкретное действие над конкретной таблицей или столбцом. Чем уже выданное право, тем меньше последствий у ошибки.

## Пользователь и host

Учётная запись MySQL состоит из двух частей: имени и узла, с которого разрешено подключение. `'dean_app'@'localhost'` и `'dean_app'@'%'` это разные записи, хотя имя совпадает. Первая пускает только с локального компьютера, вторая с любого адреса.

| Запись | Кто подключается | Когда уместна |
|---|---|---|
| `'dean_app'@'localhost'` | только этот компьютер | приложение и phpMyAdmin на учебном стенде |
| `'dean_app'@'127.0.0.1'` | подключение по IP | если клиент обращается к адресу, а не к имени |
| `'dean_app'@'%'` | любой узел сети | сервер приложения на отдельной машине |
| `''@'localhost'` | анонимный вход | не должна существовать |

Сервер выбирает наиболее подходящую запись при подключении. Если для узла заведена анонимная учётная запись, она может перехватить соединение раньше именованной. Поэтому пустые имена в `mysql.user` лучше удалять.

```sql
CREATE USER 'dean_app'@'localhost' IDENTIFIED BY 'Slozhnyi-parol-2026';
SELECT user, host FROM mysql.user ORDER BY user, host;
```

Пароль задаётся при создании и хранится в виде хеша, а не открытым текстом. Сменить его можно командой `ALTER USER 'dean_app'@'localhost' IDENTIFIED BY 'novyi-parol';`. Удаление учётной записи выполняет `DROP USER`, а не `REVOKE`: отзыв прав оставляет пользователя без доступа, но сам вход в систему сохраняется.

Способ проверки пароля зависит от сервера. В MySQL 8 по умолчанию работает `caching_sha2_password`, в MariaDB из XAMPP обычно `mysql_native_password`. MySqlConnector поддерживает оба варианта, поэтому менять плагин вручную не требуется. Пароль всё равно должен быть длинным: короткий пароль подбирается автоматически за минуты, поэтому учебный стенд не открывают в общую сеть.

## Роли

Роль это именованный набор привилегий, который выдают нескольким пользователям. Без ролей приходится повторять один и тот же `GRANT` для каждого приложения и каждой замены сотрудника, и рано или поздно наборы прав расходятся.

```sql
CREATE ROLE dean_read;
CREATE ROLE dean_write;

GRANT SELECT ON dean.* TO dean_read;
GRANT SELECT, INSERT, UPDATE, DELETE ON dean.* TO dean_write;

GRANT dean_read TO 'student_read'@'localhost';
GRANT dean_write TO 'dean_app'@'localhost';
SET DEFAULT ROLE dean_read FOR 'student_read'@'localhost';
SET DEFAULT ROLE dean_write FOR 'dean_app'@'localhost';
```

Роль не является пользователем: у неё нет пароля, и подключиться под ней нельзя. При входе пользователь получает роли, назначенные по умолчанию, либо включает их командой `SET ROLE dean_write;`. Команда `SET ROLE NONE;` отключает роли в текущей сессии.

Синтаксис последней строки зависит от сервера. В сборке XAMPP на MariaDB применяют `SET DEFAULT ROLE dean_read FOR ...`, в MySQL 8 пишут `SET DEFAULT ROLE dean_read TO ...`. Смысл один: выбрать роль, которая действует сразу после подключения.

Проверить, какая роль действует в текущей сессии, можно командой `SELECT CURRENT_ROLE();`. Она возвращает имя роли или `NONE`. Если приложение ожидает права роли, а получает отказ, смотрят эту строку: роль могла быть выдана, но не включена.

Роли удобны, когда права меняются вместе с должностью. Студенту выдают `student_read` с правом читать ведомость, лаборанту `dean_write`, аудитору отдельную роль без права изменения. При увольнении достаточно отозвать роль, а не искать выданные по одной привилегии.

| Уровень | Запись | Пример |
|---|---|---|
| Глобальный | `*.*` | `GRANT PROCESS ON *.*` |
| База | `dean.*` | `GRANT SELECT ON dean.*` |
| Таблица | `dean.payments` | `GRANT INSERT ON dean.payments` |
| Столбец | `dean.students` | `GRANT SELECT (full_name, email) ON dean.students` |

Для приложения достаточно базы. Для отчёта, которому нужны только имя и почта, подойдёт уровень столбцов: остальные поля таблицы он не увидит. Уровень `*.*` оставляют для служебных задач: резервное копирование, наблюдение, управление пользователями.

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON dean.* TO 'dean_app'@'localhost';
GRANT SELECT (full_name, email) ON dean.students TO 'student_read'@'localhost';
REVOKE DELETE ON dean.payments FROM 'dean_app'@'localhost';
SHOW GRANTS FOR 'dean_app'@'localhost';
```

`REVOKE` отзывает ранее выданное право и не удаляет пользователя. `SHOW GRANTS` показывает итоговый набор, включая роли. После `CREATE USER` и `GRANT` команда `FLUSH PRIVILEGES` не нужна: сервер обновляет таблицы прав сам. Она требуется только при ручном изменении таблиц `mysql.*`.

Если глобальных прав нет, в выводе `SHOW GRANTS` есть строка `GRANT USAGE ON *.*`. Она означает, что учётная запись существует, но глобальных прав не имеет: `USAGE` не разрешает ничего, кроме входа. Если кроме `USAGE` и роли в выводе ничего нет, значит права выданы только через роль, и её проверяют отдельно.

> [!TRADEOFF] Роль или прямая привилегия
> Прямая привилегия быстрее выдаётся для одного человека, но плохо проверяется, когда пользователей десятки. Роль добавляет шаг настройки, зато набор прав описан в одном месте и его видно в `SHOW GRANTS`.

## Минимальные права для приложения

Приложению деканата нужны четыре команды над базой `dean`: `SELECT`, `INSERT`, `UPDATE`, `DELETE`. Ему не нужны `DROP`, `ALTER`, `CREATE`, `GRANT OPTION`, `FILE`, `PROCESS` и `SUPER`. Если приложение вдруг попытается удалить таблицу, сервер откажет, и это правильное поведение.

Отдельно стоит `GRANT OPTION`: право выдавать права другим. Его не дают приложению никогда, иначе ошибка в коде сможет создать нового пользователя с полным доступом.

Для чтения ведомости достаточно одной привилегии:

```sql
CREATE USER 'student_read'@'localhost' IDENTIFIED BY 'Chtenie-parol-2026';
GRANT SELECT ON dean.enrollments TO 'student_read'@'localhost';
GRANT SELECT ON dean.courses TO 'student_read'@'localhost';
```

Если студент должен видеть только свои строки, одной табличной привилегии мало: `SELECT` разрешает все строки. Ограничение по строкам делают через представление с условием и выдают право на представление, а не на таблицу.

Если приложение вызывает хранимые процедуры, вместо прямых прав на таблицы ему выдают `EXECUTE` на процедуру. Тогда доступ к данным остаётся внутри процедуры, а клиент не может выполнить произвольный `SELECT`. Для представлений добавляют `SHOW VIEW`, иначе описание представления не прочитается.

## Проверка из phpMyAdmin и .NET

Права проверяют не по тексту `GRANT`, а по поведению. В phpMyAdmin выходят из `root` и входят как `dean_app`. Вкладка `SQL` выполняет `SELECT * FROM students LIMIT 5;` и получает строки. Затем `DROP TABLE students;` должен завершиться ошибкой `DROP command denied`. Если таблица удалилась, права выданы слишком широко.

phpMyAdmin показывает только те базы, на которые у учётной записи есть хотя бы одно право. Если `dean_app` не видит `dean` в списке слева, значит `GRANT` не сработал или вход прошёл под другой записью. Это быстрая проверка перед запуском приложения.

В приложении .NET проверка выглядит так же, но результат приходит исключением:

```csharp
await using var cmd = new MySqlCommand("SELECT CURRENT_USER(), DATABASE();", conn);
await using var reader = await cmd.ExecuteReaderAsync();
if (await reader.ReadAsync())
    Console.WriteLine($"{reader.GetString(0)} в базе {reader.GetString(1)}");
```

`CURRENT_USER()` показывает учётную запись, которую выбрал сервер при проверке прав. Она может отличаться от имени, переданного клиентом: например, клиент представился как `dean_app`, а сервер сопоставил его с другой записью для этого узла.

Попытка запрещённой команды возвращает ошибку 1142 с текстом `command denied to user`. Это не сбой соединения, а нормальный отказ. Приложение должно показать понятное сообщение и записать событие в журнал, а не пытаться обойти запрет.

Отказ на входе с кодом 1045 означает, что сервер не принял имя, узел или пароль. Ошибка 1142 приходит позже, когда соединение уже установлено, но на конкретную команду прав нет. Лечатся они по-разному: первая проверяет учётную запись, вторая список привилегий.

Проверить выданные права можно и запросами к `information_schema`:

```sql
SELECT grantee, privilege_type FROM information_schema.SCHEMA_PRIVILEGES
WHERE table_schema = 'dean';
SELECT grantee, table_name, privilege_type FROM information_schema.TABLE_PRIVILEGES
WHERE table_schema = 'dean';
```

## Типичные ошибки

**GRANT ALL ON *.*.** Одна строка выдаёт всё, включая управление пользователями и доступ к чужим базам. Она удобна на учебном стенде и недопустима для приложения. Взамен пишут список из четырёх команд на конкретную базу.

**root для приложения.** В XAMPP `root` входит без пароля, поэтому соблазн велик. Но приложение с `root` не ограничено ничем: ошибка в `DELETE` без `WHERE` удалит данные, а SQL-инъекция позволит создать нового администратора. Для приложения создают `dean_app`.

**Пользователь с любым host.** `'dean_app'@'%'` пускает с любого адреса, включая соседний компьютер в аудитории. Для локального стенда достаточно `localhost`. Если приложение вынесено на другой сервер, указывают его конкретный адрес, а не шаблон.

**Роль выдана, но не включена.** Пользователь входит, но не видит таблиц, потому что роль не назначена по умолчанию и не активирована. Проверка `SHOW GRANTS` показывает роль, а `CURRENT_ROLE()` объясняет, действует ли она в сессии.

**Общая учётная запись на группу.** Когда один пароль знают пять человек, невозможно понять, кто изменил оценку. У каждого администратора должна быть своя запись, а общие приложения получают отдельную сервисную.

**Забытый REVOKE.** Сотрудник перешёл в другой отдел, а права остались. Регламент должен включать проверку `mysql.user` и `SHOW GRANTS` при каждом изменении ролей.

## Проверьте себя

> [!CHECK] Приложение подключается как dean_app и не видит таблицу payments. С чего начать?
> С `SHOW GRANTS FOR 'dean_app'@'localhost';` и `SELECT CURRENT_USER();`. Если прав на `payments` нет, выдают `GRANT SELECT, INSERT ON dean.payments`. Если права есть, проверяют, к какой базе подключилось приложение.

> [!CHECK] Почему нельзя выдать приложению GRANT OPTION «на всякий случай»?
> Это право позволяет выдавать привилегии другим учётным записям. Ошибка или инъекция в приложении сможет создать пользователя с полным доступом, и ограничение прав потеряет смысл.

> [!CHECK] Чем роль отличается от пользователя?
> Роль это набор привилегий без пароля, её нельзя использовать для входа. Пользователь получает роль и действует с её правами в сессии.

## Итоги

- Учётная запись MySQL состоит из имени и узла, и `localhost` не равен `%`.
- Роль собирает типовой набор прав и выдаётся пользователям, а `SET DEFAULT ROLE` включает её при входе.
- Привилегии выдают на базу, таблицу или столбец; приложению нужны только команды, которые оно действительно выполняет.
- Доступ проверяют поведением: вход из phpMyAdmin, запрос из .NET и ожидаемый отказ на запрещённую команду.

Q: Какая команда выводит привилегии текущего пользователя?
= SHOW GRANTS;
= SHOW GRANTS
= SHOW GRANTS FOR CURRENT_USER();
! SHOW GRANTS без аргументов показывает права текущей учётной записи.

Q: Почему учётная запись с host "%" опаснее, чем с host "localhost"?
+ Она принимает подключения с любого адреса
- Она не требует пароля
- Она автоматически получает права root
- Она отключает журналы
! Шаблон % расширяет круг клиентов, которые могут пытаться войти.
