## Одна идея

В 11:40 скрипт очистки тестовых данных выполнил `UPDATE enrollments SET grade = NULL` без условия по группе и обнулил оценки во всех двадцати записях. Последняя полная копия снята в 02:00. Развернуть её значит потерять девять часов работы деканата: новых студентов, платежи, заявления. Оставить базу как есть значит восстанавливать ведомость вручную.

**Восстановление решает не задачу «вернуть копию», а задачу «вернуть базу к нужному моменту».** Копия даёт стартовую точку, журнал изменений даёт движение вперёд, а параметр восстановления говорит, где остановиться. Поэтому в PostgreSQL два разных инструмента: логический дамп возвращает содержимое на момент выгрузки, а физическая копия вместе с журналом WAL позволяет выбрать почти любую секунду между копией и сбоем.

Две величины описывают стратегию. **RPO** это сколько данных допустимо потерять, **RTO** это сколько времени допустимо потратить на возврат в строй. Ночная копия без архива журнала даёт RPO в сутки, и для деканата это неприемлемо.

> [!KEY]
> Восстановление это выбор точки на шкале времени, а не выбор файла. Файл копии только задаёт, откуда начинать движение.

## Две дороги: логика и физика

Логическое восстановление читает дамп и заново выполняет команды создания объектов и вставки строк. Физическое копирует файлы данных и проигрывает журнал изменений поверх них.

| Признак | Логическое | Физическое |
|---|---|---|
| Что переносится | команды и строки | файлы данных и журнал |
| Инструменты | `pg_dump`, `pg_restore`, `psql` | `pg_basebackup`, архив WAL, `restore_command` |
| Точка возврата | момент выгрузки | любая секунда, покрытая журналом |
| Другая версия PostgreSQL | возможен перенос | только та же мажорная версия |
| Отдельная таблица | да, флаг `--table` | нет, только вся база |
| Скорость на большой базе | медленно, объекты строятся заново | быстро, файлы копируются |
| Чего нет в копии | ролей кластера и статистики | ничего, но нужен весь журнал |

Логическое восстановление удобно для переноса на другую машину, обновления версии и возврата одной таблицы. Физическое нужно, когда важна скорость и точность до секунды.

## Логическое восстановление

Логическая копия это текст команд или архив с этими командами. Формат `plain` даёт SQL-файл, который читается глазами и правится руками. Формат `custom` даёт сжатый архив, из которого `pg_restore` умеет выбирать отдельные объекты и распараллеливать работу.

```bash
pg_dump -U dean_owner -Fc -f /backup/dean.dump dean
pg_dump -U dean_owner -Fp dean > /backup/dean.sql
pg_restore -l /backup/dean.dump | head -n 15
```

Третья команда показывает оглавление: видно, какие таблицы, последовательности и ограничения попали в копию.

Восстановление всегда идёт **в отдельную базу**, а не поверх рабочей: так остаётся источник для сравнения.

```bash
createdb -U postgres dean_restore
pg_restore -U postgres -d dean_restore --no-owner --role=dean_owner -j 2 /backup/dean.dump
```

Флаг `-j 2` запускает два потока и работает только с форматами `custom` и `directory`. Пара `--no-owner --role=dean_owner` возвращает объектам законного владельца: без неё всё созданное окажется у роли, от имени которой шло восстановление. Так появляется ошибка `permission denied for table students`, хотя данные на месте.

Для SQL-файла используется `psql`:

```bash
psql -U postgres -d dean_restore -v ON_ERROR_STOP=1 -1 -f /backup/dean.sql
```

`ON_ERROR_STOP=1` останавливает выполнение на первой ошибке, а флаг `-1` выполняет файл одной транзакцией: база либо соберётся целиком, либо не изменится вовсе.

## Физическое восстановление и журнал

Физическая копия снимается с работающего сервера и включает все файлы данных. Чтобы её можно было дополнить журналом, архивирование включают заранее.

```
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /backup/wal/%f && cp %p /backup/wal/%f'
```

`archive_command` вызывается для каждого заполненного сегмента. Проверка `test ! -f` не даёт перезаписать уже лежащий файл, а `%p` и `%f` подставляют путь и имя. Состояние архива видно в `pg_stat_archiver`: если `failed_count` растёт, журнал не уезжает.

```bash
sudo -u postgres pg_basebackup -D /backup/base/2026-04-14 -Fp -X stream -P -c fast
pg_verifybackup /backup/base/2026-04-14
```

`-X stream` забирает журнал, накопленный за время копирования, `-c fast` сразу запускает контрольную точку. `pg_verifybackup` сверяет файлы с контрольными суммами из манифеста: копия, не прошедшая проверку, для восстановления не годится.

Дальше базу разворачивают на чистом месте: службу останавливают, каталог данных очищают, копию распаковывают, добавляют файл-сигнал и параметры.

```bash
sudo systemctl stop postgresql
sudo rm -rf /var/lib/postgresql/16/main/*
sudo -u postgres cp -a /backup/base/2026-04-14/. /var/lib/postgresql/16/main/
sudo -u postgres touch /var/lib/postgresql/16/main/recovery.signal
```

```
restore_command = 'cp /backup/wal/%f %p'
recovery_target_time = '2026-04-14 11:39:00+03'
recovery_target_action = 'pause'
```

`recovery.signal` включает режим восстановления, `restore_command` объясняет, откуда брать сегменты, `recovery_target_time` задаёт момент остановки. Значение `pause` оставляет сервер доступным только для чтения: это возможность проверить данные до того, как база снова начнёт принимать записи.

В журнале сервера появляются строки `starting point-in-time recovery`, затем `consistent recovery state reached`, затем `recovery stopping before commit of transaction`. Слово `before` ключевое: PostgreSQL отменяет транзакцию целиком, а не половину, поэтому частичного изменения в базе не остаётся.

Если проверка прошла, восстановление завершают повышением:

```sql
SELECT pg_promote();
```

Сервер выходит из режима восстановления, и только теперь разрешена запись: до этого изменение возвращает ошибку о транзакции только для чтения.

Точку задают и номером транзакции (`recovery_target_xid`), и позицией в журнале (`recovery_target_lsn`), и именованной точкой из `pg_create_restore_point`. Последнюю ставят перед рискованным изменением схемы и возвращаются к ней, не выясняя время по часам.

## Порядок действий на чистом месте

Паника толкает к перезаписи рабочей базы, поэтому последовательность лучше держать перед глазами.

1. Остановить приложение или перевести его в режим только для чтения.
2. Зафиксировать точку отказа по журналу приложения и `audit_log`.
3. Проверить копию и журнал: `pg_verifybackup` и наличие сегментов.
4. Развернуть восстановление на отдельном каталоге, порту или машине.
5. Дождаться строки о достигнутой согласованности.
6. Сверить данные с контрольными числами.
7. Переключить приложение и проверить записи.
8. Сохранить старую базу и журналы до разбора причин.

Пока рабочая база слушает `5432`, восстановленная поднимается на `5433`, и две версии одной таблицы можно сравнить, не останавливая деканат.

## Восстановление отдельной таблицы

Иногда испорчена одна таблица, а терять остальные изменения нельзя. Полное восстановление к моменту до ошибки откатило бы и корректные записи, поэтому работают точечно.

Сначала копию поднимают на порту `5433` и доводят до нужного момента, затем выгружают только нужную таблицу.

```bash
pg_dump -h 127.0.0.1 -p 5433 -U dean_owner -Fc -t enrollments -f /backup/enrollments.dump dean
createdb -U postgres dean_fix
pg_restore -U postgres -d dean_fix --no-owner --role=dean_owner /backup/enrollments.dump
```

Строки переносят в рабочую базу через промежуточную таблицу, чтобы не смешать хорошие и плохие данные одной командой.

```sql
CREATE TEMP TABLE enrollments_fix (LIKE enrollments INCLUDING ALL);
\copy enrollments_fix FROM '/tmp/enrollments_fix.csv' CSV HEADER
INSERT INTO enrollments
SELECT * FROM enrollments_fix
ON CONFLICT (student_id, course_id) DO UPDATE SET grade = EXCLUDED.grade;
```

Файл для `\copy` готовят выгрузкой из `dean_fix`. Перенос сохраняет идентификаторы, поэтому последовательность не нужна, а конфликт по паре ключей решается обновлением оценки.

Точечное восстановление опаснее полного: связи между таблицами остаются на совести администратора. Возвращённая строка может ссылаться на удалённого студента, поэтому перед переносом проверяют внешние ключи, а после переноса повторяют сверку.

## Проверка целостности

Успешный запуск сервера ещё не означает, что данные целы. Проверяют три уровня: физическую структуру, статистику и смысл данных.

```bash
pg_amcheck --all --heapallindexed --parent-check --jobs=2
```

`pg_amcheck` обходит индексы и проверяет ссылки между уровнями, порядок ключей и соответствие записям таблицы. Ключ `--heapallindexed` добавляет сверку индекса с таблицей: она медленнее, но именно она ловит потерянные строки. Утилита проверяет индексы B-tree, остальные типы она пропускает.

```sql
VACUUM (ANALYZE, VERBOSE) enrollments;
ANALYZE;
```

После логического восстановления статистики планировщика нет: дамп её не переносит. Без `ANALYZE` сложный запрос получит план по значениям по умолчанию и будет работать медленнее. `VACUUM` заодно обновляет карту видимости, без которой не работает индексное покрытие.

Сверка опирается на контрольные числа, снятые до сбоя, и каждую величину считают отдельным запросом.

```sql
SELECT 'groups' AS table_name, count(*) FROM groups
UNION ALL SELECT 'students', count(*) FROM students
UNION ALL SELECT 'enrollments', count(*) FROM enrollments
UNION ALL SELECT 'payments', count(*) FROM payments
ORDER BY table_name;

SELECT count(*) AS rows, count(grade) AS graded, round(avg(grade), 2) AS avg_grade
FROM enrollments;

SELECT count(*) AS payments, sum(amount) AS total FROM payments;
```

Последовательности проверяют отдельно: при частичном восстановлении счётчик отстаёт от данных.

```sql
SELECT last_value FROM students_id_seq;
SELECT max(id) FROM students;

SELECT setval(pg_get_serial_sequence('students', 'id'), COALESCE(max(id), 1)) FROM students;
```

Если `last_value` меньше `max(id)`, следующая вставка получит занятый номер и завершится ошибкой повторяющегося ключа.

Затем проверяют права и владельцев: `SELECT tableowner FROM pg_tables WHERE schemaname = 'public';` и `\dp students`. Если владелец `postgres`, а приложение ходит под `dean_app`, чтение может работать, а запись нет. Последний шаг это сценарий обычного пользователя: открыть список группы, поставить оценку, создать платёж.

## Типичные ошибки

- **Восстановление поверх рабочей базы.** `dropdb dean` выполняется до проверки копии, и второй попытки уже нет. Рабочую базу не трогают, пока восстановленная не прошла проверку.
- **Нет журнала.** `archive_mode` выключен, сегменты не уезжают, восстановление останавливается на ночной копии.
- **Неверный владелец.** Объекты созданы ролью `postgres`, приложение подключается ролью `dean_app` и получает отказ в доступе. Лечится парой `--no-owner --role`.
- **Не проверили данные.** Число строк совпало, но последовательности отстали, статистики нет, часть прав не выдана. Через день база падает на первой вставке.
- **Забыли про роли и расширения.** `pg_dump` не содержит ролей кластера, а расширения должны быть установлены на целевой машине. Роли снимают через `pg_dumpall --globals-only`, расширения ставят отдельным скриптом.

> [!PITFALL] Копия в тот же каталог
> Копию нельзя распаковывать в каталог данных работающего сервера: файлы заняты, служба продолжает писать. Сначала остановка, потом очистка каталога, потом распаковка. И только после проверки приложение переводят на восстановленную базу.

## Проверьте себя

> [!CHECK] Можно ли вернуть базу на 11:39, если базовая копия снята вчера в 02:00, а архивирование журнала включили сегодня в 09:00?
> Нет. Для проигрывания нужны все сегменты начиная с контрольной точки копии, а сегменты до 09:00 не сохранялись. Восстановление дойдёт до первого отсутствующего файла и остановится. Нужна копия, снятая после включения архивирования.

> [!CHECK] После восстановления вставка студента падает с ошибкой повторяющегося ключа. Что проверять?
> Последовательность `students_id_seq`: её значение отстало от `max(id)`, поэтому `nextval` выдаёт занятый номер. Значение выравнивают через `setval` и повторяют вставку.

> [!CHECK] Почему восстановление одной таблицы требует больше ручной работы, чем полное?
> Полное восстановление возвращает согласованный срез всей базы, где связи и последовательности уже сходятся. При точечном переносе администратор сам отвечает за внешние ключи, уникальность и совпадение идентификаторов.

## Итоги

- Восстановление выбирает момент времени, а копия задаёт только начало пути.
- Логическое восстановление переносит объекты и строки, физическое копирует файлы и проигрывает журнал.
- `recovery_target_time` и `recovery.signal` включают возврат на момент, `pause` даёт проверить данные до записи.
- После восстановления проверяют индексы, статистику, контрольные числа и последовательности.
- Рабочую базу не перезаписывают, пока восстановленная копия не прошла проверку.

::quiz
Q: Что задаёт параметр recovery_target_time?
+ Момент, на котором проигрывание журнала останавливается
- Время создания базовой копии
- Интервал между копиями
- Время последней контрольной точки
! Восстановление идёт от копии вперёд и останавливается перед первой транзакцией, зафиксированной позже указанного времени.

Q: Какой формат pg_dump позволяет распараллелить восстановление флагом -j?
+ Пользовательский и каталог
- Только plain
- Только tar
- Любой формат без ограничений
! Параллельное восстановление работает с форматами custom и directory, где архив хранит оглавление объектов.

Q: Что делает флаг psql -1 при загрузке SQL-дампа?
+ Выполняет весь файл одной транзакцией
- Пропускает первую ошибку
- Подключается к первой базе кластера
- Ограничивает вывод одной строкой
! Единая транзакция означает, что база либо соберётся целиком, либо останется неизменной.

Q: Зачем при восстановлении указывают --no-owner и --role=dean_owner?
+ Чтобы объекты получили нужного владельца, а не роль, выполнявшую восстановление
- Чтобы ускорить загрузку данных
- Чтобы пропустить проверку внешних ключей
- Чтобы создать базу заново
! Без этих флагов объекты принадлежат роли, от имени которой шёл pg_restore, и приложение получает отказ в доступе.

Q: Какой файл-сигнал включает режим восстановления в PostgreSQL 16?
+ recovery.signal
- recovery.conf
- standby.signal
- postgresql.auto.conf
! В современных версиях recovery.conf упразднён, режим включается пустым файлом recovery.signal в каталоге данных.

Q: Что проверяет pg_amcheck с ключом --heapallindexed?
+ Соответствие записей индекса строкам таблицы
- Свободное место на диске
- Настройки архивирования журнала
- Права ролей на таблицы
! Без этого ключа проверяется структура индекса, с ним добавляется сверка индекса с таблицей.

Q: Что произойдёт, если last_value последовательности меньше max(id) в таблице?
+ Следующая вставка получит занятый номер и завершится ошибкой
- Таблица будет заблокирована на чтение
- Последовательность пересоздастся автоматически
- Восстановление отменится
! Значение счётчика отстаёт от данных, поэтому nextval выдаёт уже существующий идентификатор.

Q: Зачем выполняют ANALYZE сразу после логического восстановления?
+ Чтобы планировщик получил статистику распределения данных
- Чтобы сжать файлы таблиц
- Чтобы проверить контрольные суммы страниц
- Чтобы обновить значения последовательностей
! Дамп не переносит статистику, и без неё планы запросов строятся по значениям по умолчанию.

Q: Что означает RPO в стратегии восстановления?
+ Допустимый объём данных, который можно потерять
- Время полного восстановления базы
- Число копий на диске
- Размер журнала в гигабайтах
! RPO задаёт допустимую потерю данных и определяет частоту копирования и архивирования журнала.

Q: Что входит в физическое восстановление базы?
+ Базовая копия каталога данных
+ Сегменты журнала WAL
+ Параметр restore_command
- SQL-файл, созданный pg_dump
- Команда psql -f
! Физическое восстановление разворачивает файлы копии и дополняет их журналом; дамп и psql относятся к логическому способу.

Q: Какие проверки имеют смысл после восстановления?
+ Сверка числа строк и сумм по таблицам
+ Запуск pg_amcheck по индексам
+ Сравнение last_value последовательностей с max(id)
+ Проверка владельцев таблиц
- Повторный запуск pg_dump без сравнения
- Удаление старой базы сразу после запуска
! Проверяют структуру, контрольные числа, последовательности, права и работу приложения.

Q: Чего нет в логическом дампе базы, снятом через pg_dump?
+ Ролей кластера
+ Статистики планировщика
- Определений таблиц
- Данных таблиц
- Ограничений целостности
! Роли живут на уровне кластера и снимаются отдельно через pg_dumpall, статистика заново собирается через ANALYZE.

Q: Почему восстановление на момент времени может остановиться, не дойдя до цели?
+ В архиве отсутствует нужный сегмент журнала
+ Целевой момент раньше контрольной точки базовой копии
+ Сегменты удалены по политике хранения
- Базовая копия снята в той же мажорной версии
- Целевой момент указан с часовым поясом
! Проигрывание требует непрерывной цепочки сегментов начиная с контрольной точки копии.

Q: Какой параметр задаёт время остановки восстановления?
= recovery_target_time
= recovery_target_time = '2026-04-14 11:39:00+03'
! Именно этот параметр указывает момент, перед которым восстановление должно остановиться.

Q: Какая утилита проверяет структуру индексов после восстановления?
= pg_amcheck
= amcheck
! pg_amcheck обходит индексы и сверяет их структуру, при необходимости и содержимое, с таблицами.
