## Одна идея

В 11:40 скрипт очистки тестовых записей выполнил `UPDATE enrollments SET grade = NULL` без условия `WHERE` и стёр оценки во всех двадцати строках. Полный дамп снят в 02:00. Развернуть только дамп значит потерять девять часов работы деканата: новых студентов, платежи, заявления. Оставить базу как есть значит восстанавливать ведомость вручную.

**Восстановление MySQL это возврат базы к выбранному моменту, а не к последней копии.** Дамп задаёт состояние на 02:00, binary log хранит все изменения после, а `mysqlbinlog` проигрывает их до нужной секунды или позиции. Два инструмента вместе отвечают на вопрос «как было в 11:39».

Ещё две величины задают требования к процедуре. **RPO** это сколько данных допустимо потерять, **RTO** это за сколько база должна вернуться в работу. Ночной дамп без журнала даёт RPO в девять часов, и для деканата это неприемлемо.

## Снимок и журнал

Дамп это текст команд: `CREATE TABLE`, `INSERT`, ограничения. Он читается глазами, переносится на другую версию MySQL и восстанавливается одной командой, но помнит только момент выгрузки.

Binary log это файл событий, которые сервер применил к данным. В него попадают изменения строк, смена схемы и служебные записи. Журнал пополняется непрерывно, пока включён параметр `log_bin`, и именно он превращает снимок в машину времени.

| Свойство | Дамп | Binary log |
|---|---|---|
| Что содержит | команды и строки на момент выгрузки | последовательность изменений после |
| Кто создаёт | `mysqldump` | сам сервер MySQL |
| Что даёт | стартовую точку | движение вперёд |
| Чем применяется | `mysql` или phpMyAdmin | `mysqlbinlog`, затем `mysql` |
| Ограничение | не знает, что было после | бесполезен без дампа |

На рисунке слева стоит снимок 02:00, от него вправо тянется полоса событий, а пунктир цели обрывает её на 11:39. Красная линия сбоя стоит на 11:40, и заштрихованный хвост журнала в работу не идёт. Восстановление это движение по полосе, а не выбор файла.

Дамп снимают с расчётом на такую процедуру:

```powershell
mysqldump -u root --single-transaction --routines --triggers --default-character-set=utf8mb4 --source-data=2 --result-file=.../backup/dean_2026-10-26.sql dean
```

Флаг `--single-transaction` берёт согласованный снимок InnoDB, не блокируя таблицы на запись. `--routines` и `--triggers` добавляют процедуры и триггеры, без них база восстановится без части логики. `--default-character-set=utf8mb4` сохраняет кириллицу, а `--source-data=2` записывает в начало файла позицию журнала на момент выгрузки. В MariaDB из XAMPP тот же флаг называется `--master-data=2`.

Отдельно про `--result-file`. В Windows PowerShell знак `>` пишет текст в UTF-16, и дамп не читается. Параметр `--result-file` пишет байты так, как их создал `mysqldump`.

## Импорт дампа: mysql и phpMyAdmin

Импорт идёт в отдельную базу: рабочая остаётся источником для сравнения, а неудачный импорт не превращает её в смесь старых и новых таблиц. Для журнала понадобится экземпляр, где база называется `dean`.

```sql
CREATE DATABASE dean_restore CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

Дальше файл читает клиент `mysql`. Команда `source` выполняет его построчно и останавливается на первой ошибке, если не указан `--force`:

```powershell
mysql -u root --default-character-set=utf8mb4 dean_restore -e "source .../backup/dean_2026-10-26.sql"
```

Перед импортом полезно посмотреть первые строки файла:

```powershell
Get-Content .../backup/dean_2026-10-26.sql -TotalCount 25
```

Если дамп снимали с флагом `--databases`, в нём есть строки `CREATE DATABASE dean` и `USE dean`. Импорт такого файла в `dean_restore` запишет таблицы в `dean`. Поэтому либо снимают дамп без `--databases`, либо правят строку `USE` перед импортом.

В phpMyAdmin путь короче: выбрать базу, вкладка **Импорт**, файл, формат SQL, кодировка `utf8mb4`, частичный импорт выключен. Способ удобен для небольших файлов и для разбора ошибки, но размер файла ограничен параметрами `upload_max_filesize` и `post_max_size` в `php.ini`. Большой дамп импортируют через `mysql`.

## Binary log: включить и прочитать

Журнал включают заранее, в `.../xampp/mysql/bin/my.ini`, и перезапускают MySQL из панели XAMPP:

```ini
[mysqld]
log-bin=mysql-bin
server-id=1
binlog_format=ROW
binlog_expire_logs_seconds=1209600
```

`server-id` нужен для репликации, `binlog_format=ROW` пишет изменения строками, а `binlog_expire_logs_seconds` держит журнал две недели. В MariaDB срок задают параметром `expire_logs_days=14`. Включить журнал задним числом нельзя: события за прошлые сутки не сохранились.

Проверка после перезапуска:

```sql
SHOW VARIABLES WHERE Variable_name IN ('log_bin', 'binlog_format', 'server_id');
SHOW BINARY LOGS;
```

Первая команда должна показать `ON`, `ROW` и ненулевой номер, вторая выдаёт список файлов и их размеры. В каталоге `.../xampp/mysql/data` эти файлы лежат рядом с папками баз.

Чтобы найти границу, журнал читают в окне вокруг аварии. `mysqlbinlog` показывает события строками и подписывает позиции:

```powershell
.../xampp/mysql/bin/mysqlbinlog.exe --base64-output=DECODE-ROWS -v --start-datetime="2026-10-26 11:30:00" --stop-datetime="2026-10-26 11:45:00" --result-file=.../backup/window.sql .../xampp/mysql/data/mysql-bin.000007
```

В файле видно событие `UPDATE dean.enrollments`, время `SET TIMESTAMP` и позицию `end_log_pos`. Номер `# at 1720` перед этим событием и есть граница: всё, что раньше, применяем, всё, что позже, отбрасываем. Время и позиция дают две независимые координаты одной и той же точки.

## Восстановление на момент времени

Проигрывание начинают не от начала журнала, а от позиции из заголовка дампа. Иначе события, уже попавшие в снимок, применятся второй раз и дадут ошибку дублирующего ключа.

Журнал адресован базе `dean`: события содержат `USE dean`. Репетиция идёт на экземпляре на порту 3307, где база снова называется `dean`.

```powershell
.../xampp/mysql/bin/mysqlbinlog.exe --start-position=154 --stop-datetime="2026-10-26 11:40:00" --result-file=.../backup/pitr.sql .../xampp/mysql/data/mysql-bin.000006 .../xampp/mysql/data/mysql-bin.000007
mysql -u root -h 127.0.0.1 -P 3307 --default-character-set=utf8mb4 -e "source .../backup/pitr.sql" dean
```

`--start-position` задаёт первое событие, `--stop-datetime` обрывает чтение на первом событии с указанным временем или позже, поэтому событие 11:40:00 в файл не попадает. Файлы журнала перечисляют по порядку номеров: если авария попала в следующий файл, одного имени мало.

У позиции есть особенность: номер относится к конкретному файлу журнала, поэтому пара «файл и позиция» идёт вместе.

## Порядок действий на копии

Порядок важнее скорости: шаг идёт после предыдущего.

1. **Зафиксировать точку.** Записать время аварии, файл журнала и позицию последнего хорошего события.
2. **Остановить запись.** Приложение переводится в режим только чтения или выключается. Пока в базу идут изменения, любая копия устаревает быстрее, чем её проверяют.
3. **Поднять отдельный экземпляр.** Второй сервер запускают из своего каталога данных на другом порту:
   ```powershell
   .../xampp/mysql/bin/mysqld.exe --initialize-insecure --datadir=.../mysql-restore/data
   .../xampp/mysql/bin/mysqld.exe --datadir=.../mysql-restore/data --port=3307 --console
   ```
   В MariaDB первый шаг выполняет `mysql_install_db.exe` с тем же `--datadir`.
4. **Развернуть дамп.** Создать `dean` с `utf8mb4`, импортировать файл, сверить число таблиц.
5. **Проиграть журнал.** Применить события от позиции дампа до цели и остановиться.
6. **Проверить данные.** Счётчики, `CHECK TABLE`, кодировка, отсутствие висячих ссылок.
7. **Переключить приложение.** Только после проверки, с записью в журнал изменений и планом возврата на прежний экземпляр.

Шаг с отдельным экземпляром отделяет репетицию от рабочей системы: если копия испортится, рабочая не пострадает.

## Проверка после восстановления

Восстановление закончено не тогда, когда команда прошла без ошибок, а когда данные совпали с ожиданием. Начинают со счётчиков:

```sql
SELECT 'groups' AS tbl, COUNT(*) AS n FROM groups
UNION ALL SELECT 'students', COUNT(*) FROM students
UNION ALL SELECT 'courses', COUNT(*) FROM courses
UNION ALL SELECT 'enrollments', COUNT(*) FROM enrollments
UNION ALL SELECT 'payments', COUNT(*) FROM payments;
```

Для учебной базы ожидание известно: 3, 10, 5, 20 и 10. Если `enrollments` даёт 19, значит журнал оборвался на событии раньше цели или одно удаление попало в снимок. Счётчик не доказывает правильность строк, но сразу показывает грубый промах.

Дальше проверяют структуру и индексы:

```sql
CHECK TABLE students, enrollments, payments;
```

Для InnoDB команда читает индексные страницы и сообщает о расхождении. Ответ `status OK` означает, что индексы таблицы согласованы. Ту же проверку из командной строки делает `mysqlcheck`:

```powershell
mysqlcheck -u root --check dean_restore
```

Кодировку проверяют на данных: `SHOW CREATE TABLE students` должен показать `utf8mb4`, а `SELECT full_name FROM students LIMIT 3` вернуть читаемые фамилии. Строки вида `Ð”ÐµÐºÐ°Ð½Ð°Ñ‚` означают, что файл читали не в той кодировке.

Висячие ссылки ищут соединением:

```sql
SELECT COUNT(*) AS orphans
FROM enrollments e
LEFT JOIN students s ON s.id = e.student_id
WHERE s.id IS NULL;
```

Ноль обязателен: внешний ключ такое состояние не пропустит, но при импорте с `SET FOREIGN_KEY_CHECKS=0` оно появляется.

> [!CHECK] Почему `CHECK TABLE` не заменяет проверку счётчиков?
> `CHECK TABLE` смотрит на страницы и индексы таблицы, но не знает, сколько строк должно быть. Таблица может быть полностью исправна и при этом содержать данные на девять часов назад. Счётчики и сверка значений отвечают на другой вопрос: те ли это данные.

## Типичные ошибки

- **Восстановление поверх рабочей базы.** Ошибка в середине импорта оставляет базу в промежуточном состоянии, и сравнивать результат не с чем. Рабочую базу трогают последней.
- **Журнал не включён или уже удалён.** Параметр `log_bin` нельзя включить задним числом, а срок хранения в две недели однажды обрежет точку восстановления. Проверка `SHOW BINARY LOGS` должна быть в регламенте.
- **Неверная кодировка.** Дамп снят в `latin1`, импорт выполнен без `--default-character-set`, и кириллица превратилась в набор символов. Данные при этом целы, но приложение показывает мусор.
- **Не проверили данные.** Команда импорта завершилась, таблицы на месте, а часть строк потеряна. Без счётчиков и `CHECK TABLE` это выяснится на первом отчёте.
- **Применили весь журнал.** Восстановление до конца файла возвращает и ошибочный `UPDATE`. Цель ставят до аварии, а не после неё.
- **Применили журнал дважды.** Повторный запуск того же файла даёт дубликаты ключей или удвоенные суммы. Начальная позиция берётся из заголовка дампа.

> [!PITFALL] Флаг `--databases` в дампе
> Дамп с `--databases dean` содержит `USE dean`. Если импортировать его в `dean_restore` на том же сервере, таблицы уйдут в рабочую базу, а `dean_restore` останется пустой. Проверяйте первые строки файла до импорта, а не после.

## Проверьте себя

> [!CHECK] Дамп снят в 02:00, журнал включён, авария в 11:40. Что нужно, чтобы вернуться к 11:39?
> Нужны дамп, все файлы журнала с позиции из заголовка дампа и граница остановки: время 11:39 или позиция события перед ошибочным `UPDATE`. После проигрывания данные проверяют счётчиками и `CHECK TABLE`.

> [!CHECK] Почему нельзя проиграть журнал в базу `dean_restore` на том же сервере?
> События журнала адресованы базе `dean`: в них записан контекст `USE dean`. При проигрывании они изменят рабочую базу, а не копию. Копия должна называться так же, поэтому её разворачивают на отдельном экземпляре сервера.

> [!CHECK] Импорт завершился без ошибок, но `enrollments` содержит 19 строк вместо 20. Где искать причину?
> Сначала в границе остановки: журнал могли оборвать раньше цели. Потом в дампе: он мог быть снят без `--single-transaction`. Затем в журнале приложения: одну строку могли удалить до аварии, и тогда 19 это правильное число.

## Итог

- Восстановление возвращает базу к моменту, а не к файлу: дамп даёт старт, binary log даёт движение.
- `mysqldump` снимают с `--single-transaction`, `--routines`, `--triggers` и записью позиции журнала, а импортируют в отдельную базу.
- Границу ставят по времени или позиции до ошибочного события, а не в конце журнала.
- Результат проверяют счётчиками, `CHECK TABLE`, кодировкой и отсутствием висячих ссылок.

- Все изменения после выгрузки
- Полную историю транзакций

- В строке подключения .NET
- В таблице schema_version
! Журнал включается в конфигурации сервера и требует перезапуска MySQL.

Q: Какая утилита читает и проигрывает binary log?
+ mysqlbinlog
- mysqldump
- mysqlcheck
- mysqladmin
! mysqlbinlog превращает журнал в текст событий, который затем применяет клиент mysql.

Q: Зачем импортировать дамп в отдельную базу?
+ Чтобы сохранить рабочую базу как источник сравнения
- Чтобы ускорить импорт
- Чтобы уменьшить размер файла
- Чтобы включить binary log
! Отдельная база позволяет сравнить результат с рабочей и не рискует её испортить.

Q: Что делает флаг --single-transaction при снятии дампа?
+ Берёт согласованный снимок InnoDB без блокировки таблиц на запись
- Выполняет все команды одной транзакцией при импорте
- Отключает внешние ключи
- Сжимает файл дампа
! Снимок читается на одном моменте, поэтому таблицы согласованы между собой.

Q: Какая команда проверяет согласованность индексов таблицы InnoDB?
+ CHECK TABLE
- SHOW INDEX
- ANALYZE TABLE
- OPTIMIZE TABLE
! CHECK TABLE читает страницы и сообщает о расхождении, не меняя данные.

Q: Где берут начальную позицию журнала для проигрывания?
+ В заголовке дампа, записанном флагом --source-data=2
- В конце файла журнала
- В таблице audit_log
- В выводе SHOW INDEX
! Дамп хранит позицию на момент выгрузки, с неё и начинают.

Q: Почему событие 11:40 не попадает в файл при --stop-datetime="2026-10-26 11:40:00"?
+ Чтение обрывается на первом событии с указанным временем или позже
- Утилита округляет время до минуты назад
- Событие удаляется из журнала
- Время в журнале хранится в другом часовом поясе
! Граница исключает событие, поэтому ошибочное изменение не применяется.

Q: Что произойдёт при повторном применении того же файла журнала?
+ Появятся ошибки дублирующих ключей или удвоенные изменения
- База вернётся к состоянию дампа
- Журнал очистится
- Ничего не изменится
! События применяются повторно, а вставки и обновления не рассчитаны на второй проход.

Q: Что проверяют после восстановления базы?
+ Число строк в каждой таблице
+ Результат CHECK TABLE
+ Читаемость кириллицы в строках
+ Отсутствие висячих ссылок между таблицами
- Размер файла дампа
- Скорость интернета
! Счётчики, проверка таблиц, кодировка и ссылки вместе показывают, что данные пригодны.

Q: Какие причины мешают восстановлению на момент времени?
+ Binary log не был включён заранее
+ Файлы журнала удалены по сроку хранения
+ Начальная позиция взята не из заголовка дампа
+ Журнал проигран поверх рабочей базы
- Дамп снят с флагом --routines
- Таблицы используют движок InnoDB
! Журнал нужно включить заранее, хранить дольше точки восстановления и применять на копии.

Q: Что даёт флаг --default-character-set=utf8mb4 при снятии и импорте дампа?
+ Сохраняет кириллицу без искажений
+ Задаёт кодировку соединения при чтении файла
- Меняет кодировку самой базы данных
- Ускоряет импорт больших таблиц
- Отключает проверку внешних ключей
! Одна и та же кодировка на выгрузке и загрузке сохраняет текст читаемым.

Q: Какие флаги mysqldump полезны для базы InnoDB с процедурами и триггерами?
+ --single-transaction
+ --routines
+ --triggers
+ --source-data=2
- --force
- --all-databases
! Согласованный снимок, процедуры, триггеры и позиция журнала делают дамп пригодным для восстановления.

Q: Как называется журнал изменений MySQL, по которому восстанавливают базу на момент времени?
= binary log
= binlog
= бинарный журнал
! Binary log хранит события изменений и позволяет доиграть состояние после дампа.

Q: Какая команда проверяет таблицу на согласованность страниц и индексов?
= CHECK TABLE
= check table
! CHECK TABLE возвращает status OK, если таблица и её индексы согласованы.
