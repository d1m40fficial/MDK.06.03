## Одна идея

Бухгалтерия присылает файл на пять тысяч студентов. В нём одна строка с опечаткой в адресе почты, а в целевой таблице стоит ограничение `email text unique not null`. Если грузить файл одной командой, ограничение отменит **всю** загрузку из-за одной строки. Если написать скрипт, который просто пропускает неудачные строки, деканат потеряет студента и не узнает об этом.

**Обмен данными** это не «залить файл в таблицу», а договорённость: какой формат, какая кодировка, что считать ошибкой и что делать с плохой строкой. Пока эти пункты не названы явно, импорт будет то терять данные, то падать целиком.

Главный приём, который снимает почти все проблемы, простой: сначала загрузить файл **как есть** в промежуточную таблицу, проверить её запросами, а в рабочие таблицы перенести только проверенные строки. Тогда ошибка строки перестаёт быть катастрофой и становится записью в журнале брака.

## Форматы обмена

Формат выбирают по двум признакам: структура данных и кто будет файл читать. Универсального формата нет.

| Формат | Сильная сторона | Слабая сторона |
|---|---|---|
| CSV | понимают Excel, Python, любая СУБД | нет типов, всё зависит от разделителя и кодировки |
| JSON | хранит вложенность и разные типы | файл больше, структуру надо разбирать |
| SQL | переносит и схему, и данные | опасен при запуске чужого файла |
| Бинарный COPY | самый быстрый и точный по типам | нечитаем и привязан к версии сервера |

CSV хорош для плоских таблиц: одна строка файла равна одной строке таблицы. JSON хорош, когда у записи есть вложенные части, например студент и список его курсов в одном документе. SQL удобен для переноса базы целиком через `pg_dump`, но запускать чужой SQL на рабочем сервере нельзя: в нём может быть что угодно. Бинарный формат `COPY ... WITH (FORMAT binary)` даёт максимальную скорость, но файл нельзя открыть и поправить, а совместимость между версиями PostgreSQL ограничена.

Для учебной базы `dean` чаще всего нужен CSV: его легко получить из Excel и так же легко проверить глазами. JSON пригодится, когда данные приходят из веб-сервиса.

На схеме у каждой строки два исхода. Хорошая строка проходит проверку и попадает в `students` или `groups`. Плохая не исчезает: она попадает в таблицу брака с номером строки и причиной. Именно этого не хватает простому `COPY` в рабочую таблицу: там у строки только один исход, и при ошибке он общий для всего файла.

## COPY и \copy

В PostgreSQL есть две похожие команды, и их постоянно путают.

`COPY` выполняется **на сервере**. Он читает файл по пути, который видит серверный процесс, и требует прав на чтение этого файла. Для этого роль должна входить в предопределённую роль `pg_read_server_files`, а файл должен лежать там, куда сервер имеет доступ.

`\copy` это метакоманда `psql`. Она выполняется **на клиенте**: psql сам читает файл и передаёт данные серверу через обычное соединение. Прав на серверные файлы не нужно, зато файл должен быть доступен там, где запущен psql.

Для учебной работы удобнее `\copy`: файл лежит на той же виртуальной машине, где открыт psql.

```sql
create table import_students (
  line_no bigserial,
  full_name text,
  group_name text,
  email text,
  created_at text
);

\copy import_students (full_name, group_name, email, created_at) from 'students.csv' with (format csv, header true, delimiter ';', encoding 'UTF8')
```

Первая строка файла при `header true` пропускается. Если её не указать, заголовок станет первой записью, и в таблице появится студент с именем `full_name`. Это одна из самых частых ошибок при первой загрузке.

Обратная операция выглядит так же, только с `to`:

```sql
\copy (select id, full_name, email from students order by id) to 'students_export.csv' with (format csv, header true, encoding 'UTF8')
```

В скобках можно указать не таблицу, а запрос. Это удобно для выгрузки выборки: в файл попадут только нужные столбцы и строки.

## Заголовки, разделители, кодировка

CSV кажется простым форматом, но у него много невидимых договорённостей. Перед загрузкой их нужно проверить, иначе ошибка проявится не сразу, а в странных данных.

**Разделитель.** В русской локали Excel часто сохраняет файл с точкой с запятой, потому что запятая занята десятичным разделителем. Если загрузить такой файл с `delimiter ','`, вся строка попадёт в один столбец. Проверить просто: посмотреть первую строку файла и явно указать разделитель.

**Кодировка.** Сервер обычно работает в UTF-8, а файл из старой программы может быть в Windows-1251. Признак проблемы: русские буквы превращаются в `???` или в набор символов, а иногда загрузка падает с ошибкой `invalid byte sequence for encoding "UTF8"`. Файл приводят к UTF-8 до загрузки, например командой `iconv`, а не надеются, что сервер угадает.

```bash
iconv -f WINDOWS-1251 -t UTF-8 students.csv > students_utf8.csv
```

**BOM.** Некоторые редакторы добавляют в начало UTF-8 файла невидимый маркер. Тогда первый столбец называется не `full_name`, а `\ufefffull_name`, и `COPY` сообщает, что такого столбца нет. Лечится удалением BOM или загрузкой с явным списком столбцов.

**Пустые значения.** В CSV пустое неэкранированное поле означает `NULL`, а пустая строка в кавычках `""` означает пустую строку. Разница важна: при переносе в `students` ограничение `not null` не пропустит `NULL`, а пустая строка пройдёт и создаст запись с пустой почтой.

**Даты и числа.** `27.10.2026` и `2026-10-27` это разные записи для базы. В приёмной таблице дата хранится текстом, поэтому её формат проверяют и приводят явно, а не полагаются на настройку `datestyle`. Аналогично `12,50` при десятичной запятой не станет числом без замены запятой на точку.

Правило простое: **все поля приёмной таблицы с данными имеют тип `text`**. Файл не обязан быть правильным, чтобы в него загрузиться. Типы и ограничения применяются на следующем шаге, где ошибку можно объяснить.

## JSON и jsonb

JSON приходит из веб-сервисов и внешних систем. В PostgreSQL есть два типа: `json` хранит текст как есть, `jsonb` разбирает его в двоичное представление и позволяет индексировать и искать по ключам. Для загрузки почти всегда берут `jsonb`.

Файл может содержать массив объектов:

```json
[
  {"full_name": "Иванов Иван", "group_name": "ИС-21", "email": "ivanov@example.ru"},
  {"full_name": "Петрова Анна", "group_name": "ИС-22", "email": "petrova@example.ru"}
]
```

Загружаем его целиком в одну строку приёмной таблицы. `COPY` читает файл построчно, поэтому многострочный JSON сначала сжимают в одну строку утилитой `jq`:

```bash
jq -c . students.json > students.min.json
```

```sql
create table import_json (doc jsonb);
\copy import_json from 'students.min.json'
```

Если файл большой и лежит на сервере, вместо `jq` можно прочитать его функцией `pg_read_file` с теми же правами, что и для серверного `COPY`. Главное, чтобы в колонку `jsonb` попал целый документ, а не его первая строка.

Затем разворачиваем массив в строки функцией `jsonb_to_recordset`:

```sql
insert into students(full_name, group_id, email)
select r.full_name, g.id, lower(r.email)
from import_json j
cross join lateral jsonb_to_recordset(j.doc)
  as r(full_name text, group_name text, email text)
join groups g on g.name = r.group_name;
```

`jsonb_to_recordset` принимает массив и список столбцов с типами. Если документ это объект с ключом `students`, массив достают через `j.doc -> 'students'`. Если внутри есть вложенный список курсов, его разворачивают вторым вызовом или сохраняют в отдельную таблицу.

У JSON есть ловушка типов: число в документе может оказаться строкой, а отсутствующий ключ даст `NULL`. Поэтому проверка нужна и здесь: `jsonb_to_recordset` не проверяет, что `group_name` существует в таблице `groups`.

## Промежуточная таблица и пакетная загрузка

Приёмная таблица решает три задачи сразу: сохраняет исходные значения без искажений, даёт место для проверки и позволяет повторить загрузку, не трогая рабочие данные.

Проверку удобно оформить представлением, где у каждой строки есть причина брака или `NULL`.

```sql
create view import_students_checked as
select s.*,
       case
         when s.full_name is null or btrim(s.full_name) = '' then 'пустое имя'
         when s.email is null or btrim(s.email) = '' then 'пустой email'
         when s.email !~ '^[^@[:space:]]+@[^@[:space:]]+\.[^@[:space:]]+$' then 'некорректный email'
         when exists (
           select 1 from import_students d
           where d.line_no < s.line_no and lower(d.email) = lower(s.email)
         ) then 'дубль email в файле'
         when g.id is null then 'нет такой группы'
       end as reason
from import_students s
left join groups g on g.name = s.group_name;
```

Проверка дублей стоит в том же представлении: вторая строка с тем же email попадает в брак, а не роняет вставку уникальным ограничением.

Дальше брак переносят в журнал, а хорошие строки в цель. Журнал брака создают заранее, чтобы у каждой отброшенной строки было место с номером и причиной.

```sql
create table import_errors (
  id bigserial primary key,
  line_no bigint,
  raw jsonb,
  reason text,
  at timestamptz default now()
);
```

Оба запроса читают одно и то же представление, поэтому правила не расходятся.

```sql
insert into import_errors(line_no, raw, reason)
select line_no, to_jsonb(c), reason
from import_students_checked c
where reason is not null;

insert into students(full_name, group_id, email)
select c.full_name, g.id, lower(c.email)
from import_students_checked c
join groups g on g.name = c.group_name
where c.reason is null
  and not exists (select 1 from students s where s.email = lower(c.email));
```

Условие `not exists` защищает от повторной вставки при перезапуске. Это первый шаг к идемпотентности: повторный запуск не создаёт дублей, а пропускает уже загруженное.

Если файл очень большой, его грузят частями. Каждая часть это отдельная транзакция: сбой на середине не отменяет уже загруженные части, а повтор начинают с упавшей.

```bash
tail -n +2 students.csv > students_body.csv
split -l 100000 -d students_body.csv part_
for f in part_*; do
  psql -d dean -v ON_ERROR_STOP=1 \
    -c "\copy import_students (full_name, group_name, email) from '$f' with (format csv, delimiter ';')" || exit 1
done
```

`tail -n +2` убирает заголовок, `split` режет файл по сто тысяч строк, а `ON_ERROR_STOP=1` останавливает цикл на первой ошибке. Без него psql продолжит работу после сбоя, и часть файлов останется незагруженной.

## Ошибки строк и транзакция

Главное решение при импорте: что считать ошибкой и как с ней поступать. Есть три политики.

- **Остановиться на первой ошибке.** Подходит для небольших справочников, где любая ошибка означает проблему в источнике.
- **Отбраковать строку и продолжить.** Подходит для больших файлов: строка уходит в журнал брака с причиной, остальные загружаются.
- **Исправить источник и повторить.** Самый правильный вариант, если файл формируется автоматически и ошибку можно устранить в правилах выгрузки.

Чего делать нельзя, так это **молча пропускать** строки. Если строка не загрузилась, у неё должна быть запись с причиной и номером. Иначе расхождение обнаружится через месяц, когда никто уже не вспомнит, откуда взялся файл.

В PostgreSQL 16 у `COPY` нет режима «пропустить плохие строки»: ошибка отменяет всю команду. Поэтому приёмная таблица это не украшение, а способ получить частичную загрузку с полным учётом потерь. Каждая строка либо попадает в цель, либо в журнал брака, третьего пути нет.

## Сверка после обмена

Импорт закончен не тогда, когда команда вернула `COPY 5000`, а когда числа сошлись. Минимальная проверка состоит из трёх шагов.

Первый: сравнить число строк в источнике и в цели.

```sql
select (select count(*) from import_students) as source_rows,
       (select count(*) from students) as target_rows,
       (select count(*) from import_errors) as rejected;
```

Второй: сравнить содержимое, а не только количество. Одинаковое число строк ничего не говорит о том, что значения не перепутаны. Контрольная сумма по отсортированному столбцу ловит перестановки и подмены.

```sql
select count(*) as rows,
       md5(string_agg(lower(email), ',' order by lower(email))) as fingerprint
from students;
```

Третий: проверить ограничения и связи. Число строк может сойтись, а внешний ключ указывать на несуществующую группу, если проверку обошли. Запрос на сирот закрывает этот пробел.

```sql
select count(*) as orphans
from students s
left join groups g on g.id = s.group_id
where g.id is null;
```

При экспорте сверка идёт в обратную сторону: файл загружают в проверочную таблицу и сравнивают с исходной. Только так видно, что выгрузка не потеряла строки и не испортила кодировку.

## Типичные ошибки

- **Молчаливый пропуск строк.** Скрипт ловит ошибку и идёт дальше без записи в журнал. Число строк в отчёте красивое, данные неполные. Каждая отбракованная строка должна иметь причину.
- **Неверная кодировка.** Файл в Windows-1251 грузят как UTF-8. Симптом: `invalid byte sequence` или ромбики вместо букв. Кодировку приводят до загрузки и указывают в `COPY` явно.
- **Загрузка сразу в рабочую таблицу.** Одна плохая строка отменяет весь файл, а частичный результат уже смешан с рабочими данными. Приёмная таблица отделяет проверку от записи.
- **Забытый заголовок.** Без `header true` первая строка становится данными, и в таблице появляется запись с именем столбца вместо имени студента.
- **Неверный разделитель.** Файл с точкой с запятой читают с запятой, и вся строка оказывается в одном поле. Проверяют первую строку файла до запуска.
- **Повторная загрузка без защиты.** Скрипт запускают дважды, и появляются дубли. Помогают `not exists`, `on conflict` и очистка приёмной таблицы перед новой загрузкой.
- **Сверка только по количеству.** Число строк совпало, а значения перепутаны. Контрольная сумма и проверка связей обязательны.

> [!PITFALL] «Файл открылся в Excel, значит, формат верный»
> Excel молча подставляет свою кодировку, разделитель и формат даты. Файл, который выглядит правильно на экране, может иметь совсем другую структуру на диске. Смотрите исходные байты и первую строку, а не картинку в редакторе.

## Проверьте себя

> [!CHECK] Файл содержит пять тысяч строк, одна из них с пустым email. Что произойдёт при `COPY` прямо в `students` и как изменить схему загрузки?
> `COPY` отменит всю команду, потому что ограничение `not null` сработает на одной строке. Нужна приёмная таблица с текстовыми полями: файл загрузится целиком, проверка отправит плохую строку в журнал брака, а остальные попадут в `students`.

> [!CHECK] Почему сравнения только `count(*)` недостаточно после импорта?
> Количество не показывает, те ли это строки. Ошибка в сопоставлении столбцов или потеря одного значения и появление другого дадут то же число. Нужны контрольная сумма по содержимому и проверка связей.

> [!CHECK] В файле JSON у студента есть список курсов. Как разложить его по таблицам?
> Внешний массив разворачивают через `jsonb_to_recordset` в строки студентов, а вложенный список курсов разворачивают отдельно и связывают с `students` по ключу. В реляционной таблице вложенность всегда превращается в отдельную таблицу и внешний ключ.

## Итог

- Формат выбирают под структуру и читателя: CSV для плоских таблиц, JSON для вложенности, SQL для переноса схемы, binary для скорости.
- `COPY` работает на сервере, `\copy` на клиенте и не требует прав на серверные файлы.
- Разделитель, кодировку, заголовок и формат даты проверяют до загрузки, а не после.
- Приёмная таблица с текстовыми полями отделяет загрузку от проверки и позволяет учесть каждую плохую строку.
- JSON разворачивают через `jsonb_to_recordset`, вложенные списки переносят в отдельные таблицы.
- Ошибка строки должна попадать в журнал с причиной; молчаливый пропуск недопустим.
- После обмена сверяют число строк, контрольную сумму и связи, а выгрузку проверяют обратной загрузкой.

Q: Чем \copy отличается от COPY?
+ \copy читает файл на стороне клиента и не требует прав на серверные файлы
- \copy работает только с JSON
- \copy выполняется на сервере и требует роли pg_read_server_files
- \copy не умеет записывать данные в файл
! \copy это метакоманда psql: файл читает клиент, данные передаются через обычное соединение.

Q: Что произойдёт, если в файле одна строка нарушает ограничение, а загрузка идёт через COPY прямо в рабочую таблицу?
+ Вся команда COPY будет отменена
- Загрузится только повреждённая строка
- PostgreSQL пропустит строку и запишет её в отдельный файл
- Загрузка продолжится, а ограничение будет удалено
! В PostgreSQL 16 ошибка строки отменяет всю команду COPY, поэтому нужна приёмная таблица.

Q: Какой формат лучше подходит для данных с вложенными списками?
+ JSON
- CSV
- Бинарный COPY
- SQL
! JSON хранит вложенные объекты и массивы, а CSV описывает только плоскую таблицу.

Q: Что означает пустое неэкранированное поле в CSV при загрузке через COPY?
+ NULL
- Пустую строку
- Ноль
- Ошибку загрузки
! Пустое поле без кавычек читается как NULL, а пустая строка в кавычках даёт пустое значение.

Q: Зачем нужна приёмная таблица при импорте?
+ Чтобы проверить и отбраковать строки до записи в рабочие таблицы

- Чтобы заменить внешние ключи
- Чтобы хранить резервную копию базы
! Приёмная таблица принимает файл как текст и даёт место для проверки и журнала брака.

Q: Что показывает контрольная сумма после импорта?

- Размер файла на диске
- Число внешних ключей в схеме
! Контрольная сумма ловит перестановки и подмены значений при том же количестве строк.

Q: Какой формат самый быстрый, но непригодный для ручной правки?
+ Бинарный COPY
- CSV
- JSON
- SQL
! Бинарный COPY точен по типам и быстр, но нечитаем и привязан к версии сервера.

Q: Что делать, если файл сохранён в Windows-1251, а сервер работает в UTF-8?
+ Привести файл к UTF-8 до загрузки и указать кодировку явно
- Загрузить файл как есть, сервер исправит буквы
- Удалить все русские буквы из файла
- Отключить проверку кодировки в PostgreSQL
! Кодировку приводят заранее, иначе загрузка упадёт или испортит текст.

- DOCX

Q: Какие проверки выполняют после импорта?

+ Поиск дублей

- Перезапуск сервера
