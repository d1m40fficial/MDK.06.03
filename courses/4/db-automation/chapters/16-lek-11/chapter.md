## Одна идея

В начале семестра деканат присылает список первокурсников файлом CSV на двести строк. Администратор открывает phpMyAdmin, нажимает «Импорт», выбирает файл и получает сообщение «Импорт успешно завершён». Через неделю выясняется, что в базе сто восемьдесят семь студентов, а тринадцать строк пропали: у части не было группы, у части почта повторяла уже существующую.

**Обмен данными требует трёх вещей: формата, кодировки и правил ошибок.** Формат задаёт, как разложить строку на поля. Кодировка задаёт, как прочитать байты. Правила ошибок задают, что делать со строкой, которую нельзя принять: остановить всю загрузку, отложить строку или молча пропустить.

Третья часть самая опасная. Молчаливый пропуск выглядит как успех, и именно поэтому ошибку замечают через неделю, когда студент не может войти в систему.

## Форматы обмена

У MySQL три обычных способа отдать и принять данные, и у каждого своя область применения.

| Формат | Что внутри | Сильная сторона | Слабая сторона |
|---|---|---|---|
| CSV | строки с разделителем | открывается в Excel, понятен человеку | нет типов, легко испортить кодировку |
| JSON | вложенные объекты и массивы | хранит структуру и связи | требует разбора и проверки схемы |
| SQL | команды `INSERT` и `CREATE` | переносит схему и данные вместе | привязан к версии сервера |

CSV выбирают, когда данные приходят из таблицы или из другой системы и представляют собой плоский список. JSON выбирают, когда источник отдаёт вложенную структуру: студент, его группы, оценки и платежи в одном документе. SQL выбирают для копии базы и переноса между серверами, потому что он сохраняет типы, индексы и ограничения.

Внутри MySQL обмен идёт через два разных механизма. phpMyAdmin работает в браузере и удобен для небольших файлов и разовых операций. Команда `LOAD DATA` работает на сервере и держит большие объёмы, но требует прав и настроек. Выбор между ними определяет не вкус, а размер файла и повторяемость.

Промежуточная таблица устроена просто: все столбцы текстовые, ограничений почти нет, есть поле для имени файла. Она принимает файл целиком, даже кривой. Дальше запрос проверяет каждую строку и либо переносит её в рабочую таблицу, либо оставляет в стороне с понятной причиной.

> [!KEY]
> Импорт это две операции, а не одна: сначала принять, потом проверить. Пока обе склеены в одну, ошибка строки становится ошибкой всей загрузки или тихой потерей.

## Подготовка: кодировка, разделитель, права

До первой команды нужно ответить на четыре вопроса о файле.

**Кодировка.** Файл должен быть в UTF-8. Excel по умолчанию сохраняет CSV в кодировке системы, и кириллица превращается в `Ð˜Ð²Ð°Ð½Ð¾Ð²` или в знаки вопроса. В диалоге сохранения выбирают «CSV UTF-8 (разделитель запятая)».

**Разделитель.** В русской локали Excel ставит точку с запятой, а `LOAD DATA` по умолчанию ждёт запятую. Симптом характерный: вся строка попадает в первый столбец, остальные пустые.

**Заголовок.** Первая строка с именами столбцов не является данными, её пропускают через `IGNORE 1 LINES`. Если этого не сделать, в таблицу попадёт студент по имени «ФИО».

**Права и каталог.** Для чтения файла серверу нужен каталог, разрешённый параметром `secure_file_priv`.

```sql
SHOW VARIABLES LIKE 'secure_file_priv';
SHOW VARIABLES LIKE 'local_infile';
```

Если `secure_file_priv` пуст, ограничений нет. Если указан путь, сервер читает только из него. `LOAD DATA LOCAL INFILE` читает файл на стороне клиента, поэтому ограничение обходится, но клиент должен разрешить такую загрузку: в MariaDB из XAMPP параметр обычно включён, в MySQL 8 его включают явно.

```sql
SET GLOBAL local_infile = 1;
```

Клиент запускают с разрешением локальной загрузки:

```bash
C:\xampp\mysql\bin\mysql.exe --local-infile=1 -u root dean
```

## Загрузка CSV через LOAD DATA

Промежуточная таблица для списка студентов выглядит так:

```sql
CREATE TABLE students_stage (
  full_name   VARCHAR(128),
  group_name  VARCHAR(32),
  email       VARCHAR(128),
  source_file VARCHAR(128)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Загрузка задаёт кодировку, разделитель, кавычки и конец строки. Для файла из Windows конец строки это `\r\n`, иначе последнее поле каждой строки получит лишний символ возврата каретки.

```sql
LOAD DATA LOCAL INFILE 'C:/xampp/htdocs/import/students.csv'
INTO TABLE students_stage
CHARACTER SET utf8mb4
FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
LINES TERMINATED BY '\r\n'
IGNORE 1 LINES
(full_name, group_name, email)
SET source_file = 'students.csv';
```

После загрузки обязательно смотрят предупреждения. Именно там появляются строки, которые сервер принял не полностью.

```sql
SHOW WARNINGS;
```

Слово `IGNORE` в этой команде означает две разные вещи, и их легко перепутать. `IGNORE 1 LINES` пропускает первую строку файла. Отдельное `IGNORE` перед `INTO TABLE` превращает ошибки строк в предупреждения и позволяет загрузке продолжиться. Второе полезно только вместе с разбором `SHOW WARNINGS`, иначе это и есть тот самый молчаливый пропуск.

Строгий режим задаёт, что считать ошибкой. Проверить его состав стоит до загрузки.

```sql
SELECT @@sql_mode;
```

Если в списке есть `STRICT_TRANS_TABLES`, слишком длинное значение или неверная дата отклонят строку. Без строгого режима сервер обрежет значение и запишет предупреждение. Для импорта это означает: результат зависит от настройки сервера, а не только от файла.

## Загрузка через phpMyAdmin

phpMyAdmin делает то же самое, но прячет команды за формой. Вкладка «Импорт» просит выбрать файл, формат, кодировку и разделитель. Для CSV нужно указать, что первая строка содержит имена столбцов, и выбрать кодировку файла `utf-8`, а не кодировку соединения по умолчанию.

У браузерного пути есть предел. Размер файла ограничен настройками PHP:

```ini
upload_max_filesize = 64M
post_max_size = 64M
max_execution_time = 300
```

Правки вносят в `C:\xampp\php\php.ini`, после чего перезапускают Apache. Если файл больше предела, phpMyAdmin либо откажется его принимать, либо оборвёт импорт на середине. Второй случай опаснее: часть строк уже в таблице, и повторная загрузка создаст дубли.

> [!PITFALL] Успешный импорт не означает полный
> Сообщение «Импорт успешно завершён» говорит только о том, что команда не упала. Сколько строк принято, сколько отклонено и почему, phpMyAdmin показывает отдельным блоком, и его нужно читать, а не закрывать.

## Проверка промежуточной таблицы

Проверка начинается с общего числа строк: оно должно совпадать с числом строк в файле минус заголовок.

```sql
SELECT COUNT(*) AS total FROM students_stage;
```

Дальше ищут строки, которые нельзя перенести: пустые имена, почту без символа `@`, неизвестную группу.

```sql
SELECT
  SUM(full_name IS NULL OR full_name = '') AS no_name,
  SUM(email NOT REGEXP '^[^@]+@[^@]+\\.[a-z]{2,}$') AS bad_email,
  SUM(group_name NOT IN (SELECT name FROM groups)) AS unknown_group
FROM students_stage;
```

Каждый ненулевой результат это список строк для разбора, а не повод удалить данные. Строку с неизвестной группой можно принять после того, как группа появится, а строку с пустым именем нужно вернуть источнику.

Перенос в рабочую таблицу делают одной командой, чтобы он был атомарным.

```sql
START TRANSACTION;

INSERT INTO students (full_name, group_id, email)
SELECT s.full_name, g.id, s.email
FROM students_stage AS s
JOIN groups AS g ON g.name = s.group_name
WHERE s.email <> ''
ON DUPLICATE KEY UPDATE full_name = VALUES(full_name);

COMMIT;
```

`JOIN` отбрасывает строки с неизвестной группой, а `ON DUPLICATE KEY UPDATE` не даёт упасть на повторной почте. Обе операции меняют число строк, поэтому до и после считают не только исходную таблицу, но и промежуточную.

```sql
SELECT
  (SELECT COUNT(*) FROM students_stage) AS stage_rows,
  (SELECT COUNT(*) FROM students) AS students_rows,
  (SELECT COUNT(*) FROM students_stage AS s
     LEFT JOIN students AS p ON p.email = s.email
   WHERE p.id IS NULL) AS not_transferred;
```

`not_transferred` это и есть цена импорта: строки, которые остались в промежуточной таблице. Их число плюс число принятых должно дать исходное. Если сумма не сходится, часть строк потерялась по дороге, и загрузку повторяют на копии.

## JSON в MySQL

JSON удобен, когда источник отдаёт вложенный документ. В MySQL и MariaDB есть тип `JSON`, а функции разбора позволяют достать поля.

```json
{"full_name": "Иванов Иван", "group": "ИС-21", "email": "ivanov@example.ru"}
```

Загрузка JSON идёт построчно: один документ на строку. Такой файл принимает `LOAD DATA` в таблицу с одним столбцом типа `JSON`.

```sql
CREATE TABLE students_json_stage (
  id  INT AUTO_INCREMENT PRIMARY KEY,
  doc JSON NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

LOAD DATA LOCAL INFILE 'C:/xampp/htdocs/import/students.jsonl'
INTO TABLE students_json_stage
CHARACTER SET utf8mb4
LINES TERMINATED BY '\r\n'
(doc);
```

Разбор достаёт поля оператором `->>`, который возвращает текст без кавычек JSON.

```sql
SELECT doc->>'$.full_name' AS full_name,
       doc->>'$.group'     AS group_name,
       doc->>'$.email'     AS email
FROM students_json_stage
WHERE JSON_VALID(doc);
```

Проверка `JSON_VALID` обязательна: битая скобка в одной строке иначе остановит разбор всего набора. Для вложенных массивов, например списка оценок, поле извлекают через `JSON_EXTRACT` и разворачивают в отдельные строки запросом, а не в приложении.

JSON не заменяет нормализацию. Хранить в одном поле всю историю студента удобно для обмена, но связи, уникальность и внешние ключи работают только в обычных таблицах. Поэтому JSON почти всегда промежуточный формат: документ принимают, разбирают и раскладывают по таблицам.

## Экспорт

Экспорт это тот же обмен, только в обратную сторону, и здесь важны те же три вещи. Для CSV подходит `SELECT ... INTO OUTFILE`.

```sql
SELECT id, full_name, email
FROM students
INTO OUTFILE 'C:/xampp/mysql/export/students.csv'
CHARACTER SET utf8mb4
FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
LINES TERMINATED BY '\r\n';
```

Команда требует привилегии `FILE` и каталога из `secure_file_priv`. Если каталог не разрешён, файл не появится, и ошибка будет не про права, а про доступ к пути.

Для копии базы целиком используют `mysqldump`, который сохраняет схему, данные и кодировку.

```bash
C:\xampp\mysql\bin\mysqldump.exe -u root --default-character-set=utf8mb4 --single-transaction --routines --triggers dean > dean.sql
```

phpMyAdmin на вкладке «Экспорт» умеет CSV, JSON и SQL, но для больших таблиц упирается в лимиты PHP и в память браузера. Проверка выгрузки простая: загрузить файл обратно в промежуточную таблицу и сверить число строк.

## Кодировка utf8mb4

`utf8mb4` это кодировка, которая хранит любой символ Unicode, включая эмодзи и редкие иероглифы, в четырёх байтах. Старое имя `utf8` в MySQL означает `utf8mb3` и хранит только три байта: часть символов теряется или заменяется знаком вопроса.

Кодировка должна совпадать на четырёх уровнях: база, таблица, столбец и соединение. Если соединение объявлено как `latin1`, сервер перекодирует текст при вставке, и кириллица искажается даже при правильной таблице.

```sql
CREATE DATABASE dean CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
SET NAMES utf8mb4;
SHOW VARIABLES LIKE 'character_set%';
```

В phpMyAdmin кодировку соединения задаёт параметр `$cfg['DefaultCharset']` в `config.inc.php`. В .NET её задаёт `CharSet=utf8mb4` в строке подключения. В CSV её задаёт сам файл, и это единственное место, где ошибку нельзя исправить настройкой сервера.

Отдельная ловушка это BOM. Excel сохраняет CSV с тремя невидимыми байтами в начале файла, и первый столбец получает имя вида `\ufeffemail`. При загрузке с явным списком столбцов это не мешает, при загрузке по именам заголовка даёт ошибку «неизвестный столбец». Лечится сохранением без BOM или пропуском первой строки.

## Сверка результата

Сверка отвечает на вопрос «данные доехали целиком», а не «команда не упала». Минимальный набор проверок:

- число строк в файле, в промежуточной таблице и в рабочей;
- число отклонённых строк и причина по каждой;
- сумма по денежному столбцу до и после, потому что она ловит и потери, и дубли;
- выборочное сравнение пяти строк из файла с пятью строками в базе.

```sql
SELECT COUNT(*) AS rows_now, SUM(amount) AS total_now FROM payments;
CHECKSUM TABLE payments;
```

`CHECKSUM TABLE` даёт быстрый отпечаток содержимого, но он меняется от любой правки, поэтому годится для сравнения копии с оригиналом, а не для поиска причины расхождения.

## Типичные ошибки

- **Молча пропустить строки.** `LOAD DATA` с `IGNORE` или импорт в phpMyAdmin без чтения блока предупреждений дают «успех» при потерях. Лечение: всегда `SHOW WARNINGS` и сверка counts.
- **Неверная кодировка.** Файл в cp1251 читают как utf8mb4, и текст превращается в мусор. Проверяют кодировку файла до загрузки, а не после.
- **Загрузка в рабочую таблицу без проверки.** Одна ошибка в файле портит данные, а откатить импорт нечем, если не было ни копии, ни промежуточной таблицы.
- **Забыть про конец строки.** Файл с `\r\n` читают с `\n`, и последнее поле каждой строки получает лишний символ. Ошибка видна только при сравнении строк.
- **Путать `IGNORE 1 LINES` и `IGNORE`.** Первое пропускает заголовок, второе глушит ошибки. Вторая форма без разбора предупреждений и есть тихая потеря.
- **Импортировать поверх работающей системы.** Пока идёт загрузка, пользователи видят половину данных. Импорт делают в промежуточную таблицу, а перенос в рабочую на короткое время и в транзакции.

> [!TRADEOFF] Скорость и проверка
> Прямая загрузка в рабочую таблицу быстрее на одну команду, но не даёт ни причин отказа, ни возможности отменить часть строк. Промежуточная таблица стоит одного лишнего шага и окупается первым же кривым файлом.

## Проверьте себя

> [!CHECK] После импорта CSV в таблице 187 строк вместо 200. С чего начать разбор?
> С `SHOW WARNINGS` сразу после загрузки и с числа строк в промежуточной таблице. Если промежуточная таблица содержит все 200, потеря случилась на переносе: скорее всего, `JOIN` отбросил строки с неизвестной группой или `ON DUPLICATE KEY` перезаписал дубли. Если в промежуточной меньше 200, файл прочитан не полностью: проверяют конец строки, разделитель и кодировку.

> [!CHECK] Почему файл, сохранённый Excel, часто ломает первый столбец?
> Excel пишет BOM в начале UTF-8 файла, и первый заголовок получает невидимый символ. При загрузке по именам столбцов сервер не находит `email` и сообщает о неизвестном столбце. Помогает сохранение без BOM или явный список столбцов в `LOAD DATA`.

> [!CHECK] Зачем сверять сумму по денежному столбцу, если число строк совпало?
> Число строк не ловит пару «одна строка потеряна, одна продублирована». Сумма и уникальные ключи показывают, что набор не только той же длины, но и того же состава.

## Итоги

- Обмен требует формата, кодировки и явных правил обработки ошибок.
- CSV годится для плоских списков, JSON для вложенных документов, SQL для копии базы.
- Промежуточная таблица отделяет приём файла от проверки и переноса.
- `LOAD DATA LOCAL INFILE` задаёт кодировку, разделитель и конец строки явно.
- `SHOW WARNINGS` и сверка counts показывают, что произошло на самом деле.
- `utf8mb4` нужен на всех четырёх уровнях, включая соединение и сам файл.

## Тест по лекции

::quiz
Q: Что означает сообщение phpMyAdmin «Импорт успешно завершён»?
+ Команда не упала, но часть строк могла быть отклонена
- Все строки файла точно попали в таблицу
- Кодировка файла определена автоматически
- Таблица переименована в рабочую
! Успешное завершение говорит только об отсутствии ошибки команды.

Q: Зачем нужна промежуточная таблица при импорте?
+ Чтобы принять файл как текст и проверить строки до переноса
- Чтобы ускорить работу сервера MySQL
- Чтобы обойти права пользователя
- Чтобы заменить внешние ключи
! Промежуточная таблица отделяет приём файла от проверки и переноса.

Q: Что задаёт параметр secure_file_priv?
+ Каталог, из которого серверу разрешено читать и писать файлы
- Максимальный размер импортируемого файла
- Кодировку соединения по умолчанию
- Список пользователей с правом FILE
! Без разрешённого каталога LOAD DATA и SELECT INTO OUTFILE не работают.

Q: Чем IGNORE 1 LINES отличается от IGNORE перед INTO TABLE?
+ Первое пропускает строку заголовка, второе превращает ошибки строк в предупреждения
- Оба пропускают первую строку файла
- Первое глушит ошибки, второе пропускает заголовок
- Оба отключают проверку типов
! Это разные механизмы с похожими словами.

Q: Какой конец строки указывают для CSV, сохранённого в Windows?
+ \r\n
- \n
- \r
- \t
! Windows пишет возврат каретки и перевод строки, иначе последнее поле получит лишний символ.

Q: Что делает оператор ->> при разборе JSON?
+ Возвращает значение поля как текст без кавычек JSON
- Удаляет поле из документа
- Проверяет документ на корректность
- Преобразует документ в таблицу
! Оператор ->> сразу снимает кавычки, поэтому результат годится для вставки.

Q: Почему Excel сохраняет CSV, который плохо читается?
+ Он пишет BOM и может использовать точку с запятой как разделитель
- Он всегда сжимает файл
- Он меняет тип столбцов на числа
- Он удаляет первую строку
! BOM ломает имя первого столбца, а точка с запятой не совпадает с разделителем по умолчанию.

Q: Что показывает SHOW WARNINGS после загрузки?
+ Строки, которые сервер принял не полностью, и причину
- Список пользователей с доступом к таблице
- Размер файла и число столбцов
- План выполнения запроса
! Предупреждения это единственный след частично принятых строк.

Q: Зачем нужна команда CHECKSUM TABLE?
+ Быстро сравнить содержимое копии и оригинала
- Найти строку с неверной кодировкой
- Ускорить импорт большого файла
- Создать резервную копию таблицы
! Отпечаток содержимого удобен для сверки, но не указывает причину расхождения.

Q: Какие данные лучше передавать в формате JSON?
+ Вложенный документ с массивом оценок
+ Структуру, где поля могут отсутствовать
- Плоский список студентов с одинаковыми столбцами
- Полную копию базы вместе со схемой
! JSON хранит вложенность, но не заменяет нормализацию и внешние ключи.

Q: Какие проверки нужны после импорта?
+ Сравнить число строк в файле, промежуточной и рабочей таблице
+ Прочитать SHOW WARNINGS и разобрать отклонённые строки
+ Сверить сумму по денежному столбцу
- Ограничиться сообщением об успешном завершении
! Сверка отвечает на вопрос, доехали ли данные целиком.

Q: Какие ошибки приводят к тихой потере строк?
+ Загрузка с IGNORE без разбора предупреждений
+ Перенос через JOIN, который отбрасывает строки с неизвестной группой
+ Обрыв импорта phpMyAdmin на пределе размера файла
- Явный список столбцов в LOAD DATA
! Потеря почти всегда сопровождается «успешным» сообщением.

Q: Где должна совпадать кодировка utf8mb4?
+ База данных
+ Таблица и её столбцы
+ Соединение с сервером
+ Сам файл обмена
- Только имя пользователя MySQL
! Кодировка должна совпадать на всех уровнях, иначе сервер перекодирует текст.

Q: Какая кодировка хранит любой символ Unicode в MySQL?
= utf8mb4
= utf8 mb4
! utf8mb4 занимает до четырёх байт и хранит эмодзи, в отличие от utf8mb3.

Q: Какой параметр задаёт каталог, из которого серверу разрешено читать файлы?
= secure_file_priv
= secure-file-priv
! Пустое значение снимает ограничение, путь разрешает только указанный каталог.
