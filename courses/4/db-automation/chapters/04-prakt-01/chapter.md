## Цель работы

СУБД считается установленной не тогда, когда закончилась установка пакета, а тогда, когда к ней подключается нужный пользователь с нужного адреса и получает ожидаемые права. Поэтому работа идёт от пакета до двух успешных сеансов: один изнутри виртуальной машины, второй с хоста через проброс порта.

Вы устанавливаете PostgreSQL 16 в Ubuntu Server, создаёте роль `dean_app` и базу `dean`, открываете сетевой доступ и фиксируете каждый шаг в протоколе. Итог работы: работающий кластер, база «Деканат» и доказательства того, что подключение настроено осознанно, а не случайно.

## Оборудование и программное обеспечение

- Хост на Windows 10 или 11 с VirtualBox 7 и свободными 2 ГБ оперативной памяти.
- Виртуальная машина Ubuntu Server 24.04 LTS: 2 vCPU, 2 ГБ памяти, 15 ГБ диска, учётная запись с `sudo`.
- Сеть машины: режим NAT с пробросом порта `127.0.0.1:5432` на гостевой `10.0.2.15:5432`.
- Клиент `psql` для Windows из архива бинарников PostgreSQL, распакованный в личную папку. Установка и права администратора не нужны.
- Текстовый редактор для протокола и табличный редактор для отчёта.

## Краткие теоретические сведения

**Кластер** это один экземпляр сервера со своим каталогом данных, журналом WAL и набором баз. Пакет `postgresql` в Ubuntu создаёт кластер с именем `main` версии 16 и службу `postgresql@16-main`. Утилита `pg_lsclusters` показывает версию, имя кластера, порт, статус и каталог данных. Один сервер может держать несколько кластеров на разных портах, и это штатный способ поставить рядом вторую версию.

Каталог данных принадлежит служебному пользователю операционной системы `postgres`. Поэтому администратор входит в `psql` командой `sudo -u postgres psql`, а не от своего имени: так он получает доступ к файлам кластера и к локальному сокету. Смешивать эту служебную роль с рабочими учётными записями нельзя, иначе приложение получит права суперпользователя.

**Роль** это учётная запись внутри кластера. Роль с атрибутом `LOGIN` может открыть сеанс, роль без `LOGIN` служит группой для выдачи прав. Отдельного объекта «пользователь» в PostgreSQL нет: пользователь это роль, которой разрешили вход. База и роль существуют независимо: роль одна на кластер, база принадлежит кластеру и принимает подключения от любой роли, которой выдали `CONNECT`.

**Подключение** по TCP проходит три проверки. Клиент обращается к адресу и порту. Сервер принимает соединение только на тех адресах, которые перечислены в параметре `listen_addresses`. Затем сервер читает `pg_hba.conf` и ищет первую строку, совпавшую по типу подключения, базе, роли и адресу клиента. Если строка требует пароль, проверяется метод `scram-sha-256`. Порядок строк важен: первое совпадение выигрывает, поэтому широкое правило не должно стоять выше узкого.

**Проброс порта** в режиме NAT работает так: VirtualBox слушает `127.0.0.1:5432` на хосте и передаёт соединение в гостевую машину на `10.0.2.15:5432`. Для сервера источником выглядит не хост, а шлюз NAT с адресом `10.0.2.2`. Именно этот адрес и указывают в `pg_hba.conf`.

**`pg_isready`** проверяет только то, что сервер принимает соединения. Она не проверяет пароль, права и существование базы, поэтому зелёный ответ не заменяет успешный вход через `psql`.

## Ход работы

### Шаг 1. Подготовьте машину и проброс порта

Запустите виртуальную машину и узнайте её адрес.

```bash
hostname -I
ip route
```

В настройках VirtualBox откройте `Сеть`, адаптер 1, `Дополнительно`, `Проброс портов` и добавьте правило: протокол TCP, адрес хоста `127.0.0.1`, порт хоста `5432`, адрес гостя `10.0.2.15`, порт гостя `5432`. Если адрес гостя другой, подставьте его.

Дальше каждый вывод начинайте строкой с фамилией и группой: так скриншот подтверждает, кто его сделал. Для командной строки это `echo`, для `psql` отдельный запрос.

```bash
echo "Иванов ИС-41"
sudo apt update
```

### Шаг 2. Установите PostgreSQL

```bash
echo "Иванов ИС-41"
sudo apt install -y postgresql postgresql-contrib
psql --version
pg_lsclusters
sudo systemctl status postgresql --no-pager
```

`pg_lsclusters` должен показать одну строку: версия 16, кластер `main`, порт 5432, статус `online`. Если статус `down`, прочитайте журнал `sudo journalctl -u postgresql@16-main -n 50`.

Сделайте скриншот вывода `psql --version` и `pg_lsclusters`.

### Шаг 3. Войдите под служебной ролью

```bash
sudo -u postgres psql
```

```sql
\conninfo
SHOW server_version;
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
```

Пароль не запрашивается, потому что подключение идёт через локальный сокет, а `pg_hba.conf` для него использует `peer`: сервер доверяет имени пользователя операционной системы. Запишите в протокол пути к `postgresql.conf` и `pg_hba.conf`, они понадобятся на шаге 5. Выйдите командой `\q`.

### Шаг 4. Создайте роль и базу

Снова войдите под `postgres` и выполните два оператора.

```sql
CREATE ROLE dean_app LOGIN PASSWORD 'DeanApp_2026';
CREATE DATABASE dean OWNER dean_app ENCODING 'UTF8' TEMPLATE template0;
```

```sql
\l
\du
SELECT datname, pg_get_userbyid(datdba) AS owner
FROM pg_database
WHERE datname = 'dean';
```

`\l` показывает список баз и владельца, `\du` список ролей и их атрибуты. У `dean_app` не должно быть атрибутов `Superuser` и `Create DB`, а вход проверяется отдельным подключением: приложению не нужны права выше владения своей базой.

Шаблон `template0` выбран намеренно: он остаётся неизменным, поэтому допускает явное указание кодировки. Шаблон `template1` копирует всё, что в него однажды добавили, и тогда кодировку уже не поменять.

Пароль в открытом виде попал в историю команд. В учебной машине это допустимо, в рабочей среде пароль задают командой `\password dean_app`, чтобы он не остался в журнале и в файле истории.

Сделайте скриншот `\l` и `\du`.

### Шаг 5. Откройте сетевой доступ

Откройте `postgresql.conf` и найдите строку `listen_addresses`.

```bash
sudo nano /etc/postgresql/16/main/postgresql.conf
```

```text
listen_addresses = '*'
```

Звёздочка означает «слушать все адреса машины». Для учебной VM это приемлемо, потому что машина не выходит в общую сеть, а допуск всё равно решает `pg_hba.conf`. В рабочей среде перечисляют конкретные адреса.

Теперь добавьте правило в `pg_hba.conf` выше остальных строк типа `host`.

```text
host    dean    dean_app    10.0.2.2/32    scram-sha-256
```

Строка читается так: TCP, база `dean`, роль `dean_app`, адрес `10.0.2.2`, пароль по `scram-sha-256`. Перезапустите службу и проверьте, что сервер слушает порт.

```bash
echo "Иванов ИС-41"
sudo systemctl restart postgresql
sudo systemctl status postgresql --no-pager
pg_isready -h 127.0.0.1 -p 5432
sudo ss -ltnp | grep 5432
```

`pg_isready` печатает `accepting connections`. Если ответ `no response`, сервер не поднялся: смотрите `journalctl` и синтаксис `postgresql.conf`.

### Шаг 6. Подключитесь изнутри машины

```bash
psql "host=127.0.0.1 port=5432 dbname=dean user=dean_app"
```

```sql
SELECT 'Иванов ИС-41' AS student;
SELECT current_user, current_database(), inet_server_addr(), inet_client_addr();
SHOW listen_addresses;
SELECT version();
```

`inet_client_addr()` вернёт `127.0.0.1`, потому что клиент и сервер на одной машине. Убедитесь, что запросы выполняются от `dean_app`, а не от `postgres`: это разные права.

Сделайте скриншот вывода `SHOW listen_addresses` и успешного сеанса с фамилией в первой строке.

### Шаг 7. Подключитесь с хоста

Распакуйте архив бинарников PostgreSQL в личную папку и откройте PowerShell в каталоге `bin`.

```powershell
.\psql.exe -h 127.0.0.1 -p 5432 -U dean_app -d dean
```

```sql
SELECT 'Иванов ИС-41' AS student;
\conninfo
SELECT inet_client_addr(), inet_server_addr();
```

Теперь `inet_client_addr()` вернёт `10.0.2.2`: это шлюз NAT, через который VirtualBox передал соединение. Если вход не проходит, проверьте по порядку проброс порта, значение `listen_addresses`, строку в `pg_hba.conf` и файрвол `sudo ufw status`.

Сделайте скриншот успешного подключения с хоста.

### Шаг 8. Соберите протокол установки

Протокол это таблица, по которой другой человек повторит вашу установку. Заполните её по шагам.

| № | Команда или оператор | Что проверяли | Результат | Скриншот |
|---|---|---|---|---|
| 1 | `psql --version` | Версия клиента | 16.x | 1 |
| 2 | `pg_lsclusters` | Кластер, порт, статус | `16 main 5432 online` | 1 |
| 3 | `\l` | База `dean` и владелец | `dean`, `dean_app` | 2 |
| 4 | `\du` | Роль `dean_app` | Вход разрешён, без `Superuser` | 2 |
| 5 | `SHOW listen_addresses` | Сервер слушает сеть | `*` | 3 |
| 6 | `psql` с хоста | Проброс порта и `pg_hba` | Вход выполнен | 4 |

В выводах на скриншотах должны быть видны версия, имя базы, имя роли и адрес клиента. Скриншоты шапки отчёта и текста теории не нужны.

### Требования к отчёту

Отчёт содержит цель, параметры машины (версия Ubuntu, объём памяти, режим сети), протокол из таблицы, четыре скриншота и короткий вывод: какие три условия должны совпасть, чтобы подключение с хоста прошло. Отдельно укажите, что вы изменили в `postgresql.conf` и `pg_hba.conf` и почему правило для `10.0.2.2` стоит выше общего правила.

## Что сдать

- Протокол установки с командами, результатами и номерами скриншотов.
- Скриншоты `psql --version`, `pg_lsclusters`, `\l`, `\du`, `SHOW listen_addresses` и успешного подключения с хоста.
- Фрагменты `postgresql.conf` и `pg_hba.conf`, которые вы изменили.
- Вывод о том, какие проверки проходит подключение и где оно может отказать.
- Файл отчёта с титульной шапкой и данными студента.
