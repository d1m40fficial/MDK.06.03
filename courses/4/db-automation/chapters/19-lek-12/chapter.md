## Одна идея

Ручное обслуживание выглядит надёжным, пока его делает один человек. Он помнит, что копию надо класть в `/var/backups/dean`, что база называется `dean`, что старые файлы удаляют через неделю. Стоит заболеть, уехать или просто устать, и порядок рассыпается: копия легла не туда, имя базы перепутано, старые файлы заняли весь диск.

**Скрипт** превращает действие в процедуру с контрактом. У него есть вход (аргументы), выход (код возврата), след (журнал) и защита от наложения запусков. Если контракт соблюдён, обслуживание можно повторять сколько угодно раз и поручать машине.

Главная мысль этой лекции: автоматизация это не «записать команды в файл». Это договорённость о том, что скрипт делает при ошибке, что пишет в журнал и что вернёт планировщику.

## Каркас скрипта

Начнём с минимального каркаса. Он ещё ничего не делает с базой, но уже задаёт правила игры.

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'

usage() {
  echo "usage: $0 --db NAME [--out DIR] [--dry-run]" >&2
  exit 2
}

db=""
out="/var/backups/dean"
dry=0
```

Разберём три ключа в `set`. `-e` завершает скрипт при первой неудачной команде. `-u` считает обращение к незаданной переменной ошибкой. `-o pipefail` делает код возврата конвейера равным коду первой упавшей команды. Без последнего `pg_dump | gzip` вернёт успех, даже если `pg_dump` упал, потому что `gzip` завершился нормально.

`IFS` задаёт разделители полей. Значение из перевода строки и табуляции защищает от разбиения имён файлов с пробелами. Это мелочь, которая ломает скрипты на путях вроде `/home/dean/backup 2026`.

`usage` печатает подсказку в поток ошибок и возвращает код 2. Код 2 отличает ошибку вызова от ошибки работы: планировщик по нему поймёт, что повторять запуск бессмысленно, пока не исправлены аргументы.

## Аргументы и --dry-run

Аргументы задают всё, что может измениться между запусками: имя базы, каталог выгрузки, глубину хранения. Внутри скрипта не должно быть зашитых имён, кроме значений по умолчанию.

```bash
while [ $# -gt 0 ]; do
  case "$1" in
    --db) [ $# -ge 2 ] || usage; db="$2"; shift 2 ;;
    --out) [ $# -ge 2 ] || usage; out="$2"; shift 2 ;;
    --dry-run) dry=1; shift ;;
    *) usage ;;
  esac
done
[ -n "$db" ] || usage
```

Проверка `[ $# -ge 2 ]` не даёт разобрать ключ без значения. Без неё `shift 2` на последнем аргументе завершит скрипт с кодом 1 вместо понятной подсказки. Неизвестный ключ тоже ведёт к `usage`, а не игнорируется молча.

Режим `--dry-run` печатает команды, которые скрипт собирается выполнить, и завершается с кодом 0. Он нужен, чтобы проверить путь и параметры до реальной работы.

```bash
if [ "$dry" -eq 1 ]; then
  echo "pg_dump -Fc -d $db -f $out/$db.dump"
  exit 0
fi
```

Печатать команду и выполнять её лучше из одного места, иначе подсказка разойдётся с реальностью. Простой приём: собрать команду в массив, напечатать его при `--dry-run`, а иначе запустить тот же массив.

## psql и ON_ERROR_STOP

Скрипт обслуживания почти всегда вызывает `psql`. Здесь есть ловушка: по умолчанию `psql` продолжает выполнять файл после ошибки SQL и возвращает 0, если до конца файла дошёл. Для интерактивной работы это удобно, для автоматизации опасно.

```bash
psql -X -q -v ON_ERROR_STOP=1 -d "$db" -f "$sql"
```

`ON_ERROR_STOP=1` заставляет psql остановиться на первой ошибке и вернуть код 3. `-X` запрещает читать `~/.psqlrc`: чужой файл настроек не должен менять поведение скрипта. `-q` убирает приветствие и служебные сообщения, чтобы журнал оставался читаемым.

Для разбора результата в скрипте используют `-t -A`: только значения, без заголовков и выравнивания. Тогда вывод можно сравнить строкой.

```bash
count=$(psql -X -q -t -A -v ON_ERROR_STOP=1 -d "$db" -c "select count(*) from students")
[ "$count" -gt 0 ] || { echo "таблица students пуста" >&2; exit 1; }
```

Проверка после запроса обязательна: успешный код `psql` говорит, что запрос выполнился, но не что результат осмысленный.

## Журналирование

Журнал отвечает на вопрос «что произошло ночью», когда рядом никого нет. Без него сбой виден только по отсутствию результата, и причину приходится угадывать.

Минимальный набор записей: время старта, аргументы, имя базы, выполненная команда, результат, время окончания и код возврата. Хороший журнал пишется и при успехе, и при ошибке.

```bash
log() {
  printf '%s %s\n' "$(date -Is)" "$*"
}

logfile="/var/log/dean/maintenance.log"
exec >>"$logfile" 2>&1
log "start db=$db out=$out dry=$dry"
```

`exec >>` перенаправляет весь дальнейший вывод скрипта в файл, включая сообщения `pg_dump` и `psql`. Ошибки стандартного потока попадают туда же, поэтому в журнале оказывается полная картина, а не только то, что автор скрипта решил напечатать. Каталог журнала создают заранее и дают пользователю задания права на запись, иначе перенаправление не сработает.

У журнала есть цена: он растёт. Если файл не ограничивать, через год он займёт диск и станет нечитаемым. Помогают `logrotate` или ротация прямо в скрипте: хранить последние несколько файлов и удалять старые.

Отдельно стоит писать в журнал **итог работы**, а не только команды. Строка вида `done rows=5000 status=ok` позволяет потом сверить результат с базой, не открывая файлы.

## Защита от параллельного запуска

Планировщик может запустить вторую копию скрипта, пока первая ещё работает: копия базы идёт долго, а расписание уже наступило. Две копии одновременно пишут в один файл, мешают друг другу и нагружают диск.

Проверка «есть ли процесс с таким именем» ненадёжна: процесс мог завершиться, а файл с номером остался. Правильнее взять блокировку файла, которую ядро снимает автоматически при завершении процесса.

```bash
lockfile="/var/lock/dean-maintenance.lock"
exec 9>"$lockfile"
if ! flock -n 9; then
  log "already running, skip"
  exit 0
fi
```

`flock -n` не ждёт, а сразу сообщает, что блокировка занята. Файл остаётся на диске, но это не проблема: важен не файл, а блокировка на нём, а она исчезает вместе с процессом. Номер 9 это просто свободный дескриптор, который остаётся открытым до конца скрипта.

Каталог для файла блокировки должен быть доступен пользователю задания на запись. Если `/var/lock` закрыт, берут каталог в домашнем каталоге пользователя задания или создают отдельный каталог с нужными правами.

Код возврата 0 при пропуске это решение, а не случайность. Если считать пропуск ошибкой, планировщик начнёт присылать тревоги каждую ночь, и настоящий сбой потеряется среди ложных.

::gate Что останется на диске, если скрипт прервётся посередине?

## Временные файлы и trap

Копия базы пишется не мгновенно. Если прервать скрипт посередине, на диске останется недописанный файл, который выглядит как настоящая копия. Хуже того, его могут взять для восстановления.

Решение: писать во временный каталог и переносить готовый файл на место одной операцией.

```bash
tmp="$(mktemp -d)"
cleanup() {
  rm -rf "$tmp"
}
trap cleanup EXIT

pg_dump -Fc -d "$db" -f "$tmp/$db.dump"
mv "$tmp/$db.dump" "$out/$db.dump"
```

`trap cleanup EXIT` вызывает уборку при любом завершении: обычном, по ошибке, по сигналу. Без него временные каталоги копятся, пока не закончится место.

`mv` в пределах одной файловой системы атомарен: файл появляется на месте целиком или не появляется вовсе. Если каталоги на разных дисках, `mv` копирует и удаляет, и атомарность теряется; тогда временный каталог создают рядом с целевым.

С `set -u` пустая переменная в `rm -rf "$tmp"` не превратится в `rm -rf /`: подстановка упадёт раньше. Это ещё одна причина не отключать `-u` ради «удобства».

## Идемпотентность

**Идемпотентность** это свойство операции давать тот же результат при повторном выполнении. Для обслуживания базы она обязательна: скрипт запускают после сбоя, по расписанию и вручную, и никто не помнит, дошёл ли прошлый запуск до конца.

Плохой пример: `insert into groups(name) values ('ИС-23')`. Второй запуск упадёт на уникальном ограничении или создаст дубль, если ограничения нет.

Хорошие приёмы:

```sql
create table if not exists report_cache (
  day date primary key,
  payload jsonb not null
);

insert into report_cache(day, payload)
values (current_date, '{}'::jsonb)
on conflict (day) do update set payload = excluded.payload;
```

`if not exists` не падает на существующей таблице. `on conflict do update` заменяет строку, а не добавляет вторую. Для отчёта, который пересчитывается целиком, подходит другая схема: удалить старые строки и вставить новые в одной транзакции.

```sql
begin;
delete from report_cache where day = current_date;
insert into report_cache(day, payload)
select current_date, jsonb_build_object('students', count(*))
from students;
commit;
```

Если скрипт упадёт между `delete` и `insert`, транзакция откатится, и старая версия останется на месте. Читатель не увидит пустую таблицу.

Отдельно проверяют версию схемы. Если скрипт накатывает изменение, он сначала смотрит в `schema_version`, применено ли оно, и только потом работает. Это защищает от повторного `alter table`, который упадёт на уже существующем столбце.

## Секреты и .pgpass

Пароль в тексте скрипта это худший вариант: файл попадает в резервные копии, в систему контроля версий и в вывод `ps` при неаккуратном вызове. Даже права 600 не спасают от копии, сделанной от имени владельца.

PostgreSQL читает пароль из файла `~/.pgpass`. Формат строки: хост, порт, база, пользователь и пароль через двоеточие.

```
127.0.0.1:5432:dean:dean_app:secret
```

Файл должен принадлежать пользователю, от имени которого работает скрипт, и иметь права `600`. Иначе `psql` предупредит и откажется его читать.

```bash
chmod 600 ~/.pgpass
```

Путь можно задать явно через `PGPASSFILE`, если у задания свой пользователь или свой набор баз. Это удобнее, чем держать один общий файл на все случаи.

```bash
export PGPASSFILE="/etc/dean/pgpass"
psql -X -v ON_ERROR_STOP=1 -d "$db" -c "select 1"
```

Пароль в переменной окружения тоже рискован: переменные процесса видны другим процессам того же пользователя и наследуются дочерними процессами. `.pgpass` с правильными правами остаётся самым простым способом, который не требует прав администратора сервера.

## Коды возврата

Код возврата это единственный канал, по которому планировщик понимает, что произошло. Поэтому коды назначают осознанно, а не оставляют случайными.

| Код | Значение | Что делать дальше |
|---|---|---|
| 0 | успех или пропуск по блокировке | ничего |
| 1 | ошибка работы | тревога |
| 2 | ошибка аргументов | исправить вызов, повтор бесполезен |
| 75 | временная ошибка | повторить позже |

Код 75 (`EX_TEMPFAIL`) говорит, что база была недоступна или занята, и запуск имеет смысл повторить. Код 1 говорит об ошибке, которую повтором не исправить: нет прав, битый файл, неверный запрос.

Важно не терять код по пути. Конструкция `command || true` в конце скрипта превращает любую ошибку в успех. Так же опасен `exit 0` после неудачной ветки: он сообщает планировщику, что всё хорошо, хотя работа не сделана.

```bash
if ! pg_dump -Fc -d "$db" -f "$tmp/$db.dump"; then
  log "pg_dump failed db=$db"
  exit 1
fi
```

Без явной проверки скрипт завершится с кодом упавшей команды, но в журнале не останется понятной причины. Явная ветка нужна ради записи, а не ради самого кода.

## Типичные ошибки

- **Пароль в скрипте.** Файл уходит в копии и в репозиторий. Пароль хранят в `.pgpass` с правами 600, а путь задают через `PGPASSFILE`.
- **Нет журнала.** Ночной сбой виден только по отсутствию файла. Журнал пишут при успехе и при ошибке, с временем и кодом.
- **Скрипт ломает базу при повторном запуске.** Вставка без `on conflict`, повторный `alter table`, дописывание в файл. Каждую операцию делают идемпотентной.
- **`set -e` без `pipefail`.** Конвейер возвращает код последней команды, и ошибка `pg_dump` теряется за успешным `gzip`.
- **Нет блокировки.** Два запуска пишут в один файл и мешают друг другу. `flock` снимает вопрос.
- **Забытый `ON_ERROR_STOP`.** psql продолжает после ошибки SQL и возвращает 0. Скрипт считает работу выполненной.
- **`rm -rf` без кавычек и без `set -u`.** Пустая переменная превращает уборку в удаление не того каталога.
- **Журнал без ротации.** Через год файл занимает диск, и найти в нём нужную ночь невозможно.

> [!PITFALL] «Работает же вручную»
> Скрипт, запущенный из терминала, наследует окружение, права и текущий каталог. Планировщик запускает его в другом окружении, от другого пользователя и без переменных из профиля. Проверяйте скрипт тем же способом, каким его будет запускать планировщик.

## Проверьте себя

> [!CHECK] Скрипт делает `pg_dump`, затем `gzip`. Команда `pg_dump` упала, но скрипт вернул 0. Почему?
> Без `set -o pipefail` код конвейера равен коду последней команды, а `gzip` завершился успешно. Нужно добавить `pipefail` и проверять результат `pg_dump` до сжатия.

> [!CHECK] Почему пропуск по занятой блокировке возвращает 0, а не ошибку?
> Потому что работа уже выполняется другой копией скрипта, и повторять её не нужно. Код 0 избавляет планировщик от ложных тревог. Ошибкой считают ситуацию, когда работа не выполнена и не выполняется.

> [!CHECK] Скрипт создаёт таблицу `report_cache` и заполняет её. Как сделать повторный запуск безопасным?
> Создание заменить на `create table if not exists`, вставку на `insert ... on conflict do update` или на удаление и вставку в одной транзакции. Тогда повтор даст то же состояние, а не ошибку и не дубли.

## Итог

- Скрипт это контракт: аргументы, журнал, код возврата и защита от наложения.
- `set -euo pipefail` останавливает работу при ошибке, включая ошибку внутри конвейера.
- `psql -v ON_ERROR_STOP=1` обязателен: без него ошибка SQL не меняет код возврата.
- `flock` надёжнее проверки номера процесса: блокировку снимает ядро.
- Временный каталог и `trap ... EXIT` не оставляют недописанных файлов.
- Идемпотентность достигается `if not exists`, `on conflict` и транзакцией вокруг замены.
- Пароль хранят в `.pgpass` с правами 600, а не в тексте скрипта.
- Коды 0, 1, 2 и 75 дают обработчику понять, что делать дальше.

::quiz
Q: Что делает set -e в начале скрипта?
+ Завершает скрипт при первой неудачной команде
- Печатает каждую команду перед выполнением
- Игнорирует ошибки и продолжает работу
- Проверяет синтаксис всех команд заранее
! Без set -e скрипт продолжит работу после сбоя и может испортить данные.

Q: Зачем нужен set -o pipefail?
+ Чтобы ошибка любой команды конвейера не терялась
- Чтобы конвейер выполнялся параллельно
- Чтобы отключить вывод ошибок
- Чтобы автоматически повторять команду
! Без pipefail код возврата конвейера равен коду последней команды.

Q: Что делает psql -v ON_ERROR_STOP=1?
+ Останавливает выполнение и возвращает код ошибки при сбое SQL
- Продолжает выполнение после ошибки SQL
- Отключает проверку прав доступа
- Сохраняет результат в файл
! Без ON_ERROR_STOP psql доходит до конца файла и возвращает 0.

Q: Зачем скрипт берёт flock на файл блокировки?
+ Чтобы вторая копия не работала одновременно с первой
- Чтобы ускорить pg_dump
- Чтобы зашифровать файл копии
- Чтобы проверить права пользователя
! Блокировка не даёт двум запускам мешать друг другу.

Q: Что делает trap cleanup EXIT?
+ Вызывает уборку при любом завершении скрипта
- Запускает скрипт заново после ошибки
- Блокирует выход из скрипта
- Передаёт управление планировщику
! EXIT срабатывает и при успехе, и при ошибке, и при сигнале.

Q: Где правильно хранить пароль для psql?
+ В файле .pgpass с правами 600
- В тексте скрипта
- В имени базы данных
- В журнале работы
! .pgpass читает сам psql, и пароль не попадает в текст скрипта.

Q: Что означает код возврата 0?
+ Работа выполнена успешно или запуск пропущен по блокировке
- Произошла ошибка работы
- Неверно указаны аргументы
- База недоступна и нужен повтор
! Ноль сообщает планировщику, что тревожиться не нужно.

Q: Что такое идемпотентность скрипта?
+ Повторный запуск приводит к тому же состоянию
- Скрипт выполняется быстрее при повторном запуске
- Скрипт нельзя запустить дважды
- Скрипт всегда возвращает код 0
! Идемпотентная операция не создаёт дублей и не падает на повторном шаге.

Q: Что должно попадать в журнал работы скрипта?
+ Время старта и окончания
+ Аргументы запуска
+ Результат и код возврата
+ Текст ошибки при сбое
- Пароль пользователя базы
- Содержимое всех таблиц
! Журнал объясняет, что и когда произошло, но не хранит секреты.

Q: Что делает скрипт устойчивым к повторному запуску?
+ CREATE TABLE IF NOT EXISTS
+ INSERT с ON CONFLICT
+ Удаление и вставка в одной транзакции
- Вставка без проверки существующих строк
- Повторный ALTER TABLE без проверки
! Эти приёмы приводят базу к тому же состоянию при повторе.

Q: Какие ошибки типичны для скриптов обслуживания?
+ Пароль записан в тексте скрипта
+ Отсутствует журнал работы
+ Нет защиты от параллельного запуска
- Явная проверка кода возврата
- Использование .pgpass
! Секрет в тексте, отсутствие журнала и блокировки ломают автоматизацию.

Q: Что проверяет скрипт до начала работы с базой?
+ Наличие обязательных аргументов
+ Доступность базы и права
+ Свободное место для копии
+ Занятость блокировки
- Цвет темы терминала
- Число строк во всех таблицах
! Вход, доступ, место и блокировка проверяются до изменений.

Q: Какая команда берёт блокировку файла в Linux?
= flock
! flock ставит блокировку на дескриптор, и ядро снимает её при завершении процесса.

Q: Как называют свойство скрипта давать тот же результат при повторном запуске?
= идемпотентность
! Идемпотентность позволяет безопасно повторять запуск после сбоя.

Q: В каком файле psql ищет пароль по умолчанию?
= .pgpass
! По умолчанию psql читает пароли из ~/.pgpass.
