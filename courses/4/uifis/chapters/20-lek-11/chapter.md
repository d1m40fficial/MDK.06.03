## Одна идея

Пользователь нажимает «Показать расписание». Браузер отправляет запрос, приложение обращается к базе, получает строки и возвращает JSON. Браузер рисует таблицу. Если база не ответила, пользователь увидит ошибку, а не пустое расписание. Вся эта цепочка держится на одном контракте: **запрос и ответ**.

**Клиент** это сторона, которая инициирует обмен: браузер, мобильное приложение, скрипт, Postman. **Сервер** принимает запрос, проверяет права, выполняет работу и возвращает ответ. Клиент и сервер это роли, а не обязательно разные компьютеры: один процесс может быть клиентом для другого сервиса.

Главная мысль: веб-взаимодействие это не «магия страницы», а **последовательность HTTP-сообщений**. Поняв запрос и ответ, вы сможете проверить любой API, не открывая исходный код приложения.

## Запрос и ответ

Посмотрите на последовательность. Клиент открывает соединение, отправляет метод, путь, заголовки и иногда тело. Сервер выбирает обработчик, обращается к базе, формирует статус, заголовки и тело ответа. Соединение может закрыться или остаться для следующих запросов.

## Анатомия HTTP

HTTP-запрос состоит из четырёх частей:

- **метод**: что клиент хочет сделать;
- **путь и параметры**: с каким ресурсом;
- **заголовки**: метаданные, тип данных, авторизация, язык;
- **тело**: данные для создания или изменения.

Пример:

```http
GET /api/schedule?group=ИС-21&date=2026-10-22 HTTP/1.1
Host: uifis.local
Authorization: Bearer <token>
Accept: application/json
```

Ответ содержит статус, заголовки и тело:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"group":"ИС-21","lessons":[{"time":"09:00","subject":"Базы данных"}]}
```

**Код состояния** это короткий итог обработки. `2xx` означает успех, `3xx` перенаправление, `4xx` ошибка клиента, `5xx` ошибка сервера. Важно различать `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found` и `500 Internal Server Error`: каждая ошибка указывает на свою причину.

| Код | Значение | Типичная причина |
|---|---|---|
| `200` | OK | запрос выполнен |
| `201` | Created | ресурс создан |
| `400` | Bad Request | неверный JSON или параметры |
| `401` | Unauthorized | нет или истёк токен |
| `403` | Forbidden | прав недостаточно |
| `404` | Not Found | ресурс не найден |
| `500` | Internal Server Error | ошибка приложения или базы |

## Методы и идемпотентность

`GET` запрашивает данные и не должен менять состояние. `POST` создаёт ресурс или запускает действие. `PUT` заменяет ресурс, `PATCH` меняет часть, `DELETE` удаляет. Это соглашение, а не запрет: технически `GET` может изменить данные, но тогда клиенты, кэши и прокси будут вести себя непредсказуемо.

**Идемпотентность** означает, что повторный запрос даёт тот же результат, что и первый. `GET`, `PUT` и `DELETE` обычно идемпотентны, `POST` нет. Если пользователь дважды нажал «Оплатить», повторный `POST` может создать второй платёж. Поэтому в API добавляют ключ идемпотентности или проверку уникальности.

## API и REST

**API** это контракт, по которому одна программа обращается к другой. Веб-API обычно работает через HTTP и обменивается JSON. **REST** это стиль, где ресурсы имеют адреса, а методы HTTP описывают действия:

- `GET /students` список;
- `GET /students/15` один студент;
- `POST /students` создать;
- `PUT /students/15` заменить;
- `DELETE /students/15` удалить.

REST не требует именно такого вида. Важнее единообразие: одинаковые ошибки, понятные имена, предсказуемые статусы, версия API. Контракт фиксируют в OpenAPI: пути, параметры, схемы ответов и коды ошибок.

**JSON** удобен для веб-API: это текст с объектами и массивами. Он не описывает типы так строго, как XML-схема, поэтому сервер обязан валидировать вход. Иначе строка `"15"` может попасть в числовое поле, а `null` сломает расчёт.

## Веб-архитектура

Типовой веб-контур ИС:

1. **Клиент**: браузер или мобильное приложение.
2. **Обратный прокси**: принимает соединение, завершает TLS, направляет запрос.
3. **Сервер приложений**: проверяет права, выполняет бизнес-логику.
4. **База данных**: хранит состояние.
5. **Внешние службы**: почта, платежи, каталог пользователей.

Разделение нужно не для красоты. Оно позволяет обновлять приложение отдельно от базы, ставить несколько экземпляров за прокси и ограничивать доступ к данным. Но каждый слой добавляет точку отказа: прокси может вернуть `502`, приложение `500`, база не ответить вовсе.

**Статический** ресурс отдаётся как файл. **Динамический** ответ вычисляется приложением. Для учебной ИС достаточно статической страницы и одного JSON-эндпоинта, но принцип тот же: клиент получает результат по HTTP.

## Авторизация и сессии

HTTP не хранит состояние между запросами. Чтобы сервер понимал, кто пришёл, клиент присылает **cookie** или **токен** в заголовке `Authorization`. Сервер проверяет подпись, срок действия и права.

- **Сессия** хранится на сервере, клиент получает идентификатор.
- **JWT-токен** содержит подписанные утверждения и проверяется без обращения к сессии.
- **OAuth** позволяет выдать приложению ограниченный доступ к ресурсам пользователя.

Ошибки авторизации опасны тем, что выглядят как обычные ошибки: `401` после истечения токена, `403` при неверной роли, `CORS` при запросе с другого origin. В учебной работе проверяйте успешный и ошибочный сценарии отдельно.

## Кэш и задержка

Кэш сокращает число запросов к серверу. HTTP-заголовки `Cache-Control`, `ETag` и `Last-Modified` говорят клиенту и прокси, можно ли использовать сохранённый ответ. Ошибка кэша проявляется как «старые данные»: пользователь видит расписание прошлой недели, хотя в базе уже новое.

Задержка складывается из сети, очереди, приложения и базы. Среднее значение мало что говорит: важна **хвостовая задержка**. Если 99 процентов запросов быстрые, а один процент ждёт несколько секунд, пользователи всё равно заметят.

## Postman и проверка API

**Postman** позволяет отправить запрос без написания клиента, сохранить коллекцию и добавить тесты. Минимальный набор проверок для учебного API:

- статус `200` при корректном запросе;
- статус `400` или `401` при неверных данных;
- `Content-Type: application/json`;
- обязательные поля в JSON;
- отсутствие лишних персональных данных.

Коллекция это артефакт: её можно передать другому разработчику и повторить проверку. В ДЭ коллекция Postman входит в задание по интеграции модулей.

## Типичные ошибки

- **Проверять только статус 200.** Успешный статус не гарантирует правильные поля.
- **Путать 401 и 403.** 401 значит «не представился», 403 значит «представился, но нельзя».
- **Возвращать HTML вместо JSON.** Клиент не сможет разобрать ответ.
- **Не указывать `Content-Type`.** Браузер и Postman могут интерпретировать тело по-разному.
- **Хранить секреты в URL.** Они попадут в журналы и историю.
- **Игнорировать повторные запросы.** Двойной `POST` создаёт дубликат.

> [!CHECK] Клиент получил 500. Это ошибка клиента?
> Нет. 5xx означает ошибку сервера или его зависимости. Клиент может быть ни при чём, но ему всё равно нужно показать понятное сообщение.

## Проверьте себя

> [!CHECK] Чем 401 отличается от 403?
> 401 говорит, что клиент не аутентифицирован. 403 говорит, что клиент известен, но прав на действие нет.

> [!CHECK] Почему GET не должен менять данные?
> GET могут повторять браузеры, кэши и поисковые роботы. Если он меняет состояние, повторный запрос создаёт неожиданный эффект.

> [!CHECK] Зачем API нужен контракт?
> Контракт фиксирует пути, параметры, форматы и ошибки. По нему клиент и сервер развиваются независимо и проверяются одинаковыми тестами.

> [!CHECK] Что проверить в Postman, кроме статуса?
> Заголовок `Content-Type`, структуру JSON, обязательные поля, типы значений и отсутствие секретов.

## Итоги

- Веб-взаимодействие строится на запросе и ответе.
- HTTP описывает метод, путь, заголовки, тело и код состояния.
- `4xx` это ошибка клиента, `5xx` ошибка сервера или зависимости.
- REST и JSON задают контракт API, а OpenAPI фиксирует его.
- Веб-контур разделяет клиент, прокси, приложение и базу данных.
- Postman проверяет API и сохраняет проверки как артефакт.
- В учебной среде служба работает в VirtualBox, доступ с хоста идёт через проброс порта.
