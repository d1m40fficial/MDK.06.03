## Одна идея

Пользователь нажимает «Показать расписание». Браузер отправляет запрос, приложение проверяет его на пяти рубежах, обращается к базе, получает строки и возвращает JSON. Браузер рисует таблицу. Если замок не пройден, пользователь увидит не пустое расписание, а конкретную ошибку с конкретной причиной. Вся цепочка держится на одном контракте: **запрос и ответ**.

**Клиент** это сторона, которая инициирует обмен: браузер, мобильное приложение, скрипт, Postman. **Сервер** принимает запрос, выполняет проверки, делает работу и возвращает ответ. Клиент и сервер это роли, а не обязательно разные компьютеры: один процесс может быть клиентом для другого сервиса.

Главная мысль: веб-взаимодействие это не «магия страницы», а **последовательность HTTP-сообщений**. Поняв, из чего состоит запрос и на какой проверке он останавливается, вы сможете продиагностировать любой интернет-сервис, не открывая его исходный код.

## Запрос и ответ

Разберём типовое расписание: запрос всегда один и тот же, а ответов может быть шесть. Ответ зависит не от фантазии сервера, а от того, на какой проверке запрос остановился. Посмотрите на машину ниже: один и тот же бланк запроса проходит пять штампов, и первый непройденный штамп останавливает бланк. Диск ставит код, лента журнала печатает строку.

::figure fig-11-http | Выберите сценарий: штампы покажут, на какой проверке запрос остановился.

Пять проверок идут в строгом порядке:

1. **Аутентификация.** Кто прислал запрос? Нет токена, токена мало или он истёк: сервер отвечает `401 Unauthorized` и не смотрит данные дальше.
2. **Права.** Токен есть, но студенту не разрешено смотреть ведомости с оценками: `403 Forbidden`, собеседование и пароль в порядке, действие не положено.
3. **Маршрут.** Обработчик для пути `/api/teacher/11` не существует: `404 Not Found`, запрос верен, но адрес таблицы неверный.
4. **Параметры.** Дата ушла в завтрашний год или поле `group` пусто: `400 Bad Request`, маршрут есть, но данные не проходят валидацию.
5. **База и логика.** Запрос корректен, учебная база не отвечает или падает вычисление: `500 Internal Server Error`, клиент ни в чём не виноват.

Когда все пять штампов сработали, диск ставит `200` и ответ уходит клиенту. Один и тот же запрос, шесть разных исходов, и каждый исход однозначно указывает на своё место в цепочке. Это и есть главная польза кодов состояния: они заменяют словесное перекладывание ответственности точным адресом причины.

## Анатомия HTTP

HTTP-запрос состоит из четырёх частей:

- **метод**: что клиент хочет сделать;
- **путь и параметры**: с каким ресурсом и с какими деталями;
- **заголовки**: метаданные, тип данных, авторизация, язык, формат ответа;
- **тело**: данные для создания или изменения.

Пример:

```http
GET /api/schedule?group=ИС-21&date=2026-10-22 HTTP/1.1
Host: uifis.local
Authorization: Bearer <token>
Accept: application/json
```

Каждая строка здесь существует не для красоты. `Host` говорит, на каком сервере искать ресурс: на одной машине может жить несколько приложений с разным именем. `Authorization` несёт токен; именно его отсутствие даёт `401`. `Accept` просит формат: серверу не обязательно отдавать JSON клиенту, который хочет HTML. Параметры в пути берёт на себя обработчик: он разложит `group` и `date` в отдельные значения, и пустая дата здесь как раз причина `400`.

Ответ содержит статус, заголовки и тело:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"group":"ИС-21","lessons":[{"time":"09:00","subject":"Базы данных"}]}
```

**Код состояния** это короткий итог обработки. `2xx` означает успех, `3xx` перенаправление, `4xx` ошибка клиента, `5xx` ошибка сервера. Важно различать не диапазоны, а конкретные коды: каждый указывает на свой замок.

| Код | Значение | Замок, на котором остановился запрос |
|---|---|---|
| `200` | OK | все проверки пройдены, ответ готов |
| `201` | Created | ресурс создан и записи в базе есть |
| `400` | Bad Request | параметры не прошли валидацию |
| `401` | Unauthorized | нет или истёк токен |
| `403` | Forbidden | прав недостаточно |
| `404` | Not Found | обработчика для этого пути нет |
| `500` | Internal Server Error | ошибка приложения или базы |
| `502` | Bad Gateway | прокси не смог дозвониться до приложения |

Заголовок `Content-Type` в ответе не менее важен, чем сам код: при `application/json` браузер и Postman разбирают тело как JSON, а при `text/html` попытка прочитать объект из строки вернёт либо `undefined`, либо молчаливую ошибку клиента, которую потом объяснить никто не сможет.

## Методы и идемпотентность

`GET` запрашивает данные и не должен менять состояние. `POST` создаёт ресурс или запускает действие. `PUT` заменяет ресурс целиком, `PATCH` меняет часть, `DELETE` удаляет. Это соглашение, а не запрет: технически `GET` может изменить данные, но тогда браузеры, кэши и роботы, которые ходят ко всем адресам подряд, будут вести себя непредсказуемо. Расписание должны иметь возможность получить все, изменять же ведомости и учебные планы стоит только на явно разрешённых маршрутах.

**Идемпотентность** означает, что повторный запрос даёт тот же результат, что и первый. `GET`, `PUT` и `DELETE` обычно идемпотентны, `POST` нет. Пользователь дважды нажал «Оплатить»: первый `POST` создаёт платёж, второй снова денег резервирует и создаёт уже два платежа. В API против этого встают двумя способами: ключом идемпотентности в заголовке и проверкой уникальности в самой базе, чтобы даже «двойной клик» не породил вторую запись.

У методов есть и «ленивые» варианты проверки: условные запросы. `If-None-Match: "abc123"` спрашивает сервер, изменился ли ресурс со времени прошлого обращения. Если ресурс не менялся, сервер отвечает `304 Not Modified` и не передаёт тело вовсе: экономить трафик и серверное время стоит сам по себе, а не потому, что сеть медленная.

## JSON и выбор формата

Практически весь веб-обмен сейчас идёт в JSON. Это текст с объектами, массивами и парами ключ-значение: компактный, читаемый и легко отображающийся прямо в структуры Python и C#. Именно поэтому в наших сервисах мы могли отдать список занятий из базы как массив объектов и тут же рисовать его на странице.

Но у JSON есть подводные камни, о которых сервер обязан помнить:

- JSON не задаёт типы строго. Строка `"15"`, число `15` и случайно попавшее `true` в числовом поле выглядят по-разному, и сервер обязан проверить тип входа, прежде чем записать его в базу или посчитать по нему суммы.
- `null` требует отдельного решения: «поле не задано» и «поле равно пустой строке» это разные состояния, и неявное превращение одного в другое создаёт трудноуловимые ошибки.
- Кодировка всегда оговаривается: `charset=utf-8` в `Content-Type` означает, что строки сравниваются по байтам. «Иванов И.» с пробелом и «Иванов И.» без него это уже разные значения, и сверка без нормализации даст ложные расхождения.
- Вложенность не бесплатна: чем глубже объект, тем сложнее клиенту обрабатывать вложенные массивы, а серверу валидировать вложенность.

Если объект не прошёл проверку, сервер должен вернуть `400` и **сообщить, в чём именно ошибся**, а не молча закрыть соединение. Правило «сначала проверь вход, потом делай работу» живёт в каждом учебном сервисе, независимо от того, что вы пишете: сайт расписания, локальную CRM или сервис заявок.

::gate Что происходит с запросом в сети и кэше?

## Сеть под HTTP

HTTP это протокол поверх сети, а не её замена. Чтобы запрос дошёл, нужно решить три задачи: найти машину, открыть порт и доставить сообщение. По имени `uifis.local` система сначала спрашивает DNS и получает IP-адрес. Затем открывает соединение на конкретном порту, и по нему уже идут HTTP-сообщения. Всё вместе это транспорт, и HTTP заявлениям «просто работает» обязан тем, что транспорт заранее настроен.

В учебной среде сервер работает на виртуальной машине в VirtualBox, поэтому путь запроса виден целиком: браузер на хосте идёт на `http://localhost:8080`, VirtualBox пробрасывает порт 8080 хоста на порт 80 внутри виртуальной машины, и запрос попадает к приложению. От хоста до гостя пакет не покидает компьютер, но проходит по полноценно настроенной сети: адрес, порт и маршрут там реальные. На продакшене вместо VirtualBox стоит роутер или прокси, а механика та же: HTTP не знает, где именно заканчивается сеть, он просто отправляет по адресу и порту.

Разница между учебной средой и промышленной не в протоколе, а в том, кто отвечает за доставку. В VirtualBox настройка доступна вам сами́м, поэтому проброс порта это первый способ понять, что «сервис недоступен» имеет конкретной причиной: не запущено приложение, занят порт или закрыт путь.

## Веб-архитектура

Типовой веб-контур ИС выглядит так:

1. **Клиент**: браузер или мобильное приложение.
2. **Обратный прокси**: принимает соединение, отвечает за TLS и распределяет запросы.
3. **Сервер приложений**: смотрит токен, права, бизнес-логику.
4. **База данных**: хранит состояние.
5. **Внешние службы**: почтовый сервер, платёжный шлюз, каталог пользователей.

Разделение нужно не для красоты. Оно позволяет обновлять приложение отдельно от базы, ставить несколько экземпляров за прокси, ограничивать доступ к данным снаружи и выдавать `502` прокси в момент, когда приложение падает, вместо бездетального «сервер не отвечает». Но каждый слой добавляет точку отказа: прокси может вернуть `502`, приложение `500`, база не ответить вовсе. Поэтому диагностика всегда идёт снаружи внутрь: сначала посмотреть статус, затем заголовки, затем тело, затем журнал сервера.

**Статический** ресурс отдаётся как файл: список аудиторий, инструкция по загрузке расписания, страница с приветствием. Он не меняется и стоит серверу одну операцию чтения с диска. **Динамический** ответ вычисляется приложением на основании запроса, прав и данных базы. Для учебной ИС достаточно одного JSON-эндпоинта рядом со статической страницей расписания, но принцип тот же: клиент получает результат по HTTP, и каждая часть контура вносит свой вклад в общее время ответа.

## Состояние, авторизация и кэш

HTTP сам по себе не помнит предысторию: два запроса подряд о друг друге ничего не знают. Чтобы сервер понимал, кто пришёл, клиента запоминают двумя способами:

- **Cookie и сессия.** Установка: сервер в первом ответе отправляет `Set-Cookie: sessionid=...`, браузер хранит cookie и рассылает с каждым запросом на этот домен. Само состояние остаётся на сервере, в базе или в хранилище сессий. Это удобно, когда «кто пришёл» меняется часто: выйти, сменить пароль, заблокировать пользователя.
- **JWT-токен.** Сервер выдаёт подписанное утверждение «этот пользователь имеет права X до момента Y», и дальше проверяет только подпись и срок, не обращаясь к сессии. Это удобно для API, где сессий нет вовсе.

Для учебного сервиса расписания достаточно одной из схем: cookie с сессией проще, JWT удобнее в задании «разработать модуль авторизации», где клиент не браузер, а Postman. Главное правило: не класть секрет в URL. URL сохраняется в истории, в реферерах, в логах сервера; токен в `Authorization` этого избегает.

Кэш настраивают заголовками, которые сервер ставит сам: `Cache-Control`, `ETag` и `Last-Modified` говорят клиенту и прокси, можно ли переиспользовать сохранённый ответ. Ошибка кэша проявляется как «старые данные»: пользователь видит расписание прошлой недели, хотя в базе уже новое. Правильно настроенный кэш обязает сервер сообщать, на сколько секунд клиенту можно доверять копии ответа, и отпустить копию быстрее, когда данные изменились: для расписания хватит 120–300 секунд, для отметок ведомости ноль.

## Задержка и хвосты

Когда расписание «поднимается» медленно, разбираться нужно не в «медленно вообще», а в том, где именно мы теряем время:

- **Сеть**: ход через VPN, узкое соединение мобильного интернета или проброс порта виртуальной машины.
- **Очередь**: сервер занят соседним запросом или потоком; очередь растёт при всплеске утром в понедельник, когда все сразу открывают расписание.
- **Приложение**: обработка токена, расчёт прав, подтверждение, сбор аналитики.
- **База**: самая частая причина; выборка по таблице на десять тысяч записей может быть заметно дольше самой логики обработки.

Среднее значение мало что говорит: важна **хвостовая задержка**. Если 99 процентов запросов быстрые, а один процент ждёт несколько секунд, пользователи всё равно заметят, потому что «медленно» в их глазах это «иногда бесконечно». Поэтому в API принято падать быстро (таймаут), а не «звонить вечность»: ответил `504 Gateway Timeout`, дать пользователю повторить, а не держать интерфейс зависшим.

## Postman и проверка API

**Postman** позволяет отправить запрос без написания клиента, сохранить коллекцию и добавить тесты. Тесты разного рода учебные и промышленные проверяют три вещи: успех, ошибку и валидность ответа. Минимальный набор для учебного API:

- статус `200` при корректном запросе: расписание вернулось;
- статус `400` или `401` при неверных данных и при отсутствии токена: сервер обязан отвергнуть, а не «интерпретировать на глаз»;
- заголовок `Content-Type: application/json` в ответе;
- обязательные поля в JSON: `group`, `lessons`, `time`, `subject`;
- отсутствие лишних персональных данных: телефон и адрес студента в расписании занятий не нужны.

Коллекция это артефакт: её можно передать другому разработчику, и он повторит проверку тем же сценарием. Внутри коллекции удобно распределять окружения: локальный порт 8080 на виртуальной машине и публичный адрес сервиса на хостинге это два разных `baseUrl`, а запросы и тесты не меняются вовсе.

## Типичные ошибки

- **Проверять только статус 200.** Успешный статус не гарантирует правильные поля: тело могло вернуться с нулевым массивом, и интерфейс молча покажет «занятий нет».
- **Путать 401 и 403.** 401 значит «не представился», 403 значит «представился, но нельзя». Лечение разное: вернуться на страницу входа против проверки прав.
- **Возвращать HTML вместо JSON.** Клиент не сможет разобрать ответ, и ошибка всплывёт далеко от места её возникновения.
- **Не указывать `Content-Type`.** Браузер и Postman могут интерпретировать тело по-разному; «у меня на странице работает, у Postman нет» почти всегда от этого.
- **Хранить секреты в URL.** Они попадут в журналы и историю браузера; токен идёт в заголовок.
- **Игнорировать повторные запросы.** Двойной `POST` создаёт дубликат; нужен ключ идемпотентности или проверка уникальности в базе.
- **Игнорировать время.** Дата без часового пояса и timestamp «сейчас» без смещения превращаются в неверное расписание на практике; в API передавайте дату со смещением `Z` или явным `+03:00`.
- **Лечить 500 от клиента.** Нет, это не «у меня руки кривые»: 500 это ошибка сервера или его зависимости, и ссылаться на клиента тут не стоит.

> [!CHECK] Клиент получил 500. Это ошибка клиента?
> Нет. 5xx означает ошибку сервера или его зависимости. Клиент может быть ни при чём, но ему всё равно нужно показать понятное сообщение и предложить повторить.

## Проверьте себя

> [!CHECK] Чем 401 отличается от 403?
> 401 говорит, что клиент не аутентифицирован. 403 говорит, что клиент известен, но прав на действие нет.

> [!CHECK] Почему GET не должен менять данные?
> GET могут повторять браузеры, кэши и поисковые роботы. Если он меняет состояние, повторный запрос создаёт неожиданный эффект.

> [!CHECK] Что значит код 400 и на каком этапе он возникает?
> Параметры не прошли валидацию. Маршрут и права к этому моменту проверены, а до базы дело не дошло.

> [!CHECK] Зачем API нужен контракт?
> Контракт фиксирует пути, параметры, форматы и ошибки. По нему клиент и сервер развиваются независимо и проверяются одинаковыми тестами.

> [!CHECK] Что проверить в Postman, кроме статуса?
> Заголовок `Content-Type`, структуру JSON, обязательные поля, типы значений и отсутствие секретов.

> [!CHECK] Почему 502 и 504 обычно приходят вместе с прокси?
> 502 значит «прокси не дозвонился до приложения», 504 значит «время соединения вышло». Обе ошибки принадлежат уровню между клиентом и приложением.

## Итоги

- Веб-взаимодействие строится на запросе и ответе, а не на «странице как артефакте».
- HTTP описывает метод, путь, заголовки, тело и код состояния; каждая часть на своём месте.
- Код состояния отвечает на вопрос «на какой проверке запрос остановился»: 401 без токена, 403 без прав, 404 без пути, 400 без валидных параметров, 500 без работающего сервера.
- REST и JSON задают контракт API, а OpenAPI и Postman-коллекция делают его проверяемым.
- Веб-контур разделяет клиент, прокси, приложение и базу данных, и каждая часть вносит свой вклад в нагрузку.
- Сессия и JWT это два способа «вспомнить клиента», а кэш это обещание «на сколько секунд можно доверять копии ответа».
- Postman проверяет API и сохраняет проверки как артефакт, который можно повторить или передать завтра.

Q: Какой код состояния говорит, что запрос остановился на проверке прав?
+ 403
- 401
- 404
- 400
! 403 значит «представился, но прав недостаточно».

Q: Что означает код 404?
+ Обработчика для этого пути нет
- Ошибка сервера или базы
- Параметры не прошли валидацию
- Нет или истёк токен
! 404 говорит, что ресурс или маршрут не найдены.

Q: Какой код ставит сервер, когда параметры не прошли валидацию?
+ 400
- 403
- 404
- 500
! 400 Bad Request это неверно собранные данные запроса.

Q: Какой метод обычно идемпотентен и безопасен для повторных запросов?
+ GET
- POST
- PATCH
- CONNECT
! GET можно повторять без нового эффекта.

Q: Какой код вернёт прокси, когда приложение не отвечает?
+ 502
- 401
- 400
- 404
! 502 Bad Gateway значит «прокси не дозвонился до приложения».

Q: Какой заголовок ответа говорит браузеру, как разбирать тело?
+ Content-Type
- Host
- Accept
- Cache-Control
! Content-Type объявляет формат тела ответа.

Q: Что говорит серверу заголовок Authorization?
+ Кто прислал запрос и с какими учётными данными
- Какой формат ответа ожидается
- На какое расписание смотреть
- Как долго кэшировать ответ
! Authorization несёт токен или учётные данные клиента.

Q: Какие проверки идут на сервере до обращения к базе?
+ Аутентификация
+ Права
+ Маршрут
+ Валидация параметров
- Установка операционной системы
- Пересборка ядра
! Базу затрагивают только после того, как запрос корректен и разрешён.

Q: Что входит в типовой веб-контур ИС?
+ Клиент
+ Обратный прокси
+ Сервер приложений
+ База данных
- DHCP-сервер
- NTP-сервер
! Веб-контур обслуживает запросы приложения.

Q: Какие артефакты проверки API создаёт Postman-коллекция?
+ Сценарий запроса с окружением
+ Тесты на статус 200
+ Тесты на ошибки 400 и 401
+ Тесты на структуру JSON
- Экспорт базы в PDF
- Снимок экрана браузера
! Коллекция это воспроизводимый сценарий проверки, а не снимок.

Q: Что значит идемпотентность метода?
+ Повторный запрос даёт тот же результат
- Запрос всегда быстрее
- Ответ всегда в JSON
- Клиент не требует авторизации
! Идемпотентный запрос можно повторять без нового эффекта.

Q: Что отличает кэширование от серверной логики?
+ Клиент или прокси переиспользуют копию ответа по заголовкам Cache-Control и ETag
- Сервер пересчитывает каждый раз с нуля
- Ответ приходит без заголовков вообще
- Данные всегда берутся из базы без спроса
! Кэш закрывает лишние запросы, когда ответ обещано считать «свежим».

- 400
