## Цель работы

Собрать два результата: план внедрения «Склад+» для ООО «Северный склад» и настройку учебной системы под этот план. План показывает, какие работы, в каком порядке и в какие сроки приводят к запуску. Настройка доказывает, что требования превратились в конкретные роли, справочники и маршрут, а не остались на бумаге.

На выходе нужны план с этапами, зависимостями, вехами и ответственными, протокол настройки и заполненный чек-лист проверки. План и настройка должны ссылаться друг на друга: каждая настройка закрывает требование, а требование стоит в плане отдельной работой.

## Оборудование и программное обеспечение

- Персональный компьютер с Excel и Word.
- Браузер с draw.io для диаграммы Ганта.
- XAMPP 8.5.12 с MySQL и phpMyAdmin для учебной базы.
- VS Code с Python для проверки выгрузки, если понадобится сверка.
- Учебная ИС «Склад+» и папка проекта с требованиями и справочниками.

**Комплект «Склад+».** [Скачать архив](reports/kit/sklad-plus-kit.zip) и распаковать в папку работы. Внутри: `app/index.html` (учебный прототип, открывается в браузере), `database/schema.sql` и `database/seed.sql` (импорт в phpMyAdmin), `data/` (CSV и JSON для импорта), `templates/` (шаблоны отчётов). Демо-доступы прототипа: `admin / admin`, `manager / manager`, `storekeeper / storekeeper`.

## Краткие теоретические сведения

**План внедрения** это работы, зависимости, сроки, ресурсы и вехи. Работа имеет один результат и одного ответственного. Зависимость показывает, что нельзя начать раньше другого результата. **Критический путь** это самая длинная цепочка работ: её задержка переносит финиш. **Резерв** показывает, на сколько работу можно сдвинуть без переноса финиша. **Веха** отмечает факт или решение и имеет нулевую длительность.

**Роль** это набор прав, а **пользователь** это учётная запись с ролью. Права назначают роли, а не человеку, и проверяют негативными тестами: запрещённое действие должно быть действительно запрещено. **Справочник** хранит нормативно-справочную информацию с уникальным кодом. **Маршрут** задаёт шаги согласования, условия, сроки, заместителя и эскалацию.

**Протокол настройки** фиксирует параметр, значение, связанное требование, способ проверки и результат. Протокол нужен не для отчёта, а для передачи системы: по нему администратор повторит настройку, а приёмка проверит её без догадок.

## Ход работы

### Шаг 1. Составьте перечень работ

**Приложение 1 к договору.** Срок внедрения 56 рабочих дней с даты подписания. Обязательные результаты: реестр требований, настроенная ИС, перенесённые и сверенные данные, работающий обмен с сайтом и бухгалтерией, обученные группы пользователей, акт пилота на складе в Твери, рабочие места в Москве, Туле и Калуге, подписанный акт приёмки.

**Вехи по договору.** «Требования согласованы» на день 10, «Пилот запущен» не позднее дня 35, «Приёмка» не позднее дня 56.

### Шаг 5. Создайте роли и пользователей

Разберите короткий пример. Он создаёт две роли и одного пользователя в демонстрационных таблицах.

```sql
CREATE TABLE demo_roles (
  id INT PRIMARY KEY AUTO_INCREMENT,
  code VARCHAR(32) NOT NULL UNIQUE,
  title VARCHAR(100) NOT NULL
);

CREATE TABLE demo_users (
  id INT PRIMARY KEY AUTO_INCREMENT,
  login VARCHAR(40) NOT NULL UNIQUE,
  role_id INT NOT NULL,
  warehouse_code CHAR(3),
  FOREIGN KEY (role_id) REFERENCES demo_roles(id)
);

INSERT INTO demo_roles (code, title) VALUES ('manager', 'Менеджер по продажам');
INSERT INTO demo_users (login, role_id, warehouse_code)
VALUES ('ivanov', (SELECT id FROM demo_roles WHERE code = 'manager'), NULL);
```

Подзапрос находит номер роли по её коду, поэтому скрипт не зависит от порядка вставки строк. Внешний ключ не даст создать пользователя со ссылкой на несуществующую роль.

Теперь постройте такие же таблицы `app_roles` и `app_users` в базе `sklad` и заполните их для «Северного склада»: шесть ролей (директор, коммерческий директор, менеджер по продажам, кладовщик, бухгалтер, администратор ИС) и шесть пользователей. У кладовщика укажите склад `ТВР`, остальным склад не нужен.

### Шаг 6. Настройте права

Создайте таблицу прав.

```sql
CREATE TABLE app_rights (
  role_id INT NOT NULL,
  object_code VARCHAR(40) NOT NULL,
  can_view TINYINT(1) NOT NULL DEFAULT 0,
  can_edit TINYINT(1) NOT NULL DEFAULT 0,
  can_approve TINYINT(1) NOT NULL DEFAULT 0,
  PRIMARY KEY (role_id, object_code),
  FOREIGN KEY (role_id) REFERENCES app_roles(id)
);
```

Заполните матрицу прав для объектов `orders`, `order_amount`, `products`, `stock`, `invoices`, `users`. Решите для каждой пары «роль и объект», нужен ли просмотр, изменение и согласование. Одна ячейка заполнена как образец.

| Объект | Директор | Коммерческий | Менеджер | Кладовщик | Бухгалтер | Админ |
|---|---|---|---|---|---|---|
| orders | просмотр | | | | | |
| order_amount | | | | | | |
| products | | | | | | |
| stock | | | | | | |
| invoices | | | | | | |
| users | | | | | | |

Право записывают отдельной строкой. Пример для просмотра заказов директором:

```sql
INSERT INTO app_rights (role_id, object_code, can_view)
VALUES ((SELECT id FROM app_roles WHERE code = 'director'), 'orders', 1);
```

Запросом проверьте, что у роли `storekeeper` нет права просмотра `order_amount`. Результат запроса сохраните для протокола.

### Шаг 7. Заполните справочники

Занесите в справочники склады, единицы измерения и не меньше десяти товаров. Для каждого товара укажите код, наименование, категорию, единицу и ставку НДС. Отдельно занесите трёх контрагентов с ИНН.

Проверьте дубли запросом: он группирует строки по названию и оставляет только те группы, где копий больше одной.

```sql
SELECT name, COUNT(*) AS copies
FROM products
GROUP BY name
HAVING COUNT(*) > 1;
```

Если запрос вернул строки, объедините карточки по правилу: главная карточка остаётся, остальные помечаются неактивными, документы переводятся на главную. Запишите правило в протокол.

### Шаг 8. Настройте маршрут согласования

**Приказ № 14 «О порядке согласования заказов».** Скидка до 5 процентов включительно согласуется менеджером, свыше 5 процентов коммерческим директором. Отсрочка платежа до 14 дней включительно согласуется менеджером, свыше 14 дней бухгалтером. Заказ резервируется только после согласования. Срок ответа согласующего: 2 часа по скидке, 4 часа по отсрочке. При отказе заказ возвращается менеджеру с причиной.

Опишите маршрут заказа в таблице. У каждого шага должны быть роль, условие, срок и действие при отказе. Первая строка дана как образец.

| Шаг | Роль | Условие | Срок | При отказе |
|---|---|---|---|---|
| Проверка заказа | менеджер | всегда | 15 минут | вернуть на доработку |
| | | | | |
| | | | | |

Настройте маршрут в учебной ИС или опишите его в таблице статусов, если конструктор маршрутов недоступен. Главное, чтобы условие было однозначным: укажите, входит ли НДС в сумму и как округляется скидка.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

| Оценка | Условие |
|---|---|
| 5 | Работа выполнена полностью и самостоятельно, все пункты ниже выполнены |
| 4 | Работа выполнена, есть 1 или 2 незначительных замечания |
| 3 | Работа выполнена частично, есть существенные замечания |
| 2 | Работа не выполнена |
| 1 | Работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления |

Что проверяется:
- **План и зависимости.** работы, предшественники и сроки согласованы
- **Критический путь и вехи.** путь найден, вехи имеют признаки достижения
- **Роли и права.** матрица заполнена, негативные тесты пройдены
- **Справочники и маршрут.** дубли обработаны, условия однозначны
- **Протокол и комплект.** документы связаны и подписаны
