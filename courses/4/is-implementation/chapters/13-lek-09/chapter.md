## Одна идея

«Северный склад» запускает «Склад+», но заказы по-прежнему приходят с сайта, счета уходят в бухгалтерию, а остатки должны появляться на витрине интернет-магазина. Три обмена, три разных требования. Заказ нужно принять за секунды, иначе покупатель уйдёт. Счёт достаточно передать раз в час. Остатки на сайте можно обновлять каждые пять минут, но если они устарели на десять, магазин продаст товар, которого нет на складе.

Интеграция начинается не с выбора технологии, а с вопроса: кто владеет данными и что произойдёт, если они не дойдут. Ответ на этот вопрос определяет и способ передачи, и поведение при отказе.

**Интеграция это договор между системами о том, кто владеет объектом, в каком формате его передаёт, с какой гарантией и что делает при сбое.** Технология лишь выполняет договор.

## Четыре способа обмена

**Файловый обмен** это выгрузка данных в файл и передача его в согласованную папку или на сервер. «Склад+» раз в час кладёт `orders_20261027_1000.csv` в каталог обмена, бухгалтерия забирает файл и оставляет рядом квитанцию `orders_20261027_1000.ok`. Способ дешёвый, не требует прямой связи между системами и хорошо переживает недоступность получателя: файл лежит и ждёт. Зато подтверждение отложенное, задержка измеряется минутами, а повторная выкладка того же файла создаёт дубли, если получатель не проверяет имя и хеш.

Файловый обмен уместен для редких пакетов: справочник клиентов раз в сутки, счета раз в час, обмен с контрагентом, который не даёт API. Для оформления заказа он не годится: покупатель не будет ждать час.

**API** это программный интерфейс, через который одна система вызывает другую по сети и получает ответ сразу. Чаще всего это HTTP и JSON: `POST /api/orders` отправляет заказ, `201 Created` подтверждает приём, `422 Unprocessable Entity` сообщает о неверных данных. API даёт немедленный ответ и точную причину отказа, поэтому подходит для заказов, проверки остатка и статуса.

```json
{
  "order_number": "SO-2026-10417",
  "customer_external_id": "C-1001",
  "warehouse_code": "TVER",
  "created_at": "2026-10-27T10:15:00+03:00",
  "lines": [
    { "sku": "CEM-500", "qty": 20, "price": 410.00 }
  ]
}
```

У API есть цена: он связывает системы во времени. Пока «Склад+» отвечает, сайт держит соединение и ждёт. Если смежная система недоступна, вызов завершается ошибкой, и вызывающая сторона должна решить, что делать с заказом.

**Очередь сообщений** ставит между системами посредника. Отправитель кладёт сообщение в очередь и сразу получает подтверждение, а получатель забирает его, когда готов. Пик заказов в понедельник утром не роняет «Склад+»: сообщения копятся и разбираются с доступной скоростью. Очередь даёт асинхронность, повторную доставку и несколько независимых потребителей: одно событие `order.created` читают склад, бухгалтерия и модуль уведомлений.

Плата за это: доставка не мгновенная, порядок сообщений нужно обеспечивать отдельно, а сбойный обработчик может бесконечно возвращать сообщение в очередь. Для таких случаев заводят очередь необработанных сообщений, куда попадает всё, что не удалось разобрать после нескольких попыток.

**Шина данных** это слой, который связывает много систем через единые правила маршрутизации и преобразования форматов. Она полезна, когда систем больше пяти и у каждой свой формат. Для четырёх складов и трёх систем «Северного склада» шина избыточна: её внедрение и поддержка стоят дороже, чем три прямых обмена.

| Способ | Задержка | Подтверждение | Сложность | Когда выбирать |
|---|---|---|---|---|
| Файл | минуты и часы | квитанция или следующий запуск | низкая | редкие пакеты, нет API у партнёра |
| API | секунды | код ответа сразу | средняя | нужен ответ сейчас |
| Очередь | секунды | подтверждение брокера | высокая | пики, несколько потребителей |
| Шина | секунды | через слой маршрутизации | очень высокая | много систем и форматов |

## Паспорт обмена

У каждого обмена есть паспорт, и его заполняют до настройки. Паспорт отвечает на вопросы, которые позже превращаются в дефекты, если остались без ответа.

| Параметр | Значение для заказов сайта |
|---|---|
| Системы | сайт магазина и «Склад+» |
| Направление | сайт передаёт, «Склад+» принимает |
| Владелец данных | «Склад+» после приёма заказа |
| Объект | заказ и строки заказа |
| Формат | JSON, кодировка UTF-8 |
| Частота | по событию оформления |
| Протокол | HTTPS, REST |
| Ключ сопоставления | `order_number` |
| Подтверждение | `201` и внутренний номер заказа |
| Допустимая задержка | ответ до 2 секунд, 99,5 процента сообщений доставляются за 5 минут |
| Ответственный | администратор ИС |

**Владелец данных** это система, которая признаётся источником истины. Остатки ведёт «Склад+», и сайт не имеет права править их напрямую: он только показывает полученное. Клиентов ведёт «Склад+», бухгалтерия получает их копию. Если владельца не назначить, две системы начнут перезаписывать друг друга, и после каждого обмена остатки будут прыгать.

**Ключ сопоставления** связывает объект в двух системах. Для заказа это номер, для клиента `external_id`, для склада код `TVER`. Ключ не меняется при обновлении записи и уникален в пределах системы. По нему приёмник понимает, что пришло повторное сообщение, а не новый заказ.

## Контракт и надёжность

Контракт API описывает поля, типы, обязательность, коды ошибок и версию. Без контракта поставщик меняет имя поля, и приёмник молча получает `null` вместо суммы.

```json
{
  "order_number": "SO-2026-10417",
  "status": "accepted",
  "internal_id": 88213,
  "accepted_at": "2026-10-27T10:15:02+03:00"
}
```

Коды ответа делят ошибки на две группы. `400`, `401`, `403`, `404`, `409` и `422` означают, что повторять тот же запрос бессмысленно: данные неверны, доступа нет, объект уже существует. `429`, `500`, `502`, `503`, `504` и истечение таймаута означают временную проблему, и запрос имеет смысл повторить с паузой.

**Идемпотентный ключ** защищает от двойного создания заказа. Сайт передаёт заголовок `Idempotency-Key` с номером заказа. Если ответ потерялся в сети и сайт повторил отправку, «Склад+» находит ключ и возвращает прежний результат вместо второго заказа. Без ключа повтор после таймаута создаёт дубль, и кладовщик собирает два одинаковых заказа.

**Повтор с паузой** не должен быть плотным циклом. Пауза растёт: 5 секунд, 15, 45, 135. После пяти попыток сообщение уходит в очередь необработанных, а администратор получает уведомление. Пять попыток подряд с интервалом в секунду лишь добивают уже перегруженную систему.

**Предохранитель** отключает вызовы к смежной системе после серии ошибок. Если пять запросов подряд завершились отказом, следующие две минуты сайт не звонит в «Склад+», а сразу отвечает запасным сценарием. Это даёт упавшей системе время подняться.

**Журнал обмена** хранит время, направление, ключ, код ответа, длительность и текст ошибки. По нему считают долю успешных обменов и находят зависшие заказы. Без журнала разбор начинается с фразы «менеджер говорит, что заказ не пришёл».

**Версия контракта** позволяет менять обмен без остановки. Новое поле сначала добавляют как необязательное, приёмник учится его читать, и только потом отправитель начинает его заполнять. Удаление поля это отдельный шаг после того, как все потребители обновились. Если менять контракт одним рывком, старая версия приёмника отвергнет новые сообщения, и обмен встанет.

Наблюдать за обменом нужно по трём числам: доля успешных сообщений, возраст самого старого неотправленного сообщения и число сообщений в очереди необработанных. Первое показывает качество, второе показывает задержку, третье показывает, что уже требует человека. Рост любого из них это повод разобраться до того, как о проблеме сообщит покупатель.

## Недоступность смежной системы

Отказ смежной системы это нормальное событие, а не авария. Вопрос не в том, случится ли он, а в том, что увидит пользователь и куда денется заказ.

Первый вариант, самый плохой: сайт вызывает «Склад+» напрямую и при ошибке показывает покупателю сообщение об ошибке. Заказ теряется, покупатель уходит, а менеджер узнаёт о проблеме от него же. Такой сценарий допустим только для некритичных операций вроде просмотра остатка.

Второй вариант это **исходящая очередь в своей базе**, её называют outbox. Заказ сохраняется локально вместе с записью в таблице исходящих сообщений в одной транзакции. Фоновая задача отправляет сообщения и отмечает результат. Если «Склад+» недоступен, запись остаётся со статусом `pending` и повторится позже.

```sql
CREATE TABLE outbox (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  message_key VARCHAR(64) NOT NULL,
  payload JSON NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'pending',
  attempts INT NOT NULL DEFAULT 0,
  next_attempt_at DATETIME NOT NULL,
  created_at DATETIME NOT NULL,
  sent_at DATETIME NULL,
  last_error TEXT NULL,
  UNIQUE KEY uq_outbox_key (message_key)
);
```

Транзакция важна: заказ и сообщение появляются вместе. Если сохранить заказ, а сообщение не записать, заказ останется в системе навсегда. Если записать сообщение, а заказ не сохранить, склад получит заказ, которого нет на сайте.

Третий вариант это очередь сообщений с гарантией доставки. Сообщение лежит у брокера, пока потребитель не подтвердит обработку. Брокер повторяет доставку, поэтому обработчик обязан быть идемпотентным: одно и то же сообщение может прийти дважды.

**Деградация** это осознанное упрощение работы при отказе. Если недоступен обмен остатками, сайт показывает последние известные значения с пометкой «данные на 09:15» и не обещает наличие. Если недоступна бухгалтерия, счета копятся в outbox и уходят после восстановления. Главное, чтобы деградация была описана заранее и не превращалась в тихую потерю данных.

| Канал | Отказ | Поведение системы |
|---|---|---|
| Заказы с сайта | «Склад+» не отвечает | заказ в outbox, статус `pending`, повтор, покупатель видит «заказ принят» |
| Остатки на сайт | обмен не прошёл | показать последние данные с временем обновления |
| Счета в бухгалтерию | очередь недоступна | накопление в outbox, повтор, ручная выгрузка при долгом отказе |
| Клиенты из бухгалтерии | ночной файл не пришёл | работать на прежнем справочнике, уведомить администратора |

**Приоритеты** помогают не тратить силы на всё сразу. Потеря заказа недопустима, задержка остатков на десять минут терпима, задержка справочника на сутки почти незаметна. При аварии сначала восстанавливают канал заказов, потом остатки, потом справочники.

## Выбор способа

Выбор делают по четырём вопросам. Как часто идут данные: раз в сутки или сто раз в минуту. Нужен ли ответ прямо сейчас: покупатель ждёт или бухгалтер подождёт. Сколько потребителей: один или пять. Что будет при потере: заказ, деньги, неудобство.

| Задача | Частота | Ответ сейчас | Выбор |
|---|---|---|---|
| Заказ с сайта | по событию, до 60 в час | да | API с идемпотентным ключом |
| Остатки на сайт | каждые 5 минут | нет | API или короткий файл |
| Счета в бухгалтерию | раз в час | нет | очередь или файл |
| Справочник клиентов | раз в сутки | нет | файл |
| Уведомления о статусе | по событию | нет | очередь |

Если сомневаетесь между файлом и API, посмотрите на допустимую задержку. Пятнадцать минут ожидания для справочника нормальны, для заказа нет. Если сомневаетесь между API и очередью, посмотрите на пики и число потребителей. Один потребитель и ровный поток переживут API, три потребителя и утренний пик требуют очереди.

## Типичные ошибки

- **Обмен без владельца данных.** Сайт и «Склад+» правят остатки по очереди, и после каждого обмена числа расходятся.
- **Повтор без идемпотентности.** Таймаут воспринимается как отказ, заказ отправляется снова, на складе появляется дубль.
- **Плотный цикл повторов.** Сбойная система получает сотни запросов в секунду и не может восстановиться.
- **Журнал без ключа.** В логе есть код ошибки, но непонятно, к какому заказу он относится.
- **Синхронный вызов в критичном пути без запасного сценария.** Недоступность одной системы останавливает продажи.
- **Файл без квитанции.** Отправитель считает обмен успешным, хотя получатель файл не забрал.

> [!PITFALL] Повторная отправка после таймаута
> Таймаут не означает, что заказ не принят. Он означает, что ответ не пришёл. Если отправить заказ снова без ключа, склад получит два заказа, и оба придётся отменять вручную. Идемпотентный ключ превращает повтор в безопасную операцию.

## Проверьте себя

> [!CHECK] Сайт отправляет заказ, «Склад+» отвечает через 40 секунд. Что не так в схеме?
> Синхронный вызов держит покупателя и соединение. Нужен либо короткий ответ с подтверждением приёма и последующей обработкой, либо очередь. Сорок секунд ожидания в оформлении заказа недопустимы.

> [!CHECK] Бухгалтерия просит передавать счета мгновенно, хотя обрабатывает их раз в день. Что предложить?
> Оставить файловый обмен или очередь с часовым расписанием: мгновенная доставка не даёт бухгалтерии пользы, но добавляет связность и риск. Требование нужно проверять по реальному процессу, а не по желанию.

> [!CHECK] Сообщение из очереди пришло дважды. Это ошибка?
> Нет, доставка «хотя бы один раз» допускает повтор. Обработчик должен быть идемпотентным: проверить ключ и не создавать второй счёт. Ошибкой будет обработчик, который этого не умеет.

## Итог

- Интеграция это договор о владельце данных, формате, частоте и поведении при отказе.
- Файл прост и терпим к недоступности, API даёт ответ сразу, очередь сглаживает пики, шина нужна при большом числе систем.
- Паспорт обмена фиксирует направление, ключ, формат и допустимую задержку до настройки.
- Идемпотентный ключ, повтор с растущей паузой, предохранитель и журнал делают обмен предсказуемым.
- При отказе заказ сохраняют в outbox, остатки показывают с отметкой времени, а каналы восстанавливают по приоритету.

## Тест по лекции

::quiz
Q: Что такое API в контексте интеграции?
+ Программный интерфейс, через который одна система вызывает другую
- Папка для обмена файлами
- Таблица базы данных
- Протокол резервного копирования
! API принимает запрос и возвращает ответ по сети, чаще всего через HTTP.

Q: Чем очередь сообщений отличается от прямого вызова API?
+ Отправитель не ждёт обработки и получает подтверждение от посредника
- Очередь работает только внутри одной базы
- Очередь не поддерживает повторную доставку
- Очередь требует файлового обмена
! Асинхронность отделяет отправку от обработки и сглаживает пики.

Q: Зачем нужен идемпотентный ключ при отправке заказа?
+ Чтобы повтор после таймаута не создал второй заказ
- Чтобы ускорить ответ сервера
- Чтобы зашифровать тело запроса
- Чтобы выбрать склад отгрузки
! Приёмник узнаёт повторный запрос и возвращает прежний результат.

Q: Что делать при ответе 503?
+ Повторить запрос с растущей паузой
- Повторить запрос сразу же без паузы
- Считать данные неверными и не повторять
- Удалить заказ из системы
! 503 означает временную недоступность, повтор имеет смысл.

Q: Какая система владеет остатками в кейсе «Северного склада»?
+ «Склад+»
- Сайт магазина
- Бухгалтерия
- Почтовая программа
! Владелец данных один, остальные получают копию.

Q: Зачем нужна таблица outbox?
+ Чтобы сохранить исходящее сообщение вместе с заказом и отправить позже
- Чтобы хранить пароли пользователей
- Чтобы заменить журнал обмена
- Чтобы ускорить чтение остатков
! Outbox защищает от потери заказа при недоступности смежной системы.

Q: Что такое очередь необработанных сообщений?
+ Место, куда попадают сообщения после исчерпания попыток
- Список всех успешных обменов
- Таблица справочника клиентов
- Резервная копия базы
! Туда смотрит администратор, чтобы разобрать сбой вручную.

Q: Что означает доставка «хотя бы один раз»?
+ Сообщение дойдёт, но может прийти повторно
- Сообщение дойдёт ровно один раз
- Сообщение может потеряться без следа
- Сообщение доставляется только по расписанию
! Поэтому обработчик обязан быть идемпотентным.

Q: Когда файловый обмен уместен?
+ Для редких пакетов, где задержка в минуты допустима
- Для оформления заказа в реальном времени
- Для проверки остатка перед оплатой
- Для синхронного ответа покупателю
! Файл хорош там, где получатель может подождать.

Q: Какие признаки указывают, что нужен API, а не файл?
+ Нужен ответ сразу
+ Запросы идут часто и малы по размеру
+ Ошибку нужно показать пользователю немедленно
- Партнёр не имеет программного интерфейса
- Данные передаются раз в сутки
! API даёт немедленный ответ и точную причину отказа.

Q: Что входит в паспорт обмена?
+ Направление передачи
+ Владелец данных
+ Формат и частота
+ Ключ сопоставления и допустимая задержка
- Пароль администратора
- Цвет интерфейса
! Паспорт фиксирует договор до настройки.

Q: Какие меры применяют при недоступности смежной системы?
+ Сохранение сообщения в outbox
+ Повтор с растущей паузой
+ Очередь необработанных сообщений
+ Деградация с отметкой времени данных
- Удаление заказа для очистки очереди
- Отключение журнала обмена
! Заказ сохраняют, повторяют доставку и честно показывают устаревшие данные.

Q: Какие коды ответа означают временную ошибку?
+ 503
+ 504
+ 429
+ 500
- 400
- 422
! Временные ошибки имеет смысл повторять, ошибки данных нет.

Q: Как называется таблица исходящих сообщений, сохраняемая вместе с заказом?
= outbox
= outbox table
! Outbox хранит сообщение в той же транзакции, что и бизнес-данные.

Q: Какой HTTP-код сообщает о конфликте, например о повторном создании объекта?
= 409
= 409 Conflict
! Конфликт означает, что объект уже существует или состояние не совпадает.
