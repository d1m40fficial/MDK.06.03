## Цель работы

«Северный склад» передаёт собранные заказы в службу доставки «ТрансЛогистик». Сервис принимает отгрузку по API и возвращает номер трека. Если сервис недоступен, отгрузка не должна потеряться, а если данные неверны, склад должен получить понятную причину отказа.

Цель работы: настроить обмен между учебной ИС и внешним сервисом, проверить его успешным и аварийными сценариями и оформить протокол тестирования. Результат работы это схема обмена, скрипт отправки, журнал обмена и протокол с карточкой дефекта.

## Краткие теоретические сведения

**Точка интеграции** это место, где данные переходят из одной системы в другую. У неё есть направление, формат, протокол и ответственный. Для отгрузки точка одна: «Склад+» отправляет JSON, сервис доставки отвечает кодом и номером трека.

**Контракт обмена** фиксирует поля, типы и коды ответа. `201` означает, что отгрузка принята, `422` что данные неверны, `503` что сервис временно недоступен. Коды делят ошибки на две группы: `422` не повторяют, `503` повторяют с паузой.

**Идемпотентный ключ** защищает от дубля. Повторная отправка с тем же `shipment_number` не должна создавать вторую отгрузку. В учебном сервисе номер трека строится из `shipment_number`, поэтому повтор даёт тот же результат. В реальном сервисе для этого нужен отдельный заголовок.

**Журнал обмена** хранит попытку, код, длительность и результат. По нему видно, что отгрузка ждёт повтора, а не исчезла.

**Тест-кейс** содержит данные, шаги, ожидаемый и фактический результат. **Дефект** оформляют, когда фактический результат расходится с ожидаемым, с указанием окружения и шагов воспроизведения.

**Аварийный сценарий** проверяют наравне с успешным. Для обмена это недоступность сервиса, таймаут, неверные данные и повторная отправка. Если проверить только успешный путь, отказ обнаружится в день отгрузки, когда исправлять его дороже всего.

### Шаг 4. Поднимите учебный внешний сервис

Создайте `mock_delivery.py`. Сервис принимает `POST /api/shipments`, проверяет обязательные поля и отвечает `201`, `422` или `503`. Файл `fail.flag` в рабочей папке включает режим недоступности.

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import json, os

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        if os.path.exists("fail.flag"):
            self.send_response(503)
            self.end_headers()
            self.wfile.write(b'{"error":"service unavailable"}')
            return
        length = int(self.headers.get("Content-Length", 0))
        body = json.loads(self.rfile.read(length) or b"{}")
        if not body.get("shipment_number") or not body.get("city"):
            self.send_response(422)
            self.end_headers()
            self.wfile.write(b'{"error":"shipment_number and city required"}')
            return
        self.send_response(201)
        self.send_header("Content-Type", "application/json")
        self.end_headers()
        track = "TRK-" + body["shipment_number"]
        self.wfile.write(json.dumps({"track_id": track}).encode())

HTTPServer(("127.0.0.1", 8081), Handler).serve_forever()
```

Запустите сервис в отдельном окне терминала и проверьте его в Postman запросом `POST http://127.0.0.1:8081/api/shipments` с телом JSON. Ответ `201` означает, что стенд готов.

### Шаг 5. Напишите отправку с повтором

Создайте `send_shipment.py`. Скрипт отправляет отгрузку, повторяет только временные ошибки и пишет каждую попытку в `exchange_log.csv`.

```python
import csv, json, os, time, urllib.request, urllib.error

URL = "http://127.0.0.1:8081/api/shipments"

def send(payload, timeout=5):
    req = urllib.request.Request(
        URL, data=json.dumps(payload, ensure_ascii=False).encode("utf-8"),
        method="POST", headers={"Content-Type": "application/json",
                                "Idempotency-Key": payload["shipment_number"]})
    started = time.time()
    try:
        with urllib.request.urlopen(req, timeout=timeout) as r:
            return r.status, r.read().decode("utf-8"), int((time.time() - started) * 1000)
    except urllib.error.HTTPError as e:
        return e.code, e.read().decode("utf-8"), int((time.time() - started) * 1000)
    except Exception as e:
        return 0, str(e), int((time.time() - started) * 1000)

payload = {"shipment_number": "SH-2026-0451", "order_number": "SO-2026-10417",
           "city": "Тверь", "weight_kg": 120.5}
for attempt in range(1, 4):
    code, body, ms = send(payload)
    result = "sent" if code == 201 else ("pending" if code == 0 or code >= 500 else "rejected")
    with open("exchange_log.csv", "a", encoding="utf-8", newline="") as f:
        writer = csv.writer(f, delimiter=";")
        if f.tell() == 0:
            writer.writerow(["created_at", "shipment_number", "attempt", "http_code",
                             "duration_ms", "result", "message"])
        writer.writerow(
            [time.strftime("%Y-%m-%d %H:%M:%S"), payload["shipment_number"], attempt, code, ms, result, body])
    print(attempt, code, ms, body)
    if result != "pending":
        break
    time.sleep(2 ** (attempt - 1))
```

Повтор срабатывает только при коде `0` и ошибках `5xx`. Ответ `422` означает ошибку данных, его не повторяют. Пауза удваивается: одна секунда, две, четыре.

### Шаг 6. Проведите успешный тест

При выключенном `fail.flag` запустите скрипт. Ожидается код `201`, номер трека `TRK-SH-2026-0451` и одна строка в журнале со статусом `sent`. Занесите результат в протокол.

```sql
UPDATE shipments SET status = 'sent', track_id = 'TRK-SH-2026-0451'
WHERE shipment_number = 'SH-2026-0451';
```

Проверьте, что в `shipments` отгрузка имеет статус `sent` и заполнен `track_id`.

Статус `sent` ставится только после ответа `201`. Если записать его до отправки, при отказе сервиса отгрузка будет выглядеть переданной, хотя трека нет. Порядок такой: сначала успешный ответ, потом смена статуса и запись трека.

### Шаг 7. Проверьте отказ сервиса

Создайте файл `fail.flag` в папке, откуда запущен сервис, и запустите скрипт снова. Сервис отвечает `503`, скрипт делает три попытки и пишет в журнал статус `pending`. В журнале три строки с кодами `503` и растущими паузами. В таблице отгрузок поставьте ожидающий статус.

```sql
UPDATE shipments SET status = 'pending' WHERE shipment_number = 'SH-2026-0451';
```

Удалите `fail.flag`, повторите запуск и снова выполните `UPDATE` из шага 6. Отгрузка переходит в `sent`. Это и есть восстановление после временного отказа: данные не потеряны, повтор безопасен благодаря ключу.

Пока отгрузка в статусе `pending`, кладовщик видит её в списке ожидающих и не считает переданной. Это важнее, чем кажется: молчаливая потеря отгрузки означает, что машина уехала без сопроводительных документов, а сервис доставки о ней не знает.

### Шаг 8. Проверьте неверные данные

Отправьте отгрузку без города. Удобно временно убрать `city` из `payload` или отправить запрос в Postman. Ожидается `422`, статус `rejected` и одна попытка без повторов. Запишите сообщение об ошибке в протокол.

Верните корректные данные и убедитесь, что та же отгрузка снова проходит. Скрипт не должен считать `422` временной ошибкой.

### Шаг 9. Проверьте повтор и замерьте время

Отправьте `SH-2026-0451` ещё раз с тем же ключом. Сервис вернёт тот же номер трека, а в журнале появится вторая успешная попытка. Проверьте, что в таблице отгрузок осталась одна строка.

```sql
SELECT shipment_number, COUNT(*) AS copies
FROM shipments WHERE shipment_number = 'SH-2026-0451'
GROUP BY shipment_number;
```

Ожидается одна строка со значением `copies = 1`. Если появилось две, значит скрипт или сервис создаёт новую отгрузку на каждый запрос, и идемпотентность не работает.

Импортируйте накопленный `exchange_log.csv` в таблицу `exchange_log`: phpMyAdmin, вкладка «Импорт», формат CSV, разделитель `;`, первая строка содержит имена столбцов. Дальше считайте по таблице.

Затем отправьте двадцать запросов подряд. Оберните вызов `send(payload)` в цикл `for n in range(20)` и посчитайте среднее и максимальное время из журнала. Запишите оба числа и объясните, почему для критерия приёмки важнее максимальное и девяносто пятый перцентиль, а не среднее.

Двадцать запросов это не нагрузочный тест, а замер отклика одного обмена. Полноценная нагрузка требует десятков одновременных отправителей и хотя бы получаса работы. Но и короткий замер показывает, не растёт ли время от запроса к запросу: рост означает, что сервис или скрипт накапливает состояние.
