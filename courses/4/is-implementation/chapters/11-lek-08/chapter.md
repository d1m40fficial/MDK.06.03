## Одна идея

В пятницу «Северный склад» переносил клиентов из старой программы в «Склад+». Бухгалтер выгрузила справочник в CSV, менеджер попросил тот же список в JSON для сайта, а администратор запустил загрузку дважды: вечером и утром, потому что вечером «что-то не сошлось». К обеду в базе оказалось 9 624 клиента вместо 4 812, у тридцати четырёх записей телефон начинался с восьмёрки, а семнадцать контрагентов исчезли совсем.

Программа здесь ни при чём. Файл описывает данные так, как удобно источнику, а таблица требует типов, обязательных полей и связей. Между ними стоит преобразование, и если его не описать правилами, каждая загрузка будет сюрпризом.

**Импорт это преобразование по правилам, а не копирование файла.** Хороший импорт отвечает на четыре вопроса: какая у файла структура, куда попадает каждое поле, что делать с плохой записью и что произойдёт при повторном запуске. Ответы записывают до первого запуска, а не после разбора расхождений.

## Два формата, две логики

CSV хранит таблицу в текстовом виде: одна строка файла это одна запись, поля разделены символом, первая строка часто содержит заголовки. Выгрузка клиентов из старой программы «Северного склада» выглядит так:

```csv
external_id;name;inn;phone;created_at
C-1001;ООО "Стройбаза Тверь";5047001234;+7 4822 33-15-40;27.10.2026
C-1002;ИП Ковалёв А.С.;504700987654;;27.10.2026
C-1003;ООО "Ромашка";5047001111;8 (910) 000-11-22;27/10/2026
```

Простота обманчива. Excel на русской машине сохраняет разделителем точку с запятой, а не запятую, и добавляет в начало файла невидимую метку BOM. Кодировка может быть windows-1251, тогда фамилия с буквой «ё» превратится в мусор. Телефон и ИНН Excel охотно превращает в число и теряет ведущий ноль. Десятичная запятая в сумме ломает разбор числа. Перевод строки внутри названия организации разрывает запись на две, если поле не взято в кавычки. Пустое поле не отличает «не знаю» от «не заполнено».

JSON хранит данные деревом: объект это набор пар «ключ и значение», массив это список, вложенный объект описывает связанную часть записи. Тот же клиент в JSON выглядит иначе:

```json
{
  "batch_id": "2026-10-27-customers",
  "customers": [
    {
      "external_id": "C-1001",
      "name": "ООО \"Стройбаза Тверь\"",
      "inn": "5047001234",
      "phone": "+7 4822 33-15-40",
      "address": { "city": "Тверь", "street": "Индустриальная, 12" },
      "credit_limit": 250000.00,
      "active": true
    },
    {
      "external_id": "C-1002",
      "name": "ИП Ковалёв А.С.",
      "inn": null,
      "phone": null,
      "address": { "city": "Тула", "street": null },
      "credit_limit": 0,
      "active": true
    }
  ]
}
```

JSON передаёт вложенность и различает `null`, ноль и пустую строку. За это приходится платить: у JSON нет обязательной схемы, ключ может отсутствовать в одной записи и присутствовать в другой, число может прийти строкой `"250000.00"`, а файл на сотни мегабайт нельзя целиком держать в памяти. Дубли ключей в объекте не запрещены синтаксисом, и разные парсеры оставят разные значения.

| Свойство | CSV | JSON |
|---|---|---|
| Форма | плоская таблица | дерево с вложенностью |
| Типы | все поля текст | число, строка, логическое, null |
| Обязательность | задаётся отдельно | задаётся схемой или кодом |
| Чтение человеком | удобно в Excel | удобно в редакторе |
| Размер файла | меньше | больше из-за ключей |
| Частая поломка | разделитель и кодировка | отсутствующий ключ и тип |

## Сопоставление полей

Сопоставление, или маппинг, это таблица, где для каждого поля файла указан столбец приёмника, тип и правило преобразования. Для справочника клиентов «Северного склада» она выглядит так:

| Поле файла | Столбец `customers` | Тип MySQL | Правило |
|---|---|---|---|
| `external_id` | `external_id` | `VARCHAR(32)` | обязателен, уникален, ключ сопоставления |
| `name` | `name` | `VARCHAR(150)` | обязателен, обрезать пробелы, сжать двойные |
| `inn` | `inn` | `CHAR(12)` | только цифры, 10 или 12 знаков, пусто даёт `NULL` |
| `phone` | `phone` | `VARCHAR(20)` | привести к виду `+7XXXXXXXXXX` |
| `address.city` | `city` | `VARCHAR(60)` | пусто даёт `NULL` |
| `credit_limit` | `credit_limit` | `DECIMAL(12,2)` | запятая заменяется точкой, пусто даёт 0 |
| `active` | `is_active` | `TINYINT(1)` | `true` даёт 1, `false` даёт 0 |
| `created_at` | `created_at` | `DATETIME` | принять `ДД.ММ.ГГГГ` и ISO, вывести ISO |

Главный в таблице приёмник, а не источник. Тип выбирают по смыслу данных и по тому, как их будут сравнивать и суммировать. Деньги хранят в `DECIMAL`, потому что `FLOAT` накапливает ошибку округления, и сумма тысячи счетов перестаёт сходиться. Телефон хранят строкой, потому что ведущий плюс и пробелы значимы, а арифметика над ним не нужна. ИНН хранят строкой фиксированной длины: ведущий ноль в нём допустим, а число его потеряет.

Дата требует отдельного правила. В файле встречаются `27.10.2026`, `27/10/2026` и `2026-10-27T00:00:00`. Приёмник ждёт один формат `2026-10-27 00:00:00`, поэтому преобразование описывают явно и проверяют на трёх примерах. Если положиться на «MySQL разберётся», часть дат молча станет `0000-00-00`.

## Типы и проверки

Проверка идёт слоями, от дешёвой к дорогой. Сначала структура: файл разбирается целиком, обязательные ключи на месте. Потом типы: число это число, дата это дата. Затем бизнес-правила: ИНН нужной длины, сумма не отрицательна, город из списка складов. В конце ссылочная целостность: клиент, указанный в заказе, существует.

| Слой | Что проверяется | Пример отказа |
|---|---|---|
| Структура | файл читается, ключи и заголовки на месте | нет массива `customers` |
| Тип | значение приводится к типу столбца | `credit_limit` равен `"много"` |
| Формат | длина, шаблон, диапазон | ИНН из девяти цифр |
| Бизнес-правило | значение допустимо по смыслу | отрицательный кредитный лимит |
| Связь | внешний ключ существует | заказ ссылается на удалённого клиента |
| Уникальность | ключ не повторяется | две записи `C-1002` |

Проверка не должна останавливаться на первой ошибке. Файл из четырёх тысяч строк разбирают целиком и собирают все отказы в отдельный список: номер записи, поле, значение, причина. Так бухгалтер видит, что исправить в источнике, а администратор не запускает импорт двадцать раз подряд.

Отдельно решают, что делать с ошибкой: остановить весь импорт или загрузить хорошие записи, а плохие отложить. Для справочника клиентов допустима частичная загрузка с журналом отказов. Для переноса остатков на дату инвентаризации нужен режим «всё или ничего», иначе склад получит половину данных и неверные суммы.

## Пропуски и пустые значения

Пропуск это не одно значение, а четыре разных: ключа нет совсем, ключ есть со значением `null`, пришла пустая строка, пришёл ноль. Для имени клиента все четыре означают «данных нет» и запись отклоняется. Для кредитного лимита ноль это законное значение, а `null` означает «не задан», и подставлять ноль нельзя, иначе клиент получит нулевой лимит вместо отсутствия ограничения.

Правило простое: **у каждого необязательного поля есть явное значение по умолчанию или разрешённый `NULL`, и это записано в маппинге.** Нельзя оставлять решение на усмотрение базы: MySQL в строгом режиме отвергнет пустую строку в `DATETIME`, а в нестрогом подставит нулевую дату. Поведение сервера не должно быть частью бизнес-правила.

Пустые строки в текстовых полях приводят к `NULL` или к пустой строке осознанно. Если в отчёте «клиенты без ИНН» нужны только реально отсутствующие, пустая строка и `NULL` должны означать одно и то же. Договориться об этом дешевле, чем потом чистить справочник запросом.

## Идемпотентность

**Идемпотентность это свойство операции давать один и тот же результат при повторном выполнении с теми же данными.** Для импорта это значит: второй запуск не добавляет дублей, не меняет суммы и не создаёт новых клиентов. Без этого свойства любой сбой посреди загрузки ставит администратора перед выбором: запускать снова и рисковать дублями или разбирать половину вручную.

Первый способ обеспечить повторяемость это полная перезагрузка: очистить таблицу и залить файл заново в окно обслуживания. Способ простой, но опасный: между очисткой и загрузкой система не работает, а ссылки из других таблиц на время становятся битыми.

Второй способ это естественный ключ. У каждой записи есть признак, который не меняется от загрузки к загрузке: `external_id` из старой программы, ИНН плюс КПП, номер заказа. По этому ключу создают уникальный индекс, и база сама не даст вставить дубль.

```sql
ALTER TABLE customers
  ADD UNIQUE KEY uq_customers_external (external_id);
```

Третий способ это промежуточная таблица и слияние. Файл сначала грузят в `stg_customers`, где нет связей и ограничений приёмника, проверяют и сравнивают, а затем одной командой переносят в основную таблицу.

## Staging и UPSERT

Промежуточная таблица повторяет структуру файла, а не структуру приёмника. В неё можно загрузить всё как есть, посмотреть глазами и посчитать.

```sql
CREATE TABLE stg_customers (
  external_id VARCHAR(32) NOT NULL,
  name VARCHAR(150) NOT NULL,
  inn CHAR(12) NULL,
  phone VARCHAR(20) NULL,
  city VARCHAR(60) NULL,
  credit_limit DECIMAL(12,2) NOT NULL DEFAULT 0,
  row_hash CHAR(64) NOT NULL,
  PRIMARY KEY (external_id)
);
```

Слияние делают командой, которая вставляет новую строку или обновляет существующую по уникальному ключу.

```sql
INSERT INTO customers (external_id, name, inn, phone, city, credit_limit)
SELECT external_id, name, inn, phone, city, credit_limit
FROM stg_customers
ON DUPLICATE KEY UPDATE
  name = VALUES(name),
  inn = VALUES(inn),
  phone = VALUES(phone),
  city = VALUES(city),
  credit_limit = VALUES(credit_limit);
```

Команда обновляет и те строки, которые не изменились. На четырёх тысячах записей это незаметно, на миллионе лишняя запись в журнал и индексы становится дорогой. Поэтому в staging хранят `row_hash`, хеш нормализованных полей, и обновляют только записи с другим хешем.

```sql
UPDATE customers c
JOIN stg_customers s ON s.external_id = c.external_id
SET c.name = s.name, c.phone = s.phone, c.credit_limit = s.credit_limit
WHERE NOT (c.row_hash <=> s.row_hash);
```

Хеш считают по значениям после нормализации: обрезанные пробелы, единый формат телефона, дата в ISO. Если считать по сырой строке файла, порядок полей или лишний пробел дадут ложное изменение.

## Журнал импорта и ошибки

У каждого запуска есть запись в журнале: имя файла, его хеш, время начала и конца, сколько строк прочитано, вставлено, обновлено, пропущено и отклонено, статус. Журнал отвечает на вопрос «что произошло в прошлый раз» без чтения логов сервера.

```sql
CREATE TABLE import_batch (
  id INT AUTO_INCREMENT PRIMARY KEY,
  file_name VARCHAR(255) NOT NULL,
  file_hash CHAR(64) NOT NULL,
  started_at DATETIME NOT NULL,
  finished_at DATETIME NULL,
  rows_total INT NOT NULL DEFAULT 0,
  rows_inserted INT NOT NULL DEFAULT 0,
  rows_updated INT NOT NULL DEFAULT 0,
  rows_rejected INT NOT NULL DEFAULT 0,
  status VARCHAR(20) NOT NULL DEFAULT 'running'
);
```

Хеш файла защищает от случайного повтора: если тот же файл уже загружен успешно, система предупреждает и просит подтверждение. Это не заменяет идемпотентность по ключу, а дополняет её: ключ защищает данные, хеш защищает от человеческой ошибки.

Отклонённые записи складывают в таблицу отказов с причиной и номером строки. По ней строят отчёт для источника: двадцать записей без ИНН, восемь с битой датой, три с дублем ключа. Источник исправляют, файл выгружают заново, импорт повторяют. Править файл руками можно только с записью в журнал изменений, иначе следующая выгрузка вернёт ошибку.

## Сверка

Сверка сравнивает источник и приёмник по независимым показателям. Количество строк это первый и самый слабый показатель: две записи могли исчезнуть, а две другие появиться, и общее число совпадёт. Поэтому к нему добавляют число уникальных ключей, сумму денежного столбца, минимальную и максимальную дату, а для небольших таблиц контрольную сумму по отсортированным ключам.

```sql
SELECT COUNT(*) AS rows_total,
       COUNT(DISTINCT external_id) AS keys_total,
       SUM(credit_limit) AS credit_sum,
       MIN(created_at) AS first_created,
       MAX(created_at) AS last_created
FROM customers;
```

Сумма тоже не панацея: перестановка значений между двумя клиентами сохранит итог. Поэтому сверяют ещё и по группам: по городу, по признаку активности, по диапазонам суммы. Расхождение в группе указывает, где искать, даже если общий итог совпал.

Контрольная сумма по ключам считается вне базы, в скрипте: ключи сортируют, склеивают в одну строку и берут MD5 или SHA-256. До и после импорта значение должно совпасть. Если файл большой, хешируют не все ключи, а выборку из каждой тысячи.

```python
import hashlib, json

with open("customers.json", encoding="utf-8") as f:
    rows = json.load(f)["customers"]

keys = sorted(r["external_id"] for r in rows)
print(len(keys), hashlib.sha256("\n".join(keys).encode()).hexdigest())
print(sum(float(r.get("credit_limit") or 0) for r in rows))
```

Сверка заканчивается протоколом: показатель, значение до, значение после, расхождение, объяснение. Строка «расхождений нет» без чисел ничего не доказывает, а строка «сумма 12 480 300,00 до и после» доказывает.

## Откат и повтор

Перед импортом делают резервную копию таблиц, которые меняются. Для файла в несколько сотен строк загрузку можно завернуть в транзакцию и откатить целиком, но большой импорт в одну транзакцию держит блокировки и раздувает журнал. Практичнее грузить пачками по пятьсот строк и фиксировать каждую пачку, а откат делать по номеру партии.

Если у строк есть `import_batch_id`, неудачную партию удаляют одной командой и повторяют загрузку. Если партия уже смешалась с ручными правками, сначала выгружают эти правки, потом откатывают, потом возвращают.

> [!PITFALL] Повторный запуск без ключа
> Импорт без уникального ключа и без журнала выглядит работающим ровно до второго запуска. Дубли обнаруживаются не сразу: клиент появляется дважды, менеджер выбирает первого, счёт уходит не туда. Уникальный индекс ставят до первой загрузки, а не после инцидента.

## Проверьте себя

> [!CHECK] В CSV поле с названием организации содержит точку с запятой. Что произойдёт при разборе?
> Поле разорвётся на два, и все следующие значения сдвинутся на столбец. Спасают кавычки вокруг поля и настройка разделителя в парсере. Проверять нужно на реальных данных, а не на учебной строке без спецсимволов.

> [!CHECK] Импорт загрузил 4 795 записей из 4 812. С чего начать разбор?
> С журнала отказов: семнадцать записей отклонены с причиной. Если журнала нет, сравнивают ключи источника и приёмника и находят отсутствующие. Начинать с повторного запуска нельзя: причина не устранена, а дубли могут добавиться.

> [!CHECK] Зачем нужен `row_hash`, если есть `ON DUPLICATE KEY UPDATE`?
> Команда обновляет каждую совпавшую строку, даже если значения те же. Хеш позволяет пропустить неизменённые записи и не тратить журнал и индексы. На больших справочниках это заметная разница.

## Итог

- CSV это плоская таблица с проблемами разделителя, кодировки и типов, JSON это дерево с вложенностью и свободной схемой.
- Маппинг фиксирует для каждого поля столбец, тип и правило преобразования, а приёмник задаёт тип.
- Проверки идут слоями: структура, тип, формат, бизнес-правило, связь, уникальность.
- Пропуск, `null`, пустая строка и ноль это разные значения, и для каждого поля решение записано заранее.
- Идемпотентность даёт естественный ключ, staging с слиянием и журнал партий, а сверка подтверждает результат числами.

## Тест по лекции

::quiz
Q: Что представляет собой CSV?
+ Плоскую таблицу, где запись это строка текста
- Дерево с вложенными объектами
- Двоичный формат базы данных
- Архив со сжатыми таблицами
! CSV хранит строки и столбцы в текстовом виде, без вложенности и типов.

Q: Чем JSON отличается от CSV по структуре?
+ Поддерживает вложенные объекты и массивы
- Всегда занимает меньше места
- Не содержит текстовых значений
- Требует обязательной схемы
! Вложенность это главное отличие, за неё файл платит размером.

Q: Почему сумму кредитного лимита хранят в DECIMAL, а не в FLOAT?
+ DECIMAL не накапливает ошибку округления
- DECIMAL быстрее при сложении
- FLOAT не поддерживает дробные числа
- FLOAT запрещён в MySQL
! Двоичное представление дробей даёт расхождение в копейках, и суммы перестают сходиться.

Q: Что делать с обязательным полем, которого нет в записи?
+ Отклонить запись и записать причину в журнал
- Записать пустую строку вместо значения
- Подставить ноль
- Игнорировать ошибку и продолжить молча
! Выдумывать значение нельзя, запись отклоняют и объясняют причину.

Q: Что означает идемпотентность импорта?
+ Повторный запуск с теми же данными не меняет результат
- Импорт выполняется за одну секунду
- Файл загружается без проверок
- Ошибки импорта игнорируются
! Свойство защищает от дублей при повторном запуске после сбоя.

Q: Зачем нужна промежуточная таблица stg_customers?
+ Чтобы проверить и сравнить данные до записи в основную таблицу
- Чтобы ускорить работу сайта
- Чтобы заменить резервную копию
- Чтобы хранить пароли пользователей
! Staging отделяет приём файла от изменения боевых данных.

Q: Что делает INSERT ... ON DUPLICATE KEY UPDATE?
+ Вставляет строку или обновляет её при совпадении уникального ключа
- Удаляет дубли из файла
- Создаёт резервную копию таблицы
- Пересчитывает статистику таблицы
! Команда опирается на уникальный индекс и даёт повторяемую загрузку.

Q: Что показывает file_hash в журнале импорта?
+ Совпадает ли файл с уже загруженным
- Сколько строк отклонено
- Кто запустил импорт
- Сколько места заняла таблица
! Хеш ловит случайный повтор того же файла.

Q: Почему количество строк это слабый показатель сверки?
+ Пропавшие и лишние записи могут уравновесить друг друга
- Количество строк всегда считается неверно
- Количество строк не хранится в базе
- Строки нельзя посчитать дважды
! Нужны ключи, суммы и сверка по группам.

Q: Какие проблемы типичны для CSV?
+ Разделитель отличается от ожидаемого
+ Кодировка windows-1251 вместо UTF-8
+ Потеря ведущих нулей в ИНН и телефоне
+ Перевод строки внутри значения без кавычек
- Вложенный объект адреса
- Различие null и пустой строки на уровне формата
! CSV не хранит типы и вложенность, зато ломается на текстовых деталях.

Q: Какие проверки выполняют до загрузки?
+ Обязательность полей
+ Соответствие типу столбца
+ Уникальность естественного ключа
+ Существование внешнего ключа
- Скорость интернет-канала
- Цвет заголовка таблицы
! Проверки идут слоями от структуры к связям.

Q: Что записывают в журнал импорта?
+ Имя и хеш файла
+ Число вставленных, обновлённых и отклонённых строк
+ Время начала и окончания
+ Статус запуска
- Пароль учётной записи
- Содержимое всех страниц сайта
! Журнал отвечает на вопрос, что произошло в прошлый раз.

Q: Какие приёмы защищают от дублей при повторном импорте?
+ Уникальный индекс по естественному ключу
+ Слияние через staging
+ Проверка хеша файла
+ ON DUPLICATE KEY UPDATE
- Полная очистка таблицы без копии
- Отключение проверок уникальности
! Ключ, staging и хеш работают вместе, очистка без копии создаёт риск потери.

Q: Как называется свойство повторного запуска без дублей?
= идемпотентность
= идемпотентный
! Идемпотентность означает один и тот же результат при повторе.

Q: Какая команда MySQL обновляет строку при совпадении уникального ключа?
= ON DUPLICATE KEY UPDATE
= INSERT ON DUPLICATE KEY UPDATE
! Команда вставляет новую строку или обновляет существующую по ключу.

::/gate
