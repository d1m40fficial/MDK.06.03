## Цель работы

Научиться проходить два связанных изменения учебной ИС: восстановление базы после логической ошибки и установку обновления на тестовый стенд с проверкой и откатом.

Результат работы это два протокола и один план. В протоколе восстановления есть хронология, точка восстановления, таблица сверки и оценка потерь. В протоколе обновления есть чек-лист приёмки с фактами. План отката содержит условие, состав работ и время. Работа считается выполненной, когда оба протокола подтверждены числами.

## Оборудование и программное обеспечение

- Компьютер с Windows 10 или 11, PowerShell и браузером.
- XAMPP 8.5.12 с MySQL или MariaDB и phpMyAdmin, панель управления запущена.
- Учебная база sklad с таблицами orders, order_lines, stock, clients и products.
- Учебный комплект обновления «Склад+ 1.4»: архив с файлами приложения и скрипт migration_1.4.sql, выданный преподавателем.
- Рабочая папка приложения C:\sklad_app_test с версией 1.3.
- Папки D:\backup и D:\update, не менее 1 ГБ свободного места.
- Word для протоколов, Excel или калькулятор для сверки сумм.

## Краткие теоретические сведения

Логическая ошибка отличается от отказа оборудования тем, что система остаётся доступной. База открывается, приложение отвечает, но часть строк удалена или испорчена неверным запросом. Последняя копия в таком случае уже содержит порчу, поэтому точку восстановления выбирают до ошибочного действия.

Точка восстановления это конкретные дата и время. Её находят по границе между последней корректной и первой испорченной операцией. В учебном стенде роль журнала изменений играет время создания копии и время выполнения ошибочного запроса.

Восстановление идёт на отдельную базу. Сначала разворачивается копия под другим именем, затем проверяется целостность, сверяются число строк и суммы, и только потом приложение переключают на восстановленные данные. Такой порядок позволяет откатиться одним переключением.

Обновление проверяют на тестовом стенде, который повторяет конфигурацию рабочей системы. Стенд показывает, запустится ли новая версия, пройдёт ли миграция базы и работают ли ключевые сценарии. План отката пишут до установки и формулируют условие отката измеримо.

Два изменения связаны. Обновление меняет и файлы приложения, и схему базы, поэтому откат требует двух копий: папки приложения и базы. Если сохранить копию только базы, после отката останутся новые файлы приложения со старой схемой. Если сохранить только файлы, новый код будет читать таблицы, которые уже изменились.

## Ход работы

### Шаг 1. Подготовьте протоколы и папки

Создайте в Word два документа: «Протокол восстановления базы sklad» и «Протокол обновления учебного стенда». В шапке каждого укажите дату, фамилию, имя стенда и версию MySQL из phpMyAdmin.

Создайте папки для копий и для обновления.

```powershell
New-Item -ItemType Directory -Path D:\backup -Force
New-Item -ItemType Directory -Path D:\update -Force
```

### Шаг 2. Зафиксируйте эталонное состояние

До любых изменений снимите контрольные значения. Они станут эталоном для сверки после восстановления.

```sql
SELECT 'orders' AS tbl, COUNT(*) AS cnt, SUM(total) AS total_sum FROM orders
UNION ALL SELECT 'order_lines', COUNT(*), SUM(qty) FROM order_lines
UNION ALL SELECT 'stock', COUNT(*), SUM(qty) FROM stock;

CHECKSUM TABLE orders, order_lines, stock;
SELECT MAX(id) AS last_order, MAX(created_at) AS last_created FROM orders;
```

Заполните таблицу эталона. Значения перепишите в протокол, а не оставляйте только на экране.

| Таблица | Строк | Сумма | Контрольная сумма | Последний номер |
|---|---|---|---|---|
| orders | | | | |
| order_lines | | | | |
| stock | | | | |

### Шаг 3. Снимите копию и смоделируйте сбой

Снимите полную копию базы и посчитайте её хеш.

```powershell
& C:\xampp\mysql\bin\mysqldump.exe -u root sklad `
  --single-transaction --routines --triggers `
  --result-file=D:\backup\sklad_before_fault.sql
Get-FileHash D:\backup\sklad_before_fault.sql -Algorithm SHA256
```

Теперь смоделируйте логическую ошибку: удалите заказы за прошлый год, как будто скрипт очистки сработал с неверным условием.

```sql
DELETE FROM orders WHERE created_at < '2026-01-01';
SELECT COUNT(*) FROM orders;
```

Запишите в протокол время выполнения запроса и число оставшихся строк. Разница с эталоном и есть объём порчи.

### Шаг 4. Остановите потери и зафиксируйте факты

Повторно ничего не удаляйте и не запускайте очистку. Запишите в протокол хронологию: время копии, время ошибочного запроса, время обнаружения, что именно видно в системе.

| Время | Событие | Источник |
|---|---|---|
| | снята полная копия | журнал копирования |
| | выполнен ошибочный запрос | журнал запросов |
| | обнаружено расхождение | сверка с эталоном |

Определите точку восстановления. В учебном стенде это время копии: она снята до ошибочного запроса, поэтому подходит.

### Шаг 5. Восстановите базу из копии

Создайте отдельную базу и загрузите в неё копию. Замерьте время загрузки.

```powershell
& C:\xampp\mysql\bin\mysql.exe -u root -e "DROP DATABASE IF EXISTS sklad_restore; CREATE DATABASE sklad_restore;"
Measure-Command { cmd /c "C:\xampp\mysql\bin\mysql.exe -u root sklad_restore < D:\backup\sklad_before_fault.sql" }
```

Запишите время в таблицу этапов. Если загрузка остановилась с ошибкой, прочитайте номер строки: чаще всего это отсутствующая таблица или несовпадение кодировки.

|---|---|---|---|
| создание базы | | | |
| загрузка копии | | | |
| проверка | | | |

### Шаг 6. Проверьте целостность и сверьте данные

Проверьте таблицы и связи, затем сравните восстановленную базу с эталоном.

```powershell
& C:\xampp\mysql\bin\mysqlcheck.exe -u root --check sklad_restore
```

```sql
SELECT COUNT(*) AS orphan_lines FROM order_lines ol
LEFT JOIN orders o ON o.id = ol.order_id WHERE o.id IS NULL;

SELECT 'orders' AS tbl, COUNT(*) AS cnt, SUM(total) AS total_sum FROM sklad_restore.orders
UNION ALL SELECT 'order_lines', COUNT(*), SUM(qty) FROM sklad_restore.order_lines
UNION ALL SELECT 'stock', COUNT(*), SUM(qty) FROM sklad_restore.stock;

CHECKSUM TABLE sklad_restore.orders, sklad_restore.order_lines, sklad_restore.stock;
```

Заполните таблицу сверки. Расхождение по числу строк означает неполную копию, расхождение по сумме при равном числе строк означает замену значений.

### Шаг 8. Подготовьте тестовый стенд к обновлению

Стенд это восстановленная база sklad_restore и отдельная папка приложения. Скопируйте папку версии 1.3, чтобы откат был возможен.

```powershell
Copy-Item C:\sklad_app_test -Destination D:\backup\sklad_app_1.3 -Recurse
```

|---|---|---|

| копия папки приложения | есть в D:\backup | |
| копия базы | есть, хеш совпадает | |
| окно работ | согласовано | |

### Шаг 9. Установите обновление и проверьте сценарии

Распакуйте архив обновления и примените миграцию базы.

```powershell
Expand-Archive D:\update\sklad_app_1.4.zip -DestinationPath C:\sklad_app_test -Force
cmd /c "C:\xampp\mysql\bin\mysql.exe -u root sklad_restore < D:\update\migration_1.4.sql"
```

Пройдите чек-лист приёмки. Каждый пункт отмечайте фактом, а не галочкой без записи.

| Проверка | Ожидание | Факт | Результат |
|---|---|---|---|
| запуск приложения | страница входа открывается | | |
| вход администратором | вход выполнен | | |
| справочник товаров | список не пуст | | |
| создание заказа | номер присвоен, сумма верна | | |
| отчёт за смену | цифры совпадают с эталоном | | |
| журнал приложения | нет повторяющихся ошибок | | |

Если проверка не пройдена, зафиксируйте, какой именно пункт отказал. Это условие для перехода к откату.

| настройки | вернуть файл конфигурации | | |

Смоделируйте отказ: измените в тестовой базе обязательное поле так, чтобы создание заказа перестало проходить, и убедитесь, что приёмка этого не пропускает. Затем выполните откат по плану: остановите приложение, верните папку, восстановите базу, запустите и повторите проверку.

Работа завершена, когда после отката создание заказа снова проходит, а число строк совпадает с эталоном.

## Что сдать

- Протокол восстановления с хронологией, точкой восстановления и таблицей этапов.
- Таблицу эталона и таблицу сверки по трём таблицам с контрольными суммами.
- Оценку потерь с числом удалённых заказов и вывод с числами.
- Протокол обновления с чек-листом приёмки и фактами по каждому пункту.
- План отката с условием, составом, временем и ответственным.
- Результат отката с подтверждением, что создание заказа снова работает.

## Критерии оценки

- Копия снята до сбоя, хеш посчитан и записан, до 15 баллов.
- Точка восстановления обоснована временем, до 15 баллов.
- Восстановление выполнено на отдельную базу, время замерено, до 20 баллов.
- Целостность проверена, сверка по числу строк и суммам выполнена, до 20 баллов.
- Обновление установлено, приёмка пройдена по шести пунктам, до 20 баллов.
- План отката содержит измеримое условие, откат выполнен и проверен, до 10 баллов.

Работа без сверки данных или без плана отката возвращается на доработку.
