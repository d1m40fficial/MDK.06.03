## Цель работы

Научиться проходить два связанных изменения учебной ИС: восстановление базы после логической ошибки и установку обновления на тестовый стенд с проверкой и откатом.

Результат работы это два протокола и план отката. В протоколе восстановления есть хронология, точка восстановления, сверка и оценка потерь, в протоколе обновления чек-лист приёмки с фактами. Работа считается выполненной, когда оба протокола подтверждены числами.

## Оборудование и программное обеспечение

- Компьютер с Windows 10 или 11, PowerShell, браузер, Word и Excel.
- XAMPP 8.5.12 с MySQL или MariaDB и phpMyAdmin, панель управления запущена.
- Учебная база sklad с таблицами orders, order_lines, stock, clients и products.
- Учебный комплект обновления «Склад+ 1.4»: архив с файлами приложения и скрипт migration_1.4.sql, выданный преподавателем.
- Рабочая папка приложения .../sklad_app_test с версией 1.3.
- Папки .../backup и .../update, не менее 1 ГБ свободного места.

## Краткие теоретические сведения

Логическая ошибка отличается от отказа оборудования тем, что система остаётся доступной. База открывается, приложение отвечает, но часть строк удалена или испорчена неверным запросом. Последняя копия в таком случае уже содержит порчу, поэтому точку восстановления выбирают до ошибочного действия.

Точка восстановления это конкретные дата и время. Её находят по границе между последней корректной и первой испорченной операцией, а в учебном стенде опорой служат время копии и время ошибочного запроса.

Восстановление идёт на отдельную базу. Сначала разворачивается копия под другим именем, затем проверяется целостность, сверяются число строк и суммы, и только потом приложение переключают на восстановленные данные.

Обновление проверяют на тестовом стенде, который повторяет конфигурацию рабочей системы. Стенд показывает, запустится ли новая версия, пройдёт ли миграция базы и работают ли ключевые сценарии. План отката пишут до установки и формулируют условие отката измеримо.

Два изменения связаны. Обновление меняет и файлы приложения, и схему базы, поэтому откат требует двух копий. Копия только базы оставит новые файлы приложения со старой схемой, копия только файлов даст новый код на изменённых таблицах.

## Ход работы

### Шаг 1. Подготовьте протоколы и папки

Создайте в Word два документа: «Протокол восстановления базы sklad» и «Протокол обновления стенда». В шапке каждого укажите дату, фамилию, имя стенда и версию MySQL.

Создайте папки для копий и для обновления.

```powershell
New-Item -ItemType Directory -Path .../backup -Force
New-Item -ItemType Directory -Path .../update -Force
```

### Шаг 2. Зафиксируйте эталонное состояние

До любых изменений снимите контрольные значения: они станут эталоном для сверки.

```sql
SELECT 'orders' AS tbl, COUNT(*) AS cnt, SUM(total) AS total_sum FROM orders
UNION ALL SELECT 'order_lines', COUNT(*), SUM(qty) FROM order_lines
UNION ALL SELECT 'stock', COUNT(*), SUM(qty) FROM stock;

CHECKSUM TABLE orders, order_lines, stock;
SELECT MAX(id) AS last_order, MAX(created_at) AS last_created FROM orders;
```

Заполните таблицу эталона и перепишите значения в протокол.

| Таблица | Строк | Сумма | Контрольная сумма | Последний номер |
|---|---|---|---|---|
| orders | | | | |
| order_lines | | | | |
| stock | | | | |

### Шаг 3. Снимите копию и смоделируйте сбой

Снимите полную копию базы и посчитайте её хеш.

```powershell
& mysqldump -u root sklad `
  --single-transaction --routines --triggers `
  --result-file=.../backup/sklad_before_fault.sql
Get-FileHash .../backup/sklad_before_fault.sql -Algorithm SHA256
```

Теперь смоделируйте логическую ошибку: удалите заказы за прошлый год, как будто скрипт очистки сработал с неверным условием.

```sql
DELETE FROM orders WHERE created_at < '2026-01-01';
SELECT COUNT(*) FROM orders;
```

Запишите время запроса и число оставшихся строк: разница с эталоном это объём порчи.

### Шаг 4. Остановите потери и зафиксируйте факты

Повторно ничего не удаляйте. Соберите хронологию по выпискам, которые остались после работы: журнал копирования, журнал запросов, сообщения пользователей.

```text
09:02  mysqldump sklad -> sklad_before_fault.sql, 42 МБ
09:15  DELETE FROM orders WHERE created_at < '2026-01-01', 312 rows
09:15  приложение: список заказов открылся, за март пусто
09:31  бухгалтер: пропали заказы за прошлый год
09:33  сверка с эталоном: orders 1180 вместо 1492
```

Заполните хронологию: одна строка выписки даёт одно событие, источник берите из строки.

| Время | Событие | Источник |
|---|---|---|
| | | |
| | | |
| | | |
| | | |

Точку восстановления определите сами по двум границам: последняя корректная операция и первая испорченная. Запишите её с обоснованием в одну фразу и проверьте, что она раньше первой испорченной операции.

### Шаг 5. Восстановите базу из копии

Создайте отдельную базу и загрузите в неё копию. Замерьте время загрузки.

```powershell
& mysql -u root -e "DROP DATABASE IF EXISTS sklad_restore; CREATE DATABASE sklad_restore;"
Measure-Command { cmd /c "mysql -u root sklad_restore < .../backup/sklad_before_fault.sql" }
```

Запишите время в таблицу этапов. Если загрузка остановилась с ошибкой, прочитайте номер строки: обычно это отсутствующая таблица или несовпадение кодировки.

|---|---|---|---|

| проверка | | | |

### Шаг 6. Проверьте целостность и сверьте данные

Проверьте таблицы и связи, затем сравните восстановленную базу с эталоном.

```powershell
& mysqlcheck -u root --check sklad_restore
```

```sql
SELECT COUNT(*) AS orphan_lines FROM order_lines ol
LEFT JOIN orders o ON o.id = ol.order_id WHERE o.id IS NULL;

SELECT 'orders' AS tbl, COUNT(*) AS cnt, SUM(total) AS total_sum FROM sklad_restore.orders
UNION ALL SELECT 'order_lines', COUNT(*), SUM(qty) FROM sklad_restore.order_lines
```

Потеря данных это разница между моментом сбоя и точкой восстановления. Посчитайте, сколько заказов удалено и что придётся вводить заново.

| Показатель | Значение |
|---|---|
| точка восстановления | |
| время сбоя | |
| длительность потери | |
| удалено заказов | |

Вывод соберите из своих чисел: размер копии, время восстановления, результат сверки, период и число потерянных заказов. Пример формы на другом сбое: «Копия 310 МБ восстановлена за 2 минуты, строки совпали, потеряны заказы за 40 минут, их 6, повторный ввод займёт около часа».

### Шаг 8. Подготовьте тестовый стенд к обновлению

Стенд это база sklad_restore и отдельная папка приложения. Скопируйте папку версии 1.3: без неё откат невозможен.

| копия базы | есть, хеш совпадает | |

### Шаг 9. Установите обновление и проверьте сценарии

Распакуйте архив обновления и примените миграцию базы.

```powershell
Expand-Archive .../update/sklad_app_1.4.zip -DestinationPath .../sklad_app_test -Force
cmd /c "mysql -u root sklad_restore < .../update/migration_1.4.sql"
```

Пройдите чек-лист приёмки. Каждый пункт отмечайте фактом, а не галочкой.

| Проверка | Ожидание | Факт | Результат |
|---|---|---|---|
| запуск приложения | страница входа открывается | | |
| вход администратором | вход выполнен | | |
| справочник товаров | список не пуст | | |
| создание заказа | номер присвоен, сумма верна | | |
| отчёт за смену | цифры совпадают с эталоном | | |

Если проверка не пройдена, зафиксируйте, какой пункт отказал: это условие перехода к откату.

### Шаг 10. Составьте план отката и выполните откат

Заполните план отката до принятия решения. Первая строка это образец формы, остальные строки относятся к этому обновлению.

| Что откатывается | Как | Время | Ответственный |
|---|---|---|---|
| служба печати на сервере | перезапустить службу Spooler | 2 минуты | инженер второй линии |
| | | | |
| | | | |
| | | | |

Что и откуда вернуть, возьмите из шагов 3 и 8. Время оцените по фактам шага 5. Условие отката сформулируйте до установки: какой пункт приёмки должен отказать, чтобы работа была отменена.

Смоделируйте отказ. Пример: ограничьте поле status двумя символами и сохраните заказ.

```sql
ALTER TABLE sklad_restore.orders MODIFY status VARCHAR(2) NOT NULL;
INSERT INTO sklad_restore.orders (client_id, status, total) VALUES (17, 'new', 1200.00);
```

Вторая команда вернёт ошибку «Data too long for column 'status'», создание заказа перестанет проходить. Повторите опыт на поле total: задайте тип DECIMAL(4,2) и сохраните заказ на 48200. Убедитесь, что приёмка ловит отказ, затем выполните откат: остановите приложение, верните папку, восстановите базу, запустите и повторите проверку.

| восстановление базы | | |
| повторная проверка | | |

Работа завершена, когда после отката создание заказа снова проходит, а число строк совпадает с эталоном.

## Что сдать

- Протокол восстановления с хронологией, точкой восстановления и таблицей этапов.
- Таблицу эталона и таблицу сверки по трём таблицам с контрольными суммами.
- Оценку потерь с числом удалённых заказов и вывод с числами.
- Протокол обновления с чек-листом приёмки и фактами по каждому пункту.
- План отката с условием, составом, временем и ответственным.
- Результат отката с подтверждением, что создание заказа снова работает.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

| Оценка | Условие |
|---|---|
| 5 | Работа выполнена полностью и самостоятельно, все пункты ниже выполнены |
| 4 | Работа выполнена, есть 1 или 2 незначительных замечания |
| 3 | Работа выполнена частично, есть существенные замечания |
| 2 | Работа не выполнена |
| 1 | Работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления |

Что проверяется:
- Копия снята до сбоя, хеш посчитан и записан.
- Точка восстановления обоснована временем.
- Восстановление выполнено на отдельную базу, время замерено.
- Целостность проверена, сверка по числу строк и суммам выполнена.
- Обновление установлено, приёмка пройдена по шести пунктам.
- План отката содержит измеримое условие, откат выполнен и проверен.

Работа без сверки данных или без плана отката возвращается на доработку.
