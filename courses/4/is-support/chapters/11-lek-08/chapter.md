## Одна идея

В понедельник 26 октября кладовщик тульского склада «Северного склада» не смог провести приёмку. «Склад+» показала «Ошибка сохранения», и заказ повис без номера. Инженер «Сервис-ИТ» открыл журнал веб-сервера и увидел ответ 500. В журнале приложения нашлось исключение про запись во временный файл. В журнале MySQL стояла ошибка про нехватку места. В мониторинге свободное место на диске было 0,02 гигабайта.

Четыре источника рассказали четыре версии одного события. Ни одна из них не была ложной, но по отдельности они не объясняли, почему заказы перестали сохраняться ровно в 09:11 и почему заработали снова в 09:41, когда администратор переместил старые журналы Apache на внешний диск.

Причина стала видна на пересечении: журналы Apache занимали 38 гигабайт, диск заполнился, MySQL не смог создать временный файл, приложение вернуло ошибку, а пользователь увидел 500. Ни один журнал не содержал этой истории целиком, потому что каждый писал только свою часть.

**Журнал это последовательность записей об событиях, у которых есть общие поля.** Пять полей делают запись пригодной для разбора: время, источник, уровень, событие и контекст. Пока всех пяти нет, файл остаётся текстом для чтения, а не данными для поиска. Разбор сбоя начинается не с чтения, а с вопроса: какие источники писали об этом событии и что у них общего.

## Пять источников

У «Склад+» пять слоёв, и каждый ведёт свой журнал.

Первый слой это операционная система. В Windows события лежат в Event Viewer, каналы System, Application и Security. Канал System пишет о службах, драйверах, питании и перезагрузках, канал Security о входах и правах. В Linux ту же роль играют journald и файлы в `/var/log`, например `syslog` и `auth.log`. Системный журнал знает, что служба запустилась или остановилась, но не знает, что в этот момент не сохранился заказ.

Второй слой это приложение. «Склад+» пишет свой файл `sklad.log`, где отмечает вход пользователя, открытие справочника, сохранение заказа и исключение. Здесь появляется бизнес-смысл: не «процесс завершился», а «не сохранён заказ SO-10482 кладовщика Ивановой». Прикладной журнал знает пользователя и объект, но не знает, что происходило с диском.

Третий слой это веб-сервер. Apache ведёт два файла. `access.log` хранит по строке на запрос: адрес, метод, путь, код ответа, размер и время. `error.log` хранит ошибки самого сервера и сообщения PHP. По `access.log` видно, что с 09:12 до 09:41 все запросы `POST /orders/save` получали 500, а главная страница продолжала отдаваться с кодом 200. Это сразу снимает версию «сервер недоступен».

Четвёртый слой это СУБД. MySQL пишет журнал ошибок `mysql_error.log`, журнал медленных запросов `slow.log` и, если включён, общий журнал `general.log`. Журнал ошибок фиксирует запуск и остановку сервера, сбои InnoDB и нехватку места. Медленный журнал показывает запросы дольше заданного порога. Общий журнал пишет каждый запрос и потому быстро растёт, его включают на короткое время для разбора.

Пятый слой это сеть. Межсетевой экран, коммутатор, VPN и DNS пишут о соединениях, блокировках и маршрутах. Если пользователь не может открыть страницу, именно здесь видно, дошёл ли запрос до сервера или был отброшен на входе.

| Источник | Где смотреть | Что даёт | Чего не знает |
|---|---|---|---|
| Система Windows | Event Viewer, каналы System и Security | службы, драйверы, питание, входы | смысл бизнес-операции |
| Система Linux | `journalctl`, `/var/log/syslog` | ядро, службы, аутентификация | состояние приложения |
| Приложение | `logs/sklad.log` | операция, пользователь, объект, исключение | состояние диска и сети |
| Веб-сервер | `access.log`, `error.log` | запрос, код ответа, время, ошибка PHP | что было внутри СУБД |
| СУБД | `mysql_error.log`, `slow.log` | запуск, сбои InnoDB, медленные запросы | что делал пользователь |
| Сеть | журналы firewall, VPN, DNS | соединения, блокировки, маршруты | содержимое запроса |

Ни один источник не главный. Главный тот, который отвечает на текущий вопрос, а остальные подтверждают или исключают версию.

## Уровни записи

Уровень говорит, насколько событие серьёзно для программы. В syslog принята шкала от 0 до 7: EMERGENCY, ALERT, CRITICAL, ERROR, WARNING, NOTICE, INFO, DEBUG. Прикладные библиотеки обычно оставляют пять рабочих уровней.

| Уровень | Смысл | Пример из «Склад+» |
|---|---|---|
| DEBUG | подробности для разработки | значение параметров запроса |
| INFO | штатное событие | пользователь вошёл, заказ сохранён |
| WARNING | работа продолжается, но есть отклонение | повтор соединения с СУБД |
| ERROR | операция не выполнена | заказ не сохранён |
| CRITICAL | не работает система или её часть | нет соединения с СУБД |

Уровень описывает серьёзность для программы, а не важность для бизнеса. Запись INFO о неудачном входе администратора может быть важнее записи ERROR о недоступном изображении. Поэтому журнал безопасности ведут отдельно и не фильтруют по уровню ERROR.

Настройка уровня зависит от среды. На стенде разработчика полезен DEBUG, в рабочей системе остаются INFO и выше, а DEBUG включают на время разбора и выключают обратно. Постоянный DEBUG на нагруженном сервере даёт гигабайты записей и замедляет работу.

Опасна настройка «только ERROR». Она скрывает WARNING о том, что диск заполнен на 92 процента, и о том, что соединение с СУБД пришлось повторять. Когда появляется ERROR, причина уже развилась до отказа, а предупреждения, которые могли её показать, не сохранились.

Уровни разных систем не совпадают по названиям. В PHP их задаёт `error_reporting`, в Apache важность стоит в скобках, например `[core:error]` или `[php:warn]`, в журнале MySQL встречаются Note, Warning и ERROR. При сведении хронологии уровни приводят к одной шкале: Note считают INFO, Warning оставляют WARNING, Error и Critical относят к ERROR. Иначе сортировка по уровню даст разный порядок в разных файлах.

## Контекст записи

Сравните две строки.

```text
2026-10-27 09:11:58 ERROR Ошибка сохранения заказа
```

```text
2026-10-27T09:11:58.412+03:00 ERROR order.save user=ivanova order=SO-10482 request=8f3c1a duration=2412ms errno=28 msg="No space left on device"
```

Первая строка сообщает, что что-то не получилось. Вторая отвечает на вопросы: когда, у кого, с каким заказом, в каком запросе, сколько это длилось и с какой ошибкой. По ней можно найти остальные записи того же запроса и открыть нужный заказ.

Контекст не должен содержать секретов. Пароль, номер банковской карты, паспортные данные и содержимое документа в журнал не попадают. Логин, идентификатор заказа, адрес рабочей станции и код ошибки попадать могут. Если поле нужно для разбора, но содержит персональные данные, его маскируют: `ivanova@example.ru` превращается в `i***@example.ru`.

## Время

Время есть в каждой записи, поэтому оно служит осью сопоставления. С ним связаны три проблемы: формат, часовой пояс и точность.

Форматы различаются даже на одном сервере. Apache пишет `27/Oct/2026:09:11:58 +0300`, MySQL пишет `2026-10-27T09:11:57.884512+03:00` или `...Z`, если настроен на UTC, приложение пишет `2026-10-27T09:11:58.412+03:00`, Windows показывает локальное время с миллисекундами. Буква `Z` означает UTC, смещение `+03:00` означает московское время. Если MySQL настроен на UTC, при сравнении строк он окажется на три часа раньше остальных, хотя события произошли одновременно.

Поэтому перед сопоставлением все метки приводят к одному виду, обычно к UTC или к местному времени с явным смещением. В таблице хронологии всегда указывают, в каком поясе она составлена.

Точность зависит от синхронизации. Часы сервера и рабочей станции уходят вперёд или отстают, и тогда причина оказывается позже следствия. В Windows состояние проверяют командой `w32tm /query /status`, в Linux командой `timedatectl status`. Источник времени должен быть один для всех узлов: контроллер домена, внутренний сервер времени или пул NTP.

Для длительности события нужны монотонные часы, которые не переводятся назад. Время в записи отвечает на вопрос «когда», а длительность измеряют отдельным счётчиком и пишут в поле `duration`.

## Корреляция

Корреляция это сопоставление записей по общим признакам. Признаки бывают явные и косвенные. Явный признак это идентификатор запроса, который приложение передаёт в веб-сервер и в СУБД. Косвенный признак это совпадение времени, пользователя, адреса и объекта.

| Время | Источник | Уровень | Запись | Что означает |
|---|---|---|---|---|
| 09:11:55.002 | Windows | INFO | служба MySQL, код 7036 | служба остановлена |
| 09:11:57.884 | MySQL | ERROR | errno 28 | нет места для временного файла |
| 09:11:58.412 | PHP | ERROR | request 8f3c1a | исключение при сохранении |
| 09:11:58.418 | Apache | INFO | 500, request 8f3c1a | клиент получил ошибку |
| 09:12:03.115 | Apache | INFO | 500, request 91b7d2 | следующий заказ тоже не прошёл |

Идентификатор запроса связывает приложение и веб-сервер. Чтобы связать СУБД, приложение добавляет его в комментарий к запросу, и тогда тот же код появляется в медленном журнале. Если сквозного идентификатора нет, остаются время, пользователь и текст ошибки, но точность падает: два пользователя могли сохранять заказы в одну секунду.

Корреляция не доказывает причину. Совпадение по времени может быть случайным. Причину подтверждают порядком событий и повтором: если после остановки службы каждый запрос получает ошибку, а после запуска снова проходит, связь подтверждена. Если ошибки начались за час до остановки службы, причина в другом месте.

## Поиск

Читать файл целиком бессмысленно: в рабочем журнале десятки тысяч строк. Поиск сужают в три шага: окно времени, затем уровень или код, затем текст.

```powershell
Select-String -Path .../sklad/logs\sklad.log -Pattern 'request=8f3c1a'
Get-WinEvent -FilterHashtable @{LogName='System'; StartTime=(Get-Date).AddHours(-2)} |
  Where-Object { $_.Id -in 41, 1074, 7036 } |
  Select-Object TimeCreated, Id, ProviderName
```

```bash
journalctl -u sklad --since "2026-10-27 09:00" --until "2026-10-27 09:45" -p warning
grep -n '27/Oct/2026:09:1[2-9]' /var/log/apache2/access.log
```

Полезно не только находить строки, но и считать их. Число ответов 500 по минутам показывает начало и конец сбоя точнее, чем первая найденная строка. Запрос сохраняют в заметке вместе с временем запуска, чтобы коллега повторил его и получил тот же результат.

## Ротация

Журнал растёт всегда. За месяц Apache на «Склад+» записал 31 гигабайт `access.log` и 7 гигабайт `error.log`, потому что ротацию при установке не настроили. Диск на 60 гигабайт заполнился, и MySQL не смог создать временный файл. Журналы стали причиной сбоя, о котором они же и сообщили.

Ротация это замена файла журнала по размеру или по календарю с сохранением старых копий. Настройка отвечает на четыре вопроса: когда менять файл, сколько копий хранить, сжимать ли их и что делать с открытым файлом.

В Linux ротацией управляет logrotate.

```text
/var/log/sklad/*.log {
    daily
    rotate 30
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
```

Строка `daily` задаёт период, `rotate 30` оставляет тридцать копий, `compress` сжимает старые, `copytruncate` копирует файл и очищает исходный. Последний приём удобен, если приложение не умеет переоткрывать файл по сигналу, но между копированием и очисткой можно потерять несколько строк. Если приложение поддерживает переоткрытие, лучше использовать его и не терять записи.

В Apache на Windows ту же задачу решает `rotatelogs`.

```text
CustomLog "|bin/rotatelogs.exe logs/access_%Y%m%d.log 86400" combined
ErrorLog  "|bin/rotatelogs.exe logs/error_%Y%m%d.log 86400"
```

MySQL ограничивает срок жизни бинарных журналов параметром `binlog_expire_logs_seconds`, а размер журнала ошибок контролируют внешней ротацией. Event Viewer в Windows настраивают через максимальный размер канала и режим перезаписи.

Правило простое: журналы не лежат на том же разделе, где данные СУБД, и на разделе всегда остаётся запас. Порог оповещения ставят на 80 процентов, а не на 99. Проверка ротации входит в регламент обслуживания, потому что ошибка в ней проявляется через месяц, когда свободное место заканчивается.

## Срок хранения и защита

Срок хранения это ответ на вопрос, как долго запись должна быть доступна. Он зависит от назначения. Для разбора свежих инцидентов хватает 30 дней, для расследования инцидентов безопасности и финансовых операций нужен год и больше. Точный срок задаёт внутренний регламент и требования регулятора, а не привычка администратора.

| Тип журнала | Типовой срок | Зачем |
|---|---|---|
| Приложение | 30 дней | разбор обращений пользователей |
| Веб-сервер | 30 дней | нагрузка и коды ответов |
| СУБД | 90 дней | сбои, медленные запросы |
| Безопасность | 1 год | входы, права, инциденты |
| Сеть | 90 дней | соединения и блокировки |

Журнал содержит логины, адреса и иногда персональные данные, поэтому доступ к нему ограничен. Читать журналы должны администраторы и инженеры поддержки, а не все сотрудники. Файлы защищают от изменения: на центральном сервере сбора записей их дописывают, но не редактируют, а целостность проверяют по хешу.

Хранение на том же сервере не защищает от отказа диска. Записи отправляют на отдельный узел или в отдельное хранилище, иначе вместе с сервером теряется история его последних часов. Синхронизация времени на узле сбора обязательна, иначе общая хронология снова распадётся.

Настройку проверяют, а не предполагают. После включения журнала инженер выполняет тестовую операцию, находит её запись, убеждается, что время и уровень верны, и только потом закрывает заявку. Через месяц проверяют, что ротация создала новый файл, старый сжат, а свободное место не изменилось. Такая проверка занимает несколько минут и предотвращает сбой, который иначе обнаружится в самый неудобный момент.

::gate Какие ошибки чаще всего делают журналы бесполезными?

## Типичные ошибки

| Ошибка | Как проявляется | Как исправить |
|---|---|---|
| Журнал не включён | в файле пусто или только запуск | включить нужный журнал и проверить запись |
| Уровень только ERROR | нет предупреждений перед отказом | оставить INFO и WARNING |
| Часовой пояс не указан | события не сходятся по времени | писать смещение или UTC |
| Нет идентификатора запроса | записи не связать | добавить request_id во все слои |
| Ротация не настроена | диск заполнен журналами | настроить ротацию и порог 80 процентов |
| Срок хранения меньше месяца | окно инцидента уже удалено | увеличить глубину хранения |
| Журнал на диске с данными | сбой базы и потеря журналов сразу | вынести на отдельный раздел |
| В журнале пароли и карты | утечка при чтении | маскировать чувствительные поля |

## Итог

- Журнал это набор записей с полями времени, источника, уровня, события и контекста, а не текст для чтения.
- Системный, прикладной, серверный, сетевой журналы и журнал СУБД знают разные части одного события.
- Уровень говорит о серьёзности для программы, поэтому настройка «только ERROR» скрывает начало сбоя.
- Время сводят к одному поясу и синхронизируют, иначе причина оказывается позже следствия.
- Корреляция опирается на сквозной идентификатор и подтверждается порядком событий, а не совпадением.
- Ротация и срок хранения защищают диск и сохраняют окно, в котором ещё можно разобрать инцидент.

## Проверьте себя

> [!CHECK] В журнале приложения время 09:11, в журнале MySQL 06:11. Это сбой?
> Скорее всего нет. MySQL пишет UTC, приложение пишет московское время. Разницу в три часа даёт часовой пояс, а не ошибка. Проверяют смещение в формате метки и настройку часов.

> [!CHECK] Почему запись ERROR без идентификатора запроса почти бесполезна?
> По ней нельзя найти остальные события той же операции в других журналах. Остаётся совпадение по времени и пользователю, а оно неоднозначно. Идентификатор превращает набор строк в историю.

> [!CHECK] Чем опасна ротация с copytruncate?
> Между копированием и очисткой приложение может дописать строки, и они пропадут. Если приложение умеет переоткрывать файл по сигналу, лучше использовать этот способ. Потерю строк замечают только при разборе, когда их уже нет.

## Тест по лекции

::quiz
Q: Что делает запись журнала пригодной для поиска?
+ Набор общих полей: время, источник, уровень, событие, контекст
- Большой размер файла
- Наличие пароля пользователя
- Хранение на том же диске, что и база
! Без общих полей строки нельзя отфильтровать и сопоставить.

Q: Какой журнал показывает, что запрос POST /orders/save получил ответ 500?
+ access.log веб-сервера
- mysql_error.log
- auth.log
- slow.log
! Код ответа и путь запроса фиксирует журнал доступа веб-сервера.

Q: Что означает уровень WARNING?
+ Работа продолжается, но есть отклонение
- Операция не выполнена
- Система полностью остановлена
- Подробности для разработчика
! Предупреждение сигнализирует о проблеме до того, как она станет отказом.

Q: Почему настройка «только ERROR» опасна?
+ Она скрывает предупреждения, которые показывают развитие сбоя
- Она ускоряет диск
- Она запрещает вход пользователей
- Она удаляет старые файлы
! К моменту первой ошибки причина уже развилась, а следов подготовки нет.

Q: Зачем в записи указывают часовой пояс?
+ Чтобы сопоставить события разных источников по времени
- Чтобы уменьшить размер файла
- Чтобы скрыть имя пользователя
- Чтобы ускорить ротацию
! Без пояса метки разных систем не сравнимы.

Q: Что такое корреляция записей?
+ Сопоставление событий по общим признакам, например по идентификатору запроса
- Сжатие журнала перед хранением
- Удаление старых записей
- Перезапуск службы после сбоя
! Корреляция собирает историю из записей разных источников.

Q: Что задаёт параметр rotate 30 в logrotate?
+ Сколько старых копий журнала хранить
- Через сколько дней удалить журнал целиком
- Сколько строк писать в файл
- Размер одной записи
! Параметр ограничивает глубину хранения копий.

Q: Почему журналы не стоит хранить на разделе с данными СУБД?
+ Заполнение раздела журналами остановит базу, а отказ диска уничтожит и данные, и журналы
- Журналы мешают работе процессора
- MySQL не умеет читать соседние файлы
- Это замедляет вход пользователей
! Общий раздел связывает две разные нагрузки и две разные потери.

Q: Что означает буква Z в метке времени?
+ Время указано в UTC
- Время указано в московском поясе
- Запись сделана последней
- Запись повреждена
! Z это обозначение UTC по стандарту ISO 8601.

Q: Какие источники журналов есть у «Склад+»?
+ Операционная система
+ Приложение
+ Веб-сервер и СУБД
+ Сеть
- Печатный отчёт бухгалтерии
- Файл резервной копии
! Каждый слой системы ведёт свой журнал.

Q: Что должно быть в записи приложения о неудачном сохранении заказа?
+ Идентификатор запроса
+ Пользователь и номер заказа
+ Код ошибки и длительность
+ Время с часовым поясом
- Пароль пользователя
- Номер банковской карты клиента
! Контекст нужен для поиска, секреты в журнал не попадают.

Q: Какие признаки говорят, что ротация не настроена?
+ Файл журнала растёт до десятков гигабайт
+ Свободное место на диске падает без роста данных
+ В каталоге лежит один файл за несколько месяцев
+ Появляются ошибки записи во временный файл
- В журнале появились записи уровня INFO
- Служба перезапустилась по расписанию
! Нерастущий набор файлов и падающее место выдают отсутствие ротации.

Q: Какие меры защищают журналы?
+ Ограничение доступа по ролям
+ Отправка на отдельный узел сбора
+ Маскирование персональных данных
+ Синхронизация времени
- Публикация файлов в общей папке
- Хранение паролей в открытом виде
! Журнал содержит чувствительные данные и должен быть защищён.

Q: Как называется замена файла журнала по размеру или календарю?
= ротация
= log rotation
! Ротация сохраняет старые копии и освобождает место.

Q: Какой протокол используют для синхронизации часов?
= NTP
= network time protocol
! NTP поддерживает единое время на серверах и рабочих станциях.

::/gate
