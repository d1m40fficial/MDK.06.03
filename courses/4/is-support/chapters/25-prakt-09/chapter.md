## Цель работы

Научиться проверять безопасность учебной ИС по единому чек-листу и превращать результат проверки в понятный план устранения.

Результат работы это заполненный чек-лист, перечень слабых мест с оценкой риска и план устранения с ответственными и сроками. Каждый пункт чек-листа подтверждается фактом: командой, значением настройки или записью журнала, а не общим выводом «всё в порядке».

## Оборудование и программное обеспечение

- Компьютер с Windows 10 или 11, PowerShell и браузером.
- XAMPP 8.5.12 с MySQL или MariaDB и phpMyAdmin, панель управления запущена.
- Учебная база sklad и учебные учётные записи MySQL, выданные преподавателем.
- Учебное приложение «Склад+» с формой входа.
- Папка D:\backup с копиями базы и папкой приложения.
- Word и Excel для чек-листа и плана.

## Краткие теоретические сведения

Безопасность поддержки начинается с учётных записей. У каждого человека своя учётная запись, у каждой службы отдельная. Общая учётная запись не позволяет установить автора действий и не позволяет заблокировать одного сотрудника, не заблокировав остальных.

Права выдаются по принципу минимальных привилегий: ровно то, что нужно для задачи, и на нужный срок. Проверка прав показывает, какие разрешения выданы фактически, а не какие предполагались при настройке.

Парольная политика задаёт длину, сложность и срок действия пароля. Отдельно проверяют, нет ли паролей в скриптах, текстовых файлах и общих папках.

Журналирование отвечает на вопрос, кто и что сделал. Проверяют, включены ли нужные журналы, куда они пишутся и можно ли их изменить с самого сервера.

Резервная копия содержит все данные в одном файле, поэтому её защищают отдельно: шифруют архив, сужают доступ к папке и держат одну копию вне сети.

Проверка идёт по фактам. Запись «права настроены правильно» ничего не доказывает, а вывод SHOW GRANTS с перечнем разрешений доказывает. Поэтому каждый пункт чек-листа заполняют после команды или просмотра настройки, а не по памяти.

Слабое место описывают через последствие: что сможет сделать человек, который им воспользуется. Общая учётная запись позволяет действовать от чужого имени, пароль в файле утекает вместе с копией, лишнее право превращает ошибку кода в потерю данных.

## Ход работы

### Шаг 1. Подготовьте чек-лист

Создайте в Word документ «Чек-лист безопасности учебной ИС» и таблицу проверок. Строки оставьте пустыми до выполнения шагов.

| Раздел | Что проверяется | Норма | Факт | Оценка |
|---|---|---|---|---|
| учётные записи | у каждого человека своя запись | да | | |
| пароли | политика задана | да | | |
| права | нет лишних разрешений | да | | |
| журналы | включены и вынесены | да | | |
| копии | архив зашифрован | да | | |
| обновления | нет критичных пропусков | да | | |
| порты | наружу только нужные | да | | |

### Шаг 2. Проведите инвентаризацию учётных записей

Получите список учётных записей СУБД и приложения.

```sql
SELECT user, host FROM mysql.user ORDER BY user;
SELECT user, host, account_locked FROM mysql.user WHERE user LIKE 'sklad%';
```

Заполните таблицу. Для каждой записи укажите, кому она принадлежит, нужна ли она и когда использовалась последний раз.

| Учётная запись | Кому принадлежит | Назначение | Нужна | Общая |
|---|---|---|---|---|
| root | администратор стенда | управление | да | нет |
| | | | | |

Отдельно отметьте общие записи, записи без владельца и записи уволенных сотрудников. Учебная запись sklad_user без владельца в перечне слабых мест отмечается как избыточная.

### Шаг 3. Проверьте парольную политику

Посмотрите настройки парольной политики и срок действия паролей.

```sql
SHOW VARIABLES LIKE 'validate_password%';
SELECT user, host, password_last_changed FROM mysql.user;
```

Запишите факты: задана ли минимальная длина, требуется ли сложность, менялся ли пароль за последний год. Если политика не включена, это слабое место с высоким риском.

Проверьте папки и скрипты на наличие паролей в открытом виде.

```powershell
Select-String -Path C:\sklad_app_test\*.php -Pattern "password|passwd|pwd" -SimpleMatch
```

Найденная строка с паролем означает, что секрет хранится вместе с кодом и попадёт в копию приложения.

### Шаг 4. Проверьте права

Для каждой учётной записи выведите выданные разрешения.

```sql
SHOW GRANTS FOR 'sklad_user'@'localhost';
SHOW GRANTS FOR 'backup_operator'@'localhost';
```

Сравните выданные права с матрицей ролей. Признаки избыточных прав: ALL PRIVILEGES у прикладной записи, право DELETE у скрипта копирования, право GRANT OPTION у инженера, доступ к базе mysql у пользователя приложения.

| Учётная запись | Выдано | Требуется по роли | Лишнее |
|---|---|---|---|
| sklad_user | | SELECT, INSERT, UPDATE | |
| backup_operator | | SELECT, LOCK TABLES | |
| | | | |

Каждое лишнее право запишите отдельной строкой: его придётся отзывать и проверять, не сломает ли отзыв работу приложения.

### Шаг 5. Проверьте журналы

Убедитесь, что нужные журналы включены.

```sql
SHOW VARIABLES LIKE 'general_log';
SHOW VARIABLES LIKE 'log_error';
SHOW VARIABLES LIKE 'log_bin';
```

Запишите путь к журналу ошибок и проверьте последние записи. Затем посмотрите, может ли прикладная учётная запись изменить журнал: если файл лежит в папке, доступной на запись пользователю приложения, это слабое место.

| Журнал | Включён | Куда пишется | Защищён от изменения |
|---|---|---|---|
| ошибок | | | |
| общий | | | |
| двоичный | | | |
| входов приложения | | | |

### Шаг 6. Проверьте резервные копии

Осмотрите папку копий и ответьте на четыре вопроса: зашифрован ли архив, кто имеет доступ к папке, есть ли копия вне сети, проверялась ли она восстановлением.

```powershell
Get-ChildItem D:\backup | Select-Object Name, Length, LastWriteTime
Get-FileHash D:\backup\sklad_before_fault.sql -Algorithm SHA256
```

| Проверка копии | Норма | Факт |
|---|---|---|
| архив зашифрован | да | |
| доступ к папке | не более трёх человек | |
| копия вне сети | есть | |
| проверка восстановлением | за последний месяц | |
| хеш совпадает | да | |

### Шаг 7. Проверьте обновления и открытые порты

Запишите версию СУБД и приложения, дату последнего обновления и наличие известных критичных исправлений. Затем посмотрите, какие порты слушают на компьютере.

```powershell
netstat -ano | Select-String "LISTENING"
```

| Порт | Служба | Нужен снаружи | Действие |
|---|---|---|---|
| 80 | Apache | да, только в учебной сети | |
| 443 | Apache | да, только в учебной сети | |
| 3306 | MySQL | нет | закрыть для внешних адресов |

Порт, который слушает весь мир и не нужен снаружи, отмечается как слабое место.

### Шаг 8. Соберите перечень слабых мест

Перенесите все найденные отклонения в отдельную таблицу. Риск оцените по двум признакам: насколько легко воспользоваться слабым местом и что оно позволит сделать.

| Слабое место | Раздел | Риск | Почему |
|---|---|---|---|
| общая учётная запись sklad_user | учётные записи | высокий | нельзя установить автора действий |
| пароль в файле config.php | пароли | высокий | утечёт вместе с копией |
| ALL PRIVILEGES у приложения | права | высокий | ошибка кода удалит данные |
| журнал входов отключён | журналы | средний | инцидент не разобрать |
| копия без шифрования | копии | высокий | утечка всех данных |

Пустым перечень не бывает: в учебном стенде почти всегда есть хотя бы отключённый журнал или лишнее право. Если отклонение не найдено, запишите, чем это подтверждено.

### Шаг 9. Составьте план устранения

Для каждого слабого места укажите меру, ответственного и срок. Сначала закрывают высокий риск, потом средний, потом низкий.

| Слабое место | Мера | Ответственный | Срок | Проверка результата |
|---|---|---|---|---|
| общая учётная запись | создать персональные записи | администратор БД | неделя | вход под своей записью |
| пароль в файле | вынести в хранилище секретов | инженер второй линии | три дня | поиск по папке не находит пароль |
| ALL PRIVILEGES | отозвать лишние права | администратор БД | день | SHOW GRANTS без ALL |
| журнал отключён | включить и вынести на отдельный узел | системный администратор | неделя | записи появляются вне сервера |
| копия без шифрования | включить шифрование архива | администратор БД | месяц | архив открывается только с ключом |

План считается готовым, когда у каждой меры есть проверка результата. Формулировка «усилить безопасность» проверкой не является.

## Что сдать

- Заполненный чек-лист по семи разделам с фактами.
- Таблицу учётных записей с владельцами и назначением.
- Таблицу выданных и требуемых прав с перечнем лишних.
- Перечень слабых мест с оценкой риска и объяснением.
- План устранения с мерами, ответственными, сроками и проверкой результата.
- Вывод о том, какие три слабых места опаснее всего и почему.

## Критерии оценки

- Инвентаризация учётных записей выполнена, общие записи найдены, до 15 баллов.
- Парольная политика проверена, поиск паролей в файлах выполнен, до 15 баллов.
- Права сверены с ролями, лишние разрешения перечислены, до 20 баллов.
- Журналы и резервные копии проверены по фактам, до 20 баллов.
- Перечень слабых мест содержит оценку риска и объяснение, до 15 баллов.
- План устранения содержит меру, срок, ответственного и проверку, до 15 баллов.

Чек-лист без фактов и план без проверки результата возвращаются на доработку.
