## Цель работы

Научиться проверять состояние учебной СУБД и проходить полный цикл копирования: снять полную копию, зафиксировать изменения, снять разностную копию, восстановить обе на тестовый экземпляр и сверить данные.

Результат работы это протокол с четырьмя таблицами: состояние экземпляра, список копий с контрольными суммами, сверка данных и отклонения с мерами. Протокол заканчивается выводом о том, пригодна ли копия для восстановления.

## Оборудование и программное обеспечение

- Компьютер с Windows 10 или 11, PowerShell и браузером.
- XAMPP 8.5.12 с MySQL или MariaDB и phpMyAdmin, панель управления XAMPP запущена.
- Учебная база sklad с таблицами orders, order_lines, stock и тестовыми данными.
- Учебная учётная запись MySQL с правами на создание баз и чтение данных.
- Папка D:\backup для файлов копий, не менее 1 ГБ свободного места.
- Word для протокола, калькулятор или Excel для сверки сумм.

## Краткие теоретические сведения

Состояние экземпляра проверяют до копирования. Если экземпляр перегружен, копия растянется на всё окно и создаст лишнюю нагрузку. Если на диске мало места, копия оборвётся на середине, а скрипт вернёт ошибку, которую легко пропустить.

Полная копия содержит все таблицы базы. Логическая копия создаётся программой mysqldump: она читает данные и записывает набор SQL-команд, который создаёт таблицы и заполняет их. Параметр single-transaction снимает согласованный снимок, не блокируя запись на всё время работы.

Разностная копия содержит изменения после полной. В рабочей схеме её роль выполняет двоичный журнал: он записывает каждую операцию, и поверх полной копии применяются события до нужного момента. В учебном стенде двоичный журнал может быть отключён, поэтому разностная копия снимается как дамп строк, изменившихся после полной копии. Смысл тот же: восстанавливается она поверх полной, а не сама по себе.

Контрольная сумма защищает от незамеченного повреждения файла. Сумма считается по готовому файлу копии и записывается в протокол. Если через месяц файл изменился, сумма не совпадёт, и это видно до восстановления.

Сверка данных обязательна. Сравнивают число строк в ключевых таблицах и суммы по количественным столбцам. Совпадение числа строк при разных суммах означает, что часть строк заменилась, а часть потерялась.

## Ход работы

### Шаг 1. Подготовьте протокол и папку

Создайте в Word документ «Протокол копирования и восстановления базы sklad». В шапке укажите дату, фамилию, стенд, версию MySQL из phpMyAdmin и имя базы.

Создайте папку для копий и таблицу для записей о файлах.

```powershell
New-Item -ItemType Directory -Path D:\backup -Force
```

|---|---|---|---|---|
| полная | sklad_full.sql | | | |
| разностная | sklad_diff.sql | | | |

### Шаг 2. Проверьте состояние экземпляра

Откройте phpMyAdmin или командную строку MySQL и выполните запросы.

```sql
SHOW STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Uptime';
SELECT table_schema, ROUND(SUM(data_length + index_length) / 1024 / 1024, 1) AS mb
FROM information_schema.tables
WHERE table_schema = 'sklad'
GROUP BY table_schema;
SHOW TABLE STATUS FROM sklad;
```

Заполните таблицу состояния. Нормы возьмите из лекции: соединения до 70 процентов лимита, свободное место на диске не ниже 15 процентов, время работы больше суток.

| Показатель | Команда | Норма | Факт |
|---|---|---|---|
| соединения | SHOW STATUS LIKE 'Threads_connected' | до 70 процентов лимита | |
| лимит | SHOW VARIABLES LIKE 'max_connections' | 151 и выше | |
| размер базы | запрос к information_schema | известен и стабилен | |
| свободное место | проводник, свойства диска | не ниже 15 процентов | |
| журнал ошибок | файл в каталоге данных | нет ошибок за сутки | |

Откройте журнал ошибок в каталоге C:\xampp\mysql\data и найдите последние записи. Запишите в протокол, что было при последнем запуске и есть ли ошибки за сутки.

### Шаг 3. Снимите полную копию

Выполните дамп базы в файл.

```powershell
& C:\xampp\mysql\bin\mysqldump.exe -u root sklad `
  --single-transaction --routines --triggers `
  --result-file=D:\backup\sklad_full.sql

Get-Item D:\backup\sklad_full.sql | Select-Object Length, LastWriteTime
Get-FileHash D:\backup\sklad_full.sql -Algorithm SHA256
```

Запишите размер, время и хеш в таблицу копий. Откройте начало файла в VS Code и убедитесь, что там есть команды CREATE TABLE и INSERT: пустой или обрезанный файл видно сразу.

Если mysqldump выдал ошибку доступа, проверьте имя пользователя и права. Сообщение «Access denied» означает проблему с учётной записью, а не с базой.

### Шаг 4. Внесите контрольные изменения

Изменения нужны, чтобы разностная копия отличалась от полной. Внесите их через phpMyAdmin и запишите, что именно сделали.

```sql
INSERT INTO orders (client_id, created_at, updated_at, status, total)
VALUES (17, NOW(), NOW(), 'new', 48200.00);

UPDATE stock SET qty = qty - 3, updated_at = NOW()
WHERE product_id = 12 AND warehouse_id = 2;

UPDATE orders SET status = 'paid', updated_at = NOW()
WHERE id = 1043;
```

Запишите в протокол три факта: номер нового заказа, остаток по товару 12 на складе 2 до и после, старый и новый статус заказа 1043. Эти значения понадобятся при сверке.

### Шаг 5. Снимите разностную копию

Снимите дамп строк, изменившихся после полной копии. Время начала полной копии возьмите из шага 3.

```powershell
& C:\xampp\mysql\bin\mysqldump.exe -u root sklad `
  --no-create-info --replace --skip-triggers `
  --where="updated_at >= '2026-11-05 10:00:00'" `
  orders stock `
  --result-file=D:\backup\sklad_diff.sql

Get-FileHash D:\backup\sklad_diff.sql -Algorithm SHA256
```

Ключ replace превращает INSERT в REPLACE: при восстановлении изменённая строка заменит старую, а не вызовет ошибку дубликата ключа. Ключ no-create-info убирает команды создания таблиц, они уже есть в полной копии.

Если двоичный журнал включён, дополнительно выполните SHOW MASTER STATUS и запишите имя файла и позицию. Это точка, с которой в рабочей схеме применялись бы события журнала.

### Шаг 6. Восстановите на тестовый экземпляр

Создайте отдельную базу и загрузите в неё полную копию, затем разностную.

```powershell
& C:\xampp\mysql\bin\mysql.exe -u root -e "CREATE DATABASE sklad_restore;"
cmd /c "C:\xampp\mysql\bin\mysql.exe -u root sklad_restore < D:\backup\sklad_full.sql"
cmd /c "C:\xampp\mysql\bin\mysql.exe -u root sklad_restore < D:\backup\sklad_diff.sql"
```

Замерьте время каждого шага. Сумма времени и есть практическая оценка RTO для этой базы: именно столько займёт восстановление, если считать без поиска копии и проверки приложения.

Если загрузка остановилась на ошибке, прочитайте строку с номером: чаще всего это отсутствующая таблица или несовпадение кодировки. Исправлять копию вручную нельзя, нужно понять причину и переснять дамп.

### Шаг 7. Сверьте данные и оформите вывод

Сравните источник и восстановленную базу по трём таблицам.

```sql
SELECT 'orders' AS tbl, COUNT(*) AS rows_cnt, SUM(total) AS total_sum FROM sklad.orders
UNION ALL
SELECT 'order_lines', COUNT(*), SUM(qty) FROM sklad.order_lines
UNION ALL
SELECT 'stock', COUNT(*), SUM(qty) FROM sklad.stock;

SELECT 'orders' AS tbl, COUNT(*) AS rows_cnt, SUM(total) AS total_sum FROM sklad_restore.orders
UNION ALL
SELECT 'order_lines', COUNT(*), SUM(qty) FROM sklad_restore.order_lines
UNION ALL
SELECT 'stock', COUNT(*), SUM(qty) FROM sklad_restore.stock;

CHECKSUM TABLE sklad.orders, sklad.stock;
CHECKSUM TABLE sklad_restore.orders, sklad_restore.stock;
```

Заполните таблицу сверки. Расхождение по числу строк означает, что разностная копия не применилась. Расхождение по сумме при равном числе строк означает, что заменились не все изменённые строки.

| Таблица | Строк в источнике | Строк в копии | Сумма в источнике | Сумма в копии | Расхождение |
|---|---|---|---|---|---|
| orders | | | | | |
| order_lines | | | | | |
| stock | | | | | |

Проверьте три контрольных значения из шага 4: новый заказ есть в копии, остаток товара 12 совпадает, статус заказа 1043 равен paid. Если все три совпали и суммы сошлись, копия пригодна.

Заполните таблицу отклонений. Даже при успешном восстановлении отклонения бывают: копия дольше окна, размер вырос, хеш не совпал при повторной проверке.

| Отклонение | Причина | Риск | Мера |
|---|---|---|---|
| | | | |

Вывод формулируется одной фразой с числами: «Полная копия 9,2 ГБ и разностная 1,4 ГБ восстановлены за 11 минут, число строк и суммы совпали по трём таблицам, копия пригодна». Фраза «копия создана успешно» выводом не является: она не подтверждает, что из неё можно восстановиться.

## Что сдать

- Протокол в Word с шапкой, датой и исполнителем.
- Таблицу состояния экземпляра с фактами и нормами.
- Таблицу копий с размерами, временем и контрольными суммами SHA256.
- Файлы sklad_full.sql и sklad_diff.sql, сохранённые в папке D:\backup.
- Таблицу сверки по трём таблицам с суммами и расхождениями.
- Таблицу отклонений и вывод о пригодности копии с числами.

## Критерии оценки

- Состояние экземпляра проверено по пяти показателям, до 20 баллов.
- Полная копия снята с single-transaction, хеш посчитан, до 20 баллов.
- Разностная копия содержит только изменения и применяется поверх полной, до 20 баллов.
- Восстановление выполнено на отдельную базу, время замерено, до 15 баллов.
- Сверка проведена по числу строк и суммам, расхождения объяснены, до 15 баллов.
- Вывод содержит числа и подтверждает пригодность копии, до 10 баллов.

Работа без сверки данных возвращается на доработку: созданная копия без проверки не подтверждает ничего.
