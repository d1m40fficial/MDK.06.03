## Цель работы

Во вторник 27 октября в 09:12 кладовщики «Северного склада» начали сообщать, что «Склад+» не сохраняет заказы. Страница открывается, справочники работают, но при нажатии «Сохранить» появляется сообщение об ошибке. К 09:41 поступило шесть обращений, и в каждом речь о заказе, который пришлось записывать на бумагу.

Цель работы: разобрать журналы учебного стенда, найти все записи об инциденте по времени и коду, собрать единую хронологию из четырёх источников и назвать причину сбоя. Результат работы это набор журналов, таблица событий по минутам, выписка с хронологией и вывод о причине.

## Оборудование и программное обеспечение

- Персональный компьютер с Windows 10 и VS Code.
- Python 3 из комплекта VS Code, модули `pathlib`, `re`, `collections` из стандартной библиотеки.
- PowerShell для поиска по файлам.
- XAMPP 8.5.12 с Apache и MySQL, файл `C:\xampp\apache\conf\httpd.conf` для проверки настроек.
- Word или Excel для оформления выписки.
- Рабочая папка `C:\sklad\logs`.

## Краткие теоретические сведения

**Журнал** это последовательность записей об событиях с общими полями. Для разбора важны пять полей: время, источник, уровень, событие и контекст. В учебном стенде каждое поле присутствует, поэтому записи можно фильтровать и сопоставлять.

**Источники** отвечают за разные части одной операции. Веб-сервер пишет запрос и код ответа, приложение пишет бизнес-операцию и исключение, СУБД пишет ошибку хранения, система пишет состояние служб. Ни один источник не показывает картину целиком.

**Уровень записи** говорит о серьёзности события для программы. INFO сообщает о штатной операции, WARNING о отклонении, ERROR о невыполненной операции. Уровень нужен для быстрого сужения поиска, но фильтр «только ERROR» часто скрывает начало сбоя.

**Метка времени** позволяет выстроить события в ряд. Форматы различаются: Apache пишет `27/Oct/2026:09:11:58 +0300`, приложение пишет `2026-10-27T09:11:58.409+03:00`, MySQL пишет `2026-10-27T09:11:57.884512+03:00`. Смещение `+03:00` означает московское время, поэтому все три записи сравнимы напрямую.

**Код ошибки** это короткий признак, по которому ищут причину. Код ответа 500 означает ошибку на стороне сервера. `errno 28` в системном вызове означает нехватку места на устройстве. `SQLSTATE[HY000]` обозначает общую ошибку СУБД. Код сужает поиск лучше, чем слово «ошибка».

**Хронология** это таблица, где записи разных источников стоят в порядке времени. Хронология показывает не только «что сломалось», но и «что произошло раньше»: сначала закончилось место, затем СУБД не смогла записать временный файл, затем приложение вернуло исключение, затем веб-сервер отдал код 500.

**Выписка из журнала** это документ для обращения или отчёта. В неё включают окно времени, отфильтрованные строки, таблицу событий, причину и меры. Выписка не заменяет полный журнал, но позволяет коллеге повторить разбор.

**Ложный след** это событие, которое совпало по времени, но не связано с инцидентом. В полном журнале рядом с ошибками всегда есть штатные записи: перезапуск Apache по расписанию, вход администратора, плановая задача. Их отсекают окном времени и проверкой повтора: событие, которое случается каждый день в одно и то же время, редко объясняет разовый сбой. Поэтому в хронологию попадают только записи, которые меняют состояние системы.

### Шаг 3. Найдите ответы 500 в журнале доступа

Отфильтруйте записи с кодом 500 и постройте счёт по минутам. Сначала посмотрите строки глазами.

```powershell
Select-String -Path C:\sklad\logs\access.log -Pattern ' 500 '
```

Затем посчитайте коды и минуты скриптом.

```python
import re, collections
rows = []
for line in open(r"C:\sklad\logs\access.log", encoding="utf-8"):
    m = re.search(r"\[([^\]]+)\] \"(\S+) (\S+)[^\"]*\" (\d{3})", line)
    if m:
        rows.append((m.group(1), m.group(2), m.group(3), m.group(4)))
print("всего запросов:", len(rows))
print("коды:", dict(collections.Counter(r[3] for r in rows)))
print("минуты с ошибкой:", dict(collections.Counter(r[0][12:17] for r in rows if r[3] == "500")))
```

Заполните таблицу по результату.

| Минута | Запросов с кодом 500 | Путь |
|---|---|---|
| 09:11 | | |
| 09:12 | | |
| 09:13 | | |
| 09:15 | | |
| 09:22 | | |
| 09:31 | | |
| 09:40 | | |

Обратите внимание: главная страница и справочник отдавались с кодом 200. Значит, веб-сервер работал, и версия «сервер недоступен» отпадает. Счёт по минутам показывает, что ошибки повторялись с 09:11 до 09:40, а не появились один раз. Повторяемость важна: разовый сбой объясняют случайностью, повторяющийся сбой имеет постоянную причину.

### Шаг 8. Подтвердите причину и оформите выписку

Сравните объём журналов с освободившимся местом. Перемещено 31,40 и 6,80 гигабайта, то есть 38,20 гигабайта, а свободное место выросло с 0,00 до 38,20 гигабайта. Числа сходятся, значит место освободили именно журналы.

Проверьте настройку ротации в `httpd.conf`. Найдите строки `CustomLog` и `ErrorLog`.

```powershell
Select-String -Path C:\xampp\apache\conf\httpd.conf -Pattern 'CustomLog|ErrorLog'
```

| Проверка | Результат | Вывод |
|---|---|---|
| Свободное место в 09:11 | 0,02 ГБ | |
| Объём `access.log` | 31,40 ГБ | |
| Объём `error.log` | 6,80 ГБ | |
| Ротация в `httpd.conf` | нет `rotatelogs` | |
| Срок хранения журналов | не настроен | |

Причина сбоя: журналы Apache росли без ротации и заняли почти весь диск. СУБД не смогла создать временный файл, поэтому сохранение заказов завершалось ошибкой. После перемещения журналов на внешний диск место освободилось и запись восстановилась.

Оформите выписку на одну страницу Word. В ней укажите номер обращения, окно времени, пять отфильтрованных строк, таблицу хронологии, причину и три меры: настроить `rotatelogs` с хранением 30 дней, вынести журналы на отдельный раздел, поставить оповещение при заполнении диска на 80 процентов. Удалять журналы целиком нельзя: вместе с ними теряется доказательство причины. Их перемещают на отдельный носитель и хранят по регламенту.
