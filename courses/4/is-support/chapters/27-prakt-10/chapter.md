## Цель работы

Научиться описывать доступы так, чтобы их можно было проверить: построить матрицу ролей для «Северного склада», найти в выданных доступах лишние права, оформить заявку на доступ, выполнить её в учебной базе и зафиксировать изменения в журнале.

Результат работы это четыре артефакта: матрица доступа, заполненная заявка, журнал изменений доступов и вывод о найденных избыточных правах с мерами.

## Оборудование и программное обеспечение

- Компьютер с Windows 10 или 11, браузер, PowerShell, Word и Excel.
- XAMPP 8.5.12 с MySQL или MariaDB и phpMyAdmin, панель управления XAMPP запущена.
- Учебная база sklad с таблицами orders, order_lines, stock и справочником пользователей.
- Учётная запись MySQL с правами создавать пользователей и роли.

## Краткие теоретические сведения

Доступ описывают двумя сущностями. Роль это именованный набор прав на объекты, учётная запись это человек или служба с назначенной ролью. Пока права выдаются роли, матрица остаётся проверяемой: роли сотрудника сравнивают с его должностью.

Минимальные привилегии означают, что роль получает только нужные действия над нужными объектами. Кладовщику нужны чтение остатков своего склада и создание документов приёмки, а удаление заказов и закупочные цены не нужны, даже если выдать их несложно.

Лишние права накапливаются по трём причинам: сотрудника перевели, а роль не сняли; доступ выдали временно и забыли про срок; права добавили напрямую в обход роли. Каждая причина оставляет след в журнале, поэтому его ведут с первого дня.

Заявка на доступ содержит фамилию и подразделение, объект, действие, причину, срок и согласователя. Без срока заявка не принимается. Отзыв доступа оформляется так же, как выдача: с основанием и подписью руководителя.

Блокировка отличается от удаления: заблокированная запись остаётся в системе, но войти под ней нельзя, а удаление стирает историю действий. Поэтому при увольнении сначала блокируют, а удаляют через тридцать дней.

## Ход работы

### Шаг 1. Подготовьте отчёт и исходные данные

Создайте в Word документ «Отчёт по доступам ООО "Северный склад"». В шапке укажите дату, фамилию, стенд и имя базы.

Возьмите список сотрудников и выданных ролей. В учебном кейсе он такой.

| Логин | Сотрудник | Должность | Роли в системе | Примечание |
|---|---|---|---|---|
| ivanova.ao | Иванова А. О. | менеджер по продажам | Менеджер, Бухгалтер | подменяла коллегу в июле |
| petrov.vs | Петров В. С. | кладовщик, Тверь | Кладовщик, Администратор ИС | настраивал принтер |
| sidorova.en | Сидорова Е. Н. | бухгалтер | Бухгалтер, Менеджер | помогала с заказами |
| kuznetsov.dm | Кузнецов Д. М. | кладовщик, Тула | Кладовщик | уволен 12.10 |
| sklad-service-backup | служба копирования | сервисная запись | Администратор ИС | владелец не указан |
| morozov.ii | Морозов И. И. | стажёр | Менеджер, прямой доступ к закупочным ценам | принят 01.11 |

Скопируйте таблицу в отчёт.

### Шаг 2. Постройте матрицу доступа

Нарисуйте таблицу, где строки это роли, столбцы это объекты. Используйте обозначения: Ч для чтения, С для создания, И для изменения, У для удаления, А для администрирования. Пустая ячейка означает запрет.

| Роль | Заказы | Остатки | Приёмка | Отгрузка | Закупочные цены | Отчёты | Пользователи |
|---|---|---|---|---|---|---|---|
| Кладовщик | | | | | | | |
| Менеджер по продажам | | | | | | | |
| Бухгалтер | | | | | | | |
| Администратор ИС | | | | | | | |
| Инженер поддержки | | | | | | | |
| Аудитор | | | | | | | |

Заполните матрицу по правилам кейса.

- Кладовщик читает остатки и заказы, создаёт и изменяет приёмку и отгрузку, видит отчёты только по своему складу.
- Менеджер по продажам создаёт и изменяет заказы, читает остатки и отгрузку, видит отчёты. Закупочные цены ему недоступны.
- Бухгалтер читает все документы и закупочные цены, видит отчёты, но не меняет заказы.
- Администратор ИС читает все объекты, управляет пользователями и видит журнал действий.
- Инженер поддержки читает объекты и журнал, но не меняет данные клиента и не управляет пользователями.
- Аудитор только читает, включая журнал действий, и ничего не меняет.

Проверьте матрицу двумя вопросами: может ли роль сделать лишнее и хватает ли ей прав. Запишите в отчёт по примеру на каждый ответ.

Сравните таблицу сотрудников с матрицей. В журнале выдачи доступов только факты: дата, кому, что выдали и на каком основании.

Для каждой находки запишите риск одной фразой: что сможет сделать человек, у которого осталось это право. Например: «право DELETE на orders позволит стереть заказы за любой период, восстановление займёт часы».

### Шаг 4. Оформите заявку на доступ

Заполните заявку на нового сотрудника: кладовщик Калужского склада Никитин П. А. выходит 05.11, ему нужны приёмка и отгрузка своего склада.

| Поле заявки | Значение |
|---|---|
| Фамилия, имя, отчество | |
| Подразделение и должность | |
| Объект доступа | |
| Требуемое действие | |
| Причина | |
| Срок | |
| Согласователь | |
| Дата и подпись заявителя | |

Отдельно заполните вторую заявку на отзыв: у Петрова В. С. снимается роль Администратор ИС, потому что настройка принтера закончена. В заявке на отзыв укажите основание и дату.

Проверьте обе заявки по шести обязательным полям. Если хотя бы одно поле пустое, заявка возвращается заявителю, а доступ не выдаётся.

### Шаг 5. Выполните заявку в учебной базе

Роль это именованный набор прав. Пример: роль аудитора, которая только читает заказы и остатки.

```sql
CREATE ROLE 'auditor';
GRANT SELECT ON sklad.orders TO 'auditor';
GRANT SELECT ON sklad.stock TO 'auditor';
SHOW GRANTS FOR 'auditor';
```

В выводе SHOW GRANTS будет строка GRANT USAGE ON *.* и два GRANT SELECT. Если появилось право на другую таблицу, роль собрана с ошибкой.

Соберите роль кладовщика по матрице из шага 2: команды те же, объекты orders, stock, receipts и shipments, набор действий возьмите из матрицы.

Создайте учётную запись по заявке и назначьте роль.

```sql
CREATE USER 'nikitin.pa'@'localhost' IDENTIFIED BY 'Uchebnyj-2026';
GRANT 'kladovshchik' TO 'nikitin.pa'@'localhost';
SET DEFAULT ROLE 'kladovshchik' TO 'nikitin.pa'@'localhost';
SHOW GRANTS FOR 'nikitin.pa'@'localhost';
```

Проверьте результат: в выводе SHOW GRANTS должна быть роль kladovshchik и не должно быть прав на users, закупочные цены и удаление заказов. Лишнее право отзовите командой REVOKE и запишите это в журнал.

Если в вашей версии MariaDB роли работают иначе, выдайте те же права напрямую и отметьте в отчёте, что матрица остаётся источником истины.

### Шаг 6. Снимите лишние права и заблокируйте уволенного

Выполните решения из шага 3. Синтаксис команд показан на условной учётной записи temp.operator.

```sql
REVOKE 'auditor' FROM 'temp.operator'@'localhost';
ALTER USER 'temp.operator'@'localhost' ACCOUNT LOCK;
```

Свои команды составьте по находкам: на каждую лишнюю роль REVOKE, уволенному сотруднику ACCOUNT LOCK.

Проверьте блокировку: попробуйте подключиться под записью уволенного. Ошибка доступа это ожидаемый результат, запишите её текст в отчёт.

```sql
SELECT user, host, account_locked FROM mysql.user
WHERE user IN ('kuznetsov.dm', 'petrov.vs', 'nikitin.pa');
```

Убедитесь, что у Петрова осталась только роль кладовщика, а у Никитина ровно одна роль. Заблокированную запись не удаляйте: она понадобится для разбора действий.

### Шаг 7. Заполните журнал изменений доступов

Журнал это доказательство того, что доступ выдан по заявке, а не по устной просьбе.

| Дата | Номер заявки | Логин | Действие | Роль | Основание | Кто выполнил | Проверка |
|---|---|---|---|---|---|---|---|
| 05.11 | 3-2026 | nikitin.pa | создание | Кладовщик | заявка на приём | инженер второй линии | SHOW GRANTS |
| | | | | | | | |
| | | | | | | | |
| | | | | | | | |

Первая строка это образец формы. Остальные строки заполните по своим действиям из шагов 5 и 6.

В столбце «Проверка» укажите, чем подтвердили результат: вывод SHOW GRANTS, отказ во входе, запрос к mysql.user. Без подтверждения строка считается невыполненной.

### Шаг 8. Сформулируйте вывод

Соберите вывод из трёх частей: сколько избыточных прав найдено и у кого, какие меры приняты и чем подтверждены, что изменить в процессе.

Числа возьмите из своих таблиц. Пример формы на другом кейсе: «Проверено восемь записей, избыточные права найдены у двух, сняты обе роли, блокировка подтверждена отказом во входе. Предложено указывать срок в заявке и сверять права раз в квартал».

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

| Оценка | Условие |
|---|---|
| 5 | Работа выполнена полностью и самостоятельно, все пункты ниже выполнены |
| 4 | Работа выполнена, есть 1 или 2 незначительных замечания |
| 3 | Работа выполнена частично, есть существенные замечания |
| 2 | Работа не выполнена |
| 1 | Работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления |

Что проверяется:
- Матрица заполнена по правилам кейса, пустые ячейки обозначают запрет.
- Избыточные права найдены у всех шести учётных записей.
- Заявки содержат шесть обязательных полей и корректный срок.
- Роль и учётная запись созданы в базе, права проверены запросом.
- Лишние роли сняты, уволенный заблокирован, блокировка проверена входом.
- Журнал заполнен с основанием и подтверждением, вывод содержит числа.

Работа без проверки выданных прав возвращается на доработку: созданная роль без запроса SHOW GRANTS ничего не доказывает.
