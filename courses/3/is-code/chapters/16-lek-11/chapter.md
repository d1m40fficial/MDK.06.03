## Накладная без буквы

В 07:20 бухгалтер «Северного склада» открывает файл `nakladnaya-2210.csv` в Excel. В колонке площадки вместо «Тула» стоит `РўСѓР»Р°`, вместо «Калуга» набор странных символов. Суммы и артикулы на месте, а названия городов читать невозможно.

Файл при этом не испорчен. Четыре буквы «Тула» записаны в него восемью байтами, и эти байты лежат ровно там, куда их положила программа. Испорчена только договорённость о том, как их читать: программа записала текст в UTF-8, а Excel открыл файл в другой кодировке.

Вторая история того же дня. В 23:50 администратор выключил сервер, и в журнале `priemka.log` не хватает последних двенадцати строк. Программа вызывала запись после каждой приёмки, но не сбрасывала буфер, поэтому часть строк осталась в памяти процесса и исчезла вместе с ним.

Обе истории стоят денег. Из-за нечитаемых городов накладную возвращают поставщику и оформляют заново. Из-за пропавшего хвоста журнала нельзя доказать, что последние двенадцать приёмок действительно были, и остатки приходится пересчитывать вручную. Ни та, ни другая ошибка не связана с логикой склада: обе выросли из договорённости о файле.

**Файл это последовательность байтов плюс договорённость, как их читать: путь, кодировка, режим открытия и момент сброса на диск.** Пока все четыре части совпадают у писателя и читателя, данные доходят. Как только одна расходится, появляются ромбики, пустые строки или пропавший хвост журнала.

## Байты и символы

Строка в Python хранит символы, а файл на диске хранит байты. Преобразование между ними называется кодированием. `encode` переводит строку в байты, `decode` возвращает байты в строку. Пока эти операции делают одной и той же таблицей, текст читается правильно.

| Слово | Символов | Байт в UTF-8 | Байт в cp1251 |
|---|---|---|---|
| `Тула` | 4 | 8 | 4 |
| `Москва` | 6 | 12 | 6 |
| `Калуга` | 6 | 12 | 6 |

Кириллица в UTF-8 занимает два байта на букву, в cp1251 один. Поэтому русский текст в UTF-8 тяжелее, но зато одинаково читается на Windows, Linux и в веб-странице. cp1251 это старая однобайтовая кодировка, которая ещё встречается в выгрузках из бухгалтерских программ.

```python
text = "Тула"
print(len(text), "символа")
print(len(text.encode("utf-8")), "байт в UTF-8")
print(len(text.encode("cp1251")), "байта в cp1251")
print(text.encode("utf-8"))
print(text.encode("cp1251"))
```

Вывод показывает, что одна и та же строка даёт разные последовательности байтов:

```text
4 символа
8 байт в UTF-8
4 байта в cp1251
b'\xd0\xa2\xd1\x83\xd0\xbb\xd0\xb0'
b'\xd2\xf3\xeb\xe0'
```

Теперь прочитаем те же байты не той кодировкой. Ошибка не в данных, а в паре «байты плюс таблица».

```python
text = "Тула"
raw = text.encode("utf-8")
print("байты UTF-8:", raw)
print("прочитано как cp1251:", raw.decode("cp1251"))

cp = text.encode("cp1251")
print("байты cp1251:", cp)
try:
    print(cp.decode("utf-8"))
except UnicodeDecodeError as err:
    print("ошибка чтения:", err.reason, "на байте", err.start)
```

Первая строка даёт ровно те ромбики, которые увидел бухгалтер. Вторая попытка читать cp1251 как UTF-8 заканчивается ошибкой, потому что последовательность байтов недопустима для этой кодировки.

```text
байты UTF-8: b'\xd0\xa2\xd1\x83\xd0\xbb\xd0\xb0'
прочитано как cp1251: РўСѓР»Р°
байты cp1251: b'\xd2\xf3\xeb\xe0'
ошибка чтения: invalid continuation byte на байте 0
```

Отсюда практическое правило: **кодировку указывают явно и с обеих сторон**. Если файл создаёт ваша программа, она же и читает его в той же кодировке. Если файл приходит извне, кодировку выясняют по источнику или по первым байтам, а не угадывают.

Обратная ошибка возникает при записи, когда символ нельзя представить выбранной кодировкой. Эмодзи или длинное тире в cp1251 не помещаются в один байт, и Python поднимает `UnicodeEncodeError`. UTF-8 принимает любой символ Unicode, поэтому для текста с произвольными знаками выбирают именно её.

Отдельная деталь это BOM, невидимый маркер в начале файла. Некоторые программы на Windows пишут его перед текстом UTF-8. Маркер занимает три байта: `EF BB BF`. В редакторе он не виден, но в сравнении строк участвует. Python читает такой файл с кодировкой `utf-8-sig`, которая маркер отбрасывает. Если открыть файл как `utf-8`, BOM останется первым символом первой строки, и сравнение заголовка с ожидаемым не сработает.

## Путь: где именно лежит файл

Путь бывает абсолютным и относительным. Абсолютный отсчитывается от корня диска или от корневой папки, относительный от текущей рабочей папки процесса. Одна и та же строка `data/priemka.log` означает разные файлы в зависимости от того, откуда запущена программа.

| Запись | Что означает |
|---|---|
| `priemka.log` | файл в текущей рабочей папке |
| `data/priemka.log` | подпапка `data` внутри рабочей папки |
| `../logs/priemka.log` | папка `logs` на уровень выше |
| `Path(__file__).parent / "data"` | папка `data` рядом с файлом программы |

В Python работа с путями удобнее через `pathlib`. Объект `Path` сам подставляет разделитель своей платформы, умеет выделять папку, имя и расширение и не требует ручной склейки строк.

```python
import io
from pathlib import Path

path = Path("data") / "priemka.log"
print("путь:", path)
print("папка:", path.parent)
print("имя:", path.name)
print("расширение:", path.suffix)
print("размер буфера:", io.DEFAULT_BUFFER_SIZE, "байт")
```

На Windows путь печатается с обратной косой чертой, хотя в коде стояла прямая:

```text
путь: data\priemka.log
папка: data
имя: priemka.log
расширение: .log
размер буфера: 8192 байт
```

Главная ловушка относительного пути в том, что рабочая папка не равна папке скрипта. VS Code обычно запускает программу из корня проекта, а терминал может стоять в другой папке. Программа, которая вчера находила `data/priemka.log`, сегодня сообщает, что файла нет, хотя файл лежит на месте.

Если файл должен лежать рядом с модулем, путь строят от `__file__`. Если файл задаётся настройкой, путь приходит из конфигурации. Если файл выбирает пользователь, путь приходит из диалога. Угадывать рабочую папку нельзя.

Метод `resolve()` приводит путь к абсолютному и убирает `..`, поэтому его полезно вызывать перед записью в журнал: в сообщении об ошибке появится полный путь, и сразу видно, куда именно смотрела программа. Для вывода пользователю абсолютный путь часто слишком длинный, но для диагностики он незаменим.

## Кодировка на практике

Правило простое: в каждом вызове `open` есть `encoding`. Если его нет, Python берёт кодировку по умолчанию, а она зависит от платформы, локали и режима запуска. На одной машине файл прочитается, на другой тот же код даст ромбики или `UnicodeDecodeError`.

Для обмена данными выбирают UTF-8. Это кодировка по умолчанию для веба, JSON, большинства API и современных редакторов. cp1251 оставляют только там, где её требует внешняя программа, и тогда её указывают явно в обоих концах обмена.

| Ситуация | Кодировка | Почему |
|---|---|---|
| свой журнал или выгрузка | `utf-8` | одинаково читается на любой машине |
| файл с BOM из Windows | `utf-8-sig` | маркер не попадает в первую строку |
| обмен с 1С или старой бухгалтерией | `cp1251` | так требует принимающая сторона |
| таблица для Excel с русским текстом | `utf-8-sig` | Excel распознаёт кодировку по BOM |

Для CSV добавляют `newline=""`. Без него Python может превратить перевод строки `\r\n` в `\r\r\n`, и таблица разъедется на лишние пустые строки. Это не ошибка кодировки, а ошибка перевода строк, но симптом похож: строк стало больше, чем было.

Параметр `errors` задаёт поведение при неподходящем байте. Значение `strict` поднимает ошибку, `replace` ставит вопросительный знак, `ignore` молча выбрасывает байт. `replace` допустим при показе черновика, `ignore` почти никогда: он превращает потерю данных в незаметную.

## Контекстный менеджер

Открытый файл занимает дескриптор операционной системы. Если его не закрыть, дескрипторы заканчиваются, а буфер не сбрасывается на диск. Конструкция `with` закрывает файл при любом выходе из блока, включая исключение.

```python
from pathlib import Path

path = Path("data") / "priemka.log"
try:
    with path.open("r", encoding="utf-8") as file:
        for number, line in enumerate(file, 1):
            print(number, line.rstrip("\n"))
except FileNotFoundError:
    print("файл не найден:", path)
```

Если файла нет, управление уходит в `except`, а сообщение называет относительный путь, по которому программа его искала. Такой вывод полезнее, чем голая трассировка: видно, что именно проверять.

```text
файл не найден: data\priemka.log
```

`with` работает не только с файлами. Так же открывают сетевые соединения, блокировки и транзакции. Смысл один: ресурс освобождается в обратном порядке и даже тогда, когда внутри блока произошла ошибка. Полагаться на сборщик мусора нельзя: момент закрытия файла в таком случае непредсказуем.

Внутри `with` файл уже открыт и готов к чтению или записи. После выхода из блока обращаться к нему нельзя, даже если переменная ещё существует. Проверка `file.closed` после блока должна давать `True`; это хороший способ убедиться, что ресурс действительно освобождён.

## Построчное чтение

У Python есть три способа прочитать текстовый файл, и они отличаются расходом памяти.

| Способ | Что делает | Память |
|---|---|---|
| `file.read()` | возвращает весь файл одной строкой | равна размеру файла |
| `file.readlines()` | возвращает список всех строк | больше размера файла |
| `for line in file` | выдаёт по одной строке | равна буферу чтения |

Разница заметна на больших файлах. Выгрузка остатков на 4800 позиций по 120 байт занимает около 560 КБ, и её можно прочитать целиком без последствий. Журнал приёмки за год может вырасти до нескольких гигабайт, и `readlines()` на нём исчерпает память задолго до конца.

Размер буфера по умолчанию 8192 байта. Файл читается кусками по 8 КБ, а не по одной строке с диска. Строка длиннее буфера тоже читается, просто буфер расширяется. Настраивать размер вручную нужно редко, но понимать, откуда берётся постоянный расход памяти, полезно.

Построчное чтение работает лениво: файл читается порциями по буферу, а цикл получает строки по мере надобности. Память при этом не зависит от размера файла.

```python
from pathlib import Path

def read_events(path):
    with path.open("r", encoding="utf-8") as file:
        for line in file:
            line = line.strip()
            if line:
                yield line

path = Path("data") / "priemka.log"
path.write_text(
    "07:40;SKU-1042;+12\n"
    "07:42;SKU-2087;+4\n"
    "\n"
    "07:45;SKU-1042;-3\n",
    encoding="utf-8",
)
for event in read_events(path):
    time, sku, delta = event.split(";")
    print(time, sku, int(delta))
```

Пустая строка пропускается, остальные разбираются на три поля:

```text
07:40 SKU-1042 12
07:42 SKU-2087 4
07:45 SKU-1042 -3
```

Функция с `yield` называется генератором. Она не читает файл целиком и не хранит список строк: каждая строка живёт до следующего шага цикла. Для журнала это важнее, чем кажется: обработка 4800 позиций и обработка десяти миллионов строк пишутся одинаково.

Снимая перевод строки, используйте `rstrip("\n")`, а не `strip()`, если пробелы в конце поля значимы. `strip()` уберёт и пробелы, и табуляцию, и тогда значение `" 12 "` превратится в `"12"` раньше, чем вы успеете его проверить. Для журнала это обычно безопасно, для текста накладной уже нет.

Номер строки удобно получать через `enumerate(file, 1)`, а не считать вручную. Тогда сообщение об ошибке называет место в файле, и поиск дефекта начинается с конкретной строки, а не с начала журнала. Для файла на 4800 позиций это экономит время, для файла на миллион строк это уже часы.

## Запись и сохранность

Режим открытия задаёт, что произойдёт с существующим файлом.

| Режим | Что делает | Когда использовать |
|---|---|---|
| `r` | читает, файл должен существовать | чтение готовых данных |
| `w` | создаёт или очищает файл | полная перезапись результата |
| `a` | дописывает в конец | журнал событий |
| `x` | создаёт, но падает, если файл есть | защита от перезаписи |
| `r+` | читает и пишет с начала | правка отдельных мест |

Ошибка с режимом `w` стоит дорого: программа открывает журнал на запись, очищает его и только потом понимает, что данных для записи нет. История операций исчезает. Для журнала нужен `a`, для полной выгрузки `w`, для файла, который нельзя потерять, `x` с проверкой существования.

Запись идёт через буфер. Текст попадает в буфер процесса, затем в буфер операционной системы, затем на диск. `flush()` сбрасывает первый буфер, `os.fsync()` просит систему записать данные на носитель.

```python
from pathlib import Path

path = Path("data") / "buffer.txt"
file = path.open("w", encoding="utf-8")
file.write("первая строка\n")
print("размер до flush:", path.stat().st_size)
file.flush()
print("размер после flush:", path.stat().st_size)
file.close()
```

Пока буфер не сброшен, файл на диске пуст, хотя программа уже выполнила запись:

```text
размер до flush: 0
размер после flush: 27
```

Именно поэтому журнал из начала лекции потерял хвост. Строки были в памяти, но не на диске. `with` сбрасывает буфер при закрытии, а аварийное завершение процесса этого не делает.

Если файл должен замениться целиком и без половинчатого состояния, пишут во временный файл, сбрасывают его на диск и переименовывают поверх старого. Переименование в пределах одной файловой системы атомарно: читатель видит либо старую версию, либо новую, но не смесь.

Временный файл должен лежать в той же папке, что и итоговый. Переименование через границу файловой системы не атомарно, и вместо замены получится копирование. Имя временного файла делают уникальным, иначе два процесса перезапишут друг друга. Для учебного проекта достаточно добавить к имени идентификатор процесса или метку времени.

```python
import os
from pathlib import Path

path = Path("data") / "ostatki.csv"
tmp = path.with_suffix(".tmp")
with tmp.open("w", encoding="utf-8", newline="") as file:
    file.write("sku;stock\n")
    file.write("SKU-1042;40\n")
    file.write("SKU-2087;12\n")
os.replace(tmp, path)
print(path.read_text(encoding="utf-8"))
print("временный файл существует:", tmp.exists())
```

После замены остаётся только итоговый файл, а временный исчезает:

```text
sku;stock
SKU-1042;40
SKU-2087;12

временный файл существует: False
```

Для журнала такой приём не нужен: журнал дописывают в конец и сбрасывают буфер после каждой записи, которую нельзя потерять. Для выгрузки остатков он обязателен: иначе при сбое посередине получится файл с половиной строк.

`flush()` не гарантирует, что данные уже на магнитном диске: он лишь передаёт их операционной системе. Для критичной записи вызывают `os.fsync(file.fileno())`, но у этого есть цена. Каждый сброс ждёт диск, поэтому тысяча строк с `fsync` после каждой превратит быструю приёмку в медленную. На практике выбирают компромисс: `flush` после каждой строки журнала и `fsync` после закрытия пакета.

Проверка результата записи это отдельный шаг. После закрытия файла полезно убедиться, что он существует и его размер больше нуля. Если места на диске не хватило, ошибка может проявиться только при закрытии, а не при вызове `write`.

## Тот же файл в C#

В C# файл открывают через `StreamReader` или `File.ReadLines`. Конструкция `using` играет роль `with`: она вызывает `Dispose` при выходе из блока, даже если внутри произошло исключение.

```csharp
using System;
using System.IO;
using System.Text;

class Program {
    static void Main() {
        Console.OutputEncoding = Encoding.UTF8;
        string path = Path.Combine("data", "priemka.log");
        int lines = 0;
        int total = 0;
        using (StreamReader reader = new StreamReader(path, Encoding.UTF8)) {
            string line;
            while ((line = reader.ReadLine()) != null) {
                if (line.Length == 0) continue;
                string[] parts = line.Split(';');
                total += int.Parse(parts[2]);
                lines++;
            }
        }
        Console.WriteLine("строк: " + lines + ", сумма изменений: " + total);
    }
}
```

На том же журнале с пустой строкой программа выдаёт:

```text
строк: 3, сумма изменений: 13
```

| Действие | Python | C# |
|---|---|---|
| Открыть с кодировкой | `open(path, encoding="utf-8")` | `new StreamReader(path, Encoding.UTF8)` |
| Гарантировать закрытие | `with` | `using` |
| Прочитать строку | `for line in file` | `reader.ReadLine()` |
| Прочитать все строки лениво | генератор | `File.ReadLines(path)` |
| Записать строку | `file.write(text)` | `writer.WriteLine(text)` |

В C# `Encoding.UTF8` это объект кодировки, а не строка с именем. Для cp1251 в .NET Framework нужен `Encoding.GetEncoding(1251)`, в .NET Core требуется зарегистрировать поставщика кодировок. Это ещё один довод в пользу UTF-8 в учебном проекте.

Метод `File.ReadLines` возвращает последовательность строк и читает файл по мере перебора, как питоновский генератор. `File.ReadAllLines` сначала загружает все строки в массив и на большом журнале ведёт себя так же расточительно, как `readlines()`. Выбор между ними тот же: потоковая обработка для больших файлов, массив для небольших, где нужен случайный доступ.

## Типичные ошибки

**Открытие без кодировки.** Код работает на машине разработчика и ломается на другой локали. Симптом: ромбики или `UnicodeDecodeError` на кириллице, при этом латиница читается. Лечение: явный `encoding` в каждом вызове.

**`readlines()` на большом файле.** Программа съедает память и падает с `MemoryError` или замедляет всю машину. Симптом: чем больше журнал, тем дольше запуск. Лечение: цикл по файлу или генератор.

**Режим `w` вместо `a`.** Журнал очищается при каждом запуске, история исчезает. Симптом: после перезапуска в файле одна строка. Лечение: `a` для дописывания и `x` там, где перезапись запрещена.

**Относительный путь от рабочей папки.** Программа находит файл в терминале и не находит в IDE. Симптом: `FileNotFoundError` при существующем файле. Лечение: путь от `__file__` или из настроек.

**`errors="ignore"`.** Битые байты молча выбрасываются, текст теряет буквы. Симптом: в отчёте слова короче, чем в источнике, ошибок нет. Лечение: `strict` и разбор причины.

**Забытый `flush` перед чтением.** Программа пишет файл, затем сразу читает его и видит пустоту. Симптом: размер 0 сразу после записи. Лечение: `with` или явный `flush`.

**Склейка строк без перевода.** Две записи превращаются в одну длинную. Симптом: число строк меньше числа событий. Лечение: `\n` в конце каждой записи и `newline=""` для CSV.

**Чтение файла, который ещё открыт на запись.** Программа пишет журнал, не закрывает его и пытается прочитать тот же файл вторым открытием. На Windows второе открытие может завершиться ошибкой доступа, а на другой системе вернёт неполные данные. Симптом: файл занят или прочитан не до конца. Лечение: закрыть писателя перед чтением или читать через тот же дескриптор после `flush`.

| Ошибка | Симптом | Лечение |
|---|---|---|
| нет `encoding` | ромбики на кириллице | указать UTF-8 |
| `readlines()` | растёт память | цикл по файлу |
| режим `w` | журнал очищен | режим `a` |
| путь от рабочей папки | файл не найден | путь от `__file__` |
| `errors="ignore"` | пропали буквы | `strict` |
| нет `flush` | файл пуст | `with` или `flush` |

## Итоги

- Файл хранит байты, а текст появляется только после декодирования известной кодировкой.
- Кодировку указывают явно с обеих сторон, для обмена выбирают UTF-8.
- Относительный путь зависит от рабочей папки, поэтому путь строят от файла программы или из настроек.
- `with` закрывает файл при любом выходе и сбрасывает буфер.
- Большой файл читают построчно, а не через `readlines()`.
- Для журнала используют режим `a` и сброс буфера, для полной выгрузки временный файл и атомарную замену.

Q: Что хранит файл на диске?
+ Последовательность байтов
- Готовые символы в кодировке Unicode
- Только текстовые строки без служебных данных
- Объекты Python в исходном виде
! Текст появляется после декодирования байтов выбранной кодировкой.

Q: Сколько байтов занимает слово «Тула» в UTF-8?
+ 8
- 4
- 6
- 2
! Каждая кириллическая буква в UTF-8 занимает два байта.

Q: Почему вместо «Тула» появились символы `РўСѓР»Р°`?
+ Байты UTF-8 прочитали как cp1251
- Файл записался в двоичном режиме
- Слово было заменено при сохранении
- Кодировка UTF-8 потеряла первую букву
! Данные целы, но декодированы другой таблицей.

Q: От чего отсчитывается относительный путь?
+ От текущей рабочей папки процесса
- От папки, где лежит файл программы
- От корня диска
- От папки с настройками Windows
! Поэтому один и тот же код находит разные файлы при разном запуске.

Q: Что делает конструкция `with` при выходе из блока?
+ Закрывает файл и сбрасывает буфер даже при исключении
- Удаляет файл с диска
- Переводит файл в режим только для чтения
- Копирует файл в резервную папку
! Освобождение ресурса не зависит от того, была ли ошибка.

Q: Какой способ чтения не загружает файл целиком?
+ Цикл `for line in file`
- `file.read()`
- `file.readlines()`
- `file.read().splitlines()`
! Цикл читает файл порциями через буфер.

Q: Что делает режим `a`?
+ Дописывает данные в конец файла
- Очищает файл и пишет заново
- Создаёт файл и падает, если он существует
- Открывает файл только для чтения
! Режим `a` сохраняет прежние записи.

Q: Зачем нужен `flush()`?
+ Сбрасывает буфер программы в операционную систему
- Меняет кодировку файла
- Удаляет временный файл
- Закрывает файл навсегда
! Без сброса данные могут остаться в памяти процесса.

Q: Что даёт запись во временный файл с последующим `os.replace`?
+ Читатель видит либо старую, либо новую версию целиком
- Файл записывается быстрее в два раза
- Кодировка определяется автоматически
- Временный файл остаётся для истории
! Замена в пределах одной файловой системы атомарна.

Q: Какие действия защищают русский текст от ромбиков?
+ Указать `encoding="utf-8"` при записи
+ Указать ту же кодировку при чтении
+ Использовать `utf-8-sig`, если в файле есть BOM
- Открыть файл без параметра кодировки
- Заменить все буквы латиницей
! Кодировка должна совпадать у писателя и читателя.

Q: Какие признаки указывают на потерю данных при работе с файлом?
+ Число строк меньше числа событий
+ В журнале нет последних записей после сбоя
+ В тексте пропали отдельные буквы
- Размер файла больше нуля
- Программа закрыла файл через `with`
! Потеря строк, хвоста и букв говорит о режиме, буфере или кодировке.

Q: Где уместно читать файл построчно?
+ Журнал приёмки за год
+ Выгрузка на десять миллионов строк
+ Файл, размер которого неизвестен заранее
- Файл настроек на двадцать строк
- Небольшой список категорий
! Построчное чтение держит память постоянной.

Q: Что произойдёт, если открыть журнал в режиме `w`?
+ Прежние записи будут удалены
- Новые записи добавятся в конец
- Программа откажется открывать файл
- Кодировка сменится на cp1251
! Режим `w` очищает файл перед записью.

Q: Как называется кодировка, которая отбрасывает маркер BOM в начале файла?
= utf-8-sig
= utf8-sig
! Она читает UTF-8 и не оставляет невидимый маркер в первой строке.

Q: Какой режим открытия дописывает данные в конец файла?
= a
= режим a
! Режим `a` сохраняет прежнее содержимое и добавляет новое.
