## Сканер в Туле

Кладовщик на площадке в Туле наводит сканер на штрихкод ячейки C-01-07. Приложение «Склад+» отправляет запрос `GET /api/stock/3` и через мгновение показывает карточку: стрейч-плёнка, 240 единиц, площадка Тула. В этот момент на сервере успевает отработать целая цепочка: сетевой сервер принимает соединение, несколько промежуточных слоёв проверяют запрос, маршрутизация выбирает нужный метод контроллера, метод обращается к хранилищу, а результат превращается в JSON.

Пользователь видит только два события: нажатие и ответ. Между ними проходит запрос, который последовательно минует ступени, заранее собранные при старте приложения. Одна ступень добавляет идентификатор запроса в журнал, другая проверяет, не истекла ли сессия, третья решает, что адрес `/api/stock/3` относится к методу `GetById`, четвёртая вызывает этот метод. Если поменять ступени местами, приложение продолжит собираться и даже запустится, но поведение изменится: часть проверок перестанет срабатывать, а ошибки будут выглядеть иначе.

Вот как выглядит обмен для этого запроса. Ответ приведён в том виде, в каком его возвращает учебный сервис:

```http
GET /api/stock/3 HTTP/1.1
Host: localhost:5248
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"id":3,"item":"Стрейч-плёнка 500 мм","category":"Упаковка","site":"Тула","cell":"C-01-07","quantity":240}
```

**Приложение ASP.NET Core это конвейер, собранный при старте: каждый запрос проходит одни и те же ступени в одном и том же порядке.** Код контроллера выполняется в середине этой цепочки. Всё, что стоит до него, готовит сведения о запросе и пользователе. Всё, что стоит после, превращает возвращённое значение в HTTP-ответ.

У «Северного склада» 120 сотрудников, четыре площадки и 4800 позиций хранения. Каждое открытие карточки товара, каждая приёмка и каждая отгрузка проходят через один и тот же конвейер. Поэтому порядок ступеней это не деталь оформления, а часть поведения системы.

::gate Что именно происходит с запросом до того, как управление попадёт в метод контроллера?

## Конвейер обработки запроса

Промежуточный слой, или middleware, это компонент, который получает запрос, может что-то с ним сделать и либо передать дальше, либо сразу вернуть ответ. Слои выстраиваются в цепочку при запуске приложения. Каждый слой знает только следующего за ним, поэтому цепочку можно собирать из независимых частей.

Минимальная программа учебного сервиса выглядит так:

```csharp
using SkladPlus.Api.Storage;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();
builder.Services.AddScoped<IStockRepository, InMemoryStockRepository>();

var app = builder.Build();

app.UseExceptionHandler("/error");
app.UseHttpsRedirection();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();
```

Первые строки создают построитель и регистрируют сервисы. Строка `builder.Build()` собирает приложение, а вызовы `Use...` задают порядок ступеней. `MapControllers()` присоединяет к конвейеру конечные точки контроллеров. Пока приложение работает, эта цепочка не меняется.

Разберём ступени по порядку.

| Порядок | Ступень | Что делает | Что ломается при перестановке |
|---|---|---|---|
| 1 | Обработчик исключений | ловит ошибки всех следующих слоёв и превращает их в ответ | исключение из верхних слоёв остаётся необработанным |
| 2 | Перенаправление на HTTPS | отвечает 307 и переводит запрос на защищённый адрес | пароль и токен могут уйти по открытому каналу |
| 3 | Статические файлы | отдаёт готовый файл и не пускает запрос дальше | запрос к картинке ищет контроллер и получает 404 |
| 4 | Маршрутизация | выбирает конечную точку по шаблону адреса | проверка прав не знает, какой метод защищать |
| 5 | Аутентификация | читает cookie или токен и заполняет сведения о пользователе | проверка прав видит анонимного пользователя |
| 6 | Авторизация | сверяет политику доступа с выбранной конечной точкой | запрещённый метод выполняется |
| 7 | Конечная точка | вызывает действие контроллера | запрос не доходит до кода |

Перед первым промежуточным слоем стоит сервер Kestrel. Он принимает TCP-соединение, разбирает строку запроса и заголовки, собирает объект `HttpContext` и только затем передаёт управление цепочке. Для учебного проекта этого достаточно. На боевом стенде перед Kestrel часто ставят обратный прокси, который завершает HTTPS и распределяет нагрузку, но правила внутри приложения не меняются.

Правило первое: обработчик исключений ставят в начало, потому что он должен оборачивать всё, что находится ниже. Если поставить его после маршрутизации, ошибка, возникшая в маршрутизации или в проверке прав, до него не дойдёт.

Правило второе: маршрутизация идёт до проверки прав. Атрибут `[Authorize]` привязан к конкретной конечной точке, а конечную точку выбирает маршрутизация. Если проверка прав окажется раньше, у неё не будет сведений о том, какой метод запрошен, и ограничение не сработает. Приложение ответит так, будто метод открыт всем.

Правило третье: аутентификация идёт до авторизации. Первая отвечает на вопрос «кто это», вторая на вопрос «что ему разрешено». Проверять права раньше, чем установлена личность, бессмысленно.

Правило четвёртое: конечная точка стоит последней. До неё запрос может быть остановлен на любой ступени. Если файл найден в папке статических файлов, контроллер уже не вызывается. Если проверка прав вернула отказ, метод контроллера не выполняется вовсе.

Собственный слой добавляют через `app.Use`. Например, слой, который помечает каждый запрос идентификатором и пишет строку в журнал:

```csharp
app.Use(async (context, next) =>
{
    var started = DateTime.UtcNow;
    context.Response.Headers["X-Request-Id"] = Guid.NewGuid().ToString("N")[..8];

    await next();

    var elapsed = DateTime.UtcNow - started;
    app.Logger.LogInformation("{Path} {Status} {Elapsed} ms",
        context.Request.Path, context.Response.StatusCode, elapsed.TotalMilliseconds);
});
```

Слой вызывает `await next()`, и только после этого управление возвращается к нему. Поэтому строку в журнал он пишет, когда ответ уже сформирован, и видит настоящий код состояния. Порядок `app.Use` важен: слой, поставленный после явного `UseEndpoints`, для совпавшего маршрута уже не выполнится, потому что конечная точка завершает цепочку. При этом `MapControllers()` только регистрирует маршруты, а завершающий слой добавляется в конец автоматически.

## Внедрение зависимостей

Контроллеру нужны хранилище, часы, журнал и настройки. Можно создать их прямо в конструкторе: `_repository = new InMemoryStockRepository()`. Тогда контроллер жёстко привязан к классу хранилища, а проверить его с подставным хранилищем уже не получится. Придётся менять код ради теста.

Внедрение зависимостей устроено иначе: класс объявляет, что ему нужно, а контейнер создаёт объект и передаёт готовую зависимость. Контроллер не знает, какой именно класс стоит за интерфейсом.

```csharp
using Microsoft.AspNetCore.Mvc;
using SkladPlus.Api.Models;
using SkladPlus.Api.Storage;

namespace SkladPlus.Api.Controllers;

[ApiController]
[Route("api/stock")]
public class StockController : ControllerBase
{
    private readonly IStockRepository _repository;

    public StockController(IStockRepository repository)
    {
        _repository = repository;
    }

    [HttpGet("{id:int}")]
    public ActionResult<StockItem> GetById(int id)
    {
        var item = _repository.Find(id);
        if (item is null)
        {
            return NotFound();
        }
        return Ok(item);
    }
}
```

Конструктор принимает интерфейс. Контейнер видит регистрацию `AddScoped<IStockRepository, InMemoryStockRepository>()` и создаёт нужный объект сам. В тесте достаточно зарегистрировать другую реализацию, и код контроллера не меняется.

Время жизни сервиса задаётся при регистрации. От него зависит, сколько экземпляров создаст контейнер и когда он их освободит.

| Время жизни | Когда создаётся | Сколько живёт | Что подходит | Чем опасно |
|---|---|---|---|---|
| Singleton | при первом обращении | до остановки приложения | кеш справочников, часы, настройки | хранит состояние между запросами |
| Scoped | один раз на HTTP-запрос | до конца запроса | репозиторий, контекст базы | попадает в singleton и живёт вечно |
| Transient | при каждом запросе зависимости | до освобождения создавшего объекта | лёгкие объекты без состояния | создаётся чаще, чем нужно |

В учебном сервисе репозиторий зарегистрирован как scoped. На каждый запрос контейнер создаёт свой экземпляр, передаёт его контроллеру и освобождает после ответа. Если тот же репозиторий открывает соединение с базой, соединение закрывается вместе с областью запроса.

Опасная комбинация называется захватом зависимости. Singleton создаётся один раз и живёт всё время работы приложения. Если ему нужен scoped сервис, контейнер вынужден создать этот сервис в корневой области и держать его до остановки. В режиме разработки проверка областей включена, и приложение сообщает об ошибке:

```text
InvalidOperationException
Cannot consume scoped service 'IStockRepository' from singleton 'StockCache'.
```

Сообщение говорит буквально: singleton `StockCache` пытается использовать scoped `IStockRepository`. Если такую проверку отключить, ошибка не исчезнет, а спрячется. Контекст базы, созданный один раз, начнёт обслуживать параллельные запросы, и появится другая ошибка: `A second operation was started on this context instance before a previous operation completed`.

Сравним с Python, где контейнера нет и время жизни задаёт программист. Небольшая модель показывает разницу между двумя режимами:

```python
class StockRepository:
    def __init__(self):
        self.calls = 0

    def next_call(self):
        self.calls += 1
        return self.calls


class Singleton:
    """Один экземпляр на всё время работы приложения."""

    def __init__(self, factory):
        self._factory = factory
        self._instance = None

    def resolve(self):
        if self._instance is None:
            self._instance = self._factory()
        return self._instance


class Scoped:
    """Новый экземпляр на каждый запрос."""

    def __init__(self, factory):
        self._factory = factory

    def begin_request(self):
        return self._factory()


single = Singleton(StockRepository)
print("singleton:", [single.resolve().next_call() for _ in range(3)])

scoped = Scoped(StockRepository)
print("scoped:", [scoped.begin_request().next_call() for _ in range(3)])
```

Вывод:

```text
singleton: [1, 2, 3]
scoped: [1, 1, 1]
```

Один и тот же класс ведёт себя по-разному. В режиме singleton счётчик накапливается, потому что все обращения получают один объект. В режиме scoped каждый запрос начинается с нового объекта, и счётчик всегда равен единице. В Python такой режим нужно помнить и соблюдать вручную. В ASP.NET Core он объявляется один раз при регистрации, и контейнер следит за ним сам.

## Конфигурация

Параметры приложения не должны быть зашиты в код. Адрес базы, размер страницы, площадка по умолчанию и ключи меняются от стенда к стенду, а код остаётся одним и тем же. В ASP.NET Core настройки собираются из нескольких источников и накладываются друг на друга.

Базовый файл `appsettings.json` лежит рядом с проектом:

```json
{
  "ConnectionStrings": {
    "Sklad": "Data Source=sklad.db"
  },
  "Stock": {
    "PageSize": 50,
    "DefaultSite": "Москва"
  }
}
```

Источники применяются в порядке от общего к частному: сначала `appsettings.json`, затем `appsettings.{Среда}.json`, затем секреты разработчика, затем переменные окружения, затем аргументы командной строки. Каждый следующий источник перекрывает предыдущий. Поэтому один и тот же код на учебной машине читает локальный файл, а на сервере берёт адрес из переменной окружения.

Строку подключения читают отдельным методом:

```csharp
var connectionString = builder.Configuration.GetConnectionString("Sklad");
var pageSize = builder.Configuration.GetValue<int>("Stock:PageSize");
```

Двоеточие в ключе означает вложенность: `Stock:PageSize` это поле `PageSize` внутри раздела `Stock`. Для группы настроек удобнее отдельный класс и шаблон параметров:

```csharp
public class StockOptions
{
    public int PageSize { get; set; } = 20;
    public string DefaultSite { get; set; } = "Москва";
}
```

```csharp
builder.Services.Configure<StockOptions>(builder.Configuration.GetSection("Stock"));
```

Контроллер получает настройки через `IOptions<StockOptions>` и обращается к свойству `Value`. Значения по умолчанию в классе важны: если раздела в файле нет, приложение не упадёт, а возьмёт разумную основу.

| Параметр | Где хранить | Почему |
|---|---|---|
| размер страницы, площадка по умолчанию | `appsettings.json` | не секрет, меняется редко |
| адрес и порт стенда | `appsettings.{Среда}.json` | различаются между стендами |
| пароль базы, ключ подписи | переменная окружения или секреты разработчика | не попадает в репозиторий |
| журнал и уровень сообщений | `appsettings.{Среда}.json` | зависит от стенда |

Пароль в `appsettings.json` это утечка, даже если файл лежит в закрытом репозитории. История Git хранит старые версии, а копия файла легко попадает в архив или в переписку. Для разработки используют хранилище секретов: команда `dotnet user-secrets init` добавляет идентификатор в проект, команда `dotnet user-secrets set "ConnectionStrings:Sklad" "..."` кладёт значение вне папки проекта. На сервере то же значение задают переменной окружения. Двойное подчёркивание заменяет двоеточие: `ConnectionStrings__Sklad`.

## Контроллер: маршрут, действие и ответ

Контроллер это класс, который принимает запрос определённого вида и возвращает результат. Атрибут `[ApiController]` включает поведение, удобное для API: автоматическую проверку модели, разбор источников данных и ответ с описанием ошибки в формате ProblemDetails. Атрибут `[Route("api/stock")]` задаёт общий префикс адресов.

```csharp
[HttpGet]
public ActionResult<IEnumerable<StockItem>> GetAll([FromQuery] string? site)
{
    var items = _repository.GetAll(site);
    return Ok(items);
}

[HttpGet("{id:int}")]
public ActionResult<StockItem> GetById(int id)
{
    var item = _repository.Find(id);
    if (item is null)
    {
        return NotFound(new ProblemDetails
        {
            Title = "Позиция не найдена",
            Detail = $"Позиция с кодом {id} отсутствует",
            Status = StatusCodes.Status404NotFound
        });
    }
    return Ok(item);
}

[HttpPost]
public ActionResult<StockItem> Create(StockItem item)
{
    var created = _repository.Add(item);
    return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
}
```

Разберём, откуда берутся значения. В методе `GetById` число `id` приходит из адреса, потому что шаблон содержит `{id:int}`. Ограничение `:int` не пропустит строку вместо числа. В методе `GetAll` параметр `site` приходит из строки запроса благодаря `[FromQuery]`: адрес `api/stock?site=Тула` даёт значение «Тула», а без параметра остаётся `null`. В методе `Create` объект собирается из тела запроса в формате JSON.

Возвращаемый тип `ActionResult<T>` позволяет вернуть либо сам объект, либо результат с кодом состояния. `Ok(item)` даёт 200 и тело с объектом. `NotFound()` даёт 404. `CreatedAtAction` даёт 201, заголовок `Location` с адресом созданной записи и тело с новым объектом. В проверенном запросе заголовок выглядел так:

```text
HTTP/1.1 201 Created
Location: http://localhost:5248/api/stock/6
```

Коды состояния это часть контракта API, а не украшение. Клиент по коду понимает, что делать дальше: показать данные, сообщить об отсутствии записи, исправить тело запроса или повторить попытку позже.

| Код | Когда возвращается | Кто формирует |
|---|---|---|
| 200 | данные найдены и переданы | действие контроллера |
| 201 | запись создана | `CreatedAtAction` |
| 204 | изменение выполнено, тела нет | `NoContent` |
| 400 | тело или параметры не прошли проверку | `[ApiController]` или действие |
| 404 | запись не найдена | действие контроллера |
| 500 | необработанная ошибка | обработчик исключений |

Если тело запроса не соответствует модели, `[ApiController]` сам возвращает 400 и перечисляет поля с ошибками. Проверка отрицательного количества в учебном сервисе дала такой ответ:

```json
{"type":"https://tools.ietf.org/html/rfc9110#section-15.5.1","title":"One or more validation errors occurred.","status":400,"errors":{"Quantity":["Количество не может быть отрицательным"]},"traceId":"00-709008c4ecfadf95ac10f08759cfb53f-000ed456f817ac62-00"}}
```

Клиент получает не просто «ошибка», а имя поля и причину. По этому ответу можно исправить форму, не читая серверный журнал.

Отдавать клиенту сущность хранилища целиком удобно только в учебном примере. В рабочем коде между хранилищем и ответом ставят отдельную модель, в которой нет служебных полей:

```csharp
public record StockItemResponse(int Id, string Item, string Site, string Cell, int Quantity);

[HttpGet("{id:int}")]
public ActionResult<StockItemResponse> GetById(int id)
{
    var item = _repository.Find(id);
    if (item is null)
    {
        return NotFound();
    }

    var response = new StockItemResponse(
        item.Id, item.Item, item.Site, item.Cell, item.Quantity);
    return Ok(response);
}
```

Запись `record` занимает одну строку и сразу задаёт неизменяемый набор полей ответа. Если завтра в таблице появится поле с внутренним кодом площадки, клиент его не увидит: модель ответа перечисляет только разрешённые поля.

Действия с обращением к базе делают асинхронными: `await _repository.GetAllAsync(site)`. Пока идёт запрос к диску, поток сервера свободен и может обслуживать другие запросы. Свойство `.Result` блокирует поток и под нагрузкой приводит к нехватке потоков: приложение отвечает всё медленнее, хотя база уже вернула данные.

::/gate

::gate Какие ошибки в конвейере и зависимостях проявляются только под нагрузкой?

## Типичные ошибки

**Толстый контроллер.** В действии одновременно проверяют права, считают остаток, пишут SQL и формируют ответ. Такой метод невозможно проверить отдельно от базы, а любое изменение правила задевает транспортный код. Контроллер должен принять запрос, вызвать сервис и вернуть результат.

**Создание зависимости вручную.** Строка `new InMemoryStockRepository()` внутри контроллера обходит контейнер. В тесте подменить хранилище нельзя, а освобождение ресурсов никто не контролирует. Зависимость объявляют в конструкторе, а регистрируют в `Program.cs`.

**Singleton, которому нужен scoped сервис.** Приложение падает с сообщением `Cannot consume scoped service ... from singleton ...`. Лечится не отключением проверки, а сменой времени жизни: либо сервис становится singleton, если он действительно не хранит состояние, либо потребитель становится scoped.

**Проверка прав до маршрутизации.** Атрибут `[Authorize]` не срабатывает, потому что у промежуточного слоя ещё нет выбранной конечной точки. Запрещённый метод выполняется, и ошибка обнаруживается только при проверке безопасности, а не при запуске.

**Ожидание асинхронного вызова через `.Result`.** Под небольшой нагрузкой всё работает. При десятках одновременных запросов потоки заканчиваются, и сервер перестаёт отвечать, хотя база свободна. Признак в журнале: время ответа растёт, загрузка процессора низкая.

**Возврат сущности базы напрямую.** В JSON попадают служебные поля, а иногда и хеш пароля. Отдавать клиенту нужно отдельную модель ответа с теми полями, которые ему действительно нужны.

**Ошибка, спрятанная за кодом 200.** Контроллер ловит исключение и возвращает `Ok(new { error = "..." })`. Клиент считает запрос успешным, мониторинг не видит сбоя, а данные не сохранены. Для ошибки есть код 500 и журнал.

**Секрет в репозитории.** Строка подключения с паролем в `appsettings.json` остаётся в истории Git даже после удаления. Пароль считается скомпрометированным и подлежит смене, а не только удалению из файла.

## Итоги

- ASP.NET Core собирает конвейер при старте, и каждый запрос проходит его ступени в заданном порядке.
- Обработчик исключений ставят первым, маршрутизацию до проверки прав, аутентификацию до авторизации, конечную точку последней.
- Внедрение зависимостей передаёт объекты через конструктор, а время жизни задаётся при регистрации.
- Singleton живёт всё приложение, scoped один запрос, transient создаётся при каждом обращении.
- Настройки собираются из файлов, секретов, переменных окружения и аргументов, а секреты хранят вне репозитория.
- Контроллер принимает данные из маршрута, строки запроса и тела, а результат выражает кодом состояния.

Q: Что делает промежуточный слой в конвейере ASP.NET Core?
+ Обрабатывает запрос и либо передаёт его дальше, либо сразу возвращает ответ
- Компилирует код контроллера при первом запросе
- Хранит строки подключения в памяти
- Заменяет базу данных при недоступности
! Слой получает запрос, может его изменить и решает, вызывать ли следующий слой.

Q: Какая ступень выбирает конечную точку по шаблону адреса?
+ Маршрутизация
- Аутентификация
- Авторизация
- Обработчик исключений
! Маршрутизация сопоставляет адрес с шаблоном и выбирает действие контроллера.

Q: Где должен стоять обработчик исключений?
+ В начале конвейера, чтобы оборачивать остальные слои
- Последним, после контроллера
- Между маршрутизацией и авторизацией
- Внутри каждого действия контроллера
! Исключение должно пройти через обработчик, поэтому он стоит раньше остальных слоёв.

Q: Что означает время жизни scoped?
+ Один экземпляр на HTTP-запрос
- Один экземпляр на всё приложение
- Новый экземпляр при каждом обращении к контейнеру
- Экземпляр на каждое соединение с базой
! Область запроса создаётся на время обработки одного запроса и освобождается после ответа.

Q: Какая ошибка возникает, если singleton зависит от scoped сервиса?
+ Контейнер сообщает, что singleton не может использовать scoped сервис
- Приложение собирается и работает без изменений
- Контейнер создаёт второй экземпляр singleton
- Scoped сервис автоматически становится singleton
! Захват зависимости приводит к ошибке проверки областей или к долгой жизни scoped объекта.

Q: Откуда приложение берёт строку подключения в учебном сервисе?
+ Из конфигурации, собранной из файлов, секретов и переменных окружения
- Из кода контроллера
- Из комментария в файле Program.cs
- Из имени проекта
! Строка подключения это настройка, а не часть кода.

Q: Что возвращает метод CreatedAtAction?
+ Код 201, заголовок Location и тело с созданным объектом
- Код 200 и пустое тело
- Код 204 без тела
- Код 400 со списком ошибок
! Клиент получает адрес созданной записи и может сразу её прочитать.

Q: Что делает атрибут ApiController при неверной модели запроса?
+ Возвращает код 400 с перечнем полей и ошибок
- Игнорирует неверные поля
- Возвращает код 500
- Вызывает действие с пустыми значениями
! Автоматическая проверка модели избавляет от ручных проверок в каждом действии.

Q: Зачем действию возвращать ActionResult?
+ Чтобы вернуть либо данные, либо результат с кодом состояния
- Чтобы ускорить сериализацию JSON
- Чтобы отключить проверку модели
- Чтобы создать отдельный поток для запроса
! ActionResult объединяет успешный ответ и ответы с ошибками.

Q: Какие ступени должны идти до конечной точки?
+ Маршрутизация
+ Аутентификация
+ Авторизация
- Вызов действия контроллера
- Сериализация результата
! Конечная точка выполняется последней, после выбора маршрута и проверок.

Q: Какие признаки указывают на толстый контроллер?
+ В действии есть SQL-запрос и расчёт остатка
+ Действие само проверяет права и формирует ответ об ошибке
- Действие принимает параметр из строки запроса
- Действие возвращает Ok с моделью ответа
! Контроллер должен заниматься приёмом запроса и возвратом результата.

Q: Что допустимо хранить в appsettings.json?
+ Размер страницы и площадку по умолчанию
+ Уровень журналирования для стенда
- Пароль базы данных
- Ключ подписи токенов
! Секреты хранят в переменных окружения или в хранилище секретов.

Q: Как называется передача зависимостей через конструктор?
= внедрение зависимостей
= dependency injection
= di

Q: Какое время жизни создаёт один экземпляр на HTTP-запрос?
= scoped
= scoped сервис
! Scoped означает область одного запроса.

Q: Какой метод контроллера возвращает код 404?
= NotFound
= NotFound()
! Метод NotFound формирует ответ об отсутствии записи.
