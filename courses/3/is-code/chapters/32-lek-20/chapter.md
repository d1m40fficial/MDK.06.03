## Одна кавычка в поиске

Кладовщик на площадке в Калуге ищет товар и вводит в строку поиска `' OR 1=1 --`. Приложение показывает не одну позицию, а все 4800. Ещё через минуту он открывает карточку с чужим кодом и получает остатки московского склада. Ни пароль, ни роль он не подбирал: он воспользовался тем, что введённый текст попал прямо в SQL-запрос и стал его частью.

Такая ошибка встречается в учебных проектах постоянно, потому что на маленькой базе она незаметна. Запрос с подстановкой работает, поиск находит товар, отчёт строится. Проблема проявляется только тогда, когда кто-то вводит кавычку, дефис или слово `UNION`.

**Безопасность приложения с базой держится на трёх правилах: данные не становятся кодом, секреты не лежат в репозитории, права проверяются на сервере для каждой записи.** Нарушение любого из них открывает путь к остальным: через инъекцию можно прочитать таблицу пользователей, через украденный ключ подключиться к базе напрямую, через слабую проверку прав забрать чужие документы.

У «Северного склада» 4800 позиций, 120 учётных записей и четыре площадки. Потеря базы остатков остановит отгрузку, а утечка накладных раскроет условия работы с поставщиками. Поэтому защита здесь не абстрактное требование, а условие ежедневной работы.

## Инъекция: когда данные становятся кодом

SQL-запрос это строка. Если приложение склеивает команду и пользовательский ввод в одну строку, база получает единый текст и не различает, где закончилась команда и начались данные. Кавычка во вводе закрывает строковый литерал, а всё после неё база читает как продолжение команды.

Проверим это на учебной таблице остатков:

```python
import sqlite3

connection = sqlite3.connect(":memory:")
connection.execute(
    "CREATE TABLE stock (id INTEGER PRIMARY KEY, item TEXT, site TEXT, qty INTEGER)"
)
connection.executemany(
    "INSERT INTO stock VALUES (?, ?, ?, ?)",
    [
        (1, "Кабель UTP", "Москва", 120),
        (2, "Коробка 400", "Тверь", 80),
        (3, "Стрейч-плёнка", "Тула", 240),
        (4, "Паллета", "Калуга", 60),
    ],
)

user_input = "' OR 1=1 --"
query = f"SELECT id, item, site FROM stock WHERE item = '{user_input}'"

print("запрос:", query)
print("склейка:", connection.execute(query).fetchall())

safe = connection.execute(
    "SELECT id, item, site FROM stock WHERE item = ?", (user_input,)
).fetchall()
print("параметр:", safe)

count = connection.execute("SELECT COUNT(*) FROM stock").fetchone()[0]
print("всего строк в таблице:", count)
```

Вывод:

```text
запрос: SELECT id, item, site FROM stock WHERE item = '' OR 1=1 --'
склейка: [(1, 'Кабель UTP', 'Москва'), (2, 'Коробка 400', 'Тверь'), (3, 'Стрейч-плёнка', 'Тула'), (4, 'Паллета', 'Калуга')]
параметр: []
всего строк в таблице: 4
```

Склейка вернула все четыре строки. Условие `item = ''` ложно, но `OR 1=1` истинно всегда, а два дефиса превращают остаток строки в комментарий. Параметризованный запрос вернул пустой список: значение `' OR 1=1 --` сравнивалось с названием товара как обычный текст и ни с чем не совпало.

Причина в том, что параметр передаётся отдельно от текста команды. База сначала разбирает запрос с местом для значения, а потом подставляет значение в это место. Кавычки внутри значения остаются данными и не могут изменить структуру команды.

Инъекция не ограничивается обходом условия. Через `UNION` злоумышленник дописывает второй запрос и читает другую таблицу, через сообщение об ошибке узнаёт имена колонок, через точку с запятой пытается выполнить отдельную команду. Драйверы часто запрещают несколько команд в одном вызове, но чтение чужой таблицы через `UNION` от этого не исчезает. Поэтому защита не сводится к запрету кавычек: запрет обходят кодировкой и другими символами, а параметр убирает саму возможность изменить структуру запроса.

Проверка ввода остаётся полезной, но как второй слой. Она отсекает заведомо неверные значения, ограничивает длину и формат, помогает вернуть понятную ошибку. Заменить параметры проверкой она не может: любая проверка опирается на список запрещённых символов, а список всегда неполон.

Ущерб от неудачной инъекции ограничивают права учётной записи базы. Если приложение подключается пользователем с правом читать только свои таблицы, `UNION` не откроет таблицу пользователей. Если у него права администратора, одна ошибка в запросе открывает всю базу. Поэтому минимальные права это не формальность, а последний рубеж.

В C# опасный вариант выглядит так же, как в Python, только с интерполяцией строки:

```csharp
var search = Console.ReadLine() ?? "";
var sql = $"SELECT id, item, site FROM stock WHERE item = '{search}'";
using var bad = new SqliteCommand(sql, connection);
```

Исправленный вариант использует параметр:

```csharp
var sql = "SELECT id, item, site FROM stock WHERE item = $search";
using var command = new SqliteCommand(sql, connection);
command.Parameters.AddWithValue("$search", search);
```

Правило простое: **любое значение, пришедшее от клиента, передаётся параметром, а не вставляется в текст запроса.** Это касается не только поиска, но и фильтров, сортировки, имени таблицы и номера страницы.

| Место в коде | Опасный вариант | Безопасный вариант |
|---|---|---|
| Поиск по названию | `WHERE item = '{text}'` | `WHERE item = ?` и кортеж значений |
| Фильтр по площадке | `WHERE site = '{site}'` | `WHERE site = ?` |
| Сортировка | `ORDER BY {column}` | выбор из белого списка колонок |
| Ограничение строк | `LIMIT {count}` | приведение к числу и проверка диапазона |

Сортировка и имя таблицы параметром не передаются: база подставляет параметры только вместо значений. Для них заранее задают допустимый список: если клиент просит сортировку по `quantity`, приложение подставляет строку `quantity` из списка, а любой другой ввод заменяет на сортировку по умолчанию.

ORM снижает риск, но не отменяет его. Обычные запросы EF Core параметризуются автоматически. Опасность появляется там, где в ORM передают готовую строку: методы вида `FromSqlRaw` с интерполяцией снова склеивают текст. Для параметров есть `FromSql` с интерполяцией, которая создаёт параметры, а не строку.

Отдельный случай это второй порядок. Значение сохранили в базе без вреда, а через неделю другой отчёт подставил его в текст запроса. Поэтому проверять нужно не только момент ввода, но и каждое место, где значение снова становится частью команды.

## Секреты: строка подключения, ключи, пароли

Секрет это значение, которое даёт доступ к системе: пароль базы, ключ подписи токенов, ключ внешнего сервиса, пароль администратора. У секрета есть особенность: он ценен только пока неизвестен. Поэтому задача не в том, чтобы спрятать файл, а в том, чтобы секрет не попал туда, откуда его можно прочитать.

Каналов утечки несколько. Секрет попадает в репозиторий вместе с `appsettings.json`, в историю Git после удаления строки, в журнал приложения при отладке, в текст ошибки на странице, в снимок экрана на совещании, в архив с резервной копией и в переписку с коллегой. Один и тот же пароль часто используют на учебном стенде и на рабочем сервере, поэтому утечка учебного файла открывает боевую базу.

Правильное хранение выглядит скучно. В коде остаётся имя настройки, значение приходит извне. Для разработки используют хранилище секретов, для сервера переменные окружения или отдельное хранилище, для всех сред разные значения.

```text
ConnectionStrings__Sklad=Data Source=sklad.db;Password=...
Jwt__Key=...
```

В Python тот же принцип:

```python
import os

dsn = os.environ.get("SKLAD_DSN")
if not dsn:
    raise SystemExit("Не задана переменная SKLAD_DSN")

print("строка подключения получена, длина:", len(dsn))
```

Приложение не печатает саму строку, а сообщает только, что настройка есть. Если переменная не задана, оно останавливается с понятным сообщением, а не подставляет пароль по умолчанию.

| Где хранить | Что можно | Что нельзя |
|---|---|---|
| `appsettings.json` | адрес сервера, размер страницы, уровень журнала | пароль, ключ подписи |
| `appsettings.Development.json` | локальный адрес базы | пароль от рабочей базы |
| секреты разработчика | пароль учебной базы | общий пароль для всех разработчиков |
| переменные окружения сервера | пароль и ключи стенда | значения, которые попадут в журнал |
| хранилище секретов | все боевые секреты | открытая выдача всем сотрудникам |

Если секрет уже попал в репозиторий, удалить строку недостаточно. История Git сохраняет старую версию, а копии могли разойтись по форкам и архивам. Секрет считают скомпрометированным, меняют на новый и только потом чистят историю. Смена важнее чистки: старый пароль уже нельзя считать тайной.

Учётная запись базы тоже подчиняется правилу наименьших привилегий. Приложению «Склад+» нужны чтение и запись в свои таблицы, но не удаление базы и не управление пользователями. Отдельная учётная запись для приложения, отдельная для миграций и отдельная для администратора сокращают ущерб от ошибки.

Журнал и страница ошибки это отдельный канал. Когда база недоступна, драйвер часто пишет в текст исключения всю строку подключения вместе с паролем. Если приложение показывает такую ошибку клиенту, секрет уходит в браузер и в системы сбора ошибок. Поэтому клиенту возвращают короткое сообщение с идентификатором запроса, а подробности пишут в журнал, где строка подключения уже вырезана.

Снимок экрана и переписка кажутся безобидными, но на учебных и рабочих совещаниях в кадр попадают окна с настройками, вкладки с токенами и файлы конфигурации. Правило простое: секрет не показывают на экране и не пересылают в чате. Для передачи используют хранилище секретов с ограниченным доступом и сроком действия.

## Доступ: проверка на сервере

Нарушение контроля доступа стоит первым в списке типовых веб-угроз OWASP Top 10 2021. Причина в том, что проверку легко поставить не там: спрятать кнопку, отфильтровать список на клиенте, доверить полю из тела запроса.

Есть три частых сценария. Первый: пользователь открывает адрес `/api/admin/users` напрямую, хотя ссылки в интерфейсе нет. Если маршрут не защищён ролью, страница откроется. Второй: кладовщик меняет в адресе номер записи и получает чужую накладную. Третий: клиент отправляет в теле запроса лишнее поле `role` или `site`, и модель принимает его целиком.

Третий сценарий называют массовым назначением полей. Приложение ждёт название и количество, а получает ещё и роль. Если модель совпадает с сущностью базы, лишнее поле запишется. Защита простая: для входящих данных описывают отдельную модель, где перечислены только разрешённые поля, а остальные игнорируются.

| Угроза | Как выглядит | Защита |
|---|---|---|
| Обход маршрута | прямой запрос к административному адресу | `[Authorize(Roles = "admin")]` на контроллере |
| Чужая запись | подмена идентификатора в адресе | сравнение площадки записи с площадкой пользователя |
| Лишнее поле | в теле запроса пришла роль | отдельная модель запроса без служебных полей |
| Скрытая кнопка | запрет только в интерфейсе | проверка на сервере для каждого запроса |

Проверку прав проектируют от запрета: по умолчанию закрыто всё, а открывается только то, что нужно. Новый контроллер без атрибута не должен становиться общедоступным. Для этого в приложении включают глобальную политику, которая требует вход для всех маршрутов, а исключения помечают явно.

Проверять защиту нужно двумя учётными записями. Одна с ролью кладовщика своей площадки, вторая с ролью менеджера. Запросы повторяют с обеими: кладовщик не должен получить чужую запись, менеджер должен. Проверка только «своим» пользователем ничего не доказывает: она показывает, что доступ есть, но не показывает, что чужой его не получит.

Административные маршруты выносят в отдельный префикс и закрывают отдельной политикой. Это упрощает проверку: все адреса, начинающиеся с `api/admin`, требуют роль администратора, и новый контроллер в этой папке получает защиту по общему правилу. Ссылки в интерфейсе при этом остаются удобством, а не защитой.

Отдельно проверяют прямые адреса. Список маршрутов можно получить из документации API, из журнала или перебором. Если административная страница существует, но не защищена, отсутствие ссылки в меню ничего не меняет.

Права дублируют на уровне базы. Приложению не нужен доступ к таблице пользователей, если оно только читает остатки. Ограничения внешних ключей и проверки значений не дают записать бессмысленные данные даже при ошибке в коде. Защита на нескольких уровнях не лишняя: каждый уровень закрывает свой способ обхода.

## Шифрование, хеширование и кодирование

Эти три операции часто путают, а разница определяет, от чего каждая защищает.

Кодирование переводит данные в другой вид без секрета. Base64 превращает байты в текст и легко раскрывается обратно. Это удобно для передачи, но совершенно не защищает: строка `U2tsYWQr` читается любой библиотекой за одну команду и даёт «Sklad+».

Хеширование необратимо. Из пароля получают хеш, из хеша пароль не восстанавливают. Хеш подходит для проверки пароля и для контроля целостности файла. Для паролей нужен медленный алгоритм с солью, а не быстрый SHA-256.

Шифрование обратимо, но только с ключом. Оно защищает данные, которые нужно прочитать позже: файл базы, резервную копию, номер договора. Ключ хранится отдельно от данных, иначе шифрование защищает только от потери диска.

| Операция | Обратима | Секрет | Для чего |
|---|---|---|---|
| Кодирование | да, без ключа | нет | передача и хранение текста |
| Хеширование | нет | соль | пароли, контроль целостности |
| Шифрование | да, с ключом | ключ | данные при хранении и передаче |

Данные в пути защищает TLS. Без него пароль и токен идут открытым текстом, и любой узел в сети может их прочитать. HTTPS обязателен не только для внешнего сайта, но и для обмена между сервисами внутри сети: внутренняя сеть не делает трафик безопасным.

Клиент проверяет сертификат сервера по цепочке доверия и сроку действия. Если проверку отключить ради удобства, соединение останется зашифрованным, но собеседник не будет проверен, и данные уйдут тому, кто выдаёт себя за сервер. Отключение проверки допустимо только на изолированном учебном стенде и только на время отладки.

Данные при хранении защищают шифрованием диска, файла базы или резервных копий. Отдельно решают, что делать с ключом: он не должен лежать в том же архиве, что и зашифрованная копия. Резервная копия без ключа бесполезна при восстановлении и опасна при утечке.

Собственные алгоритмы шифрования не пишут. Для стандартных задач берут библиотеку: TLS для канала, проверенный алгоритм для паролей, штатное шифрование для файлов. Самодельная схема почти всегда содержит ошибку, которую автор не видит.

Ключ живёт отдельно от данных и меняется по расписанию. Если ключ лежит рядом с зашифрованной резервной копией, кража архива даёт и замок, и ключ. При смене ключа старые копии перешифровывают или хранят вместе с идентификатором ключа, чтобы при восстановлении было понятно, чем их открывать. Потерянный ключ означает потерянные данные, поэтому копия ключа хранится в другом месте и с другим доступом.

Шифрование не заменяет права доступа. Расшифрованную базу может прочитать любой, у кого есть учётная запись приложения. Поэтому права на таблицы, проверка роли и журнал действий остаются обязательными даже при шифровании диска.

## Типичные ошибки

**Склейка SQL.** Строка `WHERE item = '{text}'` пропускает кавычку и комментарий. Симптом: поиск с апострофом возвращает весь список или ошибку синтаксиса. Лечится параметром, а не экранированием вручную.

**Секрет в репозитории.** Пароль в `appsettings.json` остаётся в истории Git. Симптом: секрет находят в старом коммите после удаления строки. Лечится сменой пароля и хранением вне репозитория.

**Проверка только в интерфейсе.** Кнопка скрыта, маршрут открыт. Симптом: запрос из Postman с обычным токеном выполняет запрещённое действие. Лечится атрибутом и политикой на сервере.

**Доверие полям из тела запроса.** Клиент присылает `role` вместе с названием товара, и модель записывает роль. Симптом: пользователь повышает себе права одним запросом. Лечится отдельной моделью с разрешёнными полями.

**Подробная ошибка на клиенте.** В ответ попадает текст SQL, имя таблицы и стек вызовов. Симптом: страница 500 рассказывает, как устроена база. Лечится общим сообщением клиенту и подробной записью в журнал.

**Кодирование вместо шифрования.** Base64 считают защитой и хранят в нём пароли. Симптом: строка легко раскрывается. Лечится хешированием паролей и настоящим шифрованием данных.

**Полные права у приложения.** Сервис подключается к базе как администратор. Симптом: ошибка в коде позволяет удалить таблицу. Лечится отдельной учётной записью с минимальными правами.

**Устаревшая зависимость.** В библиотеке есть известная уязвимость, а версия не обновлялась. Симптом: сканер находит проблему в пакете. Лечится обновлением и проверкой `dotnet list package --vulnerable`.

## Проверка перед выпуском

| Проверка | Вопрос | Признак проблемы |
|---|---|---|
| Запросы | все значения переданы параметрами | в коде есть интерполяция в SQL |
| Секреты | в репозитории нет паролей и ключей | поиск по слову `password` находит значение |
| Доступ | каждый маршрут защищён | новый контроллер открыт без атрибута |
| Записи | проверяется владелец | действие доверяет номеру из адреса |
| Ошибки | клиент не видит внутренностей | в ответе есть текст SQL |
| Канал | HTTPS обязателен | пароль идёт по HTTP |
| Зависимости | нет известных уязвимостей | сканер пакетов выдаёт предупреждение |

Проверку повторяют не один раз перед сдачей, а при каждом изменении, которое касается входа, запросов и настроек. Новый маршрут, новая таблица и новый внешний сервис добавляют путь, которого раньше не было. Список проверок короткий, поэтому его можно пройти за несколько минут и не полагаться на память.

Отдельно проверяют поведение при ошибке. Отключают базу, вводят неверный пароль, отправляют чужой идентификатор и смотрят, что видит клиент. Если в ответе есть текст SQL, имя таблицы или стек вызовов, защита настроена неверно, даже когда обычные запросы работают.

## Итоги

- Инъекция возникает там, где ввод склеивают с текстом команды, и лечится параметрами.
- Секреты хранят вне репозитория, а попавший в историю секрет считают скомпрометированным и меняют.
- Доступ проверяют на сервере для маршрута, роли, конкретной записи и допустимых полей.
- Кодирование не защищает, хеширование необратимо, шифрование требует ключа.
- TLS защищает данные в пути, шифрование и права доступа защищают данные при хранении.
- Инъекцию, утечку секретов и слабые права объединяет одно: приложение доверяет данным, которые пришли извне.
- Перед выпуском проверяют запросы, секреты, маршруты, ошибки и зависимости.
