## Цель работы

Научиться превращать работающий проект в комплект документов, по которому другой человек запускает приложение, вызывает его API и понимает устройство системы. Работа идёт на материале индивидуального проекта и учебного примера `sklad-plus` для ИС «Склад+»: 120 сотрудников, четыре площадки, 12 товарных категорий и 4800 позиций на складе.

Результат работы это четыре согласованных документа и один проверенный маршрут показа. README отвечает на вопрос «как запустить», описание API на вопрос «как вызвать», слайды на вопрос «как устроено и зачем», сценарий демонстрации на вопрос «что именно будет на экране». Если ответы расходятся, читатель теряет доверие ко всему комплекту, даже когда код работает правильно.

Главный признак готовности простой: человек, который не видел проект, открывает README, выполняет команды по порядку и получает работающее приложение. Остальные документы проверяют так же: описание API сверяют запросом, слайды сверяют с кодом и данными, сценарий проверяют прогоном. Документ, который никто не проверял, считается черновиком, а не результатом.

## Оборудование и программное обеспечение

- Персональный компьютер с Windows 10.
- Python 3.11 или новее и VS Code с расширением Python.
- Postman для проверки маршрутов API.
- Git и терминал PowerShell.
- MS Word или LibreOffice Writer для отчёта.
- MS PowerPoint или LibreOffice Impress для презентации.
- Репозиторий индивидуального проекта с кодом, базой и тестами.

## Краткие теоретические сведения

Документация проекта делится не по объёму, а по адресату. У каждого читателя своя задача, и документ нужен только тогда, когда он отвечает на его вопрос. Кладовщик ищет, как провести приёмку, администратор ищет, где выдать доступ, разработчик ищет, как поднять проект на новой машине. Один документ на все случаи превращается в текст, который никто не дочитывает.

| Документ | Адресат | Вопрос читателя |
|---|---|---|
| README | новый разработчик, проверяющий | как установить и запустить проект |
| Описание API | разработчик другого модуля, тестировщик | как вызвать операцию и что вернётся |
| Презентация | комиссия, руководитель, заказчик | какую задачу решает система и как она устроена |
| Сценарий демонстрации | тот, кто показывает проект | что нажать и что должно появиться |
| Отчёт | проверяющий работу | что сделано, как проверено, какие выводы |

README это входная точка проекта. Он лежит в корне репозитория и называется `README.md`, чтобы его увидел каждый, кто открыл репозиторий. Хороший README содержит назначение проекта, пользователей и роли, требования к окружению, установку, запуск, проверку работы, структуру каталогов, ссылку на описание API и сведения об авторе. Команды в нём можно скопировать и выполнить без догадок: рядом с каждой командой указано, из какого каталога она выполняется.

Команды в README проверяют на чистой копии проекта. Чистая копия это папка без виртуального окружения, без кеша Python и без базы, созданной во время разработки. Если проект запускается только на машине автора, причина обычно в одном из трёх: не описана установка пакетов, не создана база, не указан обязательный файл настроек. Все три причины видны при первом же прогоне на чистой копии.

Описание API фиксирует контракт: метод, адрес, параметры, тело запроса, успешный ответ и ошибки. Контракт нужен не для красоты, а для стыковки. Фронтенд, мобильный клиент и тесты пишутся по описанию, и если оно расходится с кодом, ошибка обнаружится только при вызове. Поэтому каждый маршрут описывают примером настоящего запроса и настоящего ответа, а не фразой «возвращает данные склада».

| Часть описания | Что указывают | Пример ошибки |
|---|---|---|
| Метод и адрес | `GET /api/stock/<sku>` | адрес без параметра пути |
| Назначение | одну фразу о результате | «работает со складом» |
| Доступ | роль или требование токена | доступ не указан вовсе |
| Параметры | имя, тип, обязательность | тип «строка» для количества |
| Успешный ответ | код и поля JSON | код 200 без структуры тела |
| Ошибки | коды и условия | перечислен только 500 |

Если сервис собран на FastAPI, часть описания создаётся автоматически: схемы запроса и ответа попадают в страницу `/docs`. Это не отменяет ручного описания. Автоматическая схема показывает поля и типы, но не объясняет, зачем нужен маршрут, какая роль его вызывает и что означает ошибка 409. Хорошее описание соединяет машинную схему и человеческое объяснение.

Презентация это не отчёт, переложенный на слайды. У слайда одна мысль и один объект: схема, таблица, фрагмент кода или снимок экрана. Текст на слайде служит опорой для говорящего, а не заменяет его. Слайд с двадцатью строками кода не читается с последнего ряда, поэтому на экран выносят пять-восемь строк, а остальное объясняют словами.

Структура доклада повторяет логику проекта. Сначала задача и пользователи, затем границы системы, архитектура, модель данных, ключевой сценарий, API, роли и безопасность, проверки и ограничения. В конце итог и направление развития. Такая последовательность отвечает на вопросы, которые возникают у слушателя по порядку: зачем, для кого, из чего состоит, как работает, чем доказано.

Сценарий демонстрации отличается от презентации тем, что описывает действия, а не мысли. В нём для каждого шага записано, что нажать, какие данные ввести, что должно появиться на экране и что сказать в этот момент. Данные для показа готовят заранее и делают повторяемыми: одна и та же приёмка должна давать один и тот же результат. Если база меняется после каждого прогона, второй показ пройдёт иначе, и сценарий перестанет работать.

У демонстрации есть запасной путь: копия базы, скрипт наполнения и снимки ключевых экранов. Живой запуск может сорваться из-за занятого порта или забытого пароля, и тогда показ продолжают по снимкам. Запасной путь не отменяет живой показ, но спасает защиту от технической мелочи.

Согласованность документов проверяют сравнением, а не памятью. Единый источник правды это код и данные: маршруты берут из файла приложения, числа из базы, команды из терминала. Если на слайде указано 4800 позиций, а в базе 4795, слушатель заметит расхождение раньше автора.

| Признак хорошего комплекта | Признак плохого комплекта |
|---|---|
| команды скопированы из проверенного прогона | команды написаны по памяти |
| у каждого маршрута есть пример ответа | перечислены только названия маршрутов |
| слайды называют те же числа, что и база | числа на слайдах округлены «примерно» |
| сценарий проверен на чистой базе | сценарий держится на данных разработчика |
| в документах указана дата и версия | непонятно, к какой версии относится текст |

## Ход работы

### Шаг 1. Определите адресатов и состав комплекта

Ниже переписка руководителя проекта с разными участниками. В ней названы просьбы, но не сказано, в каком документе на них отвечать.

```text
Руководитель: «Покажи, что уже готово и что осталось».
Кладовщик: «Где в системе провести приёмку и куда смотреть, если не сохраняется?»
Тестировщик: «Какие коды возвращает отгрузка при нехватке товара?»
Новый разработчик: «Я склонировал репозиторий, но не понимаю, как его запустить».
Заказчик: «Почему база именно такая и что будет при росте до 10 площадок?»
```

Составьте таблицу комплекта: документ, адресат, вопрос, на который документ отвечает. Первая строка дана как образец, остальные заполните по переписке и по своему проекту.

| Документ | Адресат | Вопрос | Где лежит |
|---|---|---|---|
| README | новый разработчик | как установить и запустить | корень репозитория |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |

Проверьте, что на каждую просьбу из переписки отвечает хотя бы один документ. Если просьба осталась без адреса, добавьте документ или раздел, а не рассчитывайте, что вопрос зададут ещё раз.

### Шаг 2. Напишите README

Начните с каркаса разделов. Готового текста здесь нет: заполняйте разделы фактами своего проекта.

```text
# Название проекта
## Назначение
## Пользователи и роли
## Требования
## Установка
## Запуск
## Проверка работы
## Структура проекта
## Описание API
## Автор и дата
```

Разберите команды установки на примере учебного проекта. Каждая строка что-то создаёт или меняет, поэтому порядок важен.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m sklad
```

Первая команда создаёт виртуальное окружение в каталоге `.venv`. Вторая активирует его в текущем терминале. Третья устанавливает пакеты с зафиксированными версиями из файла `requirements.txt`, который получают командой `pip freeze > requirements.txt` в рабочем окружении. Четвёртая запускает приложение по имени пакета.

В README рядом с блоком команд укажите текущий каталог и ожидаемый результат. Для запуска это обычно строка о том, что сервис слушает порт 5000, а для консольной программы несколько строк вывода. Не вставляйте вывод, который вы не видели: его всё равно сверят при проверке.

Добавьте раздел о базе. Если проект использует SQLite, опишите, откуда берётся файл базы, что делать при первом запуске и как наполнить её учебными данными. Если база создаётся скриптом, назовите команду и файл. Читатель не должен угадывать, нужен ли ему готовый файл или скрипт создания.

В разделе «Структура проекта» перечислите каталоги и их назначение. Достаточно верхнего уровня и одного пояснения на каталог: `src` для кода, `tests` для проверок, `docs` для документов, `data` для учебных данных. Подробное дерево на сто строк не нужно, оно устаревает после первой правки.

### Шаг 3. Проверьте README на чистой копии

Скопируйте проект в соседнюю папку, удалив каталоги `.git` и `.venv`, а также файл базы, созданный во время разработки. Затем откройте README и выполняйте команды ровно в том порядке, в каком они записаны, не заглядывая в код.

Заполните таблицу проверки. Первая строка дана как образец.

| Проверка | Как проверяли | Результат | Что исправлено |
|---|---|---|---|
| Создание окружения | команда из раздела «Установка» | окружение создано | ничего |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |

Отдельно проверьте три вещи. Первая: команда запуска работает из того каталога, который указан в README. Вторая: после запуска появляется именно тот результат, который описан. Третья: остановка приложения описана, и читатель понимает, как освободить порт.

Частая ошибка это скрытая зависимость от файла `.env` или локальной базы. Если проект без них не стартует, README должен содержать раздел о настройках: какие переменные нужны, какие значения допустимы, что произойдёт при отсутствии значения. Секреты в README не пишут, вместо них указывают имена переменных и пример без настоящих ключей.

### Шаг 4. Опишите маршруты API

Ниже список маршрутов учебного сервиса `sklad-plus` в том виде, в каком он извлекается из кода. Описаний здесь нет, их нужно составить.

```text
GET  /api/stock
GET  /api/stock/<sku>
POST /api/receipts
POST /api/shipments
GET  /api/invoices/<number>
```

Для каждого маршрута заполните строку таблицы: метод, адрес, назначение, успешный ответ, ошибки. Первая строка дана как образец.

| Метод | Адрес | Назначение | Успех | Ошибки |
|---|---|---|---|---|
| GET | /api/stock/<sku> | остаток по артикулу | 200, JSON с полями sku, title, available | 404, если артикул не найден |
|  |  |  |  |  |
|  |  |  |  |  |
|  |  |  |  |  |

Затем раскройте каждый маршрут по шаблону. Шаблон одинаковый, поэтому описание остаётся предсказуемым и его можно читать выборочно.

```text
Метод и адрес:
Назначение:
Доступ:
Параметры пути:
Параметры запроса:
Тело запроса:
Успешный ответ:
Ошибки:
Пример запроса:
Пример ответа:
```

Пример ответа берите из Postman, а не придумывайте. Для маршрута `GET /api/stock/SKU-1042` ответ выглядит так:

```json
{
  "sku": "SKU-1042",
  "title": "Перфоратор",
  "available": 30
}
```

Поле `available` равно разнице между количеством на складе и резервом. В учебных данных у этого артикула 40 единиц и 10 в резерве, поэтому ответ содержит 30. Если в вашем проекте формула другая, опишите её одной фразой в поле «Назначение», иначе читатель решит, что видит ошибку.

Для маршрутов записи добавьте тело запроса и код успеха. Приёмка обычно возвращает 201 и идентификатор созданной записи, отгрузка может вернуть 200 с обновлённым остатком. Ошибку нехватки товара описывают отдельно: код 409 и понятное сообщение, а не 500.

Если приложение собрано на Flask, маршруты ищут поиском по декораторам:

```powershell
Select-String -Path src\sklad\api.py -Pattern "@app\."
```

Команда `Select-String` печатает строки файла, которые совпали с шаблоном. Шаблон `@app\.` находит декораторы маршрутов, а точка экранирована, чтобы она читалась как символ, а не как «любой символ». Для FastAPI тот же поиск даёт декораторы `@app.get`, `@app.post` и другие.

### Шаг 5. Сверьте описание API с кодом и Postman

Описание проверяют вызовом. Откройте коллекцию Postman, пройдите по каждому маршруту и сравните фактический ответ с документом. Заполните таблицу сверки.

| Маршрут | Запрос | Ожидаемый код | Фактический код | Тело совпало |
|---|---|---|---|---|
| GET /api/stock/SKU-1042 | артикул существует | 200 |  |  |
| GET /api/stock/SKU-9999 | артикул не существует | 404 |  |  |
| POST /api/shipments | количество больше остатка | 409 |  |  |
|  |  |  |  |  |

Проверьте не только успешный сценарий. Ошибки описывают чаще всего неверно, потому что их не вызывают вручную. Отправьте запрос с пустым обязательным полем, с отрицательным количеством и с чужим токеном. Если фактический код отличается от описанного, исправляют либо код, либо описание, но не оставляют расхождение.

Отдельно проверьте, что описание не обещает лишнего. Фраза «возвращает все позиции склада» при ответе в 4800 записей означает тяжёлый запрос и медленный ответ. Если маршрут поддерживает фильтр по площадке или категории, это указывают в параметрах запроса, иначе читатель будет скачивать весь справочник.

### Шаг 6. Составьте структуру доклада

Распределите материал по слайдам. Ниже блоки доклада в том порядке, в каком их удобно показывать. Готовых формулировок нет, есть только назначение блока.

```text
титул
задача и пользователи
границы системы
архитектура
модель данных
ключевой сценарий
API
роли и безопасность
проверки и тесты
ограничения и развитие
итог
```

Составьте таблицу слайдов: номер, что на нём, что сказать. Первая строка дана как образец.

| Слайд | Что на нём | Что сказать |
|---|---|---|
| 1 | тема, автор, группа, дата | назвать тему и одним предложением задачу проекта |
| 2 |  |  |
| 3 |  |  |

На слайде с архитектурой покажите слои и связи между ними, а не список файлов. Слушателю важно понять, где интерфейс, где правила расчёта и где доступ к данным. На слайде с моделью данных покажите пять-семь главных таблиц и связи между ними; полную схему из двадцати таблиц не читают с экрана.

Числа проекта должны совпадать с базой и с текстом доклада: 120 пользователей, четыре площадки, 12 категорий, 4800 позиций. Если вы показываете рост нагрузки, объясните, какая часть системы изменится при переходе к десяти площадкам. Общие слова «система масштабируется» без указания места изменения звучат как обещание, которое никто не проверял.

### Шаг 7. Соберите слайды

Соберите презентацию в PowerPoint или Impress. Придерживайтесь простых правил, которые проверяются глазами с последнего ряда.

- Один слайд содержит одну мысль и один главный объект.
- Заголовок слайда формулирует вывод, а не тему: не «Архитектура», а «Три слоя разделяют интерфейс и расчёты».
- Фрагмент кода занимает не больше восьми строк и набран шрифтом, который читается с экрана.
- Каждый снимок экрана подписан: что на нём и зачем он нужен.
- Таблица содержит не больше пяти строк и четырёх столбцов.
- На каждом слайде виден номер, чтобы вопрос можно было задать по номеру.

Проверьте презентацию на проекторе или втором экране: мелкий шрифт и бледные линии на проекторе исчезают. Если проектора нет, уменьшите масштаб слайда до 60 процентов, чтобы увидеть то, что увидит зал.

Отчёт читают, презентацию смотрят: если на слайде больше пяти строк текста, часть переходит в речь.

### Шаг 8. Подготовьте сценарий демонстрации

Ниже операции, которые система умеет выполнять. Порядок в списке произвольный: его нужно выстроить так, чтобы показ складывался в связную историю, а не в набор разрозненных нажатий.

```text
вход кладовщиком
приёмка 24 коробок на площадку Тула
перемещение 10 единиц в ячейку хранения
отгрузка по накладной
вход менеджером и просмотр отчёта по остаткам
вход администратором и блокировка пользователя
попытка кладовщика открыть отчёт по остаткам
```

Заполните таблицу сценария: шаг, действие, что видно на экране, что сказать. Первая строка дана как образец.

| Шаг | Действие | Что видно на экране | Что сказать |
|---|---|---|---|
| 1 | вход кладовщиком | главная страница с меню приёмки и отгрузки | показать, что меню зависит от роли |
| 2 |  |  |  |
| 3 |  |  |  |

Сценарий должен содержать не меньше шести шагов и хотя бы одну проверку ограничения: нехватку товара, запрет доступа или неверный пароль. Ошибка в показе убеждает лучше, чем рассказ о том, что проверка есть. Заранее решите, какую ошибку вы покажете и какое сообщение должно появиться.

Подготовьте данные так, чтобы шаги не зависели друг от друга. Если отгрузка уменьшает остаток, после неё повторный прогон даст другой результат. Поэтому перед показом базу возвращают в исходное состояние скриптом наполнения или копией файла. Проверьте, что скрипт действительно возвращает исходные числа: 4800 позиций, 12 категорий, четыре площадки.

Продумайте запасной путь. Держите под рукой копию базы, скрипт наполнения и снимки экранов ключевых шагов. Если приложение не запустится, показ продолжают по снимкам и объясняют, что должно было произойти. Запасной путь не заменяет живой запуск, но защищает от случайной технической задержки.

### Шаг 9. Проверьте документы на соответствие проекту

Сравните документы между собой и с кодом. В последнем столбце запишите конкретное расхождение из своего комплекта или слово «нет».

| Проверка | Что сравнить | Признак ошибки | Найдено |
|---|---|---|---|
| Команды | README и терминал | команда не выполняется из указанного каталога |  |
| Маршруты | описание API и файл приложения | маршрут есть в коде, но не описан |  |
| Коды | описание API и Postman | документ обещает 400, ответ приходит 500 |  |
| Числа | слайды и база | количество позиций или площадок не совпадает |  |
| Роли | слайды и проверка доступа | на слайде роль, которой нет в системе |  |
| Снимки | слайды и текущий интерфейс | на снимке старая версия экрана |  |
| Версия | титульный слайд и README | разные даты и версии проекта |  |

Если нашли расхождение, исправляйте источник, а не формулировку. Когда число на слайде не совпадает с базой, проверяют, какое из них верно, и приводят второе к нему. Когда маршрут не описан, добавляют описание, а не убирают маршрут из кода.

Отдельно проверьте ссылки: репозиторий должен открываться у человека без доступа к вашей машине, а ссылка на описание API вести на существующий файл. Битая ссылка выглядит хуже, чем её отсутствие.

### Шаг 10. Зафиксируйте версию комплекта

Соберите документы в репозиторий и сделайте коммит. Презентацию и отчёт можно хранить в каталоге `docs`, если он не попадает под игнор файлов.

```powershell
git status
git add README.md docs
git commit -m "Документация и презентация проекта"
git log --oneline -5
```

Команда `git status` показывает, какие файлы изменены. `git add` готовит их к коммиту, `git commit` записывает снимок с сообщением, `git log --oneline -5` печатает пять последних коммитов в коротком виде. По журналу должно быть видно, что документация добавлена отдельным шагом, а не смешана с правками кода.

На титульном слайде и в README укажите одну дату и версию. Если планируется доработка, добавьте раздел о том, что осталось за границами версии: названное ограничение вызывает больше доверия, чем его отсутствие.

## Требования к отчёту

Отчёт оформляют в Word, объём четыре-шесть страниц. В отчёте должны быть:

- тема проекта, цель работы и краткое описание пользователей;
- таблица адресатов и документов комплекта;
- фрагмент README с командами установки и запуска;
- таблица проверки README на чистой копии с исправлениями;
- таблица маршрутов API с кодами успеха и ошибок;
- таблица сверки описания API с ответами Postman;
- структура доклада по слайдам с назначением каждого слайда;
- сценарий демонстрации с ожидаемым результатом каждого шага;
- заполненный чек-лист соответствия документов проекту;
- снимок экрана с титульным слайдом презентации, на нём видны тема, автор и дата;
- снимок экрана с ответом Postman на один маршрут, на нём видны код состояния и тело ответа;
- короткий вывод о том, какие расхождения нашлись и как исправлены.

## Что сдать

- README.md в корне репозитория с проверенными командами установки, запуска и проверки;
- файл описания API с таблицей маршрутов, примерами запросов и ответов;
- презентация PPTX на 10-12 слайдов с архитектурой, моделью данных и демонстрацией;
- сценарий демонстрации с данными, ожидаемым результатом и запасным путём;
- отчёт DOCX с таблицами проверки и снимками экрана;
- ссылка на репозиторий с коммитом документации.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: README позволяет запустить проект на чистой копии без пояснений, описаны все маршруты с примерами ответов и ошибками, слайды содержат архитектуру и модель данных, сценарий проверен прогоном, числа и роли совпадают с проектом, чек-лист заполнен, отчёт содержит снимки и вывод.
- **4**: комплект собран полностью, но один маршрут описан без примера ответа, либо на слайдах нет модели данных, либо в сценарии не предусмотрен запасной путь, либо одно расхождение найдено, но не исправлено.
- **3**: документы составлены частично, README не проверен на чистой копии, описание API перечисляет адреса без параметров и кодов, слайды повторяют отчёт текстом, сценарий не проверен.
- **2**: работа не выполнена или приложение по README не запускается.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
