## Сбой в 07:40

В 07:40 кладовщик в Туле принимает машину от поставщика. В накладной 380 строк, приёмка идёт по одной позиции, и после каждой строки остаток товара увеличивается в базе. На 214-й строке количество записано как «12,5»: поставщик указал дробное число упаковок, а поле в «Склад+» принимает только целые штуки.

Программа останавливается. В терминале последняя строка сообщения:

```text
ValueError: invalid literal for int() with base 10: '12,5'
```

Первые 213 строк уже записаны. Накладная не закрыта, остатки на 213 позиций разошлись с фактическим товаром на складе. Кладовщик не видит, на какой строке всё сломалось, и повторяет приёмку целиком. Теперь первые 213 позиций задваиваются, и расхождение растёт.

**Исключение это объект, который несёт тип, сообщение и путь вызовов, а обработка ошибки это решение о том, что делать дальше.** Сообщение на экране лишь верхушка: по нему человек понимает, что случилось, а программа по типу ошибки выбирает, какой код должен сработать. Пока эти две вещи смешаны, любая ошибка выглядит одинаково: «что-то пошло не так».

## Что несёт исключение

Когда Python встречает `int("12,5")`, он не возвращает специальное значение и не печатает текст. Он создаёт объект класса `ValueError` и передаёт управление вверх по стеку вызовов, пока кто-нибудь не перехватит этот объект. Если не перехватил никто, интерпретатор печатает трассировку и завершает программу.

У объекта исключения есть несколько частей. Тип отвечает на вопрос «какая категория сбоя», и именно по типу программа принимает решение. Аргументы и сообщение объясняют подробности для человека. Трассировка хранит последовательность вызовов от точки запуска до места сбоя. Причина, если её сохранили, указывает на ошибку, из которой выросла текущая.

| Исключение | Когда возникает | Пример в «Склад+» |
|---|---|---|
| `ValueError` | значение правильного типа, но недопустимое | количество «12,5» вместо целого |
| `TypeError` | значение неподходящего типа | остаток сложили со строкой |
| `KeyError` | в словаре нет ключа | в записи нет поля `cell` |
| `IndexError` | индекс за пределами последовательности | строка накладной короче ожидаемой |
| `ZeroDivisionError` | деление на ноль | средний расход при нулевом периоде |
| `FileNotFoundError` | файл не найден | нет файла выгрузки остатков |
| `PermissionError` | нет прав на файл или папку | запись в чужой каталог |
| `ConnectionError` | сеть или сервер недоступны | обрыв связи с базой |

Все системные исключения Python растут от `BaseException`. Внутри неё есть `Exception`, а уже от неё происходят `ValueError`, `TypeError`, `LookupError` с наследниками `KeyError` и `IndexError`, `OSError` с наследниками `FileNotFoundError` и `PermissionError`. Практический вывод простой: перехватывая `Exception`, вы ловите почти всё, что может случиться в обычной программе, но не трогаете `KeyboardInterrupt` и `SystemExit`.

В C# устроено похоже. Базовый класс `System.Exception`, от него `SystemException`, а дальше `ArgumentException`, `FormatException`, `InvalidOperationException`, `IOException`. Собственные классы наследуют от `Exception` или от общего доменного предка. Разница в том, что C# проверяет типы при компиляции, поэтому часть ошибок видна ещё до запуска, а исключения остаются для ситуаций, которые нельзя проверить заранее: данные из файла, ответ сети, ввод пользователя.

Главное правило: **ловить нужно по типу, а не по тексту сообщения**. Текст предназначен человеку, его переводят, дополняют и меняют между версиями. Тип стабилен и участвует в выборе ветки кода. Проверка вида «если в сообщении есть слово "12,5"» ломается при первом же изменении формулировки.

```python
def parse_quantity(text):
    return int(text)

for raw in ["12", "12,5"]:
    try:
        print(raw, "->", parse_quantity(raw))
    except ValueError as err:
        print(raw, "->", type(err).__name__, ":", err)
```

Вывод показывает, что во втором случае управление ушло в `except`, а программа продолжила работу:

```text
12 -> 12
12,5 -> ValueError : invalid literal for int() with base 10: '12,5'
```

Обратите внимание на формат последней строки. Мы печатаем `type(err).__name__`, то есть имя класса, и только потом сообщение. Такой вывод сразу говорит, какая ветка обработки сработала бы, если бы обработчиков было несколько.

## Как работает try

Конструкция `try` делит код на две части: то, что может не получиться, и то, что должно произойти при сбое. Внутри `try` стоит обычная последовательность действий. В `except` перечислены типы, которые этот участок умеет обрабатывать. Между ними Python ищет совпадение по классу и его предкам.

У конструкции есть четыре блока, и у каждого своя роль.

| Блок | Когда выполняется | Что туда пишут |
|---|---|---|
| `try` | до первого исключения | действия, которые могут дать исключение |
| `except` | при совпадении типа | реакция на конкретную ошибку |
| `else` | если исключения не было | продолжение работы после успеха |
| `finally` | всегда, даже при выходе | освобождение ресурсов |

Порядок обработчиков важен. Python проверяет их сверху вниз и выбирает первый подходящий. Поэтому конкретный тип ставят раньше общего: `except ValueError` перед `except Exception`. Если поменять местами, второй обработчик перехватит всё, и первый станет недостижимым.

```python
try:
    number = int("12,5")
except ValueError as err:
    print("ValueError:", err)
finally:
    print("finally выполнился")

try:
    number = int("12,5")
except (ValueError, TypeError) as err:
    print("перехвачено:", type(err).__name__)

try:
    number = int("12,5")
except Exception as err:
    print("широкий перехват:", type(err).__name__)
```

Во всех трёх случаях срабатывает `ValueError`, поэтому вывод называет один и тот же класс:

```text
ValueError: invalid literal for int() with base 10: '12,5'
finally выполнился
перехвачено: ValueError
широкий перехват: ValueError
```

`finally` полезен, когда после ошибки нужно закрыть файл, вернуть соединение в пул или снять блокировку. В Python для файлов чаще используют `with`, но `finally` остаётся страховкой для случаев, где контекстного менеджера нет. В C# ту же роль играет `finally` внутри `try`.

Ловить исключение имеет смысл только тогда, когда участок знает, что с ним делать. Если обработчик просто печатает «ошибка» и продолжает, он не решает проблему, а переносит её дальше в менее понятном виде. Если обработчик возвращает значение по умолчанию, он скрывает сбой от вызывающего кода. Хороший обработчик делает одно из трёх: исправляет ситуацию, переводит ошибку в понятную форму для своего уровня или освобождает ресурс и передаёт ошибку выше.

## Собственная ошибка

Системные исключения описывают язык и платформу, а не предметную область. `ValueError` говорит, что значение недопустимо, но не говорит, какое поле, какая строка накладной и что делать кладовщику. Для этого вводят собственный класс ошибки.

Собственное исключение это обычный класс, унаследованный от `Exception` или от общего предка проекта. В нём есть сообщение и, что важнее, поля с данными: артикул, запрошенное количество, доступный остаток. Вызывающий код может прочитать эти поля и построить ответ, не разбирая текст сообщения.

```python
class SkladError(Exception):
    """Базовая ошибка учебной системы."""


class StockShortage(SkladError):
    def __init__(self, sku, requested, available):
        self.sku = sku
        self.requested = requested
        self.available = available
        super().__init__(
            f"Товар {sku}: запрошено {requested}, доступно {available}"
        )


def reserve(product, qty):
    if qty > product["stock"]:
        raise StockShortage(product["sku"], qty, product["stock"])
    product["stock"] -= qty
    return product["stock"]


product = {"sku": "SKU-1042", "stock": 40}
try:
    reserve(product, 55)
except StockShortage as err:
    print(type(err).__name__, ":", err)
    print("не хватает:", err.requested - err.available)
print("остаток после отказа:", product["stock"])
print("остаток после резерва:", reserve(product, 25))
```

Функция `reserve` проверяет условие до изменения состояния. Если товара не хватает, остаток остаётся прежним, а вызывающий код получает объект с тремя полями:

```text
StockShortage : Товар SKU-1042: запрошено 55, доступно 40
не хватает: 15
остаток после отказа: 40
остаток после резерва: 15
```

Иерархия здесь не украшение. Общий предок `SkladError` позволяет на границе приложения написать один обработчик для всех ошибок предметной области. Конкретный `StockShortage` позволяет складу или API отреагировать по-своему: предложить меньшее количество, показать остаток, вернуть код 409. Один класс на все случаи заставил бы вызывающий код снова разбирать сообщение.

В C# тот же приём выглядит так:

```csharp
using System;
using System.Text;

class SkladException : Exception {
    public SkladException(string message) : base(message) { }
}

class StockShortageException : SkladException {
    public string Sku { get; private set; }
    public int Requested { get; private set; }
    public int Available { get; private set; }

    public StockShortageException(string sku, int requested, int available)
        : base("Товар " + sku + ": запрошено " + requested + ", доступно " + available) {
        Sku = sku;
        Requested = requested;
        Available = available;
    }
}

class Program {
    static int Reserve(int stock, int qty, string sku) {
        if (qty > stock) {
            throw new StockShortageException(sku, qty, stock);
        }
        return stock - qty;
    }

    static void Main() {
        Console.OutputEncoding = Encoding.UTF8;
        try {
            Console.WriteLine("остаток: " + Reserve(40, 55, "SKU-1042"));
        } catch (StockShortageException err) {
            Console.WriteLine(err.GetType().Name + ": " + err.Message);
            Console.WriteLine("не хватает: " + (err.Requested - err.Available));
        }
    }
}
```

Вывод совпадает по смыслу с питоновским:

```text
StockShortageException: Товар SKU-1042: запрошено 55, доступно 40
не хватает: 15
```

| Действие | Python | C# |
|---|---|---|
| Объявить предка | `class SkladError(Exception)` | `class SkladException : Exception` |
| Вызвать конструктор предка | `super().__init__(...)` | `: base(...)` |
| Объявить поле | `self.sku = sku` | `public string Sku { get; private set; }` |
| Поднять ошибку | `raise StockShortage(...)` | `throw new StockShortageException(...)` |
| Перехватить | `except StockShortage as err` | `catch (StockShortageException err)` |

Имена классов в двух языках отличаются традицией: в Python суффикс `Error` привычнее, в C# суффикс `Exception` почти обязателен. Важнее другое: класс ошибки должен называть ситуацию, а не настроение разработчика. `BadThingHappened` бесполезен, `StockShortage` говорит и о причине, и о том, какие данные приложены.

## Стек вызовов и причина сбоя

Сообщение об ошибке отвечает на вопрос «что случилось», а стек отвечает на вопрос «где и через что прошло управление». В накладной из начала лекции одного сообщения мало: непонятно, какая функция вызвала разбор количества и почему строка оказалась дробной.

Питоновская трассировка хранит кадры вызовов. Каждый кадр знает имя функции, файл и строку. Если ошибку перехватили, трассировку можно прочитать из `err.__traceback__` и превратить в последовательность имён.

```python
import traceback

def read_price(text):
    return int(text)

def read_line(text):
    return read_price(text)

def import_batch(rows):
    total = 0
    for row in rows:
        total += read_line(row)
    return total

try:
    import_batch(["120", "80", "12,5"])
except ValueError as err:
    frames = traceback.extract_tb(err.__traceback__)
    print("ошибка:", err)
    print("путь:", " -> ".join(frame.name for frame in frames))
```

Путь читается от запуска к месту сбоя: модуль, затем `import_batch`, затем `read_line`, затем `read_price`, где и произошёл сбой.

```text
ошибка: invalid literal for int() with base 10: '12,5'
путь: <module> -> import_batch -> read_line -> read_price
```

Теперь представьте, что `read_price` умеет объяснить ошибку по-своему, но не хочет её проглатывать. Она может поднять новую ошибку с понятным текстом и сохранить исходную как причину. В Python для этого есть `raise ... from err`.

```python
class SkladError(Exception):
    pass


def parse_quantity(text):
    try:
        return int(text)
    except ValueError as err:
        raise SkladError(
            f"количество должно быть целым числом, получено {text!r}"
        ) from err


try:
    parse_quantity("12,5")
except SkladError as err:
    print(type(err).__name__, ":", err)
    print("причина:", type(err.__cause__).__name__, ":", err.__cause__)
```

Вывод показывает обе части: понятное сообщение верхнего уровня и исходную системную ошибку.

```text
SkladError : количество должно быть целым числом, получено '12,5'
причина: ValueError : invalid literal for int() with base 10: '12,5'
```

Без `from` Python тоже сохранит связь, но положит её в `__context__` с формулировкой «во время обработки предыдущего исключения». Такая связь появляется неявно и легко теряется, если между `except` и `raise` выполнить ещё код. `from` делает намерение явным: эта ошибка выросла из той.

В C# аналог называется внутренним исключением. Его передают вторым аргументом конструктора.

```csharp
using System;
using System.Text;

class Program {
    static int ParseQuantity(string text) {
        try {
            return int.Parse(text);
        } catch (FormatException err) {
            throw new ArgumentException("количество должно быть целым числом: " + text, err);
        }
    }

    static void Main() {
        Console.OutputEncoding = Encoding.UTF8;
        try {
            Console.WriteLine(ParseQuantity("12,5"));
        } catch (ArgumentException err) {
            Console.WriteLine(err.GetType().Name + ": " + err.Message);
            Console.WriteLine("внутренняя ошибка: " + err.InnerException.GetType().Name);
        }
    }
}
```

Внутренняя ошибка остаётся доступной через `InnerException`, даже если верхний уровень показывает только своё сообщение.

```text
ArgumentException: количество должно быть целым числом: 12,5
внутренняя ошибка: FormatException
```

Причина нужна не для красоты. По ней разработчик отличает ошибку данных от ошибки кода. Если под сообщением «не удалось сохранить накладную» лежит `sqlite3.OperationalError: database is locked`, проблема в блокировке базы, а не в накладной. Если под ним `KeyError: 'cell'`, в записи не хватает поля, и это дефект разбора. Одинаковый текст наверху скрывает разные причины, и время на поиск растёт.

В журнал при сбое пишут тип, сообщение, идентификаторы операции и данные, стек и причину. Не пишут пароли, токены и персональные данные целиком. Строка журнала должна позволять восстановить ход событий, но не создавать новую утечку.

## Граница модуля

Если ловить ошибку в каждой функции, программа превращается в набор обработчиков, которые мешают друг другу. Верхний уровень видит только «что-то не получилось», нижний уже потерял данные, а середина решила вернуть `None`. Поэтому перехват ставят на границе: там, где код встречается с внешним миром и где есть полномочия решить судьбу операции.

| Слой | Что делает с ошибкой | Что отдаёт дальше |
|---|---|---|
| Доступ к данным | переводит сбой драйвера в `StorageError`, сохраняя причину | `StorageError` с причиной |
| Бизнес-логика | проверяет правила, поднимает доменную ошибку | `SkladError` с полями |
| Интерфейс командной строки | перехватывает `SkladError`, печатает понятный текст | код возврата 2 |
| HTTP-обработчик | переводит тип ошибки в код состояния | 400, 404, 409 |
| Точка входа | ловит непредвиденное, пишет стек в журнал | код возврата 3 |

Граница это не обязательно `main`. Для консольной программы это функция запуска, для API обработчик запроса, для фоновой задачи одна итерация цикла. Общее у них одно: дальше ошибку обрабатывать некому, и именно здесь принимают решение, что увидит пользователь и что попадёт в журнал.

```python
class SkladError(Exception):
    pass


def import_stock(rows):
    result = []
    for number, row in enumerate(rows, 1):
        sku, qty = row.split(";")
        if int(qty) < 0:
            raise SkladError(f"строка {number}: отрицательное количество {qty}")
        result.append((sku, int(qty)))
    return result


def main(rows):
    try:
        data = import_stock(rows)
    except (SkladError, ValueError) as err:
        print("Импорт отменён:", err)
        return 2
    print("Загружено позиций:", len(data))
    return 0


print("код возврата:", main(["SKU-1042;12", "SKU-2087;4", "SKU-3310;8"]))
print("код возврата:", main(["SKU-1042;12", "SKU-2087;4", "SKU-3310;-8"]))
```

Первый запуск проходит целиком, второй отменяет весь пакет и возвращает код 2. Ни одна строка не записана, потому что проверка идёт до записи.

```text
Загружено позиций: 3
код возврата: 0
Импорт отменён: строка 3: отрицательное количество -8
код возврата: 2
```

Именно этого не хватило в сценарии с 07:40. Программа проверяла и писала строку за строкой, поэтому падение на 214-й оставило 213 записей. Правильная схема для пакета: сначала разобрать и проверить все строки, затем записать результат одной операцией. Если запись идёт в базу, её оформляют транзакцией, но и без базы правило «сначала проверить, потом менять» спасает от половины накладной.

Есть ещё одно правило границы: **не превращать ошибку в `None`**. Функция, которая при сбое возвращает `None`, заставляет каждого вызывающего помнить о проверке. Забыл один, и через десять строк появляется `AttributeError: 'NoneType' object has no attribute 'stock'`, который указывает не на причину, а на следствие. Исключение идёт вверх само, и его нельзя случайно проигнорировать.

Код возврата это часть контракта программы. Ноль означает успех, два означает отказ проверки, три означает непредвиденный сбой. Скрипт автоматизации читает код и решает, повторять ли запуск. Если все ошибки возвращают ноль, вызывающая сторона считает ночную выгрузку успешной, хотя ни одна строка не записана.

Сообщение пользователю и сообщение журналу это разные тексты. Пользователю нужно действие: «проверьте количество в строке 214», а журналу нужны тип, идентификатор операции и стек. Один и тот же объект ошибки может дать оба текста, если у него есть поля.

::/gate

::gate Что произойдёт, если перехватить ошибку в каждой функции?

## Типичные ошибки

**Пустой обработчик.** `except Exception: pass` выглядит как аккуратность, а работает как выключатель сигнализации. Импорт возвращает пустой список, отчёт строится по нулям, и никто не знает, что 380 строк не прочитаны. Симптом: операция «успешна», результат пуст.

**Широкий `try` вокруг всего запуска.** Если обернуть `main` целиком в `except Exception`, обработчик поймает и неверный ввод, и опечатку в имени переменной. Дефект кода будет выглядеть как ошибка данных, а журнал получит одну строку без контекста. Симптом: «иногда не работает», воспроизвести не удаётся.

**Проверка по тексту сообщения.** Код вида `if "не хватает" in str(err)` ломается, когда сообщение переписали или когда язык интерфейса сменился. Для решения нужен тип и поля, для человека сообщение.

**Потеря причины.** `raise SkladError("не удалось сохранить")` без `from` оставляет разработчика с одним текстом. В журнале нет исходной ошибки, и поиск начинается с нуля. Симптом: сообщение одинаковое для блокировки базы, нехватки места и неверного пароля.

**Возврат значения вместо ошибки.** Функция `find_product` при отсутствии товара возвращает `None`, а вызывающий код сразу читает `product["stock"]`. Симптом: `TypeError` вдалеке от места, где товар не нашли.

**`return` внутри `finally`.** Такой `return` отменяет исключение, которое шло наружу. Симптом: операция завершилась «успешно», хотя внутри был сбой. `finally` предназначен для освобождения ресурсов, а не для возврата значений.

**Повторное логирование на каждом уровне.** Ошибку записали в журнал в трёх функциях и подняли дальше. Симптом: одна причина занимает три строки, и по журналу трудно понять, сколько на самом деле было сбоев. Логируют один раз, на границе, где ошибка превращается в ответ.

| Ошибка | Вход | Симптом |
|---|---|---|
| `except Exception: pass` | строка «12,5» | импорт «прошёл», позиций 0 |
| широкий `try` | опечатка `prodct` | сообщение «неверные данные» |
| проверка по тексту | смена формулировки | ветка перестала срабатывать |
| `raise` без `from` | блокировка базы | причина потеряна |
| `None` вместо ошибки | товар не найден | `TypeError` через десять строк |
| `return` в `finally` | любой сбой | операция считается успешной |

## Итоги

- Исключение это объект с типом, сообщением, стеком и причиной, а не просто текст на экране.
- Тип выбирает ветку обработки, сообщение объясняет ситуацию человеку.
- Собственный класс ошибки несёт поля предметной области и позволяет обработать сбой без разбора текста.
- `raise ... from err` и `InnerException` сохраняют исходную причину сбоя.
- Перехватывают на границе модуля, где есть полномочия решить судьбу операции, а не в каждой функции.
- Ошибку не глотают и не заменяют на `None`: иначе дефект всплывёт далеко от места сбоя.

::quiz
Q: Что несёт объект исключения кроме текста сообщения?
+ Тип, стек вызовов и причину
- Только имя файла и номер строки
- Настройки проекта и версию Python
- Пароль пользователя и токен сессии
! По типу программа выбирает обработчик, по стеку и причине разработчик находит источник сбоя.

Q: Какой блок выполняется всегда, даже если исключение не перехвачено?
+ `finally`
- `else`
- `except`
- `try`
! `finally` нужен для освобождения ресурсов при любом исходе.

Q: Что означает исключение `ValueError`?
+ Значение правильного типа, но недопустимое
- Значение неподходящего типа
- В словаре нет нужного ключа
- Файл не найден
! Пример: строка «12,5» не превращается в целое число.

Q: Зачем нужен собственный класс ошибки?
+ Он несёт поля предметной области и отдельный тип для обработки
- Он ускоряет работу интерпретатора
- Он заменяет сообщение об ошибке на код возврата
- Он отключает трассировку
! Вызывающий код читает поля, а не разбирает текст.

Q: Где ставят перехват исключения?
+ На границе модуля, где есть полномочия решить судьбу операции
- В каждой функции на всякий случай
- Только внутри циклов
- Только в конструкторе класса
! Внутренние слои передают ошибку выше, не скрывая её.

Q: Что делает `raise SkladError(...) from err`?
+ Сохраняет исходную ошибку как причину новой
- Печатает обе ошибки в консоль
- Отменяет новую ошибку и оставляет старую
- Превращает ошибку в предупреждение
! Причина доступна через `__cause__` и помогает найти источник.

Q: Почему `except Exception: pass` опасен?
+ Он скрывает сбой и оставляет программу работать с неверными данными
- Он замедляет программу при каждом запуске
- Он запрещает использовать `finally`
- Он меняет тип исключения
! Операция выглядит успешной, хотя данные не обработаны.

Q: Чем системное исключение отличается от собственного?
+ Системное описывает язык и платформу, собственное описывает ситуацию предметной области
- Системное всегда важнее собственного
- Собственное нельзя перехватить
- Системное существует только в C#
! Собственный класс добавляет смысл и поля конкретной системы.

Q: Что произойдёт, если повторно запустить приёмку после падения на 214-й строке?
+ Первые 213 позиций задвоятся
- Программа продолжит с 214-й строки
- Накладная закроется автоматически
- Остатки не изменятся
! Без транзакции и проверки всего пакета повтор создаёт дубли.

Q: Какие признаки делают сообщение об ошибке полезным?
+ Указано, что делали и с какими данными
+ Указано, что произошло и что делать дальше
+ Сохранена причина сбоя
- В сообщение добавлен пароль пользователя
- Текст заменён на слово «ошибка»
! Сообщение должно помогать человеку и не раскрывать секреты.

Q: Что стоит записывать в журнал при сбое?
+ Тип и сообщение исключения
+ Идентификаторы операции и данные
+ Стек вызовов и причину
- Пароли и токены доступа
- Полный дамп памяти без необходимости
! Журнал должен позволять восстановить ход событий и не создавать утечку.

Q: Где уместен перехват исключения?
+ В обработчике HTTP-запроса
+ В функции запуска консольной программы
+ В цикле фоновой задачи на одну итерацию
- В каждом геттере класса
- Внутри конструктора собственной ошибки
! Перехват нужен там, где ошибка превращается в ответ или в запись журнала.

Q: Какие ошибки нельзя проглатывать?
+ Все, потому что любая скрытая ошибка искажает результат
- Только ошибки сети
- Только ошибки ввода
- Только ошибки базы данных
! Проглатывание любой ошибки лишает вызывающий код информации.

Q: Как называется объект, который несёт тип, сообщение и стек вызовов?
= исключение
= exception
! Именно этот объект передаётся вверх по стеку до обработчика.

Q: Какой блок выполняется, если в `try` не было исключения?
= else
= блок else
! `else` отделяет успешное продолжение от обработки ошибок.
