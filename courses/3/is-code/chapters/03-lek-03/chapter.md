## Четырнадцать файлов в корне

В первый день в проекте «Склад+» новый разработчик открывает папку и видит четырнадцать файлов подряд: `main.py`, `main_new.py`, `main_final.py`, `main2.py`, `test.py`, `test2.py`, `settings.py`, `settings_old.py`, `db.sqlite`, `dump.sql`, `temp.py`, `check.py`, `backup.zip`, `notes.txt`. В задаче написано «поправить расчёт резерва в отчёте». Он ищет слово «резерв» и находит три версии формулы: в `main.py`, в `main_new.py` и в `service.py`. Какая из них работает на площадке в Туле, неизвестно.

Полдня уходит на выяснение, какой файл настоящий. Ещё полдня на то, чтобы понять, почему правка в `main.py` ничего не меняет: приложение запускают из `main_new.py`, а `main.py` остался от прошлой попытки. Это не история про неаккуратного разработчика. Это история про отсутствие договорённости о местах.

**Структура проекта это договорённость о том, где лежит каждая часть работы, чтобы файл можно было найти по вопросу, а не по памяти автора.** Хорошая структура отвечает на вопрос «где расчёт остатка» быстрее, чем поиск по всему диску. Плохая заставляет читать четырнадцать файлов, чтобы понять, какой из них живой.

## Зачем проекту структура

Структура нужна не для красоты дерева в отчёте. У неё четыре потребителя, и каждый предъявляет свои требования.

**Человек** ищет место по смыслу задачи. Если нужно правило приёмки, он открывает модуль приёмки, а не листает корень. Предсказуемость экономит не минуты, а часы: новый участник выходит на рабочую скорость за день, а не за неделю.

**Инструменты** опираются на имена каталогов. `pytest` ищет файлы `test_*.py` по проекту, и каталог `tests/` делает этот поиск предсказуемым. Линтер настраивают на `src/`, чтобы он не проверял копии в `.venv`. Сборщик читает `pyproject.toml`. Когда файлы разбросаны, каждый инструмент приходится настраивать вручную, и настройки расходятся у разных разработчиков.

**Сборка** должна понимать, что входит в пакет, а что нет. База данных, журналы и виртуальное окружение не являются частью приложения. Если они лежат рядом с кодом, однажды они попадут в архив релиза или в репозиторий.

**История изменений** становится читаемой, когда правка одной задачи затрагивает предсказуемый набор файлов. В Git видно, что изменилось в модуле, тесте и документе, и ревью не тонет в переименованиях.

| Вопрос | Где искать | Пример |
|---|---|---|
| Как считается доступный остаток? | service | src/sklad/service/stock.py |
| Как достаются строки из базы? | repo | src/sklad/repo/stock.py |
| Как выглядит экран отчёта? | ui | src/sklad/ui/report.py |
| Чем подтверждено правило? | tests | tests/service/test_stock.py |
| Как запустить проект? | docs | docs/run.md |
| Что нужно установить? | корень | pyproject.toml |

Структура не обязана быть уникальной. В Python принято несколько раскладок, и каждая работает, если выдержана во всём проекте. Опасна не нестандартность, а смешение: половина модулей в `src/`, половина в корне, тесты в двух местах, настройки и в файле, и в коде. Тогда любой инструмент приходится настраивать под каждую часть отдельно.

## Верхний уровень проекта

Верхний уровень проекта это несколько каталогов с ясным назначением. Их не должно быть много: чем меньше дверей, тем легче запомнить, куда идти.

| Каталог или файл | Что внутри | Чего там быть не должно |
|---|---|---|
| src/ | код приложения | тесты, база, пароли |
| tests/ | автоматические проверки | копии рабочего кода |
| docs/ | требования, схема, инструкции | черновики и личные заметки |
| data/ | учебные данные | боевая база склада |
| migrations/ | скрипты изменения схемы | ручные правки таблиц |
| pyproject.toml | имя проекта, зависимости, команды | секреты и пароли |
| README.md | как запустить и что где лежит | история проекта на десять страниц |
| .gitignore | что не хранить в репозитории | список всех файлов проекта |

Каталог `src/` называют исходным корнем. Внутри него лежит пакет `sklad`, а не файлы россыпью. Такое расположение иногда называют src-layout: код отделён от корня проекта, и импорт `import sklad` находит установленный пакет, а не случайный файл из текущего каталога.

Разница видна на практике. Если пакет лежит в корне, запуск из папки проекта может подхватить одноимённый модуль из другого места или старую копию. Если код в `src/`, тесты проверяют именно то, что собрано и установлено. Для учебного проекта это дисциплинирует: нельзя случайно запустить не тот файл.

`README.md` это входная дверь проекта. В нём коротко: что делает система, какие нужны версии Python и библиотек, как создать окружение, как запустить приложение и тесты. README не заменяет документацию, но отвечает на первые вопросы нового человека за пять минут. Если для запуска нужно прочитать переписку, README написан плохо.

Каталог `tests/` повторяет структуру `src/`. Тест правила остатка лежит в `tests/service/test_stock.py`, тест запроса в `tests/repo/test_stock_repo.py`. Зеркальность не украшение: по имени теста сразу понятно, какой модуль он проверяет, а при переносе модуля видно, что перенести вместе с ним.

## Внутри src: пакеты по предмету

Внутри `src/sklad/` код делят на пакеты. Для «Склад+» выбрано деление по слоям, потому что предметных областей пока четыре: приёмка, отгрузка, остатки, накладные, и каждая небольшая.

```text
sklad-plus/
  src/
    sklad/
      __init__.py
      __main__.py
      config.py
      ui/
        __init__.py
        menu.py
        report.py
      service/
        __init__.py
        stock.py
        receiving.py
        shipping.py
        invoice.py
        roles.py
      repo/
        __init__.py
        stock.py
        receiving.py
  tests/
    service/
      test_stock.py
      test_receiving.py
      test_shipping.py
      test_invoice.py
      test_roles.py
    repo/
      test_stock_repo.py
  docs/
    requirements.md
    schema.md
    run.md
  data/
    demo.sqlite
  migrations/
    001_init.sql
  pyproject.toml
  README.md
  .gitignore
```

Файл `__init__.py` превращает каталог в пакет и задаёт его публичное имя. Он может быть пустым, и это нормально: пустой файл сообщает Python, что `sklad.service` это пакет, а не просто папка. Складывать в него весь код не нужно.

Имя модуля отвечает на вопрос «что здесь». `receiving.py` содержит приёмку, `invoice.py` накладную, `stock.py` остатки. Имена вида `helpers.py`, `utils.py`, `common.py` допустимы, только если внутри действительно общие вещи без предметного смысла, и таких файлов должно быть мало. Чаще всего `utils.py` разрастается до свалки, куда складывают всё, что жалко удалить.

| Задача | Модуль | Тест |
|---|---|---|
| новая проверка при приёмке | src/sklad/service/receiving.py | tests/service/test_receiving.py |
| формат номера накладной | src/sklad/service/invoice.py | tests/service/test_invoice.py |
| запрос остатков по площадке | src/sklad/repo/stock.py | tests/repo/test_stock_repo.py |
| пункт меню «Отгрузка» | src/sklad/ui/menu.py | проверяется вручную или сквозным тестом |

Выбор места начинается с вопроса о причине изменения, а не с типа файла. Проверка «ячейка хранения обязательна» меняется вместе с правилами склада, значит, это сервис. Запрос «выбрать остатки по площадке» меняется вместе со схемой, значит, это репозиторий. Подпись кнопки меняется вместе с интерфейсом, значит, это представление.

Имена пакетов пишут латиницей, строчными буквами, без пробелов и дефисов: `sklad`, `service`, `receiving`. Дефис в имени пакета невозможен, потому что Python использует его как минус в выражении импорта. Русские имена файлов технически допустимы, но создают проблемы при переносе между системами и в командной строке, поэтому в коде их избегают, а в документации пишут свободно.

Глубина вложенности тоже имеет предел. Три уровня (`sklad/service/stock.py`) читаются легко, шесть уровней (`sklad/modules/core/domain/entities/stock/model.py`) заставляют прокручивать дерево и не добавляют смысла. Если путь длиннее четырёх уровней, скорее всего, часть уровней можно убрать.

## Файлы конфигурации и зависимостей

Код и настройки разделяют, потому что у них разная судьба. Код один для всех площадок, настройки у каждой свои. Пароль к базе вообще не должен попадать в репозиторий.

| Файл | Назначение | В репозитории |
|---|---|---|
| pyproject.toml | имя, версия, зависимости, команды сборки | да |
| requirements.txt | список пакетов для установки | да, если используется |
| .env | значения для текущей машины, включая секреты | нет |
| .env.example | перечень переменных без значений | да |
| .gitignore | что исключить из репозитория | да |
| .venv/ | виртуальное окружение | нет |
| data/demo.sqlite | учебная база | обычно да, если небольшая |
| var/ | журналы, выгрузки, временные файлы | нет |

`pyproject.toml` это главный файл проекта. В нём записаны имя пакета, версия, зависимости и команды. Одна строка зависимостей фиксирует библиотеку, а версия рядом не даёт ей обновиться неожиданно. Для учебного проекта достаточно нескольких строк, но они должны быть, иначе на другой машине установка превращается в угадывание.

`config.py` читает настройки и отдаёт их остальному коду. Он не хранит пароль, а берёт его из переменной окружения или файла `.env`, которого нет в репозитории. В репозитории лежит `.env.example` с именами переменных и пустыми значениями, чтобы новый человек знал, что заполнить.

```text
SKLAD_DB=data/demo.sqlite
SKLAD_LOG_LEVEL=INFO
```

Такая запись ничего не раскрывает и показывает состав настроек. Пароль в примере заменяют на пустое место или на слово `change_me`. Если пароль попал в историю Git, его считают скомпрометированным и меняют, а не пытаются удалить коммит.

Версии зависимостей фиксируют не из любви к точности. Библиотека, которая обновилась между сборками, может изменить поведение так, что тесты упадут не в том месте. В `pyproject.toml` указывают допустимый диапазон, а в lock-файле точные версии, которые действительно установлены. Тогда на учебной машине и на стенде собирается одно и то же окружение, а расхождение объясняется, а не ищется наугад.

## Точка входа и пакет

Приложение запускают командой `python -m sklad`. Python находит пакет `sklad`, выполняет файл `__main__.py` и передаёт ему управление. Команда работает из любого каталога, где пакет установлен, и не зависит от того, какая папка открыта в терминале.

| Команда | Что происходит | Когда использовать |
|---|---|---|
| python -m sklad | выполняется `__main__.py` пакета | основной способ для проекта |
| python src/sklad/__main__.py | путь добавляется в sys.path, импорты могут сломаться | разовая отладка |
| sklad | команда из pyproject.toml | после установки пакета |
| python -m pytest | запускаются тесты | проверка перед коммитом |

В `__main__.py` лежит функция `main` и защита `if __name__ == "__main__":`. Защита нужна, чтобы модуль можно было импортировать в тесте и не запускать приложение. Без неё импорт `sklad.__main__` начнёт открывать базу и ждать ввода команд.

Точка входа не должна разрастаться. Её работа: прочитать настройки, собрать объекты, запустить цикл. Всё, что похоже на правило, уходит в сервис. Если в `__main__.py` появился запрос `SELECT`, значит, структура проекта уже нарушена, даже если каталоги выглядят правильно.

Настройки проверяют на входе. Если путь к базе пуст или файл не найден, приложение должно сказать об этом понятной строкой, а не падать с `TypeError` через двадцать вызовов. Проверка настроек относится к точке входа, потому что только она знает, в каком окружении запущено приложение. Сервис получает уже готовое соединение и не занимается выяснением, где лежит файл.

## tests, docs, data

Несколько каталогов заслуживают отдельного разговора, потому что именно в них чаще всего складывают лишнее.

**tests/** содержит тесты и тестовые данные. Тест повторяет структуру модулей, а общие фикстуры лежат в `conftest.py`. Тестовые базы и файлы небольшие и создаются заново при каждом прогоне. Если тест требует боевую базу склада, он перестаёт быть тестом и становится ручной проверкой.

Фикстура это подготовка состояния перед тестом: создать таблицу, наполнить её четырьмя площадками, открыть соединение. Фикстуры выносят в `conftest.py`, чтобы каждый тест не повторял двадцать строк настройки. Тестовые данные хранят рядом с тестами, а не в `data/`, если они нужны только проверке: так видно, что они не являются учебным набором.

**docs/** содержит требования, схему данных и инструкцию запуска. Это документы, по которым работают другие люди, а не личные заметки. Черновик с вопросом «а как тут резерв» остаётся в переписке или в задаче, но не в `docs/`. Иначе через месяц никто не отличит действующую инструкцию от размышления.

**data/** содержит учебные данные: небольшую базу с четырьмя площадками и несколькими десятками позиций. Полные 4800 позиций в репозиторий не кладут: файл тяжёлый, а для проверки правил хватает выборки. Полный набор генерируют скриптом или берут из выгрузки.

Каталог `var/` появляется во время работы: журналы, выгрузки накладных, временные файлы. Его добавляют в `.gitignore`, потому что содержимое зависит от машины и не является частью проекта. Если журнал нужен для разбора дефекта, его прикладывают к задаче, а не коммитят.

| Каталог | Живёт долго | Попадает в Git | Кто использует |
|---|---|---|---|
| tests/ | да | да | разработчик, сборка |
| docs/ | да | да | команда, новый участник |
| data/ | да, если небольшая | да | демонстрация, тесты |
| var/ | нет | нет | приложение во время работы |
| .venv/ | пока идёт работа | нет | конкретная машина |

::/gate

## Проверка структуры скриптом

Договорённость легко нарисовать и легко нарушить. Скрипт проверки читает дерево и сообщает о трёх типичных расхождениях: нет обязательного каталога, в корне появился файл Python, у правила нет теста.

```python
from pathlib import Path
import sys

root = Path(sys.argv[1])
required = ["src/sklad", "tests", "docs", "pyproject.toml"]

for item in required:
    if not (root / item).exists():
        print(f"нет: {item}")

for path in sorted(root.glob("*.py")):
    print(f"лишний файл в корне: {path.name}")

rules = {
    path.stem
    for path in (root / "src" / "sklad" / "service").glob("*.py")
    if path.name != "__init__.py"
}
tests = {
    path.stem.removeprefix("test_")
    for path in (root / "tests" / "service").glob("test_*.py")
}
for name in sorted(rules - tests):
    print(f"правило без теста: {name}")
```

Запуск на дереве, где остался старый `main.py`, а тест приёмки ещё не написан, даёт две строки.

```text
лишний файл в корне: main.py
правило без теста: receiving
```

Первая строка говорит, что в корне остался старый запуск. Вторая говорит, что для приёмки нет теста. Скрипт не проверяет качество кода и не знает, тот ли это `main.py`, который нужен. Он лишь сужает область внимания перед ревью.

Проверку ставят в сборку, чтобы она выполнялась при каждом изменении. Тогда структура перестаёт зависеть от аккуратности отдельного человека. Новый файл в корне не пройдёт проверку, и автор добавит его в нужный каталог до слияния, а не через полгода.

Скрипт проверяет только то, что можно выразить путём. Он не увидит модуль, который лежит на своём месте, но содержит чужие обязанности, и не отличит тест, который действительно проверяет правило, от теста, который вызывает функцию и ничего не утверждает. Поэтому проверка дерева дополняет ревью, а не заменяет его. Хороший порядок такой: скрипт отсекает формальные нарушения, человек смотрит смысл.

## Типичные ошибки

**Тесты рядом с кодом в src.** Симптом: пакет при установке тащит тесты, а `pytest` может собрать не тот набор. Лечение: тесты в `tests/`, структура зеркальная.

**Настройки в коде.** Симптом: на стенде приложение открывает чужую базу. Причина: путь записан строкой в модуле. Лечение: `config.py` и переменные окружения.

**Виртуальное окружение в Git.** Симптом: репозиторий весит сотни мегабайт, а у коллеги не работает установка. Лечение: `.venv/` в `.gitignore`, зависимости в `pyproject.toml`.

**Слишком глубокая вложенность.** Симптом: путь не помещается в окно, а новый человек не понимает, чем `domain` отличается от `core`. Лечение: убрать уровни, за которыми нет отдельной причины изменения.

**Свалка в utils.py.** Симптом: файл на 800 строк, который импортирует полпроекта. Лечение: разложить по предметным модулям, оставить действительно общее.

**Файлы main2 и final.** Симптом: непонятно, какая версия работает. Лечение: одна точка входа, история изменений в Git, старые версии не хранят копиями.

**Дубли имён без контекста.** Два файла `stock.py` в `service/` и `repo/` это нормально, потому что пакет задаёт контекст. Два файла `stock.py` в корне и в `src/` это ошибка, потому что непонятно, какой из них импортируется.

## Практический вывод

Откройте свой учебный проект и нарисуйте его дерево до третьего уровня. Проверьте по нему три вопроса. Где лежит правило расчёта остатка? Где лежит его тест? Где лежит путь к базе? Если ответы находятся за десять секунд, структура работает. Если для ответа нужно открыть несколько файлов, начните с переноса тестов и настроек, потому что это самые дешёвые изменения.

Полезно договориться о правиле заранее: новый файл появляется только в существующем каталоге с понятным назначением. Если для файла нет места, сначала обсуждают каталог, а потом создают файл. Иначе через месяц в корне снова окажется `main_final.py`, и поиск начнётся заново.

## Итоги

- Структура это договорённость о местах, которая позволяет найти файл по смыслу задачи.
- Верхний уровень проекта: src, tests, docs, data, migrations и файлы сборки.
- Внутри src код делят на пакеты по слоям или предметным областям, глубина больше четырёх уровней не нужна.
- Настройки живут в config.py и переменных окружения, секреты не попадают в репозиторий.
- Запуск идёт через `python -m sklad`, точка входа собирает приложение и не содержит правил.
- Тесты повторяют структуру кода, а проверка дерева выполняется в сборке.
- README отвечает на первые вопросы запуска, docs на рабочие вопросы команды.
- Каталог var/ для журналов и выгрузок не попадает в репозиторий.
- Проверка дерева в сборке удерживает договорённость без напоминаний.
- Секреты хранят вне репозитория, а в примере оставляют только имена переменных.
