## Цель работы

Собрать историю учебного проекта `sklad-plus` так, чтобы по ней можно было понять, что и зачем менялось. Вы инициализируете репозиторий, настроите `.gitignore`, сделаете серию коммитов, проверите историю и отправите проект в удалённый репозиторий.

Результат работы это ссылка на репозиторий, в котором нет лишних файлов, а каждый коммит отвечает на вопрос «зачем». История становится документом проекта: по ней видно, когда появился расчёт остатка, когда к нему добавились тесты и почему в проекте оказался именно такой список зависимостей.

История нужна не для отчёта. Через месяц по ней ищут причину поломки, откатывают неудачное изменение и объясняют новому участнику, как устроен проект. Репозиторий, в котором лежит виртуальное окружение, база и файл с паролем, эту задачу не решает: в нём трудно найти нужное изменение, а секрет остаётся в истории навсегда.

## Оборудование и программное обеспечение

- Персональный компьютер с Git версии 2.28 или новее.
- VS Code с встроенным терминалом.
- Браузер и учётная запись GitHub.
- Папка проекта `.../sklad-plus` с исходным кодом, тестами и файлами данных.
- Текстовый редактор для отчёта, например Word или LibreOffice Writer.

Права администратора не нужны. Git устанавливается в пользовательский профиль, а удалённый репозиторий создаётся в личной учётной записи GitHub.

## Краткие теоретические сведения

Git хранит не разницу между версиями, а снимки состояния проекта. У каждого снимка есть автор, дата, сообщение и ссылка на предыдущий снимок. Из этих ссылок складывается история, которую можно читать, сравнивать и восстанавливать.

Работа проходит через три области. Рабочий каталог это файлы на диске. Индекс это набор изменений, подготовленных к следующему коммиту. Репозиторий это сохранённые снимки. Команда `git add` переносит изменение в индекс, команда `git commit` превращает индекс в снимок.

| Область | Что содержит | Как посмотреть | Как изменить |
|---|---|---|---|
| Рабочий каталог | файлы на диске | `git status` | редактировать файлы |
| Индекс | то, что войдёт в коммит | `git status --short` | `git add`, `git restore --staged` |
| Репозиторий | снимки и история | `git log` | `git commit` |

Сообщение коммита пишут в повелительном наклонении и отвечают им на вопрос «что делает этот коммит». «Добавить расчёт свободного остатка» лучше, чем «Изменения» или «Правки». Если одной строки мало, после пустой строки добавляют тело: что было не так, что изменилось и на что это влияет. В учебном проекте достаточно первой строки, но она должна быть конкретной.

Один коммит содержит одно законченное изменение. Если в коммите смешаны новая функция, исправление дефекта и переименование файлов, его трудно проверить и невозможно аккуратно откатить. Дробление на небольшие коммиты не усложняет работу: оно делает историю читаемой, а откат безопасным.

Файл `.gitignore` перечисляет то, что не должно попадать в репозиторий: виртуальное окружение, кеш Python, базу данных, журналы, собранные артефакты и файлы с секретами. Шаблоны читаются сверху вниз, `*` заменяет любую часть имени, завершающая косая черта указывает на каталог. Настроить игнор нужно до первого коммита: удалить секрет из истории позже гораздо сложнее, чем не добавлять его.

Удалённый репозиторий это общая копия истории на сервере. Локальная ветка `main` и её удалённая копия `origin/main` двигаются отдельно. Команда `git push` отправляет локальные коммиты на сервер, `git pull` забирает чужие. При первой отправке флаг `-u` связывает локальную ветку с удалённой, чтобы дальше не указывать имя сервера.

## Ход работы

### Шаг 1. Проверьте Git и настройки автора

Откройте терминал в папке проекта и проверьте версию:

```text
git --version
```

```text
git version 2.48.1.windows.1
```

Версия ниже 2.28 не поддерживает команду `git init -b main`, поэтому в ней ветку переименовывают отдельно. Проверьте, что Git знает автора коммитов:

```text
git config --global user.name
git config --global user.email
```

Если команды ничего не выводят, задайте значения. Имя и почта попадут в каждый коммит, поэтому указывайте учебные или рабочие данные, а не вымышленные.

```text
git config --global user.name "Имя Фамилия"
git config --global user.email "study@example.ru"
```

Настройки можно задать только для одного проекта, если убрать флаг `--global` и выполнить команду внутри папки. Заполните таблицу проверки.

| Проверка | Команда | Результат |
|---|---|---|
| Версия Git | `git --version` |  |
| Имя автора | `git config --global user.name` |  |
| Почта автора | `git config --global user.email` |  |

### Шаг 3. Настройте игнор файлов

Создайте в корне проекта файл `.gitignore`. Начните с одной строки и объясните её: `.venv/` исключает каталог виртуального окружения целиком, потому что его содержимое восстанавливается командой установки зависимостей.

```text
.venv/
```

Добавьте шаблоны для кеша Python, базы, журналов, собранных артефактов и файла с секретами. Для каждого шаблона запишите, что именно он исключает и почему этот файл не нужен в истории.

| Шаблон | Что исключает | Почему не храним |
|---|---|---|
| `.venv/` | виртуальное окружение | восстанавливается установкой зависимостей |
|  |  |  |
|  |  |  |
|  |  |  |
|  |  |  |

Проверьте, что Git видит только нужные файлы:

```text
git status --short
```

```text
?? .gitignore
?? README.md
?? docs/
?? requirements.txt
?? src/
?? tests/
```

Два знака вопроса означают неотслеживаемый файл. Если в списке появились `.env`, `sklad.db` или `logs/`, шаблон написан неверно. Проверить конкретный путь можно командой `git check-ignore -v`:

```text
git check-ignore -v .env logs/app.log sklad.db
```

```text
.gitignore:4:.env	.env
.gitignore:5:logs/	logs/app.log
.gitignore:6:*.db	sklad.db
```

Вывод показывает номер строки, шаблон и путь. Если команда ничего не вывела, файл не игнорируется и попадёт в коммит.

### Шаг 4. Сделайте первый коммит

Добавьте в индекс только те файлы, которые описывают каркас проекта. Перечисляйте файлы явно, чтобы случайная база или журнал не попали в снимок.

```text
git add .gitignore README.md requirements.txt src/app.py
git status --short
```

```text
A  .gitignore
A  README.md
A  requirements.txt
A  src/app.py
```

Буква `A` в первом столбце означает, что файл добавлен в индекс. Создайте коммит с сообщением, которое объясняет назначение изменения:

```text
git commit -m "Добавить каркас проекта и список зависимостей"
```

```text
[main (root-commit) 2f3632e] Добавить каркас проекта и список зависимостей
 4 files changed, 12 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 README.md
 create mode 100644 requirements.txt
 create mode 100644 src/app.py
```

Первый коммит называют корневым. В нём ещё нет родителя, поэтому история начинается с него. Проверьте, что рабочее состояние чистое:

```text
git status
```

```text
On branch main
nothing to commit, working tree clean
```

### Шаг 5. Разделите работу на серию коммитов

Ниже перечислены изменения, которые нужно внести в проект. Разложите их по коммитам так, чтобы каждый коммит можно было проверить отдельно. Для первой строки сообщение дано как образец, остальные сформулируйте сами.

| Изменение | Файлы | Сообщение коммита |
|---|---|---|
| Расчёт свободного остатка | `src/stock.py` | `Добавить расчёт свободного остатка` |
| Маршрут выдачи остатка | `src/api.py` |  |
| Тест расчёта остатка | `tests/test_stock.py` |  |
| Инструкция запуска | `README.md` |  |
| Список зависимостей | `requirements.txt` |  |

После каждого изменения выполняйте три команды: `git status`, `git add` с нужным файлом, `git commit` с сообщением. Не добавляйте все файлы сразу командой `git add .`: она захватит и то, что вы ещё не проверили.

В конце проверьте, что получилось не меньше пяти коммитов:

```text
git log --oneline
```

```text
0b3c5d7 Зафиксировать зависимости проекта
7c9d1e2 Описать запуск проекта
a47f901 Проверить расчёт остатка тестом
5e2f8c1 Добавить маршрут выдачи остатка
c39a972 Добавить расчёт свободного остатка
2f3632e Добавить каркас проекта и список зависимостей
```

Это пример истории из шести коммитов, у вас порядок и сообщения могут отличаться. Если коммитов меньше, часть работы слилась в один снимок. Разделить уже сделанный коммит сложнее, поэтому лучше сразу планировать шаги.

### Шаг 6. Прочитайте историю

История отвечает на вопросы, которые возникают при разборе поломки: что менялось, когда и в каком файле. Проверьте три команды и запишите, что показывает каждая.

```text
git log --oneline
git show --stat HEAD
git diff HEAD~2..HEAD --stat
```

```text
a47f901 Проверить расчёт остатка тестом
 tests/test_stock.py | 5 +++++
 1 file changed, 5 insertions(+)
```

```text
 src/stock.py        | 2 ++
 tests/test_stock.py | 5 +++++
 2 files changed, 7 insertions(+)
```

Примеры выше относятся к истории, где последним идёт коммит с тестом. `git show` показывает один коммит и статистику файлов. `git diff HEAD~2..HEAD` сравнивает состояние два коммита назад с текущим. Заполните таблицу по своей истории.

| Команда | Что показывает | Что видно в вашем проекте |
|---|---|---|
| `git log --oneline` |  |  |
| `git show --stat HEAD` |  |  |
| `git diff HEAD~2..HEAD --stat` |  |  |

### Шаг 7. Исправьте последний коммит

Ошибку в сообщении последнего коммита исправляют командой `git commit --amend`. Она заменяет последний снимок новым, поэтому хэш коммита меняется. Пример ниже показывает случай, когда в последний коммит забыли добавить файл: сначала его добавляют в индекс, затем выполняют команду.

```text
git add README.md
git commit --amend -m "Описать запуск проекта"
```

```text
[main 18a57b0] Описать запуск проекта
 Date: Sat Oct 31 11:39:38 2026 +0500
 1 file changed, 1 insertion(+)
```

Исправлять можно только последний коммит и только до отправки в общий репозиторий. Если коммит уже отправлен, его изменение создаст расхождение у тех, кто успел забрать историю.

Иногда файл попал в индекс случайно. Убрать его из индекса, не удаляя с диска, помогает `git restore --staged`:

```text
git restore --staged README.md
```

После этого файл снова становится неотслеживаемым или изменённым, но его содержимое остаётся на месте.

### Шаг 8. Отправьте проект в удалённый репозиторий

Создайте на GitHub пустой репозиторий с именем `sklad-plus`. Не добавляйте в него README, лицензию и `.gitignore`: они уже есть в локальном проекте, и лишний коммит на сервере создаст конфликт при первой отправке.

Свяжите локальный проект с удалённым. Адрес берите со страницы своего репозитория.

```text
git remote add origin https://github.com/<учётная запись>/sklad-plus.git
git remote -v
```

```text
origin  https://github.com/<учётная запись>/sklad-plus.git (fetch)
origin  https://github.com/<учётная запись>/sklad-plus.git (push)
```

Отправьте главную ветку и свяжите её с удалённой:

```text
git push -u origin main
```

В конце вывода появятся строки о новой ветке и о том, что локальная ветка связана с `origin/main`:

```text
To https://github.com/<учётная запись>/sklad-plus.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

GitHub не принимает пароль учётной записи при отправке по HTTPS. Вместо него используют личный токен доступа, который создают в настройках профиля. Для SSH настраивают ключ и указывают адрес вида `git@github.com:<учётная запись>/sklad-plus.git`. Токен вводят вместо пароля и не сохраняют в файлах проекта.

Проверьте связь веток:

```text
git branch -vv
```

```text
* main 18a57b0 [origin/main] Описать запуск проекта
```

Квадратные скобки показывают, что ветка отслеживает удалённую. После этого достаточно команд `git push` и `git pull` без имени сервера.

| Проверка | Команда | Ожидаемый результат |
|---|---|---|
| Адрес удалённого репозитория | `git remote -v` | две строки с `origin` |
| Связь ветки | `git branch -vv` | `[origin/main]` рядом с `main` |
| Отправка | `git push` | сообщение об успешной отправке |
| Страница GitHub | браузер | видны коммиты и файлы проекта |

### Шаг 9. Проверьте, что в репозиторий не попало лишнее

Список отслеживаемых файлов показывает, что именно увидят другие участники после клонирования:

```text
git ls-files
```

```text
.gitignore
README.md
docs/schema.md
requirements.txt
src/api.py
src/app.py
src/stock.py
tests/test_api.py
tests/test_stock.py
```

Если в списке есть `.env`, `sklad.db`, `logs/app.log` или файлы из `.venv`, файл уже попал в историю. Уберите его из индекса командой `git rm --cached имя`, добавьте шаблон в `.gitignore` и сделайте отдельный коммит. Пароль, который попал в историю, считайте раскрытым: его нужно сменить, а не только удалить файл.

Проверьте игнор и рабочее состояние:

```text
git check-ignore -v .env sklad.db
git status
```

```text
.gitignore:4:.env	.env
.gitignore:6:*.db	sklad.db
On branch main
nothing to commit, working tree clean
```

Заполните итоговую таблицу проверки репозитория.

| Что проверить | Как проверить | Результат |
|---|---|---|
| В репозитории нет секретов | `git ls-files` |  |
| База и журналы игнорируются | `git check-ignore -v` |  |
| Все изменения закоммичены | `git status` |  |
| Удалённая копия совпадает | `git branch -vv` |  |

## Требования к отчёту

Отчёт оформляется в Word или LibreOffice Writer на 3-5 страниц. В нём должны быть цель работы, состав проекта, таблица файлов с решением о хранении, содержимое `.gitignore` с объяснением шаблонов, список коммитов с сообщениями и вывод команд проверки.

Для каждого коммита укажите, какое законченное изменение он содержит. Для каждого шаблона игнора объясните, почему файл не хранится в репозитории. В конце приведите ссылку на удалённый репозиторий и один абзац о том, что изменилось бы в истории, если бы все файлы попали в один коммит.

Приложите снимок вывода `git log --oneline` и снимок страницы репозитория на GitHub. На снимке истории должны быть видны хэши, сообщения и порядок коммитов; на снимке GitHub должны быть видны файлы проекта и отсутствие `.env`, базы и виртуального окружения.

## Что сдать

- ссылку на удалённый репозиторий `sklad-plus` с историей не меньше чем из пяти коммитов;
- файл `.gitignore` с шаблонами для окружения, кеша, базы, журналов и артефактов;
- вывод `git log --oneline` и `git status` после последнего коммита;
- таблицу файлов проекта с решением о хранении и объяснением;
- отчёт на 3-5 страниц с описанием коммитов и проверкой репозитория.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: репозиторий создан с веткой `main`, игнор закрывает окружение, кеш, базу, журналы и артефакты; история содержит не меньше пяти осмысленных коммитов, каждый коммит описывает одно изменение; сообщения конкретны; проект отправлен на GitHub, лишние файлы отсутствуют; отчёт содержит все таблицы и объяснения.
- **4**: история и игнор выполнены, но один коммит объединяет два изменения или одно сообщение сформулировано общими словами; проект отправлен, проверка репозитория выполнена не полностью.
- **3**: репозиторий создан и коммиты есть, но `.gitignore` закрывает не все лишние файлы, сообщения не объясняют изменение, отправка на GitHub не выполнена или выполнена без проверки содержимого.
- **2**: работа не выполнена или репозиторий не содержит истории изменений.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
