## Проект, который работал только у автора

На консультации перед защитой приложение открывается с полпинка. Автор показывает вход, добавляет товар, строит отчёт и уверенно говорит, что всё готово. Через день тот же проект запускают на учебной машине, и он не стартует. База лежит в папке автора и в репозиторий не попала. Пароль записан прямо в коде и меняется только в одном месте, о котором знает один человек. README отсутствует, поэтому непонятно, какую команду выполнять первой. Вход работает с тестовой учётной записью, которую автор добавил вручную месяц назад.

Проект был почти готов. Не хватило нескольких вещей, каждая из которых кажется мелочью, пока не попробуешь повторить работу на другом компьютере. Именно эту проверку и проходит итоговый проект: не «получилось ли у автора», а «получится ли у другого человека по инструкции и без вопросов».

**Итоговый проект это работающая система с проверяемыми артефактами, а не самый большой файл за семестр.** Артефакт это то, что можно открыть, запустить, выполнить или сравнить: скрипт схемы, файл базы, набор тестов, коллекция запросов, README, описание API. Чем больше решений подтверждено артефактами, тем меньше остаётся места для рассказа вместо доказательства.

В курсе есть сквозной пример «Склад+»: 120 сотрудников, четыре площадки, 12 товарных категорий и 4800 позиций на складе. Он показывает масштаб и связи, но итоговый проект каждый выбирает сам. Предметная область может быть другой: прокат инструмента, заявки на ремонт, запись на приём, учёт оборудования в мастерской. Требования к устройству системы остаются теми же.

## Что считается итоговым проектом

Итоговый проект это небольшая информационная система, которую можно целиком объяснить коротко. В ней есть данные, правила работы с ними, пользователи с разными правами, программный интерфейс и способ запуска. Всё остальное считается расширением и добавляется только после того, как обязательная часть работает.

Границы задаются числами, а не ощущением «пока не надоест». Минимум нужен, чтобы проверить все изученные темы: базу, доступ к данным, бизнес-логику, вход, API, тесты и документацию. Максимум нужен, чтобы проект остался обозримым и его можно было закончить.

| Признак | Минимум | Что проверяют |
|---|---|---|
| Предметная область | одна, понятная без длинного пояснения | тему можно назвать одним предложением |
| Сущности | 4-6 таблиц со связями | ключи, внешние ключи, справочники |
| Роли | 3 роли с разными правами | запрет настраивается на сервере, а не в интерфейсе |
| Сценарии | 5-7 законченных действий | каждый сценарий имеет начало, результат и проверку |
| Маршруты API | 6-8 маршрутов | чтение, создание, изменение, удаление и вход |
| Тесты | не меньше 10 модульных и 3 интеграционных | проверяются и успешные, и ошибочные случаи |
| Документы | README и описание API | по ним проект поднимает другой человек |

Числа не случайны. Четыре таблицы уже дают одну главную сущность, справочник, таблицу пользователей и связь между ними. Шесть таблиц позволяют показать связь «многие ко многим» и историю операций. Три роли дают разные права: администратор управляет справочниками, менеджер оформляет операции, обычный пользователь видит только свои записи. Пять сценариев покрывают вход, чтение, создание, изменение и отчёт. Если сценариев меньше, часть модулей останется без применения и её невозможно проверить.

Копировать «Склад+» целиком не нужно и вредно. В нём 4800 позиций, четыре площадки и десяток отчётов, потому что это пример промышленной системы. Для итогового проекта достаточно одной площадки и одного склада, но схема, вход и API должны быть устроены так же честно, как в большом примере.

## Обязательные модули

Модуль это часть системы с понятной ответственностью и проверяемым результатом. Список ниже не является меню, из которого выбирают половину. Каждый модуль закрывает отдельный риск: без него проект либо не запускается, либо не доказывает, что автор умеет работать с соответствующей темой.

| Модуль | Артефакт | Критерий готовности |
|---|---|---|
| Репозиторий и каркас | каталоги `src`, `tests`, `docs`, `db`, файлы `README.md`, `requirements.txt`, `.gitignore` | проект клонируется, структура видна без пояснений |
| База данных | `db/schema.sql` и файл базы | схема создаётся с нуля одной командой, внешние ключи включены |
| Доступ к данным | модуль с запросами и соединением | значения передаются параметрами, соединение закрывается |
| Бизнес-логика | функции проверки и операции | правила не размазаны по обработчикам маршрутов |
| Вход и роли | таблица пользователей и модуль проверки пароля | пароль хранится хешем, роли проверяются на сервере |
| API | 6-8 маршрутов и единый формат ошибки | успех и отказ различаются кодом состояния |
| Интерфейс | командная строка или веб-страница | главный сценарий проходится без правки кода |
| Тесты | набор модульных и интеграционных проверок | прогон зелёный на чистой копии проекта |
| Документация и запуск | README, описание API, пример настроек | другой человек повторяет запуск по инструкции |

Репозиторий и каркас задают место каждому файлу. Если код, тесты и скрипты базы лежат в корне вперемешку, проверяющий тратит время на поиск точки входа, а автор путается в собственных файлах. Каркас нужен не для красоты: он показывает, что разработчик умеет отделять исходный код от данных, тестов и документации.

База данных хранит не только строки, но и правила. Первичный ключ не даёт создать дубль, внешний ключ не даёт сослаться на несуществующую запись, `CHECK` не даёт записать отрицательный остаток. Если все ограничения проверяются только в Python, база постепенно накопит мусор: достаточно одной программы, которая пишет в неё напрямую.

Доступ к данным отделяют от бизнес-логики, чтобы запросы не повторялись в каждом обработчике. Один модуль знает, как открыть соединение, выполнить параметризованный запрос и превратить строку в объект. Обработчик маршрута вызывает функцию и не занимается SQL. Такое разделение упрощает тесты: функцию доступа можно проверить на учебной базе, не поднимая веб-сервер.

Бизнес-логика отвечает на вопросы предметной области. Можно ли вернуть инструмент после срока? Какие поля обязательны при создании заявки? Кто имеет право отменить операцию? Если ответы записаны в одном месте, их можно проверить тестами. Если они разбросаны по кнопкам интерфейса, при появлении второго клиента (командной строки или API) правила придётся писать заново.

Вход и роли закрывают доступ. Пароль хранится не в открытом виде, а в виде хеша с солью. Роль и признак блокировки проверяются на сервере перед каждым действием. Интерфейс может скрыть кнопку, но запрос всё равно можно отправить из Postman, поэтому запрет должен жить в коде, который обрабатывает запрос.

API делает функции системы доступными извне. Шесть-восемь маршрутов достаточно, чтобы показать чтение списка, чтение одной записи, создание, изменение, удаление, вход и один отчёт. У каждого ответа есть код состояния, а у ошибки единый формат с полем `error` и, где нужно, списком проблемных полей.

Интерфейс нужен не для украшения. Он показывает, что систему можно использовать, не зная внутреннего устройства. Командная строка подходит, если сценарий понятен и выполняется последовательностью команд. Веб-страница подходит, если важны формы и таблицы. В любом случае главный сценарий должен проходиться без правки исходного кода.

Тесты подтверждают, что правила работают после изменений. Модульные проверяют отдельные функции: расчёт стоимости, проверку даты, разбор строки. Интеграционные проверяют связку: маршрут, база и ответ. Отрицательные случаи обязательны, потому что именно они показывают, что система умеет отказывать.

Документация и запуск завершают проект. README отвечает на вопросы «что это», «как установить», «как запустить», «как проверить». Описание API перечисляет маршруты, параметры, ответы и ошибки. Пример настроек показывает, какие переменные окружения нужны, не раскрывая секретов. Если инструкция проверена на чистой машине, проект перестаёт зависеть от памяти автора.

## Готовность как пропускная способность

Считать готовность процентом удобно для планирования и опасно для решения. Семь закрытых модулей из десяти дают 70 процентов, и число выглядит солидным. Но если среди трёх незакрытых оказался вход в систему, показать главный сценарий всё равно нельзя: без входа нет ролей, без ролей нет проверки прав, а без проверки прав API открыт всем.

Ниже небольшой скрипт, который считает готовность по списку модулей. У каждого модуля есть код, название, признак обязательности и признак выполнения. Скрипт печатает таблицу, находит блокирующие пункты и возвращает код завершения: ноль, если проект готов, и единицу, если нет.

```python
import sys

MODULES = [
    {"code": "repo", "title": "Репозиторий и каркас", "required": True, "done": True},
    {"code": "db", "title": "Схема базы и справочники", "required": True, "done": True},
    {"code": "data", "title": "Доступ к данным", "required": True, "done": True},
    {"code": "logic", "title": "Бизнес-логика и CRUD", "required": True, "done": True},
    {"code": "auth", "title": "Вход и роли", "required": True, "done": True},
    {"code": "api", "title": "Маршруты API и ошибки", "required": True, "done": True},
    {"code": "ui", "title": "Интерфейс", "required": True, "done": True},
    {"code": "tests", "title": "Тесты", "required": True, "done": False},
    {"code": "docs", "title": "Документация и запуск", "required": True, "done": False},
    {"code": "report", "title": "Дополнительный отчёт", "required": False, "done": False},
]


def report(modules):
    total = len(modules)
    done = sum(1 for m in modules if m["done"])
    percent = round(100 * done / total)
    print(f"Модулей: {total}, закрыто: {done}, готовность: {percent}%")
    for m in modules:
        mark = "готово" if m["done"] else "нет"
        print(f"{m['code']:<8}{m['title']:<32}{mark}")
    blocking = [m["title"] for m in modules if m["required"] and not m["done"]]
    if blocking:
        print("Блокирующие пункты: " + ", ".join(blocking))
        print("Вердикт: проект не готов к защите")
        return 1
    print("Вердикт: проект готов к защите")
    return 0


if __name__ == "__main__":
    sys.exit(report(MODULES))
```

Вывод на учебном наборе выглядит так:

```text
Модулей: 10, закрыто: 7, готовность: 70%
repo    Репозиторий и каркас            готово
db      Схема базы и справочники        готово
data    Доступ к данным                 готово
logic   Бизнес-логика и CRUD            готово
auth    Вход и роли                     готово
api     Маршруты API и ошибки           готово
ui      Интерфейс                       готово
tests   Тесты                           нет
docs    Документация и запуск           нет
report  Дополнительный отчёт            нет
Блокирующие пункты: Тесты, Документация и запуск
Вердикт: проект не готов к защите
```

Семь модулей из десяти закрыты, но вердикт отрицательный. Скрипт не пытается усреднить качество: он отделяет сведения от решения. Процент отвечает на вопрос «сколько сделано», список блокирующих пунктов на вопрос «что именно мешает показать проект». Для плана работ полезны оба ответа, для допуска к защите только второй.

Проверка списка не заменяет проверку кода. Скрипт читает признаки, которые заполнил автор, и не знает, действительно ли тесты проходят, а README описывает текущие маршруты. Поэтому каждый признак должен опираться на артефакт: тесты на зелёный прогон, README на запуск с чистой копии, API на коллекцию запросов. Самопроверка без артефакта превращается в оптимистичный список.

| Ситуация | Процент | Вердикт |
|---|---|---|
| все десять модулей закрыты | 100 | готов |
| не закрыт дополнительный отчёт | 90 | готов |
| не закрыт вход | 90 | не готов |
| не закрыты тесты и документация | 80 | не готов |
| не закрыты база и API | 80 | не готов |

Разница между второй и третьей строкой показывает, зачем нужен признак обязательности. Необязательным может быть дополнительный отчёт или экспорт, без которого главный сценарий работает. Вход, база и API необязательными не бывают: без них система не выполняет обещанное.

## План работ по этапам

План строят от результата, а не от списка тем. У каждого этапа есть законченный результат, который можно показать, и критерий, по которому видно, что этап закрыт. Пока результата нет, следующий этап не начинают: иначе схема базы пишется под функции, которых ещё нет, а тесты проверяют код, который скоро перепишут.

| Этап | Результат | Критерий готовности |
|---|---|---|
| 1. Заявка и каркас | заявка на проект и репозиторий с каталогами | 11 обязательных путей на месте, первый коммит отправлен |
| 2. Схема и вход | `schema.sql` и модуль проверки пароля | 4-6 таблиц, четыре сценария входа проверены |
| 3. Операции CRUD | создание, чтение, изменение и удаление записи | четыре операции и пять отказов на неверных данных |
| 4. API и ошибки | маршруты и единый формат ошибки | успешный и ошибочный запрос видны в Postman |
| 5. Тесты и коллекция | модульные и интеграционные тесты | прогон зелёный, отчёт о прогоне сохранён |
| 6. Доступ и запуск | проверка ролей и запуск на чистой машине | секретов в репозитории нет, README повторяется |
| 7. Документация и слайды | README, описание API, презентация | документы совпадают с текущими маршрутами |
| 8. Защита | сценарий показа и ответы на вопросы | пять-семь сценариев показаны без правок |

Первый этап кажется подготовительным, но он задаёт границы. В заявке написано, какие сущности входят в систему, кто ею пользуется и какие сценарии считаются главными. Без заявки проект растёт в стороны: сначала добавляется экспорт в Excel, потом уведомления, потом вторая площадка, и к защите не закрыт даже вход.

Второй этап соединяет данные и доступ. Схема создаётся скриптом, а не в графическом редакторе по памяти. Модуль входа проверяется на четырёх случаях: верный пароль, неверный пароль, неизвестный логин и заблокированная запись. Если все четыре дают одинаковый отказ, пользователь не понимает, что исправлять, а проверяющий не видит разницы между ошибкой ввода и запретом.

Третий этап добавляет операции. Для каждой операции заранее выписывают, какие поля обязательны, какие значения допустимы и что происходит при нарушении. Пять отказов это минимум: пустое обязательное поле, слишком длинная строка, неверный формат даты, отрицательное число, ссылка на несуществующую запись. Проверки пишут в бизнес-логике, а не в интерфейсе, иначе API обойдёт их.

Четвёртый этап открывает операции через API. Маршрут не содержит SQL и не проверяет пароль вручную: он вызывает функцию и превращает результат в ответ. Ошибки приводят к одному формату, чтобы клиент разбирал их одинаково. На этом этапе появляется коллекция Postman, которая позже станет доказательством работы.

Пятый этап закрепляет поведение тестами. Сначала проверяют функции, которые легко изолировать, затем связку маршрута с базой. Тест на успешный сценарий обязателен, но недостаточен: если нет теста на отказ, ошибка в проверке полей останется незамеченной. Отчёт о прогоне сохраняют, потому что зелёный экран через неделю уже не докажет, что тесты проходили.

Шестой этап выносит секреты и проверяет запуск. Пароль базы, ключ подписи и адрес сервера берутся из переменных окружения, а в репозитории лежит только пример настроек. Запуск повторяют на чистой копии: клонируют репозиторий в новый каталог, создают окружение, устанавливают зависимости, создают базу, запускают приложение. Всё, что при этом пришлось доделывать вручную, дописывают в README.

Седьмой этап приводит документы в соответствие с кодом. README и описание API пишут не по памяти, а по фактическим маршрутам и ответам. Презентация содержит не скриншоты всех файлов, а схему, главный сценарий и одно трудное решение. Слайды нужны для рассказа, а не для замены работающего приложения.

Восьмой этап это репетиция. Сценарий показа прогоняют целиком на чистой базе, засекают места, где приложение ведёт себя не так, как ожидалось, и исправляют их до защиты. Вопросы задают заранее: почему выбрана такая схема, где проверяется роль, что будет при неверном пароле, какой тест ловит ошибку. Репетиция показывает не пробелы в знаниях, а пробелы в подготовке.

Этапы связаны зависимостями. Нельзя писать CRUD раньше схемы: непонятно, какие поля обязательны. Нельзя проверять роли раньше входа: неизвестно, откуда берётся роль. Нельзя писать описание API раньше стабильных маршрутов: документ устареет за один день. Порядок этапов экономит работу, а не ограничивает свободу.

> [!TRADEOFF] Сначала глубина или сначала ширина
> Можно сначала сделать все модули в минимальном виде, а потом углублять. Можно довести до блеска один модуль и не успеть закрыть остальные. Для учебного проекта выгоднее ширина: проверяющий должен увидеть все обязательные модули, а глубина одного из них не компенсирует отсутствие входа или тестов.

## Как выбрать границы

Границы проекта удобно записывать двумя списками: что входит и что не входит. Второй список важнее. Он защищает от разговоров «а почему нет экспорта» и напоминает автору, что обещанное нужно закончить, а не добавленное.

| Входит | Не входит |
|---|---|
| справочник инструмента с ценой и состоянием | бухгалтерский учёт и проводки |
| выдача и возврат с датой и клиентом | онлайн-оплата и эквайринг |
| роли администратора, менеджера и клиента | мобильное приложение и push-уведомления |
| отчёт по просроченным выдачам | обмен с внешней учётной системой |
| вход по логину и паролю | восстановление пароля по SMS |

Такой список не уменьшает проект, а делает его законченным. Каждая строка слева имеет сущность, сценарий и проверку. Каждая строка справа требует отдельной инфраструктуры, которую за учебное время не проверить. Если очень хочется добавить строку справа, её записывают в раздел «развитие» и не трогают до защиты.

Есть три признака, по которым тему стоит отклонить или сузить. Первый: нет данных, которые нужно хранить. Система «умный дом» без датчиков и журнала событий превращается в одну кнопку. Второй: все пользователи имеют одинаковые права. Тогда нечего проверять в авторизации. Третий: готовое решение скачивается из интернета целиком. Такой проект не показывает работу автора, даже если запускается.

Хорошая тема отвечает на конкретный вопрос и имеет очевидного пользователя. «Учёт заявок мастерской» лучше, чем «цифровая платформа сервиса». «Прокат инструмента» лучше, чем «маркетплейс оборудования». Конкретность не делает проект слабее: она делает его проверяемым.

## Критерии готовности

Перед защитой проект проверяют по списку, где каждый пункт можно доказать действием. Проверку выполняют на чистой копии репозитория, а не на рабочем каталоге автора. Если пункт не выполняется, его записывают в список исправлений и закрывают до показа.

| Проверка | Чем доказать |
|---|---|
| репозиторий клонируется без ошибок | новый каталог и успешный `git clone` |
| зависимости ставятся по инструкции | `requirements.txt` или файл проекта |
| база создаётся с нуля | `schema.sql` и пустой файл базы |
| приложение запускается | команда из README и открывшийся интерфейс |
| вход работает для трёх ролей | три учётные записи и разные права |
| главный сценарий проходится целиком | пять-семь действий без правки кода |
| неверные данные отклоняются | код 400 и понятное сообщение |
| тесты проходят | зелёный прогон и отчёт |
| секретов в репозитории нет | поиск по истории и `.gitignore` |
| документы совпадают с кодом | сверка маршрутов и полей |
| проект работает на другой машине | повторный запуск по README |
| есть сценарий показа | пять-семь шагов и запасной план |

Отдельно проверяют, что проект умеет отказывать. Успешный сценарий показывает, что система работает. Отказ показывает, что она защищена: неверный пароль не пускает, чужая роль не меняет запись, пустое поле не сохраняется, повторный логин не создаётся. Без отказов проверяющий видит только парадную сторону.

На защите спрашивают не «сколько строк кода», а «почему так». Ответ должен опираться на артефакт: таблицу, строку схемы, функцию, тест, запрос. Если ответ звучит как «так было удобнее», значит, решение не осознано. Если ответ показывает альтернативу и её цену, значит, автор понимает свою систему.

| Вопрос | Где искать ответ |
|---|---|
| почему эта таблица выделена отдельно | схема и связи |
| почему ключ составной | ограничение и данные |
| что будет при неверном пароле | модуль входа и тест |
| где хранится секрет | пример настроек и `.gitignore` |
| какой тест поймает ошибку | файл теста и отчёт |
| что сломается при удалении роли | проверка прав и сценарий |

## Типичные ошибки

**Проект живёт на одной машине.** Путь к базе записан абсолютным, файл базы не попал в репозиторий, инструкции нет. Симптом: на учебной машине приложение падает при старте. Лечение: относительные пути, скрипт создания базы, README с проверкой на чистой копии.

**Секреты лежат в репозитории.** Пароль базы, ключ подписи и токен записаны в коде или в `.env`, который закоммичен. Симптом: секрет виден в истории даже после удаления файла. Лечение: переменные окружения, `.env.example`, `.gitignore` до первого коммита, замена скомпрометированного секрета.

**База создаётся вручную.** Таблицы сделаны в графическом редакторе, скрипта нет. Симптом: на другой машине нет ни таблиц, ни справочников. Лечение: `schema.sql` и отдельный скрипт заполнения справочников, повторяемый запуск без дублей.

**Вход настроен для одного пользователя.** Тестовая учётная запись добавлена вручную, ролей нет, блокировка не проверяется. Симптом: проверяющий не может войти под другой ролью. Лечение: три учётные записи, хеши в базе, проверка роли и блокировки.

**API возвращает 200 на ошибку.** Клиент получает тело с текстом «ошибка», но код успеха. Симптом: форма показывает пустой список вместо сообщения. Лечение: коды 400, 401, 403, 404, 409 и единый формат ошибки.

**Тесты проверяют только успех.** Функция проверки полей не покрыта, поэтому отрицательные значения проходят. Симптом: тесты зелёные, а неверная запись сохраняется. Лечение: по одному тесту на каждый отказ.

**Документация отстала от кода.** Маршрут переименован, README описывает старый адрес. Симптом: проверяющий повторяет запрос и получает 404. Лечение: сверка документов с кодом перед защитой, описание API из фактических маршрутов.

**Проект растёт быстрее, чем закрываются модули.** Добавляются экспорт, уведомления и вторая площадка, а вход и тесты не готовы. Симптом: к защите много кода и ни одного законченного сценария. Лечение: список «не входит» и правило закрывать обязательные модули до расширений.

- Итоговый проект оценивают по проверяемым артефактам, а не по объёму кода.
- Обязательные модули: репозиторий, база, доступ к данным, логика, вход, API, интерфейс, тесты, документация и запуск.

- Перед защитой проект проверяют на чистой копии и показывают не только успех, но и отказ.
