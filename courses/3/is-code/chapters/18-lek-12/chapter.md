## Накладная, которая пришла двумя файлами

В понедельник 5 октября 2026 года в ООО «Северный склад» приходят два файла. Поставщик «ТрансЛогистика» присылает `supplies.json` с тремя поставками. Бухгалтерия выгружает `stock.csv` со справочником товаров. В справочнике 4800 позиций, 12 товарных категорий и четыре площадки: Москва, Тверь, Тула и Калуга. Кладовщик открывает оба файла и ищет товар `SKU-1042`.

В JSON количество записано как `"qty": 48`, в CSV та же величина стоит в ячейке `48`. На экране это одно и то же число. После разбора выясняется, что в первом случае программа получила целое число `48`, а во втором строку `"48"`. Пока значение только печатают, разницы не видно. Как только его складывают с другим количеством или сравнивают с порогом, строка ведёт себя иначе: `"48" + "12"` даёт `"4812"`, а `"48" > "100"` возвращает `True`, потому что строки сравниваются посимвольно.

**Формат обмена это договор о структуре данных, а не о внешнем виде файла.** Договор отвечает на вопросы: где лежит заголовок, чем разделены поля, какие значения считаются числом, что означает пустая ячейка и можно ли вкладывать один объект в другой. Если договор не описан, каждая сторона понимает его по-своему, и ошибка проявляется уже в базе склада.

Дальше разберём два формата, которые чаще всего встречаются в учебном проекте `sklad-plus`: JSON для обмена с сервисами и CSV для обмена с таблицами и бухгалтерией. Главный вопрос занятия простой: что именно формат сообщает о данных и что приходится восстанавливать вручную.

## Что на самом деле хранит JSON

JSON строится из шести видов значений: объект, массив, строка, число, логическое значение и `null`. Объект это набор пар «ключ и значение» в фигурных скобках. Массив это упорядоченный список в квадратных скобках. Всё остальное это скалярные значения.

```json
{
  "number": "НК-2026-0417",
  "warehouse": "Москва",
  "date": "2026-10-05",
  "items": [
    {"sku": "SKU-1042", "title": "Перчатки нитриловые", "qty": 48, "price": 312.50},
    {"sku": "SKU-2210", "title": "Стрейч-плёнка", "qty": 12, "price": 890.00}
  ],
  "closed": false
}
```

Разберём этот документ в Python и посмотрим на типы.

```python
import json

raw = """{
  "number": "НК-2026-0417",
  "warehouse": "Москва",
  "date": "2026-10-05",
  "items": [
    {"sku": "SKU-1042", "title": "Перчатки нитриловые", "qty": 48, "price": 312.50},
    {"sku": "SKU-2210", "title": "Стрейч-плёнка", "qty": 12, "price": 890.00}
  ],
  "closed": false
}"""

doc = json.loads(raw)
print(type(doc).__name__, list(doc))
print(doc["items"][0]["qty"], type(doc["items"][0]["qty"]).__name__)
print(doc["date"], type(doc["date"]).__name__)
print(doc["closed"], type(doc["closed"]).__name__)
print(sum(item["qty"] * item["price"] for item in doc["items"]))
```

Вывод:

```text
dict ['number', 'warehouse', 'date', 'items', 'closed']
48 int
2026-10-05 str
False bool
25680.0
```

Четыре наблюдения по этому выводу.

Первое: объект стал словарём `dict`, массив стал списком `list`, строка осталась строкой, число стало `int` или `float`, логическое значение стало `bool`. Соответствие предсказуемое, и на нём строится вся работа с JSON в Python.

Второе: дата `2026-10-05` осталась строкой. В JSON нет типа «дата». Для дат договариваются об ISO 8601, потому что такая строка сортируется как текст и однозначно читается, но проверять её всё равно должна программа. Если поставщик пришлёт `05.10.2026`, разбор не упадёт: он просто вернёт другую строку, и ошибка всплывёт позже, при сравнении или записи в базу.

Третье: `false` стало `False`. Это уже логическое значение, а не строка `"false"`. Разница существенна: `if doc["closed"]` работает, а `if doc["closed"] == "false"` никогда не выполнится.

Четвёртое: сумма `25680.0` получилась вещественной, потому что цена задана как `312.50`. Для учебного примера это нормально. Для денег в рабочей системе так поступать не стоит: двоичное представление дроби накапливает погрешность. Ниже разберём, чем заменить `float`.

Отдельно стоит сказать про порядок ключей. В спецификации JSON объект это неупорядоченный набор пар. Python сохраняет порядок вставки при разборе, и на этом удобно строить вывод, но полагаться на порядок ключей в чужом документе нельзя. Если порядок важен, используйте массив, а не объект.

## Вложенность: сила и цена

Главное преимущество JSON в том, что он хранит структуру, а не только значения. Накладная содержит список строк, и этот список лежит внутри объекта накладной. Никакой отдельной таблицы связей для этого не нужно.

К вложенному значению ведёт путь из ключей и индексов.

```python
print(doc["items"][1]["sku"])
print(doc["warehouse"])
```

```text
SKU-2210
Москва
```

Путь читается слева направо: взять ключ `items`, затем второй элемент списка, затем ключ `sku`. Если на любом шаге ключа нет, Python выбросит `KeyError`, а если индекс вышел за границы списка, то `IndexError`. Это не недостаток формата, а сигнал, что документ не соответствует договору.

Для необязательных полей используют `get`.

```python
discount = doc.get("discount", 0)
print(discount)
```

```text
0
```

Вложенность удобна, но у неё есть цена. Чем глубже структура, тем больше кода проверяет наличие промежуточных уровней. Если документ приходит от внешней системы, каждое обязательное поле стоит проверить явно и вернуть понятную ошибку с именем поля, а не молча получить `KeyError` в середине импорта.

Типичная ошибка новичка выглядит так: программа обращается к `doc["shipments"][0]["items"][0]["qty"]`, а поставщик присылает пустой список поставок. Индекс `0` падает, импорт останавливается, и в журнале остаётся только трассировка. Правильнее сначала проверить, что список не пуст, и обработать пустой документ как отдельный случай.

## CSV: таблица, у которой всё строки

CSV это текст, в котором строки файла соответствуют строкам таблицы, а поля разделены одним символом. Обычно это запятая, точка с запятой или табуляция. Первая строка часто содержит заголовок с именами столбцов.

```csv
sku;title;qty;price
SKU-1042;Перчатки нитриловые;48;312,50
SKU-2210;Стрейч-плёнка;12;890,00
```

Формат кажется простым, но у него нет единого стандарта, который соблюдали бы все программы. RFC 4180 описывает распространённое соглашение: разделитель запятая, строки разделены CRLF, поля с разделителем или переводом строки заключаются в двойные кавычки, кавычка внутри поля удваивается. Excel и русская локаль часто используют точку с запятой, потому что запятая занята десятичным разделителем. Поэтому первое, что нужно сделать при чтении CSV, это выяснить разделитель и кодировку.

Прочитаем тот же файл модулем `csv`.

```python
import csv
import io

text = (
    "sku;title;qty;price\n"
    "SKU-1042;Перчатки нитриловые;48;312,50\n"
    "SKU-2210;Стрейч-плёнка;12;890,00\n"
)

rows = list(csv.DictReader(io.StringIO(text), delimiter=";"))
print(rows[0])
print(type(rows[0]["qty"]).__name__)
print(type(rows[0]["price"]).__name__)
```

```text
{'sku': 'SKU-1042', 'title': 'Перчатки нитриловые', 'qty': '48', 'price': '312,50'}
str
str
```

`DictReader` берёт первую строку как имена полей и возвращает словари. Удобно, что порядок столбцов можно менять, а код обращается к значениям по имени. Но все значения остаются строками, включая количество и цену. Модуль `csv` не знает, что `48` это число: он видит только текст между разделителями.

Вторая особенность касается десятичной запятой. Строка `312,50` не преобразуется в число функцией `float` напрямую. Нужно заменить запятую на точку или использовать локаль. В учебном проекте выбирают один способ и фиксируют его в договоре обмена.

Третья особенность это BOM. Excel при сохранении в UTF-8 может поставить в начало файла невидимый символ `\ufeff`. Если открыть файл с кодировкой `utf-8`, этот символ попадёт в имя первого столбца.

```python
from pathlib import Path

path = Path("bom.csv")
path.write_text("\ufeffsku;qty\nSKU-1042;48\n", encoding="utf-8")

with path.open(encoding="utf-8", newline="") as file:
    reader = csv.DictReader(file, delimiter=";")
    print("поля:", reader.fieldnames)

with path.open(encoding="utf-8-sig", newline="") as file:
    reader = csv.DictReader(file, delimiter=";")
    print("поля с sig:", reader.fieldnames)
```

```text
поля: ['\ufeffsku', 'qty']
поля с sig: ['sku', 'qty']
```

Кодировка `utf-8-sig` читает BOM и отбрасывает его. Если этого не сделать, код `row["sku"]` выбросит `KeyError`, хотя столбец `sku` в файле есть. Симптом коварный: глазами файл выглядит правильным.

## Откуда берётся потеря типов

Потерю типов удобно свести в таблицу. В левом столбце поле из накладной, в среднем то, что приходит в JSON, в правом то, что приходит в CSV, и действие, которое нужно выполнить перед использованием.

| Поле | JSON | CSV | Что сделать |
|---|---|---|---|
| Количество | `48` (число) | `48` (строка) | `int(row["qty"])` |
| Цена | `312.5` (число) | `312,50` (строка) | заменить запятую, затем `Decimal` |
| Дата | `2026-10-05` (строка) | `05.10.2026` (строка) | разобрать `datetime.strptime` |
| Артикул | `SKU-1042` (строка) | `SKU-1042` (строка) | оставить строкой |
| Признак | `false` (логическое) | `0` или `нет` (строка) | сопоставить с таблицей значений |
| Пустая ячейка | `null` | пустая строка | решить, это ноль или отсутствие |

Начнём с количества. В JSON число приходит числом, потому что формат различает строку и число синтаксически: `48` без кавычек это число, `"48"` в кавычках это строка. В CSV кавычки означают только экранирование разделителя, а не тип. Поэтому `48` и `"48"` в CSV это одна и та же строка.

Цена сложнее. Даже если заменить запятую на точку и вызвать `float`, для денег получится неточное значение. Проверка `0.1 + 0.2 == 0.3` возвращает `False`, потому что двоичная дробь не представляет десятичные доли точно. В учебном проекте для цен и сумм используют `Decimal`, а в базу записывают целое число копеек или тип `NUMERIC` с фиксированной точностью.

```python
from decimal import Decimal

price = Decimal("312.50")
qty = 48
print(price * qty)
print(Decimal("0.1") + Decimal("0.2") == Decimal("0.3"))
```

```text
15000.00
True
```

Дата требует явного формата. Строка `05.10.2026` не разбирается функцией `datetime.fromisoformat`. Нужен `strptime` с шаблоном `%d.%m.%Y`. Если формат в файле может измениться, его указывают в договоре обмена и проверяют при импорте. Молчаливая попытка угадать формат приводит к тому, что часть дат читается как май, а часть как декабрь.

Артикул наоборот нельзя превращать в число. `SKU-1042` содержит буквы, поэтому остаётся строкой. Но и чисто цифровые артикулы вроде `007` опасно пропускать через `int`: ведущий ноль исчезнет, и товар перестанет находиться. Правило простое: идентификатор всегда строка, даже если выглядит числом.

Логический признак в CSV не имеет стандарта. Встречаются `true` и `false`, `1` и `0`, `да` и `нет`, `Y` и `N`. Программа должна привести их к одному типу явной таблицей соответствия, а не полагаться на `bool("false")`, который вернёт `True`, потому что непустая строка истинна. Это одна из самых частых ошибок при импорте.

Пустая ячейка тоже требует решения. В JSON есть `null`, и он отличается от нуля и от пустой строки. В CSV пустая ячейка неотличима от отсутствующего значения, если договор не задаёт правило. Для количества пустая ячейка обычно означает ноль, для цены отсутствие данных, для даты «ещё не выполнено». Одно и то же пустое место в разных столбцах означает разное, и это нужно прописать.

## Сравнение форматов

Теперь можно сравнить форматы по признакам, которые важны при обмене.

| Признак | JSON | CSV |
|---|---|---|
| Структура | дерево с вложенностью | плоская таблица |
| Типы значений | различает число, строку, логическое значение, null | все значения строки |
| Заголовок | ключи объекта | первая строка, часто обязательна |
| Повторяющиеся группы | массив внутри объекта | отдельная таблица или повторение строк |
| Читаемость для человека | средняя, много скобок | высокая, похоже на таблицу |
| Открытие в Excel | требует преобразования | открывается напрямую |
| Размер | больше из-за ключей | меньше при том же наборе полей |
| Обмен с API | естественный формат | редкий, требует описания |
| Потоковая обработка | возможна построчно, но сложнее | удобна построчно |
| Риск потери типов | низкий | высокий |

Из таблицы видно, что форматы решают разные задачи. JSON выигрывает там, где данные имеют структуру: накладная со строками, заказ с позициями, ответ сервиса с вложенными объектами. CSV выигрывает там, где данные плоские и их много: справочник товаров, остатки по складам, выгрузка для бухгалтерии.

Есть и промежуточный случай. Иногда одну и ту же информацию отдают в двух форматах: JSON для программы и CSV для человека. Это нормальная практика, если оба файла строятся из одного источника и проходят проверку. Плохо, когда два формата живут отдельно и расходятся по составу полей.

У JSON есть ограничения, о которых забывают. В нём нет комментариев, нет ссылок между объектами, нет типа «дата» и нет обязательных полей. Два документа с одинаковой структурой могут отличаться набором ключей. Поэтому JSON-схему описывают отдельно, например через JSON Schema, и проверяют документ перед импортом.

У CSV тоже есть скрытые сложности. Разделитель зависит от локали, кодировка от программы, десятичный разделитель от настроек Windows, а кавычки внутри поля требуют удвоения. Файл, который открывается в Excel, не обязательно правильно прочитается модулем `csv` с настройками по умолчанию.

## Чтение и запись в Python

Начнём с JSON. Чтение из файла выполняет `json.load`, разбор строки выполняет `json.loads`. Запись в файл выполняет `json.dump`, преобразование в строку выполняет `json.dumps`.

```python
import json

record = {"sku": "SKU-1042", "title": "Перчатки нитриловые"}

print(json.dumps(record, ensure_ascii=False, indent=2))
print(json.dumps(record))
```

```text
{
  "sku": "SKU-1042",
  "title": "Перчатки нитриловые"
}
{"sku": "SKU-1042", "title": "\u041f\u0435\u0440\u0447\u0430\u0442\u043a\u0438 \u043d\u0438\u0442\u0440\u0438\u043b\u043e\u0432\u044b\u0435"}
```

Параметр `ensure_ascii=False` оставляет кириллицу читаемой. Без него каждый русский символ превращается в последовательность `\uXXXX`. Оба варианта корректны с точки зрения JSON, но первый удобнее для чтения и меньше по размеру. Параметр `indent=2` добавляет отступы: файл становится длиннее, зато его можно сравнивать глазами и в системе контроля версий.

Для записи в файл удобно использовать контекстный менеджер.

```python
from pathlib import Path

path = Path("supplies.json")
with path.open("w", encoding="utf-8") as file:
    json.dump(record, file, ensure_ascii=False, indent=2)
```

Теперь CSV. Чтение через `DictReader` мы уже видели. Запись выполняет `DictWriter`.

```python
import csv

rows = [
    {"sku": "SKU-1042", "qty": 48},
    {"sku": "SKU-2210", "qty": 12},
]

with open("stock.csv", "w", encoding="utf-8-sig", newline="") as file:
    writer = csv.DictWriter(file, fieldnames=["sku", "qty"], delimiter=";")
    writer.writeheader()
    writer.writerows(rows)
```

Здесь важны три параметра. `encoding="utf-8-sig"` добавляет BOM, чтобы Excel правильно показал кириллицу. `newline=""` отключает преобразование переводов строк: без него на Windows каждая запись получит лишний `\r`, и в файле появятся пустые строки между данными. `delimiter=";"` задаёт разделитель, совпадающий с настройками русской локали.

Проверить результат можно повторным чтением и сравнением количества строк. Это дешевле, чем открывать файл вручную, и хорошо ложится в автоматическую проверку.

## Тот же обмен на C#

В C# для JSON есть `System.Text.Json`. Код читает документ и обходит вложенные массивы.

```csharp
using System.IO;
using System.Text.Json;

string json = File.ReadAllText(".../sklad-plus/data/supplies.json");
using JsonDocument doc = JsonDocument.Parse(json);

JsonElement root = doc.RootElement;
Console.WriteLine(root.GetProperty("supplier").GetString());

foreach (JsonElement shipment in root.GetProperty("shipments").EnumerateArray())
{
    string number = shipment.GetProperty("number").GetString()!;
    foreach (JsonElement item in shipment.GetProperty("items").EnumerateArray())
    {
        int qty = item.GetProperty("qty").GetInt32();
        decimal price = item.GetProperty("price").GetDecimal();
        Console.WriteLine($"{number} {item.GetProperty("sku").GetString()} {qty * price}");
    }
}
```

Разница с Python видна сразу: C# требует указывать тип при чтении. `GetInt32` упадёт, если в документе окажется строка `"48"`. Это не придирка языка, а полезная проверка договора: документ, который не соответствует схеме, не пройдёт дальше. В Python такая же проверка выполняется вручную или через библиотеку валидации.

Для CSV в .NET нет встроенного разборщика. Простой `line.Split(';')` ломается на поле с точкой с запятой внутри кавычек и на переводе строки внутри значения. В учебном проекте CSV читают на Python, а на C# обрабатывают JSON, либо подключают отдельную библиотеку и фиксируют её версию в файле зависимостей.

## Типичные ошибки

Ошибки удобно запоминать по симптому: что видно на экране и какая строка кода виновата.

**Лишний символ в имени столбца.** Симптом: `KeyError: 'sku'`, хотя столбец есть. Причина: BOM в начале файла, чтение с `encoding="utf-8"`. Лечение: `utf-8-sig`.

**Пустые строки при записи.** Симптом: между строками CSV появился пустой ряд. Причина: открытие файла без `newline=""` на Windows. Лечение: добавить параметр и перезаписать файл.

**Цена не преобразуется.** Симптом: `ValueError: could not convert string to float: '312,50'`. Причина: десятичная запятая. Лечение: заменить запятую или разбирать с учётом локали, для денег использовать `Decimal`.

**Дата читается неверно.** Симптом: месяц и день поменялись местами. Причина: формат `%d.%m.%Y` и `%m.%d.%Y` похожи, а даты вроде `05.10.2026` и `10.05.2026` обе допустимы. Лечение: фиксировать формат в договоре и проверять диапазон.

**JSON не разбирается.** Симптом: `json.decoder.JSONDecodeError` с указанием позиции. Частые причины: комментарий `//`, лишняя запятая после последнего элемента, одинарные кавычки вместо двойных, `NaN` вместо числа. JSON не допускает ничего из этого.

**Дубли ключей.** Симптом: значение поля не то, что ожидалось. Причина: в объекте два одинаковых ключа, парсер оставил последний. Спецификация не запрещает дубли, но и не определяет, какой ключ главный. Лечение: проверять документ на дубли до разбора.

**Файл не помещается в память.** Симптом: программа падает или начинает использовать гигабайты. Причина: `json.load` читает весь документ целиком. Лечение: потоковый разбор для больших файлов или разбиение выгрузки на части.

**Опасная формула в CSV.** Симптом: Excel выполняет содержимое ячейки. Причина: значение начинается с `=`, `+`, `-` или `@`. Лечение: экранировать такие значения при выгрузке и не открывать чужие CSV без проверки.

**Не тот разделитель.** Симптом: весь файл попал в один столбец. Причина: ожидалась запятая, а файл сохранён с точкой с запятой. Лечение: определять разделитель по заголовку и фиксировать его в договоре.

## Как выбрать формат и зафиксировать договор

Выбор формата сводится к трём вопросам. Есть ли вложенность? Кто будет открывать файл? Какие типы нужно сохранить?

| Задача | Формат | Причина |
|---|---|---|
| Ответ API с накладной и строками | JSON | вложенность и типы |
| Справочник товаров для Excel | CSV | плоская таблица, открывается напрямую |
| Обмен с бухгалтерией | CSV | привычный инструмент и простая сверка |
| Конфигурация приложения | JSON | структура и явные типы |
| Выгрузка 4800 позиций для сверки | CSV | компактность и построчная обработка |
| Журнал событий для другой системы | JSON Lines | по одному объекту на строку |

Если данные нужны и человеку, и программе, делают две выгрузки из одного источника. Это лучше, чем один файл, который каждая сторона трактует по-своему.

Договор обмена удобно оформить коротким списком. В нём указывают кодировку, разделитель, десятичный разделитель, формат даты, наличие заголовка, правило для пустых значений, способ экранирования кавычек, максимальный размер файла и версию схемы. Для CSV добавляют строку о том, что делать с BOM, а для JSON о том, какие поля обязательны.

Пример договора для файла остатков.

```text
Файл: stock.csv
Кодировка: UTF-8 с BOM
Разделитель: точка с запятой
Заголовок: обязателен, первая строка
Десятичный разделитель: запятая
Дата: ДД.ММ.ГГГГ
Пустое количество: 0
Пустая цена: ошибка импорта
Артикул: строка, ведущие нули сохраняются
Версия схемы: 2
```

Такой договор занимает полстраницы, но снимает большинство споров при импорте. Если поставщик меняет формат, он меняет версию схемы, и программа может отклонить незнакомый файл с понятным сообщением, а не испортить данные.

## Итоги

- JSON хранит дерево и различает число, строку, логическое значение и `null`, поэтому вложенные документы описываются естественно.
- CSV хранит плоскую таблицу, где все ячейки строки, а типы восстанавливает программа.
- Потеря типов проявляется в количестве, цене, дате, артикуле и логическом признаке, и каждое поле требует своего правила.
- BOM, десятичная запятая и `newline=""` это три причины большинства ошибок при работе с CSV на Windows.
- Формат выбирают по структуре данных и по тому, кто будет файл открывать, а не по привычке.
- Договор обмена фиксирует кодировку, разделитель, формат даты и правила для пустых значений.

::quiz
Q: Чем JSON отличается от CSV по структуре?
+ JSON хранит вложенные объекты и массивы, а CSV хранит плоскую таблицу
- JSON не поддерживает кириллицу, а CSV поддерживает
- CSV хранит типы значений, а JSON только строки
- JSON всегда меньше по размеру, чем CSV
! JSON это дерево, CSV это таблица с разделителями.

Q: Какое значение вернёт разбор JSON для поля `"qty": 48`?
+ Целое число 48
- Строку "48"
- Вещественное число 48.0
- Логическое значение True
! Число без кавычек разбирается как числовой тип.

Q: Почему дата в JSON остаётся строкой?
+ В JSON нет отдельного типа даты
- JSON запрещает хранить даты
- Дата всегда приходит числом
- Python не умеет читать даты
! Формат рекомендует ISO 8601, но проверять дату должна программа.

Q: Что вернёт `csv.DictReader` для столбца с количеством?
+ Строку
- Целое число
- Вещественное число
- Логическое значение
! Модуль csv не определяет типы и возвращает текст.

Q: Зачем при чтении CSV указывают кодировку `utf-8-sig`?
+ Чтобы убрать BOM из имени первого столбца
- Чтобы ускорить чтение файла
- Чтобы заменить десятичную запятую на точку
- Чтобы включить проверку типов
! BOM попадает в заголовок и ломает обращение по имени поля.

Q: Почему для денежных сумм не используют `float`?
+ Двоичная дробь накапливает погрешность
- Float не поддерживает отрицательные значения
- Float медленнее целых чисел
- Float нельзя записать в JSON
! Для денег применяют Decimal или целое число копеек.

Q: Что произойдёт, если открыть файл на запись без `newline=""` на Windows?
+ Между строками CSV появятся пустые строки
- Файл будет записан в кодировке cp1251
- Заголовок исчезнет
- Разделитель заменится на запятую
! Текстовый режим добавит лишний символ перевода строки.

Q: Какие признаки указывают на потерю типов при импорте CSV?
+ Количество приходит строкой и складывается как текст
+ Ведущий ноль в артикуле исчезает после преобразования в число
+ Десятичная запятая не преобразуется в число
- В файле есть строка заголовка
- В файле используется разделитель точка с запятой
! Потеря типов связана со строками, ведущими нулями и десятичным разделителем.

Q: Какие ошибки делают JSON недопустимым?
+ Комментарий внутри объекта
+ Запятая после последнего элемента массива
+ Одинарные кавычки вместо двойных
- Вложенный массив внутри объекта
- Кириллица в строковом значении
! JSON не допускает комментариев, висячих запятых и одинарных кавычек.

Q: В каком случае CSV удобнее JSON?
+ Плоский справочник товаров для открытия в Excel
- Ответ API с вложенными строками накладной
- Документ с массивом объектов разной структуры
- Конфигурация с вложенными настройками
! CSV хорошо подходит для плоских таблиц и работы в табличном редакторе.

Q: Что должно быть записано в договоре обмена CSV?
+ Кодировка и разделитель
+ Формат даты и правило для пустых значений
+ Десятичный разделитель
- Список сотрудников, которые будут открывать файл
- Пароль от базы данных
! Договор фиксирует технические правила разбора.

Q: Какой формат выбрать для журнала событий, где каждая запись это отдельный объект?
+ JSON Lines, по одному объекту на строку
- Один большой JSON-массив
- CSV с вложенными полями
- Текстовый файл без разделителей
! JSON Lines позволяет читать журнал построчно и дописывать новые события.

Q: Что означает параметр `ensure_ascii=False` при записи JSON?
+ Кириллица сохраняется читаемыми символами
- Кириллица заменяется на escape-последовательности
- Файл записывается без отступов
- Из документа удаляются пустые поля
! Без параметра русские буквы превращаются в `\uXXXX`.

Q: Как называется символ, который Excel ставит в начало UTF-8 файла?
= BOM
= byte order mark
! BOM это невидимая метка порядка байтов, её убирает кодировка utf-8-sig.

Q: Какой модуль Python используют для чтения и записи CSV?
= csv
= модуль csv
! Модуль csv входит в стандартную библиотеку и учитывает кавычки и разделители.
