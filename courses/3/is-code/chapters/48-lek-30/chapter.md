## Администратор, который не смог запустить сервис

В Калуге сменился администратор информационной системы. В первый день ему нужно было поднять «Склад+» на новой машине. В репозитории лежал README из трёх строк: «Установите зависимости. Запустите приложение. База создастся сама». Администратор установил зависимости, запустил команду и получил ошибку о том, что порт занят.

Он потратил три часа. Сначала искал, какой порт нужен: в коде было 8000, в старой инструкции 5000, в настройках сервера 8080. Потом выяснилось, что база не создаётся сама, а должна лежать в каталоге `data`. Потом не хватило прав на запись журнала. В итоге он позвонил в поддержку, и инженер за десять минут объяснил то, чего не было в документе.

В «Северном складе» 120 сотрудников на четырёх площадках. Служба поддержки принимает около 34 обращений в неделю, и часть из них начинается с вопроса «как запустить», «как обновить», «где взять адрес API». Каждый такой вопрос стоит времени и инженера, и пользователя. Документация сокращает эти обращения не потому, что она красивая, а потому, что человек находит ответ без звонка. Если ответ на частый вопрос есть в документе, инженер не повторяет его в двадцатый раз, а занимается сбоями. Это экономит часы поддержки каждую рабочую неделю.

**Документ это инструмент для конкретного читателя, который решает конкретную задачу.** У документа есть адресат, задача и признак успеха. Если после чтения читатель не смог выполнить действие, документ не выполнил работу, даже если в нём много страниц и красивых схем.

## Кому и зачем нужен документ

Документация проекта не является одним файлом. Это набор документов, и у каждого свой читатель. Кладовщику нужно принять товар, менеджеру сформировать накладную, администратору запустить сервис, разработчику понять, как устроен модуль, а службе поддержки разобраться с ошибкой. Один текст не может ответить всем сразу.

| Документ | Читатель | Вопрос читателя | Признак успеха |
|---|---|---|---|
| README | разработчик, администратор | как установить и запустить | проект запущен по шагам |
| Руководство пользователя | кладовщик, менеджер | как выполнить операцию | операция выполнена |
| Руководство администратора | администратор ИС | как обновить и восстановить | сервис работает после обновления |
| Описание API | разработчик интеграции | как отправить запрос | получен ожидаемый ответ |
| Архитектурная записка | разработчик, аналитик | почему сделано так | решение понятно и проверяемо |
| Журнал изменений | заказчик, поддержка | что изменилось в версии | понятно, что проверять |

README отвечает на вопрос «как поднять проект с нуля». Руководство пользователя отвечает на вопрос «как выполнить рабочую операцию». Руководство администратора отвечает на вопрос «как обслуживать систему». Описание API отвечает на вопрос «как вызвать функцию из другой программы». Архитектурная записка объясняет решения, а журнал изменений сообщает, что поменялось между версиями.

Разделение нужно не для порядка в папках. У документов разный срок жизни и разный способ проверки. README проверяют запуском на чистой машине. Руководство пользователя проверяют, дав его человеку, который не знает систему. Описание API проверяют запросами из Postman. Архитектурную записку проверяют на соответствие коду и принятым решениям.

| Читатель | Что ему нужно | Что ему не нужно |
|---|---|---|
| Кладовщик | шаги приёмки, сообщения об ошибках | схема базы и код модуля |
| Менеджер | формирование накладной, отчёты | настройки сервера |
| Администратор | запуск, обновление, копии, права | внутреннее устройство классов |
| Разработчик | структура кода, API, тесты | инструкция по приёмке товара |
| Поддержка | коды ошибок, журналы, эскалация | маркетинговое описание продукта |

## Один документ не обслуживает всех

Попытка написать «общую документацию для всех» заканчивается текстом, который не помогает никому. Кладовщик тонет в терминах `SQLite` и `WSGI`, администратор ищет команду среди описания бизнес-процессов, разработчик не находит структуру модулей. Поэтому документы разделяют по читателю, а не по типам файлов.

Разделение не означает, что документы не связаны. README ссылается на руководство администратора, руководство пользователя ссылается на описание API, журнал изменений ссылается на версию. Ссылки должны работать, а версии совпадать. Если README описывает версию 1.0.0, а руководство 0.9, читатель не поймёт, какая команда правильная.

У каждого документа есть владелец. Обычно это роль, а не человек: README ведёт разработчик, руководство пользователя аналитик или методист, описание API разработчик вместе с интегратором. Владелец обновляет документ при изменении поведения и отвечает на замечания. Без владельца документ устаревает через месяц после выпуска.

Документация входит в результат проекта, а не прикладывается к нему в конце. На приёмке заказчик проверяет не только работающее приложение, но и то, сможет ли сотрудник заказчика выполнить операцию без разработчика. Если руководство появилось за день до сдачи, его никто не проверял на чистом окружении, и первые вопросы пользователей станут первыми дефектами документа.

## Инструкция, которую можно выполнить

Инструкция состоит из предусловий, шагов, ожидаемого результата каждого шага, раздела ошибок и проверки в конце. Предусловия сообщают, что должно быть готово до начала: версия Python, доступ к базе, свободный порт, права на каталог. Шаги описывают действие, а не намерение. Ожидаемый результат позволяет понять, что шаг выполнен, не заглядывая в следующий.

Плохой шаг звучит так: «Настройте базу данных». Что именно настроить, где, с какими правами и как понять, что получилось, неизвестно. Хороший шаг называет действие и результат: «Создайте каталог `data` командой `mkdir data`. Ожидаемый результат: каталог существует и доступен на запись пользователю службы».

| Признак плохого шага | Признак хорошего шага |
|---|---|
| «Настройте окружение» | «Создайте окружение командой `python -m venv .venv`» |
| «Запустите сервис» | «Выполните `.venv/bin/python -m sklad_plus.api`, дождитесь строки `Running on`» |
| «Проверьте работу» | «Отправьте запрос `/api/health`, ожидайте код 200 и `positions` 4800» |
| «При необходимости поправьте» | «Если порт занят, измените `SKLAD_API_PORT` и перезапустите службу» |

В инструкции не должно быть формулировок «интуитивно понятно», «как обычно», «по необходимости». Они перекладывают решение на читателя, а читатель пришёл за готовым порядком. Если выбор действительно нужен, опишите условие выбора и два варианта: «если база уже есть, перейдите к шагу 5; если нет, выполните шаг 4».

Команды должны быть готовы к копированию. Место, куда подставляют значение, обозначают явно: `python -m pip install dist/sklad_plus-1.0.0-py3-none-any.whl`. Если имя файла зависит от версии, скажите, где её взять. Не оставляйте в команде уголки и многоточия без пояснения: читатель скопирует их буквально.

Предупреждения ставят перед опасным шагом, а не после. Удаление базы, смена прав, остановка службы и миграция могут привести к потере данных. Перед таким шагом указывают, что будет потеряно, как сделать копию и как отменить действие. После шага пишут, как проверить результат.

Снимки экрана помогают, если на них видно то, о чём говорит текст. К снимку добавляют подпись: что именно смотреть. Снимок окна без адреса, команды и кода ответа не подтверждает проверку. Если интерфейс меняется, снимок устаревает быстрее текста, поэтому команды и текстовые шаги остаются основой.

## README проекта

README это первый документ, который открывает новый человек. Он отвечает на вопросы: что это за проект, на чём написан, что нужно установить, как настроить, как запустить, как проверить и где искать дальше. Хороший README занимает одну-две страницы и не пересказывает весь код.

| Раздел | Что содержит | Проверка |
|---|---|---|
| Название и назначение | что делает `sklad-plus` | понятно за одно предложение |
| Стек | Python, Flask, SQLite, версии | совпадает с проектом |
| Требования | Python 3.11+, свободный порт | перечислены все зависимости |
| Установка | создание окружения и установка | команды выполняются |
| Настройки | `.env.example`, переменные | нет настоящих секретов |
| Запуск | команда и ожидаемый вывод | сервис поднимается |
| Проверка | health check и тесты | код 200, тесты зелёные |
| Структура | каталоги `src`, `tests`, `docs` | совпадает с репозиторием |
| Ошибки | три частых случая | есть признак и действие |

README начинается с назначения, а не с истории компании. «`sklad-plus` это учебная ИС склада с API на Flask и базой SQLite» даёт больше, чем абзац о миссии. Затем идут требования и команды. Секреты в README не приводят: вместо них указывают `.env.example` и объясняют, какие значения заполнить.

Проверка README проста: возьмите чистую машину или новый каталог, выполните только то, что написано, и сравните результат. Если пришлось открывать исходники, чтобы понять команду, README неполон. Если команда работает только после устного пояснения, этого пояснения не хватает в тексте.

## Пользовательская документация

Пользовательская документация строится вокруг задач, а не вокруг кнопок. Кладовщику не нужен раздел «Кнопка Сохранить», ему нужен раздел «Принять товар на склад». Внутри раздела шаги описывают сценарий: открыть накладную, проверить количество, указать ячейку, подтвердить приёмку, увидеть результат.

Сценарий начинают с предусловий: пользователь вошёл в систему, у него есть роль кладовщика, накладная создана менеджером. Затем идут шаги с ожидаемым результатом. В конце описывают, что изменилось в системе: остаток увеличился, накладная получила статус «Принята», в журнале появилась запись.

Пример сценария для приёмки занимает полстраницы. Сначала кладовщик открывает список накладных и выбирает ту, которая ожидает приёмки. Затем проверяет артикул и количество, указывает ячейку хранения и подтверждает операцию. После подтверждения он видит новое состояние накладной и обновлённый остаток. Если ячейка занята или количество не совпадает, сценарий отправляет его в раздел ошибок, а не оставляет гадать.

Термины должны совпадать с интерфейсом. Если в системе написано «Ячейка хранения», не называют её «местом» в одном разделе и «слотом» в другом. Новый термин объясняют при первом появлении. Список терминов в конце помогает, но не заменяет понятный текст.

Ошибки описывают с точки зрения пользователя. «Ошибка 500» ему ничего не говорит. «Если после подтверждения появилось сообщение о занятой ячейке, выберите другую ячейку или обратитесь к администратору» даёт действие. Для каждой частой ошибки указывают признак, причину и что делать.

Версия документа должна совпадать с версией системы. Если интерфейс изменился, старый снимок и старые названия кнопок вводят в заблуждение. Поэтому в руководстве указывают версию и дату, а при выпуске новой версии проверяют затронутые разделы.

Отдельный раздел частых вопросов собирают из обращений поддержки. Если за месяц 34 обращения повторяют одни и те же вопросы о приёмке, это не проблема пользователей, а пробел в руководстве. Вопросы формулируют словами пользователей, а ответы дают короткий порядок действий и ссылку на полный сценарий. Раздел пересматривают вместе с журналом обращений, иначе он превращается в свалку устаревших советов.

## Описание API

Описание API нужно разработчику, который вызывает сервис из другой программы. Ему нужны базовый адрес, способ авторизации, формат данных, список маршрутов, параметры, примеры запроса и ответа, коды ошибок и правила пагинации. Без этого он будет угадывать по коду и тратить время на пробы.

| Что описать | Пример для `sklad-plus` |
|---|---|
| Метод и путь | `GET /api/stock/{sku}` |
| Авторизация | заголовок `Authorization: Bearer <token>` |
| Параметры пути | `sku` это артикул вида `SKU-1042` |
| Параметры запроса | `limit` от 1 до 100, по умолчанию 20 |
| Успешный ответ | код 200, поля `sku`, `title`, `available` |
| Ошибки | 401 без токена, 404 неизвестный артикул, 500 сбой сервера |
| Формат ошибки | `{"error": "not found", "code": "SKU_NOT_FOUND"}` |

Пример запроса лучше давать в виде команды, которую можно скопировать. Пример ответа должен быть настоящим, а не придуманным. Если в описании указано поле `available`, а сервис возвращает `qty`, интеграция сломается на первом же запросе. Примеры проверяют запуском на тестовом стенде, а не переписывают из головы: только тогда описание и поведение совпадают.

Документация API бывает ручной и автоматической. Ручную таблицу пишут в Word или Markdown и проверяют запросами. Автоматическую получают из кода: FastAPI строит OpenAPI-схему по типам и маршрутам, ASP.NET Core показывает Swagger. Автоматическая схема не расходится с кодом, но её всё равно дополняют описаниями и примерами.

Проверим, как FastAPI описывает ответы маршрута. В схеме видны коды 200, 404 и 422, а также ссылки на модели данных.

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI(title="Склад+ API", version="1.0.0")

class StockItem(BaseModel):
    sku: str
    title: str
    available: int

@app.get("/api/stock/{sku}", response_model=StockItem, responses={404: {"description": "Товар не найден"}})
def get_stock(sku: str) -> StockItem:
    """Вернуть свободный остаток товара по артикулу."""
    if sku != "SKU-1042":
        raise HTTPException(status_code=404, detail="not found")
    return StockItem(sku=sku, title="Перфоратор", available=30)
```

```text
{
  "200": {
    "description": "Successful Response",
    "content": {
      "application/json": {
        "schema": {
          "$ref": "#/components/schemas/StockItem"
        }
      }
    }
  },
  "404": {
    "description": "Товар не найден"
  },
  "422": {
    "description": "Validation Error",
    "content": {
      "application/json": {
        "schema": {
          "$ref": "#/components/schemas/HTTPValidationError"
        }
      }
    }
  }
}
```

Схема показывает, что маршрут возвращает модель `StockItem`, а для неизвестного артикула описан код 404. Код 422 появляется автоматически: FastAPI проверяет типы параметров и сообщает об ошибке валидации. Разработчику интеграции этого достаточно, чтобы понять формат и не гадать о кодах.

Документация в коде тоже полезна. Строка документации рядом с функцией объясняет смысл, а не пересказывает имя. Из неё можно собрать справку и проверить, что описание не потерялось.

```python
def available_qty(stock: int, reserved: int) -> int:
    """Вернуть количество товара, доступное к отгрузке.

    :param stock: остаток на складе, не меньше нуля
    :param reserved: зарезервированное количество
    :return: stock - reserved, но не меньше нуля
    :raises ValueError: если stock или reserved отрицательны
    """
    if stock < 0 or reserved < 0:
        raise ValueError("количество не может быть отрицательным")
    return max(stock - reserved, 0)
```

```text
(stock: int, reserved: int) -> int
Вернуть количество товара, доступное к отгрузке.
```

В C# вместо строки документации используют XML-комментарии перед методом: `/// <summary>`, `/// <param>`, `/// <returns>`. При сборке из них получают XML-файл, который подключают к справке или Swagger. Смысл тот же: описание стоит рядом с кодом и обновляется вместе с ним.

## Документация и код

Документация живёт в репозитории рядом с кодом. Тогда изменение поведения и изменение описания попадают в один запрос на слияние, а рецензент видит расхождение. Если документация лежит в общем диске или в личной папке, она отстаёт от кода и никто не замечает, когда перестала быть верной.

| Что изменилось | Что обновить | Как проверить |
|---|---|---|
| Новый маршрут API | описание API и коллекцию Postman | запрос возвращает описанный ответ |
| Новый параметр настройки | README и `.env.example` | проект запускается по инструкции |
| Новая роль | руководство пользователя и права | сценарий роли проходит |
| Изменение шага | инструкция и снимок | шаг выполняется на чистой машине |
| Новая версия | журнал изменений | список изменений совпадает с тегами |

Автоматически проверяют то, что можно проверить. Ссылки в документе проверяет сборка сайта, примеры запросов запускают в Postman, команды из README выполняют в конвейере. Полностью автоматическая проверка невозможна: понятность текста оценивает человек. Но механические ошибки ловятся без чтения.

Журнал изменений ведут отдельно от README. В нём перечисляют версии, даты и изменения так, как их увидит пользователь: «добавлен экспорт накладной в CSV», «исправлена ошибка с занятой ячейкой». Внутренние переименования классов пользователю не нужны. По журналу поддержка понимает, что проверять после обновления, а заказчик видит, за что заплатил.

## Проверка документа

Перед публикацией документ проверяют по чек-листу. Главная проверка это прохождение на чистом окружении: читатель, который не участвовал в разработке, выполняет шаги и получает ожидаемый результат. Все места, где он остановился или спросил, становятся задачами на исправление.

| Проверка | Как выполнить | Признак ошибки |
|---|---|---|
| Адресат | назвать читателя и его задачу | документ написан «для всех» |
| Полнота | пройти шаги на чистой машине | нужен устный вопрос |
| Результат шага | сравнить с ожидаемым | непонятно, получилось или нет |
| Команды | скопировать и выполнить | команда не работает без правки |
| Ссылки | открыть каждую | ссылка ведёт на старую версию |
| Термины | сверить с интерфейсом | одно и то же названо по-разному |
| Ошибки | вызвать и описать | читатель не знает, что делать |
| Версия | сверить с релизом | документ от другой версии |

Проверка на чистой машине не требует второго человека, если есть снимок виртуальной машины. Достаточно откатить снимок, пройти инструкцию и записать каждое отклонение. Если инструкция ссылается на файл, которого нет в репозитории, это обнаружится сразу.

У документации есть долг, как у кода. Каждый пропущенный шаг, устаревший снимок и неверный код ошибки накапливаются и возвращаются вопросами в поддержку. Долг закрывают небольшими правками при каждом изменении, а не генеральной перепиской раз в год. Если документ переписывают целиком, его снова никто не проверяет, и старые ошибки возвращаются вместе с новыми. Владелец документа следит за этим долгом так же, как разработчик следит за дефектами в коде.

## Типичные ошибки

**Документ написан для автора.** Автор знает, где лежит база и какой порт свободен, поэтому пропускает важные шаги. Симптом: читатель останавливается на третьем шаге. Лечение: проверка человеком, который не участвовал в работе.

**Нет предусловий.** Инструкция начинается с команды, но не говорит, что нужен Python 3.11 и свободный порт. Симптом: команда не найдена или порт занят. Лечение: раздел требований и проверка окружения.

**Шаг без результата.** Написано «запустите сервис», но не сказано, какую строку ждать. Симптом: читатель не понимает, запустилось ли. Лечение: ожидаемый вывод и проверка здоровья.

**Устаревшие снимки.** Интерфейс изменился, кнопка называется иначе. Симптом: читатель ищет кнопку, которой нет. Лечение: проверять снимки при каждом изменении интерфейса.

**Секрет в примере.** В README или руководстве оставлен настоящий пароль. Симптом: секрет виден всем, у кого есть доступ к документу. Лечение: только условные значения и ссылка на `.env.example`.

**Описание API без ошибок.** Есть только успешный ответ. Симптом: интегратор не знает, что делать с 401 и 404. Лечение: таблица кодов и формат ошибки.

**Документ вне репозитория.** Файл лежит на общем диске и обновляется отдельно. Симптом: версия документа не совпадает с версией кода. Лечение: документация в репозитории и проверка в запросе на слияние.

**«Интуитивно понятно».** Текст перекладывает решение на читателя. Симптом: каждый делает по-своему. Лечение: конкретные шаги и условие выбора.

> [!KEY] Документ проверяют действием
> Красивый текст не доказывает полноту. Доказывает её читатель, который прошёл инструкцию на чистой машине и получил ожидаемый результат.
