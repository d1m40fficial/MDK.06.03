## Одна колонка и двадцать запросов

В проекте `sklad-plus` понадобилось хранить ячейку хранения не только в остатке, но и в справочнике товаров: у каждой позиции появилась основная ячейка. Разработчик добавил поле в класс, запустил программу и получил ошибку `no such column: products.default_cell`. База осталась прежней, потому что класс изменился, а файл `sklad.db` нет.

Во втором случае разработчик поменял имя колонки `price` на `unit_price`. Программа собралась, но двадцать мест, где был написан SQL, продолжили обращаться к старому имени. Ошибка проявлялась не сразу: часть отчётов работала, часть падала, а один запрос молча возвращал пустой список.

Обе истории об одном. Ручной SQL размазывает знание о схеме по всему проекту: имена таблиц и колонок повторяются в десятках строк. ORM собирает это знание в одном месте. Таблица описывается классом, строка становится объектом, а запросы строятся из свойств класса. Если колонка переименована, ошибка появляется в одном месте, а не в двадцати.

Цена такой ошибки не в одной строке кода. Пока разработчик ищет имя колонки по проекту, склад не получает отчёт, а менеджер не видит остатки. В проекте на 120 сотрудников и 4800 позиций отчёт по остаткам нужен каждое утро, поэтому ошибка схемы останавливает не программиста, а смену.

**ORM это слой, который переводит объекты программы в строки таблиц и обратно.** Аббревиатура расшифровывается как object-relational mapping, отображение объектов в реляционную модель. В Python чаще всего используют SQLAlchemy, в C# Entity Framework Core. Оба инструмента решают одну задачу, но называют части по-разному.

## Таблица как класс

Модель описывает таблицу: имя, колонки, типы, ключи и связи. В SQLAlchemy 2.x модель наследуется от `DeclarativeBase`, а колонки объявляются через `mapped_column`. Аннотация типа подсказывает и разработчику, и библиотеке, что за данные лежат в поле.

```python
from sqlalchemy import ForeignKey, String, create_engine, func, select
from sqlalchemy.orm import DeclarativeBase, Mapped, Session, mapped_column, relationship


class Base(DeclarativeBase):
    pass


class Warehouse(Base):
    __tablename__ = "warehouses"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(40), unique=True)
    stock: Mapped[list["Stock"]] = relationship(back_populates="warehouse")


class Product(Base):
    __tablename__ = "products"

    id: Mapped[int] = mapped_column(primary_key=True)
    sku: Mapped[str] = mapped_column(String(20), unique=True)
    title: Mapped[str] = mapped_column(String(80))
    price: Mapped[int]
    stock: Mapped[list["Stock"]] = relationship(back_populates="product")


class Stock(Base):
    __tablename__ = "stock"

    warehouse_id: Mapped[int] = mapped_column(ForeignKey("warehouses.id"), primary_key=True)
    product_id: Mapped[int] = mapped_column(ForeignKey("products.id"), primary_key=True)
    qty: Mapped[int]
    cell: Mapped[str] = mapped_column(String(12))
    warehouse: Mapped[Warehouse] = relationship(back_populates="stock")
    product: Mapped[Product] = relationship(back_populates="stock")


engine = create_engine("sqlite:///orm.db")
Base.metadata.create_all(engine)
```

Сравните с `schema.sql` из практики 8. Там были знакомые таблицы склада, но имена и типы жили в тексте SQL. Здесь они живут в классе. `__tablename__` задаёт имя таблицы, `mapped_column` описывает колонку, `ForeignKey` объявляет внешний ключ, `relationship` описывает связь для удобной навигации. Цена в модели целая, потому что в базе она хранится в копейках.

`Base.metadata.create_all(engine)` создаёт недостающие таблицы. Это удобно на старте, но не является миграцией. Если таблица уже есть, команда ничего не изменит: новую колонку она не добавит. Именно поэтому первый случай из начала лекции закончился ошибкой.

Типы в модели не совпадают с типами SQLite один в один. SQLite хранит целые, вещественные, текст, двоичные данные и NULL, а `String(40)` в модели это подсказка для схемы и для других СУБД. В SQLite длина строки не ограничивается, но проверка на уровне приложения всё равно нужна. `unique=True` создаёт уникальный индекс, `primary_key=True` задаёт ключ, а `index=True` добавляет индекс для поиска. ORM переносит эти объявления в `CREATE TABLE`, но не придумывает индексы сам.

`back_populates` связывает две стороны отношения: `warehouse.stock` и `stock.warehouse` указывают друг на друга. Без него SQLAlchemy не знает, как синхронизировать объекты в памяти. `cascade` задаёт, что делать с дочерними строками при удалении родителя: запретить, удалить вместе с ним или обнулить ссылку. По умолчанию поведение осторожное, и это хорошо: случайное удаление площадки не должно уносить остатки.

## Сессия как единица работы

Сессия `Session` это не соединение и не курсор. Это граница транзакции и хранилище загруженных объектов. Пока сессия открыта, она помнит, какие объекты прочитаны, какие изменены и какие добавлены. При `commit()` она сама решает, какие команды `INSERT`, `UPDATE` и `DELETE` отправить базе.

```python
with Session(engine) as session:
    moscow = Warehouse(title="Москва")
    tver = Warehouse(title="Тверь")
    cable = Product(sku="SKU-1005", title="Кабель ВВГнг 3x2,5", price=12800)
    hammer = Product(sku="SKU-1002", title="Молоток слесарный 500 г", price=69000)
    session.add_all([moscow, tver, cable, hammer])
    session.flush()
    print(moscow.id, tver.id, cable.id, hammer.id)
    session.add_all([
        Stock(warehouse=moscow, product=cable, qty=320, cell="B-02-02"),
        Stock(warehouse=tver, product=cable, qty=140, cell="B-02-02"),
        Stock(warehouse=moscow, product=hammer, qty=24, cell="A-01-02"),
    ])
    session.commit()
```

Вывод:

```text
1 2 1 2
```

`flush()` отправляет накопленные вставки в базу, но не фиксирует транзакцию. Он нужен, чтобы получить сгенерированные идентификаторы до создания связанных строк. `commit()` фиксирует всё целиком. Если между `flush()` и `commit()` произойдёт исключение, транзакция откатится, и в базе не останется ни площадок, ни товаров.

Сессия также работает как кэш первого уровня, его называют identity map. Если один и тот же товар запрошен дважды в одной сессии, второй запрос может не пойти в базу: библиотека вернёт уже загруженный объект. Это экономит время, но создаёт ловушку: данные, изменённые другим процессом, останутся старыми, пока сессия не будет закрыта или обновлена.

Метод `add` ставит объект в сессию, `add_all` делает то же для списка. `merge` нужен, когда объект пришёл из другого слоя и в сессии уже есть строка с тем же ключом: он копирует состояние в существующий объект. `delete` помечает объект на удаление. Ни одна из этих операций не отправляет команду сразу: сессия накапливает изменения и отправляет их при `flush` или `commit`. Такое поведение называют unit of work, единица работы.

Сессия понимает, что объект изменился, сравнивая его текущее состояние с тем, что было загружено. Это называют dirty checking. Достаточно присвоить новое значение полю, а `commit()` сам отправит `UPDATE` с нужными колонками.

```python
with Session(engine) as session:
    product = session.scalars(select(Product).where(Product.sku == "SKU-1005")).one()
    product.price = 13500
    session.commit()
```

Проверка чтением в новой сессии показывает новое значение:

```python
with Session(engine) as session:
    print(session.scalars(select(Product.price).where(Product.sku == "SKU-1005")).one())
```

Вывод:

```text
13500
```

## Запросы вместо строк

Запрос в SQLAlchemy 2.x начинается с `select`. Условие пишется через свойства класса, а не через имена колонок в тексте. Результат возвращается объектами или кортежами, в зависимости от того, что запрошено.

```python
with Session(engine) as session:
    stmt = select(Product).where(Product.price < 100000).order_by(Product.title)
    for p in session.scalars(stmt):
        print(p.id, p.sku, p.title, p.price)
```

Вывод:

```text
1 SKU-1005 Кабель ВВГнг 3x2,5 13500
2 SKU-1002 Молоток слесарный 500 г 69000
```

Цена кабеля уже изменена в примере с dirty checking, поэтому в выборке стоит 13500 копеек, а не 12800. Это показывает, что новая сессия читает зафиксированное состояние базы, а не старый объект из памяти. Порог `100000` в запросе это 1000 рублей, поэтому в выборку попадают оба товара.

Метод `scalars` возвращает по одному объекту на строку. Если запрос выбирает несколько колонок, используют `session.execute` и распаковывают кортеж. Агрегаты и соединения строятся теми же выражениями.

```python
with Session(engine) as session:
    stmt = (
        select(Warehouse.title, func.sum(Stock.qty).label("total"))
        .join(Stock, Stock.warehouse_id == Warehouse.id)
        .group_by(Warehouse.title)
        .order_by(func.sum(Stock.qty).desc())
    )
    for title, total in session.execute(stmt):
        print(title, total)
```

Вывод:

```text
Москва 344
Тверь 140
```

Эквивалентный SQL выглядит знакомо:

```sql
SELECT warehouses.title, sum(stock.qty) AS total
FROM warehouses
JOIN stock ON stock.warehouse_id = warehouses.id
GROUP BY warehouses.title
ORDER BY sum(stock.qty) DESC;
```

ORM не отменяет SQL. Он строит его за вас, но построенный запрос всё равно уходит в базу. Полезно уметь прочитать его и проверить, что соединение и группировка сделаны так, как задумано. В SQLAlchemy для этого включают `echo=True` у движка, в Entity Framework Core включают журнал команд или смотрят `ToQueryString()`.

Выражения `select`, `where`, `join`, `group_by` и `order_by` не выполняют запрос сразу. Они собирают объект запроса, который можно передать в `session.execute`, распечатать или объединить с другим. Это отличается от `cursor.execute` в `sqlite3`, где вызов сразу идёт в базу. Отложенное выполнение удобно для тестов: запрос можно собрать и сравнить его SQL без подключения к файлу.

## Связи и ленивая загрузка

Связь `warehouse.stock` описана в модели, но данные по ней загружаются не сразу. По умолчанию SQLAlchemy применяет ленивую загрузку: пока к свойству не обратились, связанные строки не читаются. Это экономит запросы, когда связь не нужна, и создаёт лишние, когда нужна.

```python
with Session(engine) as session:
    warehouse = session.scalars(select(Warehouse).where(Warehouse.title == "Москва")).one()
    print(warehouse.title, len(warehouse.stock))
    for s in warehouse.stock:
        print(s.product.title, s.qty)
```

Вывод:

```text
Москва 2
Кабель ВВГнг 3x2,5 320
Молоток слесарный 500 г 24
```

На экране три строки, а в журнале четыре запроса. Первый выбирает площадку. Второй, при обращении к `warehouse.stock`, выбирает остатки этой площадки. Третий и четвёртый, при обращении к `s.product`, выбирают товары для каждой строки остатка. Если бы товары не понадобились, последние два запроса не выполнились бы.

Ленивая загрузка удобна в интерактивной консоли и опасна в цикле. Классическая ошибка называется N+1: один запрос выбирает список из N строк, а затем для каждой строки выполняется ещё один запрос. Для двух площадок это три запроса, для четырёх уже пять, для тысячи площадок тысяча один.

```python
with Session(engine) as session:
    for warehouse in session.scalars(select(Warehouse)):
        print(warehouse.title, sum(s.qty for s in warehouse.stock))
```

Журнал показывает один запрос к `warehouses` и по одному запросу к `stock` на каждую площадку. Чем больше справочник, тем хуже время ответа. База тратит время не на работу, а на подготовку и передачу множества мелких команд.

## Жадная загрузка

Жадная загрузка говорит сессии: загрузи связь сразу, одним дополнительным запросом. В SQLAlchemy для коллекций применяют `selectinload`. Он выполняет второй запрос с условием `IN` по идентификаторам родителей и собирает объекты в памяти.

```python
from sqlalchemy.orm import selectinload

with Session(engine) as session:
    stmt = select(Warehouse).options(selectinload(Warehouse.stock))
    for warehouse in session.scalars(stmt):
        print(warehouse.title, sum(s.qty for s in warehouse.stock))
```

Вывод:

```text
Москва 344
Тверь 140
```

В журнале два запроса: первый выбирает площадки, второй выбирает остатки для обеих площадок одним условием `WHERE stock.warehouse_id IN (?, ?)`. Число запросов не зависит от числа площадок. Это и есть лечение N+1.

У жадной загрузки есть цена. Если связь большая, а нужна только одна строка, `selectinload` прочитает больше данных, чем требуется. Если связей несколько, количество запросов и объём результата растут. Выбор между ленивой и жадной загрузкой зависит от сценария: список для таблицы обычно требует жадной, карточка одного объекта может обойтись ленивой.

`joinedload` собирает связь в один SQL-запрос через `LEFT OUTER JOIN`. Он удобен для связи «один к одному» и для небольших коллекций, но на больших коллекциях дублирует колонки родителя в каждой строке. `selectinload` делает второй запрос и не дублирует данные. Выбор зависит от размера коллекции и от того, сколько родителей в выборке.

| Сценарий | Загрузка | Почему |
|---|---|---|
| Список площадок с остатками | `selectinload` | один дополнительный запрос на всю коллекцию |
| Карточка товара без связей | ленивая | связанные данные не нужны |
| Отчёт по всем товарам и категориям | `joinedload` или ручной JOIN | нужны обе таблицы сразу |
| API, который отдаёт объект после закрытия сессии | жадная | ленивая загрузка уже недоступна |

## Отсоединённый объект

Сессия владеет загруженными объектами. Пока она открыта, объект может догрузить связи. После закрытия объект остаётся в памяти, но теряет связь с сессией. Обращение к незагруженному свойству вызывает `DetachedInstanceError`.

```python
with Session(engine) as session:
    warehouse = session.scalars(select(Warehouse)).first()
print(warehouse.title)
print(warehouse.stock)
```

Вывод:

```text
Москва
DetachedInstanceError: Parent instance <Warehouse ...> is not bound to a Session;
lazy load operation of attribute 'stock' cannot proceed
```

Адрес объекта в сообщении сокращён, чтобы не зависеть от запуска. Остальной текст совпадает с выводом библиотеки.

Название площадки осталось доступным, потому что оно уже было загружено. Коллекция остатков не загружалась, и догрузить её больше нечем. Лечение зависит от задачи: либо загрузить связь до закрытия сессии через `selectinload`, либо оставить сессию открытой до конца обработки запроса, либо преобразовать объект в словарь или DTO внутри сессии.

В веб-приложении сессию обычно открывают на один HTTP-запрос и закрывают после формирования ответа. Шаблон или сериализатор должен получить все нужные данные до закрытия. Если сессию держат глобально, она накапливает объекты, держит транзакцию и мешает параллельным запросам. Если открывать сессию на каждое обращение к свойству, теряется кэш и растёт число запросов.

## Миграции

Модель описывает желаемую схему, а база хранит текущую. Пока они совпадают, всё работает. Как только в модели появилась колонка, базу нужно изменить отдельной командой. Такую команду называют миграцией.

В Python для SQLAlchemy используют Alembic. Он хранит версии схемы в таблице и применяет их по порядку. Типичный цикл выглядит так: изменить модель, создать миграцию командой `alembic revision --autogenerate -m "add default cell"`, проверить сгенерированный файл, применить командой `alembic upgrade head`. Автоматическая генерация не всегда угадывает переименование: она может предложить удалить одну колонку и добавить другую, потеряв данные. Поэтому файл миграции читают перед применением.

В C# Entity Framework Core делает то же самое командами `dotnet ef migrations add AddDefaultCell` и `dotnet ef database update`. Миграции хранятся в проекте, как и код, и попадают в репозиторий. Это важное свойство: схема базы становится частью истории проекта, а не набором ручных действий на сервере.

Роль сессии в Entity Framework Core играет `DbContext`. Он тоже хранит загруженные объекты, отслеживает изменения и фиксирует их через `SaveChanges()`. Правила те же: контекст живёт один запрос, а не всё время работы приложения. `AsNoTracking()` отключает отслеживание для чтения и экономит память в отчётах, где объекты не собираются меняться.

`create_all` и автоматическое создание базы удобны для учебного проекта и тестов. В рабочем проекте схему меняют только миграциями. Иначе на одной машине колонка есть, на другой нет, и ошибка зависит от того, кто когда обновлял базу.

## ORM или чистый SQL

ORM не лучше и не хуже SQL. Это инструмент с своей ценой. Он ускоряет обычные операции с объектами и усложняет сложные отчёты. Он прячет соединения, но не отменяет их. Он помогает с параметрами, но не мешает написать `text()` с ручной склейкой.

| Критерий | ORM | Ручной SQL |
|---|---|---|
| Обычные операции с объектом | быстро писать | больше кода |
| Сложный отчёт с группировкой | громоздко | удобно и прозрачно |
| Защита от инъекций | параметры по умолчанию | нужно следить самому |
| Смена СУБД | проще | зависит от диалекта |
| Контроль над запросом | ниже | полный |
| Риск лишних запросов | высокий, N+1 | виден сразу |
| Порог входа | выше | ниже |

Практическое правило простое. Объекты, которые создаются, читаются и меняются по одному, отдают ORM. Массовые обновления, сложные отчёты и запросы к специфичным возможностям СУБД пишут SQL. В одном проекте оба подхода уживаются: SQLAlchemy позволяет выполнить сырой запрос через `session.execute(text(...))`, а Entity Framework Core через `FromSqlRaw`.

Перед заменой ORM на SQL полезно измерить, а не угадывать. В SQLite есть команда `EXPLAIN QUERY PLAN`, которая показывает, использует ли запрос индекс или читает всю таблицу. В SQLAlchemy тот же план можно получить через `session.execute(text("EXPLAIN QUERY PLAN ..."))`. Если запрос выполняется миллисекунды на учебных данных, это не значит, что он будет быстрым на 4800 позициях и сотне одновременных пользователей.

## Типичные ошибки

Первая ошибка это N+1. Симптом: страница открывается быстро на учебных данных и замедляется на рабочей базе. Лечение: включить журнал запросов, посчитать их число и добавить `selectinload` или `joinedload` там, где связь нужна.

Вторая ошибка это ленивая загрузка после закрытия сессии. Симптом: `DetachedInstanceError` в шаблоне или сериализаторе. Лечение: загрузить нужные связи до закрытия сессии или собрать DTO внутри сессии.

Третья ошибка это глобальная сессия. Симптом: данные не обновляются, транзакция висит, параллельные запросы мешают друг другу. Лечение: сессия на одну операцию или на один запрос, закрытие в `finally`.

Четвёртая ошибка это `create_all` вместо миграции. Симптом: `no such column` после изменения модели. Лечение: миграция и проверка схемы на чистой базе.

Пятая ошибка это вера в то, что ORM сам расставит индексы. Он создаёт индексы только там, где вы их описали. Запрос `WHERE sku = ?` без индекса читает всю таблицу, и ORM это не исправит.

Шестая ошибка это `commit()` после каждого объекта в цикле. Симптом: тысяча транзакций вместо одной. Лечение: одна сессия и один `commit()` на пакет, если бизнес-логика допускает частичную фиксацию.

Седьмая ошибка это отсутствие проверки данных на границе. ORM принимает любое значение, которое подходит по типу, но не проверяет бизнес-правила: отрицательную цену, пустое название, слишком длинную ячейку. Проверка остаётся задачей модели, схемы или отдельного слоя валидации. Ограничения `CHECK` и `NOT NULL` в базе это последняя линия защиты, а не замена проверке ввода.

## Итоги

- ORM отображает класс на таблицу, объект на строку, а связь на отношение между объектами.
- Сессия задаёт границу транзакции и хранит загруженные объекты, а `commit()` отправляет накопленные изменения.
- Ленивая загрузка экономит запросы, но в цикле даёт N+1; жадная загрузка лечит его ценой лишних данных.
- После закрытия сессии незагруженные связи недоступны, и это выражается в `DetachedInstanceError`.
- Схему меняют миграциями, а `create_all` подходит только для старта и тестов.
- ORM и SQL дополняют друг друга: объекты через ORM, сложные отчёты через SQL.

::quiz
Q: Что отображает ORM?
+ Класс программы на таблицу базы, а объект на строку
- Файл базы на файл журнала
- HTTP-маршрут на SQL-запрос
- Пароль на хеш
! ORM переводит объектную модель программы в реляционную модель базы.

Q: Что задаёт сессия в SQLAlchemy?
+ Границу транзакции и набор загруженных объектов
- Только имя файла базы
- Только права пользователя
- Только схему таблиц
! Сессия решает, когда отправить изменения и какие объекты уже загружены.

Q: Что делает ленивая загрузка связи?
+ Читает связанные строки при первом обращении к свойству
- Читает все таблицы при старте программы
- Запрещает доступ к связи
- Создаёт индекс на внешний ключ
! Поэтому связь может вызвать дополнительный запрос неожиданно для автора кода.

Q: В чём суть проблемы N+1?
+ Один запрос выбирает список, затем по запросу на каждую строку
- Один запрос выполняется N раз из-за повтора
- Таблица содержит N+1 колонку
- Сессия открывается N+1 раз
! Число запросов растёт вместе с числом строк списка.

Q: Что делает `selectinload`?
+ Загружает связь отдельным запросом с условием IN
- Запрещает ленивую загрузку навсегда
- Удаляет связанные строки
- Создаёт таблицу для связи
! Один дополнительный запрос обслуживает всю коллекцию родителей.

Q: Почему возникает `DetachedInstanceError`?
+ Объект используется после закрытия сессии, а связь не была загружена
- В базе закончилось место
- В модели не указан первичный ключ
- Запрос вернул слишком много строк
! После закрытия сессии догрузить связь нечем.

Q: Что делает `Base.metadata.create_all`?
+ Создаёт отсутствующие таблицы, но не изменяет существующие
- Применяет все миграции по порядку
- Удаляет таблицы перед созданием
- Обновляет колонки в существующих таблицах
! Для изменения существующей таблицы нужна миграция.

Q: Что такое миграция?
+ Версионированное изменение схемы базы
- Перенос данных в другой файл
- Копия базы на другой сервер
- Запрос на выборку всех строк
! Миграции хранят историю изменений схемы и применяются по порядку.

Q: Какие преимущества даёт ORM?
+ Меньше повторяющегося кода для обычных операций
+ Параметры запросов используются по умолчанию
+ Строка выборки превращается в объект
- Любой запрос выполняется быстрее ручного SQL
- ORM отменяет необходимость знать SQL
! ORM ускоряет разработку, но не гарантирует лучшую производительность.

Q: Когда ручной SQL удобнее ORM?
+ Для сложного отчёта с группировкой и оконными функциями
+ Для массового обновления большого числа строк
+ Для запроса к специфичной возможности СУБД
- Для создания одного объекта
- Для чтения строки по первичному ключу
! Сложная аналитика и массовые операции лучше видны в явном SQL.

Q: Что может вызвать лишние запросы к базе?
+ Обращение к ленивой связи в цикле
+ Отсутствие жадной загрузки для нужной связи
+ Запрос связи для каждой строки списка
- Использование `selectinload`
- Чтение объекта по первичному ключу через `session.get`
! Ленивая загрузка в цикле и есть источник N+1.

Q: Что должно быть в модели таблицы?
+ Имя таблицы
+ Колонки и их типы
+ Связи с другими моделями
- Пароль от базы данных
- HTTP-маршрут API
! Модель описывает данные и связи, а не доступ к серверу и не маршруты.

Q: Как называется проблема, при которой список из N строк порождает N дополнительных запросов?
= N+1
= проблема N+1
! Один запрос на список и по одному на каждую строку дают N+1 обращений.

Q: Какая функция SQLAlchemy загружает связь отдельным запросом с условием IN?
= selectinload
! `selectinload` обслуживает всю коллекцию одним дополнительным запросом.

Q: Как называется версионированное изменение схемы базы?
= миграция
! Миграции применяются по порядку и хранят историю изменений схемы.
::/gate
