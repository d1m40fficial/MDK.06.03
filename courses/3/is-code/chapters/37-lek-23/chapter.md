## Склад, который отгрузил лишнее

В пятницу кладовщик на площадке в Туле оформил отгрузку 25 перфораторов. На складе лежало 40 единиц, и 10 из них уже были зарезервированы под другой заказ. Свободных оставалось 30, значит после отгрузки должно было остаться 5. Система «Склад+» показала 15 и разрешила операцию. Через два часа менеджер попытался зарезервировать 10 единиц и получил отказ: «недостаточно товара». На экране кладовщика по-прежнему светилось 15.

Причина нашлась в одной строке функции свободного остатка. Она вычитала резерв не всегда: при нулевом резерве всё сходилось, а при ненулевом остаток завышался. Ошибку внесли две недели назад, когда переписывали расчёт. Проверяли вручную: открыли карточку товара, где резерв был равен нулю, и результат совпал с ожиданием. На складе с 4800 позициями и четырьмя площадками такая проверка не ловит ничего, потому что смотрит один удачный случай.

**Тест это записанная проверка, которую можно повторить без человека.** Он фиксирует входные данные, вызывает код и сравнивает результат с ожидаемым. Записанную проверку выполняет машина, а не память разработчика. Набор из двухсот тестов проходит меньше чем за секунду и проверяет то, на что глазами уходил бы час.

Тест не доказывает, что программа правильная. Он доказывает только одно: на этом входе код ведёт себя так, как записано в проверке. Ценность теста в том, что он не забывает, не устаёт и не пропускает случай, который разработчик считал невозможным.

## Что именно проверяет тест

У хорошего теста три части. Сначала готовят данные и окружение, затем вызывают проверяемый код, потом сравнивают результат с ожидаемым. Эти части называют «подготовка», «действие» и «утверждение». Утверждение это строка, которая падает, если поведение разошлось с ожиданием.

```python
def available_qty(stock: int, reserved: int) -> int:
    """Свободный остаток: сколько единиц можно отгрузить."""
    if stock < 0 or reserved < 0:
        raise ValueError("количество не может быть отрицательным")
    return max(stock - reserved, 0)
```

Функция принимает физический остаток и уже зарезервированное количество, а возвращает то, что можно отгрузить. Отрицательных значений здесь быть не может, поэтому функция явно сообщает об ошибке. Верхняя граница не нужна: свободный остаток не бывает больше физического, но это следствие формулы, а не отдельное правило.

Проверка выглядит так:

```python
import pytest
from stock import available_qty

def test_available_is_stock_minus_reserved():
    assert available_qty(120, 30) == 90

def test_reserved_equal_stock_leaves_nothing():
    assert available_qty(40, 40) == 0

def test_reserved_above_stock_is_not_negative():
    assert available_qty(12, 20) == 0

def test_negative_reserved_is_rejected():
    with pytest.raises(ValueError):
        available_qty(10, -1)
```

Имя теста отвечает на вопрос «что должно быть верно», а не «что делает функция». `test_reserved_equal_stock_leaves_nothing` читается как утверждение: если резерв равен остатку, свободного не остаётся. Через полгода по имени будет понятно, что сломалось, без открытия тела теста.

В C# те же три части записывают в тесте xUnit: атрибут `[Fact]` помечает метод как проверку, а `Assert.Equal` сравнивает ожидаемое и фактическое значения. Названия инструментов другие, порядок подготовки, действия и утверждения сохраняется.

Запуск из каталога проекта:

```text
python -m pytest -v
```

```text
test_stock.py::test_available_is_stock_minus_reserved PASSED             [ 25%]
test_stock.py::test_reserved_equal_stock_leaves_nothing PASSED           [ 50%]
test_stock.py::test_reserved_above_stock_is_not_negative PASSED          [ 75%]
test_stock.py::test_negative_reserved_is_rejected PASSED                 [100%]

4 passed in 0.03s
```

Четыре проверки заняли три сотых секунды. Это важное свойство: модульный тест настолько дешёвый, что его не жалко запускать после каждой правки. Чем дешевле проверка, тем чаще её делают.

`pytest.raises(ValueError)` проверяет не возвращаемое значение, а факт исключения. Если функция вернёт `0` вместо ошибки, тест упадёт. Так фиксируют контракт: отрицательное количество это не «ноль», а нарушение входа.

Данные для теста выбирают так, чтобы каждый набор объяснял одно поведение. Не нужно копировать реальную выгрузку на 4800 строк: для проверки формулы достаточно двух чисел, для проверки ограничения одно значение на границе. Чем меньше данных в тесте, тем легче понять, почему он упал. Большие выгрузки нужны на уровне интеграции, где проверяется разбор файла или запрос к базе.

В одном тесте ставят одно утверждение, которое отвечает на один вопрос. Если хочется проверить и возвращённое значение, и сообщение об ошибке, это два теста. Исключение делают для связанных полей одного объекта, например кода и текста ошибки, но и тогда имя теста должно называть оба ожидания.

## Модульный тест: одна функция под наблюдением

Модульный тест проверяет одну единицу поведения в изоляции. Для функции свободного остатка это означает: база не нужна, сервер не нужен, время и случайность не участвуют. На вход подаются числа, на выходе проверяется число. Если тест упал, причина почти всегда в самой функции или в её непосредственных зависимостях.

Изоляция даёт точность. Когда падает модульный тест, круг поиска узкий. Когда падает интеграционный тест, неизвестно, сломалась функция, запрос или соединение с базой. Поэтому модульных тестов пишут больше, а разбираются с ними быстрее.

У модульного теста есть цена. Он не видит, что функция вызывается с неправильными аргументами из другого модуля. Он не проверяет, что SQL-запрос соответствует схеме. Он не замечает, что два модуля по-разному понимают формат даты. Эти ошибки ловит следующий уровень проверки.

| Признак | Модульный тест | Интеграционный тест |
|---|---|---|
| Что проверяет | одну функцию или класс | связку модулей, базы и запросов |
| Что подставляется | простые значения, иногда заглушки | настоящая база, файл, HTTP-клиент |
| Скорость | миллисекунды | секунды |
| Круг поиска при падении | узкий | широкий |
| Сколько нужно | много | меньше, по ключевым сценариям |
| Что ловит | логику и границы | формат данных, схему, ограничения |

Для «Склад+» модульными будут проверки расчёта остатка, скидки, длины строки накладной, разбора кода ячейки. Интеграционными будут проверки записи резерва в SQLite, чтения остатка через API и сохранения накладной вместе со строками.

Иногда функцию трудно изолировать: она обращается к базе, часам или внешнему сервису. Тогда зависимость заменяют заглушкой, которая возвращает заранее заданный ответ. Заглушка полезна, когда нужно проверить реакцию на редкий сбой, например на таймаут внешней системы, который трудно вызвать вручную. Опасность в том, что заглушка проверяет не настоящий сервис, а представление разработчика о нём. Если настоящий сервис изменил формат ответа, заглушка этого не покажет. Поэтому проверки с заглушками дополняют интеграционными, где зависимость настоящая.

## Граничные значения: там, где ломается расчёт

Разработчик проверяет середину диапазона, потому что там пример удобный. Дефекты живут на краях. Для функции свободного остатка крайние случаи задаются значениями резерва относительно остатка.

| Остаток | Резерв | Ожидаемый свободный остаток | Что проверяет случай |
|---|---|---|---|
| 40 | 0 | 40 | резерва нет |
| 40 | 1 | 39 | минимальный ненулевой резерв |
| 40 | 39 | 1 | почти весь товар занят |
| 40 | 40 | 0 | свободного не осталось |
| 40 | 41 | 0 | резерв больше остатка |
| 40 | -1 | ошибка | недопустимый вход |

Середина диапазона здесь одна: 40 и 10. Она не показывает, что происходит при равенстве и при превышении. Именно на равенстве ломается условие `>` вместо `>=`, а на превышении появляется отрицательный остаток, если забыть про `max`.

Проверим, что увидит разработчик, если убрать защиту и оставить вычитание:

```python
def available_qty(stock: int, reserved: int) -> int:
    return stock - reserved
```

```text
def test_reserved_above_stock_is_not_negative():
>       assert available_qty(12, 20) == 0
E       assert -8 == 0
E        +  where -8 = available_qty(12, 20)
```

Отчёт сразу называет вход, ожидание и фактическое значение. Это и есть главная выгода теста: он не говорит «что-то не так», он показывает, что именно и где разошлось. Разработчику не нужно воспроизводить ситуацию вручную и гадать, какой товар и какой резерв выбрал кладовщик.

Граничные значения выбирают по классам эквивалентности. Все резервы от 0 до 40 ведут себя одинаково с точки зрения формулы, поэтому достаточно проверить 0, 1, 39 и 40. Значения 41 и больше образуют отдельный класс, а отрицательные ещё один. Внутри класса нет смысла проверять каждое число, на границах класса проверяют переход.

Есть и другой способ искать границы: сформулировать свойство, которое должно выполняться всегда, и проверить его на множестве случайных входов. Для свободного остатка свойство звучит так: результат неотрицателен и не больше физического остатка. Если проверять это утверждение на сотне случайных пар, можно найти сочетание, о котором не подумал автор тестов. Такой подход называют проверкой свойств; он не заменяет ручные границы, но хорошо дополняет их.

> [!PITFALL] Тест на середине диапазона
> Проверка `available_qty(120, 30) == 90` проходит и на правильной, и на многих неправильных версиях. Она не трогает равенство, превышение и отрицательный вход. Одного удачного примера недостаточно, чтобы считать функцию проверенной.

Для резервирования граница другая. Функция `free_after_reserve(stock, reserved, requested)` должна разрешить запрос, равный свободному остатку, и отказать на единицу больше. Проверяют три значения: `requested` меньше свободного, равен ему и больше на единицу. Если условие записано как `requested >= free`, отказ придёт на допустимом запросе, и склад потеряет продажу.

## Интеграционный тест: проверка связки

Модульный тест на функцию остатка прошёл бы и в тот день, когда сломалась запись в базу. Причина в том, что функция считала правильно, а ограничение `CHECK (qty >= 0)` в SQLite не давало сохранить отрицательное значение. Ошибка жила на границе двух модулей: Python передавал число, база его отвергала, а обработчик возвращал общий текст «ошибка сохранения».

Интеграционный тест поднимает настоящую базу и проходит путь целиком. Для учебного проекта достаточно SQLite в памяти: она не требует сервера и работает так же, как файловая. Данные готовят перед каждым тестом и не переиспользуют между проверками. Если один тест оставил строку, а другой рассчитывает на пустую таблицу, набор начнёт падать через раз, и доверять ему будет нельзя.

```python
import sqlite3

def connect(path: str = ":memory:") -> sqlite3.Connection:
    conn = sqlite3.connect(path)
    conn.row_factory = sqlite3.Row
    conn.execute("""
        CREATE TABLE IF NOT EXISTS stock (
            sku TEXT PRIMARY KEY,
            qty INTEGER NOT NULL CHECK (qty >= 0)
        )
    """)
    return conn

def put(conn: sqlite3.Connection, sku: str, qty: int) -> None:
    conn.execute(
        "INSERT INTO stock (sku, qty) VALUES (?, ?) "
        "ON CONFLICT(sku) DO UPDATE SET qty = excluded.qty",
        (sku, qty),
    )
    conn.commit()

def reserve(conn: sqlite3.Connection, sku: str, qty: int) -> int:
    row = conn.execute("SELECT qty FROM stock WHERE sku = ?", (sku,)).fetchone()
    if row is None:
        raise KeyError(sku)
    if row["qty"] < qty:
        raise ValueError("недостаточно товара")
    conn.execute("UPDATE stock SET qty = qty - ? WHERE sku = ?", (qty, sku))
    conn.commit()
    return row["qty"] - qty
```

Тест создаёт соединение, кладёт одну позицию и проверяет не только возвращённое значение, но и состояние таблицы после операции:

```python
import pytest
from repo import connect, put, reserve

@pytest.fixture
def conn():
    connection = connect()
    put(connection, "SKU-1042", 40)
    yield connection
    connection.close()

def test_reserve_reduces_quantity(conn):
    left = reserve(conn, "SKU-1042", 15)
    row = conn.execute("SELECT qty FROM stock WHERE sku = ?", ("SKU-1042",)).fetchone()
    assert left == 25
    assert row["qty"] == 25

def test_reserve_rejects_more_than_stock(conn):
    with pytest.raises(ValueError):
        reserve(conn, "SKU-1042", 41)

def test_unknown_sku_is_reported(conn):
    with pytest.raises(KeyError):
        reserve(conn, "SKU-9999", 1)
```

```text
test_repo.py::test_reserve_reduces_quantity PASSED                       [ 33%]
test_repo.py::test_reserve_rejects_more_than_stock PASSED                [ 66%]
test_repo.py::test_unknown_sku_is_reported PASSED                        [100%]

3 passed in 0.03s
```

Фикстура `conn` готовит окружение для каждого теста и закрывает соединение после него. Без фикстуры пришлось бы повторять три строки в каждом тесте и следить, чтобы тесты не делили одно соединение. Общее соединение делает тесты зависимыми от порядка: один оставил данные, другой упал.

Интеграционный тест проверяет то, чего не видит модульный: что колонка называется `qty`, что ограничение не пропускает минус, что `UPDATE` действительно сохраняет изменение, что неизвестный артикул даёт понятную ошибку. Он медленнее, но именно он ловит расхождения между слоями.

Цена интеграционного теста выше не только по времени. Ему нужна схема базы, тестовые данные и аккуратная очистка. Если база файловая, тест может оставить после себя файл и повлиять на следующий запуск. Поэтому для учебного проекта удобна база в памяти, а для промышленного стенда отдельная схема, которая создаётся с нуля перед прогоном. Чем ближе тест к настоящей среде, тем полезнее его результат и тем больше у него причин упасть не из-за дефекта.

| Что сломалось | Поймает модульный тест | Поймает интеграционный тест |
|---|---|---|
| Неверная формула остатка | да | да |
| Опечатка в имени колонки | нет | да |
| Забытый `commit` | нет | да |
| Ограничение базы отвергает значение | нет | да |
| Неверный код ответа API | нет | да |
| Медленный запрос | нет | обычно нет |

## Покрытие: измерение, а не цель

Покрытие показывает, какую долю кода выполнили тесты. В Python его измеряют модулем `coverage`. Модуль не входит в стандартную библиотеку, поэтому его ставят в виртуальное окружение командой `python -m pip install coverage`. Запуск заменяет обычный вызов pytest:

```text
python -m coverage run --branch --include="stock.py,repo.py" -m pytest -q
python -m coverage report -m
```

```text
Name       Stmts   Miss Branch BrPart  Cover   Missing
------------------------------------------------------
repo.py       18      0      4      0   100%
stock.py       4      0      2      0   100%
------------------------------------------------------
TOTAL         22      0      6      0   100%
```

Столбец `Stmts` считает инструкции, `Miss` показывает непройденные, `Branch` и `BrPart` относятся к ветвям условий. Сто процентов здесь означают, что каждая инструкция и каждая ветвь хотя бы раз выполнились. Это хороший знак, но не доказательство правильности.

Пример уже был выше. Тело функции `return stock - reserved` без `max` состоит из одной инструкции. Тест `available_qty(120, 30) == 90` выполняет её и даёт сто процентов покрытия строк. При этом на входе `(12, 20)` функция возвращает минус восемь. Покрытие ответило на вопрос «выполнялась ли строка», а не на вопрос «вернула ли она правильное значение».

| Вид покрытия | Что считает | Что может пропустить |
|---|---|---|
| Покрытие строк | выполненные строки | непроверенные ветви и значения |
| Покрытие ветвей | оба исхода каждого условия | неверные границы внутри ветви |
| Покрытие путей | комбинации переходов | редкие сочетания данных |
| Мутационное тестирование | ловят ли тесты намеренную поломку | требует отдельного инструмента |

Мутационное тестирование отвечает на неудобный вопрос: если изменить код намеренно, упадёт ли хотя бы один тест. Инструмент вносит мелкие поломки, например меняет `>` на `>=`, и смотрит, заметил ли набор. Тест, который проходит после любой поломки, бесполезен, даже если покрытие равно ста процентам.

> [!KEY] Покрытие это компас, а не цель
> Низкое покрытие почти всегда означает непроверенные участки. Высокое покрытие не означает отсутствие дефектов. Смотрите не на число, а на то, какие границы и сценарии остались без проверки.

## Пирамида тестов и цена проверки

Тесты делят на уровни не из любви к классификации, а из-за разной цены. Модульный тест выполняется за миллисекунды и точно указывает на функцию. Интеграционный тест идёт секунды и показывает связку. Проверка через интерфейс или настоящий браузер занимает минуты и падает по десятку причин, от таймаута до шрифта.

| Уровень | Сколько в «Склад+» | Время одного | Что проверяет | Кому показывает ошибку |
|---|---|---|---|---|
| Модульные | около 210 | 1-5 мс | формулы, разбор, границы | разработчику |
| Интеграционные | около 34 | 0,2-2 с | база, API, файлы | разработчику и тестировщику |
| Сквозные | 6 | несколько минут | путь пользователя целиком | команде и заказчику |

Числа условные, но пропорция важна: дешёвых проверок должно быть больше. Если команда пишет двести сквозных тестов и десять модульных, каждый прогон занимает часы, а причина падения неясна. Если наоборот, сквозные сценарии остаются непроверенными, и ошибка появляется на стыке интерфейса и API.

Сквозные тесты не заменяют модульные и наоборот. Модульный тест не увидит, что кнопка отгрузки вызывает не тот маршрут. Сквозной тест увидит, но не скажет, в какой из сорока функций ошибка. Уровни дополняют друг друга.

У набора тестов есть стоимость сопровождения. Каждый тест придётся обновлять, когда меняется контракт функции или формат ответа API. Тест, привязанный к каждой внутренней детали, приходится обновлять после каждой правки, а пользы он приносит мало. Поэтому набор пересматривают: удаляют проверки, которые повторяют друг друга, и переписывают те, которые падают от любого рефакторинга. Хороший набор растёт вместе с поведением системы, а не вместе с числом приватных методов.

## Типичные ошибки

**Тест без утверждения.** Функция вызывается, но результат не сравнивается. Такой тест проходит всегда и создаёт ложное чувство защиты. Симптом: в отчёте зелёные галочки, а дефект остаётся. Лечение: в каждом тесте должно быть хотя бы одно утверждение, которое может упасть.

**Проверка реализации вместо поведения.** Тест лезет во внутренний список или вызывает приватный метод. После любого рефакторинга он падает, хотя поведение не изменилось. Симптом: правка ради читаемости ломает десять тестов. Лечение: проверять результат функции и наблюдаемое состояние, а не способ, которым он получен.

**Один тест на пять сценариев.** Внутри одного теста проверяются нормальный случай, граница и ошибка. При падении непонятно, какой именно сценарий сломался, а после первого исключения остальные проверки не выполняются. Симптом: отчёт показывает одну строку на всю функцию. Лечение: один тест, одно поведение.

**Зависимость от порядка.** Тесты делят файл, базу или глобальную переменную. По отдельности проходят, вместе падают. Симптом: `pytest tests/test_stock.py` зелёный, `pytest` красный. Лечение: фикстура на каждый тест, временная база, очистка после себя.

**Только удачный путь.** Проверяется, что функция вернула число, но не проверяется, что она делает при нуле, минусе и превышении. Симптом: покрытие высокое, а отказы на складе странные. Лечение: классы эквивалентности и границы.

**Зависимость от времени и случайности.** Тест сравнивает текущую дату или перемешанный список. Симптом: тест падает раз в неделю и проходит при повторном запуске. Лечение: подставлять фиксированное время и фиксированное зерно случайности.

**Проверка заглушки вместо кода.** Тест подменяет базу заглушкой и проверяет, что заглушка вернула заранее заданное значение. Настоящий SQL при этом не выполняется. Симптом: тест зелёный, а в базе нет колонки. Лечение: модульные тесты с заглушками дополнять интеграционными с настоящей базой.

> [!PITFALL] Тест, который никогда не падал
> Если новый тест сразу зелёный, это не всегда хорошая новость. Проверьте, что он умеет падать: временно сломайте код или измените ожидание. Тест, который не падал ни разу, мог не выполниться вовсе.

## Как встроить тесты в работу

Тесты становятся частью работы, когда их запускают до коммита, а не «когда будет время». Простой цикл состоит из трёх шагов: написать падающий тест на новое поведение, сделать минимальную правку, чтобы он прошёл, затем улучшить код, не меняя поведения. Этот цикл называют красный, зелёный, рефакторинг.

| Команда | Что делает |
|---|---|
| `python -m pytest` | запускает все тесты проекта |
| `python -m pytest tests/test_stock.py -v` | запускает один файл подробно |
| `python -m pytest -k reserve` | выбирает тесты по имени |
| `python -m pytest -x` | останавливается на первом падении |
| `python -m coverage run -m pytest` | собирает покрытие вместе с прогоном |

В учебном проекте тесты лежат в каталоге `tests`, отдельно от кода. Имена файлов начинаются с `test_`, имена функций тоже. Это не формальность: pytest находит тесты по этим шаблонам и не требует ручной регистрации.

Перед коммитом достаточно запустить весь набор. Если набор занимает больше минуты, разделяют быстрые модульные тесты и медленные интеграционные, но быстрые всё равно запускают перед каждой отправкой изменений. В общем репозитории ту же команду выполняет сервер непрерывной интеграции: он собирает проект и прогоняет тесты на чистой машине, где нет забытых файлов и локальных настроек.

Пропускать падающий тест нельзя. Если проверка мешает выпустить изменение, у неё есть причина: либо в коде дефект, либо тест устарел и проверяет старое поведение. В обоих случаях решение принимают явно и записывают в задаче. Пометка «пропустить» без объяснения превращает проверки в набор зелёных галочек, которые ничего не значат.

Тесты не отменяют ручную проверку интерфейса. Они фиксируют то, что уже понятно и повторяется. Новый сценарий сначала исследуют руками, а потом закрепляют тестом, чтобы следующая правка не сломала найденное поведение.

Набор тестов ещё и документирует поведение. По именам проверок видно, какие случаи считаются важными: нулевой резерв, равный остатку резерв, превышение, отрицательный вход. Новый разработчик читает тесты быстрее, чем документацию, и сразу видит, что система обещает. Если поведение изменилось намеренно, тест обновляют вместе с кодом, и история изменений показывает, когда и почему это произошло.

## Итоги

- Тест это записанная проверка входа, действия и ожидаемого результата, которую можно повторить без человека.
- Модульный тест проверяет одну функцию в изоляции, интеграционный проверяет связку модулей и настоящую базу.
- Граничные значения выбирают на переходах между классами: ноль, равенство, превышение на единицу, недопустимый вход.
- Покрытие показывает выполненные строки и ветви, но не доказывает правильность значений.
- Дешёвых модульных тестов должно быть больше, чем интеграционных и сквозных.
- Тест без утверждения, зависящий от порядка или проверяющий реализацию, создаёт ложную защиту.

::quiz
Q: Что такое утверждение в тесте?
+ Строка, которая сравнивает фактический результат с ожидаемым и падает при расхождении
- Комментарий с описанием назначения функции
- Команда запуска всех тестов проекта
- Файл с настройками тестового окружения
! Утверждение фиксирует ожидание и превращает проверку в падающую при ошибке.

Q: Чем модульный тест отличается от интеграционного?
+ Модульный проверяет одну функцию в изоляции, интеграционный проверяет связку модулей
- Модульный всегда медленнее интеграционного
- Интеграционный не может использовать базу данных
- Модульный тест пишут только для интерфейса
! Модульный тест сужает круг поиска, интеграционный проверяет взаимодействие частей.

Q: Какое значение резерва является граничным при остатке 40?
+ 40
- 20
- 10
- 35
! Равенство остатку проверяет переход к нулевому свободному количеству.

Q: Что показывает покрытие строк?
+ Долю инструкций, которые выполнились при прогоне тестов
- Долю функций, для которых написаны тесты
- Число дефектов, найденных тестами
- Время выполнения всего набора тестов
! Покрытие строк считает выполненные инструкции, а не качество проверок.

Q: Почему сто процентов покрытия не гарантируют отсутствие дефектов?
+ Тесты могли выполнить строку, но не проверить правильность результата на границе
- Покрытие всегда считается только для тестов интерфейса
- Сто процентов покрытия невозможно получить в Python
- Покрытие не связано с выполнением кода
! Выполненная строка может вернуть неверное значение, если проверка не покрывает границу.

Q: Что означает падение теста после изменения кода?
+ Изменение нарушило поведение, которое было зафиксировано проверкой
- Тест всегда написан с ошибкой
- Код нужно немедленно откатить без разбора
- Покрытие проекта стало равно нулю
! Падение показывает расхождение с ожидаемым поведением, причину ещё предстоит найти.

Q: Зачем интеграционному тесту отдельная база на каждый тест?
+ Чтобы тесты не зависели от порядка и данных, оставленных другими проверками
- Чтобы увеличить время выполнения набора
- Чтобы база данных работала без SQL-запросов
- Чтобы заменить утверждения проверкой соединения
! Изоляция данных делает результат теста повторяемым.

Q: Что проверяет конструкция `pytest.raises(ValueError)`?
+ Что вызов функции завершился исключением ValueError
- Что функция вернула значение ValueError
- Что функция не выполнила ни одной строки
- Что тест пропущен
! Конструкция фиксирует ожидаемую ошибку как часть контракта функции.

Q: Какой тест считается хорошим?
+ Тот, который проверяет одно наблюдаемое поведение и может упасть при его нарушении
- Тот, который содержит как можно больше утверждений в одной функции
- Тот, который проверяет внутренние поля класса напрямую
- Тот, который проходит только при запуске вместе с другими тестами
! Хороший тест узкий, независимый и способный обнаружить поломку.

Q: Какие значения стоит проверить для функции свободного остатка?
+ Резерв равен нулю
+ Резерв равен остатку
+ Резерв больше остатка на единицу
- Только удобное значение 120 и 30
- Только максимальное число в базе
! Границы и переходы между классами значений ловят большинство ошибок расчёта.

Q: Какие признаки делают тест бесполезным?
+ Отсутствие утверждения
+ Зависимость от порядка запуска других тестов
+ Проверка только заранее заданного ответа заглушки
- Понятное имя, описывающее ожидаемое поведение
- Запуск на маленьком наборе входных данных
! Без утверждения и изоляции тест не обнаруживает дефект.

Q: Что входит в интеграционную проверку сохранения резерва?
+ Выполнение настоящего SQL-запроса к базе
+ Проверка ограничения целостности после записи
+ Чтение сохранённого значения обратно
- Сравнение двух заглушек между собой
- Проверка только формулы в изоляции
! Интеграционный тест проходит путь через базу и проверяет её состояние.

Q: Как называется проверка ожидаемого результата внутри теста?
= утверждение
= assertion
! Утверждение сравнивает фактическое значение с ожидаемым.

Q: Как называется доля кода, выполненного тестами?
= покрытие
= покрытие кода
! Покрытие измеряют по строкам, ветвям или путям.

Q: Какая команда запускает тесты Python в проекте?
= pytest
= python -m pytest
! Pytest находит файлы и функции с именами, начинающимися с test_.
