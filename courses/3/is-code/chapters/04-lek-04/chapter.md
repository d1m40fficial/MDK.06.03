## Ошибка на первой минуте

Новый разработчик открывает проект «Склад+» в VS Code, нажимает «Запустить» и получает `ModuleNotFoundError: No module named 'flask'`. Он устанавливает Flask командой `pip install flask`, повторяет запуск и видит ту же ошибку. На его компьютере два Python: один из Microsoft Store, другой из установщика с сайта python.org. VS Code запускает один, терминал вызывает другой, а `pip` ставит пакет в тот, который нашёл первым, не обязательно в тот, которым выполняется код.

Полчаса уходит на переустановку библиотеки, которая уже установлена. Причина не в коде и не в библиотеке. Причина в том, что никто не сказал, какой интерпретатор является интерпретатором проекта.

**Интерпретатор это конкретный файл программы, который выполняет код, и проект должен запускаться тем файлом, для которого установлены зависимости.** Пока это не зафиксировано, каждая команда может попасть в другое окружение, а ошибка будет выглядеть как дефект программы.

Хуже всего то, что ошибка воспроизводится не у всех. У одного разработчика запуск работает, у другого падает, и оба уверены, что дело в коде. На самом деле у них разные файлы `python.exe`, разные наборы библиотек и разные переменные среды. Поэтому первое, что проверяют при такой жалобе, это версию и путь интерпретатора, а не исходники.

Проверка быстрая и состоит из двух команд: `where python` в терминале и запуск скрипта с `sys.executable`. Если пути не совпадают с папкой `.venv`, дальше искать ошибку в коде бессмысленно. Сначала приводят окружение к одному интерпретатору, потом повторяют сценарий. В половине случаев ошибка исчезает вместе с неправильным окружением.

## Интерпретатор: что запускается на самом деле

Команда `python` не является программой. Это имя, которое оболочка ищет в переменной `PATH` и превращает в путь к исполняемому файлу. Если в `PATH` первым стоит Python из Microsoft Store, запустится он, даже если рядом установлен другой. Поэтому вопрос «какая у меня версия Python» имеет смысл только вместе с вопросом «какой файл запустился».

Порядок в `PATH` объясняет половину странных ошибок. Установщик может добавить новую версию, но старая останется выше в списке. Тогда `python --version` показывает 3.11, хотя в проекте уже создано окружение с 3.13, а `pip` ставит пакеты в 3.11. Команда `where python` в Windows и `which python` в Linux показывают все найденные файлы по порядку. Первый из них и будет запущен.

Проверить это можно из самого кода. Скрипт печатает версию, имя исполняемого файла и признак того, работает ли он внутри виртуального окружения.

```python
import os
import sys

print(sys.version.split()[0])
print(os.path.basename(sys.executable))
print(sys.prefix != sys.base_prefix)
```

Запуск на учебной машине даёт такой результат.

```text
3.13.14
python.exe
False
```

Третья строка `False` означает, что интерпретатор глобальный: его библиотеки лежат в общей папке системы, а не в проекте. Именно так выглядит окружение, в котором `pip install` может поставить пакет для одного проекта и сломать другой.

Есть ещё одна причина ошибок импорта. При запуске файла Python добавляет в `sys.path` папку этого файла, а не корень проекта. Поэтому команда `python src/sklad/__main__.py` может не найти пакет `sklad`, хотя из корня всё работает. Запуск через `python -m sklad` добавляет текущий каталог и находит пакет правильно. Это ещё один довод в пользу единой команды запуска.

| Откуда берётся python | Как проверить | Чем опасен |
|---|---|---|
| установщик с python.org | `python --version`, `where python` | несколько версий в PATH |
| Microsoft Store | `where python` показывает пакет WindowsApps | права на установку пакетов ограничены |
| виртуальное окружение | третья строка скрипта даёт True | нужно активировать или указать путь |
| VS Code выбрал сам | строка состояния или палитра команд | не совпадает с терминалом |

Версия важна не сама по себе, а вместе с зависимостями. Код, написанный для Python 3.12, обычно работает на 3.13, но библиотека может требовать конкретную версию. Если на учебной машине 3.13, а на стенде 3.11, расхождение лучше обнаружить до выпуска.

## Виртуальное окружение

Виртуальное окружение это отдельная папка с копией интерпретатора и своим набором библиотек. Проект получает собственные зависимости, а глобальный Python остаётся нетронутым. Для «Склад+» окружение создают в папке `.venv` внутри проекта.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python l4_env.py
```

После активации приглашение терминала начинается с имени окружения, а третья строка скрипта меняется на `True`.

```text
3.13.14
python.exe
True
```

Теперь `python` указывает на файл внутри `.venv`, а `pip` ставит пакеты туда же. Проверить состав установленного можно командой `python -m pip list`: она покажет только библиотеки проекта, а не весь набор системы.

В PowerShell активация может быть запрещена политикой выполнения сценариев. Тогда есть два выхода: разрешить сценарии для текущего пользователя командой `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` или не активировать окружение вовсе, а вызывать интерпретатор напрямую.

```powershell
.\.venv\Scripts\python.exe l4_env.py
```

Прямой вызов даже надёжнее: он не зависит от того, что сейчас активировано в терминале. Активация удобна для интерактивной работы, а в скриптах сборки и в задачах VS Code путь к интерпретатору указывают явно.

| Действие | Команда | Результат |
|---|---|---|
| создать окружение | `python -m venv .venv` | папка `.venv` с интерпретатором |
| активировать в PowerShell | `.\.venv\Scripts\Activate.ps1` | `python` указывает в `.venv` |
| запустить без активации | `.\.venv\Scripts\python.exe файл.py` | тот же интерпретатор |
| посмотреть пакеты | `python -m pip list` | список библиотек окружения |
| зафиксировать зависимости | `python -m pip freeze` | строки для файла зависимостей |

Устройство окружения простое. В папке появляется свой `python.exe`, файл `pyvenv.cfg` с путём к базовому интерпретатору и каталог `Lib/site-packages` для библиотек. Пакеты, установленные в это окружение, не видны глобальному Python, а глобальные пакеты не видны проекту, если их специально не добавить. Такая изоляция и есть смысл venv: обновление библиотеки для одного проекта не ломает другой.

Список зависимостей получают командой `python -m pip freeze`. Она печатает установленные пакеты с точными версиями, и этот список сохраняют в файле проекта. На другой машине окружение создают заново и ставят пакеты из списка. Так повторяют не папку `.venv`, а состав библиотек, что надёжнее и переносимо между системами.

Папку `.venv` не хранят в Git. Она большая, зависит от операционной системы и легко создаётся заново из списка зависимостей. В репозитории лежит файл с версиями, а окружение каждый разворачивает у себя.

## VS Code: папка, интерпретатор, терминал

VS Code не является средой выполнения Python. Он редактор, который запускает выбранный интерпретатор и показывает результат. Поэтому первое действие в новом проекте это открыть папку проекта целиком, а не отдельный файл. От корня папки зависят поиск настроек, терминал и запуск тестов.

Второе действие: выбрать интерпретатор. Это делают через палитру команд: `Python: Select Interpreter`, затем пункт с путём внутри `.venv`. Выбор сохраняется в настройках рабочей папки, и строка состояния показывает версию и имя окружения.

| Элемент | Файл | Зачем |
|---|---|---|
| выбранный интерпретатор | .vscode/settings.json | запуск и подсказки используют `.venv` |
| конфигурация запуска | .vscode/launch.json | аргументы, рабочая папка, режим отладки |
| терминал | вкладка Terminal | команды выполняются в окружении проекта |
| задачи | .vscode/tasks.json | повторяемые команды сборки и тестов |

Настройку интерпретатора можно записать в `.vscode/settings.json`, чтобы она применялась у всех, кто открыл проект.

```json
{
  "python.defaultInterpreterPath": "${workspaceFolder}/.venv/Scripts/python.exe"
}
```

Путь относительный: `${workspaceFolder}` подставляет корень открытой папки. На Linux и macOS путь к интерпретатору другой, поэтому в общем проекте такие настройки дополняют или описывают в README. Для учебной машины с Windows указанного пути достаточно.

Настройки VS Code бывают пользовательскими и на уровне рабочей папки. Пользовательские действуют во всех проектах, настройки папки лежат в `.vscode/settings.json` и применяются только здесь. Если интерпретатор выбран в пользовательских настройках, он может перебить настройку проекта. Поэтому выбор `.venv` сохраняют именно на уровне папки, а не глобально.

Файл `.vscode/launch.json` описывает запуск для отладчика. В нём указывают тип `python`, путь к программе, рабочую папку и аргументы командной строки. Рабочая папка важна для относительных путей: если она равна корню проекта, база `data/demo.sqlite` находится, а если указана папка `src/`, тот же путь ведёт в другое место. Конфигурацию хранят в репозитории, чтобы у всей команды запуск был одинаковым.

Похожий файл `.vscode/tasks.json` хранит повторяемые команды: прогон тестов, проверку стиля, сборку. Задача запускается из меню и не требует помнить длинную строку. Для проекта «Склад+» достаточно двух задач: `python -m pytest` и `python -m sklad`. Обе выполняются выбранным интерпретатором, поэтому задача и терминал дают одинаковый результат.

Терминал VS Code наследует окружение, но не всегда переключается на новый интерпретатор сам. Если после выбора `.venv` в терминале всё ещё работает глобальный Python, терминал нужно открыть заново. Проверка та же: запустить скрипт и посмотреть третью строку.

## Отладка: точка останова и шаги

Отладчик останавливает программу в выбранном месте и показывает состояние. Точка останова ставится щелчком слева от номера строки. Запуск через `F5` начинает отладку, запуск через кнопку треугольника выполняет программу без остановок.

Когда программа остановилась, доступны несколько действий. Шаг с заходом (`F11`) входит внутрь вызываемой функции. Шаг через (`F10`) выполняет строку целиком и остаётся в текущей функции. Шаг с выходом (`Shift+F11`) доходит до конца текущей функции и возвращается к вызывающему коду. Продолжить (`F5`) идёт до следующей точки останова.

В панели переменных видно текущие значения, в панели стека вызовов цепочку функций, которые привели к этой строке. Стек читают сверху вниз: верхняя строка это место, где программа стоит сейчас, нижние показывают, кто её вызвал.

| Действие | Клавиша | Когда нужно |
|---|---|---|
| продолжить | F5 | до следующей точки останова |
| шаг через | F10 | выполнить строку, не заходя в функцию |
| шаг с заходом | F11 | проверить, что происходит внутри функции |
| шаг с выходом | Shift+F11 | вернуться к вызывающему коду |
| остановить | Shift+F5 | прервать отладку |

Отладчик полезен, когда непонятно, почему значение стало не тем. Он показывает факт, а не догадку. Печать через `print` тоже работает, но требует правок в коде и не даёт посмотреть стек. Для одной переменной хватит печати, для разбора цепочки вызовов нужен отладчик.

Разберём сценарий. В отчёте по Туле вместо 1110 появляется 1150. Точку останова ставят на строку `return positions - reserved` в функции `available`. После запуска отладчик останавливается, и в панели переменных видно: `positions` равно 1150, `reserved` равно 0. Значит, значение резерва не дошло до функции. Шаг с выходом возвращает в `report`, где видно, что из строки базы взяты только позиции, а резерв потерян при разборе. Причина найдена по значениям, а не по догадке.

Отладка не заменяет тест. Она объясняет один конкретный запуск, а тест закрепляет правило для всех запусков. После находки добавляют проверку `available(1150, 40) == 1110`, и в следующий раз дефект ловит сборка, а не человек с точкой останова.

## Как читать трассировку

Трассировка это отчёт интерпретатора о том, где и почему программа остановилась. Она выглядит пугающе, но читается по правилам. Ниже скрипт, который должен показать остаток по площадке, но обращается к площадке, которой нет в словаре.

```python
def available(positions, reserved):
    return positions - reserved


def report(site):
    data = {"Тула": (1150, 40), "Калуга": (570, 15)}
    positions, reserved = data[site]
    return available(positions, reserved)


print(report("Тверь"))
```

Запуск завершается ошибкой.

```text
Traceback (most recent call last):
  File "l4_bug.py", line 11, in <module>
    print(report("Тверь"))
          ~~~~~~^^^^^^^^^
  File "l4_bug.py", line 7, in report
    positions, reserved = data[site]
                          ~~~~^^^^^^
KeyError: 'Тверь'
```

Читать нужно снизу. Последняя строка `KeyError: 'Тверь'` называет тип ошибки и значение, которого не хватило. Выше два кадра: первый показывает строку 11, где вызван `report`, второй строку 7, где произошёл сбой. Порядок кадров обратный порядку выполнения: сверху то, что было раньше, снизу то, что случилось последним.

Номер строки в нижнем кадре указывает на `data[site]`. Значение `site` равно `"Тверь"`, а в словаре есть только Тула и Калуга. Причина не в функции `available`, до неё управление не дошло. Причина в том, что код не проверил наличие площадки.

Бывает, что ошибка вызвана другой ошибкой. Тогда интерпретатор показывает две трассировки подряд, соединённые строкой `The above exception was the direct cause of the following exception`. Читают их так же снизу: нижняя часть говорит, что произошло в итоге, верхняя показывает исходную причину. При обработке исключений связь сохраняют через `raise ... from ...`, иначе причина теряется и остаётся только внешнее сообщение.

Верхние кадры нужны, чтобы понять путь. По ним видно, из какого обработчика вызвана функция и какие аргументы переданы. Но искать правку всегда начинают с нижнего кадра: именно там программа столкнулась с реальностью. Если нижний кадр находится в чужой библиотеке, смотрят кадр выше него, то есть последний свой вызов.

Под строкой кода в трассировке стоят знаки `^^^^`. Они подчёркивают выражение, на котором произошёл сбой, и помогают не гадать, что именно вычислялось. В примере каретка стоит под `data[site]`, а не под всем присваиванием. Это ускоряет чтение длинной строки с несколькими вызовами.

Путь к файлу в сообщении сокращён до имени, чтобы не загромождать запись. В реальном окне терминала перед именем стоит полный путь, и по нему видно, какой файл запущен. Если путей два и они разные, это признак того, что запускается копия из другого каталога.

Исправление добавляет проверку и понятное сообщение.

```python
def available(positions, reserved):
    return positions - reserved


def report(site):
    data = {"Тула": (1150, 40), "Калуга": (570, 15)}
    if site not in data:
        return f"Площадка {site} не найдена"
    positions, reserved = data[site]
    return f"{site}: {available(positions, reserved)} позиций"


print(report("Тула"))
print(report("Тверь"))
```

```text
Тула: 1110 позиций
Площадка Тверь не найдена
```

Такая проверка не делает программу правильной, но делает отказ понятным. Пользователь видит, что площадки нет, а не стек вызовов на пол-экрана. Для учебного проекта этого достаточно, для боевой системы сообщение дополнительно пишут в журнал.

## Типичные ошибки

**Не тот интерпретатор.** Симптом: пакет установлен, но `ModuleNotFoundError` остаётся. Причина: установка и запуск попали в разные Python. Лечение: выбрать `.venv` и проверить третью строку скрипта.

**Окружение не активировано.** Симптом: в терминале работает глобальный Python. Причина: активация выполнена в другом окне. Лечение: новый терминал или прямой путь к интерпретатору.

**Запуск из чужого каталога.** Симптом: файл не найден или база открылась пустая. Причина: относительный путь считается от текущей папки. Лечение: запускать из корня проекта или задавать рабочую папку в `launch.json`.

**Пробелы и кириллица в пути.** Симптом: команда разваливается на части. Причина: путь не взят в кавычки. Лечение: кавычки вокруг пути и латинские имена каталогов для кода.

**Читают только первую строку.** Симптом: правят не тот файл. Причина: причина указана в последней строке, а не в первой. Лечение: читать снизу вверх и смотреть нижний кадр.

**Отладка вместо теста.** Симптом: дефект найден, но завтра возвращается. Причина: проверка осталась в голове. Лечение: после отладки добавить тест на найденный случай.

**Правка установленной библиотеки.** Симптом: исправление работает на одной машине и исчезает после переустановки. Причина: файл пакета изменён прямо в `site-packages`. Лечение: не трогать чужой код, оформлять обход в своём модуле или обновлять библиотеку.

**Несколько открытых терминалов.** Симптом: в одном окне окружение активно, в другом нет. Причина: активация действует только на текущую оболочку. Лечение: проверять интерпретатор в каждом окне или вызывать его по пути.

**Запуск через стороннюю кнопку.** Симптом: в терминале всё работает, а при запуске кнопкой расширения ошибка возвращается. Причина: расширение запускает свой интерпретатор. Лечение: запускать через конфигурацию отладки или терминал.

## Практический вывод

Откройте проект «Склад+» и выполните три проверки. Запустите скрипт с версией и убедитесь, что третья строка даёт `True`. Выберите тот же интерпретатор в VS Code и перезапустите терминал. Поставьте точку останова в функции расчёта и пройдите её по шагам, записав значения переменных.

Затем намеренно сломайте код: обратитесь к несуществующей площадке и прочитайте трассировку снизу вверх. Найдите тип ошибки, нижний кадр и строку. Исправьте код проверкой и повторите запуск. Такое упражнение снимает страх перед красным текстом в терминале. Так проверка окружения становится частью работы, а не разовым разбором.

## Итоги

- `python` это имя в PATH, поэтому важно знать, какой файл запускается.
- Виртуальное окружение даёт проекту собственный интерпретатор и набор библиотек.
- `.venv` не хранят в Git, зависимости фиксируют в файле проекта.
- VS Code запускает выбранный интерпретатор, и его выбор должен совпадать с терминалом.
- Точка останова, шаги и стек вызовов показывают состояние программы без правок кода.
- Трассировку читают снизу: тип ошибки, затем нижний кадр с нужной строкой.
- Рабочая папка запуска влияет на относительные пути к базе и файлам.
- Сторонние расширения запускают свой интерпретатор, поэтому запуск проверяют в терминале.
- Окружение проекта воспроизводят из списка зависимостей, а не копированием папки.
