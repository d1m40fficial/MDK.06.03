## Склад, который открылся пустым

В понедельник в 07:50 кладовщик в Твери открыл «Склад+» и увидел пустой список товаров. Приёмка не начиналась, а на площадке уже стояла машина с товаром. Через десять минут то же самое сообщили из Тулы. В Москве система работала, в Калуге работала, а две площадки остались без данных.

Разбирательство заняло сорок минут. Код приложения был тот же, что и в пятницу. База на сервере тоже была на месте: 4800 позиций, 12 товарных категорий, все накладные. Проблема оказалась в одной строке, которую разработчик писал на своём ноутбуке:

```python
DB_PATH = "data/sklad.db"
```

Путь был относительным, и на новой машине он указывал в другой каталог. Приложение не упало: оно создало пустой файл `data/sklad.db` и продолжило работу. Кладовщик видел не ошибку, а пустой склад. Вторая строка добавляла проблем: порт 8000 на сервере был занят службой мониторинга, поэтому приложение запустилось на другом порту, а балансировщик продолжал отправлять запросы на старый.

**Настройка это значение, которое отличает один запуск программы от другого, не меняя её логику.** Путь к базе, номер порта, уровень журнала, адрес внешнего сервиса и пароль к нему относятся к настройкам. Формула свободного остатка, структура таблицы и порядок проверки прав относятся к коду и данным. Если для смены значения нужно править исходник и пересобирать приложение, значение попало не на своё место.

В «Северном складе» 120 сотрудников на четырёх площадках. У каждой площадки свой канал связи, но приложение одно. Если настройки зашиты в код, каждая площадка требует отдельной сборки, а исправление пароля превращается в выпуск новой версии. Если настройки вынесены, один и тот же артефакт запускается в Москве, Твери, Туле и Калуге с разными файлами и переменными.

## Что считается настройкой

Граница между кодом и настройкой проходит по вопросу «меняется ли это без изменения поведения». Путь к файлу базы меняется при переносе, а запрос `SELECT` остаётся тем же. Уровень журнала меняется между разработкой и эксплуатацией, а сообщения в журнале остаются теми же. Список из 12 категорий товаров меняется редко и приходит из базы, поэтому это данные, а не настройка приложения.

| Параметр | Разработка | Эксплуатация | Почему меняется |
|---|---|---|---|
| Путь к базе | `data/sklad.db` | `data/sklad.db` на сервере площадки | каталог зависит от машины |
| Порт API | 8000 | 8000 за обратным прокси | порт занимает другая служба |
| Уровень журнала | `DEBUG` | `WARNING` | объём записей и режим разбора |
| Секретный ключ | `dev-only` | случайная строка | подпись токенов и сессий |
| Адрес внешнего API | `http://localhost:9000` | `https://api.severny-sklad.ru` | адрес зависит от контура |
| Режим отладки | включён | выключен | отладчик не должен быть доступен пользователям |

Есть пограничные случаи. Признак функции, который включает новую форму приёмки для одной площадки, это настройка: поведение меняется, но код остаётся одним. Часовой пояс сервера тоже настройка, хотя он влияет на даты в накладных. А вот правило «резерв не может превышать остаток» настройкой не является: это бизнес-правило, и его изменение требует правки кода и тестов.

Полезно проверить себя простым вопросом: если значение поменять, должен ли измениться результат работы программы для того же ввода? Для пути к базе результат меняется только потому, что меняются данные. Для формулы резерва результат меняется при тех же данных, значит, это логика. Настройка выбирает, с какими данными и в каком окружении работать, но не решает, как считать.

## Три источника и порядок старшинства

У настройки обычно несколько источников. Значение по умолчанию записано в коде и работает, когда ничего не задано. Файл конфигурации хранит набор значений для конкретной среды. Переменная окружения переопределяет файл, не требуя правки. Аргумент командной строки переопределяет всё и удобен для разового запуска.

| Источник | Кто использует | Когда применяется | Риск |
|---|---|---|---|
| Значение по умолчанию | разработчик | ничего не задано | незаметно уехало в эксплуатацию |
| Файл конфигурации | команда | нужен набор значений | файл попал в репозиторий с секретом |
| Переменная окружения | сервер, контейнер, CI | значение задаёт площадка | забыли задать на новой машине |
| Аргумент командной строки | инженер | разовая проверка | расходится с остальными запусками |

Порядок старшинства важно зафиксировать в проекте, иначе два разработчика будут уверены в разных вещах. В `sklad-plus` принято правило: аргумент командной строки важнее переменной окружения, переменная окружения важнее файла, файл важнее значения по умолчанию. Такое правило совпадает с поведением большинства фреймворков и не удивляет нового человека.

Соберём небольшой модуль конфигурации на Python. Он читает четыре параметра, подставляет значения по умолчанию и маскирует секрет при выводе.

```python
import os
from dataclasses import dataclass

def env(name: str, default: str) -> str:
    return os.environ.get(name, default)

@dataclass(frozen=True)
class Config:
    db_path: str
    api_port: int
    log_level: str
    secret_key: str

def load_config() -> Config:
    return Config(
        db_path=env("SKLAD_DB_PATH", "data/sklad.db"),
        api_port=int(env("SKLAD_API_PORT", "8000")),
        log_level=env("SKLAD_LOG_LEVEL", "INFO").upper(),
        secret_key=env("SKLAD_SECRET_KEY", "dev-only"),
    )

def show(cfg: Config) -> None:
    print(f"db={cfg.db_path}")
    print(f"port={cfg.api_port}")
    print(f"log={cfg.log_level}")
    print("secret=" + ("*" * 8 if cfg.secret_key else "missing"))

if __name__ == "__main__":
    show(load_config())
```

Запуск без переменных окружения даёт значения по умолчанию:

```text
db=data/sklad.db
port=8000
log=INFO
secret=********
```

Теперь зададим порт и уровень журнала в терминале PowerShell и запустим тот же файл:

```text
$env:SKLAD_API_PORT = "8080"
$env:SKLAD_LOG_LEVEL = "warning"
python config.py
```

```text
db=data/sklad.db
port=8080
log=WARNING
secret=********
```

В Linux те же значения задают командой `export SKLAD_API_PORT=8080`. Код не изменился, изменилось окружение. Именно это и требуется от конфигурации: один файл программы, разные параметры запуска.

Обратите внимание на преобразования. `os.environ.get` всегда возвращает строку или значение по умолчанию. Порт приходится превращать в целое через `int`, иначе он останется строкой и сравнение с числом даст неожиданный результат. Уровень журнала приводится к верхнему регистру, потому что `warning` и `WARNING` должны означать одно и то же. Секрет не печатается целиком: в журнал и на экран попадает только факт его наличия.

`@dataclass(frozen=True)` делает объект настроек неизменяемым. Это мелочь, которая ловит ошибку: если какой-то модуль попытается поменять порт уже после старта, программа упадёт сразу, а не будет работать с половиной старых и половиной новых значений. Настройки читают один раз при запуске и передают дальше как готовый объект.

## Файл, среда и профиль

Файл конфигурации хранит набор значений, которые относятся к одной среде. Формат выбирают по задаче. `.env` удобен для небольших проектов и локального запуска: это простые пары «ключ=значение», которые читает библиотека вроде `python-dotenv` или загрузчик фреймворка. JSON удобен для вложенных настроек и уже используется в C#. TOML читается человеком и поддерживает комментарии. YAML компактен, но чувствителен к отступам.

| Формат | Вложенность | Комментарии | Типичное место |
|---|---|---|---|
| `.env` | нет | да | локальный запуск, переменные окружения |
| JSON | да | нет | `appsettings.json`, обмен с сервисами |
| TOML | да | да | `pyproject.toml`, настройки Python |
| YAML | да | да | конфигурация развёртывания |

В Python удобно держать настройки в `config.py` и переопределять их переменными окружения. В C# приложение ASP.NET Core собирает те же слои через `builder.Configuration`: сначала читает `appsettings.json`, затем `appsettings.{Environment}.json`, затем переменные окружения, затем аргументы командной строки. Последний источник побеждает. Имя среды задаёт переменная `ASPNETCORE_ENVIRONMENT`, а файл для эксплуатации называется `appsettings.Production.json`.

```json
{
  "Sklad": {
    "DbPath": "data/sklad.db",
    "ApiPort": 8000,
    "LogLevel": "Warning"
  }
}
```

```json
{
  "Sklad": {
    "DbPath": "data/sklad.db",
    "ApiPort": 8080,
    "LogLevel": "Warning"
  }
}
```

Первый файл относится к разработке, второй к эксплуатации. Общие значения можно оставить в базовом файле, а различия вынести в файл среды. Если значение задано в обоих, побеждает файл среды. Это позволяет не дублировать десяток одинаковых строк и видеть только то, что действительно отличается.

В C# чтение переменной окружения выглядит так:

```csharp
using System;

class Program
{
    static string Read(string name, string fallback)
    {
        string value = Environment.GetEnvironmentVariable(name);
        return string.IsNullOrEmpty(value) ? fallback : value;
    }

    static void Main()
    {
        string dbPath = Read("SKLAD_DB_PATH", "data/sklad.db");
        int port = int.Parse(Read("SKLAD_API_PORT", "8000"));
        Console.WriteLine("db=" + dbPath);
        Console.WriteLine("port=" + port);
    }
}
```

Без переменных окружения программа печатает значения по умолчанию:

```text
db=data/sklad.db
port=8000
```

После установки `SKLAD_API_PORT=8080` тот же исполняемый файл печатает:

```text
db=data/sklad.db
port=8080
```

Профиль это именованный набор настроек для среды: `dev`, `test`, `prod`. Профиль не является отдельной копией кода. Он выбирает, какие значения подставить и какие проверки включить. В разработке профиль `dev` разрешает отладочный режим и подробный журнал, в тесте `test` использует тестовую базу и выключенный отладчик, в эксплуатации `prod` требует настоящий секрет и минимальный уровень журнала.

| Профиль | База | Порт | Журнал | Отладка | Кто работает |
|---|---|---|---|---|---|
| `dev` | `data/sklad.db` | 8000 | `DEBUG` | включена | разработчик |
| `test` | `data/sklad-test.db` | 8080 | `INFO` | выключена | тестировщик |
| `prod` | `data/sklad.db` | 8000 за прокси | `WARNING` | выключена | 120 сотрудников |

Профиль задают одной переменной, например `SKLAD_ENV=prod`. Все остальные модули читают уже готовый объект настроек и не проверяют окружение самостоятельно. Если каждый модуль начнёт спрашивать `os.environ` напрямую, через месяц никто не сможет сказать, откуда взялось конкретное значение. Одна точка чтения и один объект настроек дают предсказуемость.

Профиль не должен управлять бизнес-логикой. Если от значения `prod` зависит, показывать ли кладовщику кнопку удаления накладной, это уже правило предметной области, а не настройка среды. Такое правило должно быть в коде и в правах роли, иначе на тестовом стенде одна ветка поведения, а в эксплуатации другая. Настройка выбирает окружение, но не подменяет правила работы склада.

Настройки тоже проверяют тестами. Достаточно одного теста, который загружает конфигурацию с набором переменных и сравнивает получившиеся значения. Второй тест проверяет отказ на неверном порту или отсутствующем секрете. Такие тесты не требуют базы и выполняются за доли секунды, зато ловят опечатку в имени переменной до запуска приложения. В конвейере эти проверки запускают перед сборкой, чтобы ошибка в настройках не дошла до стенда.

## Секреты не живут в репозитории

Пароль к базе, секретный ключ подписи, токен внешнего сервиса и ключ почтового шлюза называются секретами. Их нельзя хранить в Git, даже в приватном репозитории. История коммитов переживает удаление файла: если секрет попал в коммит, он остаётся в истории и доступен всем, у кого есть клон. Удаление строки из последней версии не делает секрет недействительным.

Рабочая схема состоит из двух файлов. Настоящий `.env` лежит на машине или на сервере, содержит значения и добавлен в `.gitignore`. Пример `.env.example` лежит в репозитории, содержит те же имена переменных с пустыми или условными значениями и объясняет, что нужно заполнить.

```text
# .env.example
SKLAD_ENV=dev
SKLAD_DB_PATH=data/sklad.db
SKLAD_API_PORT=8000
SKLAD_LOG_LEVEL=INFO
SKLAD_SECRET_KEY=change-me
```

```text
# .gitignore
.env
.venv/
__pycache__/
data/*.db
```

Проверка простая: `git status --short` не должен показывать `.env`. Если файл уже попал в индекс, его убирают командой `git rm --cached .env`, но это не удаляет секрет из истории. Секрет считают скомпрометированным и меняют. Затем историю очищают отдельно, если репозиторий уже отправлен другим.

| Место хранения | Кто видит | Подходит для | Опасность |
|---|---|---|---|
| Код в репозитории | все, у кого есть клон | ничего секретного | утечка навсегда |
| `.env` на машине | владелец файла | локальный запуск | файл попал в архив или коммит |
| Переменная окружения | процесс и администратор | сервер, контейнер | видна в выводе диагностики |
| Хранилище секретов | приложение по роли | эксплуатация | сложнее настроить |

В эксплуатации секрет передают переменной окружения или через хранилище секретов. На учебном стенде достаточно переменной и файла с правами `600`, то есть доступного только владельцу. В Windows права на файл настраивают через свойства безопасности, в Linux командой `chmod 600 .env`. Смысл один: секрет не должен читаться другими пользователями машины.

Секрет не печатают в журнал. Даже если очень хочется проверить, какое значение загрузилось, выводят только длину или первые символы. В `sklad-plus` принято правило: в журнал попадает имя параметра и источник, но не значение. Это спасает от утечки через диагностический архив, который отправляют в поддержку.

> [!PITFALL] Секрет в примере
> Иногда в `.env.example` оставляют настоящий пароль, чтобы «было понятно». Это тот же секрет в репозитории, только с другим именем файла. В примере допустимы только условные значения вроде `change-me` и пояснение, где взять настоящее.

## Проверка настроек при старте

Настройки читают один раз, но проверять их нужно до того, как приложение начнёт принимать запросы. Ошибка в порту или отсутствующий секрет должны остановить запуск с понятным сообщением. Иначе приложение поднимется, ответит на первый запрос ошибкой 500 и будет выглядеть как дефект бизнес-логики.

```python
import os
from config import Config, load_config

def validate(cfg: Config) -> None:
    if not 1 <= cfg.api_port <= 65535:
        raise ValueError(f"порт вне диапазона: {cfg.api_port}")
    if cfg.secret_key == "dev-only" and os.environ.get("SKLAD_ENV") == "prod":
        raise ValueError("в prod нужен собственный SKLAD_SECRET_KEY")

if __name__ == "__main__":
    validate(load_config())
    print("настройки приняты")
```

Запуск с портом 70000 останавливается на первой проверке:

```text
ValueError: порт вне диапазона: 70000
```

Запуск с профилем `prod` и значением по умолчанию для секрета останавливается на второй:

```text
ValueError: в prod нужен собственный SKLAD_SECRET_KEY
```

Проверка не заменяет тесты. Она ловит ошибку окружения, а не ошибку алгоритма. Но именно она превращает непонятный отказ через час после запуска в короткое сообщение при старте. Хорошая проверка называет параметр, допустимый диапазон и фактическое значение, чтобы дежурный мог исправить настройку без чтения исходников.

| Что проверяют | Пример ошибки | Сообщение |
|---|---|---|
| Обязательное значение | нет `SKLAD_SECRET_KEY` в `prod` | «в prod нужен собственный ключ» |
| Диапазон | порт 70000 | «порт вне диапазона: 70000» |
| Допустимое значение | уровень `TRACE` | «неизвестный уровень журнала» |
| Путь | каталог `data` отсутствует | «каталог базы не найден» |
| Согласованность | `prod` и отладка включена | «отладка запрещена в prod» |

Проверку путей стоит делать отдельно от проверки значений. Приложение может создать каталог само, но только если ему разрешено писать. На сервере служба работает под отдельным пользователем, и права на каталог `data` должны быть выданы заранее. Если приложение молча создаёт пустую базу в другом месте, получается ровно та ситуация, с которой началась лекция.

## Профили и расхождения

Настройки расходятся по четырём причинам: разные имена параметров, разные источники, разные значения по умолчанию и разное время применения. Имена должны совпадать во всех средах. Если в разработке параметр называется `DB_PATH`, а в эксплуатации `SKLAD_DB_PATH`, приложение прочитает значение по умолчанию и не заметит подмены.

Источники тоже нужно проверять. Локальный запуск может читать `.env`, а сервер получает переменные от службы. Если на сервере `.env` не загружается, все значения окажутся по умолчанию. Поэтому в журнал при старте пишут, какие источники найдены: файл, окружение, аргументы. Это не раскрывает секреты и сразу показывает расхождение.

Значения по умолчанию опасны тем, что работают молча. Значение `dev-only` для секрета удобно в разработке, но в эксплуатации оно означает предсказуемую подпись токенов. Поэтому для секретов значение по умолчанию либо отсутствует, либо запрещено в `prod`. Для несекретных параметров значение по умолчанию допустимо и полезно: новый разработчик запускает проект без чтения документации.

Время применения связано с перезапуском. Большинство настроек читается при старте, поэтому изменение файла не действует на работающий процесс. Если инженер поправил порт и не перезапустил службу, он будет искать причину в другом месте. Настройки, которые меняются на лету, выделяют отдельно и описывают в документации.

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| На новой машине пустая база | относительный путь и другой рабочий каталог | `SKLAD_DB_PATH`, текущий каталог службы |
| Порт занят | значение по умолчанию совпало с другой службой | `SKLAD_API_PORT`, список портов |
| Секрет виден в журнале | вывод объекта настроек целиком | маскирование и уровень журнала |
| В `prod` работает отладка | профиль не передан службой | `SKLAD_ENV`, файл службы |
| Изменение не действует | процесс не перезапущен | время старта процесса |

## Типичные ошибки

**Путь, привязанный к компьютеру.** В коде остаётся путь к домашней папке конкретного пользователя. На другой машине приложение либо падает, либо создаёт пустую базу. Лечение: относительный путь от каталога проекта и параметр `SKLAD_DB_PATH`.

**Секрет в репозитории.** Пароль лежит в `config.py` или в `.env`, который попал в коммит. Симптом: секрет виден в истории и в любом клоне. Лечение: вынести в переменную, сменить значение, добавить `.env` в `.gitignore`.

**Строка вместо числа.** Порт читают как строку и сравнивают с числом. Симптом: проверка `port > 1024` всегда ложна или падает с `TypeError`. Лечение: явное преобразование и проверка ошибки преобразования.

**Булево значение из строки.** `os.environ.get("DEBUG")` возвращает строку `"False"`, а любая непустая строка в Python истинна. Симптом: отладка включена, хотя в настройке написано `False`. Лечение: отдельная функция разбора `true/false` и проверка допустимых значений.

**Разные имена в средах.** В разработке `PORT`, в эксплуатации `SKLAD_API_PORT`. Симптом: на сервере всегда 8000. Лечение: один список имён и проверка при старте.

**Файл `.env` не загружен.** Локально его читает библиотека, на сервере служба запускает приложение без переменных. Симптом: все значения по умолчанию. Лечение: явная загрузка файла или передача переменных в службе.

**Рабочий каталог другой.** Относительный путь `data/sklad.db` считается от каталога, из которого запущен процесс. Симптом: база создаётся в неожиданном месте. Лечение: `WorkingDirectory` в службе и проверка каталога при старте.

**Секрет в журнале.** Приложение печатает весь объект настроек при старте. Симптом: пароль в текстовом журнале и в архиве диагностики. Лечение: маскирование и запрет вывода значений секретов.

**Настройка изменена без перезапуска.** Инженер правит файл и ждёт эффекта. Симптом: «изменение не работает». Лечение: перезапуск службы и запись времени старта в журнал.

> [!KEY] Одна точка чтения
> Все настройки читает один модуль, остальной код получает готовый объект. Тогда порядок старшинства, преобразования и проверки описаны в одном месте, а не разбросаны по проекту.

## Итоги

- Настройка отличает запуски друг от друга, не меняя логику: путь, порт, журнал, адрес и секрет.
- Источники настройки идут по старшинству: аргумент, переменная окружения, файл, значение по умолчанию.
- Значения из окружения приходят строками, поэтому число, логическое значение и уровень журнала нужно разбирать явно.
- Секреты хранят вне репозитория, в `.env` или хранилище секретов, а в репозитории держат только `.env.example`.
- Профиль выбирает набор настроек для среды, но не создаёт отдельную копию кода.
- Проверка при старте останавливает приложение с понятным сообщением, пока ошибка не дошла до пользователя.

::quiz
Q: Что относится к настройкам приложения?
+ Путь к файлу базы, порт и уровень журнала
- Формула расчёта свободного остатка
- Структура таблицы товаров
- Количество товарных категорий в справочнике
! Настройки меняют окружение запуска, а не правила расчёта и структуру данных.

Q: Что произойдёт, если параметр задан и в файле, и в переменной окружения?
+ Переменная окружения переопределит значение из файла
- Файл переопределит переменную окружения
- Приложение остановится с конфликтом
- Будет использовано среднее значение
! Переменная окружения стоит выше файла в порядке старшинства.

Q: Зачем нужен файл `.env.example`?
+ Показать состав переменных без настоящих значений
- Хранить рабочий пароль для быстрого запуска
- Заменить файл `.env` на сервере
- Хранить историю изменений настроек
! Пример описывает, какие переменные нужны, но не содержит секретов.

Q: Где хранить секрет в эксплуатации?
+ В переменной окружения или хранилище секретов
- В исходном коде рядом с настройками
- В файле `.env.example` в репозитории
- В сообщении коммита
! Секрет передают вне репозитория и ограничивают доступ к нему.

Q: Почему значение из переменной окружения нужно преобразовывать?
+ Оно всегда приходит строкой
- Оно всегда приходит числом
- Оно хранится в бинарном виде
- Оно не поддерживает кириллицу
! `os.environ.get` возвращает строку, поэтому порт и флаги разбирают явно.

Q: Что означает профиль `prod`?
+ Набор настроек для эксплуатационного запуска
- Отдельную копию исходного кода
- Ветку Git для выпуска
- Файл с журналом ошибок
! Профиль выбирает значения для среды, а код остаётся одним.

Q: Что делать, если обязательная настройка отсутствует при старте?
+ Остановить запуск с понятным сообщением
- Подставить любое значение и продолжить
- Создать пустую базу
- Отключить проверку прав
! Ошибка окружения должна быть видна сразу, а не через час работы.

Q: Почему относительный путь к базе опасен?
+ Он зависит от рабочего каталога процесса
- Он всегда длиннее абсолютного
- Его нельзя прочитать в Linux
- Он запрещён в SQLite
! Служба может запускаться из другого каталога, и база создастся не там.

Q: Что делать при утечке секрета в историю Git?
+ Заменить секрет и очистить историю репозитория
- Удалить строку из последнего коммита и считать вопрос закрытым
- Переименовать файл с секретом
- Добавить секрет в `.gitignore` задним числом
! Секрет остаётся в истории, поэтому его меняют, а историю очищают.

Q: Какие значения стоит выносить в настройки?
+ Порт API
+ Путь к файлу базы
+ Уровень журнала
- Формулу свободного остатка
- Структуру таблиц
! Настройки описывают окружение, а не бизнес-правила и схему.

Q: Какие источники настроек переопределяют друг друга?
+ Файл конфигурации
+ Переменные окружения
+ Аргументы командной строки
- Комментарии в исходном коде
! Источники образуют порядок старшинства, комментарии в нём не участвуют.

Q: Какие признаки указывают на проблему с конфигурацией?
+ На тестовой машине приложение слушает другой порт
+ В журнале появился секретный ключ
+ После переноса создалась пустая база
- Все тесты проходят на машине разработчика
! Расхождение окружений и утечка секрета относятся к настройкам.

Q: Что входит в проверку настроек при старте?
+ Диапазон порта
+ Наличие обязательного секрета
+ Доступность каталога для базы
- Цвет кнопки на главной странице
! Проверяют значения, от которых зависит запуск и безопасность.

Q: Как называют набор настроек для конкретной среды?
= профиль
= конфигурационный профиль
! Профиль выбирает значения для разработки, теста или эксплуатации.

Q: Каким способом в Python получают значение переменной окружения?
= os.environ.get
= os.getenv
! Обе функции читают переменную и позволяют задать значение по умолчанию.
