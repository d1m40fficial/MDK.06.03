## Цель работы

Сервис, который работает только на машине автора, нельзя проверить и нельзя передать другому разработчику. Цель работы: поднять Flask-приложение с двумя маршрутами, получить список товаров и добавить новый товар, затем доказать результат запросами из браузера, командной строки и Postman.

На выходе получаются приложение `.../sklad-plus/api/app.py`, файл зависимостей, коллекция Postman с положительными и отрицательными запросами, отчёт о проверке и таблица фактических кодов состояния. Коллекция должна запускаться целиком, а не состоять из отдельных запросов, которые проверяли вручную.

## Краткие теоретические сведения

Flask принимает HTTP-запрос и передаёт его функции, привязанной к маршруту. Маршрут состоит из метода и пути: `GET /api/products` и `POST /api/products` это разные операции, даже если путь совпадает. Функция читает параметры запроса, формирует данные и возвращает ответ. Ответ состоит из тела, кода состояния и заголовков.

Запрос проходит путь от клиента до функции и обратно. Клиент открывает соединение, отправляет метод, путь, заголовки и тело. Сервер разбирает сообщение, ищет маршрут, вызывает функцию и собирает ответ. После ответа соединение может закрыться или остаться открытым для следующего запроса. Сервер не хранит состояние между запросами, поэтому каждый запрос должен сам содержать всё необходимое: параметры фильтра, тело нового товара, токен доступа.

Тело ответа в API обычно JSON. Flask превращает словарь или список в JSON помощником `jsonify`. Код состояния по умолчанию 200. Если ресурс создан, возвращают 201 и заголовок `Location` с адресом новой записи. Если запрос неверен, возвращают 400 или 422 с описанием ошибки. Если ресурс уже существует, возвращают 409.

JSON состоит из объектов и массивов. Объект это набор пар «ключ: значение» в фигурных скобках, массив это список в квадратных скобках. В ответе со списком удобно вернуть объект с полем `count` и массивом `items`: клиент сразу видит общее число и может перебрать элементы, не догадываясь о структуре.

| Ситуация | Код | Что в теле |
|---|---|---|
| Список получен | 200 | `count` и `items` |
| Товар создан | 201 | созданный объект и заголовок `Location` |
| Нет обязательного поля | 400 | `error` и список `fields` |
| Некорректный JSON | 400 | `error` |
| Такой `sku` уже есть | 409 | `error` и значение `sku` |
| Метод не разрешён | 405 | описание и заголовок `Allow` |
| Ошибка сервера | 500 | нейтральное сообщение и `request_id` |

Код состояния это не украшение ответа, а часть контракта. Клиент проверяет его до разбора тела и выбирает ветку поведения: показать данные, открыть форму, повторить запрос, сообщить об ошибке. Если сервер возвращает 200 на ошибку, клиент не отличит успех от отказа. Если сервер возвращает 500 на неверное поле, клиент решит, что виноват сервер, и повторит запрос.

Валидация на сервере обязательна, даже если форма в браузере уже проверяет поля. Клиента можно обойти: отправить запрос из Postman, изменить тело вручную или использовать чужое приложение. Сервер не должен доверять ни одному полю, пока не проверил его тип, диапазон и уникальность.

Postman это клиент для HTTP-запросов. Коллекция объединяет запросы в набор, переменные хранят общий адрес, а вкладка Tests содержит проверки, которые выполняются после ответа. Проверка `pm.response.to.have.status(200)` останавливает прогон, если сервер вернул другой код. Проверка `pm.expect(body.items).to.be.an("array")` подтверждает структуру тела. Коллекцию экспортируют в JSON и прикладывают к работе, чтобы проверяющий мог повторить прогон.

Переменные коллекции избавляют от повторения адреса. Вместо `http://127.0.0.1:5000` в каждом запросе стоит `{{base_url}}`, а значение задаётся один раз. При переносе на другой порт меняется одна переменная, и все запросы продолжают работать. Тесты выполняются после ответа и имеют доступ к коду, заголовкам и телу через объект `pm.response`.

Данные в этой работе хранятся в списке Python. После перезапуска сервера список возвращается к исходным восьми товарам. Для учебной проверки этого достаточно; сохранение в файл или базу рассматривается отдельно.

Проверка API делится на положительную и отрицательную. Положительная подтверждает, что корректный запрос возвращает ожидаемые данные. Отрицательная проверяет, что неверный запрос отклонён с понятным кодом и не изменил состояние. Обе части обязательны: сервис, который принимает всё подряд, опаснее сервиса, который иногда падает.

### Шаг 2. Запустите сервис с двумя маршрутами

Создайте `.../sklad-plus/api/app.py`. Ниже исходные данные и маршрут чтения. Восемь строк взяты из выгрузки склада, полный каталог содержит 4800 позиций и двенадцать категорий, но для проверки достаточно этой выборки.

| id | sku | title | category | price | stock |
|---|---|---|---|---|---|
| 1 | SKU-1001 | Перфоратор Bosch GSB 13 RE | Инструмент | 8990.00 | 12 |
| 2 | SKU-1002 | Шуруповёрт Makita DF333D | Инструмент | 12450.00 | 4 |
| 3 | SKU-2001 | Кабель ВВГнг 3x2.5 | Электрика | 78.50 | 340 |
| 4 | SKU-2002 | Розетка Legrand Valena | Электрика | 210.00 | 85 |
| 5 | SKU-3001 | Перчатки нитриловые | Спецодежда | 12.90 | 1200 |
| 6 | SKU-3002 | Каска защитная | Спецодежда | 640.00 | 28 |
| 7 | SKU-4001 | Крепёж анкерный M10 | Крепёж | 34.00 | 560 |
| 8 | SKU-4002 | Саморез 4.2x75 | Крепёж | 3.40 | 2400 |

Одна строка показана в виде словаря, остальные добавьте по таблице. Порядок полей и типы должны совпадать: цена числом, остаток целым.

```python
from flask import Flask, jsonify, request

app = Flask(__name__)
app.json.ensure_ascii = False

PRODUCTS = [
    {"id": 1, "sku": "SKU-1001", "title": "Перфоратор Bosch GSB 13 RE", "category": "Инструмент", "price": 8990.00, "stock": 12},
]


@app.get("/api/products")
def list_products():
    category = request.args.get("category")
    items = PRODUCTS
    if category:
        items = [p for p in PRODUCTS if p["category"] == category]
    return jsonify({"count": len(items), "items": items})


if __name__ == "__main__":
    app.run(port=5000)
```

Строка `app = Flask(__name__)` создаёт приложение. Декоратор `@app.get("/api/products")` связывает функцию с методом и путём. Внутри функции `request.args` содержит параметры адреса, а `jsonify` превращает словарь в JSON-ответ. `app.run(port=5000)` запускает встроенный сервер для разработки. В рабочем контуре его заменяют на waitress или gunicorn, но для проверки хватает встроенного.

Запустите приложение из каталога `.../sklad-plus/api`.

```powershell
python app.py
```

В терминале появится адрес локального сервера. Оставьте терминал открытым: пока процесс работает, сервис принимает запросы. Остановить его можно сочетанием клавиш Ctrl+C.

### Шаг 3. Проверьте GET из браузера и командной строки

Откройте в браузере `http://127.0.0.1:5000/api/products`. Браузер покажет JSON целиком. Проверьте, что в ответе есть `count`, равный числу строк, и массив `items` с восемью товарами.

Браузер удобен для быстрой проверки, но не показывает заголовки и не позволяет отправить POST. Командная строка и Postman дают полный контроль над методом, телом и заголовками, поэтому основную проверку выполняют ими.

Затем повторите запрос из командной строки с заголовками. Ключ `-i` показывает первую строку ответа и заголовки, по которым видно код состояния и формат тела.

```powershell
curl.exe -i http://127.0.0.1:5000/api/products
```

Отфильтруйте товары по категории. Ключ `--get` добавляет параметры к адресу, `--data-urlencode` кодирует кириллицу, чтобы сервер получил её в правильной кодировке.

```powershell
curl.exe -i --get --data-urlencode "category=Инструмент" http://127.0.0.1:5000/api/products
```

Сравните `count` в обоих ответах. Если фильтр вернул ноль товаров, проверьте точное написание категории в списке и в параметре. Регистр букв должен совпадать.

В ответе `curl -i` первая строка содержит версию протокола и код. Заголовок `Content-Type` показывает, что тело размечено как JSON. `Content-Length` сообщает размер тела в байтах. Если код 200, а `Content-Type` равен `text/html`, клиент получил страницу, а не данные, и разбор JSON завершится ошибкой.

### Шаг 4. Добавьте POST с проверкой полей

Маршрут POST принимает JSON и создаёт товар. Требования к обработке:

1. Тело должно быть JSON-объектом. Массив, строка или пустое тело отклоняются с кодом 400.
2. Обязательные поля: `sku`, `title`, `price`, `stock`. Если поля нет, вернуть 400, поле `error` и список `fields` с именами пропущенных полей.
3. `price` должно быть числом больше нуля, `stock` целым числом не меньше нуля. Иначе вернуть 400 с сообщением о конкретном поле.
4. Если товар с таким `sku` уже есть, вернуть 409 и значение `sku` в теле.
5. При успехе добавить товар с новым `id`, вернуть 201, созданный объект и заголовок `Location` с адресом `/api/products/<id>`.

Проверки выполняют в определённом порядке. Сначала убеждаются, что тело вообще является объектом. Затем проверяют наличие обязательных полей, потому что обращение к отсутствующему ключу даст `KeyError`. После этого проверяют типы и диапазоны. Уникальность проверяют перед вставкой, а ограничение базы остаётся последней защитой. Такой порядок даёт клиенту точное сообщение, а не общую ошибку 500.

Ниже каркас маршрута. Проверки и добавление записи допишите сами.

```python
@app.post("/api/products")
def add_product():
    data = request.get_json(silent=True)
    if not isinstance(data, dict):
        return jsonify({"error": "Ожидается JSON-объект"}), 400
    # проверьте обязательные поля, типы и уникальность sku
    # создайте товар и верните 201 с заголовком Location
```

Для проверки отправьте новый товар. Тело сохраните в файл `.../sklad-plus/api/new_product.json`, чтобы не набирать его в командной строке заново.

```json
{
  "sku": "SKU-5001",
  "title": "Уровень строительный 600 мм",
  "category": "Измерительный инструмент",
  "price": 1290.00,
  "stock": 15
}
```

```powershell
curl.exe -i -X POST http://127.0.0.1:5000/api/products -H "Content-Type: application/json" --data-binary "@new_product.json"
```

В ответе должны быть код 201, заголовок `Location` и созданный объект с `id` 9. Повторите тот же запрос: теперь сервер обязан вернуть 409, потому что `sku` уже существует.

Код 201 сообщает, что ресурс создан. Заголовок `Location` даёт адрес, по которому его можно прочитать. Клиент не должен собирать адрес из идентификатора самостоятельно: сервер может изменить схему путей, а заголовок останется правильным.

### Шаг 5. Проверьте ошибки и коды состояния

Заполните таблицу проверок. В последнем столбце запишите, что именно подтверждает ответ: наличие поля, заголовка или сообщения. Первая строка дана как образец.

Таблица проверок нужна для доказательства, что проверены не только удачные запросы. Заполняйте её по фактическим ответам, а не по ожиданиям: если код отличается, сначала разберитесь, какое требование нарушено, затем исправьте приложение и повторите запрос.

| Запрос | Ожидаемый код | Фактический код | Тело содержит | Вывод |
|---|---|---|---|---|
| GET `/api/products` | 200 |  | `count`, `items` | список получен |
| GET `/api/products?category=Инструмент` | 200 |  |  |  |
| POST с корректным телом | 201 |  |  |  |
| POST без поля `title` | 400 |  |  |  |
| POST с `price` равной нулю | 400 |  |  |  |
| POST с существующим `sku` | 409 |  |  |  |
| DELETE `/api/products/1` | 405 |  |  |  |
| POST с телом не в формате JSON | 400 |  |  |  |

Для проверки 405 отправьте метод, который не объявлен для маршрута. Для проверки некорректного JSON уберите кавычку или фигурную скобку в файле и повторите запрос. Сервер не должен падать с трассировкой: он возвращает JSON с ошибкой.

Отрицательные проверки выполняют по одной причине за раз. Если отправить тело без `title` и с отрицательной ценой одновременно, непонятно, какое правило сработало. Раздельные запросы показывают, что каждое ограничение действительно проверяется, а сообщение указывает на нужное поле.

### Шаг 6. Соберите коллекцию Postman

Создайте коллекцию `Склад+ API`. В переменных коллекции задайте `base_url` со значением `http://127.0.0.1:5000`. В запросах используйте `{{base_url}}/api/products`: при смене порта достаточно изменить одну переменную.

Добавьте пять запросов:

1. `GET список товаров` без параметров.
2. `GET фильтр по категории` с параметром `category` равным `Инструмент`.
3. `POST новый товар` с корректным JSON.
4. `POST без обязательного поля` с телом, где нет `title`.
5. `POST повторный sku` с уже существующим артикулом.

Для каждого запроса сохраните пример ответа. В Postman пример создаётся кнопкой Save Response и позволяет увидеть ожидаемое тело рядом с фактическим.

Коллекция хранит запросы в папках и позволяет запускать их по порядку. Порядок важен: запрос создания добавляет товар, а запрос повторного `sku` должен идти после него, иначе конфликт не возникнет. Переменная `base_url` избавляет от правки пяти адресов при смене порта.

### Шаг 7. Добавьте тесты и прогоните коллекцию

Тесты пишут на вкладке Tests языка JavaScript. Ниже образец для запроса списка: он проверяет код и структуру тела.

```javascript
pm.test("Статус 200", function () {
    pm.response.to.have.status(200);
});

pm.test("Ответ содержит список товаров", function () {
    const body = pm.response.json();
    pm.expect(body.count).to.be.a("number");
    pm.expect(body.items).to.be.an("array");
});
```

`pm.test` объявляет проверку и её имя. Функция внутри выполняется после ответа. `pm.response.to.have.status` сравнивает код, `pm.response.json()` разбирает тело, `pm.expect` проверяет значение. Если проверка падает, Postman показывает имя теста и фактическое значение, поэтому имя должно быть коротким и конкретным.

Добавьте проверки для остальных запросов:

- POST с корректным телом: код 201, заголовок `Location` присутствует, в теле есть `id`.
- POST без `title`: код 400, в теле есть `fields`, и в списке есть `title`.
- POST с повторным `sku`: код 409, в теле есть `error`.
- GET с фильтром: код 200, все элементы массива имеют категорию `Инструмент`.

Запустите коллекцию через Collection Runner. В отчёте прогона должны быть видны число запросов, число пройденных тестов и время выполнения. Если тест падает, сначала сравните фактический код и тело, затем исправьте приложение или ожидание в тесте. Подгонять ожидание под неверный ответ нельзя: тест должен проверять требование, а не текущее поведение.

Прогон коллекции повторяет один и тот же набор действий после каждой правки. Это быстрее ручного перебора запросов и надёжнее: забытый отрицательный запрос не выпадет из проверки. Перед сдачей прогон выполняют на чистом запуске сервера, чтобы данные начинались с исходных восьми товаров.

Экспортируйте коллекцию в файл `.../sklad-plus/api/postman/SkladPlus.postman_collection.json`. Формат экспорта выбирайте Collection v2.1, чтобы файл открывался в других версиях Postman. Каталог `.../sklad-plus/api/postman` создайте заранее, если его ещё нет.

### Шаг 8. Оформите отчёт

Соберите отчёт из цели, структуры проекта, кода маршрутов, таблицы проверок, скриншотов Postman и вывода. Отдельно опишите, что происходит с данными после перезапуска сервера и какое изменение потребуется для сохранения в файл.

Перед сдачей остановите сервер и запустите его заново. Коллекция должна пройти на чистых данных; если тест создания зависит от товара, добавленного вручную, прогон на другой машине упадёт.

## Требования к отчёту

Отчёт содержит титульную часть, цель, схему двух маршрутов с методами, путями и кодами ответа, код `app.py`, таблицу проверок на восемь строк, скриншоты Postman и вывод.

На скриншоте запроса должны быть видны метод, полный адрес, код состояния, заголовки и тело ответа. На скриншоте прогона коллекции должны быть видны название коллекции, число запросов и итог тестов. Кадр одного тела ответа без адреса и кода не доказывает, что запрос был отправлен на нужный маршрут.

Таблицу проверок оформляют в том же порядке, в котором запросы идут в коллекции. Так проверяющий видит соответствие между Postman и отчётом. Для каждого запроса указывают фактический код, а не ожидаемый: расхождение это результат, который нужно объяснить, а не скрыть.

В выводе ответьте на три вопроса: почему список из нуля товаров возвращает 200, а не 404; чем 400 отличается от 409; почему данные исчезают после перезапуска и что нужно изменить, чтобы они сохранялись.

Доказательством служит не код, а пара «запрос и ответ». В отчёте рядом с каждым запросом указывают метод, адрес, тело и полученный код. Если запрос повторяли после правки, приводят последний результат и коротко объясняют, что изменилось.

## Что сдать

- файл `.../sklad-plus/api/app.py` с маршрутами GET и POST и проверкой полей;
- файл `.../sklad-plus/api/requirements.txt` с зафиксированными версиями Flask и requests;
- коллекцию `.../sklad-plus/api/postman/SkladPlus.postman_collection.json` с пятью запросами и тестами;
- скриншот прогона коллекции с пройденными тестами;
- заполненную таблицу проверок на восемь строк;
- отчёт с описанием поведения данных после перезапуска.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: сервис запускается, GET возвращает восемь товаров и фильтрует по категории, POST проверяет обязательные поля, типы и уникальность, возвращает 201 с `Location`, 400 и 409 с понятным телом, коллекция из пяти запросов проходит все тесты, таблица заполнена, отчёт объясняет поведение данных.
- **4**: работа выполнена полностью, но один отрицательный запрос не покрыт тестом или в таблице одна строка заполнена без фактического кода.
- **3**: работают GET и POST без полной проверки полей, коды 400 и 409 возвращаются непоследовательно, коллекция содержит запросы без тестов, таблица заполнена частично.
- **2**: сервис не запускается или выполнена только часть маршрутов без проверки запросами.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
