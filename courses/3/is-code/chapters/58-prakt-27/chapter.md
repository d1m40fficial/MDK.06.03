## Цель работы

Научиться показывать индивидуальный проект так, чтобы работающее приложение и объяснение решений подтверждали друг друга. Защита проверяет не только результат, но и понимание: почему выбрана такая структура, где хранятся данные, как проверяются права и что произойдёт при ошибке.

Результат работы это готовый комплект документов, проверенный запуск, сценарий демонстрации на данных учебного кейса «Северный склад» и короткие ответы по архитектуре, базе и коду. Комплект должен открываться у проверяющего без вашей машины: репозиторий, README, описание API, презентация, скрипт базы и отчёт.

Отдельная задача практики состоит в том, чтобы отличить показ от пересказа. На защите ценят действия в системе и ссылки на файлы, а не общие слова о современных технологиях. Поэтому каждый шаг сценария заканчивается видимым результатом, а ответ по коду указывает файл и функцию.

## Оборудование и программное обеспечение

- Персональный компьютер с Windows 10.
- Python 3.11 или новее и VS Code с расширением Python.
- Postman для проверки маршрутов API.
- Браузер для работы с приложением.
- Git и терминал PowerShell.
- MS PowerPoint или LibreOffice Impress для презентации.
- MS Word или LibreOffice Writer для протокола и отчёта.
- Репозиторий индивидуального проекта и копия базы с учебными данными.

## Краткие теоретические сведения

Защита состоит из трёх частей: доклад, демонстрация и ответы на вопросы. Доклад задаёт рамку: какую задачу решает система, кто её пользователи и какие границы у работы. Демонстрация показывает, что система действительно работает. Вопросы проверяют, насколько решения осознаны и где проходят границы возможностей приложения.

| Что проверяет защита | Как это подтверждают |
|---|---|
| Понимание задачи и пользователей | доклад называет роли и их операции |
| Работоспособность системы | демонстрация проходит по сценарию на подготовленных данных |
| Понимание архитектуры | объяснение слоёв со ссылкой на файлы |
| Понимание базы данных | схема, ключи, ограничения и транзакции своими словами |
| Качество кода | выбранные фрагменты с объяснением решений |
| Полнота комплекта | репозиторий, README, описание API, презентация, отчёт |

Демонстрация отличается от свободного исследования системы: в ней заранее выбран маршрут, роли, операции и ожидаемые сообщения. Маршрут строят вокруг одной истории, например приёмка в Туле, перемещение в ячейку и отгрузка по накладной. Слушатель видит рабочий процесс склада, а не набор кнопок.

Данные для показа готовят заранее и делают повторяемыми: 120 пользователей, четыре площадки, 12 категорий, 4800 позиций. Если после отгрузки остаток изменился, второй прогон даст другой результат, поэтому базу возвращают в исходное состояние скриптом наполнения или копией файла.

Показ ограничения убеждает сильнее рассказа о нём. Нехватка товара, запрет доступа для кладовщика и отказ при неверном пароле показывают, что проверки включены. Для каждой проверки заранее известно ожидаемое сообщение; расхождение разбирают до защиты, а не объясняют на ходу.

Архитектуру объясняют через решения и альтернативы. Недостаточно сказать «приложение разделено на слои»: нужно назвать файлы интерфейса, расчётов и доступа к данным и объяснить, что изменилось бы при другом выборе. SQLite выбрана потому, что проект работает на одной машине, а при одновременной записи с четырёх площадок понадобилась бы сетевая СУБД.

| Вопрос по архитектуре | Где искать ответ |
|---|---|
| Где начинается выполнение программы | файл точки входа |
| Где лежат правила расчёта | модуль слоя сервиса |
| Где выполняется доступ к базе | модуль работы с данными |
| Где проверяются права | маршрут API или общий обработчик |
| Где проверяются поля | схема запроса или модель |
| Как устроены тесты | каталог проверок и отчёт прогона |

База данных объясняется по схеме, а не по памяти. Достаточно пяти-семи главных таблиц, первичных и внешних ключей, ограничений и места транзакции. При отгрузке остаток уменьшается, накладная создаётся, движение записывается, и всё это происходит целиком.

Ответ строят по схеме: факт, место в проекте, причина, альтернатива. Сначала решение, затем файл или таблица, потом причина выбора и, если уместно, другой вариант. Такой ответ показывает, что решение принято осознанно.

Если ответа нет, его не придумывают. Честное «эту часть я не проверял» лучше уверенного неверного объяснения. Полезно показать, как вы будете выяснять ответ: открыть журнал, посмотреть маршрут, выполнить запрос. Проверяющий оценивает способ рассуждения.

## Ход работы

### Шаг 1. Соберите комплект документов

Ниже список того, что просят принести на защиту. Часть пунктов уже есть в проекте, часть нужно проверить и обновить.

```text
репозиторий с историей коммитов
README с установкой и запуском
описание маршрутов API
презентация на 10-12 слайдов
скрипт создания базы и учебные данные
набор тестов и отчёт о прогоне
пояснительная записка или отчёт
```

Составьте таблицу комплекта: документ, где лежит, готовность, что осталось. Первая строка дана как образец.

| Документ | Где лежит | Готовность | Что осталось |
|---|---|---|---|
| README | корень репозитория | проверен на чистой копии | обновить дату |
|  |  |  |  |
|  |  |  |  |

Проверьте каждый файл на открываемость. Документ, который не открывается на другой машине, считается отсутствующим. Ссылки на репозиторий и на описание API должны работать без вашего входа в систему.

### Шаг 2. Проверьте запуск на чистой копии

Скопируйте проект в соседнюю папку, удалив `.git`, `.venv` и файл базы, созданный во время разработки. Выполните команды из README по порядку.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m sklad
```

Первая команда создаёт окружение, вторая активирует его, третья ставит пакеты с зафиксированными версиями, четвёртая запускает приложение. Если README требует другого порядка, значит, в инструкции ошибка: порядок команд задаёт сам проект, а не привычка автора.

Заполните таблицу проверки по результатам запуска.

| Проверка | Ожидаемый результат | Фактический результат | Исправление |
|---|---|---|---|
| Создание окружения | каталог `.venv` появился |  |  |
| Запуск приложения | сервис слушает порт |  |  |
| Вход кладовщиком | открывается меню приёмки |  |  |
| Прогон тестов | все проверки пройдены |  |  |
| Запрос к API | код 200 и JSON |  |  |

Отдельно проверьте запуск после перезагрузки компьютера: терминал может открыться в другом каталоге. Если приложение запускается только из одной папки, это должно быть написано в README.

### Шаг 3. Подготовьте данные для демонстрации

Данные должны показывать систему в рабочем состоянии и при этом быть небольшими. Полный склад на 4800 позиций нужен для проверки отчётов, но для показа достаточно одной площадки и нескольких артикулов. Остальные данные остаются в базе и подтверждают объём.

Опишите скрипт наполнения: какие таблицы он очищает, в каком порядке заполняет, какие числа задаёт. Порядок важен из-за внешних ключей: сначала площадки и категории, затем товары, затем остатки и документы.

| Роль | Что видит | Что запрещено | Проверка |
|---|---|---|---|
| Кладовщик | приёмка, перемещение, отгрузка | отчёт по остаткам всех площадок | 403 на закрытом маршруте |
|  |  |  |  |
|  |  |  |  |

Проверьте, что после наполнения числа совпадают с текстом доклада: 120 пользователей, четыре площадки, 12 категорий, 4800 позиций. Расхождение в одном числе на защите заметят, потому что оно повторяется на слайде и в отчёте.

Сохраните копию базы после наполнения. Она пригодится, если во время показа данные изменятся или приложение не запустится. Копию хранят отдельно от рабочей базы, чтобы случайное сохранение не испортило исходное состояние.

### Шаг 4. Прогоните сценарий демонстрации

Ниже операции системы в произвольном порядке. Выстройте из них маршрут на шесть-восемь шагов и заполните таблицу: действие, что видно на экране, что сказать, фактический результат.

```text
вход кладовщиком
приёмка 24 коробок на площадку Тула
перемещение 10 единиц в ячейку хранения
отгрузка по накладной
вход менеджером и просмотр отчёта по остаткам
вход администратором и блокировка пользователя
попытка кладовщика открыть отчёт по остаткам
```

Первая строка таблицы дана как образец.

| Шаг | Действие | Что видно | Что сказать | Результат |
|---|---|---|---|---|
| 1 | вход кладовщиком | меню приёмки и отгрузки | меню зависит от роли | совпало |
| 2 |  |  |  |  |
| 3 |  |  |  |  |

В сценарий включают хотя бы одну ошибку и одно ограничение. Например, отгрузка на количество больше остатка должна вернуть сообщение о нехватке, а кладовщик не должен открыть отчёт по всем площадкам. Ошибку показывают спокойно: она подтверждает, что проверки работают.

Проверьте сценарий дважды с возвратом базы в исходное состояние. Если прогоны различаются, шаги зависят от предыдущих изменений и на защите сценарий сорвётся.

### Шаг 5. Подготовьте объяснение архитектуры

Ниже вопросы, которые задают чаще всего. Для каждого найдите место в проекте и подготовьте короткий ответ.

```text
Из каких слоёв состоит приложение и где они лежат?
Почему выбрана SQLite, а не серверная СУБД?
Где проверяются права пользователя?
Где проверяются поля запроса?
Как хранятся пароли?
Как устроены тесты и что они проверяют?
Что изменится при переходе на десять площадок?
```

Заполните таблицу: вопрос, файл или модуль с ответом, что сказать. Первая строка дана как образец, но ответ в ней только намечен: допишите причину и альтернативу своими словами.

| Вопрос | Где ответ | Что сказать |
|---|---|---|
| Из каких слоёв состоит приложение | каталоги `src` и файл точки входа | назвать слои, показать файлы, объяснить, почему расчёт не лежит в маршруте |
|  |  |  |
|  |  |  |

Ответ по архитектуре опирается на файлы, а не на схему из презентации. Проверяющий может открыть модуль и попросить показать расчёт, поэтому расхождение с кодом исправляют до защиты.

Отдельно подготовьте ответ о границах: что система не делает. Честные границы показывают, что проект спланирован, а не собран из случайных функций.

### Шаг 6. Подготовьте объяснение базы данных

Покажите схему на слайде или на экране и объясните её по таблицам. Достаточно пяти-семи главных: площадки, категории, товары, остатки, документы, движения, пользователи. Для каждой назовите ключ и одну связь.

| Проверка схемы | Что показать | Признак проблемы |
|---|---|---|
| Первичные ключи | идентификатор в каждой таблице | ключ собран из названия товара |
| Внешние ключи | связь остатка с товаром и площадкой | связь хранится строкой без ограничения |
| Ограничения | обязательность и допустимые значения | количество может быть отрицательным |
| Индексы | поиск по артикулу и площадке | отчёт читает всю таблицу |
| Транзакция | отгрузка целиком | остаток изменён, накладная не создана |

Объясните, где применяется транзакция и что произойдёт при сбое посередине. Для отгрузки это три изменения: остаток, накладная, движение товара. Если одно из них не записалось, транзакция откатывается, и склад остаётся в прежнем состоянии.

Подготовьте ответ о нормализации: справочники вынесены отдельно, поэтому название категории не повторяется в каждой строке товара. Намеренное отступление от нормальной формы назовите и объясните причиной.

### Шаг 7. Выберите фрагменты кода для показа

Выберите пять фрагментов, которые показывают разные стороны проекта: функцию расчёта, маршрут API, запрос к базе, тест и проверку прав. Для каждого запишите файл, строки, что он делает и почему написано именно так.

| Фрагмент | Файл и строки | Что показывает | Почему так |
|---|---|---|---|
| Расчёт свободного остатка | модуль слоя сервиса | отделение правила от маршрута | функцию можно проверить тестом |
|  |  |  |  |
|  |  |  |  |

Не выбирайте самый длинный код. Показывают место, где видно решение: параметризованный запрос вместо склейки строки, проверка роли перед действием, возврат понятного кода ошибки. Такой фрагмент занимает несколько строк и вызывает вопрос по существу.

Проверьте, что номера строк в таблице совпадают с текущей версией файла. После правки кода номера сдвигаются, и ссылка на строку 42 перестаёт работать. Если код менялся, обновите таблицу перед защитой.

### Шаг 8. Проведите тренировочную защиту в паре

Разделитесь на пары. Один показывает проект по сценарию, второй задаёт вопросы по списку и заполняет протокол. Затем роли меняются. Протокол фиксирует не оценку, а наблюдения: что было непонятно, где ответ расходился с кодом, какой шаг сценария не сработал.

| Что наблюдал | Замечание | Исправление |
|---|---|---|
| показ без пояснения роли | слушатель не понял, почему меню разное | назвать роль перед входом |
|  |  |  |
|  |  |  |

Слушатель задаёт вопросы из своего списка, а не подсказывает. Хороший вопрос начинается со слова «почему», а ответ «так было в примере» не считается: решение должно иметь причину.

После прогона исправьте сценарий и ответы, а не только текст доклада: при сбое шага меняют данные, при трудном вопросе находят место в коде и разбираются до следующего прогона.

### Шаг 9. Проведите защиту по регламенту

Порядок защиты задаёт преподаватель: доклад, демонстрация, вопросы. Регламент задаёт время каждой части, поэтому проверьте, что доклад и показ укладываются. Лишнее убирают, а не произносят быстрее.

Во время показа говорите о том, что происходит на экране, и не читайте слайды. Если что-то пошло не так, назовите причину, покажите запасной вариант и продолжите.

На вопросы отвечайте коротко и по схеме: факт, место в проекте, причина, альтернатива. Если вопрос выходит за границы работы, скажите об этом прямо и объясните, как задача решалась бы в полной версии. Проверяющий отличает границу проекта от пробела в знаниях.

Завершите защиту сдачей комплекта: репозиторий, README, описание API, презентация, скрипт базы, тесты и отчёт. Убедитесь, что в репозитории есть коммит с итоговой версией документов, а на титульном слайде указана та же дата, что в README.

## Требования к отчёту

Отчёт оформляют в Word, объём три-пять страниц. В отчёте должны быть:

- тема проекта, цель работы и перечень пользователей с ролями;
- таблица комплекта документов с готовностью и оставшимися работами;
- таблица проверки запуска на чистой копии;
- описание данных демонстрации и скрипта наполнения;
- сценарий показа с ожидаемым и фактическим результатом каждого шага;
- таблица вопросов по архитектуре и базе с указанием файлов и таблиц;
- перечень пяти фрагментов кода с номерами строк и объяснением решения;
- протокол тренировочной защиты с замечаниями и исправлениями;
- снимок экрана с работающим приложением на шаге сценария, на нём видны роль пользователя и результат операции;
- снимок экрана с окном Postman, на нём видны код состояния и тело ответа;
- короткий вывод о том, что оказалось слабым местом и что исправлено.

## Что сдать

- комплект документов проекта: репозиторий, README, описание API, презентацию, скрипт базы;
- сценарий демонстрации с данными, ожидаемым результатом и запасным путём;
- таблица вопросов по архитектуре и базе с указанием файлов и таблиц;
- перечень пяти фрагментов кода с номерами строк и объяснением;
- заполненный протокол тренировочной защиты;
- отчёт DOCX со снимками экрана и выводом.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: приложение запускается на чистой копии, демонстрация проходит по сценарию и включает проверку ограничения, архитектура и схема базы объяснены со ссылкой на файлы и таблицы, ответы на вопросы опираются на код, комплект документов полон и согласован.
- **4**: работа выполнена полностью, но один шаг сценария не имеет ожидаемого результата, либо объяснение архитектуры дано без ссылки на файлы, либо в комплекте не хватает одного документа.
- **3**: приложение работает, но показ идёт без сценария, объяснения общие, ответы на вопросы по коду затруднены, комплект документов неполон или содержит устаревшие данные.
- **2**: работа не выполнена или приложение не запускается.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
