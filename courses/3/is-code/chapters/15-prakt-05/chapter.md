## Цель работы

Сделать программу приёмки товара устойчивой к неверному вводу. Программа должна принимать целое количество от 1 до 10000, объяснять причину отказа, давать три попытки и завершаться с понятным кодом, если корректное значение так и не введено.

Результат работы это модуль `priemka.py` с проверкой ввода, собственный класс ошибки ввода, таблица проверок на восьми значениях и отчёт с разбором отказов. Падение с трассировкой на пустой строке или букве считается незавершённой работой.

## Краткие теоретические сведения

Ошибка ввода возникает, когда пользователь ввёл значение, которое программа не может принять: пустую строку, букву, дробное число, отрицательное количество. Это ожидаемая ситуация, а не дефект кода: пользователь ошибается, и программа обязана это пережить.

Ошибка логики возникает, когда неверно написан сам код: перепутаны условия, не то поле, потерян шаг. Её нельзя исправить повторным вводом. Если программа просит ввести число заново после деления на ноль, она лечит симптом и скрывает дефект.

Системная ошибка приходит извне: нет файла, закрыт доступ, оборвалась сеть. Её обрабатывают отдельно и сообщают, что именно недоступно.

Перехват должен быть узким. `int(text)` даёт `ValueError`, и ловить нужно именно его. Широкий `except Exception` вместе с ошибкой ввода поймает и опечатку в коде, и тогда дефект будет выглядеть как неверные данные. Собственное исключение `InputError` отделяет отказ проверки от системных сбоев и несёт имя поля, введённое значение и причину.

У конструкции `try` есть ещё блоки `else` и `finally`. `else` выполняется, когда исключения не было, и отделяет успешное продолжение от обработки. `finally` выполняется всегда и служит для освобождения ресурсов. В этой работе достаточно `try` и `except`, но знать о двух других блоках нужно, чтобы не путать их назначение.

Функция `int` принимает строку с пробелами по краям и знак минус, но не принимает запятую, точку и буквы. Пустая строка даёт `ValueError`, а не ноль. Эти детали важны: проверка диапазона не заменяет проверку типа, потому что `int` принимает не только цифры, но и пробелы по краям, и знак плюс.

Граница приложения в этой работе это функция `main`. Она перехватывает `InputError`, печатает сообщение и возвращает код. Внутри `parse_quantity` ошибка только поднимается, а не обрабатывается: у функции разбора нет полномочий решать, продолжать приёмку или нет. Такое разделение позволяет позже вызвать ту же проверку из другого места без копирования текста.

Проверка ввода не отменяет проверку в модели. Интерфейс отвечает за то, что человек ввёл целое число, а модель товара за то, что остаток не станет отрицательным. Дублирование правил допустимо, если каждое стоит на своём уровне и сообщает о своей причине.

### Шаг 2. Перехватите конкретное исключение

Разберите пример: функция разбора количества ловит `ValueError` от `int` и поднимает собственное исключение с понятным текстом. Новый приём `raise ... from err` здесь видно целиком: причина сохраняется, а верхний уровень получает сообщение на языке склада.

```python
class SkladError(Exception):
    pass


class InputError(SkladError):
    def __init__(self, field, value, reason):
        self.field = field
        self.value = value
        self.reason = reason
        super().__init__(f"Поле {field}: {reason}, получено {value!r}")


def parse_quantity(text):
    try:
        qty = int(text)
    except ValueError as err:
        raise InputError("quantity", text, "нужно целое число") from err
    return qty
```

Проверьте на двух значениях: `12` возвращает число, `12,5` поднимает `InputError` с причиной `ValueError`. Затем добавьте в функцию проверку диапазона: количество должно быть больше нуля и не больше 10000. Каждое нарушение это отдельный `InputError` со своей причиной.

Класс `InputError` наследуется от общего `SkladError`, поэтому граница приложения может поймать все ошибки склада одним обработчиком, а конкретный отказ проверки отличить по типу. Поля `field`, `value` и `reason` нужны не для печати: по ним интерфейс решает, какое поле подсветить и что предложить. Текст сообщения собирается в конструкторе один раз, чтобы все отказы одного вида выглядели одинаково.

Не возвращайте `None` вместо ошибки. Если функция вернёт `None`, каждый вызывающий обязан помнить о проверке, а забытая проверка проявится позже как `TypeError` при умножении. Исключение идёт вверх само.

| Ввод | Сообщение |
|---|---|
| пустая строка |  |
| `abc` |  |
| `0` |  |
| `10001` |  |

Формулировка «ошибка» или «неверное значение» не годится: по ней нельзя ни исправить ввод, ни найти место в коде. Формулировка «Поле quantity: нужно целое число, получено 'abc'» говорит и что делать, и откуда пришло значение.

Держите сообщения короткими и разными для разных причин. Если все отказы печатают один текст, пользователь не понимает, какое правило он нарушил, а разработчик не отличает пустую строку от слишком большого числа. Причину храните в поле `reason`, а не собирайте из типа исключения.

Отдельно решите, что считать ошибкой ввода, а что ошибкой логики. Если программа получает отрицательное количество из файла, который создала сама, это уже не пользовательский ввод, а дефект предыдущего шага. В отчёте приведите по одному примеру каждой категории.

### Шаг 4. Добавьте повторный запрос

Функция `ask_quantity` даёт три попытки. На каждой она читает строку, вызывает `parse_quantity` и перехватывает только `InputError`. После третьей неудачи возвращает `None`, а вызывающий код завершает работу с кодом 2.

```python
def ask_quantity(attempts=3):
    for attempt in range(1, attempts + 1):
        text = input("Количество, шт: ")
        try:
            return parse_quantity(text)
        except InputError as err:
            print(f"Попытка {attempt}: {err}")
    return None
```

Соберите программу целиком: `main` вызывает `ask_quantity`, проверяет результат и возвращает 0 или 2. Запуск через `sys.exit(main())` передаёт код операционной системе. Код 0 означает успешную приёмку, код 2 означает отказ после трёх попыток. Проверьте три сценария: корректный ввод с первой попытки, корректный ввод с третьей попытки, три неверных ввода подряд.

Для третьего сценария вывод должен заканчиваться словами «Приёмка отменена», а код завершения быть равен 2. Проверить код в терминале можно командой `echo $LASTEXITCODE` в PowerShell или `echo $?` в bash после запуска.

Параметр `attempts` задаёт число попыток и позволяет проверить цикл без долгого ввода. Бесконечный цикл `while True` для приёмки неудобен: если кладовщик отошёл, программа останется ждать и заблокирует рабочее место. Ограничение попыток и понятный отказ лучше, чем тихое ожидание.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: перехватывается конкретный тип, собственное исключение несёт поле и значение, диапазон проверен, три попытки работают, коды завершения 0 и 2 различаются, обе таблицы заполнены фактическими данными, категории ошибок объяснены.
- **4**: программа устойчива, но одно сообщение не указывает значение или в таблице проверок не хватает двух строк, а объяснение категорий дано без примеров.
- **3**: перехват есть, однако используется широкий тип, повторный запрос не ограничен или код завершения всегда равен нулю, таблицы заполнены частично.
- **2**: работа не выполнена или программа падает на пустой строке.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
