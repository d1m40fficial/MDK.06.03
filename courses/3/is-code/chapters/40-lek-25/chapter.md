## Ветка, которая потеряла скидку

В четверг два разработчика получили задачи по одному файлу `pricing.py`. Первый поднял скидку с 5 до 10 процентов, второй изменил ту же строку до 7. Оба отправили изменения в общий репозиторий. Первый слил свою ветку без замечаний, второй получил конфликт и решил его быстро: оставил свою строку, удалил чужую и нажал «завершить слияние».

Через день отдел продаж обнаружил, что скидка снова 7 процентов. Задача первого разработчика была закрыта, тесты проходили, история выглядела нормально. Пропала не строка кода, а результат работы человека. Восстановили его только по переписке и старой ветке.

**Ветка это отдельная линия работы, которая позволяет менять код, не затрагивая общую версию.** Слияние возвращает изменения в общую линию. Конфликт это место, где Git не может решить за людей, какую правку оставить. Если разрешать конфликт удалением чужой строки, Git не ошибётся: он сделает ровно то, что попросили, и потеряет работу.

Ветки нужны не для красоты истории. Они дают возможность проверить изменение до того, как оно попадёт к остальным, и вернуться к рабочей версии, если проверка не прошла. В проекте `sklad-plus` над кодом работают несколько человек, и без веток каждая незаконченная правка сразу оказывалась бы в общей версии.

Потерянная работа обходится дороже конфликта. Конфликт занимает минуты и заканчивается понятным решением. Потерянный коммит обнаруживают через день, когда по нему уже отчитались перед заказчиком. Восстанавливать приходится по журналам, переписке и резервным копиям, а иногда и переписывать заново. Поэтому правила работы с ветками защищают не удобство разработчика, а результат команды.

## Коммит, ветка и указатель

Чтобы уверенно работать с ветками, нужно представить три вещи: коммит, ветку и указатель `HEAD`. Коммит это снимок состояния проекта с автором, датой и сообщением. Он ссылается на предыдущий коммит, поэтому история образует цепочку. Ветка это подвижный указатель на один из коммитов. `HEAD` показывает, на какой ветке или коммите вы находитесь сейчас.

| Понятие | Что это | Что происходит при коммите |
|---|---|---|
| Коммит | снимок файлов и ссылка на родителя | создаётся новый снимок |
| Ветка | указатель на коммит | указатель сдвигается на новый коммит |
| `HEAD` | текущая позиция | остаётся на той же ветке |
| Индекс | подготовленные к коммиту изменения | очищается после коммита |
| Рабочий каталог | файлы на диске | не меняется сам по себе |

Когда вы делаете коммит в ветке `main`, указатель `main` сдвигается на новый коммит. Когда переключаетесь на другую ветку, Git меняет файлы в рабочем каталоге так, чтобы они соответствовали её последнему коммиту. Незакоммиченные изменения при переключении могут переноситься или мешать, поэтому перед сменой ветки рабочее состояние проверяют командой `git status`.

```text
git status
git log --oneline --graph --all
```

`git status` показывает, на какой ветке вы находитесь, какие файлы изменены и что подготовлено к коммиту. `git log` показывает историю. Флаг `--graph` рисует ветвление, `--oneline` сокращает запись, `--all` добавляет все ветки, а не только текущую.

История в Git не является одной прямой линией. Каждый коммит знает своего родителя, а ветки это ярлыки на разные концы цепочки. Слияние создаёт коммит с двумя родителями, поэтому граф разветвляется и сходится. Понимание графа избавляет от страха перед конфликтами: конфликт это не поломка, а развилка, которую нужно свести вручную.

`HEAD` может указывать не только на ветку, но и на отдельный коммит. Такое состояние называют отсоединённым указателем. В нём можно смотреть старую версию, но новые коммиты не будут принадлежать ветке, и после переключения их легко потерять. Если Git сообщает, что вы не на ветке, вернитесь на нужную командой `git switch main` или создайте ветку из текущего коммита командой `git switch -c имя`.

## Ветка под задачу

Ветку создают под одну задачу: новую функцию, исправление дефекта, обновление документации. Имя ветки должно отвечать на вопрос «что здесь делают». В учебном проекте удобны префиксы `feature/`, `fix/` и `docs/`.

```text
git switch main
git pull
git switch -c feature/discount
```

Первая команда переключает на главную ветку, вторая забирает свежие изменения из общего репозитория, третья создаёт новую ветку и сразу переключается на неё. Флаг `-c` означает create. Старая форма той же команды выглядит как `git checkout -b feature/discount`; в новых версиях Git предпочитают `switch` для веток и `restore` для файлов, потому что `checkout` делал слишком много разных вещей.

| Команда | Что делает |
|---|---|
| `git branch` | показывает локальные ветки |
| `git branch -a` | показывает локальные и удалённые ветки |
| `git switch имя` | переключает на существующую ветку |
| `git switch -c имя` | создаёт ветку и переключается на неё |
| `git branch -d имя` | удаляет слитую ветку |
| `git branch -m новое` | переименовывает текущую ветку |

После создания ветки делают серию коммитов. Один коммит должен содержать одно законченное изменение, а сообщение должно объяснять причину, а не пересказывать файлы. «Поднять скидку до 10 процентов» лучше, чем «изменён pricing.py»: через месяц по сообщению будет понятно, зачем менялась строка.

Дробление на маленькие коммиты помогает не только читать историю. Если изменение сломало тесты, можно отменить один коммит, а не всю ветку. Если задачу придётся отложить, готовые куски уже сохранены и не потеряются при переключении. Один большой коммит «сделал всё» невозможно ни проверить, ни аккуратно откатить.

```text
git add pricing.py
git commit -m "Поднять скидку до 10 процентов"
```

`git add` помещает изменение в индекс, то есть в набор того, что войдёт в следующий коммит. `git commit` создаёт снимок. Если нужно добавить все изменённые файлы, используют `git add .`, но в общем проекте лучше перечислять файлы явно: так в коммит не попадут случайные настройки и временные файлы.

Ветка должна решать одну задачу. Если в ней смешаны новая функция, исправление старого дефекта и переименование файлов, рецензенту трудно понять, что проверять, а при откате придётся выбирать нужные коммиты вручную. Несколько маленьких веток сливаются проще, чем одна большая. Пока задача не закончена, ветку периодически обновляют от главной, чтобы конфликты решались по частям, а не все сразу в конце.

## Слияние: fast-forward и merge commit

Слияние вливает изменения одной ветки в другую. Результат зависит от того, разошлась ли история. Если целевая ветка не получала новых коммитов с момента создания рабочей ветки, Git может просто передвинуть указатель вперёд. Это называют fast-forward, то есть перемоткой.

```text
git switch main
git merge feature/report
```

```text
Updating cbc67fe..4ac50e2
Fast-forward
 report.py | 4 ++++
 1 file changed, 4 insertions(+)
 create mode 100644 report.py
```

Нового коммита не появилось: указатель `main` перешёл на последний коммит ветки `feature/report`. История осталась линейной, а факт слияния в ней не виден. Для небольшой задачи это удобно, для крупной изменение лучше сохранить отдельным коммитом слияния.

Если обе ветки получили свои коммиты, fast-forward невозможен. Git создаёт коммит слияния с двумя родителями и объединяет изменения. Такой коммит показывает, где именно работа отделилась и вернулась в общую линию.

```text
git log --graph --oneline --all
```

```text
*   5773655 Свести скидку к согласованному значению
|\
| * 0fa9a5f Поднять скидку до 10 процентов
* | 6eeb16b Установить скидку 7 процентов
|/
* 2867907 Добавить расчёт стоимости со скидкой
```

Читать граф нужно сверху вниз: верхний коммит самый новый, ниже его родители. Символы `|\` и `|/` показывают, где ветка отделилась и где соединилась. Коммит `5773655` имеет двух родителей: `0fa9a5f` из рабочей ветки и `6eeb16b` из `main`. Именно в нём разрешён конфликт. Хэши в вашем репозитории будут другими: они зависят от содержимого, автора и времени коммита.

Иногда команда хочет сохранить коммит слияния даже при возможности fast-forward. Тогда используют `git merge --no-ff имя`. Это делает историю чуть длиннее, но оставляет видимую границу задачи. Обратный выбор, `--ff-only`, запрещает создавать коммит слияния и завершается ошибкой, если перемотка невозможна. Это полезная защита от неожиданной развилки.

Слияние не проверяет код и не запускает тесты. Оно только соединяет истории. Если в ветке был дефект, после слияния он окажется в главной ветке. Поэтому перед слиянием прогоняют тесты на рабочей ветке, а после слияния повторяют их на главной: объединение двух правильных изменений иногда даёт неправильный результат.

| Ситуация | Что сделает `git merge` |
|---|---|
| целевая ветка не менялась | fast-forward, новый коммит не нужен |
| обе ветки менялись, файлы не пересекаются | коммит слияния без конфликта |
| обе ветки менялись, одна строка | конфликт, нужна ручная правка |
| целевая ветка уже содержит рабочую | сообщение «Already up to date» |

Перед слиянием полезно посмотреть, что именно придёт из ветки:

```text
git log main..feature/discount --oneline
git diff main...feature/discount --stat
```

Первая команда показывает коммиты, которых нет в `main`. Вторая показывает файлы и число изменённых строк относительно общего предка. Это дешевле, чем сливать вслепую и разбираться потом.

## Конфликт и его разрешение

Конфликт возникает, когда обе ветки изменили одну и ту же строку или удалили файл, который другая ветка правила. Git не знает, какое изменение правильное, и останавливает слияние. В рабочем каталоге появляются маркеры.

```text
git merge feature/discount
```

```text
Auto-merging pricing.py
CONFLICT (content): Merge conflict in pricing.py
Automatic merge failed; fix conflicts and then commit the result.
```

```text
git status --short
```

```text
UU pricing.py
```

Две буквы `U` означают, что файл изменён обеими сторонами и конфликт ещё не разрешён. Другие сочетания, например `AA` или `DU`, говорят о добавлении или удалении с двух сторон. В любом случае `git status` подсказывает, что делать дальше.

Внутри файла Git оставляет обе версии:

```text
<<<<<<< HEAD
DISCOUNT = 7
=======
DISCOUNT = 10
>>>>>>> feature/discount
```

Верхняя часть относится к текущей ветке, в которую сливают, нижняя к вливаемой. Разрешение конфликта это не выбор одной из строк наугад, а решение, какое поведение должно остаться. В примере отдел продаж согласовал 10 процентов, поэтому правильная строка одна, а не обе.

```text
DISCOUNT = 10  # согласовано с отделом продаж
```

После правки файл сохраняют, добавляют в индекс и завершают слияние:

```text
git add pricing.py
git commit -m "Свести скидку к согласованному значению"
```

`git add` сообщает Git, что конфликт в этом файле разрешён. `git commit` создаёт коммит слияния. Если в процессе поняли, что слияние начали зря, его отменяют командой `git merge --abort`: рабочее состояние вернётся к тому, что было до слияния.

| Шаг | Команда | Что проверяют |
|---|---|---|
| 1 | `git status` | какие файлы конфликтуют |
| 2 | открыть файл | обе версии и маркеры |
| 3 | исправить | итоговое поведение, а не механический выбор |
| 4 | `git add файл` | конфликт отмечен разрешённым |
| 5 | `git commit` | сообщение объясняет решение |
| 6 | прогнать тесты | слияние не сломало поведение |

Конфликт может быть не только в одной строке. Если один разработчик переименовал файл, а другой изменил его содержимое, Git может предложить новое имя и спросить, что делать. Если один удалил функцию, а другой её вызывал, конфликт проявится как ошибка сборки уже после слияния. Поэтому после разрешения конфликта запускают тесты, а не только смотрят на исчезнувшие маркеры.

В спорной ситуации помогает разговор с автором второй ветки. Git показывает, кто и когда изменил строку, но не объясняет причину. Сообщение коммита и обсуждение задачи дают контекст: одно изменение могло быть временным обходом, а другое окончательным решением. Если договориться не удаётся, решение фиксируют в сообщении коммита слияния, чтобы через месяц было понятно, почему оставили именно эту версию.

> [!PITFALL] «Моя версия правильная»
> Кнопка «оставить моё» или «оставить чужое» разрешает конфликт механически. Если вторая сторона добавила проверку или исправление, оно исчезнет. Перед выбором нужно прочитать обе версии и понять, зачем каждая появилась.

## Перебазирование

Перебазирование берёт коммиты рабочей ветки и заново применяет их поверх другой ветки. История становится линейной, как будто работу начали позже. Хэши коммитов меняются, потому что у них появляется другой родитель.

```text
git switch feature/report
git rebase main
```

```text
Successfully rebased and updated refs/heads/feature/report.
```

После перебазирования граф выглядит так:

```text
* 4ac50e2 Добавить строку отчёта по остаткам
* cbc67fe Описать запуск проекта
*   5773655 Свести скидку к согласованному значению
|\
| * 0fa9a5f Поднять скидку до 10 процентов
* | 6eeb16b Установить скидку 7 процентов
|/
* 2867907 Добавить расчёт стоимости со скидкой
```

Коммит `4ac50e2` стоит прямо над `cbc67fe`, без боковой ветки. Читать такую историю проще: изменения идут друг за другом. Но у перебазирования есть цена: если ветку уже отправили в общий репозиторий и коллеги на неё опираются, их история разойдётся с новой. Поэтому перебазируют только личные ветки, которые ещё не стали общими.

| Признак | Слияние | Перебазирование |
|---|---|---|
| История | сохраняет ветвление и коммит слияния | делает линию линейной |
| Хэши коммитов | не меняются | меняются |
| Конфликты | решаются один раз при слиянии | могут повторяться на каждом коммите |
| Общая ветка | безопасно | опасно, если ветку уже используют |
| Читаемость | видно, где была задача | выглядит как последовательная работа |

Конфликты при перебазировании решают так же, как при слиянии: правят файл, добавляют его в индекс и продолжают командой `git rebase --continue`. Если стало сложно, перебазирование отменяют командой `git rebase --abort`. Прерывать и продолжать можно несколько раз, пока все коммиты не перенесутся.

```text
git add pricing.py
git rebase --continue
```

Есть правило, которое стоит запомнить: **перебазируют то, что ещё не отправили другим, сливают то, что уже общее.** Если ветка существует только на вашей машине, перебазирование безопасно. Если её уже скачали коллеги, перебазирование перепишет историю и создаст им лишнюю работу.

В повседневной работе перебазирование часто применяют при получении чужих изменений: `git pull --rebase` переносит ваши локальные коммиты поверх свежей главной ветки. Это избавляет от лишнего коммита слияния в личной работе. Но если в локальной ветке уже есть общие коммиты, лучше использовать обычный `git pull` с слиянием, чтобы не менять историю, которую видят другие.

## Схема ветвления учебного проекта

Для `sklad-plus` достаточно трёх уровней: главная ветка, рабочие ветки задач и короткие ветки исправлений. Главная ветка всегда должна собираться и проходить тесты. Рабочая ветка живёт до слияния задачи. Ветка исправления создаётся от главной и возвращается в неё после проверки.

Главную ветку защищают настройками репозитория: запрещают прямую отправку и требуют пройти проверку. Тогда даже опытный разработчик не сможет случайно отправить незаконченную правку. Защита не заменяет дисциплину, но делает ошибку заметной до того, как она попадёт к остальным.

| Ветка | Назначение | Время жизни | Кто сливает |
|---|---|---|---|
| `main` | рабочая версия проекта | постоянно | ответственный за слияние |
| `feature/...` | новая функция | до завершения задачи | автор после проверки |
| `fix/...` | исправление дефекта | до проверки | автор после проверки |
| `docs/...` | документация | до слияния | автор |

Рабочий цикл выглядит так. Сначала забирают свежую главную ветку, затем создают рабочую, делают коммиты, отправляют ветку в общий репозиторий, открывают запрос на слияние, проходят проверку и только потом сливают. После слияния рабочую ветку удаляют, чтобы не плодить устаревшие указатели.

```text
git switch main
git pull
git switch -c feature/stock-report
git push -u origin feature/stock-report
```

Флаг `-u` связывает локальную ветку с удалённой, чтобы следующие `git push` и `git pull` работали без указания имени. После этого в интерфейсе репозитория можно открыть запрос на слияние и попросить рецензию.

Удалённый репозиторий хранит общую копию истории. Локальная ветка и её удалённая копия это два указателя, которые синхронизируют командами `git push` и `git pull`. `push` отправляет ваши коммиты на сервер, `pull` забирает чужие и сливает их с вашими. Если сервер отклонил отправку, значит, на нём появились новые коммиты: сначала забирают их, затем повторяют отправку.

| Команда | Направление | Что делает |
|---|---|---|
| `git push` | от вас на сервер | отправляет коммиты ветки |
| `git pull` | с сервера к вам | забирает и сливает изменения |
| `git fetch` | с сервера к вам | забирает, но не сливает |
| `git push -u origin ветка` | от вас на сервер | связывает ветки при первой отправке |

`git fetch` полезен, когда нужно посмотреть чужие изменения до слияния. Он обновляет удалённые ветки, но не трогает рабочий каталог. После него можно сравнить свою ветку с серверной и решить, сливать сразу или сначала разобраться.

Перед отправкой полезно проверить, что в коммит не попали лишние файлы. `git status` показывает неотслеживаемые файлы, `git diff --cached` показывает то, что уже подготовлено. Если в списке оказались база, журнал или файл с паролем, их убирают из индекса и добавляют шаблон в `.gitignore`.

Запрос на слияние это не формальность. В нём видно, какие файлы изменились, кто автор и какие проверки прошли. Рецензент читает diff и оставляет замечания до слияния, а не после. Если в проекте нет отдельного рецензента, роль проверяющего берёт второй разработчик или преподаватель, но проверка всё равно должна быть.

| Проверка перед отправкой | Команда |
|---|---|
| текущая ветка и изменения | `git status` |
| что войдёт в коммит | `git diff --cached` |
| история ветки | `git log --oneline main..HEAD` |
| тесты | `python -m pytest` |
| отсутствие секретов | просмотр `git diff --cached` |

::/gate

::gate Какие правила защищают общую ветку от потери работы?

## Типичные ошибки

**Коммиты прямо в главную ветку.** Несколько человек пишут в `main`, и незаконченная правка ломает сборку у всех. Симптом: тесты падают, хотя никто не завершал задачу. Лечение: работать в отдельной ветке и сливать только проверенное.

**Слияние без проверки.** Ветку сливают, не запустив тесты и не прочитав diff. Конфликт разрешён, маркеры удалены, но поведение сломано. Симптом: после слияния отчёт пустой. Лечение: прогон тестов до и после слияния.

**Разрешение конфликта удалением чужой строки.** Самая дорогая ошибка в примере с начала лекции. Симптом: задача закрыта, а изменение исчезло. Лечение: читать обе версии и фиксировать решение в сообщении коммита.

**Долгоживущая ветка.** Ветка живёт месяц и расходится с главной на сотни строк. Конфликты накапливаются, слияние превращается в отдельный проект. Симптом: «сначала надо ещё раз переписать всё». Лечение: небольшие задачи и регулярное обновление от главной ветки.

**Перебазирование общей ветки.** Автор перебазирует ветку, которую уже скачали коллеги, и меняет все хэши. Симптом: у коллег расходятся истории и появляются дубли коммитов. Лечение: перебазировать только личные ветки, общие сливать.

**Принудительная отправка без предупреждения.** `git push --force` затирает удалённую ветку. Если кто-то успел отправить свои коммиты, они пропадут. Симптом: «вчера мой коммит был, сегодня его нет». Лечение: не использовать силу на общих ветках, а если она действительно нужна, применять `--force-with-lease` и предупреждать команду.

**Забытый `.gitignore`.** В репозиторий попадают база, журнал, виртуальное окружение и файл с паролем. Симптом: репозиторий растёт, а секрет виден в истории. Лечение: настроить игнор до первого коммита, а секрет при попадании заменить и удалить из истории.

**Переключение с незакоммиченными изменениями.** Файлы переносятся в другую ветку или мешают переключению. Симптом: правка оказалась не там, где планировалась. Лечение: перед сменой ветки проверять `git status` и либо коммитить, либо временно откладывать изменения через `git stash`.

**Слияние ветки в саму себя.** Автор путает ветки и выполняет `git merge` на той же ветке, где стоит. Симптом: сообщение «Already up to date», а изменения не появились в главной. Лечение: перед слиянием проверить `git branch --show-current` и явно указать целевую ветку.

> [!KEY] Ветка это не копия проекта
> Ветка это указатель на коммит. Переключение меняет файлы в рабочем каталоге, но не создаёт второй проект. Поэтому ветки дешёвые, а коммиты общие для всего репозитория.

## Итоги

- Коммит это снимок проекта, ветка это указатель на коммит, `HEAD` показывает текущую позицию.
- Ветку создают под одну задачу и дают ей имя, по которому понятно назначение.
- Fast-forward просто передвигает указатель, слияние разошедшихся веток создаёт коммит с двумя родителями.
- Конфликт разрешают вручную: прочитать обе версии, выбрать поведение, добавить файл и завершить слияние.
- Перебазирование делает историю линейной, меняет хэши и подходит только для личных веток.
- Главная ветка всегда собирается и проходит тесты, а рабочая ветка живёт до слияния задачи.

::quiz
Q: Что такое ветка в Git?
+ Указатель на коммит, который двигается при новых коммитах
- Полная копия проекта на диске
- Файл с настройками репозитория
- Список изменённых строк
! Ветка это ярлык на коммит, а не отдельная копия файлов.

Q: Что делает команда `git switch -c feature/discount`?
+ Создаёт ветку `feature/discount` и переключается на неё
- Удаляет ветку `feature/discount`
- Сливает ветку в `main`
- Отправляет ветку в удалённый репозиторий
! Флаг `-c` означает создание новой ветки.

Q: Что такое fast-forward при слиянии?
+ Перемещение указателя целевой ветки без создания коммита слияния
- Принудительная отправка ветки в удалённый репозиторий
- Удаление всех коммитов рабочей ветки
- Разрешение конфликта выбором первой версии
! Перемотка возможна, когда целевая ветка не получала новых коммитов.

Q: Когда при слиянии возникает конфликт?
+ Когда обе ветки изменили одну и ту же строку или файл
- Когда в ветке больше одного коммита
- Когда ветка отправлена в удалённый репозиторий
- Когда в проекте есть файл `.gitignore`
! Git не может выбрать между двумя изменениями одного места.

Q: Что означает `UU` в выводе `git status --short`?
+ Файл изменён обеими сторонами, конфликт ещё не разрешён
- Файл удалён из репозитория
- Файл добавлен в индекс и готов к коммиту
- Файл не отслеживается
! Две буквы `U` показывают конфликт с двух сторон.

Q: Чем слияние отличается от перебазирования?
+ Слияние сохраняет ветвление, перебазирование переносит коммиты на новую базу
- Слияние меняет хэши, перебазирование их сохраняет
- Перебазирование работает только с удалёнными ветками
- Между ними нет разницы
! Перебазирование делает историю линейной и меняет хэши коммитов.

Q: Почему нельзя перебазировать общую ветку?
+ Перебазирование меняет хэши, и история у коллег расходится
- Перебазирование удаляет все файлы проекта
- Перебазирование запрещено в Git
- После него нельзя сделать слияние
! Общую ветку безопаснее сливать, а не переписывать.

Q: Что делает `git add` после разрешения конфликта?
+ Отмечает конфликт как разрешённый и готовит файл к коммиту
- Удаляет конфликтующие строки автоматически
- Отменяет слияние
- Отправляет файл в удалённый репозиторий
! Индекс сообщает Git, что файл готов к завершению слияния.

Q: Как отменить начатое слияние?
+ `git merge --abort`
- `git commit --abort`
- `git push --abort`
- `git switch --abort`
! Команда возвращает состояние до начала слияния.

Q: Какие команды создают новую ветку?
+ `git branch feature/report`
+ `git switch -c feature/report`
+ `git checkout -b feature/report`
- `git merge feature/report`
- `git push feature/report`
! Все три команды создают ветку, но переключаются на неё не все.

Q: Какие правила защищают общую ветку?
+ Работать в отдельной ветке под задачу
+ Запускать тесты перед слиянием
+ Читать обе стороны конфликта
- Коммитить напрямую в `main` без проверки
- Разрешать конфликт удалением чужой строки
! Ветка, тесты и внимательное разрешение конфликта сохраняют чужую работу.

Q: Что показывает `git log --graph --oneline --all`?
+ Граф истории всех веток с короткими хэшами
+ Список файлов рабочего каталога
+ Содержимое индекса
+ Настройки удалённого репозитория
! Флаги включают граф, краткий формат и все ветки.

Q: Как называется слияние, при котором указатель просто перемещается вперёд?
= fast-forward
= перемотка
! При перемотке новый коммит слияния не создаётся.

Q: Как называется перенос коммитов ветки на новую базу?
= rebase
= перебазирование
! Перебазирование применяет коммиты заново поверх другой ветки.

Q: Какая команда показывает состояние рабочего каталога и индекс?
= git status
= status
! `git status` показывает ветку, изменения и конфликты.
::/gate
