## Цель работы

Открыть операции проекта через HTTP API и сделать отказы предсказуемыми. Клиент должен получать один и тот же формат ошибки, независимо от того, что случилось: неверное поле, отсутствующая запись, чужой метод, сломанный JSON или сбой на сервере. Второй результат работы это коллекция Postman, где рядом стоят успешные и ошибочные запросы.

Работа продолжает проект, собранный на предыдущем занятии. Модуль с четырьмя операциями уже умеет читать и писать базу, но вызывать его из другого приложения неудобно. API добавляет слой, который принимает HTTP-запрос, проверяет вход, вызывает модуль и собирает ответ.

Примеры построены на товарах «Северного склада»: 4800 позиций, 12 категорий, четыре площадки. В индивидуальном проекте маршруты строятся для своей сущности, но набор кодов состояния и формат ошибки остаются такими же. Единый формат важен не сам по себе: по нему клиент понимает, что делать дальше, не разбирая текст сообщения.

## Краткие теоретические сведения

HTTP API описывает ресурс, а не действие. Путь `/api/products` обозначает коллекцию товаров, `/api/products/SKU-1001` один товар. Метод говорит, что именно сделать с ресурсом: `GET` прочитать, `POST` создать, `PUT` заменить, `DELETE` удалить. Один путь с разными методами даёт разные операции, и это нормально.

Имя ресурса записывают во множественном числе и в одном стиле для всего проекта: `products`, `acceptances`, `invoices`. Глагол в пути не нужен, его заменяет метод. Фильтры, сортировка и границы страницы передаются параметрами строки запроса: `?site=Тула&limit=20`. Такая адресация переживает добавление новых полей и не превращается в набор команд вида `/getProducts`.

Слой API не заменяет модуль операций, а надстраивается над ним. Модуль знает, как читать и писать базу, но ничего не знает про HTTP. Маршрут разбирает запрос, вызывает модуль и переводит результат в код состояния. Такое разделение позволяет проверить модуль без сервера, а маршрут без настоящей базы. Если смешать разбор HTTP и SQL в одной функции, тестировать её придётся целиком и с поднятым сервером.

Код состояния это часть контракта. `200` означает успешное чтение, `201` создание, `204` удаление без тела. `400` сообщает о неверных данных клиента, `401` об отсутствующем или испорченном токене, `403` о запрете для известного пользователя, `404` об отсутствующей записи или маршруте, `405` о неподдерживаемом методе, `409` о конфликте с существующей записью, `415` о неподходящем типе тела, `500` о сбое сервера. Клиент проверяет код до разбора тела и выбирает ветку поведения.

Методы различаются не только смыслом, но и отношением к повтору. `GET`, `PUT` и `DELETE` называют идемпотентными: повторный запрос с теми же данными приводит к тому же состоянию. Первый `DELETE` удаляет запись и возвращает `204`, второй возвращает `404`, но состояние базы уже не меняется. `POST` не идемпотентен: два одинаковых запроса создают две записи, если ключ не защищён ограничением `UNIQUE`. Поэтому создание товара опирается на уникальный артикул, а не на надежду, что клиент не повторит запрос.

Ошибка в API это не просто текст. Клиенту нужны машинный код, сообщение для человека и признак, к какому полю относится нарушение. Единый конверт ошибки выглядит так:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Проверьте поля запроса",
    "request_id": "d0b686cb",
    "fields": [
      {"field": "price", "code": "range", "message": "Цена больше 0 и не выше 1 000 000"}
    ]
  }
}
```

Поле `code` внутри `error` называет класс ошибки, а коды внутри `fields` называют правило для конкретного поля. Клиент показывает общее сообщение и подсвечивает поля. `request_id` связывает ответ с записью в журнале: пользователь называет идентификатор, инженер находит по нему трассировку.

Конверт не меняют от маршрута к маршруту. Новый код ошибки добавляют в словарь и описывают в документации, а структуру оставляют прежней. Если понадобится новая версия API, её публикуют по другому пути, например `/api/v2`, и старую некоторое время поддерживают. Клиенты, написанные полгода назад, не должны ломаться из-за переименованного поля.

Успешные ответы тоже описывают заранее. Коллекция возвращает объект с `count` и `items`, а не голый массив: в объект можно добавить номер страницы и общее число записей, не ломая клиентов. Карточка возвращает объект с полями записи. Создание возвращает `201`, идентификатор и нормализованные значения. Удаление возвращает `204` без тела, потому что сообщать клиенту нечего.

Без единого формата каждый обработчик придумывает свой ответ. Один маршрут возвращает `{"message": "нет товара"}`, другой `{"error": "not found"}`, третий просто текст. Клиенту приходится писать отдельный разбор на каждый случай, и любое изменение ломает интерфейс. Конверт фиксирует структуру один раз.

Flask по умолчанию отвечает HTML-страницей на неизвестный маршрут и на неподдерживаемый метод. Для API это неудобно: клиент ждёт JSON и получает разметку. Обработчик `HTTPException` перехватывает такие ответы и переводит их в общий конверт. Отдельный обработчик `Exception` ловит непредвиденные сбои, пишет трассировку в журнал и отдаёт `500` с нейтральным текстом.

Важно различать `404` маршрута и `404` записи. Если путь не совпал ни с одним правилом, клиент ошибся адресом. Если путь верный, а товара с таким артикулом нет, клиент ошибся данными. Оба случая дают `404`, но сообщения разные, и это помогает при отладке.

Тело запроса проверяют до бизнес-логики. Заголовок `Content-Type: application/json` подтверждает, что клиент прислал JSON. Если заголовка нет, сервер отвечает `415`. Если JSON синтаксически сломан, `get_json(silent=True)` вернёт `None`, и сервер отвечает `400`. Если вместо объекта пришёл массив или строка, это тоже `400`: контракт ждёт объект с полями.

Postman хранит запросы в коллекции. Переменная `base_url` избавляет от повторения адреса, а вкладка Tests содержит проверки, которые выполняются после ответа. Проверка кода и структуры тела превращает ручной просмотр в повторяемый прогон. Коллекция экспортируется в JSON и прикладывается к работе, чтобы проверяющий мог повторить сценарии.

Коллекцию прогоняют целиком через Collection Runner. Перед запуском выбирают окружение с `base_url`, затем смотрят сводку: сколько запросов прошло, сколько проверок упало и на каком шаге. Прогон по одному запросу вручную показывает только текущий ответ и не доказывает, что сценарии совместимы между собой. Например, запрос создания должен идти раньше запроса удаления, иначе удалять будет нечего.

### Шаг 2. Подключите Flask и базу

Создайте `.../sklad-plus/app.py`. Приложение хранит путь к базе в настройке, а соединение открывает по первому обращению в пределах запроса. После ответа соединение закрывается.

```python
import sqlite3

from flask import Flask, g

app = Flask(__name__)
app.config["DATABASE"] = "sklad.db"


def get_db():
    if "db" not in g:
        g.db = sqlite3.connect(app.config["DATABASE"])
        g.db.row_factory = sqlite3.Row
        g.db.execute("PRAGMA foreign_keys = ON")
    return g.db


@app.teardown_appcontext
def close_db(exc=None):
    db = g.pop("db", None)
    if db is not None:
        db.close()
```

Путь к базе вынесите в настройку, а не в функцию. Тогда проверка подставит временный файл, а рабочее приложение останется при своей базе. Соединение на запрос не разделяют между потоками: у каждого запроса свой объект `g`, поэтому гонки за одно соединение не возникает.

Проверьте запуск. Команда `python -m flask --app app run` поднимает сервер на локальном порту. Флаг `--app app` указывает модуль, в котором создано приложение. Остановить сервер можно сочетанием клавиш Ctrl+C в терминале.

```text
python -m flask --app app run
```

```text

```

Если порт занят, укажите другой флагом `--port 5001`. Менять код приложения для этого не нужно.

### Шаг 3. Соберите успешные маршруты

Сразу подключите функцию `error_response` из будущего модуля `errors.py`: её код появится на шаге 4, а маршруты уже будут её использовать. Так не придётся переписывать обработчики дважды.

Добавьте чтение списка и карточки. Обе функции вызывают модуль из предыдущей работы и возвращают JSON.

```python
from flask import jsonify, request

from errors import error_response
from products import create_product, delete_product, get_product, list_products, update_product
from validation import validate_product


@app.get("/api/products")
def products_list():
    items = list_products(get_db(), site=request.args.get("site"))
    return jsonify({"count": len(items), "items": items})


@app.get("/api/products/<sku>")
def products_detail(sku):
    row = get_product(get_db(), sku.strip().upper())
    if row is None:
        return error_response(404, f"Артикул {sku} не найден")
    return jsonify(row)


@app.get("/api/health")
def health():
    row = get_db().execute("SELECT COUNT(*) AS n FROM products").fetchone()
    return jsonify({"status": "ok", "products": row["n"], "version": "1.0.0"})
```

Маршрут проверки сервиса не трогает бизнес-логику: он подтверждает, что приложение запустилось и база отвечает. Такой маршрут пригодится при запуске проекта на другой машине.

Ответ списка выглядит так:

```text
HTTP 200 {"count": 4, "items": [{"id": 1, "sku": "SKU-1001", "title": "Перфоратор Bosch GSB 13 RE", "category": "Инструмент", "price": 8990, "stock": 12, "site": "Москва"}, ...]}
```

Фильтр `?site=Тула` возвращает только товары этой площадки. Если совпадений нет, приходит `200` с `count` равным нулю и пустым массивом. Пустой результат это не ошибка: запрос корректен, данных просто нет.

Добавьте создание. Сначала проверьте тело и поля, затем убедитесь, что артикул свободен, и только после этого вставляйте строку. Ответ `201` содержит идентификатор и нормализованный артикул.

```python
@app.post("/api/products")
def products_create():
    data, problem = json_body()
    if problem:
        return problem
    errors = validate_product(data)
    if errors:
        return error_response(400, "Проверьте поля запроса", "validation_failed", errors)
    data["sku"] = data["sku"].strip().upper()
    if get_product(get_db(), data["sku"]):
        return error_response(409, f"Артикул {data['sku']} уже есть")
    new_id = create_product(get_db(), data)
    return jsonify({"id": new_id, **data}), 201
```

Проверка `get_product` перед вставкой не отменяет обработку `IntegrityError`. Между проверкой и вставкой артикул может занять другой запрос. Ограничение `UNIQUE` в базе остаётся последней защитой, а обработчик исключения превращает его в `409`.

Добавьте изменение и удаление. Изменение возвращает обновлённый объект, удаление возвращает пустое тело с кодом `204`.

```python
@app.put("/api/products/<sku>")
def products_update(sku):
    data, problem = json_body()
    if problem:
        return problem
    errors = validate_product({**data, "sku": sku})
    if errors:
        return error_response(400, "Проверьте поля запроса", "validation_failed", errors)
    if update_product(get_db(), sku.strip().upper(), data) == 0:
        return error_response(404, f"Артикул {sku} не найден")
    return jsonify(get_product(get_db(), sku.strip().upper()))


@app.delete("/api/products/<sku>")
def products_delete(sku):
    if delete_product(get_db(), sku.strip().upper()) == 0:
        return error_response(404, f"Артикул {sku} не найден")
    return "", 204
```

### Шаг 4. Введите единый формат ошибки

Создайте `.../sklad-plus/errors.py`. Файл хранит словари сообщений и кодов, а функция `error_response` собирает конверт. Все маршруты и обработчики вызывают только её, поэтому структура ответа не расходится.

```python
from flask import g, jsonify

MESSAGES = {
    400: "Запрос не разобран",
    401: "Нужен токен",
    403: "Операция запрещена",
    404: "Запись не найдена",
    405: "Метод не поддерживается",
    409: "Запись уже существует",
    415: "Ожидается JSON",
    500: "Внутренняя ошибка сервера",
}

CODES = {
    400: "bad_request",
    401: "unauthorized",
    403: "forbidden",
    404: "not_found",
    405: "method_not_allowed",
    409: "conflict",
    415: "unsupported_media_type",
    500: "internal_error",
}


def error_response(status, message=None, code=None, fields=None):
    body = {
        "error": {
            "code": code or CODES.get(status, "error"),
            "message": message or MESSAGES.get(status, "Ошибка запроса"),
            "request_id": getattr(g, "request_id", None),
        }
    }
    if fields:
        body["error"]["fields"] = fields
    return jsonify(body), status
```

`fields` появляется только там, где он нужен. Для `404` список полей пуст, и клиент не получает лишнюю структуру. Для `400` список содержит все нарушения, собранные валидатором.

Идентификатор запроса создаётся до обработки и возвращается в заголовке. Он нужен, чтобы связать ответ с журналом, не показывая пользователю внутренние подробности.

```python
import uuid

from flask import g


@app.before_request
def assign_request_id():
    g.request_id = uuid.uuid4().hex[:8]


@app.after_request
def add_request_id(response):
    response.headers["X-Request-Id"] = getattr(g, "request_id", "")
    return response
```

### Шаг 5. Подключите обработчики ошибок

Обработчик `HTTPException` перехватывает стандартные ответы Flask: неизвестный маршрут, неподдерживаемый метод, слишком большое тело. Он переводит их в общий конверт и заменяет английский текст на понятный.

```python
from flask import g, request
from werkzeug.exceptions import HTTPException

from errors import MESSAGES, error_response


@app.errorhandler(HTTPException)
def handle_http_error(exc):
    message = MESSAGES.get(exc.code, "Ошибка запроса")
    if exc.code == 404 and request.url_rule is None:
        message = "Маршрут не найден"
    return error_response(exc.code, message)


@app.errorhandler(Exception)
def handle_unexpected_error(exc):
    app.logger.exception("unhandled error, request_id=%s", getattr(g, "request_id", ""))
    return error_response(500)
```

Проверка `request.url_rule is None` отличает неизвестный путь от известного пути с отсутствующей записью. Без неё клиент получит «Запись не найдена» на опечатку в адресе и будет искать проблему в данных.

Обработчик `Exception` не должен отдавать текст исключения. Трассировка попадает в журнал, а клиент получает нейтральное сообщение и `request_id`. По этому идентификатору инженер найдёт запись и увидит настоящую причину.

`500` не проверяют в обычном прогоне, потому что для него нужно намеренно сломать код. Достаточно убедиться, что обработчик подключён и возвращает конверт, а не HTML. В отчёте опишите, как вы это проверили: например, временно добавили маршрут, который делит на ноль, и посмотрели ответ. После проверки маршрут удаляют.

Журнал приложения и ответ клиенту решают разные задачи. В журнал записывают время, идентификатор запроса, маршрут, код и трассировку сбоя. В ответ попадают только код, короткое сообщение и идентификатор. Пароли, токены и полные данные записи в журнал не пишут: журнал читают многие, а секрет должен остаться у владельца. Этой темы коснёмся подробнее при защите доступа.

Проверьте три ответа: неизвестный маршрут, неподдерживаемый метод и отсутствующая запись. Вывод:

```text
HTTP 404 {"error": {"code": "not_found", "message": "Маршрут не найден", "request_id": "f77064a8"}}
HTTP 405 {"error": {"code": "method_not_allowed", "message": "Метод не поддерживается", "request_id": "50bc8b09"}}
HTTP 404 {"error": {"code": "not_found", "message": "Артикул SKU-9999 не найден", "request_id": "7a16dc29"}}
```

### Шаг 6. Проверьте разбор тела запроса

Функция `json_body` отвечает за тип тела и форму JSON. Она возвращает либо данные, либо готовый ответ с ошибкой. Маршрут не продолжает работу, если пришёл не тот формат.

```python
def json_body():
    if not request.is_json:
        return None, error_response(415)
    data = request.get_json(silent=True)
    if not isinstance(data, dict):
        return None, error_response(400, "Тело должно быть объектом JSON")
    return data, None
```

`request.is_json` проверяет заголовок `Content-Type`. Без него Flask не станет разбирать тело, и маршрут получит пустой словарь. Явная проверка даёт клиенту точный код `415` вместо загадочного `400` на отсутствующих полях.

`silent=True` не выбрасывает исключение при сломанном JSON, а возвращает `None`. Это удобно для API: синтаксическая ошибка не должна превращаться в `500`. Но `None` бывает и при пустом теле, поэтому сообщение формулируют как «Тело должно быть объектом JSON», а не «Ошибка синтаксиса».

Проверьте четыре тела: корректный объект, объект с лишними полями, массив и строку без заголовка. Лишние поля можно игнорировать или отклонять; выберите правило и запишите его в отчёт. Массив и строка должны получить `400`, отсутствие заголовка `415`.

```text
HTTP 415 {"error": {"code": "unsupported_media_type", "message": "Ожидается JSON", "request_id": "1011e0e4"}}
HTTP 400 {"error": {"code": "bad_request", "message": "Тело должно быть объектом JSON", "request_id": "eeadc63e"}}
```

### Шаг 7. Прогоните сценарии в Postman

Создайте коллекцию `sklad-plus API` и переменную `base_url` со значением `http://127.0.0.1:5000`. Адрес задаётся один раз, запросы используют `{{base_url}}`. При смене порта правится одна переменная, а не десять запросов.

Соберите не меньше десяти запросов. В таблицу записывайте ожидаемый и фактический код, а также короткое тело. Первая строка дана как образец.

| Сценарий | Запрос | Ожидаемый код | Фактический код | Тело |
|---|---|---|---|---|
| Список товаров | `GET /api/products` | 200 |  |  |
| Фильтр по площадке | `GET /api/products?site=Тула` | 200 |  |  |
| Карточка товара | `GET /api/products/SKU-1001` | 200 |  |  |
| Неизвестный артикул | `GET /api/products/SKU-9999` | 404 |  |  |
| Создание товара | `POST /api/products` | 201 |  |  |
| Дубликат артикула | `POST /api/products` | 409 |  |  |
| Неверная цена | `POST /api/products` | 400 |  |  |
| Изменение товара | `PUT /api/products/SKU-1001` | 200 |  |  |
| Удаление товара | `DELETE /api/products/SKU-3001` | 204 |  |  |
| Неизвестный маршрут | `GET /api/orders` | 404 |  |  |
| Чужой метод | `PATCH /api/products/SKU-1001` | 405 |  |  |

В каждом запросе сохраните ответ. В Postman нажмите Save Response и дайте ответу имя сценария. В отчёте приведите снимок окна с методом, адресом, кодом и телом. Для `204` тело пустое, поэтому на снимке должен быть виден код и заголовок `X-Request-Id`.

Добавьте в коллекцию проверки. Начните с одной, чтобы увидеть, как работает вкладка Tests:

```javascript
pm.test("код 200", function () {
    pm.response.to.have.status(200);
});
pm.test("есть массив items", function () {
    pm.expect(pm.response.json().items).to.be.an("array");
});
```

Проверка кода останавливает сценарий, если сервер ответил иначе. Проверка структуры подтверждает, что тело пригодно для разбора. Для ошибок проверяйте не только код, но и поле `error.code`: так тест отличит `404` записи от `404` маршрута.

Имя проверки попадает в отчёт прогона, поэтому пишите его как утверждение: «код 201 при создании», «поле price в списке ошибок». Проверка с именем «тест 1» ничего не сообщает при падении. В коллекции держите не больше двух-трёх проверок на запрос: код, структура и одно значимое значение. Десяток проверок на один ответ усложняет разбор падения и не добавляет уверенности.

Сохраняйте примеры ответов вместе с запросом. Пример фиксирует, как выглядел успешный и ошибочный ответ на момент проверки, и помогает сравнить поведение после правки кода. Пример не заменяет тест: он не выполняется автоматически, но служит образцом для проверяющего.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: все операции открыты маршрутами, успешные ответы имеют разные коды, любой отказ приходит в едином конверте, неизвестный маршрут и чужой метод дают JSON, идентификатор запроса возвращается в заголовке и теле, десять сценариев прогнаны в Postman и записаны.
- **4**: маршруты работают, конверт единый, но один стандартный отказ отвечает HTML или в коллекции не хватает одного сценария.
- **3**: маршруты работают, но ошибки разного вида имеют разную структуру, `404` записи и маршрута не различаются, сценарии описаны без фактических кодов.
- **2**: работа не выполнена или приложение не запускается.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
