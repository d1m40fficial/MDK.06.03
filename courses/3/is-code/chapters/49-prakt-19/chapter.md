## Цель работы

Оформить для проекта `sklad-plus` два документа, по которым другой человек поднимет систему и проверит её API без вопросов автору. README отвечает за установку и запуск, описание API за маршруты, параметры, ответы и ошибки. Оба документа проверяются действием: клонированием в новый каталог, установкой зависимостей, созданием базы и запросами к работающему сервису.

Результат работы это README, описание API на семь маршрутов, протокол проверки на чистом окружении и список расхождений между документами и кодом. Документ, который не проверяли запуском, считается черновиком, даже если он выглядит аккуратно.

## Краткие теоретические сведения

README это документ для того, кто впервые открыл репозиторий. У него три читателя: разработчик, который будет менять код, администратор, который будет запускать систему, и проверяющий, который повторяет сценарий. Все трое задают одни и те же вопросы: что это, что нужно установить, как создать базу, как запустить, как убедиться, что всё работает.

Хороший README состоит из коротких разделов с командами и ожидаемым результатом. Команда без результата оставляет читателя в догадках: он не знает, должна ли появиться строка, открыться страница или создаться файл. Команда с результатом позволяет остановиться в момент, когда что-то пошло не так, и не искать ошибку в следующих шагах.

| Раздел README | Вопрос читателя | Что писать |
|---|---|---|
| Назначение | что это за система | одно-два предложения о предметной области |
| Требования | что установить заранее | версия Python, Git, браузер |
| Установка | как получить зависимости | создание окружения и установка пакетов |
| Настройка | какие параметры задать | переменные окружения и пример файла |
| База данных | как создать схему | команда создания и заполнения |
| Запуск | как поднять сервис | команда, порт, адрес |
| Проверка | как убедиться, что работает | запрос или действие с ожидаемым ответом |
| Ограничения | что пока не сделано | известные пределы учебной версии |

Описание API это контракт между сервером и клиентом. В нём перечислены маршруты, методы, параметры, тела запросов, успешные ответы и ошибки. Описание начинают с таблицы маршрутов, чтобы читатель увидел систему целиком, а затем раскрывают каждый маршрут отдельной карточкой.

Карточка маршрута отвечает на шесть вопросов: что делает маршрут, кому разрешён, какие параметры принимает, что возвращает при успехе, какие ошибки возможны и как выглядит пример запроса. Пример должен быть скопирован из фактического ответа, а не написан по памяти. Память хранит намерение, а сервер возвращает то, что действительно произошло.

Коды состояния в описании выполняют ту же роль, что и в коде. Успешное чтение даёт 200, создание 201, неверные поля 400, отсутствие входа 401, запрет для известной роли 403, отсутствующая запись 404, конфликт уникальности 409. Если в описании у всех ответов стоит 200, клиент не сможет отличить успех от отказа и будет разбирать текст ошибки как данные.

Документы расходятся с кодом по трём причинам: маршрут переименовали, поле переименовали, команду запуска изменили. Расхождение обнаруживают сверкой, а не памятью. Список маршрутов берут из кода, коды ответов из фактических запросов, команды из терминала. После каждой правки кода документ проверяют ещё раз, иначе он устаревает в тот же день.

Чистое окружение это новый каталог, новое виртуальное окружение и новая база. В нём нет старых пакетов, забытых переменных и данных, которые автор добавил вручную. Только чистая копия показывает, что инструкция полная. Если для запуска пришлось вручную создать папку или скопировать файл, значит, этого шага не хватает в README.

### Шаг 4. Заполните карточку маршрута

Ниже шаблон карточки и один заполненный пример для входа. По этому образцу опишите остальные маршруты, меняя назначение, тело, ответы и пример запроса.

```text
### POST /api/auth/login

Назначение: проверить пару логин и пароль и выдать токен.
Права: доступен без токена.
Тело запроса: `login`, `password`.
Успешный ответ: 200, `token`, `role`, `site`.
Ошибки: 401 при неверной паре, 403 при заблокированной записи.

    curl.exe -i -X POST http://127.0.0.1:5000/api/auth/login ^

```

В карточке не должно быть общих слов вроде «возвращает данные». Читатель должен увидеть имена полей и коды. Если маршрут требует роль, укажите её. Если тело необязательно, напишите об этом. Если ошибка возвращает список полей, покажите форму тела.

### Шаг 5. Добавьте примеры запросов и ошибок

Пример запроса это команда, которую можно скопировать в терминал. Разберите её на образце выше. Ключ `-i` показывает заголовки и строку состояния, `-X POST` задаёт метод, `-H` добавляет заголовок типа содержимого, `--data-binary "@login.json"` отправляет тело из файла. Символ `^` в PowerShell переносит команду на следующую строку.

Для каждого маршрута добавьте по одному успешному и по одному ошибочному примеру. Ошибочный запрос должен проверять конкретное правило: отсутствие обязательного поля, отрицательную цену, повторный артикул, чужую роль. Заполните таблицу проверок по фактическим ответам, первая строка дана как образец.

| Запрос | Ожидаемый код | Фактический код | Что в теле | Вывод |
|---|---|---|---|---|

| POST `/api/auth/login` с неверным паролем | 401 |  |  |  |
| GET `/api/products` | 200 |  |  |  |
| GET `/api/products/999` | 404 |  |  |  |
| POST `/api/products` без поля `title` | 400 |  |  |  |

Не придумывайте ответы. Если фактический код отличается от ожидаемого, сначала разберитесь, какое требование нарушено, затем исправьте код или ожидание. В описание API попадает фактическое поведение, а не желаемое.

### Шаг 6. Проверьте инструкцию на чистом окружении

Скопируйте проект в новый каталог и пройдите README от начала до конца. Ниже последовательность команд. Каждый шаг сопровождайте ожидаемым результатом, чтобы заметить расхождение сразу.

```powershell
git clone .../sklad-plus.git .../check-run
cd .../check-run
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r api/requirements.txt
python db/init_db.py
cd api
python app.py
```

`git clone` создаёт вторую копию проекта, не связанную с рабочим каталогом автора. `cd` переходит в неё. Дальше команды повторяют README. Обратите внимание на смену каталога перед запуском: установка и создание базы выполняются из корня проекта, а сервер запускается из каталога `api`, где лежит точка входа. Если команда завершается ошибкой импорта, проверьте, из какого каталога она запущена и совпадает ли команда в README с фактической точкой входа. Сервер занимает терминал, поэтому запросы выполняйте во втором окне терминала.

Заполните протокол проверки. Первая строка дана как образец. В последней колонке записывайте, что именно увидели: имя созданного файла, число таблиц, строку запуска сервера, ответ браузера.

| 2 | `python -m venv .venv` | создан каталог `.venv` |  |

Пройдите чек-лист и запишите конкретное расхождение или слово «нет». Проверка идёт от кода к документу, а не наоборот: список маршрутов берут из `api/app.py`, коды из фактических запросов, команды из терминала.

| Проверка | Как проверить | Найдено |
|---|---|---|
| все маршруты кода есть в таблице | сравнить список объявлений и строки таблицы |  |
| в таблице нет лишних маршрутов | отправить запрос по каждому пути |  |

Расхождение исправляют в документе, если код работает правильно, или в коде, если документ описывает согласованное требование. Молча оставлять разные версии нельзя: следующий читатель выберет неверную.

## Требования к отчёту

Отчёт содержит цель, дерево проекта, текст README, таблицу маршрутов, две-три карточки маршрутов, таблицу проверок, протокол чистого запуска и список найденных расхождений с исправлениями.

На снимке терминала должны быть видны команда, её вывод и отсутствие ошибок. На снимке запроса в Postman должны быть видны метод, полный адрес, код состояния и тело ответа. Если запрос выполняли в браузере, на снимке должны быть видны адрес и тело ответа. Кадр одного тела без адреса не показывает, что запрос ушёл на нужный маршрут.

В выводе ответьте на три вопроса: какой шаг README оказался неполным и как его исправили; какое расхождение между кодом и документом нашлось; почему описание API без примеров ошибок считается неполным.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: README позволяет поднять проект в новом каталоге без правок, описаны все семь маршрутов с параметрами, ответами и ошибками, примеры скопированы из фактических ответов, протокол заполнен, расхождения найдены и исправлены, в документах нет секретов.
- **4**: работа выполнена полностью, но один маршрут описан без ошибок или один шаг протокола заполнен без фактического результата.
- **3**: README содержит установку и запуск, но пропущен шаг создания базы; таблица маршрутов неполная; карточки заменены общими фразами; проверка на чистом окружении не выполнена.
- **2**: работа не выполнена или документы не позволяют запустить проект.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
