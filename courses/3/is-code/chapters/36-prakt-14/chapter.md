## Краткие теоретические сведения

Секрет это значение, которое даёт доступ к системе или данным: пароль базы, ключ подписи токена, ключ внешнего сервиса, строка подключения. Секрет отличается от обычной настройки тем, что его утечка требует немедленной замены. Путь к файлу базы или номер порта можно показать в отчёте, пароль показать нельзя.

Секреты хранят вне кода и вне репозитория. Рабочий вариант это переменные окружения, которые задают на машине или в панели развёртывания. Файл `.env` удобен для учебного стенда, но он попадает в `.gitignore` и не коммитится. Рядом лежит `.env.example` с именами переменных и значениями-заглушками, чтобы новый разработчик знал, что заполнить.

Если секрет уже попал в Git, удалить строку из текущего файла недостаточно: значение остаётся в истории коммитов и в клонах. Правильный порядок такой: сменить секрет, убрать файл из текущего дерева, добавить его в `.gitignore`. Переписывание истории допустимо только по согласованию со всей командой, потому что оно меняет хеши коммитов.

Опасный ввод это данные, которые меняют смысл запроса или разметки. В SQL опасность создаёт склейка строки: введённый текст становится частью команды, а не значением. Защита это параметризованный запрос, где текст передаётся отдельно от команды. Для имён колонок и направлений сортировки параметры не работают, поэтому там применяют белый список допустимых значений.

Журнал аудита фиксирует события доступа: успешный и неудачный вход, отказ в праве, изменение роли, отклонённый запрос. В нём есть время, идентификатор запроса, пользователь, действие и результат. Пароли, токены и полные персональные данные в журнал не попадают. Уровни выбирают по последствиям: INFO для штатных событий, WARNING для отказа, ERROR для сбоя операции.

## Ход работы

### Шаг 1. Найдите секреты в коде и истории

Ниже фрагмент `.../sklad-plus/app.py` в том виде, в каком он попал в репозиторий до аудита. В нём намеренно оставлены три проблемы: пароль базы, ключ приложения и склейка SQL.

```python
import sqlite3

from flask import Flask, request

app = Flask(__name__)
app.config["SECRET_KEY"] = "sklad-secret-2026"
DB_PASSWORD = "sklad_2026"


def find_products(term):
    con = sqlite3.connect("sklad.db")
    query = f"SELECT sku, name FROM products WHERE name LIKE '%{term}%'"
    return con.execute(query).fetchall()


@app.get("/api/products")
def products():
    return {"items": find_products(request.args.get("q", ""))}
```

Начните с поиска по текущему дереву. Команда `git grep` ищет строку во всех отслеживаемых файлах и показывает имя файла, номер строки и текст. Пример поиска по слову `password`:

```text
app.py:6:app.config["SECRET_KEY"] = "sklad-secret-2026"
app.py:7:DB_PASSWORD = "sklad_2026"
```

Повторите поиск для слов `secret`, `token`, `key`, `passwd` и `connection`. Затем проверьте историю: команда `git log -p -S "DB_PASSWORD"` показывает коммиты, в которых число вхождений строки изменилось. Так находится секрет, удалённый из текущего файла, но оставшийся в истории.

Составьте список найденного: файл, строка, вид секрета, где ещё встречается. Не исправляйте код на этом шаге, сначала нужен полный перечень, иначе часть находок потеряется.

Поиск по словам даёт ложные срабатывания. Слово `key` встречается в `keyboard`, `token` в названии поля, `password` в тексте сообщения об ошибке. Каждую находку проверяют глазами и решают, является ли значение настоящим секретом. В больших проектах эту работу автоматизируют сканеры секретов, но в учебной работе достаточно `git grep` и просмотра истории.

`git grep` ищет только в отслеживаемых файлах. Локальный `.env`, который ещё не добавлен в индекс, в вывод не попадёт, поэтому отдельно проверьте `git status` и список файлов в каталоге проекта. Секрет в неотслеживаемом файле тоже опасен: его легко случайно добавить командой `git add .`.

### Шаг 2. Вынесите настройки из кода

Создайте модуль `.../sklad-plus/config.py`, который читает значения из окружения. Для обязательного секрета используйте обращение по ключу, а не `get` с пустым значением по умолчанию: приложение должно упасть при запуске, а не работать с дырявой настройкой.

```python
import os

DB_PATH = os.environ.get("SKLAD_DB", "sklad.db")
SECRET_KEY = os.environ["SKLAD_SECRET"]
LOG_LEVEL = os.environ.get("SKLAD_LOG_LEVEL", "INFO")
```

Рядом положите `.../sklad-plus/.env.example` с именами переменных и учебными значениями. Настоящий `.env` создаётся на машине и не коммитится.

```text
SKLAD_DB=sklad.db
SKLAD_SECRET=change-me
SKLAD_LOG_LEVEL=INFO
```

Замените в `app.py` литералы на значения из `config.py`: путь к базе, ключ приложения и уровень журнала. После этого в исходном коде не должно оставаться ни одного настоящего секрета.

Проверьте запуск двумя способами: без переменной `SKLAD_SECRET` приложение должно завершиться с понятной ошибкой, с переменной должно стартовать. Задайте переменную в терминале перед запуском и повторите проверку. В отчёте запишите обе команды и результат.

После выноса смените сам секрет. Старый пароль базы и старый ключ подписи считаются скомпрометированными: они лежали в репозитории, значит могли попасть в чужие копии. Новая пара значений создаётся заново, старые токены после смены ключа перестают приниматься.

### Шаг 3. Закройте доступ к секретам в репозитории

Добавьте в `.../sklad-plus/.gitignore` строки для файла окружения, журналов и локальной базы. Пример:

```text
.env
logs/
*.db
```

Если `.env` уже отслеживается, уберите его из индекса командой `git rm --cached .env`, не удаляя файл с диска. После этого `git status` не должен показывать `.env` как новый файл. Проверьте, что `.env.example` остаётся в репозитории: без него новый разработчик не узнает имена переменных.

Проверьте настройки запуска в VS Code. Если переменные окружения записаны в общий `launch.json` и файл закоммичен, секрет вернулся в репозиторий другим путём. Настройки запуска хранят локально или описывают ссылку на `.env`, а не сами значения. Перед коммитом просматривайте `git diff --staged`: так видно, что именно уходит в историю.

Полезно добавить проверку перед коммитом. Простой список из двух команд `git grep -n "password"` и `git status --short` занимает секунду и ловит забытый файл. Автоматический хук делает то же самое без напоминаний, но в учебной работе достаточно привычки просматривать изменения перед отправкой.

Проверьте историю ещё раз. Если секрет остался в старом коммите, одной смены значения недостаточно: старый пароль всё ещё виден в `git log`. Запишите в отчёт, какой коммит содержит утечку и почему переписывание истории не выполнялось без согласования.

### Шаг 4. Проверьте ввод на опасные символы

Вернитесь к функции поиска. Склейка строки превращает ввод в часть SQL-команды. Ниже проверка на учебной базе из трёх товаров: обычный запрос, опасный ввод и тот же ввод через параметр.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE products (sku TEXT, name TEXT, stock INTEGER)")
rows = [
    ("SKU-1001", "Кабель UTP cat.5e", 42),
    ("SKU-1002", "Патч-корд cat.5e", 860),
    ("SKU-1003", "Коммутатор 24 порта", 14),
]
con.executemany("INSERT INTO products VALUES (?, ?, ?)", rows)


def search_unsafe(term):
    query = f"SELECT sku, name FROM products WHERE name LIKE '%{term}%'"
    return con.execute(query).fetchall()


def search_safe(term):
    query = "SELECT sku, name FROM products WHERE name LIKE ?"
    return con.execute(query, (f"%{term}%",)).fetchall()


print("обычный запрос, строк:", len(search_unsafe("Кабель")))
print("опасный ввод, строк:", len(search_unsafe("' OR '1'='1")))
print("параметры, строк:", len(search_safe("' OR '1'='1")))
print("параметры, обычный ввод:", len(search_safe("Кабель")))
```

Вывод показывает разницу: опасный ввод через склейку вернул все три строки, а через параметр не вернул ни одной.

```text
обычный запрос, строк: 1
опасный ввод, строк: 3
параметры, строк: 0
параметры, обычный ввод: 1
```

Исправьте `find_products` в проекте: команда SQL остаётся постоянной, значение передаётся вторым аргументом. Для сортировки по колонке параметр не подойдёт, поэтому принимайте только значения из списка `sku`, `name`, `stock` и отклоняйте остальные с кодом 400.

Параметризация защищает от изменения команды, но не от подстановочных знаков внутри значения. Символы `%` и `_` в `LIKE` означают «любая строка» и «любой символ», поэтому поиск по `%` вернёт весь каталог. Если пользователь ищет буквальный процент, его экранируют и указывают `ESCAPE`. Для учебного поиска достаточно ограничить длину строки и объяснить поведение в отчёте.

Отдельно проверьте повторное использование данных. Значение, сохранённое в базе без проверки, может попасть в другой запрос, где его снова склеят со строкой. Параметризация нужна во всех местах, а не только в том, которое проверяли на занятии. Поиск по слову `SELECT` и знаку `+` рядом с ним помогает найти оставшиеся склейки.

Добавьте проверку полей перед запросом: количество целое от 1 до 10000, площадка из четырёх названий, артикул вида `SKU-1001`. Опасные символы не нужно вычищать вручную, если запрос параметризован, но проверка формата всё равно нужна: она отсекает мусор до обращения к базе.

### Шаг 5. Настройте журнал событий доступа

Ниже журнал до аудита. В нём есть пароль, токен и строка без контекста. Такие записи нельзя хранить и показывать.

```text
2026-10-12 09:14:22 INFO login user=kladovshchik_1 password=Sklad-2026 result=ok
2026-10-12 09:15:03 INFO stock_list token=eyJ1c2VyX2lkIjoxLCJyb2xlIjoi... rows=4800
2026-10-12 09:16:41 ERROR failed
```

Перепишите события так, чтобы в них остались идентификаторы и результат. Успешный вход, неудачный вход, отказ в праве, отклонённая валидация и изменение роли должны иметь разные уровни и понятный набор полей. Первая строка таблицы дана как образец, остальные заполните сами.

| Событие | Уровень | Поля записи | Что не писать |
|---|---|---|---|
| Успешный вход | INFO | `request_id`, `user`, `action`, `result` | пароль |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |

Настройте запись в файл с ротацией. Пример ниже создаёт каталог `logs`, пишет четыре события и ограничивает размер файла одним мегабайтом с тремя копиями. Для учебного стенда этого достаточно, в рабочей системе предел и срок хранения задают по требованиям.

```python
import logging
from logging.handlers import RotatingFileHandler
from pathlib import Path

log_dir = Path("logs")
log_dir.mkdir(exist_ok=True)

logger = logging.getLogger("sklad.audit")
logger.setLevel(logging.INFO)
logger.propagate = False

handler = RotatingFileHandler(
    log_dir / "sklad.log", maxBytes=1_000_000, backupCount=3, encoding="utf-8"
)
handler.setFormatter(logging.Formatter(
    "%(asctime)s %(levelname)s %(message)s", datefmt="%Y-%m-%d %H:%M:%S"
))
logger.addHandler(handler)

logger.info("request_id=8f21 user=kladovshchik_1 action=login result=ok")
logger.warning("request_id=8f22 user=kladovshchik_1 action=login result=denied reason=bad_password")
logger.info("request_id=8f23 user=manager_1 action=report_export rows=312")
logger.error("request_id=8f23 user=manager_1 action=report_export error=PermissionError")

print((log_dir / "sklad.log").read_text(encoding="utf-8"))
```

Запуск создаёт файл и выводит его содержимое:

```text
2026-10-31 11:29:28 INFO request_id=8f21 user=kladovshchik_1 action=login result=ok
2026-10-31 11:29:28 WARNING request_id=8f22 user=kladovshchik_1 action=login result=denied reason=bad_password
2026-10-31 11:29:28 INFO request_id=8f23 user=manager_1 action=report_export rows=312
2026-10-31 11:29:28 ERROR request_id=8f23 user=manager_1 action=report_export error=PermissionError
```

Подключите журнал к маршрутам входа и приёмки. В записи о входе оставьте логин и результат, но не пароль. В записи об отказе в доступе укажите роль и действие, но не токен. В записи об ошибке базы укажите имя операции и класс ошибки, но не текст SQL с параметрами.

Старые записи с паролями и токенами нельзя исправить редактированием строки. Секрет уже попал в файл, в копии ротации и, возможно, в архив. Правильный порядок: сменить секрет, ограничить доступ к каталогу журналов, удалить старые файлы по правилу хранения. Если журнал нужен для разбора, храните его в защищённом месте, а не в общей папке проекта.

Проверьте, что пользовательские значения не ломают формат записи. Перевод строки в имени пользователя или в поисковом запросе создаёт вторую строку, похожую на настоящую запись. Значения экранируют или заменяют управляющие символы, а длину полей ограничивают. Журнал должен оставаться однозначным даже при странном вводе.

### Шаг 6. Проведите аудит по чек-листу

Пройдите сервис по чек-листу и заполните столбцы «Найдено» и «Исправление». В столбце «Найдено» пишите конкретный файл и строку либо слово «нет». Первая строка дана как образец.

| Проверка | Как проверить | Найдено | Исправление |
|---|---|---|---|
| Секреты в коде | `git grep -n "password"` | `app.py`, строка с `DB_PASSWORD` | вынести в переменную окружения, сменить пароль |
| Секреты в истории | `git log -p -S "DB_PASSWORD"` |  |  |
| Файл окружения в репозитории | `git ls-files .env` |  |  |
| Склейка SQL | поиск `SELECT` и знака `+` рядом |  |  |
| Проверка полей приёмки | запрос с `qty` равным 0 |  |  |
| Пароль в журнале | поиск `password=` в файле лога |  |  |
| Токен в журнале | поиск `token=` в файле лога |  |  |
| Роль из тела запроса | запрос с чужой ролью |  |  |
| Ротация журнала | проверка настроек `RotatingFileHandler` |  |  |

Для каждой строки с находкой сделайте исправление и повторите проверку. Аудит считается закрытым, когда повторная проверка даёт «нет» или объясняет, почему риск принят. Например, учебный пароль в `.env.example` допустим, если он заведомо не работает и помечен как пример.

К каждой строке приложите доказательство: вывод команды, код ответа, строку журнала. Формулировка «исправлено» без доказательства не принимается, потому что проверяющий не может отличить исправление от обещания. Если проверка невозможна в учебной среде, опишите, что именно мешает и как её выполнить в рабочей системе.

Повторный аудит проводите после всех правок, а не после каждой. Между проверками код меняется, и часть старых находок может вернуться вместе с новыми функциями. Итоговый чек-лист должен относиться к одной версии проекта, иначе выводы противоречат друг другу.

Отдельно проверьте права. Кладовщик не должен менять цены и роли, менеджер не должен создавать приёмку, администратор не должен видеть пароли пользователей. Роль берётся из проверенного токена, а не из тела запроса. Для каждой операции, которая меняет данные, нужна проверка роли до выполнения.

### Шаг 7. Соберите отчёт и файл журнала

Соберите отчёт по шагам: что найдено, что исправлено, чем подтверждено. К каждому исправлению приложите команду или запрос и результат. Например, для склейки SQL приведите запрос с опасным вводом до исправления и после, для журнала строку до и после.

Приложите файл журнала за проверку. В нём должны быть видны успешный вход, неудачный вход, отказ в доступе и отклонённая валидация, связанные идентификаторами запросов. Файл не должен содержать паролей, полных токенов и лишних персональных данных.

Назовите файл так, чтобы его можно было отличить от рабочего: `.../sklad-plus/logs/audit-check.log`. В отчёте укажите дату проверки и версию проекта, к которой она относится. Если журнал создан повторным запуском, отметьте это, чтобы проверяющий не сравнивал записи разных прогонов. Файл журнала не редактируют вручную: исправления делают в коде, а затем повторяют проверку и получают новую запись.

## Требования к отчёту

Отчёт содержит цель работы, перечень найденных секретов с файлами и строками, описание выноса настроек и смены значений. Приведите таблицу аудита с проверками, находками и исправлениями, а также подтверждения: вывод `git grep`, результат запроса с опасным вводом, строки журнала до и после.

В выводе на пять-семь предложений объясните, почему смена секрета обязательна даже после удаления строки из кода, чем параметризованный запрос отличается от очистки символов и какие события доступа теперь попадают в журнал.

## Что сдать

- исправленный проект `sklad-plus` с настройками из окружения;
- файл `.env.example` и обновлённый `.gitignore`;
- заполненный чек-лист аудита с находками и исправлениями;
- файл журнала с событиями входа, отказа и ошибки;
- отчёт с подтверждениями исправлений и выводом.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.
- **5**: секреты найдены в коде и истории, вынесены в окружение и заменены, `.env` исключён из репозитория, склейка SQL заменена параметрами, поля проверяются, журнал пишет вход, отказ и ошибку с идентификатором запроса и без секретов, чек-лист заполнен полностью и подтверждён.
- **4**: работа выполнена полностью, но один секрет остался в истории без объяснения, не проверена одна строка чек-листа или в журнале не хватает одного события.
- **3**: секреты вынесены частично, склейка SQL осталась в одном месте, журнал пишет общий текст без идентификатора, чек-лист заполнен наполовину.
- **2**: работа не выполнена.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
