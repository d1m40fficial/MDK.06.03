## Журнал движений за день

За смену «Склад+» проводит 214 документов: приёмки от поставщиков, отгрузки клиентам и списания по акту. Каждый документ меняет остаток позиции. В справочнике 4800 позиций, работают четыре площадки, и любая ошибка в проведении видна не сразу, а на инвентаризации через месяц.

Первая версия кода обходилась тремя функциями: `apply_receipt`, `apply_shipment`, `apply_write_off`. Каждая принимала словарь остатков и документ, каждая по-своему меняла число. Приёмка прибавляла количество, отгрузка вычитала, списание вычитало и записывало причину. Функции росли отдельно, и через полгода в отгрузке появилась ошибка: количество прибавилось вместо вычитания. Склад отгрузил 18 единиц, а в системе остаток вырос на 18.

Потом понадобился возврат поставщику. Пришлось править три функции, журнал, отчёт и обработчик API, потому что тип документа был размазан по условиям `if type == "receipt"`. Добавление одного типа задело шесть мест, и в двух из них проверку забыли.

**Объектно-ориентированный подход собирает данные и поведение в класс, а общий родитель убирает копирование.** Документ сам знает, как применить себя к остатку. Цикл проведения больше не спрашивает тип: он вызывает метод у каждого документа.

## Общее и различное в трёх документах

Начнём с полей. У приёмки, отгрузки и списания есть номер, позиция, количество и дата. У списания дополнительно есть причина, у приёмки может быть поставщик, у отгрузки клиент. Общие поля повторяются, различия касаются деталей.

| Документ | Номер | Позиция | Количество | Причина | Влияние на остаток |
|---|---|---|---|---|---|
| Приёмка | есть | есть | есть | нет | увеличивает |
| Отгрузка | есть | есть | есть | нет | уменьшает |
| Списание | есть | есть | есть | есть | уменьшает |

Класс это описание, объект это конкретный документ. `Receipt` описывает, что у приёмки есть номер, позиция и количество. `ПР-201` это объект с номером `ПР-201`, позицией `SKU-1042` и количеством 30. Один класс создаёт сколько угодно объектов, и каждый хранит свои значения. Класс не хранит данные сам по себе, он только задаёт их набор.

Поведение тоже общее: каждый документ умеет применить себя к остатку и описать себя строкой для журнала. Различие в знаке и в дополнительном поле причины.

Отсюда два решения. Первое: общие поля и общий контракт поднимаются в родительский класс `Movement`. Второе: каждый подкласс реализует только то, чем отличается, то есть способ изменения остатка и, при необходимости, описание.

Проверка «является ли» помогает не ошибиться. Приёмка является движением товара, отгрузка является движением, списание является движением. А склад не является движением: он хранит остатки и принимает документы. Склад станет отдельным классом, который содержит движения, но не наследует их.

| Вопрос | Ответ | Что делать |
|---|---|---|
| Общие поля повторяются? | да | вынести в родителя |
| Поведение отличается одной операцией? | да | переопределить метод |
| Отличие только в значении поля? | да | хватит одного класса с полем типа |
| Объект содержит другой объект? | да | композиция, а не наследование |
| Иерархия глубже двух уровней? | да | проверить, не пора ли упростить |

Почему не оставить один класс с полем `type`? Пока типов три и различий мало, такое решение работает. Но поведение уже разное: приёмка прибавляет, отгрузка вычитает, списание требует причину. Если оставить один класс, внутри появится `if type == "receipt"`, потом второй, потом третий. Через год такое условие встретится в проведении, в печати и в отчёте, и каждый новый тип заденет все три места.

Наследование убирает эти условия из вызывающего кода. Проверка «является ли» показывает, где проходит граница: документ является движением, а склад им не является. Если ответ отрицательный, вместо наследования используют композицию.

::gate Что должно быть скрыто внутри класса, чтобы остаток нельзя было испортить?

## Инкапсуляция: состояние меняется только через метод

Остаток склада подчиняется правилу: он не может стать отрицательным. Если код где угодно может записать число напрямую, правило перестаёт действовать. Инкапсуляция закрывает состояние внутри класса и оставляет снаружи только методы, которые это правило соблюдают.

Плохая версия хранит остатки в обычном словаре:

```python
stock = {"SKU-1042": 12}
stock["SKU-1042"] = -5
print(stock)
```

Программа печатает `{'SKU-1042': -5}` и не замечает ошибки. Отрицательный остаток попадёт в отчёт, в заказ и в накладную. Никто не помешал записи, потому что словарь ничего не проверяет.

Класс `Stock` закрывает словарь и даёт два метода: прочитать остаток и изменить его с проверкой.

```python
class Stock:
    def __init__(self):
        self._quantity = {}

    def get(self, sku):
        return self._quantity.get(sku, 0)

    def add(self, sku, delta):
        new_value = self.get(sku) + delta
        if new_value < 0:
            raise ValueError("Остаток не может стать отрицательным: " + sku)
        self._quantity[sku] = new_value
```

Теперь запись `stock._quantity["SKU-1042"] = -5` технически возможна, но нарушает соглашение: имя с подчёркиванием означает внутреннюю деталь. В Python нет запрета на доступ, зато есть договорённость, которую поддерживают инструменты и рецензенты. В C# тот же класс защищён сильнее:

```csharp
class Stock
{
    private readonly Dictionary<string, int> quantity = new Dictionary<string, int>();

    public int Get(string sku)
    {
        int value;
        return quantity.TryGetValue(sku, out value) ? value : 0;
    }

    public void Add(string sku, int delta)
    {
        int newValue = Get(sku) + delta;
        if (newValue < 0)
        {
            throw new InvalidOperationException("Остаток не может стать отрицательным: " + sku);
        }
        quantity[sku] = newValue;
    }
}
```

Поле `quantity` объявлено `private`, поэтому из другого класса к нему не обратиться: компилятор не соберёт программу. Чтение идёт через `Get`, изменение через `Add`. Оба метода можно проверить и изменить в одном месте.

Метод `Add` принимает не новое значение, а изменение. Это не случайность. Если бы он принимал абсолютное число, вызывающий код сначала прочитал бы остаток, потом посчитал новое значение и передал его обратно. Между чтением и записью остаток мог бы измениться другим документом, и одно изменение потерялось бы. Приём «прочитать, посчитать, записать» опасен в многопользовательской системе, а передача изменения оставляет вычисление внутри одного метода.

Правило «остаток не отрицательный» называется инвариантом класса. Инвариант это условие, которое истинно для каждого объекта в любой момент времени. Проверка в `Add` поддерживает инвариант: либо новое значение допустимо и сохраняется, либо операция завершается ошибкой и остаток остаётся прежним. Промежуточного состояния, когда остаток уже испорчен, не возникает.

Инкапсуляция не означает «все поля закрыты». Она означает, что снаружи видно только то, что класс обещает. Если отчёту нужен остаток, он получает его через `Get`. Если нужен список всех позиций, появится отдельный метод, который вернёт копию, а не внутренний словарь.

| Что снаружи | Python | C# |
|---|---|---|
| Прочитать остаток | `stock.get("SKU-1042")` | `stock.Get("SKU-1042")` |
| Изменить остаток | `stock.add("SKU-1042", 30)` | `stock.Add("SKU-1042", 30)` |
| Прямая запись | возможно, но нарушает соглашение | запрещена компилятором |
| Проверка правила | внутри `add` | внутри `Add` |

Свойство `quantity` только для чтения тоже возможно. В Python для этого используют `@property`, в C# свойство с `private set`. Но для склада важнее не чтение, а запрет на запись в обход правила. Поэтому метод `Add` честнее: он называет действие и проверяет его последствия.

## Наследование: общий родитель

Три типа документов имеют общие поля и общий контракт. Родительский класс `Movement` объявляет эти поля и требует, чтобы подкласс реализовал метод `apply`.

```python
class Movement:
    def __init__(self, number, sku, quantity):
        if quantity <= 0:
            raise ValueError("Количество должно быть больше нуля")
        self.number = number
        self.sku = sku
        self.quantity = quantity

    def apply(self, stock):
        raise NotImplementedError("Тип движения должен определить apply")

    def describe(self):
        return self.number + ": " + self.sku + ", " + str(self.quantity)
```

Конструктор проверяет количество один раз для всех типов. Если бы каждая приёмка проверяла его сама, одна из трёх проверок рано или поздно отличалась бы от остальных. Общая проверка в родителе убирает это расхождение.

Метод `apply` в родителе не реализован: он выбрасывает `NotImplementedError` с понятным сообщением. Это значит, что базовый класс задаёт контракт, но не умеет его выполнить. Конкретный документ обязан переопределить метод.

Приёмка и отгрузка отличаются знаком:

```python
class Receipt(Movement):
    def apply(self, stock):
        stock.add(self.sku, self.quantity)


class Shipment(Movement):
    def apply(self, stock):
        stock.add(self.sku, -self.quantity)
```

Списание отличается знаком и дополнительным полем. Его конструктор сначала вызывает родительский, а потом сохраняет причину:

```python
class WriteOff(Movement):
    def __init__(self, number, sku, quantity, reason):
        super().__init__(number, sku, quantity)
        self.reason = reason

    def apply(self, stock):
        stock.add(self.sku, -self.quantity)

    def describe(self):
        return super().describe() + ", причина: " + self.reason
```

`super().__init__` вызывает конструктор `Movement`, поэтому проверка количества и заполнение общих полей происходят в одном месте. Если её пропустить, объект останется без номера и позиции, и ошибка вылезет позже, в журнале.

В C# родитель объявляется абстрактным классом, а метод помечается `abstract`. Компилятор не даст создать объект `Movement` и потребует реализацию в каждом подклассе.

```csharp
abstract class Movement
{
    public string Number { get; private set; }
    public string Sku { get; private set; }
    public int Quantity { get; private set; }

    protected Movement(string number, string sku, int quantity)
    {
        if (quantity <= 0)
        {
            throw new ArgumentOutOfRangeException("quantity", "Количество должно быть больше нуля");
        }
        Number = number;
        Sku = sku;
        Quantity = quantity;
    }

    public abstract void Apply(Stock stock);

    public virtual string Describe()
    {
        return Number + ": " + Sku + ", " + Quantity;
    }
}
```

Свойства с `private set` доступны на чтение всем, а меняются только внутри класса, в этом примере только в конструкторе. Это ещё один уровень инкапсуляции: даже подкласс не может переписать номер документа после создания.

| Элемент | Python | C# |
|---|---|---|
| Родитель | `class Movement:` | `abstract class Movement` |
| Обязательный метод | `raise NotImplementedError` | `abstract void Apply` |
| Вызов родительского конструктора | `super().__init__(...)` | `: base(...)` |
| Переопределение | новый метод с тем же именем | `override` |
| Запрет создания родителя | соглашение | `abstract` |

Наследование даёт немного: общие поля, общую проверку и общий контракт. Всё остальное подкласс делает сам. Если соблазн положить в родителя ещё десять методов «на всякий случай», лучше остановиться: широкий родитель связывает все подклассы и делает изменения дорогими.

Проверка в конструкторе работает и для подклассов. `WriteOff` вызывает `super().__init__`, поэтому документ с нулевым количеством не создастся, даже если проверку забыли в самом подклассе. В C# цепочка конструкторов устроена так же: `: base(number, sku, quantity)` выполняется до тела конструктора подкласса. Если базовый конструктор выбрасывает исключение, объект не создаётся вовсе.

Есть и ограничение: родитель не должен знать о полях подкласса. `Movement` не знает про причину списания и не пытается её описать. Общее описание собирает `describe`, а причину добавляет `WriteOff` через `super().describe()`. Такое разделение позволяет добавлять поля в подклассы, не меняя родителя.

## Полиморфизм и переопределение

Проведение документов это один цикл. Он не знает, приёмка перед ним, отгрузка или списание, и не содержит ни одного `if` по типу.

```python
stock = Stock()
stock.add("SKU-1042", 12)
movements = [
    Receipt("ПР-201", "SKU-1042", 30),
    Shipment("ОТ-118", "SKU-1042", 18),
    WriteOff("СП-07", "SKU-1042", 4, "бой упаковки"),
    ReturnToSupplier("ВП-33", "SKU-1042", 5),
]
for m in movements:
    m.apply(stock)
    print(m.describe(), "-> остаток", stock.get("SKU-1042"))
```

Класс `ReturnToSupplier` добавлен без правки цикла:

```python
class ReturnToSupplier(Movement):
    def apply(self, stock):
        stock.add(self.sku, -self.quantity)
```

Запуск даёт:

```text
ПР-201: SKU-1042, 30 -> остаток 42
ОТ-118: SKU-1042, 18 -> остаток 24
СП-07: SKU-1042, 4, причина: бой упаковки -> остаток 20
ВП-33: SKU-1042, 5 -> остаток 15
```

Числа сходятся с ручной проверкой: 12 плюс 30 равно 42, минус 18 равно 24, минус 4 равно 20, минус 5 равно 15. Каждый документ применился по своему правилу, хотя цикл один и тот же.

Так работает полиморфизм: вызов `m.apply(stock)` выбирает метод по фактическому типу объекта, а не по типу переменной. Переменная `m` имеет тип `Movement`, но объект внутри может быть любым подклассом. Python ищет метод в классе объекта, C# использует таблицу виртуальных методов. Результат один: выполняется переопределённая версия.

Переопределение отличается от перегрузки. Перегрузка это несколько методов с одним именем и разными параметрами в одном классе. Переопределение это метод подкласса с той же сигнатурой, что у родителя. В C# переопределение помечают словом `override`, и компилятор проверяет, что в родителе есть виртуальный или абстрактный метод с такой сигнатурой.

Если забыть `override` и объявить метод с тем же именем заново, компилятор выдаст предупреждение, а вызов через базовый тип попадёт в родительскую версию. Такое сокрытие метода почти всегда ошибка: автор думает, что заменил поведение, а цикл продолжает вызывать старое. Поэтому в C# слово `override` обязательно, а в Python полезно проверять, что подкласс действительно переопределил метод, а не создал новый с опечаткой в имени.

В C# цикл выглядит так:

```csharp
Stock stock = new Stock();
stock.Add("SKU-1042", 12);
Movement[] movements = {
    new Receipt("ПР-201", "SKU-1042", 30),
    new Shipment("ОТ-118", "SKU-1042", 18),
    new WriteOff("СП-07", "SKU-1042", 4, "бой упаковки"),
    new ReturnToSupplier("ВП-33", "SKU-1042", 5)
};
foreach (Movement m in movements)
{
    m.Apply(stock);
    Console.WriteLine(m.Describe() + " -> остаток " + stock.Get("SKU-1042"));
}
```

Вывод совпадает с Python строка в строку. Массив объявлен с типом `Movement`, поэтому в него можно положить любой подкласс. Вызов `m.Apply` уходит в реализацию конкретного класса.

Выбор метода происходит во время выполнения, а не при сборке. Компилятор видит только тип переменной `Movement` и проверяет, что у этого типа есть метод `Apply`. Какой именно код выполнится, решает объект. Если в массив положили `Shipment`, вызывается `Shipment.Apply`; если `WriteOff`, вызывается `WriteOff.Apply`. Это и есть динамическое связывание.

Отсюда правило: не проверяйте тип вручную. Запись `if isinstance(m, Shipment)` в Python или `if (m is Shipment)` в C# внутри цикла означает, что различие не перенесли в класс. Она работает, но при добавлении `ReturnToSupplier` её придётся править, и одна из веток останется без обновления. Полиморфизм убирает саму возможность такой ошибки: цикл не знает типов.

| Строка вызова | Фактический объект | Какой метод выполнится |
|---|---|---|
| `m.apply(stock)` | `Receipt` | `Receipt.apply`, прибавляет количество |
| `m.apply(stock)` | `Shipment` | `Shipment.apply`, вычитает количество |
| `m.apply(stock)` | `WriteOff` | `WriteOff.apply`, вычитает количество |
| `m.describe()` | `WriteOff` | `WriteOff.describe`, добавляет причину |
| `m.describe()` | `Receipt` | `Movement.describe`, общее описание |

Строка `WriteOff.describe` показывает ещё одну возможность: переопределённый метод может вызвать родительский через `super().describe()` и добавить к нему причину. Так общее описание остаётся в одном месте, а отличие не дублируется.

Полиморфизм окупается, когда типов становится больше. Отчёт по движениям, журнал, API и печать накладной используют один контракт. Новый тип документа добавляет один класс и одну строку в список, а не правит пять условий в четырёх файлах.

## Когда иерархия не нужна

Иерархия это инструмент, а не признак хорошего кода. Иногда один класс с полем типа проще и надёжнее.

Первое условие: различие только в данных. Если приёмка и отгрузка отличаются одним полем `direction` со значениями плюс и минус, отдельные классы не нужны. Достаточно одного класса `Movement` с полем направления и проверкой допустимых значений.

Второе условие: различие в одной строке поведения. Если два класса отличаются единственным `if`, общий родитель добавит больше кода, чем уберёт. Лучше оставить один класс с параметром.

Третье условие: иерархия глубже двух уровней. `Movement`, `Receipt`, `ReturnReceipt` с особым правилом уже трудно читать. Часто средний уровень можно заменить композицией: документ содержит правило проведения, а не наследует его.

Четвёртое условие: подкласс нарушает контракт родителя. Если `FrozenShipment` наследует `Shipment`, но ничего не вычитает, цикл проведения будет считать, что остаток изменился, а он останется прежним. Это нарушение принципа подстановки: подкласс должен вести себя как родитель. Лучше вынести замороженную отгрузку в отдельный тип, который не притворяется обычной.

| Признак | Иерархия уместна | Иерархия не нужна |
|---|---|---|
| Общие поля и проверки | да | нет |
| Разное поведение в нескольких методах | да | нет |
| Отличие одним значением | нет | один класс с полем |
| Глубина больше двух | проверить | заменить композицией |
| Подкласс игнорирует контракт | нет | отдельный тип |

Композиция часто проще наследования. Склад содержит список движений, отчёт содержит склад, API содержит отчёт. Это отношение «содержит», а не «является». Оно не связывает классы общей реализацией и позволяет менять части независимо.

Переход от условий к иерархии стоит делать не сразу, а когда типов становится больше двух и различия касаются поведения, а не только данных. На трёх документах выигрыш уже виден: цикл проведения не меняется, а новый тип добавляется одним классом. На одном типе иерархия только усложнит код.

Проверка перед добавлением родителя занимает несколько строк. Выпишите поля и методы, которые совпадают у классов. Если совпадают поля, но не поведение, хватит общего класса данных. Если совпадает и поведение, родитель оправдан. Если совпадает только одно поле, родитель не нужен: хватит передать это поле в конструктор.

::/gate

## Типичные ошибки

**Ошибка первая: базовый метод молча ничего не делает.** Если `apply` в родителе содержит `pass`, забытый подкласс проведёт документ без изменения остатка. Симптом: документ есть, остаток прежний. Лечение: `raise NotImplementedError` в Python и `abstract` в C#.

**Ошибка вторая: публичное поле вместо метода.** Симптом: отрицательный остаток в отчёте. Причина: запись в обход проверки. Лечение: закрытое поле и метод `add` с правилом.

**Ошибка третья: копирование метода вместо переопределения.** Симптом: в одном подклассе формула исправлена, в другом нет. Причина: `describe` скопирован целиком. Лечение: вынести общее в родителя и вызывать его через `super` или `base`.

**Ошибка четвёртая: подкласс нарушает контракт.** Симптом: цикл ждёт изменения остатка, а его нет. Причина: подкласс переопределил метод с другим смыслом. Лечение: проверить принцип подстановки и вынести особый случай в отдельный тип.

**Ошибка пятая: родитель знает про всех потомков.** Симптом: в базовом классе появляется `if isinstance(self, Shipment)`. Причина: полиморфизм не использован. Лечение: перенести различие в переопределённый метод подкласса.

> [!PITFALL] Наследование ради переиспользования
> Если класс наследует другой только чтобы взять один метод, это слабая причина. Наследование означает «является», а не «удобно взять кусок кода».

## Итоги

- Класс собирает данные и поведение, а общий родитель убирает копирование между похожими типами.
- Инкапсуляция закрывает состояние и оставляет снаружи методы, которые соблюдают правило.
- Наследование выносит общие поля и проверки в родителя, а различия оставляет подклассам.
- Полиморфизм позволяет одному циклу обрабатывать документы разных типов через общий контракт.
- Переопределение заменяет метод родителя, перегрузка добавляет вариант с другими параметрами.
- Иерархия не нужна, если различие только в данных, в одной строке или если подкласс нарушает контракт.
