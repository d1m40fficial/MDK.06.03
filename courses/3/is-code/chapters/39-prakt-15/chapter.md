## Цель работы

Научиться проверять код тестами так, чтобы проверка находила дефект, а не подтверждала заранее известный ответ. Вы соберёте небольшой проект `sklad-plus`, напишете модульные тесты для расчёта свободного остатка, добавите тесты для маршрута API, запустите набор и разберёте падающую проверку. Итог работы это исправленный модуль, набор тестов и короткий отчёт о дефекте, в котором причина названа по наблюдениям, а не угадана.

Отдельная задача практики состоит в том, чтобы отличить тест, который действительно проверяет поведение, от теста, который проходит всегда. Для этого вы намеренно сломаете код и посмотрите, какие проверки это заметят.

Работа идёт по циклу: написать проверку, запустить набор, прочитать отчёт, изменить код, повторить. В отчёте фиксируются не только итоговые числа, но и ход рассуждения: какой вход вы выбрали, что ожидали увидеть и почему фактический результат оказался другим. Именно эта запись показывает, что дефект найден, а не случайно исправлен.

Результат практики оценивается по тому, умеет ли набор тестов обнаруживать поломку. Красивый отчёт с зелёными галочками без падающего и восстановленного прогона не считается доказательством. Поэтому сохраняйте промежуточные результаты: отчёт до исправления, вывод покрытия и таблицу мутационной проверки.

## Оборудование и программное обеспечение

- Персональный компьютер с Python 3.11 или новее.
- VS Code с расширением Python и встроенным терминалом.
- Пакеты `pytest`, `coverage` и `flask`, установленные в виртуальное окружение проекта.
- Папка проекта `.../prakt-15` с подпапкой `tests`.
- Текстовый редактор для отчёта, например Word или LibreOffice Writer.

Внешние архивы и готовые шаблоны не нужны. Все файлы создаются по ходу работы, данные для проверки приведены в тексте.

Пакеты ставят в виртуальное окружение проекта, а не в общую установку Python. Общая установка может содержать другую версию `pytest` или `flask`, и тогда команды будут вести себя иначе на разных машинах. Виртуальное окружение создают командой `python -m venv .venv`, активируют в терминале и только после этого устанавливают пакеты. В VS Code интерпретатор выбирают из папки `.venv`, чтобы редактор и терминал использовали одно окружение.

## Краткие теоретические сведения

Тест состоит из подготовки данных, вызова проверяемого кода и утверждения. Утверждение сравнивает фактический результат с ожидаемым и падает при расхождении. В Python тесты чаще всего пишут для `pytest`: он находит файлы `test_*.py` и функции `test_*`, поэтому не нужно регистрировать проверки вручную.

Имя теста это часть отчёта. Когда проверка падает, pytest печатает имя функции, строку утверждения и значения. Если имя `test_1`, разбираться придётся по коду; если `test_reserved_equal_stock_leaves_nothing`, сразу понятно, какое поведение нарушено. Поэтому имена пишут как утверждения, а не как номера.

Отчёт pytest читают по смысловым частям. Сначала находят блок `FAILURES` с именем упавшего теста, затем строку утверждения, где показаны ожидаемое и фактическое значения, и только потом смотрят трассировку. Трассировка полезна, когда ошибка возникла внутри вызываемой функции, но начинать с неё не стоит: она длиннее и отвлекает от главного расхождения.

Модульный тест проверяет одну функцию в изоляции. Интеграционный тест проверяет связку: функцию и базу, маршрут и хранилище, разбор файла и запись результата. Для этой работы достаточно модульных тестов на функцию и интеграционных тестов маршрута через тестовый клиент Flask, который не поднимает настоящий сетевой сервер.

Тестовый клиент вызывает приложение напрямую и возвращает объект ответа с кодом состояния, заголовками и телом. Это быстрее и стабильнее, чем запускать сервер на порту: не нужно ждать запуска, искать свободный порт и закрывать процесс после проверки. Настоящий сервер всё равно проверяют отдельно, но для проверки маршрута и формата JSON достаточно клиента.

Граничные значения выбирают на переходах между классами. Для свободного остатка важны нулевой резерв, резерв, равный остатку, резерв больше остатка и отрицательный вход. Для резервирования важны запрос меньше свободного остатка, запрос, равный ему, и запрос на единицу больше. Середина диапазона проверяется одним тестом, границы требуют отдельных.

Покрытие показывает, какие строки и ветви выполнились при прогоне. Оно не доказывает правильность значений, но помогает найти непроверенные участки. Мутационная проверка отвечает на другой вопрос: упадёт ли тест, если намеренно изменить код. Тест, который проходит после поломки, бесполезен.

Покрытие и мутационная проверка дополняют друг друга. Покрытие может быть высоким, а тесты при этом проверять только факт возврата числа. Мутация показывает, замечает ли набор изменение поведения. В этой работе вы выполните обе проверки и сравните их выводы: сначала посмотрите, все ли строки выполнены, затем сломайте код и убедитесь, что хотя бы один тест это обнаружил.

| Понятие | Что означает в этой работе |
|---|---|
| Утверждение | сравнение результата функции с ожидаемым числом |
| Граничное значение | вход на переходе: ноль, равенство, превышение на единицу |
| Падающий тест | проверка, которая обнаружила расхождение |
| Покрытие | доля выполненных строк и ветвей |
| Дефект | конкретная строка, из-за которой результат неверен |

## Ход работы

### Шаг 1. Соберите проект и запустите первый тест

Создайте папку `.../prakt-15` и подпапку `tests`. В корне проекта создайте файл `stock.py` с двумя функциями.

Структура проекта упрощена: код лежит в корне, тесты в отдельной папке. Разделение помогает не смешивать проверки с рабочими файлами и запускать набор одной командой. В большом проекте код оказался бы в `src`, но для двух модулей достаточно корня.

```python
def available_qty(stock: int, reserved: int) -> int:
    """Свободный остаток: сколько единиц можно отгрузить."""
    if stock < 0 or reserved < 0:
        raise ValueError("количество не может быть отрицательным")
    return max(stock - reserved, 0)

def free_after_reserve(stock: int, reserved: int, requested: int) -> int:
    """Свободный остаток после нового резервирования requested единиц."""
    if requested <= 0:
        raise ValueError("количество должно быть положительным")
    if requested > stock - reserved:
        raise ValueError("недостаточно товара")
    return stock - requested
```

Первая функция возвращает то, что можно отгрузить с учётом уже зарезервированного товара. Вторая должна вернуть свободный остаток после нового резервирования. Контракт второй функции записан в строке документации, и именно его проверяют тесты.

Контракт это обещание функции перед вызывающим кодом: какие входы допустимы, что считается ошибкой и что возвращается. Тест проверяет контракт, а не конкретную реализацию. Если завтра формулу перепишут, тест должен остаться зелёным при том же поведении и упасть, если поведение изменилось. Поэтому в тестах используют числа из предметной области, а не копируют внутренние переменные функции.

Рядом создайте файл `api.py` с небольшим сервисом на Flask. Он отдаёт остаток по артикулу.

```python
from flask import Flask, jsonify

app = Flask(__name__)

STOCK = {
    "SKU-1042": {"title": "Перфоратор", "qty": 40, "reserved": 10},
    "SKU-1043": {"title": "Шуруповёрт", "qty": 7, "reserved": 2},
}

@app.get("/api/stock/<sku>")
def get_stock(sku: str):
    row = STOCK.get(sku)
    if row is None:
        return jsonify({"error": "not found"}), 404
    return jsonify({
        "sku": sku,
        "title": row["title"],
        "available": max(row["qty"] - row["reserved"], 0),
    })
```

Установите пакеты в виртуальное окружение проекта. Команда ниже показана на примере `pytest`; для `coverage` и `flask` она выглядит так же, меняется только имя пакета.

```text
python -m pip install pytest
python -m pip install coverage flask
```

Создайте файл `tests/test_stock.py` с одной проверкой. Это образец, по которому дальше нужно писать остальные тесты.

```python
from stock import available_qty

def test_available_is_stock_minus_reserved():
    assert available_qty(120, 30) == 90
```

Запустите один файл:

```text
python -m pytest -q tests/test_stock.py
```

```text
.                                                                        [100%]
1 passed in 0.02s
```

Флаг `-q` включает краткий вывод. Путь `tests/test_stock.py` указывает, что запускать нужно только этот файл. Убедитесь, что тест найден и пройден, прежде чем добавлять следующие.

Если команда `python -m pytest` сообщает, что модуль не найден, проверьте, активировано ли виртуальное окружение и установлен ли пакет. В VS Code интерпретатор выбирают командой «Python: Select Interpreter» и указывают файл из `.venv`. После смены интерпретатора терминал нужно открыть заново, иначе он продолжит использовать старое окружение.

| 120 | 30 | 90 | обычный остаток с резервом |
|  |  |  |  |

В набор включите нулевой резерв, резерв, равный остатку, резерв больше остатка и отрицательный вход. Для каждого случая напишите отдельную функцию с именем, которое объясняет ожидание. Не объединяйте пять случаев в один тест: при падении будет непонятно, какой именно вход сломался.

Если внутри класса есть особое условие, например проверка на отрицательность, для него создают отдельный класс.

Запустите файл и запишите число пройденных проверок. Если тест падает, прочитайте строку с утверждением: в ней указаны вход, ожидаемое и фактическое значения. Не меняйте ожидание под фактический результат, пока не убедились, что ошибка не в функции.

### Шаг 3. Добавьте проверку ошибок

Отрицательные значения недопустимы, поэтому функция должна выбрасывать `ValueError`. Проверка исключения записывается через `pytest.raises`:

```python
import pytest
from stock import available_qty

def test_negative_stock_is_rejected():
    with pytest.raises(ValueError):
        available_qty(-1, 0)
```

Добавьте такие же проверки для отрицательного резерва и для отрицательного запроса в `free_after_reserve`. Заполните таблицу: вход, ожидаемое исключение, фактическое поведение.

| Функция | Вход | Ожидаемое исключение | Фактически |
|---|---|---|---|
| `available_qty` | -1, 0 | `ValueError` |  |
|  |  |  |  |
|  |  |  |  |

Проверка исключения не должна быть слишком широкой. `pytest.raises(Exception)` поймает любую ошибку, включая опечатку в имени переменной, и тест пройдёт там, где программа на самом деле сломана. Указывайте конкретный тип.

Проверяйте не только тип исключения, но и то, что операция не изменила данные. Для функции без побочных эффектов достаточно типа. Для функции, которая пишет в базу или файл, после исключения проверяют, что запись не появилась. Иначе тест подтвердит отказ, но пропустит частично выполненную операцию.

### Шаг 4. Проверьте функцию резервирования и найдите падающий тест

Для `free_after_reserve` напишите пять проверок по контракту: обычный запрос при ненулевом резерве, нулевой резерв, запрос, равный свободному остатку, запрос больше свободного остатка и неположительный запрос. Одна из проверок обнаружит расхождение.

Пример проверки, с которой можно начать:

from stock import free_after_reserve

def test_free_after_reserve_subtracts_reserved():

Запустите весь набор:

Пока не исправляйте функцию. Запишите в таблицу вход, ожидаемый результат, фактический результат и имя упавшего теста. Подумайте, какое число должно получиться по контракту функции и почему фактическое значение отличается от него.

| Вход | Ожидалось | Получено | Упавший тест |
|---|---|---|---|
| 40, 10, 25 | 5 | 15 |  |
|  |  |  |  |

Пока в таблице одна строка, этого достаточно, чтобы увидеть расхождение. Но одного примера мало для вывода о причине: возможно, функция неверно считает только при ненулевом резерве, а при нулевом работает. Добавьте второй запуск с резервом 0 и тем же запросом. Если результат совпадает с ожиданием, подозрение сужается до строки, где участвует `reserved`.

Падающий тест показывает расхождение, но не называет строку. Чтобы увидеть значения внутри функции, поставьте остановку перед возвратом. | Наблюдение | Значение | Вывод |
|---|---|---|

Команда `where` показывает, откуда вызвана функция. В этой работе вызов идёт из теста, поэтому стек короткий, но привычка смотреть на вызывающий кадр пригодится в большом проекте. Если функция получает неверный аргумент, причина может быть не в ней, а в том месте, где её вызвали.

### Шаг 6. Напишите тесты для маршрута API

Маршрут проверяют тестовым клиентом Flask. Он вызывает приложение в памяти и не требует запускать сервер и открывать порт. Образец проверки кода состояния:

```python
from api import app

client = app.test_client()

def test_stock_returns_200():
    response = client.get("/api/stock/SKU-1042")
    assert response.status_code == 200
```

Добавьте проверки тела ответа и неизвестного артикула. Заполните таблицу: запрос, ожидаемый код, ожидаемое поле, фактический результат.

| Запрос | Код | Что проверить в теле | Фактически |
|---|---|---|---|
| `/api/stock/SKU-1042` | 200 | `available` равно 30 |  |
|  |  |  |  |
|  |  |  |  |

Для тела используйте `response.get_json()`. Проверьте, что для известного артикула возвращаются `sku`, `title` и `available`, а для неизвестного приходит код 404 и поле `error`. Отдельно проверьте, что `available` не отрицателен, если резерв больше остатка: для этого можно временно добавить в `STOCK` строку с такими данными или проверить существующую логику на подготовленных значениях.

Проверка только кода состояния недостаточна. Маршрут может вернуть 200 с пустым телом или с полем, которое называется иначе. Поэтому в тесте фиксируют код, наличие нужных полей и хотя бы одно значение, которое можно посчитать вручную. Для `SKU-1042` свободный остаток равен 40 минус 10, то есть 30. Это число не зависит от реализации и останется ожидаемым при любой правильной формуле.

Запустите файл с тестами API и запишите результат. Если маршрут возвращает 500 вместо 404, прочитайте журнал Flask: в нём будет трассировка с файлом и строкой.

### Шаг 7. Прогоните набор и измерьте покрытие

Запустите все тесты подробно:

```text
python -m pytest -v
```

Запишите общее число проверок, число пройденных и время выполнения. Затем соберите покрытие:

```text
python -m coverage run --branch -m pytest
python -m coverage report -m
```

Флаг `--branch` включает подсчёт ветвей, а `-m pytest` запускает тесты под наблюдением `coverage`. Команда `report -m` печатает таблицу и показывает номера строк, которые не выполнились. Если запустить `coverage` без `--branch`, отчёт покажет только строки и не заметит непроверенный исход условия.

Заполните таблицу по выводу команды.

| Модуль | Инструкции | Пропущено | Покрытие | Непройденные строки |
|---|---|---|---|---|
| `stock.py` |  |  |  |  |
| `api.py` |  |  |  |  |

Столбец `Stmts` показывает число инструкций, `Miss` число непройденных, `Cover` долю выполненных, `Missing` номера строк, которые не выполнились. Для `stock.py` важно, чтобы выполнились обе ветви проверки на отрицательные значения и строка с `max`. Если строка с `max` не выполнялась, значит, тесты ни разу не передали резерв больше остатка.

Если в `stock.py` остались непройденные строки, объясните, почему. Например, ветка с отрицательным значением может не выполняться, если тест на ошибку написан через `pytest.raises`, но само тело проверки не доходит до нужной строки. Для каждой непройденной строки либо добавьте тест, либо запишите, почему она недостижима.

### Шаг 8. Проверьте, что тесты умеют падать

Хороший набор должен замечать поломку. Временно измените `available_qty`: уберите `max` и оставьте `return stock - reserved`. Запустите тесты и запишите, какая проверка упала. Затем верните правильную строку.

Вторая поломка: в `free_after_reserve` замените условие `requested > stock - reserved` на `requested >= stock - reserved`. Снова запустите набор и запишите, какой тест заметил изменение. Верните исходное условие.

| Поломка | Какой тест упал | Что это доказывает |
|---|---|---|
| убрали `max` |  |  |
| заменили `>` на `>=` |  |  |

Если после поломки ни один тест не упал, набор не проверяет этот участок. Вернитесь к шагу 2 и добавьте граничный случай. Если упало несколько тестов, это нормально: важно, что хотя бы один указывает на нужное поведение.

Мутационная проверка не требует специального инструмента. Достаточно вручную внести одну поломку, запустить набор и вернуть строку обратно. Главное правило: менять только одно место за раз, иначе непонятно, какая поломка вызвала падение. После проверки убедитесь, что код вернулся к рабочему состоянию, и снова получите зелёный прогон.

### Шаг 9. Оформите отчёт о дефекте

Соберите отчёт по структуре: идентификатор, входные данные, ожидаемый результат, фактический результат, среда, причина, строка кода, исправление и тест, который ловит дефект. Один абзац отведите на то, почему дефект не был виден на обычном примере с нулевым резервом.

| Поле | Значение |
|---|---|
| Идентификатор |  |
| Вход |  |
| Ожидалось |  |
| Получено |  |
| Причина |  |
| Строка |  |
| Исправление |  |
| Тест |  |

Причина должна быть проверяемой. Формулировка «функция считает неправильно» ничего не объясняет. Формулировка «в строке возврата сумма округляется до целого, поэтому дробная часть теряется» называет место и механизм. По ней можно проверить исправление и написать тест, который не даст дефекту вернуться.

Отдельно объясните, почему дефект не был виден на примере с нулевым резервом. Такой разбор показывает, что проверка одного удачного случая не заменяет границы. Если в отчёте сказано только «исправил строку», причина не доказана: следующий разработчик может вернуть прежнюю формулу, и набор снова её пропустит.

Приложите снимок падающего прогона и снимок финального зелёного прогона. На снимке должны быть видны команда запуска, имя теста, строка утверждения и итоговая строка с числом пройденных проверок. Снимок только с зелёной галочкой без команды не подтверждает, что запускался нужный набор.

## Требования к отчёту

Отчёт оформляется в Word или LibreOffice Writer на 4-6 страниц. В нём должны быть цель работы, состав проекта, таблица проверок с ожидаемыми результатами, отчёт о дефекте, таблица покрытия и таблица мутационной проверки. Каждая таблица сопровождается одним-двумя предложениями вывода.

В тексте отчёта укажите команды запуска и объясните, что означает каждый столбец отчёта pytest. Не вставляйте весь вывод целиком, если он длиннее двадцати строк: оставьте строку запуска, упавший тест и итог. Для покрытия приведите таблицу и объясните, какие строки остались непройденными.

Снимки прикладывайте к тем местам, где они подтверждают вывод. Снимок падающего прогона должен показывать команду, имя теста, строку утверждения с ожидаемым и фактическим значением, а снимок финального прогона итоговую строку с числом пройденных проверок. Если на снимке нет команды, невозможно понять, какой набор запускался и с какими настройками.

## Что сдать

- файл `stock.py` с исправленной функцией резервирования;
- файл `api.py` с маршрутом выдачи остатка;
- файлы `tests/test_stock.py` и `tests/test_api.py` с набором проверок;
- отчёт pytest с падающим и финальным зелёным прогоном;
- таблицу покрытия с объяснением непройденных строк;
- отчёт о дефекте на 1-2 страницы с причиной и исправлением.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: написаны проверки для обычного случая, всех границ и ошибок; падающий тест найден запуском, причина дефекта названа по наблюдениям, исправление минимально и подтверждено зелёным прогоном; покрытие измерено, непройденные строки объяснены; мутационная проверка показывает, что тесты умеют падать; отчёт полный.
- **4**: набор проверок полный, дефект найден и исправлен, но одна граница не проверена или причина описана общими словами без указания строки; покрытие и мутационная проверка выполнены.
- **3**: проверки покрывают только удачный случай, дефект найден чтением кода, а не падающим тестом; исправление есть, но отчёт не содержит покрытия или объяснения причины.
- **2**: работа не выполнена или набор тестов не запускается.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
