## Отгрузка, которая проходит через сеть

Кладовщик в Туле нажимает в «Склад+» кнопку «Отгрузить». На экране появляется номер накладной, и через секунду документ уже виден менеджеру в Москве. Между нажатием и номером происходит разговор двух программ: браузер отправляет запрос, сервер проверяет остатки, записывает накладную и возвращает ответ. Ни кладовщик, ни менеджер этот разговор не видят, но именно он определяет, будет ли отгрузка принята, отклонена или зависнет.

Такой разговор ведётся по HTTP. **HTTP это протокол обмена сообщениями, в котором клиент отправляет запрос, а сервер возвращает ответ.** Клиентом может быть браузер, мобильное приложение, скрипт на Python, коллекция Postman или другое приложение. Сервер не знает, кто именно к нему обратился, и не хранит состояние разговора между запросами. Каждый запрос несёт всё, что нужно для его выполнения: адрес, метод, данные и сведения о клиенте.

Из этого свойства, которое называют отсутствием состояния, вытекает многое. Сервер может обслуживать тысячи клиентов, не помня каждого. Запрос можно повторить, и он не станет «продолжением» прошлого разговора. Но за это приходится платить: клиент обязан каждый раз предъявлять токен, а сервер обязан проверять его заново. Если приложение рассчитывает, что сервер «помнит» предыдущий шаг, оно ломается при первом же перезапуске или переходе на другой экземпляр сервера.

API информационной системы это набор таких сообщений, заранее описанных и обещанных другой стороне. В «Склад+» API открывает товары, остатки, приёмку и отгрузку для сайта, мобильного приложения и будущей интеграции с бухгалтерией. Пока API не описан, каждая команда придумывает свой разговор и ломает чужой при первом изменении.

## Запрос и ответ как сообщения

Запрос HTTP состоит из четырёх частей. Первая строка называет метод, адрес и версию протокола. Затем идут заголовки, каждый на своей строке в виде «имя: значение». Пустая строка отделяет заголовки от тела. Тело содержит данные, если они нужны: например, JSON нового товара.

```http
GET /api/products/42 HTTP/1.1
Host: 127.0.0.1:5055
Accept: application/json
Authorization: Bearer <токен>
```

Ответ устроен похоже. Первая строка содержит версию протокола, код состояния и короткое пояснение. Дальше идут заголовки, пустая строка и тело ответа. Тело может быть пустым, если серверу нечего добавить: например, после успешного удаления.

```http
HTTP/1.1 200 OK
Server: Werkzeug/3.1.9 Python/3.13.14
Content-Type: application/json
Content-Length: 132

{"category":"Инструмент","id":42,"price":12450.0,"sku":"SKU-1002","stock":4,"title":"Шуруповёрт Makita DF333D"}
```

Версия протокола важна не сама по себе, а тем, какие возможности доступны. HTTP/1.1 передаёт заголовки текстом и держит соединение открытым для нескольких запросов. HTTP/2 сжимает заголовки и мультиплексирует запросы в одном соединении. HTTP/3 работает поверх QUIC и меняет поведение при потерях пакетов. Для разработчика API важнее не номер версии, а то, что структура сообщения остаётся одинаковой: метод, адрес, заголовки, тело, код ответа.

## Метод называет действие

Метод отвечает на вопрос «что сделать с ресурсом». Один и тот же адрес с разными методами означает разные операции, поэтому метод нельзя выбирать по привычке. В «Склад+» четыре основных метода покрывают почти весь обмен.

| Метод | Что означает | Пример в «Склад+» | Безопасный | Идемпотентный |
|---|---|---|---|---|
| GET | получить представление ресурса | `GET /api/products/42` | да | да |
| POST | создать ресурс или запустить операцию | `POST /api/products` | нет | нет |
| PUT | заменить ресурс целиком | `PUT /api/products/42` | нет | да |
| PATCH | изменить часть полей | `PATCH /api/products/42` | нет | нет |
| DELETE | удалить ресурс | `DELETE /api/products/42` | нет | да |
| HEAD | получить только заголовки | `HEAD /api/products/42` | да | да |
| OPTIONS | узнать допустимые методы | `OPTIONS /api/products/42` | да | да |

Безопасный метод не меняет состояние сервера. GET, HEAD и OPTIONS можно вызывать сколько угодно раз, и данные от этого не изменятся. Идемпотентный метод даёт один и тот же результат при повторе: если дважды отправить `DELETE /api/products/42`, первый запрос удалит товар, второй вернёт 404, но состояние склада останется тем же. POST не идемпотентен: два одинаковых запроса создадут две накладные, и это правильное поведение, потому что клиент действительно просил две операции.

Разницу между PUT и PATCH удобно увидеть на товаре. PUT присылает полное представление: если в теле нет поля `stock`, сервер обязан обнулить или отклонить запрос, потому что клиент заменил ресурс целиком. PATCH присылает только изменение: `{"stock": 10}` меняет остаток и не трогает название и цену. В учебном API чаще достаточно POST и PATCH, а PUT оставляют для случаев, когда клиент действительно владеет полной карточкой.

GET не должен менять данные. Это правило кажется очевидным, пока в проекте не появляется маршрут `GET /api/products/42/delete`, который удаляет товар. Браузер может открыть такой адрес заранее, поисковый робот обойдёт ссылку, а служба мониторинга проверит доступность и удалит запись. Симптом неприятный: остатки исчезают без действий пользователя, и в журнале нет ни одного POST.

## Адрес называет ресурс

Адрес API состоит из схемы, хоста, порта, пути и параметров запроса. Схема и хост отвечают за соединение, путь называет ресурс, параметры уточняют выборку.

```text
http://127.0.0.1:5055/api/v1/products/42?fields=sku,title,stock
\___/   \_________/ \__/ \_________/ \_______________/
схема      хост     порт     путь        параметры
```

Путь строят из существительных во множественном числе: `products`, `warehouses`, `shipments`. Идентификатор ресурса идёт отдельным сегментом: `/api/v1/products/42`. Вложенный ресурс показывает принадлежность: `/api/v1/warehouses/3/products` означает товары на складе номер 3, а не «действие склада над товаром». Глаголы в пути не нужны: метод уже говорит, что делать. Адрес `/api/v1/getProducts` повторяет метод словом и создаёт второй способ сделать то же самое.

Параметры запроса идут после знака вопроса и разделяются амперсандом. Они подходят для фильтра, сортировки, поиска и постраничного вывода, потому что не меняют сам ресурс, а уточняют его представление.

| Задача | Пример адреса |
|---|---|
| Все товары | `GET /api/v1/products` |
| Товар по идентификатору | `GET /api/v1/products/42` |
| Фильтр по категории | `GET /api/v1/products?category=Инструмент` |
| Поиск по названию | `GET /api/v1/products?q=перфоратор` |
| Сортировка по остатку | `GET /api/v1/products?sort=stock&order=asc` |
| Страница вывода | `GET /api/v1/products?limit=20&offset=40` |
| Товары склада | `GET /api/v1/warehouses/3/products` |
| Накладные со статусом | `GET /api/v1/shipments?status=new` |

Версия в пути (`/api/v1/`) нужна не для красоты. Когда меняется формат поля или правило фильтра, старые клиенты продолжают работать на прежней версии, а новые подключаются к следующей. Версия в заголовке тоже возможна, но в учебном проекте путь читается проще и виден в журнале сервера.

## Заголовки описывают сообщение

Заголовок это пара «имя: значение», которая уточняет, как читать тело и что делать с ответом. Заголовки не заменяют данные, но без них стороны понимают друг друга неправильно.

| Заголовок | Где встречается | Зачем нужен |
|---|---|---|
| `Host` | запрос | какой сервер выбран, важно при нескольких сайтах на одном адресе |
| `Accept` | запрос | какой формат ответа готов принять клиент |
| `Content-Type` | запрос и ответ | как разобрать тело: JSON, форма, текст, файл |
| `Content-Length` | запрос и ответ | сколько байт в теле |
| `Authorization` | запрос | кто обращается и каким способом подтверждён вход |
| `Location` | ответ | адрес созданного ресурса или адрес перенаправления |
| `ETag` | ответ | версия представления для кеша и защиты от гонок |
| `Cache-Control` | ответ | можно ли кешировать ответ и на сколько |
| `User-Agent` | запрос | какая программа и версия обратилась |

Пара `Content-Type` и `Accept` чаще всего вызывает путаницу. `Content-Type` описывает тело, которое отправитель положил в сообщение. `Accept` описывает формат, который клиент хочет получить в ответе. Клиент может отправить JSON и попросить JSON, а может отправить форму и попросить PDF. Если сервер вернул JSON, но указал `Content-Type: text/html`, клиент попробует разобрать его как страницу и получит ошибку разбора, хотя данные пришли целыми.

`Authorization: Bearer <токен>` говорит, что клиент предъявляет токен доступа. Сервер проверяет подпись и срок действия, а затем решает, хватает ли прав на операцию. Заголовок не должен попадать в журнал целиком: токен в текстовом файле журнала равносилен паролю на стикере.

`Location` появляется в ответе на создание ресурса. Сервер возвращает `201 Created` и адрес новой карточки, чтобы клиент не угадывал идентификатор. Тот же заголовок используют при перенаправлении, но там он означает другой адрес, а не созданный объект.

`ETag` и `Cache-Control` управляют кешем. Если представление товара не изменилось, сервер может ответить `304 Not Modified` и не передавать тело повторно. Для склада это экономит трафик на справочниках, которые меняются редко. Для остатков, которые меняются каждую минуту, кеш нужно настраивать осторожно, иначе менеджер увидит устаревшее число.

## Код состояния это часть контракта

Код состояния отвечает на вопрос «чем закончилась обработка». Он стоит в первой строке ответа и виден клиенту раньше тела. По первой цифре коды делятся на пять групп.

| Группа | Смысл | Примеры |
|---|---|---|
| 1xx | промежуточный ответ | 100 Continue |
| 2xx | запрос выполнен | 200 OK, 201 Created, 204 No Content |
| 3xx | нужно обратиться по другому адресу | 301 Moved Permanently, 304 Not Modified |
| 4xx | ошибка на стороне клиента | 400, 401, 403, 404, 405, 409, 422, 429 |
| 5xx | ошибка на стороне сервера | 500, 502, 503 |

Внутри групп важно различать конкретные коды, иначе клиент не поймёт, что исправлять.

| Код | Когда возвращают | Что видит клиент |
|---|---|---|
| 200 | чтение или изменение выполнено | данные или подтверждение |
| 201 | ресурс создан | данные ресурса и заголовок `Location` |
| 204 | выполнено, тела нет | пустой ответ после удаления |
| 304 | представление не изменилось | пустое тело, клиент берёт кеш |
| 400 | запрос синтаксически неверен | описание ошибки и поле |
| 401 | клиент не подтвердил вход | требование авторизации |
| 403 | вход подтверждён, прав нет | причина отказа |
| 404 | ресурс не найден | имя ресурса или адрес |
| 405 | метод не разрешён для адреса | заголовок `Allow` |
| 409 | конфликт с текущим состоянием | например, повторный `sku` |
| 422 | данные понятны, но не прошли проверку | список полей и правил |
| 429 | слишком много запросов | время до повтора |
| 500 | непредвиденная ошибка сервера | идентификатор запроса, без стека |
| 502 | вышестоящий сервер получил плохой ответ | нейтральное сообщение |
| 503 | сервис временно недоступен | время восстановления |

Разница между 400 и 422 не всегда очевидна. 400 говорят, когда тело не разбирается: пришёл не JSON, нет обязательного поля, нарушен синтаксис. 422 говорят, когда JSON разобран, поля на месте, но значения не проходят правило: цена отрицательная, остаток дробный, `sku` короче трёх символов. В FastAPI такая проверка включена по умолчанию, и клиент получает 422 со списком полей. Во Flask проверку пишут вручную, и тогда важно не смешивать оба случая в один 400.

Разница между 401 и 403 тоже практическая. 401 означает «представься», 403 означает «я тебя знаю, но сюда нельзя». Если кладовщик пытается удалить товар, а роль не позволяет, правильный ответ 403, а не 401: повторный вход не поможет. Если токен истёк, правильный ответ 401, и клиент знает, что нужно обновить токен.

Код состояния не заменяет тело ошибки. Клиенту нужно понять, какое поле исправить и что делать дальше. Единый формат ошибки экономит время поддержки.

```json
{
  "error": "validation_error",
  "message": "Поле price должно быть больше нуля",
  "fields": {"price": "должно быть больше нуля"},
  "request_id": "req-7f3c"
}
```

`request_id` связывает ответ с записью в журнале сервера. Пользователь сообщает номер, инженер находит запрос и видит, что произошло. Без идентификатора поиск по времени превращается в угадывание.

## Ответ API удобно читать из кода

Клиент на Python получает ответ и разбирает его по частям. Код состояния проверяют до чтения тела, потому что при ошибке структура тела может отличаться.

```python
import requests

r = requests.get("http://127.0.0.1:5055/api/products/42", timeout=5)
print(r.status_code)
print(r.headers["Content-Type"])
print(r.json()["title"])
print(r.json()["stock"])
```

На учебной машине этот код вывел:

```text
200
application/json
Шуруповёрт Makita DF333D
4
```

Первая строка говорит, что запрос выполнен. Вторая подтверждает, что тело можно разбирать как JSON. Две последние строки это уже данные, извлечённые из ответа. Если сервер вернул 404, вызов `r.json()["title"]` упадёт с `KeyError`, потому что в теле ошибки нет поля `title`. Поэтому в рабочем коде сначала проверяют `r.status_code` или вызывают `r.raise_for_status()`.

Создание товара выглядит так же, но с телом и методом POST.

```python
import requests

new = {
    "sku": "SKU-5001",
    "title": "Уровень строительный 600 мм",
    "price": 1290.00,
    "stock": 15,
}
r = requests.post("http://127.0.0.1:5055/api/products", json=new, timeout=5)
print(r.status_code)
print(r.headers["Location"])
print(r.json()["id"])
```

```text
201
/api/products/43
43
```

Заголовок `Location` появился потому, что сервер создал ресурс и обязан сообщить его адрес. Клиент может сразу открыть карточку по этому адресу и не строить путь самостоятельно.

Тот же обмен из командной строки показывает служебные заголовки, которые скрывает библиотека.

```text
> curl -i http://127.0.0.1:5055/api/products/42
HTTP/1.1 200 OK
Server: Werkzeug/3.1.9 Python/3.13.14
Content-Type: application/json
Content-Length: 132

{"category":"Инструмент","id":42,"price":12450.0,"sku":"SKU-1002","stock":4,"title":"Шуруповёрт Makita DF333D"}
```

Заголовок `Server` выдаёт имя и версию сервера. Для учебного стенда это удобно, для рабочего контура это лишняя подсказка тому, кто ищет известную уязвимость. Версию в ответе убирают или заменяют нейтральным значением.

## REST: ресурс, представление, ограничения

REST это стиль построения API, который описал Рой Филдинг в 2000 году. В нём нет обязательного набора технологий, зато есть несколько ограничений. Клиент и сервер разделены. Каждый запрос самодостаточен. Ответ можно кешировать. Интерфейс единообразен: ресурсы называются адресами, действия выражаются методами, данные передаются представлением. Слои, например прокси и шлюзы, могут стоять между клиентом и сервером, не меняя контракт.

Главное слово здесь «ресурс», а не «функция». Ресурс это объект, у которого есть адрес и представление: товар, склад, накладная, пользователь. Функция это действие, и в REST она выражается методом над ресурсом. Поэтому `POST /api/v1/shipments` создаёт накладную, а не вызывает процедуру `createShipment`. Если предметная область плохо ложится на ресурсы, например сложный расчёт, допускается ресурс операции: `POST /api/v1/stock/recalculate`. Это отступление, но оно остаётся явным.

| Задача | Ресурсный адрес |
|---|---|
| Список товаров | `GET /api/v1/products` |
| Один товар | `GET /api/v1/products/42` |
| Создать товар | `POST /api/v1/products` |
| Заменить товар | `PUT /api/v1/products/42` |
| Изменить остаток | `PATCH /api/v1/products/42` |
| Удалить товар | `DELETE /api/v1/products/42` |
| Товары склада | `GET /api/v1/warehouses/3/products` |
| Приёмка на склад | `POST /api/v1/warehouses/3/receipts` |

Список почти всегда требует пагинации. На складе 4800 позиций, и отдавать их одним ответом значит грузить в память клиента несколько мегабайт и ждать, пока база соберёт всё. Постраничный вывод задают параметрами `limit` и `offset` или курсором. Ответ содержит не только массив, но и общее количество или признак следующей страницы.

```json
{
  "count": 4800,
  "limit": 20,
  "offset": 40,
  "items": [
    {"id": 42, "sku": "SKU-1002", "title": "Шуруповёрт Makita DF333D", "stock": 4}
  ],
  "next": "/api/v1/products?limit=20&offset=60"
}
```

Обёртка с `count`, `items` и `next` удобнее голого массива. Клиент не ломается, когда к списку добавляют поле, а сервер может менять размер страницы без изменения формата. Голый массив тоже допустим, но расширять его труднее.

REST не требует JSON. Представлением может быть XML, CSV, PDF или изображение. JSON стал привычным для API, потому что он компактно выражает вложенные объекты и легко разбирается почти любым языком. Если клиент просит `Accept: application/xml`, сервер может вернуть XML того же ресурса. В учебном проекте достаточно JSON, но заголовок `Accept` всё равно нужно читать, иначе расширение формата превратится в переделку всех маршрутов.

REST не равен RPC. В RPC клиент вызывает удалённую функцию с именем и аргументами: `POST /api/createShipment`. В REST клиент работает с ресурсом: `POST /api/v1/shipments`. Оба подхода живут в реальных системах. REST удобнее для открытого API и кеширования, RPC удобнее для внутренних вызовов со сложной логикой. Смешивать их в одном API можно, но границу нужно описать, иначе клиент не поймёт, где ресурс, а где команда.

## Ошибки, которые ломают контракт

Большинство проблем API связано не с синтаксисом HTTP, а с нарушением обещания. Клиент ожидает один формат, получает другой и не может отличить успех от ошибки.

**Ошибка спрятана в 200.** Сервер возвращает `200 OK` и тело `{"error": "Товар не найден"}`. Клиент проверяет только код, считает запрос успешным и показывает пустую карточку. Мониторинг не видит сбоя, потому что все ответы успешны. Симптом: в отчёте доступности 100 процентов, а пользователи жалуются на пропавшие товары. Правильно вернуть 404 и тело ошибки.

**GET меняет данные.** Маршрут `GET /api/v1/products/42/delete` удаляет товар. Браузер prefetch, робот или проверка доступности вызывают его без намерения пользователя. Симптом: запись исчезает, а в журнале нет POST. Правильно использовать `DELETE` и не помещать изменение в безопасный метод.

**Проверка данных возвращает 500.** В коде `data["price"]` без проверки ключа. Клиент присылает тело без `price`, сервер падает с `KeyError`, обработчик отдаёт 500. Клиент повторяет запрос, считая сбой временным, и создаёт дубли. Правильно проверить обязательные поля и вернуть 400 или 422 с именем поля.

**Тело не разобрано, потому что нет Content-Type.** Клиент отправляет JSON, но забывает заголовок `Content-Type: application/json`. Сервер видит форму, `request.get_json()` возвращает `None`, и дальше падает на `None["sku"]`. Симптом: тот же запрос из Postman работает, а из скрипта нет. Правильно выставить заголовок на клиенте и вернуть 415 или 400, если формат не поддержан.

**Ответ слишком большой.** `GET /api/v1/products` отдаёт все 4800 позиций. Клиент ждёт несколько секунд, мобильное приложение падает по памяти, прокси обрывает соединение. Симптом: в браузере список открывается, в телефоне нет. Правильно ввести `limit` и `offset` и ограничить максимальный размер страницы.

**Ошибка раскрывает внутренности.** Сервер возвращает `str(exc)` с текстом `sqlite3.OperationalError: no such column: products.pric`. Клиент видит имя таблицы и колонки, а злоумышленник получает схему базы. Симптом: удобно отлаживать, страшно публиковать. Правильно писать подробности в журнал, а клиенту отдавать нейтральное сообщение и `request_id`.

**Контракт меняется без версии.** Поле `title` переименовали в `name`, старые клиенты продолжают читать `title` и получают пустые строки. Симптом: после обновления сервера часть пользователей видит товары без названий. Правильно добавить новое поле рядом со старым, выпустить версию или заранее предупредить клиентов.

> [!PITFALL] Код 200 не делает ответ успешным
> Успех определяется кодом состояния и форматом тела вместе. Если тело содержит `error`, а код 200, клиент и мониторинг ошибутся. Проверяйте оба признака и фиксируйте формат ошибки в описании API.

## Что проверить перед публикацией маршрута

Проверка маршрута предотвращает большинство споров с клиентом. Сначала смотрят, что метод и адрес называют один ресурс и не содержат глагола. Затем проверяют, что GET не меняет данные, а POST возвращает 201 и `Location`. После этого отправляют неверные данные: без обязательного поля, с отрицательной ценой, с чужим токеном. Каждый случай должен дать свой код и понятное тело.

Отдельно проверяют границы. Пустой список товаров возвращает 200 и `items: []`, а не 404. Неизвестный идентификатор возвращает 404. Повторный `sku` возвращает 409. Слишком большой `limit` ограничивается сервером, а не отклоняется с 500. Ошибка базы возвращает 500 с `request_id`, а подробности остаются в журнале.

Последний шаг это проверка из другого клиента. Если маршрут работает в браузере, но не работает в Postman, различие обычно в заголовке `Content-Type`, токене или методе. Если работает в Postman, но не работает из Python, смотрят, что именно отправляет библиотека: `json=` добавляет заголовок, `data=` отправляет строку без него.

## Итоги

- HTTP передаёт запрос и ответ как сообщения: метод, адрес, заголовки, тело и код состояния.
- Метод называет действие, адрес называет ресурс, а параметры уточняют выборку.
- GET и HEAD безопасны, GET, PUT и DELETE идемпотентны, POST создаёт новую операцию при каждом вызове.
- Заголовки `Content-Type`, `Accept`, `Authorization` и `Location` описывают формат, права и адрес созданного ресурса.
- Код состояния это часть контракта: 2xx успех, 4xx ошибка клиента, 5xx ошибка сервера.
- REST строит API вокруг ресурсов и представлений, а не вокруг имён функций.
- Ошибка в теле с кодом 200, GET с побочным эффектом и ответ без пагинации ломают клиентов тише, чем падение сервера.

::quiz
Q: Что означает метод GET?
+ Запросить представление ресурса без изменения состояния
- Создать новый ресурс
- Удалить ресурс
- Заменить ресурс целиком
! GET относится к безопасным методам и не должен менять данные.

Q: Какие методы являются безопасными?
+ GET
+ HEAD
+ OPTIONS
- POST
- DELETE
! Безопасные методы не меняют состояние сервера.

Q: Что означает код 201?
+ Ресурс создан, его адрес передан в заголовке Location
- Запрос выполнен, тело пустое
- Ресурс не найден
- Данные не прошли проверку
! Код 201 сопровождает создание ресурса.

Q: Когда уместен код 403?
+ Клиент подтвердил вход, но прав на операцию нет
- Клиент не передал токен
- Сервер не нашёл адрес
- Сервер упал на запросе к базе
! 403 означает запрет для уже известного клиента.

Q: Какие заголовки описывают формат тела?
+ Content-Type
+ Accept
- Location
- Host
! Content-Type описывает отправленное тело, Accept желаемый формат ответа.

Q: Какой код возвращают вместе с заголовком Location при создании ресурса?
+ 201
- 200
- 204
- 404
! Location сообщает адрес созданного ресурса.

Q: Какие методы идемпотентны?
+ GET
+ PUT
+ DELETE
- POST
! Повтор идемпотентного метода не меняет результат сверх первого вызова.

Q: Что означает код 422?
+ Тело разобрано, но значения не прошли проверку
- Сервер не понял формат тела
- Клиент не авторизован
- Ресурс создан
! 422 отделяет ошибку правила от синтаксической ошибки 400.

Q: Что такое ресурс в REST?
+ Объект с адресом и представлением, например товар или накладная
- Имя функции, которую вызывает клиент
- Таблица базы данных без связей
- Заголовок ответа
! REST строит API вокруг ресурсов, а действия выражает методами.

Q: Зачем нужны параметры limit и offset?
+ Чтобы выдавать список постранично и не грузить все записи сразу
- Чтобы заменить метод POST
- Чтобы хранить пароль в адресе
- Чтобы отключить проверку прав
! Пагинация ограничивает объём ответа и нагрузку на базу.

Q: Почему ответ с кодом 200 и телом error опасен?
+ Клиент и мониторинг считают запрос успешным
- Он всегда медленнее ответа 404
- Он запрещён протоколом HTTP
- Он не содержит заголовков
! Код состояния должен соответствовать результату операции.

Q: Какие признаки указывают на плохо спроектированный API?
+ Глагол в пути вместо метода
+ Код 200 для ошибки проверки данных
+ Отсутствие пагинации в списке из 4800 записей
- Заголовок Content-Type в ответе
- Код 404 для неизвестного идентификатора
! Перечисленные признаки ломают контракт или скрывают ошибку.
