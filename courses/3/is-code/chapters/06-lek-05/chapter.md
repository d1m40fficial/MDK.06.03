## Два способа получить один результат

В понедельник кладовщик калужской площадки просит посчитать, сколько паллет займёт отгрузка. Объём груза известен: 3,852 кубического метра, объём одной паллеты 1,44. Программист открывает Python, пишет две строки, нажимает запуск и через секунду видит ответ: три паллеты.

Во вторник тот же расчёт нужен внутри учётного приложения «Склад+», которое написано на C#. Программист копирует знакомые строки в файл `Program.cs`, нажимает F5 и получает сообщение об ошибке. Код правильный, но среда не понимает, что с ним делать: в C# нельзя запустить текст программы напрямую.

**Программа на C# проходит через сборку, и всё устройство проекта служит этой сборке.** Python читает и выполняет файл строка за строкой. C# сначала превращает все файлы проекта в один готовый модуль, сборку, и только потом запускает её. Пока это правило не усвоено, папки `bin`, `obj` и файл проекта кажутся лишним мусором, а любая ошибка выглядит необъяснимой.

## Идея: текст становится сборкой

Компилятор C# читает исходные файлы и проверяет их целиком, до запуска. Он смотрит, существуют ли переменные, совпадают ли типы, возвращает ли функция значение. Если проверка прошла, компилятор записывает промежуточный код в файл сборки. Среда исполнения загружает сборку и переводит её команды в машинные по мере работы программы.

| Этап | Что происходит | Что получается |
|---|---|---|
| Восстановление | проверяются и скачиваются зависимости проекта | список пакетов в `obj` |
| Сборка | компилятор проверяет все файлы проекта | файл `.dll` в `bin` |
| Запуск | среда загружает сборку и вызывает точку входа | работающая программа |
| Публикация | сборка готовится для другой машины | папка `publish` |

Два шага вместо одного дают то, чего нет у интерпретатора. Ошибка типов видна до первого запуска, а не в момент, когда пользователь ввёл не то значение. Готовая сборка не требует исходного кода и компилятора на машине пользователя. Один и тот же файл `.dll` можно запустить на сервере, на компьютере кладовщика и в тестовой среде, если там есть подходящая версия среды исполнения.

Цена тоже понятна. Между правкой и результатом появляется шаг сборки. Для маленького проекта он занимает секунды, для большого решения минуты, и в это время программа не работает. Разработчик ждёт, пока компилятор проверит весь проект, даже если изменена одна строка.

## Решение, проект и сборка

Три слова, которые в разговоре заменяют друг друга, означают разные вещи.

**Проект** это единица сборки. Файл с расширением `.csproj` перечисляет настройки: целевую платформу, тип результата, зависимости, версию языка. Компилятор собирает один проект в одну сборку.

**Решение** это контейнер для нескольких проектов. Файл `.sln` хранит их список и связи между ними. Решение не компилируется само по себе, оно говорит инструменту, какие проекты собрать и в каком порядке.

**Сборка** это результат компиляции: файл `.dll` с кодом и, на Windows, небольшой `.exe`, который запускает этот код. Сборка это то, что реально исполняется.

Слово «сборка» уже встречалось в разговоре об архитектуре, где оно означало соединение объектов в точке входа. Здесь речь о другом: сборка это результат компиляции проекта. Контекст различает эти значения, но в разговоре о C# лучше уточнять, о какой сборке идёт речь.

| Понятие | Файл | Что описывает | Сколько в учебном проекте |
|---|---|---|---|
| Решение | `sklad-plus.sln` | набор проектов | одно |
| Проект | `SkladPlus.App.csproj` | одну сборку и её настройки | два |
| Сборка | `SkladPlus.App.dll` | готовый код для запуска | по одной на проект |

Файл проекта у консольного приложения выглядит так:

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
```

Строка `Sdk` подключает стандартный набор правил сборки, поэтому в файле нет списка исходников: компилятор сам берёт все файлы `.cs` из каталога проекта. `OutputType` со значением `Exe` означает консольное приложение, для библиотеки здесь стояло бы `Library` или строки не было бы вовсе. `TargetFramework` задаёт версию платформы, в учебном проекте это `net10.0`. `ImplicitUsings` добавляет частые пространства имён без отдельных строк `using`. `Nullable` включает проверку на возможное отсутствие значения.

Зачем решению несколько проектов, если программа одна? Потому что части программы меняются с разной скоростью. Расчёты хранения нужны и консольному приложению, и будущему API, и проверкам. Их выносят в отдельный проект библиотеки, а приложение подключает его ссылкой после создания обоих проектов:

```bash
dotnet add src/SkladPlus.App reference src/SkladPlus.Storage
```

После этой команды приложение видит типы из библиотеки, а сама библиотека не знает, кто её использует. Такая связь в одну сторону позволяет заменить консольный интерфейс на веб-сервис, не переписывая расчёты.

## Что создаёт шаблон

Проект удобнее начать с шаблона, чем с пустого файла. Шаблон создаёт файл проекта, точку входа и служебные каталоги, которые нужны инструментам.

```bash
dotnet new sln -n sklad-plus
dotnet new console -o src/SkladPlus.App
dotnet new classlib -o src/SkladPlus.Storage
dotnet sln add src/SkladPlus.App src/SkladPlus.Storage
```

Первая команда создаёт файл решения `sklad-plus.sln`. Вторая создаёт консольный проект в каталоге `src/SkladPlus.App`. Третья создаёт проект библиотеки, четвёртая добавляет оба проекта в решение.

После этого структура выглядит так:

```text
sklad-plus/
  sklad-plus.sln
  src/
    SkladPlus.App/
      SkladPlus.App.csproj
      Program.cs
      bin/
      obj/
    SkladPlus.Storage/
      SkladPlus.Storage.csproj
      Class1.cs
      bin/
      obj/
```

Файл `Program.cs` после создания содержит строку вывода, а в некоторых версиях шаблона ещё и комментарий со ссылкой на справку:

```csharp
Console.WriteLine("Hello, World!");
```

Это не привычная программа с классом и методом. Начиная с C# 9 разрешены так называемые операторы верхнего уровня: компилятор сам заворачивает их в метод `Main` и создаёт класс. Такой файл короче, но у него есть ограничения: операторы верхнего уровня допустимы только в одном файле проекта, и объявления типов должны идти после них.

Каталог `obj` хранит промежуточные файлы: список восстановленных пакетов, сгенерированные файлы сборки, кеш компилятора. Каталог `bin` хранит готовый результат: сборку, файл запуска и копии зависимостей. Оба каталога создаются автоматически и не хранятся в Git. Править файлы внутри них бессмысленно: при следующей сборке они будут перезаписаны.

Первая сборка выполняется командой:

```bash
dotnet build
```

Она проходит по решению, собирает оба проекта и складывает результат в `src/SkladPlus.App/bin/Debug/net10.0/`. Там появляются `SkladPlus.App.dll` и файл запуска `SkladPlus.App.exe`. Запуск без сборки вручную делает другая команда:

```bash
dotnet run --project src/SkladPlus.App
```

Она сначала проверяет, изменились ли файлы, при необходимости собирает проект и только потом запускает сборку. Ключ `--project` обязателен, когда в решении несколько проектов: иначе инструмент не знает, какой из них запускать.

## Точка входа и пространство имён

У программы должен быть вход. В Python его роль играет условие `if __name__ == "__main__":`, в C# компилятор ищет метод `Main` с особой подписью. Тот же код можно записать явно, с классом и методом `Main`; так делают в старых проектах и когда точку входа нужно указать по имени класса.

```csharp
using System;

namespace SkladPlus.App
{
    class Program
    {
        static void Main(string[] args)
        {
            Console.WriteLine("Склад+ : проверка среды");
        }
    }
}
```

Метод `Main` объявлен статическим, потому что объект класса для запуска ещё не создан. Он может возвращать `void` или `int`, а параметр `string[] args` получает аргументы командной строки. Компилятор допускает ровно одну точку входа: два метода `Main` в разных классах дают ошибку `CS0017`, и тогда нужный класс указывают в параметре `StartupObject` файла проекта.

Пространство имён это адрес, по которому живут типы. Класс `Storage` из проекта библиотеки объявлен в пространстве `SkladPlus.Storage`, и приложение обращается к нему по полному имени или через `using`. Пространства имён не связаны с каталогами жёстко, но по соглашению совпадают с ними: так проще искать нужный файл.

В проекте библиотеки файл `Class1.cs` переименовывают в `Storage.cs` и заполняют расчётами:

```csharp
using System;

namespace SkladPlus.Storage
{
    public static class Storage
    {
        public const double PalletVolumeM3 = 1.44;

        public static double BoxVolume(double lengthCm, double widthCm, double heightCm)
        {
            return lengthCm * widthCm * heightCm / 1_000_000;
        }

        public static int PalletsNeeded(double totalVolumeM3)
        {
            return (int)Math.Ceiling(totalVolumeM3 / PalletVolumeM3);
        }
    }
}
```

Класс объявлен статическим, потому что ему не нужны объекты: методы принимают все данные параметрами и возвращают результат. Приложение обращается к ним по имени класса.

```csharp
using SkladPlus.Storage;

namespace SkladPlus.App
{
    class Program
    {
        static void Main(string[] args)
        {
            double volume = Storage.BoxVolume(40, 30, 25) * 24;
            Console.WriteLine($"Объём: {volume:0.###} м3");
            Console.WriteLine($"Паллет: {Storage.PalletsNeeded(volume)}");
        }
    }
}
```

Вывод на русской локали:

```text
Объём: 0,72 м3
Паллет: 1
```

Строка `using SkladPlus.Storage;` позволяет писать `Storage` вместо `SkladPlus.Storage.Storage`. Если убрать её, компилятор сообщит `CS0246`: тип не найден. Сама библиотека при этом собирается нормально, ошибка относится к приложению, которое не подключило ссылку или не импортировало пространство имён.

## Цикл работы в Visual Studio 2022

Visual Studio это не редактор с подсветкой, а среда сборки и отладки. Она показывает не только файлы, но и структуру решения, потому что именно эта структура определяет, что и как будет собрано.

При создании проекта выбирают шаблон `Console App`, версию платформы `net10.0`, имя проекта и расположение. Среда создаёт решение, проект и файл `Program.cs`, после чего проект можно запускать.

Окно `Solution Explorer` показывает решение, проекты, зависимости и файлы. Двойной щелчок по файлу открывает его в редакторе. Если проект не собирается, причина чаще всего видна в окне `Error List`: строка с номером ошибки и файлом, двойной щелчок ведёт к месту в коде.

Запуск с отладкой выполняется клавишей F5, запуск без отладки сочетанием Ctrl+F5. Разница не только в скорости. С отладкой среда останавливается на точках останова, показывает значения переменных и позволяет выполнять код по шагам. Без отладки программа просто работает, а после завершения Visual Studio оставляет окно консоли открытым до нажатия клавиши, тогда как при запуске с отладкой оно закрывается сразу.

Точка останова ставится щелчком на левом поле строки или клавишей F9. Когда выполнение доходит до неё, программа приостанавливается. В окне `Locals` видны переменные текущего метода, в `Watch` можно добавить выражение и следить за ним, в `Call Stack` виден путь вызовов. Шаг с обходом выполняется клавишей F10, шаг с заходом в функцию клавишей F11.

Сборка из меню `Build` собирает решение целиком. Внизу открывается окно `Output` с итогом: число проектов, предупреждения и ошибки. Предупреждения не мешают запуску, но показывают места, где компилятор сомневается: неиспользуемая переменная, возможное отсутствие значения, устаревший метод.

У сборки две конфигурации. `Debug` содержит отладочные символы и не оптимизирует код, поэтому в ней удобно искать ошибки. `Release` убирает отладочную информацию и включает оптимизации, её используют для передачи пользователю. Файлы двух конфигураций лежат в разных каталогах: `bin/Debug` и `bin/Release`.

| Действие | Клавиши | Что происходит |
|---|---|---|
| Собрать решение | Ctrl+Shift+B | компиляция без запуска |
| Запустить с отладкой | F5 | сборка, запуск, остановка на точках |
| Запустить без отладки | Ctrl+F5 | сборка и запуск |
| Поставить точку останова | F9 | остановка на выбранной строке |
| Шаг с обходом | F10 | следующая строка без захода в функцию |
| Шаг с заходом | F11 | переход внутрь вызываемой функции |

## Команды CLI

Visual Studio удобна, но не всегда доступна. На сервере, в контейнере и в сценарии сборки те же действия выполняет интерфейс командной строки `dotnet`. Он входит в состав SDK и работает одинаково на разных платформах.

| Команда | Что делает | Когда нужна |
|---|---|---|
| `dotnet --info` | показывает версии SDK и среды | проверить окружение |
| `dotnet new console` | создаёт проект из шаблона | начать новый проект |
| `dotnet build` | собирает решение или проект | проверить компиляцию |
| `dotnet run` | собирает и запускает | обычный запуск при разработке |
| `dotnet clean` | удаляет результат сборки | убрать старые файлы |
| `dotnet publish` | готовит сборку для передачи | выпуск на другой машине |

Команда `dotnet build` не запускает программу, а `dotnet run` запускает. Если нужно выполнить уже собранную сборку без исходного кода, её запускают через среду:

```bash
dotnet src/SkladPlus.App/bin/Release/net10.0/SkladPlus.App.dll
```

Публикация отличается от обычной сборки. `dotnet publish -c Release` собирает проект и складывает в отдельную папку всё, что нужно для запуска: сборку, зависимости, файл настроек. Для машины без установленного SDK этого достаточно, если среда исполнения на ней есть. Для машины без среды исполнения используют публикацию в один файл или самодостаточную публикацию, но это отдельная тема.

::gate Почему ошибка типов в C# видна до запуска, а в Python только во время выполнения?

## Одна задача на двух языках

Вернёмся к расчёту паллет. На Python программа выглядит так:

```python
import math

PALLET_VOLUME_M3 = 1.44
volume = 3.852
pallets = math.ceil(volume / PALLET_VOLUME_M3)

print(f"Объём: {volume} м3")
print(f"Паллет: {pallets}")
```

Вывод:

```text
Объём: 3.852 м3
Паллет: 3
```

Та же задача на C#:

```csharp
using System;

namespace SkladPlus.App
{
    class Program
    {
        static void Main(string[] args)
        {
            const double palletVolumeM3 = 1.44;
            double volume = 3.852;
            int pallets = (int)Math.Ceiling(volume / palletVolumeM3);

            Console.WriteLine($"Объём: {volume} м3");
            Console.WriteLine($"Паллет: {pallets}");
        }
    }
}
```

Вывод на русской локали:

```text
Объём: 3,852 м3
Паллет: 3
```

Число одно и то же, а разделитель дробной части при выводе разный. В исходном коде оба языка пишут дробную часть через точку, но C# при печати числа использует настройки системы: на русской локали это запятая, а Python всегда печатает точку. Для учебных примеров это мелочь, для обмена данными с внешними системами это причина ошибок, поэтому форматирование чисел разберут отдельно.

| Признак | Python | C# |
|---|---|---|
| Что запускается | файл `.py` | сборка `.dll` |
| Когда проверяются типы | во время выполнения | во время сборки |
| Точка входа | условие `if __name__ == "__main__"` | метод `Main` или операторы верхнего уровня |
| Зависимости | `pip` и виртуальное окружение | NuGet и файл проекта |
| Результат сборки | отсутствует | файл в `bin` |
| Инструмент | VS Code | Visual Studio 2022, CLI |
| Цена правки | сохранить и запустить | сохранить, собрать, запустить |

Разница в проверке типов объясняет, почему один и тот же код ведёт себя по-разному. В Python выражение с делением дойдёт до выполнения и упадёт с `TypeError` только тогда, когда очередь дойдёт до него. В C# компилятор увидит несовпадение типов заранее и не соберёт проект. Это не делает C# безопаснее во всём: ошибки логики и неверные данные он тоже не поймает. Он лишь переносит часть проверок из времени работы во время сборки.

## Типичные ошибки

Ошибки сборки отличаются от ошибок выполнения тем, что программа ещё не запустилась. Ниже те, что встречаются чаще всего.

1. `CS0103: The name 'volume' does not exist in the current context`. Переменная объявлена в другом методе или написана с другой буквой. Область видимости ограничена блоком, поэтому значение из соседней функции недоступно.
2. `CS1002: ; expected`. Пропущена точка с запятой в конце оператора. Компилятор указывает на следующую строку, потому что замечает проблему только там.
3. `CS0029: Cannot implicitly convert type 'double' to 'int'`. Результат деления дробный, а переменная целая. Нужно явное приведение или другой тип.
4. `CS0017: Program has more than one entry point defined`. В проекте два метода `Main` или файл с операторами верхнего уровня соседствует с классом, у которого есть `Main`.
5. `NETSDK1045`: установленный SDK не поддерживает целевую платформу `net10.0`. Проект создан для более новой версии, чем та, что стоит на машине.
6. `MSB1011`: в текущем каталоге несколько проектов или решений, и инструмент не знает, какой использовать. Помогает явно указать проект: `dotnet run --project ...` или путь к файлу проекта в `dotnet build`.
7. Запуск устаревшей сборки. Программа собрана в `Release`, а запускается файл из `bin/Debug`, или наоборот. Сначала смотрят путь, потом ищут ошибку в коде.
8. Правка файлов в `bin` или `obj`. Следующая сборка перезапишет изменения, и код снова станет прежним.

Отдельная ошибка не в коде, а в привычке: искать причину в тексте программы, когда сообщение говорит о ссылке на проект или о версии SDK. Полезно читать не только текст ошибки, но и её код: по коду быстрее находится причина и решение.

## Цена и выгода

Сборка добавляет шаг и требует дисциплины: файлы должны лежать в проекте, ссылки должны быть объявлены, версия платформы должна совпадать. Взамен разработчик получает раннюю проверку типов, повторяемую сборку и возможность передать программу без исходного кода.

| Что даёт сборка | Чем приходится платить |
|---|---|
| Ошибки типов до запуска | время на компиляцию |
| Одинаковый результат на разных машинах | хранение и передача сборок |
| Явные зависимости проекта | ведение файла проекта |
| Отладка по исходному коду | размер инструментов |

Для учебного проекта выгода очевидна: расчёты отделяются от интерфейса, а будущий API сможет использовать ту же библиотеку. Для маленького скрипта на десять строк сборка избыточна, и Python здесь выигрывает. Выбор языка определяется задачей, а не привычкой.

## Итоги

- C# исполняет сборку, а не исходный файл, поэтому между правкой и запуском есть этап сборки.
- Проект это единица сборки, решение это контейнер проектов, сборка это готовый файл `.dll`.
- Файл `.csproj` задаёт тип результата, целевую платформу и зависимости.
- Шаблон `dotnet new console` создаёт проект, `dotnet build` собирает, `dotnet run` собирает и запускает.
- Точка входа это метод `Main` или операторы верхнего уровня, и она должна быть одна.
- Visual Studio показывает решение целиком, потому что от него зависит сборка, а не только редактирование файла.
