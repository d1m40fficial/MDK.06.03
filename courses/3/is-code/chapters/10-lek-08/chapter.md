## Три копии одного расчёта

В понедельник «Северный склад» заказывает товар из трёх мест. Кладовщик запускает консольный отчёт и получает список позиций. Менеджер открывает страницу в «Склад+» и видит другой список. Утром в понедельник импорт из Excel добавляет третий, самый короткий. Все три отчёта считают одно и то же: сколько добрать до минимального остатка с учётом упаковки.

Расчёт живёт в трёх копиях. В консольном отчёте формула записана так: `packs = missing // pack`, то есть округление вниз. Для `SKU-1042` с дефицитом 28 и упаковкой 10 она даёт 2 коробки, то есть 20 штук вместо 30. В API формулу упростили до `order = missing` и потеряли кратность: заказ равен 28, поставщик привозит неполную коробку и требует доплату. В импорте формула верная, но результат печатается внутри функции, поэтому при повторном вызове из журнала появляются две одинаковые строки.

Три копии разошлись за полгода. Каждая правка делалась в одном месте и не доходила до двух других. **Функция собирает расчёт в одно место, а модуль делает это место доступным всем частям проекта.** Пока формула существует в трёх экземплярах, ошибка неизбежна: рано или поздно их станет четыре.

## Функция это контракт

Функция обещает: если ей дать такие входы, она вернёт такой выход. Всё остальное для вызывающего кода неважно. Ему не нужно знать, какие переменные появились внутри и в каком порядке шли строки.

У контракта три части. Имя говорит, что функция делает. Параметры описывают вход. Возвращаемый тип описывает выход. Четвёртая часть, побочные эффекты, в сигнатуре не видна, и именно она чаще всего нарушает договорённость.

Хорошее имя отвечает на вопрос, а не описывает процесс. `reorder_quantity` говорит, что вернётся количество к заказу. Имя `calculate` не говорит ничего, а `do_stuff` прямо предупреждает, что автор не решил, зачем функция нужна.

Одна функция решает одну задачу. Если внутри смешаны расчёт, печать и запись в файл, то при повторном использовании придётся тащить всё три действия. Разделение даёт свободу: расчёт возвращает число, печать выводит его в консоль, запись сохраняет в журнал. Каждую часть можно вызвать отдельно.

> [!KEY] Функция без побочных эффектов
> Если функция только читает аргументы и возвращает значение, её результат предсказуем: один и тот же вход всегда даёт один и тот же выход. Такую функцию легко проверить и безопасно вызывать повторно.

Проверим контракт на простом примере. Функция принимает остаток, минимум и кратность упаковки, а возвращает количество к заказу. Для `SKU-1042` с остатком 12 и минимумом 40 при упаковке 10 контракт обещает 30. Всё, что не описано в этих трёх числах, на результат влиять не должно.

Стоит различать параметр и аргумент. Параметр это имя в объявлении функции, аргумент это конкретное значение при вызове. В объявлении `def reorder_quantity(quantity, min_quantity, pack_size)` три параметра. В вызове `reorder_quantity(12, 40, 10)` три аргумента. Различие кажется формальным, но оно помогает читать сообщения об ошибках: «missing 1 required positional argument» означает, что при вызове не хватает значения, а не что в функции забыли строку.

## Параметры и возврат значения

Параметры это имена входных значений внутри функции. В Python они пишутся в скобках после имени, в C# ещё и с типом. Тип важен: компилятор проверяет, что в функцию не передали строку там, где ожидается число.

```python
def reorder_quantity(quantity, min_quantity, pack_size):
    if quantity >= min_quantity:
        return 0
    missing = min_quantity - quantity
    packs = (missing + pack_size - 1) // pack_size
    return packs * pack_size
```

```csharp
static int ReorderQuantity(int quantity, int minQuantity, int packSize)
{
    if (quantity >= minQuantity)
    {
        return 0;
    }
    int missing = minQuantity - quantity;
    int packs = (missing + packSize - 1) / packSize;
    return packs * packSize;
}
```

В Python параметры позиционные: важен порядок. Вызов `reorder_quantity(12, 40, 10)` означает остаток 12, минимум 40, упаковку 10. Если перепутать местами минимум и упаковку, функция не заметит ошибку: все три значения целые. Поэтому в Python полезны именованные аргументы: `reorder_quantity(quantity=12, min_quantity=40, pack_size=10)` читается однозначно.

В C# позиционные аргументы тоже зависят от порядка, но типы и имена параметров подсказывают смысл в сигнатуре. Именованные аргументы там тоже есть: `ReorderQuantity(quantity: 12, minQuantity: 40, packSize: 10)`.

Значение по умолчанию избавляет от повторения. Если упаковка чаще всего равна одной штуке, в Python пишут `pack_size=1` прямо в сигнатуре. Тогда вызов `reorder_quantity(12, 40)` вернёт 28. В C# значение по умолчанию записывают так же: `int packSize = 1`. Второй способ обойтись без лишнего аргумента это перегрузка: два метода с одним именем и разным числом параметров.

```csharp
static int ReorderQuantity(int quantity, int minQuantity)
{
    return ReorderQuantity(quantity, minQuantity, 1);
}

static int ReorderQuantity(int quantity, int minQuantity, int packSize)
{
    if (quantity >= minQuantity)
    {
        return 0;
    }
    int missing = minQuantity - quantity;
    int packs = (missing + packSize - 1) / packSize;
    return packs * packSize;
}
```

Компилятор выбирает перегрузку по числу и типам аргументов. Вызов с двумя аргументами уйдёт в первый метод, с тремя во второй. Перегрузка удобна, когда вариантов немного и они отличаются только набором входа. Если вариантов становится много, лучше оставить один метод с параметрами по умолчанию или с объектом настроек.

Возврат значения тоже часть контракта. В Python функция без `return` возвращает `None`. В C# метод с типом `void` ничего не возвращает, а метод с типом `int` обязан вернуть число на каждом пути выполнения. Компилятор C# проверяет это строго: если ветка `if` возвращает значение, а `else` нет, сборка не пройдёт.

| Что нужно | Python | C# |
|---|---|---|
| Обязательный параметр | `def f(a, b):` | `static int F(int a, int b)` |
| Значение по умолчанию | `def f(a, b=1):` | `static int F(int a, int b = 1)` |
| Именованный аргумент | `f(a=12, b=40)` | `F(a: 12, b: 40)` |
| Ничего не вернуть | `return` или без `return` | `void` |
| Вернуть число | `return 30` | `return 30;` |
| Несколько значений | кортеж `return a, b` | кортеж, `out` или отдельный класс |

Последняя строка важна для склада. Python легко возвращает пару `return count, total`, и вызывающий код распаковывает её. В C# до появления кортежей значений (C# 7) для этого использовали `out`-параметры: метод возвращает одно значение, а остальные записывает в переменные, переданные с ключевым словом `out`. На практике для двух чисел проще вернуть маленький класс или кортеж, но `out` встречается в старом коде и в стандартной библиотеке.

Отдельный случай это коллекция в параметре. Если функция принимает список и добавляет в него элемент, она меняет данные вызывающего кода, хотя это не видно в возвращаемом значении:

```python
def add_row(row, rows):
    rows.append(row)

rows = ["SKU-1042"]
add_row("SKU-2087", rows)
print(rows)
```

Программа печатает `['SKU-1042', 'SKU-2087']`. Функция ничего не вернула, но список снаружи изменился. Такой побочный эффект допустим, если он обещан именем, например `append_row`. Если же функция называется `count_rows`, менять список она не должна.

## Область видимости

Переменная существует не везде. Область видимости это часть программы, где имя доступно. Внутри функции живут локальные переменные: они создаются при вызове и исчезают при возврате. Снаружи их не видно.

```python
def order_for(quantity, min_quantity):
    missing = min_quantity - quantity
    return missing

print(order_for(12, 40))
print(missing)
```

Первый вызов печатает 28, вторая строка падает с `NameError: name 'missing' is not defined`. Переменная `missing` осталась внутри функции и наружу не попала. Это не ограничение, а защита: вызывающий код не может случайно испортить внутреннее значение.

Глобальные переменные видны всем. В Python переменная, объявленная на уровне модуля, доступна функциям на чтение. Но изменить её внутри функции без ключевого слова `global` нельзя: интерпретатор считает, что создаётся новая локальная переменная.

```python
total = 0

def add_order(value):
    total = total + value
    return total

print(add_order(30))
```

Этот код падает с сообщением `UnboundLocalError: cannot access local variable 'total' where it is not associated with a value`. Строка `total = total + value` одновременно читает и записывает имя, поэтому Python считает `total` локальной на всю функцию. К моменту чтения она ещё не создана.

С `global` код заработает:

```python
total = 0

def add_order(value):
    global total
    total += value
    return total

print(add_order(30))
print(add_order(30))
```

Программа напечатает 30 и 60. Второй вызов зависит от первого: результат определяется историей вызовов, а не только аргументами. Если эту же функцию вызовет другой модуль, он получит 90 и не поймёт почему. Такая зависимость называется скрытым состоянием, и она делает проверку функции почти невозможной.

Правильный вариант возвращает новое значение и не трогает глобальную переменную:

```python
def add_order(total, value):
    return total + value

total = 0
total = add_order(total, 30)
total = add_order(total, 30)
print(total)
```

Здесь видно каждое изменение: `total` передаётся в функцию и возвращается новым. Читающему код не нужно искать, кто ещё менял переменную.

В C# та же граница проходит между локальной переменной и статическим полем класса. Локальная переменная существует внутри метода, статическое поле живёт всё время работы программы. Если метод меняет статическое поле, у него появляется скрытое состояние, и два вызова подряд дают разные результаты при одинаковых аргументах. Компилятор такое не запрещает, но проверять и сопровождать код становится труднее.

> [!PITFALL] Глобальная переменная в учебном проекте
> Счётчик итога, объявленный на уровне модуля, удобен в первом скрипте и мешает на третьем. Два отчёта, запущенные подряд в одном процессе, сложат результаты и покажут завышенное число.

::/gate

## Модуль как граница

Пока функция лежит в том же файле, её видит только этот файл. Модуль выносит функцию в отдельный файл и даёт ей имя, по которому её можно импортировать. Для склада это файл `sklad/reorder.py` с расчётом заказа.

```python
"""Расчёт заказа по минимальному остатку."""

DEFAULT_PACK = 1


def reorder_quantity(quantity, min_quantity, pack_size=DEFAULT_PACK):
    if quantity < 0 or min_quantity < 0:
        raise ValueError("Остаток и минимум не могут быть отрицательными")
    if pack_size <= 0:
        raise ValueError("Кратность упаковки должна быть больше нуля")
    if quantity >= min_quantity:
        return 0
    missing = min_quantity - quantity
    packs = (missing + pack_size - 1) // pack_size
    return packs * pack_size


def reorder_total(rows, site=None):
    total = 0
    for row in rows:
        if site is not None and row["site"] != site:
            continue
        total += reorder_quantity(row["qty"], row["min_qty"], row["pack"])
    return total


if __name__ == "__main__":
    print("Проверка модуля:", reorder_quantity(12, 40, 10))
```

Файл `report.py` рядом с пакетом импортирует функции и печатает отчёт:

```python
from sklad.reorder import reorder_quantity, reorder_total

rows = [
    {"site": "Тула", "qty": 12, "min_qty": 40, "pack": 10},
    {"site": "Москва", "qty": 96, "min_qty": 60, "pack": 12},
    {"site": "Калуга", "qty": 3, "min_qty": 30, "pack": 6},
]
print("Тула:", reorder_total(rows, site="Тула"))
print("Всего:", reorder_total(rows))
print("Пустой остаток:", reorder_quantity(0, 25, 5))
```

Запуск `python report.py` из папки проекта даёт:

```text
Тула: 30
Всего: 60
Пустой остаток: 25
```

Строка `if __name__ == "__main__"` отделяет запуск файла от импорта. Когда `reorder.py` запускают напрямую, Python подставляет в `__name__` значение `"__main__"` и выполняет проверочный вывод. Когда файл импортируют, условие ложно, и проверочный код не срабатывает. Без этой строки импорт модуля печатал бы лишнюю строку в отчёте.

Импорт бывает трёх видов. `import sklad.reorder` подключает модуль целиком, и функции вызываются как `sklad.reorder.reorder_quantity`. `from sklad.reorder import reorder_quantity` вводит имя напрямую. `from sklad.reorder import *` импортирует всё, что не начинается с подчёркивания, и считается плохой практикой: непонятно, откуда взялось имя.

Модуль это граница видимости. Всё, что начинается с одного подчёркивания, считается внутренним и не попадает в `import *`. В Python нет строгого запрета, но соглашение соблюдают: `_round_up` это деталь реализации, а `reorder_quantity` публичная функция с обещанием.

У модулей есть обратная сторона: два модуля могут импортировать друг друга. Если `report.py` импортирует `reorder.py`, а `reorder.py` в свою очередь импортирует `report.py`, Python загрузит один из них частично и выдаст `ImportError` или `AttributeError`. Лечение простое: расчёт не должен знать про отчёт. Зависимость идёт в одну сторону, от отчёта к расчёту, а не наоборот. Это же правило пригодится в C#: класс расчёта не ссылается на интерфейс и на контроллер.

В C# границей служит класс и пространство имён. Статический класс `Reorder` в файле `Reorder.cs` с методами `Quantity` и `Total` доступен из других файлов того же проекта через `using SkladCalc;`. Пространство имён не создаёт отдельной сборки, но задаёт полное имя типа и защищает от совпадения имён.

| Что делает | Python | C# |
|---|---|---|
| Вынести в отдельный файл | модуль `reorder.py` | класс `Reorder.cs` |
| Подключить | `import` или `from ... import` | `using` и имя класса |
| Скрыть деталь | имя с `_` | `private` или `internal` |
| Точка входа | `if __name__ == "__main__"` | метод `Main` |
| Группа модулей | пакет с `__init__.py` | пространство имён и проект |

Разница в том, что Python скрывает по соглашению, а C# по уровню доступа. Компилятор C# не даст обратиться к `private` методу из другого класса, а интерпретатор Python лишь предупредит соглашением. Поэтому в Python дисциплина важнее, а в C# больше гарантий от компилятора.

В учебном проекте `sklad-plus` расчёт живёт в пакете `sklad`, а отчёт и API лежат рядом. Файл `__init__.py` может явно перечислить публичные имена в списке `__all__`, и тогда даже `import *` принесёт только обещанные функции. Явный импорт всё равно понятнее: по строке `from sklad.reorder import reorder_total` сразу видно, какая зависимость появилась у файла.

## Побочные эффекты

Побочный эффект это любое изменение вне функции: печать, запись файла, изменение глобальной переменной, отправка запроса. Сами по себе эффекты не плохи, без них программа ничего не делает. Плохо, когда эффект спрятан внутри функции, от которой ждут только числа.

Вернёмся к импорту из Excel. Функция расчёта была написана так:

```python
def reorder_quantity(quantity, min_quantity, pack_size):
    if quantity >= min_quantity:
        return 0
    missing = min_quantity - quantity
    packs = (missing + pack_size - 1) // pack_size
    result = packs * pack_size
    print("Заказ:", result)
    return result
```

Отчёт вызывает её один раз на строку и получает аккуратный список. API вызывает её же для каждой позиции и пишет в журнал запроса. В итоге каждая строка появляется в консоли дважды, а в журнале остаётся след, который никто не просил. Функция нарушила контракт: она обещала вернуть число, а попутно печатала.

Лечение простое: расчёт возвращает значение, а печать остаётся у вызывающего кода. Тогда отчёт печатает сам, API пишет в журнал сам, а импорт просто складывает числа.

| Действие | Где ему место |
|---|---|
| Расчёт заказа | чистая функция модуля |
| Печать строки отчёта | код отчёта |
| Запись в журнал | код API или общий логгер |
| Чтение файла | отдельная функция загрузки |
| Изменение остатка | метод хранилища, а не расчёт |

Побочные эффекты стоит собирать на границах программы: там, где данные входят и выходят. Чем ближе к центру, тем чище должны быть функции. Это правило пригодится, когда появится API: обработчик запроса примет данные, вызовет чистый расчёт и вернёт ответ.

> [!TRADEOFF] Печать внутри функции
> Иногда печать внутри функции удобна для отладки. Но отладочный `print` нужно удалять до сдачи работы, иначе он попадёт в отчёт и в журнал.

::/gate

::gate Чем проверка функции на наборе значений отличается от одного удачного запуска?

## Проверка функции на наборе значений

Один удачный запуск показывает, что функция работает на одном входе. Проверка на наборе показывает, где она ломается. Для расчёта заказа достаточно пяти значений: обычный дефицит, достаточный остаток, остаток ровно по минимуму, нулевой остаток и дефицит, который не делится на упаковку.

```python
from sklad.reorder import reorder_quantity

cases = [
    (12, 40, 10, 30),
    (96, 60, 12, 0),
    (7, 7, 1, 0),
    (0, 25, 5, 25),
    (3, 30, 6, 30),
]

for quantity, minimum, pack, expected in cases:
    actual = reorder_quantity(quantity, minimum, pack)
    status = "ок" if actual == expected else "ошибка"
    print(quantity, minimum, pack, "->", actual, status)
```

Программа печатает:

```text
12 40 10 -> 30 ок
96 60 12 -> 0 ок
7 7 1 -> 0 ок
0 25 5 -> 25 ок
3 30 6 -> 30 ок
```

Такая таблица называется таблицей случаев. Она хранит вход, ожидаемый выход и фактический результат. Когда функция изменится, таблица покажет, что сломалось, без чтения всего кода.

К таблице добавляют проверку ошибок. Вызов `reorder_quantity(12, 40, 0)` должен не вернуть ноль, а отказать:

```text
ValueError: Кратность упаковки должна быть больше нуля
```

Если функция молча вернёт 0 при нулевой упаковке, склад решит, что заказ не нужен, и позиция останется без товара. Ошибка входа должна быть громкой и понятной.

| Вход | Ожидание | Что проверяет |
|---|---|---|
| 12, 40, 10 | 30 | обычный дефицит |
| 96, 60, 12 | 0 | остатка достаточно |
| 7, 7, 1 | 0 | порог |
| 0, 25, 5 | 25 | нулевой остаток |
| 3, 30, 6 | 30 | округление вверх |
| 12, 40, 0 | ошибка | неверная кратность |

Проверка не обязана быть фреймворком. На этом этапе достаточно списка случаев и цикла. Позже появится отдельный инструмент тестирования, но принцип останется: вход, ожидание, сравнение.

Ожидаемое значение берут из правила, а не из запуска функции. Если записать в таблицу то, что функция вернула сегодня, проверка подтвердит любое поведение, включая ошибочное. Для `SKU-1042` ожидание 30 выводится из правила склада: дефицит 28, упаковка 10, значит нужны три коробки. Только после этого число сравнивают с ответом программы.

## Типичные ошибки

**Ошибка первая: функция печатает вместо возврата.** Симптом: отчёт работает, а API дублирует строки. Причина: `print` внутри расчёта. Лечение: вернуть значение, печать оставить вызывающему коду.

**Ошибка вторая: изменяемая глобальная переменная.** Симптом: второй вызов даёт не тот результат. Причина: `global total` или статическое поле. Лечение: передавать текущее значение параметром и возвращать новое.

**Ошибка третья: параметр по умолчанию это список.** В Python `def add_row(row, rows=[])` создаёт один список на все вызовы, и строки накапливаются между отчётами. Лечение: `rows=None` и создание списка внутри функции.

**Ошибка четвёртая: импорт по имени файла.** Симптом: `ModuleNotFoundError` при запуске из другой папки. Причина: запуск не из корня проекта или пакет не найден по пути импорта. Лечение: запускать из корня и держать модули внутри пакета.

**Ошибка пятая: проверка только удачного случая.** Симптом: на пороге или нуле функция врёт. Причина: один тестовый вызов. Лечение: таблица случаев с границами и ошибкой.

## Итоги

- Функция это контракт: имя, параметры, возвращаемое значение и честно указанные побочные эффекты.
- Python использует значения по умолчанию, C# перегрузку методов; именованные аргументы есть в обоих языках.
- Локальная переменная живёт внутри функции, глобальная видна всем и создаёт скрытое состояние.
- Модуль выносит функцию в отдельный файл, а `if __name__ == "__main__"` отделяет запуск от импорта.
- Чистая функция возвращает результат и не печатает, не пишет в файл и не меняет глобальные значения.
- Функцию проверяют таблицей случаев: обычный вход, границы и ошибочный вход.

::quiz
Q: Зачем расчёт заказа выносят в отдельную функцию?
+ Чтобы формула существовала в одном месте и не расходилась между отчётами
- Чтобы программа занимала больше строк
- Чтобы отказаться от параметров
- Чтобы каждый отчёт считал по своей формуле
! Одна копия формулы устраняет расхождение между частями проекта.

Q: Что входит в контракт функции?
+ Имя, параметры и возвращаемое значение
- Побочные эффекты, о которых должен знать вызывающий код
- Цвет подсветки в редакторе
- Число строк внутри функции
! Контракт описывает вход, выход и видимые эффекты вызова.

Q: Чем локальная переменная отличается от глобальной?
+ Локальная доступна только внутри функции
- Локальная доступна во всех модулях
- Глобальная создаётся при каждом вызове
- Глобальная не может хранить число
! Локальная переменная создаётся при вызове и исчезает при возврате.

Q: Что произойдёт при выполнении кода с `total = total + value` без `global`?
+ Возникнет `UnboundLocalError`
- Переменная обновится глобально
- Функция вернёт `None`
- Программа напечатает 0
! Python считает имя локальным на всю функцию и не находит значение при чтении.

Q: Какие способы вернуть два значения существуют в C#?
+ Кортеж
+ `out`-параметры
+ Отдельный класс с двумя свойствами
- Ключевое слово `global`
- Оператор `import`
! C# возвращает одно значение, поэтому пару оформляют кортежем, `out` или классом.

Q: Что делает строка `if __name__ == "__main__"`?
+ Выполняет код только при прямом запуске файла
- Импортирует модуль автоматически
- Запрещает импорт модуля
- Создаёт глобальную переменную
! При импорте условие ложно, и проверочный код не срабатывает.

Q: Какие способы импорта функции из модуля существуют в Python?
+ `import sklad.reorder`
+ `from sklad.reorder import reorder_quantity`
- `using sklad.reorder`
- `include sklad.reorder`
! В Python импорт начинается с `import` или `from`, а `using` относится к C#.

Q: Почему `from module import *` считается плохой практикой?
+ Непонятно, откуда взялось имя в коде
- Импортируются только имена с подчёркиванием
- Импорт работает только в Windows
- Модуль после этого нельзя запустить
! Явный список имён делает зависимости читаемыми.

Q: Что такое побочный эффект функции?
+ Изменение состояния вне функции
- Возврат значения через `return`
- Объявление параметра
- Вызов функции по имени
! Печать, запись файла и изменение глобальной переменной это побочные эффекты.

Q: Почему печать внутри функции расчёта мешает API?
+ Строка появляется в журнале дважды и засоряет вывод
- API перестаёт возвращать число
- Функция начинает работать медленнее в два раза
- Компилятор запрещает сборку
! Расчёт и вывод должны быть разделены, иначе каждый вызывающий получает лишний эффект.

Q: Что проверяет таблица случаев?
+ Вход, ожидаемый результат и фактический результат
- Только синтаксис функции
- Скорость работы программы
- Число строк в модуле
! Таблица сравнивает ожидание с фактом на нескольких входах.

Q: Какие входы обязательно включают в проверку расчёта заказа?
+ Остаток ровно по минимуму
+ Нулевой остаток
+ Дефицит, который не делится на упаковку
- Только самый большой остаток
- Только значение из первого отчёта
! Границы и округление ломаются чаще всего.

Q: Что произойдёт при вызове функции с нулевой кратностью упаковки?
+ Функция должна выдать понятную ошибку
- Функция вернёт 0
- Функция вернёт бесконечность
- Программа напечатает пустую строку
! Деление на ноль нужно отсечь проверкой входа.

Q: Как называется переменная, объявленная внутри функции?
= локальная переменная
= локальная
! Она доступна только внутри функции и исчезает при возврате.

Q: Как называется файл Python, из которого другие файлы импортируют функции?
= модуль
= python-модуль
! Модуль это файл с кодом, который подключают через `import`.
