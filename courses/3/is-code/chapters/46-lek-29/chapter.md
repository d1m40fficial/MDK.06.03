## Пятница, 18:40

В пятницу вечером команда `sklad-plus` выпустила версию 1.0.0. На ноутбуке разработчика всё работало: приёмка проводилась, накладные печатались, отчёт по остаткам открывался за секунду. В понедельник в 08:00 версию поставили на сервер в Москве, и через десять минут кладовщики четырёх площадок увидели ошибку 502.

Причин оказалось три, и все они были в переносе, а не в коде. Порт 8000 на сервере занимала служба мониторинга, поэтому приложение не смогло занять адрес. Путь к базе был относительным, а служба запускалась из другого каталога, и приложение открыло пустой файл. Миграция, которая добавляла поле статуса накладной, на сервере не выполнялась. По отдельности каждая ошибка выглядела мелкой. Вместе они остановили приёмку на четырёх площадках и потребовали отката на предыдущую версию.

**Развёртывание это повторяемый перенос собранного артефакта в подготовленное окружение, настройка этого окружения, запуск и проверка работы.** Развёртывание не является копированием исходников на сервер и не заканчивается моментом, когда процесс появился в списке. Оно заканчивается тогда, когда сервис ответил на проверочный запрос, журнал показал нормальный старт, а данные остались целыми.

В «Северном складе» 120 сотрудников и четыре площадки. Остановка «Склад+» на час означает, что машины с товаром стоят, накладные не оформляются, а менеджеры не видят остатки. Поэтому цена ошибки при переносе выше цены ошибки в локальной разработке. Хорошая процедура развёртывания не делает людей осторожнее, она делает ошибку заметной до того, как её увидят пользователи.

## Что именно переносят

Переносят не папку с исходным кодом, а собранный артефакт. Артефакт это результат сборки, который содержит всё необходимое для запуска и имеет версию. Для Python-приложения это колесо `.whl` с пакетом и метаданными. Для приложения C# это папка публикации с DLL, файлом конфигурации среды выполнения и зависимостями. Для фронтенда это набор статических файлов, для базы это скрипт миграции.

| Этап | Что получается | Что проверяют |
|---|---|---|
| Получение кода | зафиксированная версия из репозитория | тег или хеш коммита |
| Установка зависимостей | окружение сборки | версии из файла зависимостей |
| Тесты | отчёт о прогоне | все проверки зелёные |
| Сборка | артефакт с версией | артефакт создан и не пуст |
| Развёртывание на тесте | работающий тестовый стенд | проверки после запуска |
| Перенос в эксплуатацию | работающий сервис | те же проверки и журнал |

Принцип звучит коротко: **собирают один раз, разворачивают много раз**. Если собирать заново на каждом сервере, версии зависимостей и компилятора могут разойтись, и один и тот же тег даст разное поведение. Артефакт с версией и контрольной суммой позволяет сказать точно, что именно работает на площадке.

Артефакт неизменяем. После сборки его не правят руками и не докладывают в него файлы на сервере. Если нужно исправление, собирают новую версию. Это правило кажется бюрократическим, пока не придётся отвечать на вопрос «что сейчас работает в Туле». С неизменяемым артефактом ответ простой: версия 1.0.0, контрольная сумма такая, журнал сборки такой.

В артефакт не входят данные, секреты и настройки площадки. База `sklad.db`, файл `.env` и журналы лежат отдельно и переживают замену версии. Если положить базу внутрь артефакта, при следующем развёртывании её либо перезапишут, либо потеряют. Если положить туда секрет, он разойдётся по всем копиям и попадёт в архив. Граница простая: артефакт содержит код и его ресурсы, окружение содержит данные и параметры.

Для Python-проекта `sklad-plus` артефакт собирают из корня проекта командой `python -m pip wheel`. Флаг `--no-deps` означает, что в колесо не нужно складывать зависимости: они указаны в метаданных и будут установлены на сервере из файла зависимостей.

```text
python -m pip wheel . --no-deps -w dist
```

```text
Building wheel for sklad-plus (pyproject.toml): finished with status 'done'
Created wheel for sklad-plus: filename=sklad_plus-1.0.0-py3-none-any.whl size=1221
Successfully built sklad-plus
```

В каталоге `dist` появляется файл `sklad_plus-1.0.0-py3-none-any.whl`. Число `1.0.0` это версия, `py3` означает совместимость с Python 3, `none-any` говорит, что колесо не зависит от платформы. Такое имя можно прочитать без открытия файла, и это удобно при откате: предыдущая версия лежит рядом и отличается только номером.

В C# артефакт создаёт команда `dotnet publish -c Release -o publish`. Она собирает проект в релизной конфигурации и складывает в папку `publish` всё, что нужно для запуска: сборки приложения, файлы конфигурации и зависимости. Запускают приложение из этой папки командой `dotnet sklad-plus.dll`, а на Windows может появиться и исполняемый файл. Исходники на сервер не копируют.

| Тип приложения | Артефакт | Как запускают |
|---|---|---|
| Python-пакет | `sklad_plus-1.0.0-py3-none-any.whl` | `python -m sklad_plus.api` в виртуальном окружении |
| C#-приложение | папка `publish` после `dotnet publish` | `dotnet sklad-plus.dll` |
| Статический сайт | каталог с HTML, CSS и JS | веб-сервер отдаёт файлы |
| База данных | скрипт миграции с номером версии | применяют до запуска новой версии |

У артефакта должно быть три опознавательных признака: номер версии, хеш коммита и контрольная сумма файла. Номер версии понятен пользователю и заказчику. Хеш коммита связывает артефакт с точным состоянием исходников. Контрольная сумма подтверждает, что файл не повредился при копировании и не был заменён вручную. В журнале развёртывания записывают все три значения, и тогда через месяц можно точно восстановить, что и откуда взялось.

Хранят артефакты в отдельном месте, а не на ноутбуке разработчика. Подойдёт папка `dist` в конвейере, сетевой каталог или хранилище пакетов. Важно, чтобы старая версия оставалась доступной, пока новая не проверена. Если артефакт существует в единственном экземпляре и лежит только на сервере, откат превращается в поиск файла по чужим машинам.

## Окружение разработки и эксплуатации

Разработка и эксплуатация решают разные задачи, поэтому окружения отличаются. На машине разработчика один пользователь, тестовая база на несколько десятков строк, включённый отладчик и свободный доступ к журналам. В эксплуатации 120 пользователей, 4800 позиций, выключенный отладчик и ограниченный доступ к серверу.

| Признак | Разработка | Тест | Эксплуатация |
|---|---|---|---|
| Пользователи | разработчик | тестировщик | 120 сотрудников |
| Данные | несколько тестовых записей | копия справочников | реальные накладные |
| Отладка | включена | выключена | выключена |
| Журнал | подробный | обычный | предупреждения и ошибки |
| Доступ | локальный | внутри сети | через прокси и VPN |
| Цель | быстро менять код | проверить версию | обеспечить работу склада |

Различие окружений не означает, что они должны быть совершенно разными. Наоборот, чем ближе тестовый стенд к эксплуатации, тем раньше обнаруживаются ошибки. Одинаковыми должны быть версия Python или .NET, версия СУБД, набор зависимостей, структура каталогов и способ запуска. Различаться могут масштаб, данные, секреты и права доступа.

Отдельно разделяют данные и настройки. Тестовая база не должна смотреть в эксплуатационную, даже если схема совпадает. Тестовый секрет не должен подходить к эксплуатационному сервису. Если это правило нарушено, одна ошибка в настройках приводит к записи тестовых накладных в реальный склад. Проверка такого разделения входит в подготовку стенда, а не перекладывается на разработчика.

Фраза «у меня работает» обычно означает, что проверка шла в другом окружении. На машине разработчика мог быть установлен пакет, которого нет в файле зависимостей. Могла стоять другая версия Python. Мог быть другой разделитель пути, другая локаль, другой часовой пояс. Развёртывание начинается с того, что эти различия перечисляют и проверяют, а не надеются на память.

Подготовка сервера включает несколько обязательных шагов. Создают отдельного пользователя службы, чтобы приложение не работало с правами администратора. Создают каталоги для приложения, данных и журналов и выдают права только этому пользователю. Проверяют, что установлена нужная версия среды выполнения. Настраивают брандмауэр: наружу открывают только нужный порт, обычно через обратный прокси, а не напрямую к приложению.

| Что подготовить | Зачем | Признак ошибки |
|---|---|---|
| Пользователь службы | ограничить права приложения | приложение работает от администратора |
| Каталоги и права | хранить данные и журналы отдельно | запись в каталог запрещена |
| Среда выполнения | запустить артефакт | команда `python` не найдена |
| Сетевой порт | принять запросы | соединение отклонено |
| Обратный прокси | закрыть приложение от сети | порт приложения виден всем |
| Часовой пояс | согласовать даты в накладных | время в журнале не совпадает |

Привязка к адресу важнее, чем кажется. Если приложение слушает `127.0.0.1:8000`, оно доступно только с самой машины, и снаружи его отдаёт обратный прокси. Если приложение слушает `0.0.0.0:8000`, оно доступно по всем сетевым интерфейсам, и порт должен быть закрыт брандмауэром. В учебной виртуальной машине с NAT пробрасывают порт: запрос с основной машины приходит на порт гостя, а приложение остаётся внутри виртуальной сети.

Порядок подготовки тоже имеет значение. Сначала создают пользователя и каталоги, затем устанавливают среду выполнения, затем копируют артефакт, затем создают файл настроек, и только после этого запускают службу. Если начать с запуска, приложение создаст файлы от имени того, кто запустил команду, и права придётся исправлять на работающем сервисе. Такая мелочь потом проявляется как «служба не может записать журнал».

## Настройки и миграции на сервере

На сервере настройки берут из окружения или файла, который не попал в репозиторий. Файл `.env` создают из `.env.example`, заполняют значениями площадки и закрывают правами владельца. Профиль `prod` включает проверки, которые запрещают отладочный режим и значение секрета по умолчанию.

Перед запуском новой версии проверяют базу. Миграция это изменение структуры базы, которое переводит её с предыдущей версии на новую. Если новая версия приложения ожидает поле `status` в таблице накладных, а миграция не выполнена, приложение упадёт на первом же запросе. Поэтому порядок такой: резервная копия, миграция, проверка структуры, запуск приложения.

| Шаг | Действие | Ожидаемый результат | Откат |
|---|---|---|---|
| 1 | Резервная копия базы | файл копии создан | копия не нужна |
| 2 | Миграция | таблицы соответствуют версии | применить обратный скрипт |
| 3 | Проверка справочников | 12 категорий на месте | восстановить копию |
| 4 | Запуск приложения | процесс работает | вернуть прежний артефакт |
| 5 | Проверка здоровья | ответ 200 | вернуть прежний артефакт |

Миграция должна быть идемпотентной: повторный запуск не должен ломать базу и создавать дубли. Если миграция уже применена, скрипт проверяет номер версии и завершается без изменений. Это важно при повторном развёртывании после сбоя: инженер не должен гадать, выполнена миграция или нет.

Справочники и начальные данные отделяют от структуры. 12 товарных категорий и 4 площадки это данные, которые могут поставляться отдельным скриптом. 4800 позиций на складе это рабочие данные, их не пересоздают при каждом развёртывании. Если скрипт начальных данных запускается всегда, он может затереть изменения, которые сделали пользователи.

> [!TRADEOFF] Миграция до или после запуска
> Миграция до запуска делает новую схему обязательной для всех. Если новая версия не поднимется, база останется изменённой, и откат потребует обратного скрипта. Миграция после запуска позволяет сохранить старую версию, но приложение может работать со старой схемой. Выбор зависит от того, умеет ли приложение пережить промежуточное состояние.

## Запуск и проверка

Процесс появился в списке, но это ещё не значит, что сервис работает. Приложение могло занять порт и упасть при подключении к базе. Могло ответить на health check и не открыть список товаров. Могло работать, но писать в журнал ошибку на каждом запросе. Поэтому после запуска выполняют набор проверок, и каждая имеет ожидаемый результат.

Первая проверка это процесс и порт. Команда `ss -ltn` в Linux показывает, какие порты слушают. В Windows подойдёт `netstat -ano | findstr :8000`. Если порт занят другим процессом, приложение либо не стартует, либо выбирает другой порт, и тогда балансировщик отправляет запросы не туда.

Вторая проверка это health check, то есть запрос к служебному адресу, который сообщает состояние сервиса. Хороший health check проверяет не только то, что процесс жив, но и то, что доступна база. Если база недоступна, ответ должен быть не 200, а 503, иначе мониторинг будет считать сервис здоровым, пока пользователи видят ошибку.

```text
curl -i http://127.0.0.1:8000/api/health
```

```text
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 49

{"db":"sklad.db","positions":4800,"status":"ok"}
```

Ответ содержит три поля. `status` подтверждает, что приложение отвечает. `db` показывает, к какой базе оно подключено. `positions` равно 4800, то есть приложение видит полный склад, а не пустой файл. Если число равно нулю, значит, открылась не та база, и дальше проверять бизнес-логику бессмысленно.

Третья проверка это чтение данных через API. Она подтверждает, что маршрут, база и формат ответа работают вместе.

```text
curl -s "http://127.0.0.1:8000/api/stock?limit=2"
```

```text
{"items":[{"qty":40,"sku":"SKU-1040"},{"qty":39,"sku":"SKU-1041"}],"total":4800}
```

Здесь важны три вещи: код ответа 200, наличие поля `items` и общее число `total`, равное 4800. Если ответ приходит, но `items` пуст, проблема в данных или фильтре. Если приходит 500, проблема в коде или схеме базы. Если соединение отклонено, проблема в порту или процессе.

Четвёртая проверка это журнал. В нём должны быть строка старта, версия приложения, профиль, путь к базе без секретов и отсутствие трассировок. Если в журнале видно, что приложение запустилось с профилем `dev` или с уровнем `DEBUG`, развёртывание выполнено не по инструкции, даже если health check отвечает 200.

| Проверка | Команда | Хороший результат | Плохой результат |
|---|---|---|---|
| Процесс | список процессов | процесс службы работает | процесса нет |
| Порт | `ss -ltn` | порт слушается | порт занят другим |
| Здоровье | `curl -i .../api/health` | 200 и `positions` 4800 | 503 или 0 позиций |
| Данные | `curl .../api/stock?limit=2` | 200 и две позиции | 500 или пустой список |
| Журнал | чтение файла журнала | старт без ошибок | трассировка или `DEBUG` |

После проверок полезно пройти один пользовательский сценарий. Кладовщик принимает товар, менеджер формирует накладную, администратор смотрит журнал. Это занимает несколько минут и ловит ошибки прав, которые не видны в health check. Если сценарий не проходит, версию не объявляют рабочей, даже если все технические проверки зелёные.

Первые пятнадцать минут после выкладки сервис остаётся под усиленным наблюдением. Смотрят долю ответов с ошибкой, время ответа, число обращений в журнал и жалобы пользователей. Если доля ошибок выше обычной, выкладку останавливают и возвращают предыдущую версию, не дожидаясь конца дня. Порог выбирают заранее: например, не больше одного процента ответов с кодом 500 за пять минут. Без порога спор «это ещё не авария» затягивается, а склад уже не отгружает товар.

## Откат

Откат это возврат к предыдущей рабочей версии. Он должен быть описан заранее, потому что в момент сбоя думать некогда. Минимальный набор: предыдущий артефакт сохранён, резервная копия базы сделана, известна команда остановки службы, известен порядок возврата настроек.

| Сбой | Действие | Что проверяют после |
|---|---|---|
| Приложение не стартует | вернуть прежний артефакт | health check и журнал |
| Ошибка в миграции | восстановить копию базы | структуру и число позиций |
| Порт занят | освободить порт или изменить настройку | `ss -ltn` |
| Ошибки прав | вернуть прежние настройки доступа | пользовательский сценарий |
| Рост ошибок после запуска | остановить выкладку и вернуть версию | долю ошибок за 15 минут |

Откат не всегда возможен без потери данных. Если новая версия уже записала накладные в новую структуру, возврат к старой версии потребует обратного преобразования. Поэтому миграции проектируют так, чтобы старая версия могла работать с новой схемой хотя бы короткое время, или выполняют выкладку в окно, когда записи нет.

Есть более безопасные схемы. Сине-зелёная выкладка держит две версии на разных наборах серверов и переключает трафик после проверки. Канареечная выкладка отправляет новой версии небольшую долю запросов и смотрит на ошибки. Для учебного проекта достаточно одной версии и ручного переключения, но принцип тот же: сначала проверяют на малой нагрузке, потом открывают всем.

## Типичные ошибки

**Сборка на сервере.** На сервере запускают `pip install` из исходников и получают другую версию зависимостей. Симптом: на тесте работает, в эксплуатации падает. Лечение: собирать артефакт в конвейере и переносить готовый файл.

**Забытая переменная окружения.** На новом сервере не задан `SKLAD_DB_PATH` или `SKLAD_SECRET_KEY`. Симптом: приложение стартует со значениями по умолчанию. Лечение: `.env.example`, проверка при старте и журнал источников.

**Порт занят.** Служба мониторинга уже слушает 8000. Симптом: приложение не стартует или работает на другом порту. Лечение: проверить порты до запуска и закрепить номер за приложением.

**Относительный путь и другой рабочий каталог.** Служба запускается из корня, а база ожидается в `data/sklad.db`. Симптом: пустая база. Лечение: явный рабочий каталог и проверка пути при старте.

**Пропущенная миграция.** Новый код ожидает поле, которого нет в базе. Симптом: 500 на первом запросе. Лечение: миграция в процедуре развёртывания и проверка версии схемы.

**Запуск от администратора.** Приложение получает лишние права. Симптом: ошибка незаметна, пока не понадобится восстановление. Лечение: отдельный пользователь службы и минимальные права.

**Нет health check.** Мониторинг проверяет только процесс. Симптом: пользователи видят ошибку, а система считает сервис здоровым. Лечение: health check с проверкой базы и кода 503 при отказе.

**Выкладка в час пик.** Версию ставят в 09:00, когда склад начинает приёмку. Симптом: любая ошибка сразу останавливает работу. Лечение: окно обслуживания и предупреждение пользователей.

**Нет плана отката.** Предыдущий артефакт удалён, копия базы не сделана. Симптом: сбой длится часами. Лечение: хранить предыдущую версию и копию перед миграцией.

> [!PITFALL] Успешный запуск не равен успешной выкладке
> Процесс может работать, health check отвечать 200, а права роли кладовщика уже сломаны. Поэтому после технических проверок проходят один пользовательский сценарий и смотрят журнал за первые минуты.

## Итоги

- Развёртывание переносит собранный артефакт в подготовленное окружение, настраивает его, запускает и проверяет.
- Артефакт собирают один раз, версионируют и не меняют руками на сервере.
- Разработка, тест и эксплуатация различаются данными, доступом и настройками, но совпадают по версии среды и способу запуска.
- Перед запуском готовят пользователя службы, каталоги, порт, прокси и резервную копию базы.
- После запуска проверяют процесс, порт, health check, чтение данных, журнал и один пользовательский сценарий.
- Откат описывают заранее: предыдущий артефакт, копия базы и понятный порядок возврата.

Q: Что такое развёртывание приложения?
+ Перенос собранного артефакта в подготовленное окружение с запуском и проверкой
- Копирование исходников на сервер через удалённый рабочий стол
- Написание новой версии кода прямо на сервере
- Создание резервной копии базы без запуска приложения
! Развёртывание включает артефакт, настройку, запуск и проверку результата.

Q: Почему собирают один артефакт, а разворачивают его много раз?
+ Чтобы исключить различия сборки на разных машинах
- Чтобы не запускать тесты
- Чтобы сервер мог менять исходный код
- Чтобы уменьшить число пользователей
! Один артефакт с версией даёт одинаковое поведение на всех площадках.

Q: Что такое артефакт?
+ Собранный и версионированный результат сборки
- Папка с исходным кодом проекта
- Файл журнала работы приложения
- Список пользователей системы
! Артефакт содержит всё нужное для запуска и имеет версию.

Q: Чем эксплуатация отличается от разработки?
+ Реальными данными и ограниченным доступом
- Обязательным включённым отладчиком
- Отсутствием базы данных
- Работой без резервных копий
! В эксплуатации работают реальные пользователи, а доступ к серверу ограничен.

Q: Зачем нужен health check?
+ Проверить, что сервис и его зависимости работают
- Показать главную страницу пользователю
- Заменить резервное копирование
- Ускорить сборку артефакта
! Проверка здоровья сообщает о состоянии сервиса и базы.

Q: Что делать перед миграцией базы?
+ Сделать резервную копию
- Удалить старые таблицы
- Отключить журнал
- Запустить приложение без настроек
! Копия позволяет вернуться, если миграция или новая версия не подойдут.

Q: Что означает привязка приложения к `127.0.0.1`?
+ Сервис доступен только с этой машины
- Сервис доступен всем в интернете
- Сервис не принимает запросы
- Сервис работает без порта
! Локальная привязка используется вместе с обратным прокси.

Q: Зачем хранить предыдущий артефакт?
+ Чтобы вернуться к рабочей версии при сбое
- Чтобы увеличить размер сервера
- Чтобы заменить резервную копию базы
- Чтобы ускорить миграцию
! Предыдущая версия нужна для отката.

Q: Почему нельзя отлаживать приложение в эксплуатации?
+ Отладчик и подробный журнал раскрывают данные и снижают защиту
- Отладчик ускоряет работу склада
- Отладчик заменяет проверку прав
- Отладчик нужен для резервного копирования
! В эксплуатации отладка выключена, а журнал ограничен предупреждениями и ошибками.

Q: Какие этапы входят в конвейер развёртывания?
+ Прогон тестов
+ Сборка артефакта
+ Проверка после запуска
- Переписывание кода на сервере
! Конвейер проверяет, собирает, переносит и проверяет результат.

Q: Что проверяют после запуска сервиса?
+ Код ответа health check
+ Записи в журнале о старте
+ Количество позиций в базе
- Цвет кнопки на главной странице
! Технические проверки подтверждают работу сервиса и данных.

Q: Какие причины отказа возможны при переносе?
+ Другой занятый порт
+ Отсутствует переменная окружения
+ Не выполнена миграция
- Совпадает версия Python
! Расхождение окружения и пропущенные шаги ломают запуск.

Q: Что входит в подготовку сервера?
+ Отдельный пользователь службы

+ Правила брандмауэра
- Установка отладчика для эксплуатации
