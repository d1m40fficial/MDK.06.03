## Одна идея

Библиотека отправляла напоминания через почтовый сервер колледжа. Всё работало, пока однажды вечером сервер не отключили на профилактику. Библиотекарь нажал «Выдать», система попыталась отправить письмо, не дождалась ответа и показала ошибку. Выдача не сохранилась, хотя книга уже ушла читателю. Утром выяснилось, что часть выдач потеряна, а часть писем ушла дважды.

Причина не в почте. Причина в том, что две системы соединили вызовом, но не договорились, **что делать при отказе**. Интеграция это не строчка кода, которая отправляет запрос. Это контракт: что передаётся, что возвращается, сколько ждём, что повторяем и что считаем успехом.

Дальше разберём три вещи: как устроен обмен по REST, чем синхронный вызов отличается от асинхронного и какие решения делают интеграцию устойчивой к отказам.

## REST и ресурсы

REST описывает обмен через **ресурсы**. Ресурс это именованное множество однотипных объектов: книги, экземпляры, читатели, выдачи, брони. С ресурсом работают методами HTTP, и каждый метод означает определённое действие.

| Метод | Что делает | Пример для библиотеки |
|---|---|---|
| GET | читает ресурс или список | `GET /books?query=Айтматов` |
| POST | создаёт новый объект | `POST /loans` |
| PATCH | меняет часть объекта | `PATCH /loans/41` |
| DELETE | удаляет объект | `DELETE /reservations/17` |

Имя ресурса ставят в существительном и во множественном числе: `/books`, `/readers`, `/loans`. Глагол в адресе не нужен, потому что действие уже выражено методом. Адрес `/getBook?id=5` выдаёт устройство обработчика и плохо сочетается с кэшированием.

Сервер отвечает **кодом состояния** и телом. Код говорит, что произошло, тело содержит данные или описание ошибки. Основные коды стоит знать наизусть, потому что именно по ним клиент решает, что делать дальше.

Коды делятся на группы по первой цифре: 2xx успех, 4xx ошибка клиента, 5xx ошибка сервера. Это деление важно для интеграций. На 4xx повторять запрос бессмысленно: он снова будет отвергнут, пока клиент не исправит данные. На 503 повторять имеет смысл: сервер временно недоступен.

## Контракт API

Контракт это письменное обещание: какие адреса существуют, какие параметры принимают, что возвращают и как выглядят ошибки. Для REST контракт чаще всего описывают в **OpenAPI**: файл, из которого можно получить документацию, примеры и заготовки клиентов.

Хороший контракт отвечает на пять вопросов.

1. **Что передаётся.** Типы полей, обязательность, допустимые значения, максимальная длина.
2. **Что возвращается.** Структура успешного ответа и структура ошибки.
3. **Что означает код.** Не «ошибка», а конкретно: 409 при попытке выдать уже выданный экземпляр.
4. **Как листать список.** Параметры страницы и общее количество, иначе клиент не знает, есть ли ещё записи.
5. **Что считается повтором.** Какой заголовок защищает от двойного создания.

Ошибку описывают единообразно, иначе клиент не сможет её разобрать:

```json
{
  "code": "copy_already_issued",
  "message": "Экземпляр уже выдан другому читателю",
  "field": "copyId",
  "requestId": "b7f1c2"
}
```

Поле `code` нужно программе, поле `message` человеку, `field` указывает на неверное поле формы, `requestId` помогает найти запрос в журналах. Если каждый обработчик возвращает свой формат, клиент обрастает ветками и рано или поздно покажет пользователю сырой текст ошибки.

Отдельный вопрос контракта это версии. Когда правило меняется несовместимо, старый клиент не должен ломаться в тот же день. Поэтому в адресе оставляют номер версии: `/v1/books`, а новую форму поведения открывают как `/v2/books`. Старую версию какое-то время поддерживают и предупреждают клиентов заранее. Молча удалить поле из ответа проще всего, и это самая частая причина, по которой чужое приложение перестаёт работать в понедельник утром.

Листание тоже часть контракта. Клиент передаёт номер страницы и размер, сервер возвращает записи и общее количество. Без общего количества интерфейс не может показать, сколько страниц осталось, а без ограничения размера один запрос может вытянуть весь каталог и положить сервис.

## Синхронный и асинхронный обмен

Синхронный вызов это разговор с ожиданием ответа. Клиент отправил запрос и держит соединение, пока сервер не ответит. Так работает проверка входа через SSO: без ответа нельзя пустить человека в систему.

Асинхронный обмен не ждёт немедленного результата. Отправитель складывает сообщение и идёт дальше, а получатель забирает его, когда сможет. Так работает отправка письма: библиотекарю не нужно ждать почтовый сервер, чтобы выдать книгу.

На рисунке видны разные последствия отказа. Если SSO не ответил за отведённое время, вход не состоится, и это правильно: без подтверждения пускать нельзя. Если почтовый сервер недоступен, письмо остаётся в очереди и уйдёт позже, а выдача книги уже завершена.

Есть третий способ, **вебхук**. Это обратный вызов: одна система заранее сообщает адрес, по которому другая стучится при событии. SSO колледжа может уведомлять библиотеку о блокировке учётной записи. Вебхук удобен, но требует защиты: адрес должен быть известен, запрос подписан, а обработчик обязан быть готов к повторной доставке одного и того же события.

## Идемпотентность и повторные попытки

Сеть ненадёжна. Ответ может потеряться уже после того, как сервер выполнил операцию. Клиент видит таймаут и повторяет запрос, а на сервере появляется вторая выдача той же книги.

**Идемпотентность** это свойство операции, при котором повтор даёт тот же результат, что и первый вызов. `GET` идемпотентен по смыслу: чтение не меняет данные. `PUT` идемпотентен, потому что заменяет объект целиком. `POST` обычно нет: каждый вызов создаёт новый объект.

Для выдачи книги применяют ключ идемпотентности. Клиент присылает заголовок `Idempotency-Key` с уникальным значением. Сервер запоминает ключ и связанный результат. Повторный запрос с тем же ключом возвращает сохранённый ответ и не создаёт вторую выдачу.

```http
POST /loans
Idempotency-Key: 6f1a-42-loan
Content-Type: application/json

{ "copyId": 1187, "readerId": 42 }
```

Повторные попытки без такого ключа опасны там, где операция меняет состояние: выдача, возврат, начисление штрафа, отправка письма. Безопасны чтения и операции, которые явно перезаписывают значение.

Повторяют не всё подряд. Правило простое: повторяют сетевые сбои и коды 5xx, не повторяют 4xx. Между попытками делают паузу, обычно с увеличением, чтобы упавший сервис не получил лавину запросов сразу после восстановления. После исчерпания попыток сообщение отправляют в **мёртвую очередь**, где его разбирает человек.

**Таймаут** это предел ожидания. Без него зависший сосед забирает соединения и потоки, и вскоре перестаёт отвечать сама вызывающая система. Таймаут ставят по времени, которое пользователь готов ждать, а не по времени, за которое сосед «обычно успевает».

> [!TRADEOFF] Синхронно или через очередь
> Синхронный вызов проще: результат известен сразу, ошибку видно на месте. Но он связывает доступность двух систем. Очередь развязывает их, зато добавляет задержку, повторную доставку и необходимость следить за мёртвыми сообщениями. Выбор зависит от того, нужен ли результат прямо сейчас.

::/gate

## Отказы и что делать

Интеграция проверяется не на успешном сценарии, а на отказах. Разберём четыре типичных.

**Таймаут.** Сервис не дождался SSO. Решение: ограничить ожидание, показать понятное сообщение, не создавать полудохлую сессию. Повторять вход автоматически обычно нельзя, человек должен попробовать снова сам.

**Ответ 5xx.** Внешняя система сбоит. Решение: повторить с паузой ограниченное число раз, а если не помогло, сохранить задачу и вернуться к ней позже. Пользователю показывают, что операция принята и будет выполнена.

**Дубликат.** Запрос пришёл дважды. Решение: ключ идемпотентности для изменяющих операций и проверка состояния перед действием.

**Частичный успех.** Книга выдана, письмо не ушло. Решение: разделить операции. Выдача это одно действие, уведомление другое, и провал второго не отменяет первого.

Отсюда правило проектирования: **критичный путь делают коротким и синхронным, всё остальное выносят за него**. Вход в систему критичен, поэтому синхронен. Напоминание о сроке возврата не критично, поэтому идёт через очередь.

| Что сломалось | Что видит пользователь | Что делает система |
|---|---|---|
| SSO не ответил | сообщение о недоступности входа | не пускает, ждёт следующей попытки человека |
| почтовый сервер недоступен | ничего, выдача прошла | держит письмо в очереди и повторяет |
| повтор запроса выдачи | ту же выдачу | возвращает сохранённый результат по ключу |
| очередь переполнена | ничего | ограничивает приём и сообщает администратору |

::/gate

## Ошибки в интеграциях

**Адрес внешней системы в коде.** При переносе на другой стенд сервис стучится на старый адрес. Лечение: адрес в настройках окружения.

**Бесконечные повторы.** Клиент повторяет запрос, сервер отвечает ошибкой, клиент повторяет снова. Лечение: предел попыток и пауза.

**Ответ без разбора кода.** Клиент считает любой ответ успехом, если соединение не оборвалось. Лечение: проверка кода и тела.

**Общая база вместо API.** Две системы читают одни таблицы. Лечение: обмен через контракт, иначе изменение схемы ломает соседа.

**Секреты в репозитории.** Пароль почтового сервера лежит в коде. Лечение: настройки окружения и отдельные учётные записи.

## Проверьте себя

> [!CHECK] Почему отправку письма вынесли в очередь, а проверку входа оставили синхронной?
> Вход нужен немедленно: без ответа SSO нельзя принять решение о доступе. Письмо не влияет на выдачу, поэтому его можно отложить, а очередь защищает от недоступности почтового сервера.

> [!CHECK] Клиент получил таймаут на запрос создания выдачи. Можно ли просто повторить запрос?
> Только если сервер поддерживает ключ идемпотентности. Иначе первый запрос мог выполниться, и повтор создаст вторую выдачу.

> [!CHECK] Сервис отвечает 400 на запрос. Сколько раз его повторять?
> Ни одного. 400 означает ошибку в запросе, и повтор даст тот же результат, пока клиент не исправит данные.

## Итог

- REST работает с ресурсами, действия выражаются методами, результат описывается кодом состояния.
- Контракт фиксирует адреса, поля, коды, формат ошибки и правила листания.
- Синхронный вызов ждёт ответа и зависит от соседа, асинхронный разрывает ожидание через очередь или вебхук.
- Изменяющие операции защищают ключом идемпотентности, иначе повтор создаёт дубликат.
- Повторяют сетевые сбои и 5xx, не повторяют 4xx; таймаут обязателен.
- Критичный путь держат коротким, остальное выносят за него.

## Тест по лекции

::quiz
Q: Что в REST называют ресурсом?
+ Именованное множество однотипных объектов, с которым работают методы
- Файл с исходным кодом обработчика
- Сетевое соединение между сервисами
- Таблицу в базе данных
! Ресурс это книги, выдачи, читатели, адресуемые по своему имени.

Q: Какой метод создаёт новый объект?
+ POST
- GET
- DELETE
- PATCH
! POST создаёт объект, GET читает, PATCH меняет, DELETE удаляет.

Q: Что означает код 409?
+ Конфликт состояния, например экземпляр уже выдан
- Сервер не найден
- Успешное создание
- Нет прав доступа
! 409 говорит, что запрос противоречит текущему состоянию ресурса.

Q: Какой код говорит о временной недоступности сервиса?
+ 503
- 400
- 404
- 422
! 503 означает временную недоступность, такие запросы имеет смысл повторять.

Q: Зачем нужен ключ идемпотентности?
+ Чтобы повтор запроса не создал второй объект
- Чтобы ускорить ответ сервера
- Чтобы заменить авторизацию
- Чтобы сжать тело ответа
! Сервер запоминает ключ и возвращает прежний результат вместо новой операции.

Q: Что такое вебхук?
+ Обратный вызов по адресу, который получатель сообщил заранее
- Регулярный опрос сервера по расписанию
- Метод HTTP для удаления
- Формат описания API
! Вебхук это уведомление от системы при событии, а не опрос.

Q: Почему таймаут обязателен при синхронном вызове?
+ Зависший сосед забирает соединения и потоки вызывающей системы
- Таймаут ускоряет работу соседа
- Без таймаута нельзя поставить ключ идемпотентности
- Таймаут заменяет проверку кода ответа
! Без предела ожидания один медленный сосед останавливает всю цепочку.

Q: Какие коды имеет смысл повторять?
+ 503
- 400
- 401
- 422
! 503 временный, а 4xx требуют исправления запроса, а не повтора.

Q: Какие свойства относятся к хорошему контракту API?
+ Описанные поля, типы и обязательность
+ Единый формат ошибки
+ Правила листания списков
+ Однозначные коды для каждой ситуации
- Адрес сервера, зашитый в клиент
- Свободный текст ошибки без кода
! Контракт фиксирует данные, ошибки, листание и смысл кодов.

Q: В каких случаях применяют асинхронный обмен?
+ Отправка уведомления читателю
+ Задание, которое можно выполнить позже
+ Операция, не влияющая на ответ пользователю
+ Разгрузка пиковой нагрузки
- Проверка пароля при входе
- Получение списка книг для экрана каталога
! Асинхронность уместна там, где результат не нужен немедленно.

Q: Какие меры защищают интеграцию от отказов?
+ Таймаут на каждый вызов
+ Предел повторных попыток с паузой
+ Ключ идемпотентности для изменяющих операций
+ Мёртвая очередь для необработанных сообщений
- Бесконечный повтор до успеха
- Общая база данных вместо контракта
! Устойчивость дают таймауты, ограниченные повторы, идемпотентность и разбор мёртвых сообщений.

Q: Какие методы REST обычно идемпотентны?
+ GET
+ PUT
+ DELETE
+ PATCH при повторной установке того же значения
- POST без ключа идемпотентности
- POST с новым ключом каждый раз
! Повтор идемпотентной операции не меняет результат.

Q: Как называют свойство операции давать тот же результат при повторе?
= идемпотентность
! Идемпотентность защищает от дубликатов при повторной отправке.

Q: Как называют предел ожидания ответа от внешней системы?
= таймаут
! Таймаут не даёт зависшему вызову забрать ресурсы вызывающей системы.

Q: Как называют очередь, куда попадают сообщения после исчерпания попыток?
= мёртвая
! В мёртвой очереди сообщения разбирает человек, а не автоматика.

::/gate
