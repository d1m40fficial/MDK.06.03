## Цель работы

Требование это обещание, которое можно проверить. «Система должна быть удобной» проверить нельзя, а «поиск по названию возвращает результат не дольше секунды при фонде в 50 тысяч книг» можно. Цель работы: собрать реестр требований по своей теме, определить актёров и построить модель прецедентов со сценариями.

Реестр отвечает на вопрос «что нужно», диаграмма прецедентов на вопрос «кто и зачем это делает». Одно без другого не работает: по требованиям нельзя нарисовать границы, а по диаграмме нельзя принять работу.

## Оборудование и программное обеспечение

- Персональный компьютер с браузером.
- draw.io в браузере для диаграммы прецедентов.
- Word или текстовый редактор для реестра и сценариев.
- Excel или табличный редактор для матрицы трассировки.
- Паспорт темы и карта предметной области из предыдущей практики.
- Учебный заказчик или преподаватель в роли заказчика для уточнений.

## Краткие теоретические сведения

**Функциональное требование** описывает, что система делает: найти книгу, оформить выдачу, посчитать штраф. **Нефункциональное требование** описывает, как она это делает: за какое время, с какой доступностью, при какой нагрузке.

**Критерий приёмки** это проверяемое условие, по которому требование принимают. Он содержит число, состояние или наблюдаемый результат. Требование без критерия нельзя ни принять, ни отклонить.

**Приоритет** нужен, чтобы при нехватке времени отказаться от менее важного. Работает шкала Must, Should, Could, Won't: обязательное, желательное, возможное и то, что в этот проект не входит.

**Актёр** это роль, которая получает от системы результат. Актёр бывает человеком и внешней системой. **Прецедент** это законченная цель актёра: найти книгу, продлить выдачу, получить отчёт.

**Связь include** означает обязательную общую часть: и выдача, и продление включают проверку долга. **Связь extend** означает необязательное дополнение: к выдаче может добавиться печать формуляра, но может и не добавиться.

## Ход работы

### Шаг 1. Соберите источники требований

Требования не придумывают, их находят. Для каждой группы источников запишите, что вы из неё взяли.

| Источник | Что даёт | Кто отвечает |
|---|---|---|
| Интервью с заказчиком | Цели, ограничения, приоритеты | Заведующий библиотекой |
| Документы | Правила выдачи, сроки, формы отчётов | Положение о библиотеке |
| Наблюдение за работой | Реальные шаги и узкие места | Библиотекарь на выдаче |
| Существующие таблицы | Состав полей и справочников | Excel с фондом |
| Обратная связь читателей | Жалобы и повторяющиеся запросы | Опрос группы |
| Внешние системы | Форматы обмена и ограничения | Администратор SSO |

Если источник не назван, требование выглядит как ваша выдумка. В реестре оставляйте ссылку на источник в отдельном столбце.

### Шаг 2. Составьте реестр требований

Соберите не меньше пятнадцати требований. Формулируйте каждое так, чтобы его можно было проверить.

| ID | Требование | Тип | Приоритет | Критерий приёмки |
|---|---|---|---|---|
| R-01 | Поиск книги по названию, автору и ISBN | функциональное | Must | Поиск по части названия возвращает список совпадений |
| R-02 | Бронирование свободного экземпляра | функциональное | Must | Бронь получает дату истечения, экземпляр недоступен другим |
| R-03 | Выдача по номеру читательского билета | функциональное | Must | Выдача сохраняется, срок рассчитывается по правилу |
| R-04 | Продление срока не больше двух раз | функциональное | Should | Третье продление отклоняется с сообщением |
| R-05 | Напоминание за два дня до срока | функциональное | Could | Сообщение уходит в очередь за два дня |
| R-06 | Блокировка выдачи при долге | функциональное | Must | Долг больше нуля блокирует новую выдачу |

Остальные требования добавьте по своим процессам: возврат, расчёт штрафа, отчёт, справочник книг, управление читателями, роли доступа.

### Шаг 3. Проверьте формулировки

Пройдите по реестру и перепишите слабые требования.

| Плохо | Почему | Хорошо |
|---|---|---|
| Система должна быстро искать | Нет числа и условия | Поиск отвечает не дольше одной секунды при 50 тысячах книг |
| Удобный интерфейс | Неизмеримо | Библиотекарь оформляет выдачу за три действия без перехода между экранами |
| Надёжное хранение | Нет критерия | Ежедневная резервная копия, восстановление проверено на копии |
| Гибкие отчёты | Неясен состав | Отчёт по задолженностям за период с суммой долга по читателю |
| Защита данных | Не указано, что именно | Пароли хранятся как хеш с солью, персональные данные не попадают в журнал |

Требование с двумя глаголами («найти и забронировать») разделите на два: у них разные критерии и разные сценарии.

### Шаг 4. Расставьте приоритеты

| Приоритет | Значение | Доля в реестре | Пример |
|---|---|---|---|
| Must | Без этого система не работает | Не больше 60 процентов | Выдача, возврат, поиск |
| Should | Важно, но можно отложить | Около 25 процентов | Продление, отчёт |
| Could | Полезно при запасе времени | Около 15 процентов | Напоминания, экспорт |
| Won't | В этот проект не входит | Отдельный список | Мобильное приложение |

Если обязательных требований больше половины, проект расползётся. Проверьте, нельзя ли часть из них перенести в Should.

### Шаг 5. Определите актёров и границы

| Актёр | Цель | Прецеденты |
|---|---|---|
| Читатель | Найти и получить книгу | Поиск, бронирование, продление, просмотр выдач |
| Библиотекарь | Оформить выдачу и возврат без ошибок | Выдача, возврат, расчёт штрафа |
| Администратор | Поддерживать справочники и права | Управление книгами, читателями, ролями |
| Система уведомлений | Доставить сообщение | Напоминание, уведомление о брони |
| SSO колледжа | Подтвердить личность | Вход в систему |

Границу системы на диаграмме рисуйте рамкой. Всё, что внутри, вы проектируете; всё, что снаружи, только используете.

### Шаг 6. Постройте диаграмму прецедентов

Соберите 12 или больше прецедентов. Названия начинайте с глагола: «Забронировать книгу», а не «Бронирование».

| Требование к диаграмме | Как проверить |
|---|---|
| Рамка системы с названием | Внутри только прецеденты |
| Актёры за рамкой | Люди слева, внешние системы справа |
| Связь актёра с прецедентом без стрелки | Линия без наконечника |
| Include для общей обязательной части | Проверка долга входит в выдачу и продление |
| Extend для необязательного дополнения | Печать формуляра расширяет выдачу |
| Нет потоков данных и условий | На диаграмме только цели, не шаги |

Пример связей для библиотеки: «Оформить выдачу» включает «Проверить долг», «Забронировать книгу» расширяется «Уведомить о готовности». Если на диаграмме появился ромб решения, вы рисуете алгоритм, а не прецеденты.

### Шаг 7. Опишите два сценария

Возьмите ключевой прецедент и распишите основной поток по шагам. Для библиотеки это выдача.

| Шаг | Актёр | Действие | Отклик системы |
|---|---|---|---|
| 1 | Библиотекарь | Вводит номер билета | Показывает читателя и активные выдачи |
| 2 | Библиотекарь | Сканирует инвентарный номер | Показывает книгу и её состояние |
| 3 | Система | Проверяет долг и лимит | При долге выдачу блокирует |
| 4 | Система | Рассчитывает срок по правилу | Показывает дату возврата |
| 5 | Библиотекарь | Подтверждает выдачу | Создаёт запись, меняет состояние экземпляра |
| 6 | Система | Ставит напоминание | Добавляет сообщение в очередь |

Альтернативный поток опишите отдельной таблицей: что происходит, если экземпляр уже выдан, читатель заблокирован или лимит исчерпан. У каждого альтернативного шага должен быть номер основного шага, от которого он отклоняется.

В начале сценария укажите предусловие и постусловие. Предусловие для выдачи: читатель найден, экземпляр свободен. Постусловие: запись создана, экземпляр выдан, срок назначен.

### Шаг 8. Постройте матрицу трассировки

| Требование | Прецедент | Сценарий | Покрыто |
|---|---|---|---|
| R-01 | Найти книгу | Основной поток поиска | Да |
| R-02 | Забронировать книгу | Основной и альтернативный | Да |
| R-03 | Оформить выдачу | Сценарий выдачи | Да |
| R-05 | Напомнить о сроке | Сценарий напоминания | Нет, нужен сценарий |

Требование без прецедента означает пропуск в модели. Прецедент без требования означает функцию, которую никто не заказывал.

### Шаг 9. Добавьте нефункциональные требования

| Качество | Требование | Как измерить |
|---|---|---|
| Производительность | Поиск не дольше одной секунды | Замер на фонде 50 тысяч книг |
| Доступность | Не ниже 99 процентов в учебное время | Журнал доступности за месяц |
| Безопасность | Пароли только в виде хеша с солью | Проверка таблицы пользователей |
| Совместимость | Две последние версии Chrome и Edge | Проверка на двух браузерах |
| Восстановление | Потеря данных не больше суток | Дата последней резервной копии |
| Удобство | Выдача за три действия | Подсчёт шагов в сценарии |

Нефункциональное требование без способа измерения не принимают: «быстро» и «надёжно» проверяющий заменит своим пониманием.

### Шаг 10. Проверьте полноту

| Пункт | Проверка |
|---|---|
| В реестре не меньше пятнадцати требований | Подсчёт строк |
| У каждого требования есть критерий приёмки | Нет пустых ячеек |
| У каждого актёра есть хотя бы один прецедент | Сверка диаграммы и таблицы |
| У каждого прецедента есть сценарий | Ссылка на таблицу шагов |
| Обязательных требований не больше 60 процентов | Подсчёт приоритетов |
| Нефункциональные требования измеримы | Есть число и способ проверки |

Скриншот диаграммы не нужен: сдаётся PNG, экспортированный из draw.io. Если диаграмма не читается на листе A4, разбейте её на две: каталог и обслуживание читателей.
