## Цель работы

Одна широкая таблица «Выдачи» удобна, пока в ней десять строк. На сотой строке телефон читателя приходится править в пяти местах, а после удаления последней выдачи исчезает издательство. Нормализация убирает такие места до того, как они станут дефектами.

Цель работы: построить ER-модель ИС «Библиотека колледжа», привести исходную таблицу выдачи к третьей нормальной форме и оформить схему SQL-скриптом. На выходе получаете диаграмму с девятью сущностями и таблицей связи, таблицу функциональных зависимостей, разбор трёх нормальных форм и скрипт, который создаёт таблицы с ключами и ограничениями.

## Краткие теоретические сведения

**Сущность** это тип объекта, о котором система хранит данные: читатель, книга, экземпляр, выдача. На ER-диаграмме сущность рисуют прямоугольником, атрибуты перечисляют внутри.

**Ключ** однозначно определяет строку. Первичный ключ (`PK`) выбирают из естественных или добавляют суррогатный `id`. Внешний ключ (`FK`) ссылается на первичный ключ другой таблицы и задаёт связь. Альтернативный ключ это уникальный атрибут, не выбранный первичным: `ticket_no` у читателя, `isbn` у издания.

**Связь** показывает, сколько экземпляров одной сущности связано с экземплярами другой. Кардинальность бывает «один к одному», «один ко многим» и «многие ко многим». Связь многие ко многим нельзя оставить в таблицах напрямую: её разбивают промежуточной таблицей с двумя внешними ключами и составным первичным ключом.

**Обязательность** отвечает на вопрос, может ли связь отсутствовать. У выдачи всегда есть читатель и экземпляр, значит оба внешних ключа обязательны (`NOT NULL`). У читателя может не быть ни одной выдачи, поэтому со стороны читателя кратность `0..*`.

**Функциональная зависимость** `A → B` означает, что значение `A` определяет ровно одно значение `B`. В таблице читателей `reader_id → full_name, phone`. Зависимость бывает частичной (атрибут зависит от части составного ключа) и транзитивной (атрибут зависит от неключевого атрибута).

**Нормальные формы.** Первая (`1НФ`) требует атомарных значений: в ячейке одно значение, без списков через запятую. Вторая (`2НФ`) требует, чтобы все неключевые атрибуты зависели от всего составного ключа, а не от его части. Третья (`3НФ`) запрещает транзитивные зависимости: неключевой атрибут не должен зависеть от другого неключевого атрибута.

**Аномалии** это цена ненормализованной схемы. Аномалия вставки: нельзя добавить издательство, пока нет книги. Аномалия обновления: телефон читателя приходится менять в каждой его выдаче. Аномалия удаления: вместе с последней выдачей пропадает информация о книге.

## Ход работы

### Шаг 1. Выделите сущности

Возьмите модули из реестра требований: каталог, экземпляры, выдача, бронирование, читатели, штрафы. Для каждой сущности назовите назначение, первичный ключ и естественный уникальный атрибут.

| Сущность | Назначение | Первичный ключ | Уникальный атрибут |
|---|---|---|---|
| Читатель | Учёт читателя и его группа | reader_id | ticket_no |
| Группа | Учебная группа и куратор | group_id | name |
| Издание | Описание книги | book_id | isbn |
| Автор | Автор книги | author_id | full_name |
| Издательство | Название и город | publisher_id | name |
| Экземпляр | Физический экземпляр издания | copy_id | inventory_no |
| Выдача | Факт выдачи и срок возврата | loan_id | нет |
| Бронь | Заявка на издание | reservation_id | нет |
| Штраф | Начисление за просрочку | fine_id | нет |

Проверьте, что у каждой сущности есть хотя бы два собственных атрибута.

### Шаг 2. Постройте ER-модель

Разместите сущности на листе draw.io и выберите нотацию crow's foot. У каждой сущности покажите имя, первичный ключ с пометкой `PK` и внешние ключи с пометкой `FK`. Связи подпишите глаголом: «читатель получает выдачу», «издание содержит экземпляры».

Обязательные связи:

- группа содержит читателей, кратность `1` к `0..*`;
- издательство выпускает издания, `1` к `0..*`;
- издание написано авторами, `0..*` к `0..*` через таблицу `book_author`;
- издание содержит экземпляры, `1` к `1..*`, композиция;
- читатель получает выдачи, `1` к `0..*`;
- экземпляр участвует в выдачах, `1` к `0..*`;
- выдача может иметь штраф, `1` к `0..1`;
- читатель создаёт брони, `1` к `0..*`.

Связь многие ко многим между изданием и автором обязательно разбейте промежуточной сущностью. Прямая линия `M:N` на ER-диаграмме допустима как концептуальная модель, но в схеме базы она станет таблицей.

### Шаг 3. Проверьте кардинальность по правилам

| Связь | Концы | Кардинальность | Обязательность | Правило предметной области |
|---|---|---|---|---|
| Группа и читатель | 1 к 0..* | один ко многим | группа обязательна | Читатель числится в одной группе |
| Издание и экземпляр | 1 к 1..* | один ко многим | обязательна | Издание без экземпляров не выдаётся |
| Издание и автор | 0..* к 0..* | многие ко многим | необязательна | У книги может быть несколько авторов |
| Читатель и выдача | 1 к 0..* | один ко многим | выдача без читателя невозможна | Новый читатель ещё не брал книг |
| Выдача и штраф | 1 к 0..1 | один к нулю или одному | необязательна | Штраф только при просрочке |

Если кардинальность вызывает спор, найдите правило в положении о библиотеке.

### Шаг 5. Приведите таблицу к первой нормальной форме

Уберите повторяющиеся группы и составные значения. Авторов вынесите в отдельную сущность, для связи заведите `book_author`. Группу и куратора оставьте до третьего шага, но телефон читателя продублируйте осознанно: на этом шаге важна только атомарность.

| Что нарушено | Как выглядит | Исправление |
|---|---|---|
| Составное значение | `Стругацкий А., Стругацкий Б.` | Две строки в `author`, две связи в `book_author` |
| Повторяющаяся группа | Три книги одного издания в разных строках | Отдельная сущность `copy` |
| Нет первичного ключа | Строка определяется парой читатель и книга | Добавить `loan_id` |

После первого шага каждая ячейка содержит одно значение, у каждой строки есть ключ.

### Шаг 6. Приведите таблицу ко второй нормальной форме

В таблице `book_author` ключ составной: `(book_id, author_id)`. Атрибут `author_name` зависит только от `author_id`, то есть от части ключа. Это частичная зависимость.

| Таблица | Ключ | Зависимость | Нарушение | Решение |
|---|---|---|---|---|
| book_author | book_id, author_id | author_id → author_name | Частичная | Вынести `author_name` в `author` |
| book_author | book_id, author_id | book_id → title | Частичная | Вынести `title` в `book` |
| loan | loan_id | loan_id → reader_id, copy_id | Нет | Ключ простой, зависимость полная |

Проверьте остальные таблицы: если ключ простой, вторая форма выполняется автоматически при выполненной первой.

### Шаг 7. Приведите таблицу к третьей нормальной форме

Найдите транзитивные зависимости. В строке выдачи `reader_id → group_id → curator`: куратор зависит от группы, а группа от читателя. Город зависит от издательства, а издательство от книги.

| Было | Зависимость | Стало |
|---|---|---|
| reader: group_name, curator | reader_id → group_id → curator | `reader_group(group_id, name, curator)` |
| book: publisher, city | book_id → publisher_id → city | `publisher(publisher_id, name, city)` |
| loan: fine_rate | loan_id → fine_rate | `fine(loan_id, days, amount)` по правилу расчёта |

После декомпозиции неключевые атрибуты зависят только от ключа своей таблицы. Проверьте результат вопросом: если поменялся куратор группы, сколько строк придётся обновить? В третьей нормальной форме одна.

### Шаг 8. Напишите SQL-скрипт

Создайте таблицы в порядке, где родитель появляется раньше потомка. Включите проверку внешних ключей: в SQLite она выключена по умолчанию.

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE reader_group (
  group_id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  curator TEXT NOT NULL
);

CREATE TABLE reader (
  reader_id INTEGER PRIMARY KEY,
  ticket_no TEXT NOT NULL UNIQUE,
  full_name TEXT NOT NULL,
  phone TEXT,
  group_id INTEGER NOT NULL REFERENCES reader_group(group_id)
);

CREATE TABLE publisher (
  publisher_id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  city TEXT NOT NULL
);

CREATE TABLE book (
  book_id INTEGER PRIMARY KEY,
  isbn TEXT NOT NULL UNIQUE,
  title TEXT NOT NULL,
  year INTEGER CHECK (year BETWEEN 1500 AND 2100),
  publisher_id INTEGER NOT NULL REFERENCES publisher(publisher_id)
);

CREATE TABLE author (
  author_id INTEGER PRIMARY KEY,
  full_name TEXT NOT NULL UNIQUE
);

CREATE TABLE book_author (
  book_id INTEGER NOT NULL REFERENCES book(book_id) ON DELETE CASCADE,
  author_id INTEGER NOT NULL REFERENCES author(author_id),
  PRIMARY KEY (book_id, author_id)
);

CREATE TABLE copy (
  copy_id INTEGER PRIMARY KEY,
  inventory_no TEXT NOT NULL UNIQUE,
  book_id INTEGER NOT NULL REFERENCES book(book_id),
  status TEXT NOT NULL DEFAULT 'available'
    CHECK (status IN ('available', 'reserved', 'issued', 'written_off'))
);

CREATE TABLE loan (
  loan_id INTEGER PRIMARY KEY,
  copy_id INTEGER NOT NULL REFERENCES copy(copy_id),
  reader_id INTEGER NOT NULL REFERENCES reader(reader_id),
  issued_at TEXT NOT NULL,
  due_at TEXT NOT NULL,
  returned_at TEXT,
  CHECK (due_at > issued_at)
);

CREATE TABLE reservation (
  reservation_id INTEGER PRIMARY KEY,
  book_id INTEGER NOT NULL REFERENCES book(book_id),
  reader_id INTEGER NOT NULL REFERENCES reader(reader_id),
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'new'
    CHECK (status IN ('new', 'confirmed', 'ready', 'issued', 'cancelled', 'expired'))
);

CREATE TABLE fine (
  fine_id INTEGER PRIMARY KEY,
  loan_id INTEGER NOT NULL UNIQUE REFERENCES loan(loan_id),
  days INTEGER NOT NULL CHECK (days > 0),
  amount NUMERIC NOT NULL CHECK (amount > 0),
  paid_at TEXT
);
```

Выполните скрипт на `sqliteonline.com`. Затем вставьте по две строки в справочники и по одной в зависимые таблицы.

```sql

```

### Шаг 9. Проверьте схему запросами

Проверка состоит из трёх частей: связи собираются, дубликатов нет, ограничение работает.

```sql
SELECT b.title, a.full_name AS author, c.inventory_no
FROM book b
JOIN book_author ba ON ba.book_id = b.book_id
JOIN author a ON a.author_id = ba.author_id
JOIN copy c ON c.book_id = b.book_id
ORDER BY b.title;

SELECT ticket_no, COUNT(*) AS cnt
FROM reader
GROUP BY ticket_no
HAVING COUNT(*) > 1;

INSERT INTO loan (copy_id, reader_id, issued_at, due_at)
VALUES (999, 1, '2026-09-20', '2026-10-04');
```

Первый запрос возвращает книгу с автором и экземпляром. Второй возвращает пустой результат: уникальность билета работает. Третий завершается ошибкой `FOREIGN KEY constraint failed`: ссылка на несуществующий экземпляр запрещена. Если третий запрос прошёл, `PRAGMA foreign_keys` не выполнился, и это нужно исправить.

Приложите скриншот третьего запроса с текстом ошибки. Скриншоты самой диаграммы и скрипта не нужны: они сдаются файлами.
