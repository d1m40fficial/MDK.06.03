## Одна идея

База данных это не «место, где лежат данные», а **последняя линия защиты правил**. Если правило «нельзя выдать один экземпляр двум читателям» записано только в коде, то рано или поздно найдётся второй путь записи, который о нём не знает: скрипт переноса, ручная правка в админке, повторная попытка после сбоя. База, которая умеет отвергать такую запись сама, спасает от целого класса ошибок.

Из этого следуют три решения, о которых эта лекция. Первое: доступ к базе идёт через узкую границу, обычно через репозиторий, чтобы запросы не расползались по обработчикам. Второе: изменение нескольких связанных записей оформляется транзакцией, иначе система останется в половинчатом состоянии. Третье: схема меняется только миграцией, потому что ручная правка в рабочей базе не воспроизводится на другой машине.

Библиотека колледжа даёт удобный масштаб для проверки: несколько таблиц, понятные правила, предсказуемые операции. На ней видно и цену решения, и цену его отсутствия.

Слева приложение, которое знает только про интерфейс: «найди свободный экземпляр книги», «запиши выдачу». В середине репозиторий, объявленный доменом. Справа адаптер, который умеет говорить на языке конкретной СУБД. Внизу миграции, единственный законный способ изменить схему.

Такая граница нужна не для красоты. Она позволяет проверить сценарий выдачи на подставном репозитории, без базы, и заменить СУБД, не переписывая правила. И она же не даёт запросу появиться там, где его никто не ищет.

## Транзакции и ACID

Операция выдачи книги меняет несколько записей: экземпляр становится выданным, появляется запись о выдаче, у читателя уменьшается доступный лимит. Если между этими записями произойдёт сбой, библиотека получит книгу, которой нет на полке, или читателя с чужим долгом.

**Транзакция** это набор операций, который применяется целиком или не применяется вовсе. Четыре её свойства объединяют аббревиатурой ACID: атомарность (всё или ничего), согласованность (правила и ограничения соблюдены), изолированность (параллельные транзакции не видят промежуточных состояний друг друга), долговечность (после подтверждения данные переживут сбой).

```sql
BEGIN;

UPDATE copy
   SET status = 'issued'
 WHERE id = 1042
   AND status = 'available';

INSERT INTO loan (copy_id, reader_id, issued_at, due_at)
VALUES (1042, 77, '2026-02-03', '2026-02-24');

COMMIT;
```

Обратите внимание на условие `AND status = 'available'`. Оно делает обновление защищённым: если между чтением и записью другой библиотекарь успел выдать тот же экземпляр, обновление затронет ноль строк. Приложение обязано это заметить и откатить транзакцию, иначе в базе появится вторая выдача на занятый экземпляр. Проверка количества изменённых строк это не формальность, а часть правила.

> [!TRADEOFF]
> Чем шире транзакция, тем дольше держатся блокировки и тем больше запросов ждут. Транзакцию открывают вокруг одной бизнес-операции, а не вокруг всего HTTP-запроса: отправка письма или вызов внешнего сервиса внутри неё держит базу занятой, пока работает сеть.

Отдельно про изоляцию. Большинство СУБД по умолчанию работают на уровне «чтение подтверждённых данных»: транзакция видит только завершённые изменения. Этого достаточно для выдачи книги, но не для отчёта, который читает десятки тысяч строк и должен видеть согласованный срез. Для отчётов либо берут более строгий уровень изоляции, либо строят его по копии базы.

## Индексы: скорость за отдельную плату

Таблица без индекса это стопка записей, которую при поиске приходится просматривать целиком. Индекс это отдельная структура, обычно дерево, где значения столбца упорядочены и связаны со строками таблицы. Поиск по индексированному столбцу превращается из просмотра тысяч строк в несколько шагов по дереву.

Для библиотеки напрашиваются три индекса. Поиск книги по ISBN. Поиск выдач читателя по его номеру. Поиск просроченных выдач по сроку возврата. Первые два ускоряют повседневные операции, третий ночной отчёт по задолженностям.

```sql
CREATE INDEX idx_loan_reader_due ON loan (reader_id, due_date);
```

Составной индекс работает по правилу левого префикса: он поможет запросу с условием по `reader_id`, поможет запросу с `reader_id` и `due_date`, но почти не поможет запросу только по `due_date`. Поэтому порядок столбцов в индексе это проектное решение, а не случайность.

За скорость платят трижды. Индекс занимает место на диске. Каждая вставка и обновление обязаны обновить и индекс, поэтому массовая загрузка каталога с индексами идёт медленнее. И индекс устаревает: если запросы изменились, он может годами лежать мёртвым грузом. Отсюда правило: индекс добавляют под конкретный запрос, а не «на всякий случай».

Проверяют это планом выполнения. В большинстве СУБД команда `EXPLAIN` показывает, будет ли использован индекс или просмотр всей таблицы. Читать план стоит до того, как жаловаться на медленный отчёт.

## Ограничения, представления, права

Схема защищает правила не только индексами. **Ограничения** описывают то, что не должно случиться никогда: внешний ключ не даст записать выдачу на несуществующий экземпляр, `NOT NULL` не даст оставить выдачу без читателя, `CHECK` не пропустит отрицательный штраф, уникальный индекс не даст двум читателям забронировать один экземпляр на одну дату.

Выбор ограничения это выбор модели. Если по правилам библиотеки у экземпляра может быть не больше одной активной выдачи, это выражается частичным уникальным индексом или отдельным статусом, а не надеждой на аккуратность кода.

**Представление** это сохранённый запрос, который выглядит как таблица. Для отчёта по задолженностям удобно один раз описать соединение выдач, читателей и книг, а потом обращаться к нему по имени. Представление не хранит данные, оно их показывает, поэтому всегда актуально. Но и не ускоряет запрос само по себе: это способ спрятать сложность, а не заменить индекс.

Права доступа тоже часть схемы. Учётная запись приложения получает только те операции, которые ей нужны: чтение каталога, запись выдач, никакого удаления таблиц. Это тот же принцип узкой границы, только на уровне СУБД.

## Миграции: схема как версия

Схема меняется вместе с требованиями: появляется штраф, добавляется срок брони, требуется хранить причину отказа. Если каждое изменение делать вручную в клиенте СУБД, то через год никто не сможет собрать такую же базу на новой машине. **Миграция** это файл с изменением схемы и номером версии, который применяется по порядку.

```sql
-- 007_add_fine_amount.sql
ALTER TABLE loan
  ADD COLUMN fine_amount NUMERIC(10,2) NOT NULL DEFAULT 0;
```

Файл миграции лежит в репозитории рядом с кодом и применяется той же командой на всех средах: на машине разработчика, на тестовом стенде, в рабочей системе. Порядок применения хранится в служебной таблице, поэтому повторный запуск не применяет файл дважды.

Опасность появляется, когда приложение и схема выпускаются не одновременно. Безопасный приём это расширение и сжатие. Сначала добавляют новый столбец, который не мешает старой версии, и заполняют его. Потом выпускают код, который пишет в оба места и читает из нового. И только после этого удаляют старый столбец. Так каждая версия приложения работает со схемой, которая её не ломает.

Обратная операция тоже планируется. Откат миграции это отдельный файл, а не «удалить строчку и перезапустить»: если столбец уже заполнен данными, простое удаление их потеряет.

## Резервные копии и восстановление

Копия нужна не для отчёта, а для продолжения работы после потери данных. Поэтому у копирования два измеримых параметра. **RPO** это сколько данных допустимо потерять, то есть как часто снимается копия. **RTO** это сколько времени допустимо восстанавливаться.

Для библиотеки разумные значения выглядят так: копия раз в сутки плюс журнал изменений, потеря не больше часа работы, восстановление за пару часов. Для системы расчётов зарплаты требования жёстче, для архива старых отчётов мягче. Числа берут из требований, а не из удобства администратора.

Главная ошибка здесь не редкая копия, а непроверенная копия. Файл может быть битым, архив неполным, а пароль от хранилища утерянным. Поэтому копию регулярно восстанавливают на отдельную машину и сверяют количество записей. Пока восстановление ни разу не проверяли, копии юридически существуют, а фактически нет.

> [!PITFALL] Копия на том же диске
> Резервная копия, лежащая рядом с базой на том же сервере, защищает от ошибки в запросе, но не от отказа диска или шифровальщика. Копию хранят отдельно и ограничивают к ней доступ.

## Что даёт схема

Схема влияет на систему в трёх местах одновременно. На скорости: индексы и правильные типы сокращают объём чтения. На надёжности: ограничения не дают появиться несогласованным данным. На стоимости изменений: чем точнее модель, тем дешевле добавить новую функцию.

Возьмём поиск книги. Запрос ищет по названию и автору, сортирует по году издания и показывает первые двадцать результатов. Если название хранится одной строкой, поиск по части слова требует просмотра таблицы. Если добавлен индекс по названию, поиск по началу строки ускоряется, а поиск по любому фрагменту всё равно останется медленным. Это ограничение модели, а не настройки сервера.

Возьмём штраф. Если сумма штрафа вычисляется в отчёте каждый раз, правило дублируется и расходится с расчётом при возврате. Если сумма хранится в записи о выдаче и заполняется в момент возврата, у неё один источник, но появляется вопрос: что делать при изменении тарифа задним числом. Оба решения допустимы, но выбор надо сделать осознанно и записать.

## Типичные ошибки

**Запрос в цикле.** Приложение загружает двадцать выдач, а затем для каждой отдельно запрашивает книгу и читателя. Двадцать один запрос вместо одного соединения. Симптом: страница открывается секунды, хотя таблицы маленькие. Лечение: один запрос с соединением или пакетная загрузка по списку ключей.

**Транзакция на весь запрос.** Транзакция открывается в начале обработки и закрывается после отправки письма. Симптом: под нагрузкой копятся ожидания, а при таймауте письма откатывается уже подтверждённая выдача. Лечение: короткая транзакция вокруг записи, уведомление после подтверждения.

**Ручная правка схемы.** Столбец добавили в клиенте на рабочей базе, на тестовой забыли. Симптом: тесты проходят, выпуск падает. Лечение: только миграции, один и тот же набор на всех средах.

**Отсутствие ограничений.** Все проверки в коде, база принимает что угодно. Симптом: через месяц в отчёте появляются выдачи с пустым читателем, и никто не знает, откуда они. Лечение: внешние ключи, `NOT NULL`, `CHECK`, уникальные индексы.

> [!KEY]
> Схема это не картинка для отчёта, а работающий механизм. Каждое ограничение и каждый индекс должны отвечать на вопрос «какое правило или какой запрос они обслуживают».

## Проверьте себя

> [!CHECK] Библиотекарь дважды нажал кнопку «Выдать» на одном экземпляре. Что должно остановить вторую выдачу?
> Обновление статуса с условием `status = 'available'` затронет ноль строк, приложение увидит это и откатит транзакцию. Дополнительно помогает уникальный индекс на активную выдачу экземпляра: он отклонит вторую запись даже при ошибке в коде.

> [!CHECK] Отчёт по задолженностям открывается восемь секунд. Индекс по `due_date` уже есть. Что проверить в первую очередь?
> План выполнения запроса. Возможно, условие написано так, что индекс не применяется: например, дата обёрнута функцией или сравнивается с вычисляемым выражением. Второй подозреваемый это соединение с таблицей читателей без индекса по внешнему ключу.

> [!CHECK] Восстановление из копии занимает шесть часов, а допустимо два. Что менять: частоту копирования или способ восстановления?
> Частота копирования отвечает за потерю данных, а не за скорость возврата в строй. Здесь нужно ускорять восстановление: держать копию в готовом к запуску виде, заранее подготовить сервер, проверить процедуру на учебном стенде.

> [!RECAP]
> - База хранит истину и последней защищает правила ограничениями, а не только код.
> - Доступ идёт через репозиторий, SQL не расползается по обработчикам.
> - Транзакция охватывает одну бизнес-операцию; проверка числа изменённых строк обязательна.
> - Индекс ускоряет чтение и замедляет запись, поэтому его добавляют под конкретный запрос.
> - Схема меняется миграциями, копии проверяются восстановлением, а не фактом создания.

Q: Что гарантирует транзакция?
+ Набор операций применяется целиком или не применяется вовсе
- Все запросы выполняются параллельно
- Данные автоматически копируются на другой сервер

- Асинхронность
- Архивность
! ACID расшифровывается как атомарность, согласованность, изолированность, долговечность.

Q: Зачем нужен индекс в таблице?
+ Чтобы находить строки по условию без просмотра всей таблицы
- Чтобы уменьшить размер таблицы на диске
- Чтобы автоматически проверять права пользователя
- Чтобы хранить резервную копию строк
! Индекс это упорядоченная структура, ускоряющая поиск по столбцу.

Q: Чем платят за добавление индекса?
+ Замедлением вставки и обновления и местом на диске
- Потерей возможности делать соединения таблиц
- Невозможностью использовать транзакции
- Увеличением числа таблиц в схеме
! Каждая запись должна обновить и индекс, поэтому запись становится дороже.

Q: Что такое представление в базе данных?
+ Сохранённый запрос, который выглядит как таблица
- Копия таблицы, обновляемая по расписанию
- Служебная таблица с версиями схемы
- Индекс по нескольким столбцам
! Представление не хранит данные, а показывает результат запроса.

Q: Зачем нужны миграции?
+ Чтобы изменения схемы были версионированы и воспроизводимы
- Чтобы ускорить выполнение тяжёлых запросов
- Чтобы заменить резервное копирование
- Чтобы скрыть структуру таблиц от приложения
! Один и тот же набор миграций применяется на всех средах.

Q: Что проверяет ограничение внешнего ключа?
+ Что ссылка указывает на существующую строку
- Что значение столбца уникально во всей таблице
- Что пользователь имеет право на запись
- Что индекс используется в запросе
! Внешний ключ защищает связь между таблицами от висячих ссылок.

Q: Где должна проходить граница транзакции?
+ Вокруг одной бизнес-операции
- Вокруг всего HTTP-запроса вместе с отправкой письма
- Вокруг каждого отдельного оператора SQL
- Вокруг всей ночной пакетной обработки
! Широкая транзакция держит блокировки и ждёт внешние вызовы.

Q: Что такое репозиторий в архитектуре приложения?
+ Граница доступа к данным с интерфейсом, объявленным доменом
- Папка для хранения резервных копий
- Служебная таблица с журналом изменений
- Отдельный сервер базы данных
! Репозиторий скрывает SQL и позволяет заменить хранилище.

Q: Чем опасно ручное изменение схемы в рабочей базе?
+ Схема перестаёт воспроизводиться на других средах
- СУБД автоматически удаляет все индексы
- Транзакции перестают быть атомарными
- Резервные копии становятся не нужны
! Изменение, сделанное руками, не попадёт в миграции и разойдётся со стендами.

Q: Какие свойства входят в ACID?
+ Атомарность
+ Согласованность
+ Изолированность
+ Долговечность
- Масштабируемость
- Идемпотентность
! Четыре свойства транзакции описывают её надёжность, а не скорость.

Q: Что даёт правильно выбранный индекс?
+ Ускоряет выборку по условию
+ Может поддерживать уникальность значений
+ Ускоряет сортировку по индексированному столбцу
- Уменьшает объём таблицы
- Ускоряет массовую вставку строк
! Индекс помогает чтению, но добавляет работу при записи.

Q: Что входит в разумную практику резервного копирования?
+ Регулярное снятие копий по требованиям к потере данных
+ Проверка восстановления на отдельной машине
+ Хранение копии отдельно от основной системы
- Хранение копии на том же диске, что и база
- Отказ от журнала изменений ради простоты
! Копия ценна только тогда, когда из неё действительно восстановили данные.

Q: Как называется набор операций, который выполняется целиком или не выполняется вовсе?
= транзакция
= transaction
! Это транзакция; её свойства описывают аббревиатурой ACID.

Q: Как называется версионированное изменение схемы базы, применяемое по порядку?
= миграция
= миграции
! Миграции хранятся в репозитории и применяются одинаково на всех средах.
