## Цель работы

Макет из практики 10 показывает экраны по отдельности. Пока экраны не связаны, нельзя ответить на простой вопрос: сколько действий отделяет читателя от брони и что он увидит, если книга уже занята. Прототип собирает экраны в маршрут, а документация объясняет этот маршрут словами.

Цель работы: собрать кликабельный прототип ИС «Библиотека колледжа» по утверждённому макету, описать экраны и сценарии в проектном документе и сверить результат с реестром требований.

Результат работы: файл прототипа с несколькими связанными страницами и документ описания, по которому другой человек проходит те же маршруты и получает тот же результат.

## Оборудование и программное обеспечение

- Персональный компьютер с браузером.
- draw.io в браузере, режим нескольких страниц и ссылок между ними.
- Текстовый редактор Word.
- Файлы предыдущих работ: макет интерфейса из практики 10, реестр требований из практики 1, ER-модель из практики 4, описание API из практики 8.
- Папка проекта для версий файлов.

## Краткие теоретические сведения

**Прототип** это модель интерфейса, которая показывает структуру экранов и переходы между ними. Он не заменяет макет и не содержит финальной вёрстки: его задача проверить маршрут пользователя и договориться о поведении системы.

**Кликабельный прототип** связывает экраны ссылками. Проверяющий нажимает кнопку и попадает на следующий экран, а не листает картинки. В draw.io для этого у фигуры задают ссылку на другую страницу того же файла.

**Точность прототипа** бывает разной. Каркас показывает блоки и подписи без цвета и изображений. Детализированный прототип повторяет сетку, типографику и состояния элементов. Для проверки сценария достаточно каркаса, для показа заказчику нужен второй вариант.

**Экран** описывают паспортом: назначение, роль, элементы, действия, переходы и состояния. Паспорт нужен, чтобы разработчик не догадывался, что делает кнопка.

**Сценарий** это последовательность шагов пользователя от цели до результата. Сценарий связывает экраны с требованиями: каждый шаг опирается на требование, каждый экран закрывает хотя бы один шаг.

**Проектная документация** фиксирует решение и его границы. В комплект входят техническое задание, описание экранов, руководство пользователя и пояснительная записка. Для прототипа достаточно разделов о назначении, ролях, экранах, сценариях и ограничениях.

**Трассировка** показывает связь требования с экраном и элементом. Если требование не имеет экрана, оно не реализовано в прототипе. Если экран не связан с требованием, он лишний или требование пропущено.

## Ход работы

### Шаг 1. Зафиксируйте состав прототипа

Возьмите макет из практики 10 и реестр требований. В прототип включайте только экраны, которые нужны для двух сквозных сценариев: бронирование книги читателем и выдача экземпляра библиотекарем. Остальные экраны добавьте, если без них рвётся маршрут.

| ID | Экран | Роль | Требование | Что проверяет |
|---|---|---|---|---|
| S1 | Вход | все | R1 | Понятность формы и сообщений об ошибке |
| S2 | Каталог | читатель | R2 | Поиск, фильтры, пустой результат |
| S3 | Карточка книги | читатель | R3 | Доступность и число экземпляров |
| S4 | Бронирование | читатель | R4 | Подтверждение и отмена |
| S5 | Выдача | библиотекарь | R5 | Поиск читателя, ввод кода экземпляра |
| S6 | Задолженности | библиотекарь | R6 | Просрочка и штраф |
| S7 | Отчёт | администратор | R7 | Период и выгрузка |

Номера требований возьмите из своего реестра: они могут отличаться, важна связь, а не совпадение цифр.

### Шаг 2. Соберите каркас в draw.io

Создайте файл с семью страницами. На каждой странице одна и та же сетка: шапка с названием системы и ролью, боковое меню, рабочая область. Одинаковая сетка помогает проверяющему не переучиваться на каждом экране.

Правила каркаса:

- Подписи элементов пишите словами пользователя, без внутренних кодов.
- Кнопку основного действия делайте одну на экран.
- Для таблиц показывайте шапку и три строки, остальное заменяйте полосой.
- Для формы показывайте поля, подсказки и место сообщения об ошибке.

Страницы назовите по ID и смыслу: `S1 Вход`, `S2 Каталог` и так далее. Имена страниц попадут в ссылки, поэтому переименование после сборки ломает переходы.

### Шаг 3. Свяжите экраны переходами

У каждой кнопки и ссылки задайте действие `Edit link`, затем выберите страницу файла. Проверьте переходы в режиме просмотра: нажатие должно открывать нужную страницу, а не скачивать файл.

| Откуда | Действие | Куда | Условие |
|---|---|---|---|
| S1 Вход | Войти | S2 Каталог | Верные данные |
| S1 Вход | Войти | S1 Вход | Ошибка, сообщение над формой |
| S2 Каталог | Открыть книгу | S3 Карточка | Книга найдена |
| S3 Карточка | Забронировать | S4 Бронирование | Есть свободный экземпляр |
| S4 Бронирование | Подтвердить | S2 Каталог | Бронь создана, плашка об успехе |
| S2 Каталог | Рабочее место | S5 Выдача | Роль библиотекаря |
| S5 Выдача | Вернуть книгу | S6 Задолженности | Есть просрочка |
| S6 Задолженности | Отчёт | S7 Отчёт | Роль администратора |

Если переход возможен только для одной роли, нарисуйте рядом пометку. Скрывать пункт меню недостаточно: проверяющий должен видеть, что произойдёт при прямом обращении.

### Шаг 4. Добавьте состояния экранов

Пустой экран и экран с данными это разные состояния. Добавьте их отдельными страницами или блоками рядом с основным экраном.

| Экран | Пусто | Ошибка | Загрузка | Нет прав |
|---|---|---|---|---|
| S2 Каталог | «Ничего не найдено», кнопка сброса фильтров | «Сервис недоступен, повторите» | Скелетон строк | Раздел скрыт, сообщение о роли |
| S3 Карточка | Нет свободных экземпляров, кнопка брони неактивна | Нет связи с каталогом | Плейсхолдер обложки | Кнопка брони скрыта |
| S4 Бронирование | Нет активных броней | Бронь не создана, причина | Кнопка неактивна | Форма недоступна |
| S6 Задолженности | Долгов нет | Ошибка расчёта штрафа | Таблица с плейсхолдером | Раздел скрыт |

Состояние «нет прав» показывайте не пустым экраном, а понятным сообщением: пользователь должен понимать, что доступ ограничен, а не что система сломалась.

### Шаг 5. Пройдите сценарии по прототипу

Сценарий 1, читатель: вход, поиск книги, карточка, бронирование, подтверждение. Сценарий 2, библиотекарь: вход, поиск читателя, выдача экземпляра, возврат с просрочкой, просмотр штрафа.

| Шаг | Экран | Действие | Ожидаемый результат |
|---|---|---|---|
| 1 | S1 | Ввести логин и пароль читателя | Открылся каталог, в шапке имя |
| 2 | S2 | Ввести «Алгоритмы» в поиск | Список книг и счётчик найденного |
| 3 | S3 | Открыть книгу | Карточка с числом экземпляров |
| 4 | S4 | Выбрать дату и подтвердить | Сообщение о брони, книга в списке |
| 5 | S5 | Найти читателя по номеру | Карточка читателя и его брони |
| 6 | S6 | Оформить возврат с просрочкой | Строка долга и сумма штрафа |

Каждый шаг записывайте так, как его видит проверяющий: что нажал и что увидел. Если шаг требует пояснения, значит экран или подпись не готовы.

### Шаг 6. Оформите документ описания

Соберите документ в Word. Ниже каркас разделов.

```markdown
1. Назначение и область применения
2. Роли и права
3. Перечень экранов
4. Сценарии работы
5. Трассировка требований
6. Ограничения прототипа
7. Приложения: схемы переходов
```

В разделе о ролях перечислите читателя, библиотекаря и администратора, для каждого укажите доступные экраны. В разделе экранов дайте паспорт на каждый экран. В сценариях повторите шаги из таблицы. В ограничениях честно назовите, что прототип не делает: не хранит данные, не считает штраф по-настоящему, не отправляет письма.

### Шаг 7. Заполните паспорт экрана

| Поле | Что записать |
|---|---|
| ID и название | S3 Карточка книги |
| Назначение | Показать сведения о книге и доступность экземпляров |
| Роль | Читатель, библиотекарь |
| Элементы | Обложка, автор, ISBN, аннотация, счётчик экземпляров, кнопка брони |
| Действия | Забронировать, вернуться в каталог |
| Переходы | S4 при успехе, S2 при возврате |
| Состояния | Есть экземпляры, нет экземпляров, ошибка загрузки |
| Требование | R3 |

Паспорт пишите в одном стиле для всех экранов. Одинаковые поля облегчают проверку и поиск пропусков.

### Шаг 8. Постройте трассировку

| Требование | Экран | Элемент | Шаг сценария |
|---|---|---|---|
| R2 Поиск по названию и автору | S2 | Поле поиска, фильтр | 2 |
| R3 Показ доступных экземпляров | S3 | Счётчик и статус | 3 |
| R4 Бронирование на срок | S4 | Дата, подтверждение | 4 |
| R5 Выдача по коду экземпляра | S5 | Поле кода, кнопка выдачи | 5 |
| R6 Расчёт штрафа за просрочку | S6 | Строка долга, сумма | 6 |

Пустая ячейка в столбце экрана означает, что требование не покрыто. Это пробел прототипа, его нужно закрыть или объяснить в ограничениях.

### Шаг 9. Сверьте прототип с макетом и требованиями

| Проверка | Да или нет | Комментарий |
|---|---|---|
| Все экраны макета вошли в прототип | | |
| Сетка и шапка одинаковы на всех страницах | | |
| У каждого основного действия есть переход | | |
| Пустое состояние показано для списков | | |
| Ошибка показана рядом с полем или блоком | | |
| Прямой адрес закрытого экрана даёт сообщение | | |
| Подписи понятны без пояснений | | |
| Каждое требование имеет экран или ограничение | | |

### Шаг 10. Подготовьте файлы к сдаче

Назовите файлы по шаблону: `Библиотека_прототип.drawio` и `Библиотека_описание.docx`. В документ добавьте титульный лист, номер версии и дату. Проверьте, что прототип открывается на другом компьютере и ссылки работают.

Скриншоты экранов не нужны: сдаются сами файлы, проверяющий открывает их и нажимает переходы. Если защита проходит без компьютера, распечатайте карту переходов из документа.

## Что сдать

- Файл прототипа с семью связанными страницами и состояниями экранов.
- Документ описания с назначением, ролями, паспортами экранов, сценариями и ограничениями.
- Таблицу трассировки требований на экраны и элементы.
- Заполненный чек-лист сверки с макетом и требованиями.
- Карту переходов между экранами.

## Критерии оценки

| Критерий | Баллы | Что проверяется |
|---|---|---|
| Работающие переходы | 25 | Проверяющий проходит оба сценария без обрыва маршрута |
| Полнота экранов и состояний | 20 | Есть пустое состояние, ошибка, загрузка и отказ в доступе |
| Паспорта экранов | 20 | Поля заполнены единообразно, действия и переходы совпадают с прототипом |
| Трассировка | 20 | Каждое требование связано с экраном или объяснённым ограничением |
| Документ | 15 | Разделы на месте, текст понятен, версия и дата указаны |
