## Цель работы

Архитектура нужна не для красоты схемы, а чтобы договориться о границах: что делает наша система, что остаётся снаружи, из каких частей она состоит и по какому протоколу части общаются. Без такой договорённости API превращается в случайный набор адресов, а интеграция выясняется уже на разработке.

Цель работы: построить для своего индивидуального проекта контекст и контейнеры C4, выделить ресурсы API и оформить контракт спецификацией OpenAPI. Контракт проверяется импортом в Postman: если инструмент разобрал файл и построил запросы, спецификация синтаксически верна и пригодна для работы.

Опорой служат артефакты предыдущих практик: паспорт темы с границами, реестр требований, диаграмма классов, ER-модель и SQL-скрипт схемы. Если какой-то артефакт изменился, сначала обновите его, иначе архитектура разойдётся с данными.

## Оборудование и программное обеспечение

- Персональный компьютер с браузером.
- draw.io в браузере для диаграмм C4.
- VS Code для файла спецификации.
- Postman для импорта спецификации и проверки запросов.
- Word или Excel для таблиц и короткой записки о решениях.
- Папка проекта с артефактами предыдущих практик и доступ к репозиторию GitHub.

## Краткие теоретические сведения

**C4** задаёт четыре уровня описания: контекст, контейнеры, компоненты, код. Уровень выбирают по читателю. Заказчику и преподавателю достаточно контекста, архитектору и разработчику нужны контейнеры, компоненты появляются, когда контейнер становится слишком крупным для одной команды.

**Контекст** рисует систему одним прямоугольником. Вокруг стоят акторы и внешние системы, связи подписаны назначением обмена. Баз данных, фреймворков и внутренних модулей на этом уровне нет: читатель схемы ещё не решил, доверяет ли он команде.

**Контейнер** это приложение или хранилище, которое выполняется отдельно: веб-клиент, сервис приложения, база данных, очередь сообщений, файловое хранилище. У каждого контейнера есть технология и ответственность. Контейнер не равен серверу: два контейнера спокойно живут на одной машине.

**Связь** подписывают направлением и назначением, например «читает каталог через HTTPS и JSON». Стрелка без подписи не отвечает на вопрос, зачем эти части соединены. Протокол указывают на уровне контейнеров, на контексте достаточно назначения.

**Согласованность уровней** проверяется просто. Каждый контейнер лежит внутри границы системы. Каждый актор и каждая внешняя система с контекста появляются на уровне контейнеров, если с ними есть обмен. Новая внешняя система на втором уровне без первого означает, что контекст устарел.

**API-контракт** это договор: путь, метод, параметры, тело запроса, коды ответов, формат ошибки, правила пагинации. Контракт пишут до кода, потому что клиент и сервер делают разные люди, а иногда и разные команды.

**Ресурс** называется существительным во множественном числе: `/books`, `/loans`. Действие выражает метод. `GET /books` возвращает список, `GET /books/{id}` карточку, `POST /books` создаёт запись, `PATCH /books/{id}` меняет часть полей, `DELETE /books/{id}` удаляет.

**Коды ответов** выбираются по ситуации: 200 для успешного чтения, 201 для создания, 204 для удаления без тела, 400 для неверного синтаксиса, 401 для отсутствия сессии, 403 для нехватки прав, 404 для отсутствующего объекта, 409 для конфликта состояния, 422 для данных, не прошедших проверку, 500 для ошибки сервера. Один и тот же случай всегда даёт один и тот же код.

**Формат ошибки** единый для всех операций: машиночитаемый код, сообщение для человека и список проблемных полей.

```json
{
  "code": "validation_error",
  "message": "Поле не прошло проверку",
  "fields": [
    {"name": "title", "reason": "пустое значение"}
  ]
}
```

**OpenAPI** описывает API на YAML или JSON. Обязательны разделы `openapi`, `info`, `paths`. Схемы выносят в `components/schemas`, чтобы не дублировать описание в каждой операции.

```yaml
openapi: 3.0.3
info:
  title: Библиотека колледжа API
  version: 1.0.0
paths:
  /books:
    get:
      summary: Список книг
      parameters:
        - name: q
          in: query
          schema: {type: string}
        - name: page
          in: query
          schema: {type: integer, minimum: 1}
      responses:
        "200":
          description: Страница каталога
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/BookPage"
        "401":
          description: Нет сессии
```

**Пагинация** ограничивает размер ответа: клиент передаёт `page` и `size`, сервер возвращает `items`, `total` и `page`. Без неё список книг однажды придёт целиком и остановит браузер.

**Идемпотентность** означает, что повторный запрос не меняет результат: `GET`, `PUT` и `DELETE` этим свойством обладают, `POST` создаёт дубль. Для создания записи, которую нельзя продублировать, применяют ключ идемпотентности в заголовке.

## Ход работы

### Шаг 1. Сверьте границы проекта

Откройте паспорт темы. Выпишите акторов и внешние системы. Актор это роль, а не человек: читатель, библиотекарь, администратор. Внешняя система это то, что вы не разрабатываете: почтовый сервер, единый вход колледжа, платёжный сервис.

| Элемент | Тип | Что получает от системы | Что передаёт в систему |
|---|---|---|---|
| Читатель | актор | каталог, статус брони | поисковый запрос, бронь |
| Библиотекарь | актор | очередь выдач, карточка читателя | отметка о выдаче |
| Администратор | актор | отчёты, журнал действий | настройки правил |
| Почтовый сервер | внешняя система | письмо с напоминанием | отчёт о доставке |

Минимум три актора и одна внешняя система. Если внешних систем в вашем проекте нет, напишите одной строкой, почему система замкнута, и не рисуйте пустой блок.

### Шаг 2. Постройте контекст

В draw.io создайте лист с рамкой границы системы. В центре один прямоугольник с названием проекта. Акторы расположите слева, внешние системы справа. Проведите от шести до десяти связей и подпишите каждую глаголом с назначением.

Добавьте легенду из четырёх пунктов: актор, проектируемая система, внешняя система, направление обмена. Легенда снимает половину вопросов на защите.

Проверка перед экспортом: на схеме нет баз данных, фреймворков и внутренних модулей, у каждой связи есть подпись, граница системы обозначена явно.

### Шаг 3. Постройте контейнеры

Разложите систему на три или шесть контейнеров. Для каждого укажите технологию, ответственность и протокол обмена. Технологии в таблице примерные, подставьте те, что записаны в паспорте вашего проекта.

| Контейнер | Технология | Ответственность | Протокол наружу |
|---|---|---|---|
| Веб-клиент | HTML, CSS, JavaScript | экраны, ввод, отображение данных | HTTPS к API |
| Сервис приложения | Python, FastAPI | правила выдачи, брони, штрафы | HTTPS, SQL |
| База данных | SQLite | книги, читатели, выдачи, платежи | SQL |
| Очередь уведомлений | файловая очередь | отложенная отправка писем | внутренний вызов |

Ответственность формулируйте через результат: «хранит выдачи и считает просрочку», а не «работает с данными». Два контейнера с одинаковой ответственностью означают, что граница проведена неверно.

### Шаг 4. Сверьте два уровня

Пройдите по контексту и отметьте расхождения. Результат оформите таблицей.

| Что проверить | Признак ошибки | Исправление |
|---|---|---|
| Границы | контейнер оказался за рамкой | вернуть внутрь или признать внешней системой |
| Акторы | актор есть на контексте, но не на контейнерах | добавить связь к веб-клиенту |
| Технологии | фреймворк подписан на контексте | убрать, оставить на уровне контейнеров |
| Связи | стрелка без подписи | подписать назначение и протокол |

Отдельно проверьте, что каждый контейнер связан хотя бы с одним соседом. Контейнер без связей обычно остался от первой версии схемы.

### Шаг 5. Выделите ресурсы API

Соберите от восьми до двенадцати операций. Для каждой запишите ресурс, путь, метод, кто вызывает, успешный ответ и возможные ошибки. Ниже образец, продолжите его под свой проект.

| Ресурс | Метод и путь | Кто вызывает | Успех | Ошибки |
|---|---|---|---|---|
| Каталог | GET /books | читатель, библиотекарь | 200, страница | 400, 401 |
| Книга | GET /books/{id} | читатель | 200 | 404 |
| Бронь | POST /loans | читатель | 201 | 401, 409, 422 |
| Выдача | PATCH /loans/{id} | библиотекарь | 200 | 403, 404, 409 |
| Читатель | GET /readers/{id} | библиотекарь | 200 | 403, 404 |
| Отчёт | GET /reports/overdue | библиотекарь, администратор | 200 | 401, 403 |

В пути не должно быть глаголов: `/getBooks` читается как вызов функции, а не как ресурс. Регистр единый, версия указана либо в `servers`, либо префиксом `/v1`.

### Шаг 6. Опишите коды и ошибки

Для каждой операции выпишите один успешный и два ошибочных кода. Проверьте, что код соответствует причине: 403 при неверном пароле сбивает клиента, потому что пароль проверяет 401.

| Ситуация | Код | Тело ответа |
|---|---|---|
| Список получен | 200 | items, total, page |
| Запись создана | 201 | созданный объект и заголовок Location |
| Нет сессии | 401 | code, message |
| Роль не имеет права | 403 | code, message |
| Объект не найден | 404 | code, message |
| Книга уже выдана | 409 | code, message, текущий статус |
| Поле пустое | 422 | code, message, fields |

Ошибка 500 не описывается в контракте как обычный случай: она означает дефект, а не сценарий работы пользователя.

### Шаг 7. Напишите спецификацию OpenAPI

Создайте в папке проекта файл `openapi.yaml`. В нём должны быть сведения о версии API, адрес сервера, все операции из шага 5, схемы объектов и схема безопасности.

```yaml
components:
  securitySchemes:
    sessionCookie:
      type: apiKey
      in: cookie
      name: session_id
  schemas:
    Book:
      type: object
      required: [id, title, author]
      properties:
        id: {type: integer}
        title: {type: string}
        author: {type: string}
        available: {type: boolean}
```

Имена полей в схемах сверьте с ER-моделью. Если в базе столбец `book_id`, а в API поле `id`, клиент и сервер разойдутся на первом же запросе. Для одной операции добавьте примеры запроса и ответа: они попадут в документацию.

### Шаг 8. Проверьте спецификацию импортом в Postman

В Postman выберите Import, укажите файл и создайте коллекцию. Признак успеха: запросов столько же, сколько операций, у каждого заполнены путь, параметры и тело. При ошибке инструмент покажет строку YAML, начните с неё.

Затем создайте mock-сервер из коллекции, чтобы получить ответы без готового сервера. Mock проверяет форму ответа, а не бизнес-логику: он не считает штраф и не проверяет права.

### Шаг 9. Прогоните три запроса

Выполните `GET /books` с параметром `page=1`, `POST /loans` с корректным телом и `GET /books/999999` для несуществующей книги. Для каждого сохраните код, тело и заголовки.

Скриншот нужен только для ответов Postman: он доказывает, что контракт исполним. Диаграммы сдаются файлами draw.io и экспортом PNG или PDF, скриншоты окон draw.io не требуются.

### Шаг 10. Соберите записку о решениях

На одну или две страницы объясните выбор контейнеров и API. Таблица помогает не пересказывать схему, а показать компромиссы.

| Решение | Альтернатива | Почему выбрано | Цена |
|---|---|---|---|
| Три контейнера вместо микросервисов | Сервис на каждый модуль | проект делает один человек | рост связанности |
| Очередь для писем | отправка внутри запроса | медленный почтовый сервер не блокирует выдачу | нужен повтор при сбое |
| Сессия в cookie | токен в localStorage | cookie нельзя прочитать скриптом при HttpOnly | нужна защита от подделки запроса |

### Требования к отчёту

Отчёт содержит цель, границы, две диаграммы, таблицы акторов, контейнеров, ресурсов и кодов, фрагмент спецификации, результаты Postman и записку о решениях. Диаграммы вставляются как PNG или PDF с подписью «Рис. 1. Контекст C4». Имена элементов на рисунках, в таблицах и в спецификации совпадают.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

| Оценка | Условие |
|---|---|
| 5 | Работа выполнена полностью и самостоятельно, все пункты ниже выполнены |
| 4 | Работа выполнена, есть 1 или 2 незначительных замечания |
| 3 | Работа выполнена частично, есть существенные замечания |
| 2 | Работа не выполнена |
| 1 | Работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления |

Что проверяется:
- **Границы и уровни C4.** Контекст и контейнеры согласованы, лишних элементов нет
- **Контейнеры и технологии.** У каждого контейнера есть ответственность и протокол
- **Полнота API.** Операции покрывают требования, коды и ошибки описаны
- **Проверка контракта.** Спецификация импортируется, запросы выполнимы
- **Оформление.** Подписи, легенда, единые имена, читаемые таблицы
