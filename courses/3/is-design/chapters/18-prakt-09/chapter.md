## Цель работы

Контекстная диаграмма отвечает на вопрос «кто пользуется системой и с чем она связана», но внутри система остаётся одним прямоугольником. Заказчику этого достаточно, а разработчику нет: непонятно, что запускать на сервере, где лежат данные и кто с кем разговаривает.

Цель работы: детализировать контекст учебной ИС «Библиотека колледжа» до уровня контейнеров, назначить каждому контейнеру технологию и показать протоколы обмена. Результат работы это диаграмма контейнеров, две таблицы и заполненный чек-лист проверки.

## Оборудование и программное обеспечение

- Персональный компьютер с браузером.
- draw.io (diagrams.net) в браузере для диаграммы.
- Контекстная диаграмма из предыдущей практики или её описание.
- Текстовый редактор или Word для таблиц и пояснения.
- Папка проекта для файлов диаграммы и отчёта.

## Краткие теоретические сведения

**Контейнер** в модели C4 это отдельно запускаемая или отдельно развёртываемая часть системы, которая выполняет свою работу и хранит свои данные. Контейнер не равен классу, модулю или папке с кодом. Признаки контейнера простые: у него есть собственный процесс или собственное хранилище, его можно заменить, не переписывая остальные части, и у него есть технология исполнения.

В «Библиотеке колледжа» контейнерами будут веб-клиент в браузере, сервис приложения с REST API, база данных, обработчик уведомлений, файловое хранилище и брокер очереди. Каталог, выдача и бронирование это модули внутри сервиса приложения, а не отдельные контейнеры: они работают в одном процессе и используют одну базу.

**Технология** отвечает на вопрос «на чём это сделано»: JavaScript в браузере, Python с веб-фреймворком, реляционная СУБД, брокер сообщений. Технологию указывают в подписи контейнера, иначе диаграмма читается как схема обязанностей без привязки к реализации.

**Протокол** отвечает на вопрос «как они общаются»: HTTPS с JSON, SQL по TCP, AMQP, SMTP. Стрелка без подписи протоколом не считается. Направление стрелки показывает, кто инициирует вызов, а не просто «связь есть».

**Граница системы** на этом уровне отделяет контейнеры проекта от внешних систем. SSO колледжа, почтовый сервер и рабочие места пользователей остаются снаружи: вы ими не управляете и не развёртываете.

Типичные ошибки уровня контейнеров: дробление на контейнеры по командам или по таблицам базы, отсутствие технологии в подписи, стрелки «все ко всем» без протоколов, попадание внешней системы внутрь границы и клиент, который обращается к базе напрямую.

## Ход работы

### Шаг 1. Восстановите контекст

Выпишите из контекстной диаграммы всех участников и внешние системы. Проверьте, что для каждого понятно, какие данные он получает или отдаёт.

| Участник или система | Что делает с «Библиотекой» | Что получает | Что отдаёт |
|---|---|---|---|
| Читатель | Ищет книги, бронирует, продлевает | Каталог, статус брони, уведомления | Запрос брони, данные входа |
| Библиотекарь | Выдаёт и принимает экземпляры | Очередь выдач, карточка читателя | Отметки выдачи и возврата |
| Администратор | Ведёт справочники и права | Отчёты, журнал действий | Настройки, учётные записи |
| SSO колледжа | Проверяет вход сотрудников | Запрос проверки токена | Подтверждение и роли |
| Почтовый сервер | Доставляет письма | Адрес и текст письма | Отчёт о доставке |

### Шаг 2. Выделите контейнеры

Проверьте каждого кандидата по трём признакам: отдельный процесс, отдельное развёртывание, отдельное хранилище. Заполните таблицу решений.

| Кандидат | Контейнер | Обоснование |
|---|---|---|
| Веб-клиент | да | Работает в браузере, обновляется независимо от сервера |
| Сервис приложения | да | Отдельный процесс с REST API и бизнес-правилами |
| База данных | да | Отдельное хранилище с собственным жизненным циклом |
| Обработчик уведомлений | да | Читает очередь и отправляет письма вне запроса пользователя |
| Брокер очереди | да | Отдельный процесс, буфер между API и обработчиком |
| Файловое хранилище | да | Сканы и PDF лежат вне базы и вне кода |
| Модуль «Каталог» | нет | Модуль внутри сервиса приложения |
| Таблица «Выдачи» | нет | Объект базы, а не контейнер |

### Шаг 3. Назначьте ответственность и технологию

Одна строка на контейнер. В последнем столбце напишите, что контейнер делать не должен: это защищает от расползания логики.

| Контейнер | Ответственность | Технология | Чего не делает |
|---|---|---|---|
| Веб-клиент | Экраны каталога, брони, выдачи, отчётов | JavaScript, HTML, CSS | Не хранит бизнес-правила и не ходит в базу |
| Сервис приложения | Правила выдачи, брони, штрафа, проверка прав | Python, REST, JSON | Не рисует экраны и не отправляет письма сам |
| База данных | Хранение книг, экземпляров, выдач, читателей | Реляционная СУБД | Не содержит логики уведомлений |
| Брокер очереди | Приём и доставка событий о брони и возврате | Брокер сообщений (AMQP) | Не хранит историю выдач |
| Обработчик уведомлений | Письма о готовности брони и долге | Python, SMTP | Не меняет статусы выдач |
| Файловое хранилище | Сканы обложек и акты приёма | Объектное хранилище | Не хранит персональные данные читателей |

### Шаг 4. Опишите протоколы обмена

Для каждой стрелки укажите протокол, направление и данные. Строки «оба направления» избегайте: у вызова есть инициатор.

| Откуда | Куда | Протокол | Данные | Инициатор |
|---|---|---|---|---|
| Сервер приложений | Веб-клиент | HTTPS | HTML, JavaScript, CSS | Сервер приложений |
| Веб-клиент | Сервис приложения | HTTPS, JSON | Запросы каталога, брони, выдачи | Клиент |
| Сервис приложения | База данных | SQL по TCP | Чтение и запись таблиц | Сервис |
| Сервис приложения | Брокер очереди | AMQP | События брони и возврата | Сервис |
| Обработчик уведомлений | Брокер очереди | AMQP | Чтение событий | Обработчик |
| Обработчик уведомлений | Почтовый сервер | SMTP | Адрес, тема, текст письма | Обработчик |
| Сервис приложения | SSO колледжа | HTTPS, OIDC | Токен и роли сотрудника | Сервис |
| Сервис приложения | Файловое хранилище | HTTPS | Ссылки на сканы и PDF | Сервис |

### Шаг 5. Постройте диаграмму контейнеров

В draw.io создайте страницу «Контейнеры». Внутри пунктирной рамки с подписью «Библиотека колледжа» разместите контейнеры, снаружи людей и внешние системы. Для каждого контейнера подпись в две строки: название и технология в квадратных скобках. Стрелку подписывайте протоколом и коротким описанием данных.

Расположите контейнеры по потоку запроса: пользователь, веб-клиент, сервис приложения, данные и очередь. Внешние системы поставьте по краям, чтобы стрелки не пересекали центр. Добавьте легенду: человек, контейнер, внешняя система, граница системы.

Проверьте читаемость на масштабе 100 процентов: подписи не должны налезать на линии, а стрелки не должны пересекаться без необходимости.

### Шаг 6. Проверьте диаграмму по чек-листу

| Проверка | Как проверить | Признак ошибки |
|---|---|---|
| Технология у каждого контейнера | Пройдите по подписям | Подпись без квадратных скобок |
| Протокол у каждой стрелки | Пройдите по линиям | Линия без подписи |
| Направление вызова | Спросите, кто инициирует | Двусторонняя стрелка без пояснения |
| Граница системы | Внешние системы снаружи рамки | SSO или почта внутри рамки |
| Ответственность | У каждого контейнера одна зона работы | Два контейнера делают одно и то же |
| Прямой доступ к базе | Проверьте стрелки от клиента | Клиент соединяется с базой |

### Шаг 7. Сверьте уровни

Каждый участник из шага 1 должен остаться на диаграмме. Каждый поток контекста должен раскладываться в цепочку стрелок между контейнерами. Новых внешних систем появляться не должно: если вы добавили платёжный сервис, вернитесь к контексту и обоснуйте изменение.

Запишите пояснение на полстраницы: почему выбраны эти контейнеры, какие кандидаты отклонены, где проходит граница и что произойдёт при отказе брокера очереди. Отказ разбирайте честно: сервис приложения продолжает выдавать книги, но уведомления копятся в очереди и уходят позже.

### Требования к отчёту

В отчёт включите диаграмму, таблицу контейнеров, таблицу протоколов, чек-лист и пояснение. Файл draw.io сдавайте вместе с экспортом в PDF. Скриншот диаграммы не нужен, если приложен PDF: он читается лучше и не теряет подписи.

## Что сдать

- Диаграмму контейнеров в draw.io и её экспорт в PDF.
- Таблицу контейнеров с ответственностью, технологией и ограничениями.
- Таблицу протоколов с направлением, данными и инициатором.
- Заполненный чек-лист проверки диаграммы.
- Пояснение о границах и поведении при отказе одного контейнера.

## Критерии оценки

| Критерий | Баллы | Что проверяется |
|---|---|---|
| Состав контейнеров | 25 | Контейнеры выделены по признакам, модули не выданы за контейнеры |
| Технологии | 20 | У каждого контейнера указана реализация |
| Протоколы | 25 | Стрелки подписаны, направление и данные понятны |
| Согласованность с контекстом | 20 | Все участники сохранены, лишних систем нет |
| Оформление | 10 | Легенда, читаемость, единые подписи |
