## Сорок команд в текстовом файле

Тестировщик «Северного склада» проверяет API версии 2.8. У него есть файл `requests.txt`, куда он месяц складывал команды `curl`: список товаров, создание приёмки, отчёт, проверка прав, повторная отправка. Команд набралось сорок. К каждой приложен комментарий вида «тут было 200» или «тут должно быть 409».

В пятницу стенд переехал с порта 5000 на порт 8080. В понедельник восемнадцать команд из сорока перестали работать. Причина одна: старый адрес. Но правки разбросаны по файлу, часть команд скопирована с ошибкой, а часть проверяла только код ответа. Тестировщик тратит день на замену адреса и понимает, что за неделю никто не сможет сказать, какие проверки действительно проходили.

**Postman превращает набор запросов в тестовый актив: коллекцию с папками, окружение с адресами и токенами, тесты с ожидаемым результатом и отчёт о прогоне.** Один раз собранная коллекция запускается одной кнопкой, а изменение адреса делается в одном месте.

## Коллекция как тестовый актив

В Postman есть три слоя, и путать их нельзя.

**Коллекция** отвечает на вопрос «что проверяем». В ней лежат запросы, сгруппированные по папкам, и тесты к ним. Коллекцию можно экспортировать в JSON, положить в git и передать другому тестировщику.

**Окружение** отвечает на вопрос «где и с какими данными проверяем». В нём хранятся адрес стенда, токен, название площадки и другие значения, которые меняются между средами. Одно и то же окружение нельзя использовать для локального стенда и для тестового контура.

**Тесты** отвечают на вопрос «что должно получиться». Они пишутся на JavaScript в разделе Tests и выполняются после каждого запроса. Без тестов коллекция остаётся красивым списком запросов, но не проверкой.

При запуске появляется ещё один слой, данные прогона. **Runner** берёт коллекцию, окружение и данные, выполняет запросы по порядку и собирает отчёт: сколько запросов выполнено, сколько проверок прошло, что упало и сколько заняло время.

| Слой | Что хранит | Что меняется между стендами | Где живёт |
|---|---|---|---|
| Коллекция | запросы, папки, тесты, примеры ответов | почти ничего | JSON в git |
| Окружение | адрес, токен, площадка, версия | да, полностью | настройки Postman, секреты отдельно |
| Тесты | код проверок внутри запроса | редко | внутри коллекции |
| Данные прогона | наборы значений для итераций | да | CSV или JSON |

Такое разделение даёт главный выигрыш: при переезде стенда меняется одна переменная `baseUrl`, а не сорок команд. При смене роли меняется токен в окружении, а не текст каждого запроса.

## Папки и порядок запросов

Коллекция без структуры быстро становится свалкой. Папки группируют запросы по ресурсу или сценарию, а не по порядку создания.

Для «Склад+» удобна структура из четырёх папок.

| Папка | Запросы | Что проверяет |
|---|---|---|
| Товары | список своей площадки, список чужой, пустой фильтр | чтение и права на площадку |
| Приёмка | создание, повтор, неверное количество, чтение по номеру | запись, валидация, дубль |
| Отчёт | отчёт менеджера, отчёт без токена, отчёт кладовщика | формирование и права |
| Доступ | вход, истёкший токен, чужая роль | аутентификация и авторизация |

Внутри папки запросы идут в порядке сценария. Сначала вход и получение токена, затем чтение, затем создание, затем проверка созданного, затем негативные случаи. Порядок нужен для читателя, но не должен быть единственным условием работы. Если проверка зависит от предыдущей, это зависимость, и её отмечают явно.

Имя запроса пишут так, чтобы его понял человек, который открыл коллекцию впервые. `GET /api/products, своя площадка` лучше, чем `request 7`. В имени полезно оставить метод и адрес: тогда поиск по коллекции работает быстрее.

В коллекции сохраняют примеры ответов. Пример это зафиксированный ответ сервера, который можно открыть без запуска запроса. По нему новый человек понимает формат данных, а тестировщик видит, как выглядел успешный ответ до изменения. Пример не заменяет тест, потому что не выполняется автоматически, но служит документацией и точкой сравнения.

## Переменные и окружения

Переменная это имя, вместо которого Postman подставляет значение. В запросе пишут `{{baseUrl}}/api/products`, а в окружении хранят `baseUrl = http://sklad-test.local:8080`. При запуске подстановка происходит до отправки запроса.

У переменных пять областей видимости. Чем ближе область, тем выше её приоритет.

| Область | Где задаётся | Сколько живёт | Пример |
|---|---|---|---|
| Локальная | скрипт запроса | один запрос | временный номер приёмки |
| Данные | CSV или JSON прогона | одну итерацию | `site` из строки файла |
| Окружение | выбранное окружение | пока выбрано | `baseUrl`, `token` |
| Коллекция | настройки коллекции | пока живёт коллекция | `apiVersion` |
| Глобальная | настройки Postman | пока не удалят | общий адрес документации |

Приоритет идёт от локальной к глобальной. Если `baseUrl` задан и в коллекции, и в окружении, победит окружение. Это удобно, но и опасно: тестировщик меняет значение в коллекции, а запрос продолжает ходить по старому адресу из окружения.

Для «Склад+» достаточно двух окружений.

| Переменная | `sklad-local` | `sklad-test` |
|---|---|---|
| `baseUrl` | `http://localhost:8080` | `http://sklad-test.local` |
| `site` | `Тверь` | `Москва` |
| `token` | токен кладовщика | токен менеджера |
| `apiVersion` | `2.8` | `2.8` |

Токен не хранят в коллекции. Коллекцию экспортируют и передают коллегам, а вместе с ней уедет и токен. Токен живёт в окружении, а окружение с секретами не публикуют в общем репозитории. Если токен всё же попал в экспорт, его отзывают и выпускают новый.

> [!PITFALL] Переменная не подставилась
> В адресе видно `{{baseUrl}}` буквально. Причины обычно две: окружение не выбрано в правом верхнем углу или имя переменной написано с другой буквой. Postman не сообщает об ошибке, он отправляет запрос по странному адресу и возвращает непонятную ошибку соединения.

## Запрос: что заполнить

Запрос в Postman повторяет структуру HTTP-запроса. Вкладки соответствуют частям запроса, и каждая часть влияет на результат.

| Вкладка | Что заполняют | Частая ошибка |
|---|---|---|
| Params | параметры адреса | параметр продублирован в URL и в таблице |
| Authorization | тип и токен | токен вписан в заголовок вручную и не обновляется |
| Headers | `Content-Type`, `Accept` | забыт `Content-Type: application/json` |
| Body | тело `POST` в формате raw JSON | выбран form-data вместо raw |
| Pre-request Script | подготовка данных и токена | скрипт падает молча |
| Tests | проверки после ответа | проверка написана, но не выполняется |
| Settings | таймаут, редиректы | таймаут по умолчанию слишком короткий |

Авторизацию удобно задать на уровне папки. Тогда все запросы внутри наследуют токен, а менять его нужно в одном месте. Если у запроса своя авторизация, она перекрывает родительскую. Это полезно для проверки чужой роли, но легко забыть, что запрос больше не использует общий токен.

Тело `POST` для приёмки выглядит так.

```json
{
  "supply_id": 505,
  "qty": 12
}
```

Если выбрать `form-data`, сервер получит не JSON, а набор полей формы, и ответ будет 400 или 415. Это не дефект API, а ошибка настройки запроса. Перед тем как сообщать о дефекте, проверяют `Content-Type` и формат тела.

## Тесты в Postman

Тест это JavaScript, который выполняется после ответа. Внутри доступен объект `pm`: ответ, переменные, ожидания. Результат каждого теста виден в разделе Test Results.

Минимальный набор проверок для списка товаров смотрит на код, форму тела и значения полей.

```js
pm.test("Статус 200", function () {
  pm.response.to.have.status(200);
});

const body = pm.response.json();

pm.test("Ответ содержит массив items", function () {
  pm.expect(body.items).to.be.an("array");
});

pm.test("В каждом товаре есть sku и stock", function () {
  body.items.forEach(function (item) {
    pm.expect(item).to.have.property("sku");
    pm.expect(item).to.have.property("stock");
  });
});

pm.test("Остаток не отрицательный", function () {
  body.items.forEach(function (item) {
    pm.expect(item.stock).to.be.at.least(0);
  });
});
```

На ответе с двумя дефектами этот набор даёт такой результат.

```text
✓ Статус 200
✓ Ответ содержит массив items
✗ В каждом товаре есть sku и stock: нет свойства sku
✗ Остаток не отрицательный: ожидалось не меньше 0, получено -3
Проверок: 4, ошибок: 2
```

Две проверки упали, хотя код ответа был 200. Это главный смысл тестов в Postman: они не дают зелёному статусу скрыть плохие данные. Если ограничиться проверкой `pm.response.to.have.status(200)`, оба дефекта пройдут незамеченными.

Проверки стоит писать по обещаниям контракта. Код 200, наличие массива, обязательные поля, тип значения, допустимый диапазон, формат даты, отсутствие лишних полей. Для ошибок проверяют код 400, 401, 403, 404, 409 и машиночитаемый код в теле.

| Что проверяют | Пример утверждения | Что ловит |
|---|---|---|
| Код ответа | `pm.response.to.have.status(201)` | неверный код создания |
| Заголовок | `pm.response.to.have.header("Content-Type")` | HTML вместо JSON |
| Схема | `pm.response.to.have.jsonSchema(schema)` | пропущенное поле, неверный тип |
| Значение | `pm.expect(body.total).to.eql(1240)` | пустой или неверный список |
| Время | `pm.expect(pm.response.responseTime).to.be.below(2000)` | медленный ответ |
| Ошибка | `pm.expect(body.code).to.eql("duplicate")` | неверная причина отказа |

Тест без утверждения бесполезен. Конструкция `pm.test("Проверка", function () {})` с пустым телом всегда зелёная. Такие заготовки иногда остаются после копирования и создают ложное чувство покрытия.

Отдельно проверяют время ответа. Для списка товаров контракт обещает не дольше 2 секунд при 40 пользователях. В Postman ставят утверждение `pm.expect(pm.response.responseTime).to.be.below(2000)`. Оно не заменяет нагрузочный тест, но ловит явную деградацию после изменения запроса или индекса. Если проверка времени падает на одном запросе, сначала смотрят, не выросло ли время из-за холодного старта стенда, и только потом оформляют дефект.

## Прогон и отчёт

Когда запросы и тесты собраны, коллекцию запускают целиком. В Postman нажимают Run collection, выбирают окружение, число итераций и задержку между запросами. Для проверки одного набора достаточно одной итерации. Для проверки на разных площадках подключают CSV с колонкой `site` и запускают столько итераций, сколько строк в файле.

Результат прогона для «Склад+» выглядит так.

| Запрос | Проверок | Ошибок | Время |
|---|---|---|---|
| GET /api/products, своя площадка | 4 | 2 | 120 мс |
| POST /api/acceptance, создание | 4 | 0 | 180 мс |
| GET /api/acceptance/{{acceptanceId}} | 3 | 0 | 90 мс |
| GET /api/report, менеджер | 3 | 0 | 400 мс |
| POST /api/acceptance, повтор | 3 | 0 | 150 мс |
| GET /api/report, без токена | 2 | 0 | 80 мс |
| GET /api/report, кладовщик | 2 | 0 | 75 мс |
| POST /api/acceptance, неверное количество | 2 | 0 | 95 мс |
| GET /api/products, чужая площадка | 1 | 0 | 70 мс |

Итого 9 запросов, 24 проверки, 2 ошибки, среднее время около 140 мс. Ошибки те же, что в тест-скрипте: у одного товара нет `sku`, у другого отрицательный остаток. Прогон не говорит «всё плохо», он показывает конкретные запросы и конкретные утверждения.

Отчёт читают сверху вниз. Сначала смотрят, все ли запросы выполнились. Потом число ошибок и их распределение по папкам. Затем открывают упавший запрос, смотрят ответ, тело и список тестов. Если ошибка в тесте, а не в API, исправляют тест. Если в API, оформляют дефект с запросом и ответом.

### Прогон на нескольких площадках

Одна итерация проверяет одну площадку. Чтобы проверить все четыре, готовят CSV с колонкой `site`.

```text
site
Москва
Тверь
Тула
Калуга
```

В Runner выбирают этот файл и ставят четыре итерации. Переменная `site` приходит из строки, а `baseUrl` и `token` остаются из окружения. Отчёт покажет четыре итерации, 36 запросов и 96 проверок. Если на одной площадке данных нет, упадут только её проверки, и это видно по номеру итерации.

Для изменяемых данных в CSV добавляют колонки `supply_id`, `qty`, `expected_total`. Тогда один набор проверяет разные количества и суммы. Ожидаемое значение должно приходить из файла, а не вычисляться тем же кодом, который проверяют: иначе тест подтвердит любую ошибку расчёта.

### Что делать с упавшей проверкой

Сначала открывают запрос и смотрят фактический ответ. Потом сравнивают его с контрактом, а не с ожиданием, которое написали в тесте. Если контракт говорит 201, а тест ждёт 200, ошибка в тесте. Если контракт говорит 201, а API вернул 200, ошибка в API.

Дальше проверяют окружение: тот ли стенд, та ли версия, тот ли токен. Часть красных прогонов объясняется старым токеном или невыбранным окружением.

Если дефект подтверждён, в отчёт попадают запрос, ответ, идентификатор запроса, версия стенда и время. Секретный токен в отчёт не копируют, вместо него пишут `Bearer <token>`.

Прогон можно сохранить в JSON или HTML и приложить к отчёту о тестировании. В отчёте указывают окружение, версию коллекции, число итераций, число запросов, проверок и ошибок, время начала и окончания. Без этих данных результат нельзя сравнить со следующим прогоном.

## Связанные запросы

Некоторые проверки зависят от данных предыдущего запроса. Создание приёмки возвращает `id`, и следующая проверка читает документ по этому номеру. Вместо того чтобы вписывать номер вручную, его сохраняют в переменную.

В тесте создания приёмки после проверки кода пишут:

```js
const body = pm.response.json();
pm.collectionVariables.set("acceptanceId", body.id);
```

Следующий запрос использует `{{acceptanceId}}` в адресе. При каждом прогоне номер новый, и проверка не зависит от данных прошлой недели.

У зависимых запросов есть цена. Если создание упало, чтение получит пустой номер и тоже упадёт, хотя причина одна. В отчёте появится две ошибки вместо одной. Поэтому зависимость делают явной: в имени запроса пишут «после создания», а в тесте проверяют, что `id` действительно есть, прежде чем сохранять его.

Обратная ошибка тоже встречается. Все запросы делают независимыми, но для проверки дубля нужен уже созданный документ. Тогда создание и повтор объединяют в один сценарий с общей переменной, а не надеются на порядок запуска всей коллекции.

Для входа используют pre-request script: он получает токен и кладёт его в переменную окружения. Если токен живёт час, а прогон идёт дольше, скрипт обновляет его перед запросом. Это лучше, чем вписывать токен вручную и ловить 401 на середине прогона.

## Хранение и версии

Коллекция это файл. Её экспортируют в JSON и хранят в git вместе с кодом. Тогда изменение запроса видно в истории, а старую версию можно сравнить с новой.

| Что хранят в git | Что не хранят в git |
|---|---|
| коллекцию без секретов | токены и пароли |
| окружение без секретных значений | личные данные сотрудников |
| README с порядком запуска | большие выгрузки ответов |
| CSV с тестовыми данными | локальные адреса разработчиков |
| схему ответа | сертификаты и ключи |

В README коллекции пишут, какое окружение выбрать, в каком порядке запускать папки, какие данные нужны и что считать успешным прогоном. Новый человек открывает коллекцию, читает пять строк и повторяет проверку без вопросов.

Версию коллекции связывают с версией API. Если API 2.8 добавляет поле `cell`, коллекция получает тест на это поле и новую версию. Старая коллекция остаётся для проверки совместимости, но не притворяется актуальной.

### Версии коллекции

У коллекции есть версия и короткий журнал изменений. В журнале пишут, что добавили, что удалили и какое требование закрыли. Например: «2.8.3: добавлена проверка столбца cell для R-09, исправлен адрес отчёта». По журналу видно, почему коллекция изменилась, и не нужно сравнивать двести запросов вручную.

Перед выпуском коллекцию прогоняют на тестовом окружении и сохраняют отчёт. Следующий прогон сравнивают с ним по числу проверок и ошибок. Если число проверок упало без объяснения, значит часть тестов потерялась при слиянии.

::gate Какие привычки превращают коллекцию в мусор?

## Привычки, которые ломают коллекцию

**Адрес вписан в каждый запрос.** При переезде стенда правят сорок запросов и обязательно один забывают. Лечится переменной `baseUrl`.

**Проверяют только код ответа.** API возвращает 200 с пустым списком, прогон зелёный. Лечится тестами на тело и значения.

**Тест ожидает ошибку 500 и считает это нормой.** Однажды сервер начинает отвечать 500 на корректный запрос, а тест продолжает проходить. Ожидаемая ошибка должна быть описана контрактом, а не подогнана под текущее поведение.

**Запросы зависят от порядка, но зависимость не отмечена.** Запуск одной папки ломает половину проверок. Лечится явными переменными и подготовкой данных.

**Токен устарел, а окружение старое.** Прогон падает на 401, тестировщик ищет дефект в API. Лечится обновлением токена перед прогоном и проверкой окружения.

**Одно имя переменной в двух областях.** Значение из коллекции перекрывается окружением, и никто не понимает, откуда взялся адрес. Лечится правилом: адреса и токены только в окружении, версия API только в коллекции.

**Нет очистки данных.** Каждый прогон создаёт новую приёмку, через месяц база забита дублями. Лечится удалением созданного или уникальными номерами поставок.

**Коллекция растёт без структуры.** Двести запросов в одной папке, найти нужный невозможно. Лечится папками по ресурсам и понятными именами.

**Тесты запускают на рабочей базе.** Проверка создания приёмки меняет реальные остатки. Лечится отдельным стендом и запретом запускать коллекцию без проверки адреса.

**Нет негативных проверок.** Все запросы успешные, API выглядит здоровым, пока пользователь не пришлёт пустое поле. Лечится обязательным набором ошибок 400, 401, 403, 404 и 409.

## Итоги

- Postman хранит запросы, окружения и тесты как единый актив, а не как набор команд в файле.
- Коллекция отвечает за то, что проверяют, окружение за то, где и с какими данными.
- Папки группируют запросы по ресурсам, а имена запросов должны быть понятны без пояснений.
- Переменные подставляются по областям видимости, и ближняя область перекрывает дальнюю.
- Тесты проверяют код, заголовки, схему и значения, а не только статус 200.
- Связанные запросы передают данные через переменные коллекции.
- Прогон коллекции даёт отчёт с числом запросов, проверок, ошибок и временем.
- Коллекцию версионируют в git, а токены и секреты держат вне её.
- Коллекция без тестов остаётся списком запросов, а не проверкой.
- Прогон на нескольких площадках задаётся данными, а не копированием запросов. Это уменьшает число ошибок при настройке.

::quiz
Q: Что хранит коллекция Postman?
+ Запросы, папки и тесты
- Только адреса стендов
- Только токены пользователей
- Только отчёты о прогонах
! Коллекция описывает, что проверяют, а окружение отвечает за адреса и данные.

Q: Зачем нужно окружение в Postman?
+ Чтобы менять адрес, токен и площадку без правки каждого запроса
- Чтобы хранить тесты отдельно от запросов
- Чтобы заменять отчёты о прогоне
- Чтобы автоматически исправлять дефекты API
! Окружение отделяет изменяемые значения от текста запросов.

Q: Какая область переменных имеет самый высокий приоритет?
+ Локальная
- Глобальная
- Коллекция
- Окружение
! Чем ближе область к запросу, тем выше её приоритет.

Q: Где хранят токен доступа?
+ В окружении, которое не публикуют с секретами
- В тексте каждого запроса
- В имени коллекции
- В адресе запроса
! Токен в коллекции уедет вместе с экспортом и станет доступен лишним людям.

Q: Что проверяет тест `pm.response.to.have.status(200)`?
+ Только код ответа
- Тело ответа и схему
- Права роли
- Время ответа
! Одного кода недостаточно, чтобы считать ответ правильным.

Q: Что произойдёт, если в тесте оставить пустую функцию `pm.test`?
+ Проверка всегда будет зелёной, хотя ничего не проверяет
- Postman не запустит коллекцию
- Запрос вернёт 500
- Окружение очистится
! Тест без утверждения создаёт ложное покрытие.

Q: Как передать номер созданной приёмки в следующий запрос?
+ Сохранить его в переменную коллекции и использовать `{{acceptanceId}}`
- Вписать номер вручную в каждый запрос
- Скопировать номер в имя папки
- Удалить номер после создания
! Переменная связывает зависимые запросы и обновляется при каждом прогоне.

Q: Что показывает отчёт прогона коллекции?
+ Число запросов, проверок, ошибок и время выполнения
- Только список папок
- Только версию Postman
- Только имя автора коллекции
! Отчёт нужен для сравнения прогонов и доказательства результата.

Q: Почему адрес стенда лучше хранить в переменной `baseUrl`?
+ При переезде стенда меняется одно значение, а не все запросы
- Переменная ускоряет ответ API
- Переменная заменяет тесты
- Переменная скрывает ошибки 500
! Одна переменная избавляет от правки сорока запросов.

Q: Какие проверки стоит добавить в тест списка товаров?
+ Код ответа 200
+ Массив `items` и обязательные поля товара
+ Недопустимость отрицательного остатка
- Цвет кнопки выгрузки
- Расположение логотипа
! Тест API проверяет данные и контракт, а не оформление экрана.

Q: Какие значения не должны попадать в экспорт коллекции?
+ Токены доступа
+ Пароли и секретные ключи
- Названия папок
- Коды ответов
- Имена запросов
! Секреты хранят отдельно от коллекции, иначе они утекут вместе с файлом.

Q: Какие признаки хорошей коллекции?
+ Папки по ресурсам и понятные имена запросов
+ Тесты на успешные и ошибочные ответы
+ Отдельные окружения для разных стендов
- Все запросы в одной папке без имён
- Токен, вписанный в каждый запрос
! Структура, тесты и окружения делают коллекцию повторяемой.

Q: Что делать, если прогон упал на 401 после смены стенда?
+ Проверить токен и выбранное окружение
- Искать дефект в расчёте остатков
- Удалить все тесты
- Отключить проверки прав
! Ошибка доступа чаще всего связана с окружением, а не с бизнес-логикой.

Q: Как называется набор значений, который подставляется в переменные при прогоне коллекции?
= окружение
= environment
! Окружение хранит адрес, токен и другие значения для конкретного стенда.

Q: Какой раздел запроса в Postman содержит проверки после ответа?
= tests
= Tests
= тесты
! Проверки пишут в разделе Tests на JavaScript.
