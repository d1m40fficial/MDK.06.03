## Приёмка, которой нет в остатках

В понедельник в 10:20 кладовщик московского склада проводит приёмку: 12 рулонов кабеля UTP по поставке 505. Экран показывает зелёное сообщение «Приёмка создана», остаток в карточке товара становится 54. Кладовщик закрывает форму и уходит в зону разгрузки.

Во вторник менеджер строит отчёт по остаткам и видит 42 рулона. Он звонит кладовщику, тот показывает экран с 54. Два числа расходятся, и оба получены из «Склад+». Проверка API на создание приёмки вернула код 201 и правильное тело. Интерфейсный тест «приёмка создаётся» прошёл. Тест-кейс закрыт зелёным, а данные в базе не совпадают с тем, что видел пользователь.

Причина выясняется запросом. Документ приёмки записался в таблицу движений, а остаток в таблице `stock` не обновился: обработчик упал после вставки документа, но до пересчёта остатка, и ошибку проглотил общий обработчик. Экран показал число, которое пришло из кэша карточки, отчёт построился по таблице остатков.

**Тест базы проверяет то, что осталось после операции: строки, связи, типы и суммы.** Экран и API показывают намерение и ответ, база показывает результат. Если проверять только ответ, дефект доживёт до отчёта, сверки с бухгалтерией или инвентаризации.

## Что именно проверяют в базе

База это не одна проверка, а несколько слоёв. У каждого слоя свой вопрос и свой инструмент.

| Слой | Вопрос проверки | Чем смотрят |
|---|---|---|
| Схема | есть ли нужные таблицы, колонки и типы | `PRAGMA table_info`, описание схемы |
| Ограничения | запрещает ли база неверные значения | `PRAGMA index_list`, попытки записи |
| Типы значений | совпадает ли фактический тип с объявленным | `typeof`, приведение и сравнение |
| Связи | у каждой дочерней строки есть родитель | `LEFT JOIN`, `PRAGMA foreign_key_check` |
| Согласованность | сходятся ли суммы и остатки | агрегаты, инварианты |
| Транзакции | не остаётся ли половина операции | `BEGIN`, `ROLLBACK`, повторное чтение |
| Миграции | не потерялось ли что-то при обновлении | сравнение схемы до и после |
| Производительность | укладывается ли запрос в отклик | `EXPLAIN QUERY PLAN`, время |

Разница между слоями видна на одном примере. После обновления 2.8 менеджер в Твери видит пустой список товаров, хотя на площадке лежит 1240 позиций. Интерфейсный тест проходит: страница открылась, пустое состояние отрисовалось. Тест API находит ошибку фильтра: параметр `Тверь` сравнивается с латинским `Tver`. Запрос к базе добавляет третий факт: в таблице `stock` для Твери лежат 1240 строк, значит данные целы, а сломан путь от базы до экрана. Без проверки базы легко решить, что пропали данные, и начать восстановление из копии, хотя восстанавливать нечего.

Проверка базы отвечает и на вопрос, которого нет у интерфейса: **можно ли доверять данным, если экран показывает правильное число.** Кэш, денормализованный остаток, материализованное представление и вторая копия справочника живут в базе рядом с исходными таблицами. Рассинхронизация между ними не видна ни в API, ни на экране, пока не начнётся сверка.

| Что видит интерфейс | Что видит API | Что видит база |
|---|---|---|
| отрисованное число | код и тело ответа | строку, её тип и дату изменения |
| сообщение об ошибке | машиночитаемый код | запись в журнале, если она есть |
| пустой список | `items: []` | 1240 строк или их отсутствие |
| кнопку и её состояние | права роли | ограничения и индексы |
| сумму в отчёте | агрегат запроса | исходные движения и остаток |

Для «Склад+» основной набор проверок данных строится вокруг четырёх таблиц: справочник площадок, справочник товаров, остатки и движения. В справочнике 4800 товаров, в остатках до 19 200 строк, по четыре площадки на товар, в движениях десятки тысяч записей за год. Такой объём нельзя проверить глазами, поэтому проверка формулируется как запрос, который сам находит нарушение.

## Схема и ограничения как контракт

Ограничение это обещание, записанное в схеме. `NOT NULL` запрещает пустое значение, `UNIQUE` запрещает повтор, `PRIMARY KEY` задаёт идентификатор строки, `FOREIGN KEY` требует родителя, `CHECK` проверяет правило, `DEFAULT` подставляет значение. Пока ограничение включено, неверная строка не появится ни через интерфейс, ни через API, ни через скрипт импорта.

Ограничения проверяют не по описанию, а попыткой записи. Наличие строки в схеме ещё не значит, что база её применяет. Ниже учебная база склада: площадки, товары, остатки и движения.

```python
import sqlite3

conn = sqlite3.connect("sklad_db_lecture.db")
conn.isolation_level = None
conn.executescript("""
DROP TABLE IF EXISTS movements;
DROP TABLE IF EXISTS stock;
DROP TABLE IF EXISTS products;
DROP TABLE IF EXISTS sites;

CREATE TABLE sites (
  code  TEXT PRIMARY KEY,
  title TEXT NOT NULL
);
CREATE TABLE products (
  id        INTEGER PRIMARY KEY,
  sku       TEXT NOT NULL UNIQUE,
  title     TEXT NOT NULL,
  unit      TEXT NOT NULL CHECK (unit IN ('шт', 'кг', 'л')),
  min_stock INTEGER NOT NULL DEFAULT 0 CHECK (min_stock >= 0)
);
CREATE TABLE stock (
  site_code  TEXT NOT NULL REFERENCES sites(code),
  product_id INTEGER NOT NULL REFERENCES products(id),
  qty        INTEGER NOT NULL CHECK (qty >= 0),
  PRIMARY KEY (site_code, product_id)
);
CREATE TABLE movements (
  id         INTEGER PRIMARY KEY,
  doc        TEXT NOT NULL,
  kind       TEXT NOT NULL CHECK (kind IN ('приёмка', 'отгрузка')),
  site_code  TEXT NOT NULL REFERENCES sites(code),
  product_id INTEGER NOT NULL REFERENCES products(id),
  qty        INTEGER NOT NULL CHECK (qty > 0),
  created_at TEXT NOT NULL
);
""")
conn.executemany("INSERT INTO sites VALUES (?, ?)",
                 [("MSK", "Москва"), ("TVR", "Тверь"), ("TUL", "Тула"), ("KLG", "Калуга")])
conn.executemany("INSERT INTO products VALUES (?, ?, ?, ?, ?)",
                 [(1001, "SKU-1001", "Кабель UTP", "шт", 50),
                  (1002, "SKU-1002", "Коробка 400x300", "шт", 120),
                  (1003, "SKU-1003", "Стяжка нейлоновая", "шт", 500)])
conn.executemany("INSERT INTO stock VALUES (?, ?, ?)",
                 [("MSK", 1001, 42), ("MSK", 1002, 300), ("TVR", 1001, 1240), ("TVR", 1003, 800)])
conn.executemany("INSERT INTO movements VALUES (?, ?, ?, ?, ?, ?, ?)",
                 [(1, "ПР-501", "приёмка", "MSK", 1001, 60, "2026-10-02 09:12:00"),
                  (2, "ОТ-310", "отгрузка", "MSK", 1001, 18, "2026-10-03 14:40:00"),
                  (3, "ПР-502", "приёмка", "TVR", 1001, 1240, "2026-10-04 10:05:00"),
                  (4, "ПР-503", "приёмка", "TVR", 1003, 800, "2026-10-05 11:30:00")])
conn.commit()

print("колонки stock:")
for col in conn.execute("PRAGMA table_info(stock)"):
    print(f"  {col[1]:10} {col[2]:7} notnull={col[3]} pk={col[5]}")
print("внешних ключей у stock:", len(conn.execute("PRAGMA foreign_key_list(stock)").fetchall()))
print("режим внешних ключей:", conn.execute("PRAGMA foreign_keys").fetchone()[0])

try:
    conn.execute("INSERT INTO stock VALUES ('MSK', 1003, -5)")
except sqlite3.IntegrityError as error:
    print("отрицательный остаток:", error)

conn.execute("UPDATE stock SET qty = '12 шт' WHERE site_code = 'MSK' AND product_id = 1001")
print("значение и тип:", conn.execute(
    "SELECT qty, typeof(qty) FROM stock WHERE site_code = 'MSK' AND product_id = 1001").fetchone())
print("сравнение и арифметика:", conn.execute(
    "SELECT qty >= 0, qty + 10 FROM stock WHERE site_code = 'MSK' AND product_id = 1001").fetchone())
```

Скрипт создаёт базу и сразу проверяет три вещи: состав колонок, наличие внешних ключей и реакцию на неверное значение. Вот его вывод.

```text
колонки stock:
  site_code  TEXT    notnull=1 pk=1
  product_id INTEGER notnull=1 pk=2
  qty        INTEGER notnull=1 pk=0
внешних ключей у stock: 2
режим внешних ключей: 0
отрицательный остаток: CHECK constraint failed: qty >= 0
значение и тип: ('12 шт', 'text')
сравнение и арифметика: (1, 22)
```

Первые строки показывают, что схема на месте: у остатка три колонки, составной первичный ключ из площадки и товара, два внешних ключа. Строка «режим внешних ключей: 0» сообщает важное: в SQLite внешние ключи по умолчанию выключены и включаются отдельной командой для каждого соединения. Ограничение объявлено, но не работает, пока его не включили.

Строка с отрицательным остатком показывает, что `CHECK` действительно срабатывает: база отказала во вставке и вернула понятную причину. Так и проверяют ограничение: не читают схему, а пытаются записать неверное значение и смотрят, что произойдёт.

Последние две строки раскрывают ловушку типов. В колонку `qty` записали текст `12 шт`, и база его приняла. В SQLite тип колонки это рекомендация, а не жёсткий запрет: значение хранится в том виде, в каком пришло, если его нельзя привести к объявленному типу без потери. Функция `typeof` показывает `text`. При этом проверка `qty >= 0` возвращает истину, потому что в порядке сравнения SQLite любое число меньше любой строки. Арифметика `qty + 10` даёт 22, потому что из строки берётся числовое начало. Ошибка не падает, не даёт предупреждения и спокойно живёт в базе.

Именно поэтому проверка значения без проверки типа слабая. Запрос `SELECT qty FROM stock WHERE qty < 0` вернёт пустой результат и создаст ложное ощущение порядка. Запрос с `typeof(qty) <> 'integer'` находит такую строку сразу.

| Ограничение | Что запрещает | Как проверить |
|---|---|---|
| `NOT NULL` | пустое значение | вставить `NULL` в колонку |
| `UNIQUE` | повтор ключа | вставить ту же строку дважды |
| `PRIMARY KEY` | дубль идентификатора | вставить существующий ключ |
| `FOREIGN KEY` | ребёнка без родителя | включить режим и вставить чужой код |
| `CHECK` | значение вне правила | вставить ноль, минус, чужую единицу |
| `DEFAULT` | отсутствие значения | вставить строку без колонки |

Проверять стоит и то, чего в схеме нет. Если `stock.qty` не имеет ограничения `>= 0`, значит запрет живёт в коде приложения, и любой обход приложения его снимет. Тест фиксирует это как риск, даже если сегодня все обработчики аккуратны.

Отдельная проверка касается миграций. После обновления схемы сравнивают список колонок, индексов и ограничений до и после. Новая колонка с `DEFAULT NULL` на большой таблице, потерянный уникальный индекс или переименованное поле ломают не интерфейс, а отчёты и обмен с бухгалтерией. Версию схемы удобно хранить в `PRAGMA user_version` и сверять её с версией сборки.

## Дубликаты и потерянные связи

Первичный ключ защищает от повтора идентификатора, но не от повтора бизнес-ключа. Две приёмки по поставке 505 имеют разные `id` и одинаковый номер документа. Для базы это разные строки, для склада это одна и та же приёмка, проведённая дважды.

Дубликат ищут группировкой по бизнес-ключу. Бизнес-ключ это набор полей, который для пользователя означает один объект: номер документа, артикул, сочетание площадки и товара, номер накладной вместе с датой.

```python
import sqlite3

conn = sqlite3.connect("sklad_db_lecture.db")
conn.isolation_level = None

conn.execute("INSERT INTO movements VALUES (5, 'ПР-501', 'приёмка', 'MSK', 1001, 60, '2026-10-06 08:00:00')")
conn.execute("INSERT INTO movements VALUES (6, 'ПР-504', 'приёмка', 'SAR', 1001, 5, '2026-10-06 08:10:00')")

print("дубли по номеру документа:")
for doc, count in conn.execute("SELECT doc, COUNT(*) FROM movements GROUP BY doc HAVING COUNT(*) > 1"):
    print(f"  {doc}: {count} строки")

print("движения без площадки:")
for row in conn.execute("""SELECT m.id, m.doc, m.site_code
                           FROM movements m
                           LEFT JOIN sites s ON s.code = m.site_code
                           WHERE s.code IS NULL"""):
    print(" ", row)

print("нарушения внешних ключей:", conn.execute("PRAGMA foreign_key_check").fetchall())

print("сверка остатка с движениями:")
query = """
SELECT s.site_code, p.sku, s.qty,
       COALESCE(SUM(CASE WHEN m.kind = 'приёмка' THEN m.qty ELSE -m.qty END), 0) AS calc
FROM stock s
JOIN products p ON p.id = s.product_id
LEFT JOIN movements m ON m.site_code = s.site_code AND m.product_id = s.product_id
GROUP BY s.site_code, p.sku, s.qty
ORDER BY s.site_code, p.sku
"""
for site, sku, qty, calc in conn.execute(query):
    mark = "ок" if qty == calc else "расхождение"
    print(f"  {site} {sku}: в остатках {qty}, по движениям {calc}, {mark}")
```

Скрипт добавляет в базу две плохие строки: повтор приёмки ПР-501 и приёмку с площадкой `SAR`, которой нет в справочнике. Затем он ищет дубли, потерянные связи и сверяет остаток с движениями.

```text
дубли по номеру документа:
  ПР-501: 2 строки
движения без площадки:
  (6, 'ПР-504', 'SAR')
нарушения внешних ключей: [('movements', 6, 'sites', 1)]
сверка остатка с движениями:
  MSK SKU-1001: в остатках 12 шт, по движениям 102, расхождение
  MSK SKU-1002: в остатках 300, по движениям 0, расхождение
  TVR SKU-1001: в остатках 1240, по движениям 1240, ок
  TVR SKU-1003: в остатках 800, по движениям 800, ок
```

Группировка нашла документ ПР-501 с двумя строками. Это дубликат, и он виден без знания того, какая строка лишняя: решение принимают по дате, автору и связи с поставкой.

Потерянная связь нашлась левым соединением. `LEFT JOIN` сохраняет все строки движений и подставляет `NULL` там, где родитель не найден. Условие `WHERE s.code IS NULL` оставляет только такие строки. Тот же результат даёт `PRAGMA foreign_key_check`, который перечисляет таблицу, номер строки, родительскую таблицу и номер ограничения. Проверка полезна и после импорта: загрузка из файла часто идёт в обход ограничений.

Сверка остатка показывает два расхождения. В Твери остаток совпадает с движениями, в Москве нет. По кабелю в остатках стоит текст `12 шт`, а по движениям 102: сказались и подмена типа, и дубль приёмки на 60 штук. По коробкам в остатках 300, а движений нет вообще: начальный остаток ввели вручную и не занесли документ. Один запрос нашёл три разных дефекта, потому что сверяет не отдельное поле, а правило.

| Дефект | Запрос | Симптом |
|---|---|---|
| Дубль по бизнес-ключу | `GROUP BY doc HAVING COUNT(*) > 1` | две приёмки по одной поставке |
| Ребёнок без родителя | `LEFT JOIN ... WHERE parent IS NULL` | отчёт теряет строки площадки |
| Неверный тип | `typeof(qty) <> 'integer'` | число сравнивается как строка |
| Отрицательный остаток | `WHERE qty < 0` | списание больше остатка |
| Пустое значение | `WHERE qty IS NULL` | сумма игнорирует строку |
| Битая дата | `WHERE date(created_at) IS NULL` | отчёт за период пуст |

Есть классическая ловушка с `NOT IN`. Запрос `WHERE id NOT IN (SELECT product_id FROM stock)` вернёт пустой результат, если в подзапросе есть хотя бы один `NULL`: сравнение с `NULL` даёт неизвестность, и условие не выполняется ни для одной строки. Для поиска потерянных связей надёжнее `NOT EXISTS` или левое соединение с проверкой на `NULL`.

Дубликаты и потерянные связи опасны тем, что не мешают системе работать. Приёмка проводится, отчёт строится, ошибок нет. Цена проявляется позже: в сверке с бухгалтерией, в инвентаризации, в недостаче, которую невозможно объяснить.

## Транзакции и откат

Транзакция объединяет несколько изменений в одно. Либо применяются все, либо ни одного. Для склада это принципиально: приёмка состоит из записи документа, строк документа и пересчёта остатка. Если после документа упал пересчёт, склад получает документ без остатка, то есть ровно тот дефект, с которого началась лекция.

Проверка транзакции строится на откате. Сначала читают состояние, потом начинают транзакцию, выполняют операцию, намеренно вызывают ошибку, откатывают и снова читают состояние. Если числа совпали, атомарность работает.

```python
import sqlite3

conn = sqlite3.connect("sklad_db_lecture.db")
conn.isolation_level = None

before = conn.execute("SELECT COUNT(*) FROM movements").fetchone()[0]
conn.execute("BEGIN")
conn.execute("INSERT INTO movements VALUES (7, 'ПР-505', 'приёмка', 'KLG', 1002, 40, '2026-10-07 09:00:00')")
print("внутри транзакции:", conn.execute("SELECT COUNT(*) FROM movements").fetchone()[0])
conn.execute("ROLLBACK")
print("после отката:", conn.execute("SELECT COUNT(*) FROM movements").fetchone()[0], "было:", before)

conn.execute("INSERT INTO movements VALUES (8, 'ПР-506', 'приёмка', 'KLG', 1002, 40, '2026-10-07 09:00:00')")
try:
    conn.execute("INSERT INTO movements VALUES (9, 'ПР-506', 'приёмка', 'KLG', 1002, 0, '2026-10-07 09:00:05')")
except sqlite3.IntegrityError as error:
    print("вторая строка отклонена:", error)
print("строк по документу ПР-506:", conn.execute(
    "SELECT COUNT(*) FROM movements WHERE doc = 'ПР-506'").fetchone()[0])

conn.execute("BEGIN")
conn.execute("INSERT INTO movements VALUES (10, 'ПР-507', 'приёмка', 'KLG', 1002, 40, '2026-10-07 10:00:00')")
try:
    conn.execute("INSERT INTO movements VALUES (11, 'ПР-507', 'приёмка', 'KLG', 1002, 0, '2026-10-07 10:00:05')")
except sqlite3.IntegrityError as error:
    conn.execute("ROLLBACK")
    print("откат после ошибки:", error)
print("строк по документу ПР-507:", conn.execute(
    "SELECT COUNT(*) FROM movements WHERE doc = 'ПР-507'").fetchone()[0])

conn.execute("DELETE FROM movements WHERE doc = 'ПР-506'")
print("после уборки тестовых строк:", conn.execute("SELECT COUNT(*) FROM movements").fetchone()[0])
```

Скрипт проверяет три сценария: чистый откат, частичную запись без транзакции и ту же операцию внутри транзакции. Вывод показывает разницу.

```text
внутри транзакции: 7
после отката: 6 было: 6
вторая строка отклонена: CHECK constraint failed: qty > 0
строк по документу ПР-506: 1
откат после ошибки: CHECK constraint failed: qty > 0
строк по документу ПР-507: 0
после уборки тестовых строк: 6
```

Первая пара строк показывает, что откат вернул базу в исходное состояние: внутри транзакции было 7 строк, после `ROLLBACK` снова 6. Это базовая проверка атомарности.

Вторая пара показывает опасный сценарий. Две вставки шли без транзакции, в режиме автоподтверждения. Первая строка записалась, вторая нарушила `CHECK` и была отклонена. В базе осталась одна строка из двух, то есть половина документа. Приложение получило ошибку и, скорее всего, показало её пользователю, но данные уже изменились.

Третья пара показывает, как та же операция ведёт себя внутри транзакции. После ошибки выполняется `ROLLBACK`, и по документу ПР-507 остаётся ноль строк. Пользователь видит ошибку, база остаётся чистой, повтор операции безопасен.

| Проверка | Действие | Ожидание |
|---|---|---|
| Откат | `BEGIN`, вставка, `ROLLBACK` | число строк не изменилось |
| Частичная запись | две вставки без транзакции, вторая с ошибкой | появилась одна строка, дефект |
| Атомарность | две вставки в транзакции, вторая с ошибкой | ноль строк |
| Фиксация | `BEGIN`, вставка, `COMMIT`, переподключение | строка видна после переподключения |
| Блокировка | вторая транзакция на ту же строку | ожидание или отказ, без потери данных |

Проверять стоит и успешную фиксацию. Иногда тест делает `ROLLBACK` и радуется, что данные не изменились, а на самом деле операция вообще не выполнялась. Поэтому в наборе есть обе ветки: откат и подтверждение.

С транзакциями связан ещё один класс дефектов, который виден только под нагрузкой. Два кладовщика одновременно проводят приёмку по одной поставке. Оба читают остаток 42, оба прибавляют 12, оба записывают 54. Одна приёмка теряется. Защита здесь не в транзакции самой по себе, а в уникальном индексе по номеру поставки и в проверке конфликта: второй запрос получает отказ, а не молча перезаписывает результат. Тест данных проверяет, что уникальный индекс существует и что после двух параллельных попыток в базе одна приёмка и остаток 54, а не 66.

> [!PITFALL] Тест, который меняет рабочую базу
> Проверка транзакции выполняется на копии или на тестовом стенде. Если запустить её на рабочей базе и забыть `ROLLBACK`, тестовые строки попадут в отчёт, а остаток изменится. Перед проверкой фиксируют исходные суммы, после проверки сверяют их и удаляют тестовые данные по известному признаку.

## Оракул для данных

Проверка данных отличается от проверки интерфейса тем, что ожидаемый результат нельзя увидеть на экране. Его нужно вычислить из независимого источника. Таким источником может быть первичный документ, сумма движений, внешняя система или правило, которому обязаны подчиняться данные.

Правило, которому подчиняются данные, называют инвариантом. Для склада основной инвариант простой: остаток равен сумме приёмок минус сумма отгрузок по этой позиции и площадке. Если остаток ввели вручную при открытии склада, добавляется начальный остаток, и это должно быть записано в правилах.

```sql
SELECT s.site_code, p.sku, s.qty,
       COALESCE(SUM(CASE WHEN m.kind = 'приёмка' THEN m.qty ELSE -m.qty END), 0) AS calc
FROM stock s
JOIN products p ON p.id = s.product_id
LEFT JOIN movements m ON m.site_code = s.site_code AND m.product_id = s.product_id
GROUP BY s.site_code, p.sku, s.qty;
```

Запрос уже встречался в разборе дублей. Его смысл не в синтаксисе, а в том, что он сравнивает два независимых представления одного факта: текущий остаток и историю движений. Совпадение говорит, что данные согласованы. Расхождение говорит, что где-то потерялся документ, появился дубль или остаток изменили в обход движений.

| Оракул | С чем сравнивают | Что ловит |
|---|---|---|
| Сумма движений | остаток в `stock` | потерянную приёмку, дубль |
| Количество строк | число позиций в накладной | потерянную строку |
| Сумма по документу | сумма строк документа | обрезанную накладную |
| Ссылочная целостность | справочники | ребёнка без родителя |
| Диапазон | правила поля | ноль, минус, гигантское число |
| Уникальность | бизнес-ключ | повторную приёмку |
| Сверка с внешней системой | выгрузка бухгалтерии | расхождение сумм |

Оракул должен быть независимым. Если ожидаемое значение считать тем же запросом, который проверяют, тест подтвердит любой результат. Поэтому сумму движений считают по первичным документам, а не по таблице остатков, и сравнивают два разных источника.

Для больших объёмов проверку делят на полную и выборочную. Полная сверка 19 200 строк остатков идёт на тестовом стенде после загрузки и миграции. На рабочей базе запускают выборочную проверку по нескольким позициям и по площадкам с наибольшим оборотом, причём только запросами на чтение. Если нужен запрос с изменением, его выполняют в транзакции с откатом и на копии.

> [!KEY]
> Хорошая проверка данных называет ожидаемое число и правило, по которому оно получено. Проверка «значение не пустое» не говорит, верно ли значение.

## Типичные дефекты базы

Дефекты данных повторяются от проекта к проекту. Список стоит держать перед глазами, потому что каждый пункт превращается в запрос.

| Дефект | Как проявляется | Чем ловится |
|---|---|---|
| Дубль по бизнес-ключу | две приёмки по одной поставке | `GROUP BY` и `HAVING` |
| Потерянная связь | строка ссылается на удалённую площадку | `LEFT JOIN`, `foreign_key_check` |
| Неверный тип | в числе лежит `12 шт` | `typeof` |
| Отрицательный остаток | списали больше, чем было | `CHECK` и запрос на минус |
| `NULL` вместо нуля | сумма пропускает строку | `IS NULL` и `COALESCE` |
| Дата строкой | отчёт за период пуст | `date()` и сравнение форматов |
| Разные единицы | килограммы сложили со штуками | справочник единиц и `JOIN` |
| Нет уникального индекса | повтор проходит при двух запросах | `PRAGMA index_list` |
| Неполный откат | документ есть, строк нет | проверка транзакции |
| Потерянное обновление | два пользователя перезаписали остаток | уникальный ключ и проверка конфликта |
| Рассинхронизация кэша | экран и отчёт расходятся | сверка остатка и движений |
| Медленный запрос | отчёт строится минутами | `EXPLAIN QUERY PLAN` |

Два дефекта из таблицы стоит разобрать отдельно, потому что они не выглядят как ошибки.

Первый это `NULL` вместо нуля. В SQL `NULL` означает неизвестность, а не ноль. Сумма с `NULL` игнорирует строку, сравнение с `NULL` не даёт истины, а `COUNT(column)` не считает такие строки. Отчёт «сколько позиций с нулевым остатком» покажет меньше, чем есть, и никто не заметит пропажу. Проверка ищет `NULL` в колонках, где по смыслу должен быть ноль, и сверяет количество строк с ожидаемым.

Второй это разные единицы измерения. В справочнике товаров есть единица, но в движениях её может не быть. Если приёмка пришла в килограммах, а остаток хранится в штуках, арифметика формально сходится, а склад считает не то. Проверка соединяет движения со справочником и ищет строки, где единица не совпадает или отсутствует.

## Как встроить проверки данных в работу

Проверки данных оформляют как SQL-скрипт с именованными запросами. Каждый запрос возвращает пустой результат, если нарушений нет, и строки с нарушением, если они есть. Такой скрипт запускают после загрузки справочников, после миграции, после восстановления из копии и в конце приёмочного прогона.

Набор делят на три уровня. Дымовой набор из пяти запросов проверяет, что таблицы доступны, ключевые суммы сходятся и нет потерянных связей. Основной набор из двадцати запросов закрывает дубли, типы, диапазоны и согласованность по всем площадкам. Полный набор добавляет сверку с бухгалтерией и проверку истории за год. Уровни нужны, чтобы не запускать тяжёлую сверку на каждой сборке.

| Уровень | Запросов | Что закрывает | Когда запускают |
|---|---|---|---|
| Дымовой | 5 | доступность, ключевые суммы, связи | каждая сборка |
| Основной | 20 | дубли, типы, диапазоны, остатки | ночь и приёмка |
| Полный | 38 | сверка с внешней системой, история | релиз и миграция |

Дефект по данным оформляют иначе, чем дефект интерфейса. В нём указывают запрос, ожидаемый результат, фактический результат, версию схемы и набор данных. Скриншота недостаточно: по нему нельзя повторить запрос. Если дефект найден на копии, прикладывают скрипт, который создаёт такие данные.

Проверка базы не заменяет проверку API и интерфейса. Она отвечает на последний вопрос: сохранилось ли то, что обещали. Интерфейс может быть удобным, API может отвечать правильно, а данные при этом разойдутся с документами. Поэтому в отчёте о тестировании проверки данных идут отдельной строкой с числом запросов и найденных нарушений.

::/gate

## Регрессия и отчёт по данным

В регрессионный набор по данным попадает то, что уже ломалось, и то, что связано с деньгами и остатками. Для «Склад+» это шесть групп: уникальность приёмки по поставке, согласованность остатка с движениями, отсутствие потерянных связей, допустимые типы, диапазоны значений и успешный откат неудачной операции.

Каждая группа привязана к требованию. Уникальность приёмки связана с требованием «приёмка создаётся один раз на поставку». Согласованность остатка с требованием «остаток обновляется после приёмки». Ссылочная целостность с требованием о площадках и товарах. Типы и диапазоны с требованием о количестве от 1 до 10 000. Откат с требованием о целостности документа.

| Группа | Проверка | Требование |
|---|---|---|
| Уникальность | одна приёмка на поставку | приёмка создаётся один раз |
| Согласованность | остаток равен движениям | остаток обновляется после приёмки |
| Связи | нет движений без площадки | площадка из справочника |
| Типы | `typeof(qty) = 'integer'` | количество целое |
| Диапазон | от 1 до 10 000 | количество в допустимых границах |
| Откат | после ошибки ноль строк | документ целый или отсутствует |

В отчёт попадают не все запросы, а сводка: сколько проверок выполнено, сколько нашло нарушения, какие группы покрыты и какие нет. К сводке прикладывают список нарушений с номерами строк и запросами. Если проверка не запускалась, это отмечают отдельно: пропуск не равен успеху.

Вывод о готовности по данным делают по критериям, записанным заранее. Например: все критические нарушения закрыты, потерянных связей нет, расхождений остатка с движениями нет, доля выполненных проверок не ниже 95 процентов. Если критерии не выполнены, в отчёте пишут, какие данные нельзя выпускать и что нужно исправить.

## Итоги

- Тест базы проверяет схему, ограничения, типы, связи, согласованность и транзакции запросами.
- Ограничение проверяют попыткой записи, а не чтением схемы: объявленный внешний ключ может быть выключен.
- В SQLite тип колонки это рекомендация, поэтому проверяют `typeof`, а не только значение.
- Дубликат ищут по бизнес-ключу, потерянную связь по левому соединению и `foreign_key_check`.
- Транзакцию проверяют откатом и повторным чтением: половина документа не должна оставаться в базе.
- Оракул для данных это независимый источник: сумма движений, первичный документ, внешняя выгрузка.
- Проверки данных оформляют SQL-скриптом и делят на дымовой, основной и полный наборы.

+ Схему, ограничения, типы, связи и согласованность данных

- Скорость набора текста пользователем
- Цвет сообщений об ошибках

- Права роли на таблицу
- Резервную копию таблицы
! CHECK отклоняет строку, которая не проходит условие.

+ Тип колонки задаёт рекомендацию, а значение хранится как пришло
- Потому что внешние ключи выключены
- Потому что таблица не имеет первичного ключа
- Потому что база работает только в памяти
! В SQLite действует механизм сродства типов, а не жёсткий запрет.

+ text
- integer
- real
- null

+ Левым соединением со справочником и условием `WHERE s.code IS NULL`
- Внутренним соединением со справочником
- Сортировкой по коду площадки
- Запросом `COUNT(*)` по таблице движений
! Левое соединение сохраняет строки без родителя.

+ Внешние ключи не проверяются в текущем соединении
- Все внешние ключи удалены из схемы
- Таблица недоступна для чтения
- Включён режим только для чтения

+ Чтобы убедиться, что неудачная операция не оставила часть данных
- Чтобы ускорить выполнение запросов
- Чтобы удалить резервную копию
- Чтобы отключить ограничения
! Откат возвращает базу в исходное состояние, и это проверяют повторным чтением.

Q: Что такое инвариант остатка?
+ Правило, которому обязан соответствовать остаток: приёмки минус отгрузки
- Среднее число строк в таблице
- Максимальный размер базы
- Список ролей пользователей
! Инвариант связывает остаток с историей движений.

+ Поиск дубликатов по бизнес-ключу
+ Поиск потерянных связей
+ Проверка отрицательного остатка

- Измерение времени отклика страницы

+ Номер строки с нарушением
- Пароль учётной записи пользователя
- Личные данные сотрудников склада
