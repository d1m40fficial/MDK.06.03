## Краткие теоретические сведения

Проверка данных отвечает на вопрос, сохранилось ли то, что обещала система. Экран и API показывают результат операции, база хранит его. Если экран показывает 42, API отдаёт 42, а в базе лежит 40, значит экран и API читают не тот источник или кешируют старое значение.

Целостность данных держится на ограничениях и правилах. Ограничения `NOT NULL`, `UNIQUE`, `CHECK` и `FOREIGN KEY` запрещают часть неверных строк. Правила, которые нельзя записать в схему, проверяют запросами: остаток не отрицательный, сумма движений сходится с остатком, у каждого движения есть площадка и товар.

Тип значения проверяют отдельно от значения. В SQLite тип колонки это рекомендация: текст, который нельзя привести к числу, сохраняется как текст. Функция `typeof` показывает фактический тип. Запрос `WHERE qty < 0` такую строку не найдёт, потому что сравнение числа со строкой даёт неожиданный результат.

Дубликат ищут по бизнес-ключу, а не по первичному ключу. Две приёмки по поставке 505 имеют разные `id` и одинаковый номер документа. Потерянную связь ищут левым соединением со справочником: строки, у которых родитель не найден, остаются с `NULL`.

Транзакция объединяет изменения в одно целое. Проверка откатом показывает, остаётся ли половина операции после ошибки. Сначала читают количество строк, затем начинают транзакцию, выполняют вставку, откатывают и читают снова. Совпадение чисел означает, что откат работает.

Порядок проверки идёт от общего к частному. Сначала смотрят, что база доступна и схема соответствует версии. Потом проверяют ограничения и типы, затем связи и согласованность, и только после этого переходят к экрану. Если начать с экрана, легко принять дефект отображения за потерю данных и потратить время на восстановление исправной базы.

Данные для проверки готовят заранее и убирают после неё. В учебной базе это отдельный файл, который создаётся скриптом. На стенде тестовые строки помечают известным признаком, например номером документа из диапазона, который не используется в работе. Без такого признака уборка превращается в поиск иголки в стоге и рискует удалить рабочие записи.

Серьёзность нарушения данных зависит от последствий, а не от типа ошибки. Потерянная приёмка на 60 единиц влияет на остаток и на деньги, поэтому она критическая. Неверный регистр логина мешает входу, но не меняет остатки, поэтому она серьёзная, но не критическая. Оценку записывают рядом с нарушением, иначе отчёт превращается в список без приоритетов.

Валидация интерфейса проверяет те же правила, что и сервер, но показывает результат пользователю. Поле обязательное, значение в диапазоне, формат совпадает с шаблоном, сообщение стоит рядом с полем и называет действие. Тест проверяет форму на всех значениях из требования и смотрит, что сообщение появилось у нужного поля, а введённые данные сохранились.

В схеме остаток хранится отдельно от движений. Так быстрее читать текущее количество, но появляется второй источник правды. Движения отвечают на вопрос, откуда взялось число, остаток на вопрос, сколько есть сейчас. Пока оба источника обновляются одной транзакцией, они сходятся. Справочники отделены от операционных таблиц намеренно. Площадка и товар описываются один раз, а движения ссылаются на них по коду и номеру. Такая схема не даёт хранить название площадки в каждой строке и получать разные написания одного склада.

Проверка схемы и проверка данных дополняют друг друга, первая объясняет, почему вторая нашла нарушение.

### Шаг 3. Проверьте типы и пустые значения

Значение может быть заполнено, но иметь неверный тип. Найдите такие строки запросом с `typeof`.

Заполните таблицу: где найдено, какой тип или значение ожидалось, что фактически, чем это опасно. Первая строка дана как образец.

| Объект | Ожидание | Факт | Риск |
|---|---|---|---|
| Остаток KLG, товар 1006 | целое число |  |  |
|  |  |  |  |
|  |  |  |  |

Проверьте, как ведёт себя сравнение с нецелым значением. Запрос `SELECT qty < 0 FROM stock WHERE product_id = 1006` вернёт результат, который нужно объяснить в отчёте.

Причина в порядке сравнения. В SQLite любое число меньше любой строки, поэтому `'1200 шт' < 0` даёт ложь, а `'1200 шт' >= 0` даёт истину. Ограничение `CHECK (qty >= 0)` такую строку пропускает. Арифметика при этом берёт из строки числовое начало, и `qty + 10` даёт 1210. Ошибка не падает, а тихо живёт в данных.

Исправление начинают с поиска всех строк с неверным типом, затем выясняют, какой путь записи их создал. Просто заменить значение на число недостаточно: следующий импорт вернёт текст. Проверяют обработчик, который пишет остаток, и добавляют проверку типа на входе.

### Шаг 4. Найдите дубликаты и потерянные связи

Дубликат ищут группировкой по бизнес-ключу, потерянную связь левым соединением. Ниже пример для движений и пользователей.

```python
conn = sqlite3.connect("sklad_test.db")

print("нарушения внешних ключей:", conn.execute("PRAGMA foreign_key_check").fetchall())
print("похожие логины:")
for row in conn.execute("""SELECT a.id, a.login, b.id, b.login
                           FROM users a JOIN users b
                             ON lower(trim(a.login)) = lower(trim(b.login)) AND a.id < b.id"""):
    print(" ", row)
```

| Нарушение | Ключ | Строки | Причина |
|---|---|---|---|
| Дубль приёмки | номер документа |  |  |

Объясните, почему уникальный индекс по `login` не поймал логины, которые различаются регистром или пробелом. Предложите, что изменить в схеме или в проверке.

Уникальный индекс сравнивает значения так, как они записаны. Для текста в SQLite сравнение по умолчанию учитывает регистр, а пробел в конце делает строку другой. Поэтому `petrov` и `Petrov` проходят как два разных логина, хотя для пользователя это один человек. Исправление возможно на уровне схемы, через индекс с `COLLATE NOCASE` и правило нормализации, или на уровне проверки, которая ищет совпадения по `lower(trim(login))`. Выбор зависит от того, какие правила приняты в системе.

### Шаг 5. Сверьте остаток с движениями

Остаток и история движений это два представления одного факта. Сверка показывает, где они расходятся.

```python
import sqlite3

conn = sqlite3.connect("sklad_test.db")
query = """
SELECT s.site_code, p.sku, s.qty,
       COALESCE(SUM(CASE WHEN m.kind = 'приёмка' THEN m.qty ELSE -m.qty END), 0) AS calc
FROM stock s
JOIN products p ON p.id = s.product_id
LEFT JOIN movements m ON m.site_code = s.site_code AND m.product_id = s.product_id
GROUP BY s.site_code, p.sku, s.qty
ORDER BY s.site_code, p.sku
"""
for site, sku, qty, calc in conn.execute(query):
    mark = "ок" if qty == calc else "расхождение"
    print(f"  {site} {sku}: в остатках {qty}, по движениям {calc}, {mark}")
```

Для каждого расхождения укажите возможную причину: потерянная приёмка, дубль, начальный остаток без документа, отгрузка больше остатка, неверный тип. Первая строка дана как образец.

| Позиция | В остатках | По движениям | Причина |
|---|---|---|---|
| MSK SKU-1001 | 40 | 102 |  |
|  |  |  |  |

Проверьте, что запрос не скрывает строки без движений. Для этого сравните число строк в результате с числом строк в `stock`. Если они различаются, объясните почему.

Причина расхождения не всегда ошибка. Остаток мог быть введён при открытии склада, и тогда документ начального остатка должен существовать отдельно. Если такого документа нет, правило не выполнено: остаток появился из ниоткуда, и при следующей инвентаризации его придётся объяснять. Проверка требует не только найти расхождение, но и назвать источник, который его объясняет или не объясняет.

### Шаг 6. Проверьте транзакцию приёмки

Приёмка состоит из записи документа и пересчёта остатка. Проверьте, что неудачная операция не оставляет половину данных. Ниже пример для одного документа.

```python
import sqlite3

conn = sqlite3.connect("sklad_test.db")
conn.isolation_level = None
before = conn.execute("SELECT COUNT(*) FROM movements").fetchone()[0]
conn.execute("BEGIN")
conn.execute("INSERT INTO movements VALUES (13, 'ПР-509', 'приёмка', 'MSK', 1002, 25, '2026-10-12 09:00:00')")
conn.execute("ROLLBACK")
after = conn.execute("SELECT COUNT(*) FROM movements").fetchone()[0]
print("до:", before, "после отката:", after)
print("строк по ПР-509:", conn.execute("SELECT COUNT(*) FROM movements WHERE doc = 'ПР-509'").fetchone()[0])
```

Повторите опыт для документа ПР-510: внутри транзакции вставьте правильную строку, затем строку с количеством `0`, перехватите ошибку и выполните `ROLLBACK`. Заполните таблицу.

| Опыт | До | После | Строк по документу | Вывод |
|---|---|---|---|---|
| Откат ПР-509 |  |  |  |  |
| Ошибка в ПР-510 |  |  |  |  |

Проверьте, что после отката не изменился и остаток. Для этого сравните `qty` до и после опыта. Если остаток изменился, значит пересчёт шёл вне транзакции, и это дефект.

### Шаг 7. Сверьте экран, API и базу

Ниже выдержка из протокола проверки остатков на стенде. Экран и API показывают одно, база хранит другое. Значения собраны в одну таблицу.

| Позиция | Экран | API | База |
|---|---|---|---|
| MSK SKU-1001 | 42 | 42 | 40 |
| MSK SKU-1002 | 300 | 300 | 300 |
| MSK SKU-1003 | 780 | 780 | 780 |
| TVR SKU-1001 | 1240 | 1240 | 1240 |
| TUL SKU-1005 | 0 | 0 | 0 |
| KLG SKU-1006 | 1200 | 1200 | 1200 шт |

Совпадение трёх источников не доказывает правильность. Остаток может быть одинаково неверным на экране, в API и в базе, если все они читают одну и ту же ошибочную таблицу. Поэтому сверка остатка с движениями на шаге 5 остаётся отдельной проверкой, а не заменяется сравнением трёх источников.

Для каждой строки определите, где родился дефект: в интерфейсе, в API, в базе или расхождения нет. Заполните таблицу. Первая строка дана как образец.

| Позиция | Расхождение | Где родился | Что проверить |
|---|---|---|---|
| MSK SKU-1001 | экран и API 42, база 40 | кеш интерфейса или запрос | обновление кеша после приёмки |
|  |  |  |  |

Проверьте каждую версию запросом или повторным чтением. Если экран и API совпадают, а база нет, сначала исключите кеш: обновите страницу и повторите запрос. Если значение не изменилось, смотрите запрос, которым API читает остаток. Если после обновления страницы значение стало верным, дефект в кеше.

Три источника сравнивают не наугад, а по порядку. Сначала фиксируют, что показал экран до и после обновления. Затем снимают ответ API с тем же параметром площадки. Затем читают строку в базе по ключу площадки и товара. Совпадение двух источников ещё не доказывает правильность: экран и API могут читать один и тот же кеш, а база хранить верное число.

Если расходятся все три источника, начинают с базы. Проверяют, есть ли строка, какой у неё тип и когда она менялась. Если база верна, переходят к API: смотрят, какой запрос уходит и что возвращается. Если API верен, остаётся интерфейс: кеш, форматирование, фильтр или устаревшее состояние экрана.

Обратите внимание на строку KLG SKU-1006. На экране и в API значение выглядит правильным, а в базе лежит текст. Такой дефект не виден пользователю, но ломает сравнение и арифметику. Объясните в отчёте, почему проверка только экрана его пропускает.

### Шаг 8. Проверьте валидацию полей

Правила формы приёмки заданы в требовании.

```text
Поставка: обязательна, целое число от 1 до 999999
Количество: обязательно, целое число от 1 до 10 000
Ячейка: обязательна, шаблон: заглавная буква, дефис, две цифры (например, A-14)
Комментарий: необязателен, до 200 символов
```

Проверьте значения через форму. Заполните таблицу. Первая строка дана как образец.

| Поле | Значение | Ожидание | Факт | Результат |
|---|---|---|---|---|
| Количество | 0 | отказ |  |  |
| Количество |  |  |  |  |
| Поставка |  |  |  |  |
| Ячейка |  |  |  |  |

Используйте значения: пустое поле, `-1`, `1`, `10 000`, `10 001`, `12,5`, `12 `, `999999`, `A-14`, `a-14`, `A14`, строка из 201 символа. Для каждого случая запишите ожидаемый результат по требованию и фактический.

Значения подобраны не случайно. Ноль и минус проверяют нижнюю границу, единица и максимум допустимую область, максимум плюс один выход за границу. Дробное число проверяет тип, пробел в конце проверяет нормализацию, а строка из 201 символа проверяет длину комментария. Для ячейки важны три варианта: правильный `A-14`, строчная буква `a-14` и отсутствие дефиса `A14`. Требование разрешает только один из них, и форма должна объяснить отказ.

Сравнение с требованием обязательно. Форма проверяет поле в браузере, и для учебного стенда этого достаточно. Если значение, запрещённое требованием, проходит, дефект в валидации формы. Если форма отклоняет допустимое значение, дефект в правиле или в сообщении.

Проверьте, что сообщение об ошибке стоит рядом с полем, называет правило и не исчезает само. Если форма пропускает значение, которое запрещено требованием, зафиксируйте это как дефект валидации.

### Шаг 9. Проверьте клавиатуру и сообщения

### Шаг 10. Оформите результаты

Сведите найденные нарушения в таблицу: идентификатор, объект, ожидание, факт, уровень (интерфейс, API, база), серьёзность, ссылка на проверку. Отдельно запишите, какие проверки прошли без замечаний: это показывает объём выполненной работы.

Идентификаторы делают отчёт проверяемым. Нарушения нумеруют `D-01`, `D-02`, проверки `CH-01`, `CH-02`. Одна проверка может найти несколько нарушений, и тогда ссылка ведёт на проверку, а не наоборот. Если нарушение найдено на стыке, в уровне указывают два значения, например «интерфейс и API», и объясняют, где именно теряется правильное значение.

Серьёзность ставят по последствиям. Потеря или искажение остатка это критическая серьёзность, потому что страдают деньги и отгрузка. Неверное сообщение об ошибке это средняя серьёзность: работа идёт, но пользователь тратит время. Отсутствие подписи у поля это низкая серьёзность для зрячего пользователя и высокая для того, кто работает с программой экрана, поэтому в описании указывают условие.

Сделайте вывод по каждому уровню. Для базы: какие нарушения целостности найдены и что нужно исправить. Для интерфейса: какие поля и сообщения не соответствуют требованию. Для стыка: где экран и API расходятся с базой и что проверить в первую очередь.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: найдены все нарушения целостности, для каждого указана причина, таблица расхождений заполнена по трём источникам, валидация проверена по всем значениям, клавиатурный протокол заполнен, выводы подкреплены запросами и шагами.
- **4**: работа выполнена полностью, но одно нарушение описано без причины или в таблице расхождений не проверен один источник.
- **3**: проверки выполнены частично, найдены очевидные нарушения, но типы, транзакция или клавиатура не проверены, выводы общие.
- **2**: работа не выполнена.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
