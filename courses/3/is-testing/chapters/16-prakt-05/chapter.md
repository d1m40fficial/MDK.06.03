## Цель работы

Проверить учебную ИС «Склад+» целиком, а не по отдельным модулям. Сценарий проходит путь кладовщика и менеджера: приёмка партии, появление остатка, отгрузка, накладная и передача накладной во внешнюю бухгалтерию. Проверка идёт на стенде с данными четырёх площадок и ролями кладовщика, менеджера и администратора.

Результат работы это протокол системного прогона. В нём зафиксированы окружение, сценарий, данные, наблюдения, найденные расхождения и вывод о готовности. Отдельно проверяется поведение системы при сбое внешнего сервиса и повторной отправке накладной.

## Краткие теоретические сведения

Системный тест проверяет готовую систему в среде, близкой к рабочей. Его интересует не отдельная функция и не стык двух модулей, а путь пользователя к результату: кладовщик принял товар, менеджер отгрузил часть, бухгалтерия получила накладную. Ошибка на этом уровне может выглядеть как «всё работает, но результат не тот».

Сквозной сценарий описывает пользовательский путь от роли. У каждого шага есть действующее лицо, данные, ожидаемый результат и требование, которое проверяется. Сценарий не должен состоять из технических вызовов: «вызвать функцию» это шаг теста, а не путь пользователя.

Окружение влияет на результат сильнее, чем кажется. Версия приложения, настройки SQLite, объём данных, состав ролей, часовой пояс и поведение внешнего сервиса меняют вывод. Поэтому окружение фиксируют до прогона, а не описывают по памяти после.

Системный тест не равен приёмочному. Системный прогон выполняет команда, чтобы понять, где система подведёт. Приёмку проводит заказчик и решает, принимает ли он результат. Совпадение сценариев не делает эти проверки одинаковыми: у них разные критерии и разная ответственность.

Роли проверяют отдельно от функций. Кладовщик Твери не должен видеть остатки Калуги, если это запрещено требованием. Менеджер оформляет отгрузку по всем площадкам, администратор удаляет партии. Один и тот же экран с разными правами может вести себя по-разному, и это видно только на системном уровне.

В учебном кейсе 120 сотрудников, четыре площадки, 4800 позиций и требование выдерживать 40 одновременных пользователей. На этой работе полный объём не обязателен, но данные должны включать несколько площадок, разные роли и повторную операцию. Иначе система снова проверяется в тепличных условиях.

Протокол системного прогона содержит окружение, сценарий, данные, результаты шагов, расхождения и вывод о готовности. Вывод делают по критериям с числами, а не по общему впечатлению.

Ниже выдержка из требований учебного набора. Из неё нужно построить один основной путь и один путь ошибки.

```text
R-04. Приёмка партии. Кладовщик указывает артикул, площадку, количество, дату
```

Проверьте, что каждый шаг имеет ожидаемый результат на языке бизнеса. «Функция вернула 0» это техническая деталь, «остаток равен 12» это результат, который можно сверить с требованием.

Путь ошибки нужен не меньше основного. Попытка отгрузить 100 папок при остатке 5 должна оставить остаток прежним и показать сообщение. Повторная приёмка с тем же номером документа не должна удваивать партию. Если путь ошибки не описан, система может выглядеть исправной, пока пользователь не ошибётся.

Сценарий должен быть коротким настолько, чтобы его можно было повторить, и полным настолько, чтобы он проверял результат. Пять-семь шагов обычно достаточно. Если шагов двадцать, разделите путь на два сценария: приёмка и отгрузка.

Роли проверяют по действиям, которые им разрешены. Если стенд не разграничивает доступ, шаг с ролью всё равно включают в сценарий, а в протоколе отмечают, что требование не проверено из-за ограничения стенда. Это честнее, чем считать проверкой один общий вход без прав.

### Шаг 5. Проверьте внешний обмен и повтор

Добавьте в стенд файл `buh.py`, который изображает внешнюю бухгалтерию. Заглушка принимает накладную, умеет отвечать таймаутом и складывает принятые документы в `buh.json`.

```python
import json
from pathlib import Path


def send_invoice(invoice, mode="ok"):
    path = Path("buh.json")
    data = json.loads(path.read_text(encoding="utf-8")) if path.exists() else []
    data.append(invoice)
    path.write_text(json.dumps(data, ensure_ascii=False, indent=2), encoding="utf-8")
    if mode == "timeout":
        raise TimeoutError("бухгалтерия не ответила")
    return {"status": "accepted"}
```

Заглушка записывает документ до ответа, поэтому таймаут означает, что бухгалтерия документ приняла, а ответ потерялся. Отправьте накладную сначала с режимом `timeout`, затем повторите отправку с режимом `ok`. Проверьте, сколько записей оказалось в `buh.json`. Сравните с требованием R-11: на каждую отгрузку должна быть одна накладная.

Заполните таблицу обмена. Первая строка показывает формат.

| Попытка | Режим | Ответ | Записей в buh.json |
|---|---|---|---|
| 1 | ok | принято | 1 |
|  |  |  |  |
|  |  |  |  |

Если повтор создал вторую запись, зафиксируйте это как расхождение. Не исправляйте заглушку: она изображает внешнюю систему, которую вы не контролируете. Исправление ищут в системе, которая повторяет отправку.

Повторная отправка должна быть безопасной. Для этого в документ добавляют ключ идемпотентности: уникальный номер, по которому внешняя система понимает, что документ уже принят. Если ключа нет, система не может отличить повтор от новой накладной. Проверка на стенде показывает, есть ли такой ключ и используется ли он.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: сценарий покрывает все шесть требований, основной путь и путь ошибки пройдены или ограничение зафиксировано, окружение описано, внешний обмен проверен с таймаутом и повтором, расхождения локализованы, вывод о готовности опирается на критерии.
- **4**: сценарий и прогон выполнены, но один шаг не имеет доказательства, окружение описано не полностью или вывод о готовности сделан без одного критерия.
- **3**: сценарий составлен частично, проверен только основной путь, внешний обмен не проверялся, расхождения перечислены без уровня и доказательства.
- **2**: работа не выполнена.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
