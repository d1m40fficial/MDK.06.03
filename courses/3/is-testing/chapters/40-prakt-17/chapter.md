## Краткие теоретические сведения

Сводный отчёт собирает данные нескольких прогонов и приводит их к единому виду. Сначала проверяют полноту данных: у каждой проверки есть результат, у каждого дефекта есть статус и серьёзность. Пропущенный результат нельзя считать успешным, а дефект без статуса нельзя считать закрытым.

Метрика это число с формулой и источником. «Много дефектов» не метрика. «Три открытых дефекта из восьми, один критический» это метрика, потому что её можно пересчитать по журналу. У каждой метрики указывают период, набор данных и правило подсчёта.

Покрытие требований показывает, сколько требований получили хотя бы одну выполненную проверку. Доля успешных проверок показывает качество сборки, но не качество набора: слабые проверки дают высокую долю успешных при плохой системе. Поэтому рядом всегда стоят покрытие, блокировки и открытые дефекты.

Готовность оценивают по заранее записанным критериям. Критерий это порог и правило: «критических открытых дефектов не больше нуля», «доля успешных проверок не ниже 90 процентов». Если порог придумывают после прогона, под него подгоняют вывод. Критерии фиксируют в плане до начала цикла.

Вывод о готовности бывает трёх видов. Готов означает, что все критерии выполнены. Условно готов означает, что остались дефекты с обходным путём и сроком исправления. Не готов означает, что хотя бы один блокирующий критерий нарушен. Формулировка «в целом готов» без условий не принимается: она скрывает, кто и когда закроет оставшиеся дефекты.

У отчёта несколько адресатов, и каждому нужен свой уровень детализации. Заказчику важны вывод, влияние на работу склада и условия передачи. Разработке нужны дефекты с шагами и приоритетом. Тестированию нужны покрытие, блокировки и план повторных проверок. Поэтому отчёт начинают с краткой сводки на одну страницу, а подробности выносят в разделы и приложения.

Сверка выявляет три типичных расхождения. Неуспешная проверка без ссылки на дефект означает, что дефект не оформлен. Ссылка на дефект, которого нет в журнале, означает, что журнал отстал от прогона. Закрытый дефект при повторной неуспешной проверке означает, что исправление не подтверждено. Каждое расхождение исправляют до расчёта метрик, иначе числа будут описывать не тот набор данных.

### Шаг 2. Посчитайте метрики

Скрипт читает выгрузку и считает результаты, требования и долю успешных проверок. Он не заменяет решение о готовности, а даёт числа для таблицы.

```python
import csv
from collections import Counter

with open("run.csv", encoding="utf-8") as source:
    rows = list(csv.DictReader(source))

results = Counter(row["result"] for row in rows)
requirements = {row["requirement"] for row in rows}
covered = {row["requirement"] for row in rows if row["result"] != "blocked"}
executed = len(rows) - results["blocked"]

print(f"всего проверок: {len(rows)}")
print(f"результаты: {dict(results)}")
print(f"требований в наборе: {len(requirements)}")
print(f"требований с выполненной проверкой: {len(covered)}")
print(f"доля успешных: {results['passed'] / executed:.0%}")
```

Скрипт печатает:

```text
всего проверок: 18
результаты: {'passed': 12, 'failed': 5, 'blocked': 1}
требований в наборе: 6
требований с выполненной проверкой: 6
доля успешных: 71%
```

`Counter` считает строки по значению, множества убирают повторы требований, а деление идёт на число выполненных проверок, а не на весь набор. Если делить на восемнадцать, заблокированная проверка превратится в неуспешную и занизит результат.

Заполните таблицу метрик. Первая строка дана как образец.

| Метрика | Формула | Значение | Источник |
|---|---|---|---|
| Доля успешных проверок | успешные / выполненные | 71% | `run.csv` |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |
|  |  |  |  |

В таблицу входят покрытие требований, выполнение плана, число открытых дефектов, число критических открытых и число заблокированных проверок. Для каждой метрики укажите источник: файл, лист или журнал, а также период, за который собраны данные. Метрику без периода нельзя сравнивать с другой метрикой.

### Шаг 3. Постройте динамику дефектов

Динамика показывает, успевает ли команда закрывать дефекты быстрее, чем находит новые. Заполните таблицу по журналу: сколько дефектов найдено за день, сколько закрыто и сколько осталось открытыми на конец дня.

| Дата | Найдено | Закрыто | Открыто на конец дня |
|---|---|---|---|
| 12.10 |  |  |  |
| 13.10 |  |  |  |
| 14.10 |  |  |  |

Постройте по таблице линейчатую диаграмму в Excel или LibreOffice. На диаграмме должны быть видны три ряда: найдено, закрыто, открыто на конец дня. Подпишите оси и добавьте название, иначе диаграмма не читается в отчёте.

Отдельно посчитайте, сколько критических и высоких дефектов осталось открытыми. Если открытых больше, чем закрытых за последний день, темп исправлений ниже темпа находок. Это не приговор, но повод пересмотреть план выпуска.

Диаграмма показывает не только итог, но и форму работы. Быстрый рост находок в первый день и спад к третьему обычно означает, что основные зоны уже проверены. Ровный рост без закрытий говорит о том, что команда находит дефекты, но не успевает их исправлять. Скачок закрытий в последний день часто связан с тем, что дефекты закрывали без повторной проверки. Такой скачок стоит проверить по протоколу.

### Шаг 4. Сравните факт с критериями готовности

Критерии готовности записаны до прогона. Заполните столбец «Факт» по своим расчётам и сделайте вывод по каждому критерию.

| Критерий | Порог | Факт | Вывод |
|---|---|---|---|
| Покрытие требований | не ниже 90% |  |  |
| Доля успешных проверок | не ниже 90% |  |  |
| Критические открытые дефекты | 0 |  |  |
| Открытые дефекты | не больше 2 |  |  |
| Заблокированные проверки | 0 |  |  |

По факту покрытие равно 100 процентам, доля успешных 71 процент, критический открытый дефект один, открытых дефектов три, заблокирована одна проверка. Четыре критерия из пяти нарушены. Вывод «готов» при таких числах невозможен.

Сформулируйте условие передачи модуля дальше. Условие содержит действие, ответственного и признак выполнения: «исправить D-02 и повторно выполнить C-05», «разблокировать C-06 после выдачи доступа», «закрыть D-04 или принять обходной путь до 16.10». Без ответственного и срока условие остаётся пожеланием.

### Шаг 5. Сформулируйте вывод и рекомендации

Вывод состоит из трёх частей. Сначала факт: что проверено и какие метрики получены. Затем оценка: какие критерии нарушены и что это значит для пользователя. В конце решение: готова система, условно готова или не готова, и при каких условиях решение изменится.

Рекомендации делят по адресатам. Разработке нужны исправления с приоритетом. Тестированию нужны повторные проверки и разблокировка. Заказчику нужно решение о допустимости выпуска с открытыми дефектами. Рекомендация «улучшить качество» не имеет адресата и не выполняется.

Проверьте, что вывод не противоречит таблицам. Если в тексте написано «критических дефектов нет», а в журнале D-02 открыт, отчёт теряет доверие целиком. Сверьте числа в тексте, таблицах и на диаграмме.

### Шаг 6. Оформите отчёт

Соберите отчёт в Word по структуре: цель и объём, исходные данные, методика расчёта, метрики, динамика дефектов, критерии готовности, вывод, рекомендации, приложения. Объём пять-семь страниц.

В приложении приведите выгрузку `run.csv` и журнал дефектов. В основном тексте оставьте сводные таблицы и диаграмму. Снимок экрана с расчётом не заменяет таблицу, но помогает проверить, что числа получены из данных, а не вписаны вручную.

Перед сдачей проверьте отчёт по трём признакам. Сводка на первой странице должна читаться без остальных разделов. Каждая таблица должна иметь название и источник. Вывод должен повторять те же числа, что и таблицы, без округлений, которые меняют смысл. Если в таблице 71 процент, в тексте не должно появиться «около 70» без пояснения.

### Шаг 7. Соберите презентацию

Презентация состоит из семи слайдов: цель и объём, подход и риски, метрики прогона, дефекты, динамика, вывод о готовности, ограничения и следующие шаги. На каждом слайде одна мысль и не больше двух чисел, которые её подтверждают.

Титульный слайд содержит название модуля, период цикла и автора работы. Последний слайд содержит условие передачи и ответственного за выполнение. Слайды не дублируют отчёт целиком: они показывают путь от данных к решению.

## Требования к отчёту

Отчёт в DOCX объёмом пять-семь страниц. Формат: A4, поля 3 см слева, 1,5 см справа, 2 см сверху и снизу, Times New Roman 14 пт, интервал 1,5, отступ первой строки 1,25 см. Заголовки Heading 1 и Heading 2, таблицы Table Grid с шапкой по центру, название таблицы под таблицей.

В отчёте есть цель, исходные данные, методика, метрики с формулами, динамика дефектов, таблица критериев, вывод и рекомендации. Презентация в PPTX или ODP содержит семь слайдов и те же числа, что и отчёт.

## Что сдать

- файл `run.csv` с восемнадцатью проверками;
- таблицу метрик с формулами и источниками;
- таблицу динамики дефектов и диаграмму;
- заполненную таблицу критериев готовности;

- презентацию из семи слайдов.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: метрики посчитаны по данным, формулы и источники указаны, динамика сходится с журналом, критерии сравнены с фактом, вывод содержит условие передачи с ответственным и сроком, отчёт и презентация согласованы.
- **4**: работа выполнена полностью, но одна метрика посчитана без источника или вывод не содержит условия передачи.
- **3**: метрики приведены без формул, динамика дефектов отсутствует, вывод не связан с критериями, презентация пересказывает отчёт.
- **2**: работа не выполнена.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
