## Цель работы

Добавить в коллекцию Postman автоматические проверки ответов API «Склад+» компании «Северный склад»: код состояния, формат тела, схему JSON, значения полей, негативные ответы и обработку ошибки сервера. Затем прогнать коллекцию целиком и разобрать отчёт.

Результат работы это коллекция с тестами, окружение без токенов, таблица проверок, сводка прогона и отчёт. Проверка, которая не сформулирована как утверждение, остаётся наблюдением: она не покраснеет, когда API начнёт отвечать иначе.

## Краткие теоретические сведения

Тест в Postman это функция JavaScript, которая выполняется после ответа. Внутри доступен объект `pm`: ответ, переменные, окружение и библиотека утверждений. Каждый тест получает имя и результат: зелёный, если утверждение выполнено, и красный, если нет.

Имя теста читают в отчёте, поэтому оно формулирует ожидание: `Статус 201 при создании`, `Отказ на чужую площадку`, `total равен числу элементов`. Имя `Тест 1` ничего не сообщает, и при падении приходится открывать код, чтобы понять, что проверялось.

Проверки строятся слоями. Сначала код состояния: он говорит, чем закончилась операция. Затем формат: заголовок `Content-Type` и разбор тела. Потом схема: обязательные поля, типы и ограничения. В конце значения: остаток, количество, итог, права. Слой не заменяет следующий. Код 200 с пустым списком проходит первый слой и падает на последнем.

Проверки пишут в разделе Tests, а не в Pre-request Script. Pre-request выполняется до запроса и подходит для подготовки токена или данных, а Tests видит ответ и может сравнить его с ожиданием. Если перенести утверждение в Pre-request, оно проверит предыдущий ответ или ничего.

Негативный тест проверяет отказ. Для него важны и код, и машиночитаемое поле `code` в теле. Код 400 на чужую площадку формально относится к ошибкам клиента, но причина неверная: клиент должен получить 403. Поэтому тест смотрит на оба признака.

Ошибка 500 тоже входит в контракт, если её вызывают намеренно. Проверяют, что ответ пришёл в JSON, содержит понятный код и сообщение, а также не раскрывает трассировку. Индуцированная ошибка не должна менять поведение обычного запроса без параметра `fail`.

## Ход работы

### Шаг 1. Подготовьте стенд и коллекцию

Возьмите файл `sklad_api.py` из практики 7, скопируйте его в `.../api-testing/prakt-08/` и запустите командой `python sklad_api.py`. Если файла нет, создайте его по тексту практики 7. Импортируйте коллекцию и окружение из практики 7, выберите окружение `sklad-local`.

Проверьте, что запрос `GET {{baseUrl}}/api/report?fail=1` с токеном менеджера возвращает 500. Если в вашей копии API такой ветки нет, добавьте её в обработчик отчёта после проверки прав.

```python
if request.args.get("fail") == "1":
    return jsonify({"code": "internal_error", "message": "отчёт временно недоступен"}), 500
```

`request.args.get` читает параметр адреса, `jsonify` собирает JSON, второй элемент кортежа задаёт код 500. Ветка стоит после проверки прав, поэтому без токена менеджера она не сработает и вернёт 401.

### Шаг 2. Напишите первый тест на код ответа

Откройте запрос списка товаров, раздел Tests, и добавьте проверку.

```js
pm.test("Статус 200", function () {
  pm.response.to.have.status(200);
});
```

`pm.test` создаёт проверку с именем. Имя видно в отчёте, поэтому оно называет ожидание, а не запрос. `pm.response.to.have.status` сравнивает фактический код с ожидаемым.

Отправьте запрос. В разделе Test Results появится строка с зелёной отметкой. Измените ожидание на 201 и отправьте снова: проверка станет красной, хотя API не менялся. Это показывает, что тест сравнивает ответ с записанным ожиданием, а не угадывает правильный результат.

| Запрос | Ожидаемый код | Имя теста | Результат |
|---|---|---|---|
| GET товары, своя площадка | 200 | Статус 200 |  |
|  |  |  |  |
|  |  |  |  |

Добавьте тесты к девяти запросам: успешное чтение, создание, повтор, неверное количество, отсутствие токена, чужая площадка, отчёт менеджера, отчёт кладовщика, ошибка сервера. Ожидаемый код берите из кода API и из контракта, а не из первого ответа.

Если проверка зависит от данных предыдущего запроса, сначала убедитесь, что предыдущий запрос выполнился. Иначе красный тест будет следствием, а не причиной.

### Шаг 3. Проверьте формат ответа

Код 400 может прийти с HTML внутри. Формально это ошибка клиента, фактически клиент не разберёт сообщение. Добавьте проверку заголовка и типа тела.

```js
pm.test("Ответ в JSON", function () {
  pm.response.to.have.header("Content-Type");
  pm.expect(pm.response.headers.get("Content-Type")).to.include("application/json");
});
```

`pm.response.headers.get` возвращает значение заголовка, `include` проверяет подстроку. Такой тест проходит и на успешном ответе, и на ошибке, если ошибка оформлена по контракту.

`pm.response.json()` разбирает тело. Если тело не JSON, вызов бросит исключение и тест упадёт. Это ожидаемое поведение: проверка JSON не должна быть зелёной на HTML. Добавьте тест формата ко всем запросам, где ожидается JSON.

Проверка заголовка не заменяет проверку тела. Сервер может прислать `application/json` с пустым объектом или с полем `error` вместо данных. Поэтому после формата идут схема и значения, а не наоборот.

### Шаг 4. Проверьте схему JSON

Схема описывает форму ответа: какие поля обязательны, какого они типа и какие ограничения действуют. Ниже схема списка товаров.

```js
const schema = {
  type: "object",
  required: ["items", "total", "site"],
  properties: {
    items: {
      type: "array",
      items: {
        type: "object",
        required: ["sku", "title", "site", "stock"],
        properties: {
          sku: { type: "string", pattern: "^SKU-\\d{4}$" },
          title: { type: "string", minLength: 1 },
          site: { type: "string", enum: ["Москва", "Тверь", "Тула", "Калуга"] },
          stock: { type: "integer", minimum: 0 }
        },
        additionalProperties: false
      }
    },
    total: { type: "integer", minimum: 0 },
    site: { type: "string" }
  },
  additionalProperties: false
};

pm.test("Схема списка товаров", function () {
  pm.response.to.have.jsonSchema(schema);
});
```

Схема требует массив `items`, число `total` и строку `site`, а лишние поля запрещает. У товара обязательны `sku`, `title`, `site` и `stock`. Шаблон `^SKU-\\d{4}$` допускает код из букв SKU, дефиса и четырёх цифр, а `minimum: 0` запрещает отрицательный остаток.

Схема проверяет форму, а не смысл. Ответ с `total: 0` и двумя товарами пройдёт схему, потому что оба поля правильного типа. Смысл проверяют отдельным утверждением на шаге 5.

| Ответ | Обязательные поля | Типы | Ограничения |
|---|---|---|---|
| Список товаров | `items`, `total`, `site` | массив, число, строка | `stock` не меньше 0, `sku` по шаблону |
|  |  |  |  |
|  |  |  |  |

Составьте схемы для ответа создания приёмки, для тела ошибки и для отчёта. Тело ошибки в «Склад+» содержит `code` и `message`, а у ошибки валидации добавляется объект `fields`.

### Шаг 5. Проверьте значения

Схема пропускает пустой список и неверный итог. Добавьте проверки значений.

```js
const body = pm.response.json();

pm.test("total равен числу элементов", function () {
  pm.expect(body.total).to.eql(body.items.length);
});

pm.test("Все товары своей площадки", function () {
  body.items.forEach(function (item) {
    pm.expect(item.site).to.eql(pm.environment.get("site"));
  });
});
```

`eql` сравнивает значения, `forEach` проходит по массиву. Ожидание берётся из запроса или из подготовленных данных, а не из того же ответа. Проверка `total` равна длине массива ловит рассинхронизацию, но не ловит случай, когда оба значения неверны одинаково.

| Проверка | Ожидание | Что ловит |
|---|---|---|
| Остаток не отрицательный | `stock >= 0` у каждого товара | отрицательный остаток после ошибки расчёта |
|  |  |  |
|  |  |  |

Добавьте проверки: созданная приёмка вернула то количество, которое отправлено, отчёт содержит непустое имя файла, список своей площадки не пуст. Для последней проверки сначала убедитесь, что в данных действительно есть товары.

### Шаг 6. Добавьте негативные проверки

Ниже ситуации, которые нужно закрыть тестами.

```text
GET /api/products без заголовка Authorization
GET /api/products?site=Тверь с токеном кладовщика из Москвы
GET /api/products?site=Саратов
POST /api/acceptance с qty "12"
POST /api/acceptance с qty 0
POST /api/acceptance по поставке 999
POST /api/acceptance повторно по поставке 505
GET /api/report с токеном кладовщика
```

Для каждого запроса добавьте тест кода и тест поля `code` в теле. Имя теста называет причину: `Отказ без токена`, `Отказ на чужую площадку`, `Отказ на повторную приёмку`.

```js
pm.test("Причина отказа", function () {
  pm.expect(pm.response.json().code).to.eql("duplicate");
});
```

Негативный тест проверяет не только отказ, но и причину. Если API вернул 400 на чужую площадку, код относится к ошибкам клиента, но причина неверная: клиент должен получить 403 и код `forbidden`.

| Ситуация | Ожидаемый код | Ожидаемый `code` | Факт | Результат |
|---|---|---|---|---|
| Повторная приёмка | 409 | `duplicate` |  |  |
|  |  |  |  |  |
|  |  |  |  |  |

### Шаг 7. Проверьте ошибку сервера

Запрос `GET {{baseUrl}}/api/report?fail=1` с токеном менеджера возвращает 500. Проверьте код, формат и содержимое ошибки.

```js
pm.test("Статус 500", function () {
  pm.response.to.have.status(500);
});

pm.test("Ошибка в JSON без стека", function () {
  const body = pm.response.json();
  pm.expect(body.code).to.eql("internal_error");
  pm.expect(body.message).to.be.a("string").and.not.empty;
  pm.expect(JSON.stringify(body)).to.not.include("Traceback");
});
```

Проверка стека важна для безопасности. Трассировка раскрывает пути, версии библиотек и структуру кода. Клиенту нужен код и понятное сообщение, а подробности остаются в журнале сервера.

Отдельно проверьте, что обычный запрос отчёта без параметра `fail` возвращает 200. Индуцированная ошибка не должна менять поведение исправной ветки.

Параметр `fail` включают только в отдельном запросе. Если оставить его в основном запросе отчёта, тест начнёт считать отказ нормой и перестанет замечать настоящую поломку.

### Шаг 8. Прогоните коллекцию и разберите отчёт

Запустите коллекцию через Run collection с окружением `sklad-local`, одна итерация. Запишите итог по папкам.

| Папка | Запросов | Проверок | Прошло | Упало | Время |
|---|---|---|---|---|---|
| Товары | 3 | 9 |  |  |  |
|  |  |  |  |  |  |

Откройте каждый упавший тест. Причина может быть в тесте, в окружении, в данных или в API. Если ожидание в тесте не совпадает с контрактом, исправляют тест. Если API нарушает контракт, оформляют дефект с запросом и ответом.

Проверьте, что падение одного теста не скрывает остальные. У каждого запроса свои проверки, а отчёт показывает их отдельно. Если после падения создания чтение падает на пустом `acceptanceId`, в отчёте будет две ошибки, хотя причина одна. Это нормально, но в разборе указывают первопричину.

Отчёт прогона сравнивают с предыдущим. Если число проверок упало без изменения коллекции, часть тестов потерялась при слиянии или импорте. Если выросло число падений на том же стенде, сначала проверяют окружение и данные, потом ищут дефект в API.

Сводка прогона отвечает на вопрос, можно ли выпускать сборку. Если упали только негативные проверки, причина часто в тесте или в изменившемся контракте. Если упали успешные сценарии, сначала проверяют стенд и данные, потом оформляют дефект.

### Шаг 9. Оформите отчёт

Отчёт собирается в Word. Структура: цель, стенд, список проверок по запросам, описание схем, таблица прогона, разбор падений, вывод.

В отчёт вставьте снимок Test Results для успешного запроса и для упавшего, а также сводку прогона. На снимке должны быть видны имена тестов и отметки результата.

В разборе падений для каждого случая укажите: запрос, тест, фактический ответ, ожидание по контракту, причину и решение. Если дефект найден в API, добавьте запрос и тело ответа без секретного токена.

Вывод отвечает, можно ли доверять набору: все ли проверки выполнились, нет ли ложных зелёных и совпадают ли ожидания с контрактом.

## Требования к отчёту

Отчёт в DOCX объёмом четыре-шесть страниц. Формат: A4, поля 3 см слева, 1,5 см справа, 2 см сверху и снизу, Times New Roman 14 пт, интервал 1,5, отступ первой строки 1,25 см. Заголовки Heading 1 и Heading 2, таблицы Table Grid с шапкой по центру, название таблицы под таблицей.

В отчёте есть цель, стенд, таблица проверок, таблица прогона, разбор падений и вывод. Схемы приводятся фрагментами, полный код тестов остаётся в коллекции.

## Что сдать

- коллекцию с тестами для девяти запросов;
- окружение без токенов;
- таблицу проверок с кодами и ожидаемым полем `code`;
- сводку прогона с числом проверок и падений;
- отчёт в DOCX с разбором падений.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: проверки покрывают код, формат, схему и значения, негативные тесты смотрят на поле `code`, ошибка 500 проверена на JSON и на отсутствие стека, прогон разобран, отчёт согласован с коллекцией.
- **4**: работа выполнена полностью, но одна группа проверок неполная: например, схема есть только у списка товаров или не проверен `Content-Type` у ошибок.
- **3**: тесты проверяют только код ответа, схемы и значения отсутствуют, негативные случаи пропущены, разбор падений формальный.
- **2**: работа не выполнена.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
