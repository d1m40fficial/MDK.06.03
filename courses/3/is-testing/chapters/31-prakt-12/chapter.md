## Цель работы

Собрать журнал дефектов учебной ИС «Склад+»: воспроизвести наблюдения на стенде версии 2.8, оформить баг-репорты, провести записи по статусам и проверить исправления на сборке 2.8.1. Работа идёт на данных склада: 120 сотрудников, четыре площадки, 4800 позиций товара.

Результат работы это книга `defects.xlsx` с листами дефектов и истории, результаты повторной проверки и отчёт. Журнал считается рабочим, если по любой записи другой человек может повторить шаги и понять, почему она находится в текущем статусе.

## Краткие теоретические сведения

Дефект это изъян в системе, который проявляется сбоем. Тестировщик наблюдает сбой, оформляет дефект, разработчик ищет причину и исправляет её. В записи фиксируют наблюдаемое расхождение с ожиданием, а не догадку о причине.

Жизненный цикл дефекта задаёт владельца каждого шага. Запись создают в статусе «Новый», на триаже назначают исполнителя или принимают другое решение. После исправления дефект переходит в «На проверке», и только проверка на сборке с исправлением позволяет закрыть его. Если дефект остался, запись переоткрывают с новыми шагами и новой сборкой.

Серьёзность описывает влияние дефекта, приоритет описывает очерёдность исправления. Серьёзность назначает тестировщик по последствиям для данных и работы. Приоритет назначает владелец продукта по срокам и риску для бизнеса. Эти решения могут не совпадать.

Баг-репорт содержит заголовок, окружение, предусловие, шаги, ожидаемый результат, фактический результат, воспроизводимость, серьёзность, приоритет и вложения. Заголовок строится по формуле: где, при каком условии, что не так. Один дефект это одна запись.

История статусов показывает, кто и когда менял состояние записи и на каком основании. Без истории невозможно понять, почему дефект закрыт, если проверку выполнял другой человек. История также показывает, сколько времени дефект провёл в каждом статусе.

Повторная проверка исправления включает исходные шаги и проверку соседних функций. Если исправление задело общий код приёмки, проверяют и отгрузку. Такой прогон называется регрессионной проверкой.

## Ход работы

### Шаг 1. Создайте журнал

Создайте книгу `.../defects/prakt-12/defects.xlsx` с тремя листами.

Лист `Дефекты` содержит колонки: идентификатор, заголовок, экран, сборка, окружение, предусловие, шаги, ожидаемый результат, фактический результат, воспроизводимость, серьёзность, приоритет, статус, автор, исполнитель, создан, закрыт, дней до закрытия, переоткрывался, связанная запись.

Лист `История` содержит колонки: идентификатор, дата, было, стало, кто, основание.

Лист `Справочники` содержит три списка: серьёзность, приоритет, статус.

| Серьёзность | Приоритет | Статус |
|---|---|---|
| Блокирующая | P1 | Новый |
| Критическая | P2 | Назначен |
| Значительная | P3 | В работе |
| Незначительная | P4 | Исправлен |
| Тривиальная |  | На проверке |
|  |  | Закрыт |
|  |  | Переоткрыт |
|  |  | Отклонён |
|  |  | Отложен |
|  |  | Дубликат |
|  |  | Не воспроизводится |

Настройте проверку данных для колонок серьёзности, приоритета и статуса. Выделите диапазон, откройте «Данные», затем «Проверка данных», выберите тип «Список» и укажите диапазон на листе `Справочники`. В LibreOffice Calc команда находится в меню «Данные», «Проверка достоверности». После настройки в ячейке появляется раскрывающийся список, и опечатка в статусе не проходит.

Проверка данных не заменяет дисциплину. Она лишь не даёт ввести значение вне списка. Основание перехода всё равно записывают в историю.

### Шаг 3. Оформите баг-репорты

Перенесите наблюдения на лист `Дефекты`. Каждая запись получает идентификатор вида D-001 и заголовок по формуле «где, при каком условии, что не так».

Примеры ниже взяты с формы заявки учебного портала и показывают только формат заголовка.

| Плохой заголовок | Хороший заголовок |
|---|---|
| Не работает | Кнопка «Отправить» на форме заявки остаётся активной после отправки |
| Ошибка | Форма заявки возвращает 500 при пустом поле «Телефон» |
| Дубли | Повторная отправка заявки создаёт две записи с одинаковым номером |
| Нет доступа | Роль «Гость» открывает заявки другого отдела по прямой ссылке |

Заполните окружение для каждой записи: сборка 2.8, браузер, операционная система, роль, площадка. Для «Склад+» площадка важна отдельно, потому что часть дефектов проявляется только на данных Твери или только у роли менеджера.

Проверьте, что в каждой записи есть ожидаемый и фактический результат. Ожидание берут из требования, а не из привычки. Если требование говорит, что ячейка обязательна, ожидание формулируют так: строка не сохраняется, поле подсвечено, остаток не меняется.

### Шаг 4. Назначьте серьёзность и приоритет

Для каждой записи назначьте серьёзность по влиянию и приоритет по очерёдности. В колонке «Обоснование» объясните решение одним предложением.

| № | Влияние | Серьёзность | Приоритет | Обоснование |
|---|---|---|---|---|
| 1 |  |  |  |  |
| 2 |  |  |  |  |
| 3 |  |  |  |  |
| 4 |  |  |  |  |
| 5 |  |  |  |  |
| 6 |  |  |  |  |
| 7 |  |  |  |  |
| 8 |  |  |  |  |
| 9 |  |  |  |  |

Серьёзность ставят по последствию: блокирует работу, приводит к неверным данным, замедляет задачу или портит вид. Приоритет обсуждают в группе, как на триаже. Если серьёзность и приоритет расходятся, это допустимо, но расхождение нужно объяснить.

### Шаг 5. Проведите дефекты по статусам

Ниже решения, которые приняли на триаже. Примените их к своим записям и занесите каждый переход на лист `История`.

```text
1. Исправление включено в сборку 2.8.1.
2. Исправление включено в сборку 2.8.1.
3. Поведение соответствует требованию R-05: поиск идёт по полному артикулу без дефиса.
4. Исправление включено в сборку 2.8.1.
5. Исправление включено в сборку 2.8.1.
6. Исправление включено в сборку 2.8.1.
7. Не воспроизводится на данных разработчика.
8. Отложено до версии 2.9.
9. Дубликат записи по наблюдению 4.
```

Для каждого решения выберите статус из справочника. Запись, которая уходит в работу, получает статус «Назначен» или «В работе». Запись, которая не является дефектом, получает «Отклонён» со ссылкой на требование. Дубликат получает статус «Дубликат» и ссылку на основную запись. Отложенная запись получает «Отложен» и условие возврата.

Каждый переход в истории содержит дату, прежний статус, новый статус, автора и основание. Основание это не «так решили», а ссылка на решение триажа, требование или результат проверки.

Проверьте, что в журнале нет записи, которая перешла из «Новый» сразу в «Закрыт». Закрытие означает проверку, а проверки ещё не было.

### Шаг 6. Проверьте исправление на сборке 2.8.1

Откройте сборку 2.8.1 и повторите исходные шаги для записей, которые получили исправление. Сначала запишите переход в «Исправлен» с номером сборки, затем в «На проверке». Проверьте не только сам дефект, но и соседнюю функцию: если исправление задело приёмку, проверьте отгрузку и остатки.

| ID | Сборка | Исходные шаги | Результат | Соседняя функция | Новый статус | Доказательство |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |

Если дефект не повторяется, запись переходит в «Закрыт» с указанием сборки и доказательства. Если повторяется, запись переходит в «Переоткрыт», а затем в «В работе». В основание переоткрытия входят новые шаги и наблюдение, которого не было в первой записи.

Часть исправлений в 2.8.1 может работать не полностью. Это нормальная ситуация: проверка нужна именно для того, чтобы отличить исправленный дефект от заявленного.

### Шаг 7. Посчитайте метрики журнала

Соберите четыре числа по листу `Дефекты`. Формулы удобно строить на весь столбец, чтобы новые записи попадали в расчёт автоматически.

Первый пример: `=СЧЁТЕСЛИМН(Дефекты!K:K;"Критическая";Дефекты!M:M;"В работе")`. Функция считает строки, где серьёзность равна «Критическая» и статус равен «В работе». В LibreOffice Calc та же функция называется `COUNTIFS`. Пары «диапазон, условие» можно повторять, добавляя новые ограничения.

| Метрика | Формула | Значение |
|---|---|---|
| Критические дефекты в работе |  |  |
| Ждут проверки исправления |  |  |
| Доля переоткрытых |  |  |
| Среднее время до закрытия |  |  |

Для среднего времени до закрытия заполните колонку «дней до закрытия» для закрытых записей и посчитайте среднее по этой колонке. Для доли переоткрытых отметьте «да» в колонке «переоткрывался» у записей, которые возвращались после проверки, разделите их число на общее число записей и умножьте на 100.

Проверьте, что знаменатель подписан. «Переоткрыто 2» без общего числа записей ничего не говорит.

### Шаг 8. Оформите отчёт

Отчёт собирают в Word. Структура: цель, состав журнала, сводная таблица дефектов, решения триажа, результаты проверки на 2.8.1, метрики, вывод.

В сводной таблице укажите идентификатор, заголовок, серьёзность, приоритет и текущий статус. Полные шаги и окружение остаются в книге, в отчёт включают одну-две записи целиком как пример оформления.

В отчёт вставляют снимки экранов, подтверждающие дефект и результат проверки. На снимке должны быть видны название раздела, версия сборки, роль пользователя и элемент, о котором идёт речь. Для дефекта, который проявляется только при определённых данных, добавьте снимок списка данных.

В выводе ответьте на три вопроса. Сколько записей осталось открытыми и почему? Какие исправления подтверждены, а какие пришлось переоткрыть? Какие дефекты дают наибольший риск для работы склада?

## Требования к отчёту

Отчёт в DOCX объёмом пять-семь страниц. Формат: A4, поля 3 см слева, 1,5 см справа, 2 см сверху и снизу, Times New Roman 14 пт, интервал 1,5, отступ первой строки 1,25 см. Заголовки Heading 1 и Heading 2, таблицы Table Grid с шапкой по центру, название таблицы под таблицей.

В отчёте есть сводная таблица девяти дефектов, решения триажа, таблица проверки на 2.8.1 и метрики. Книга `defects.xlsx` сдаётся отдельным файлом и должна открываться без восстановления.

## Что сдать

- книгу `defects.xlsx` с листами дефектов, истории и справочников;
- девять записей с шагами, окружением и воспроизводимостью;
- решения триажа с основанием для каждого перехода;

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: девять записей воспроизводятся по шагам, окружение и сборка указаны, серьёзность и приоритет обоснованы, каждый переход имеет основание, проверка на 2.8.1 выполнена с закрытием или переоткрытием, метрики посчитаны с знаменателями, отчёт согласован с журналом.
- **4**: работа выполнена полностью, но в одной записи не хватает воспроизводимости, либо один переход не имеет основания, либо метрика приведена без знаменателя.
- **3**: шаги описаны общими словами, статусы выставлены без истории, проверка исправления не выполнялась, отчёт пересказывает записи без вывода.
- **2**: работа не выполнена.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
