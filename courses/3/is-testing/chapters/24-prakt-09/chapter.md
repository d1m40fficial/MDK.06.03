## Цель работы

Перевести ручные проверки модуля склада ИС «Склад+» в набор автотестов на pytest, запустить его одной командой и убедиться, что набор проходит на исправной сборке и падает на дефектной. Отдельно разбирается отчёт о падении: какой случай проверялся, что ожидалось и что получено.

Результат работы это папка проекта, два сохранённых вывода прогона, таблица тестов и отчёт. Набор, который всегда зелёный, ничего не доказывает, поэтому проверка на дефектной сборке обязательна.

## Краткие теоретические сведения

pytest находит файлы `test_*.py` и функции `test_*`, выполняет их и собирает результат. Проверка записывается обычным `assert`. Если утверждение ложно, pytest показывает факт, ожидание и строку кода.

Имя теста читают в отчёте, поэтому оно называет проверяемое правило: `test_available_after_reserve`, `test_accept_rejects_zero`. Имя `test_1` ничего не сообщает, и при падении приходится открывать код, чтобы понять, что сломалось.

Фикстура это подготовка, которую тест получает по имени аргумента. Она создаёт данные, клиент или соединение и убирает за собой. Параметризация подставляет в один тест несколько наборов значений, а отчёт показывает каждый набор отдельным именем. Фикстура не заменяет тест-кейс: она только готовит состояние, а проверяет утверждение.

Автотест состоит из подготовки, действия и проверки. Ожидание берут из требования или из расчёта на бумаге, а не из того же кода, который проверяют. Иначе тест подтвердит любую ошибку реализации.

В этой работе проверяется модульный уровень: функции не ходят в базу и не поднимают сервер. Модульные тесты быстрые и точные, поэтому ошибку в формуле видно сразу. Интеграционные и UI-тесты появятся, когда у склада будет API и экран.

Код возврата pytest равен 0, когда все тесты прошли, и 1, когда есть падение. На этом коде строятся сборочные конвейеры. Ключ `-q` сокращает вывод, `-k` выбирает тесты по имени, `--junitxml` пишет отчёт для машины.

## Ход работы

### Шаг 1. Подготовьте проект и окружение

Создайте папку проекта и два вложенных каталога.

```text
.../api-testing/prakt-09/
  sklad/
    __init__.py
    stock.py
  tests/
    test_stock.py
```

Файл `sklad/__init__.py` оставьте пустым: он делает каталог пакетом, чтобы импорт `from sklad.stock import available` работал из корня проекта. Все команды выполняются из корня проекта, иначе импорт не найдёт пакет.

Создайте виртуальное окружение и установите pytest.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install pytest
python -m pytest --version
```

`python -m venv` создаёт отдельный каталог с интерпретатором и библиотеками. Активация меняет путь к Python в текущем терминале, поэтому `python` и `pytest` берутся из `.venv`. Если PowerShell запрещает запуск скрипта активации, не меняйте политику безопасности и не запрашивайте права администратора: вызывайте интерпретатор напрямую командой `.venv\Scripts\python.exe -m pytest`.

### Шаг 2. Создайте модуль склада

Ниже модуль с тремя функциями. Он хранит только правила расчёта, без базы и интерфейса.

```python
import os


def available(total: int, reserved: int) -> int:
    if os.environ.get("SKLAD_DEFECT") == "reserve":
        return total
    return total - reserved


def accept(total: int, qty: int) -> int:
    if qty <= 0:
        raise ValueError("количество должно быть больше нуля")
    return total + qty


def write_off(total: int, qty: int) -> int:
    if qty <= 0:
        raise ValueError("количество должно быть больше нуля")
    if qty > total:
        raise ValueError("недостаточно товара")
    return total - qty
```

| Функция | Что делает | Когда выбрасывает ошибку |
|---|---|---|
| `available` | считает свободный остаток | не выбрасывает |
| `accept` | прибавляет количество к остатку | количество меньше или равно нулю |
| `write_off` | списывает количество | количество не положительное или больше остатка |

Функции выбрасывают `ValueError`, а не возвращают `None` или ноль. Ошибка в количестве должна останавливать операцию, иначе отрицательная приёмка уменьшит остаток. Тест проверяет именно исключение, а не любое неверное значение.

Переменная окружения `SKLAD_DEFECT` включает учебный дефект. В обычном режиме её нет, и `available` вычитает резерв. Значение `reserve` заставляет функцию вернуть весь остаток без вычета. Это не ошибка проекта, а способ проверить, что тесты умеют краснеть.

`os.environ.get` читает переменную окружения и возвращает `None`, если её нет. В рабочем коде такой переключатель не оставляют: он позволяет выключить правило одним значением. В учебном модуле он нужен, чтобы показать падение теста без правки исходников.

### Шаг 3. Разберите первый тест

Создайте `tests/test_stock.py` с одной проверкой.

```python
from sklad.stock import available


def test_available_after_reserve():
    assert available(120, 35) == 85
```

Запустите тест из корня проекта.

```powershell
python -m pytest -q
```

Вывод показывает одну пройденную проверку.

```text
.                                                                        [100%]
1 passed in 0.01s
```

Разбор по частям. Имя файла начинается с `test_`, поэтому pytest его находит. Имя функции тоже начинается с `test_`. `assert` сравнивает результат вызова с числом 85, которое взято из правила: 120 минус 35 равно 85.

Проверьте, что тест действительно проверяет. Замените 85 на 84, запустите снова и прочитайте падение. Верните 85. Если тест с неверным ожиданием остался зелёным, он не выполняется: проверьте имя файла и функции.

### Шаг 4. Переведите ручные проверки в тесты

Ниже чек-лист ручной проверки модуля. В нём восемь пунктов, записанных так, как их выполняют вручную.

```text
1. Свободный остаток при 120 всего и 35 в резерве равен 85.
2. Свободный остаток при нулевом резерве равен всему остатку.
3. Свободный остаток при нулевом остатке равен нулю.
4. Приёмка 12 единиц к остатку 42 даёт 54.
5. Приёмка нуля отклоняется с ошибкой ValueError.
6. Приёмка отрицательного количества отклоняется с ошибкой ValueError.
7. Списание 8 единиц при остатке 7 отклоняется с ошибкой ValueError.
8. Списание всего остатка даёт ноль.
```

Переведите пункты в тесты. Один тест проверяет одно поведение. Если объединить все восемь проверок в одну функцию, при падении будет непонятно, какое правило нарушено.

Для числовых правил берите значения до границы, на границе и после неё. Для остатка 7 списание 7 допустимо, списание 8 нет. Для количества приёмки ноль и минус три относятся к одному классу ошибок, но проверяются отдельными строками параметризации.

| Пункт чек-листа | Имя теста | Утверждение | Результат |
|---|---|---|---|
| 1 | `test_available_after_reserve` | `available(120, 35) == 85` |  |
|  |  |  |  |
|  |  |  |  |

Для проверки ошибки используйте `pytest.raises`.

```python
import pytest

from sklad.stock import accept


def test_accept_rejects_zero():
    with pytest.raises(ValueError):
        accept(42, 0)
```

`pytest.raises` ловит исключение и делает тест зелёным, если оно действительно возникло. Если функция вернёт значение вместо ошибки, тест упадёт. Второй аргумент `match` позволяет проверить текст сообщения, но привязывать тест к полной фразе не стоит: сообщение может измениться без изменения поведения.

### Шаг 5. Добавьте фикстуру

Вынесите повторяющиеся данные в фикстуру.

```python
import pytest

from sklad.stock import available


@pytest.fixture
def stock():
    return {"total": 120, "reserved": 35}


def test_available_after_reserve(stock):
    assert available(stock["total"], stock["reserved"]) == 85
```

Имя аргумента совпадает с именем фикстуры. pytest вызывает фикстуру перед тестом и передаёт результат. Если фикстура нужна двум тестам, она описывается один раз. Заменяйте первый тест этой версией, а не добавляйте вторую функцию с тем же именем.

Используйте фикстуру не меньше чем в двух тестах. Если данные отличаются, создайте вторую фикстуру с понятным именем, например `empty_stock`, а не меняйте словарь внутри теста.

### Шаг 6. Сократите набор параметризацией

Три проверки свободного остатка отличаются только числами. Их объединяют параметризацией.

```python
@pytest.mark.parametrize(
    "total, reserved, expected",
    [(120, 35, 85), (18, 0, 18), (0, 0, 0)],
)
def test_available(total, reserved, expected):
    assert available(total, reserved) == expected
```

Первая строка задаёт имена аргументов, вторая содержит наборы значений. Один тест выполняет три случая, а отчёт показывает три имени: `test_available[120-35-85]`, `test_available[18-0-18]`, `test_available[0-0-0]`.

Сократите так же проверки нулевого и отрицательного количества. Не параметризуйте разные поведения: успешный расчёт и выброс ошибки остаются разными тестами, иначе условие с `pytest.raises` придётся встраивать в общий код.

### Шаг 7. Запустите набор одной командой

Запустите весь набор и сохраните вывод.

```powershell
python -m pytest -q > run-ok.txt
```

В файле должно быть не меньше семи пройденных тестов. Точное число зависит от того, как вы объединили проверки, но все они зелёные.

В выводе pytest строка `passed` считает выполненные тесты, а не утверждения внутри них. Один параметризованный тест с тремя наборами даёт три строки и три имени.

| Тест | Что проверяет | Результат |
|---|---|---|
| `test_available` | свободный остаток на трёх наборах |  |
|  |  |  |
|  |  |  |

Проверьте, что набор запускается из чистого терминала одной командой. Если перед запуском нужно вручную создать файл или поменять переменную, автоматизация неполная.

Ключ `-q` убирает служебные строки и оставляет итог. Код возврата команды можно проверить в PowerShell через `$LASTEXITCODE`: 0 означает успех, 1 означает падение. На этом признаке сборочная система решает, пропускать изменение дальше или останавливать конвейер.

### Шаг 8. Проверьте набор на дефектной сборке

Включите учебный дефект и запустите тот же набор.

```powershell
$env:SKLAD_DEFECT="reserve"
python -m pytest -q > run-fail.txt
```

Один тест должен упасть: свободный остаток вернёт 120 вместо 85. Остальные проверки останутся зелёными, потому что дефект касается только вычета резерва.

```text
F......                                                                  [100%]
================================== FAILURES ===================================
__________________________ test_available[120-35-85] __________________________

total = 120, reserved = 35, expected = 85

    def test_available(total, reserved, expected):
>       assert available(total, reserved) == expected
E       assert 120 == 85
E        +  where 120 = available(120, 35)

tests/test_stock.py:16: AssertionError
=========================== short test summary info ============================
FAILED tests/test_stock.py::test_available[120-35-85] - assert 120 == 85
1 failed, 6 passed in 0.05s
```

Прочитайте падение по порядку: имя теста с параметрами, строку утверждения, фактическое значение и путь к файлу. Запишите разбор в таблицу.

| Упавший тест | Ожидание | Факт | Причина |
|---|---|---|---|
| `test_available[120-35-85]` | 85 | 120 |  |
|  |  |  |  |

Если набор на дефектной сборке остался зелёным, тест не проверяет заявленное поведение. Вернитесь к утверждению и проверьте, что ожидание не вычисляется тем же кодом, который проверяют.

Красный тест не всегда означает дефект продукта. Если ожидание в тесте не совпадает с правилом, исправляют тест. Если совпадает, а функция возвращает другое число, дефект в продукте. В учебной сборке дефект включён намеренно, поэтому причина известна, но порядок разбора остаётся тем же.

Выключите дефект и убедитесь, что набор снова зелёный.

```powershell
Remove-Item Env:SKLAD_DEFECT
python -m pytest -q
```

### Шаг 9. Оформите отчёт

Отчёт собирается в Word. Структура: цель, структура проекта, список тестов, прогон на исправной сборке, прогон на дефектной сборке, разбор падения, вывод.

В отчёт вставьте вывод `run-ok.txt` и `run-fail.txt` текстом или снимком терминала. На снимке должны быть видны команда запуска, имя упавшего теста и итоговая строка с числом прошедших и упавших проверок.

В выводе ответьте на два вопроса: какие правила покрыты тестами и что доказывает падение на дефектной сборке. Если какой-то пункт чек-листа остался без теста, укажите его и объясните почему.

Если тест упал на дефектной сборке, в отчёте фиксируют строку утверждения: по ней видно, какое правило нарушено и какое значение получено.

## Требования к отчёту

Отчёт в DOCX объёмом четыре-шесть страниц. Формат: A4, поля 3 см слева, 1,5 см справа, 2 см сверху и снизу, Times New Roman 14 пт, интервал 1,5, отступ первой строки 1,25 см. Заголовки Heading 1 и Heading 2, таблицы Table Grid с шапкой по центру, название таблицы под таблицей.

В отчёте есть цель, структура проекта, таблица тестов, два вывода прогона, разбор падения и вывод. Полный код модуля и тестов остаётся в проекте, в отчёт включаются только ключевые фрагменты. Снимок терминала должен показывать команду, имя упавшего теста и итоговую строку, чтобы результат можно было сопоставить с текстом отчёта.

## Что сдать

- проект с файлами `sklad/stock.py` и `tests/test_stock.py`;
- вывод исправной сборки `run-ok.txt`;
- вывод дефектной сборки `run-fail.txt`;
- таблицу тестов с именами и проверяемыми правилами;
- разбор упавшего теста с ожиданием, фактом и причиной;
- отчёт в DOCX с выводом о покрытии.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: не меньше семи тестов, каждый проверяет одно поведение, есть фикстура и параметризация, набор зелёный на исправной сборке и красный на дефектной, падение разобрано по имени, утверждению и причине, отчёт согласован с выводами.
- **4**: работа выполнена полностью, но фикстура или параметризация использована формально, либо разбор падения не связывает факт с причиной.
- **3**: тесты написаны частично, проверки объединены в одну функцию, дефектная сборка не проверялась, отчёт пересказывает код.
- **2**: работа не выполнена.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
