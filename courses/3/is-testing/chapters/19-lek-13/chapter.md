## Пустой список, который выглядит нормой

После обновления 2.8 менеджер в Твери открывает экран «Остатки» и видит пустую таблицу. На экране написано «Товаров нет», кнопка выгрузки неактивна, ошибок нет. Менеджер решает, что в Твери закончился товар, и звонит на склад. На складе в Твери лежит 1240 позиций из 4800, которые есть в системе.

Если проверять только интерфейс, дефект легко пропустить. Экран открылся, пустое состояние отрисовалось, сообщение появилось. Ожидаемый результат «страница остатков открывается» выполнен. Но API на запрос `GET /api/products?site=Тверь` отвечает кодом 200 и телом `{"items": [], "total": 0}`. Фильтр сравнивает значение `Тверь` с латинским `Tver`, не находит совпадений и возвращает пустой список. Интерфейс честно показывает то, что получил.

**Тест API проверяет контракт между системами: какой запрос принят, какой код вернулся, что в теле и какие последствия у операции.** Он не смотрит на кнопки и вёрстку. Он смотрит на обещание, которое API даёт интерфейсу, другой системе и тестировщику.

## Что проверяет тест API

API это граница. С одной стороны стоит интерфейс, с другой база, внешняя бухгалтерия, мобильное приложение или чужой сервис. На этой границе встречаются разные команды, разные форматы данных и разные представления о том, что считать ошибкой. Большая часть интеграционных дефектов живёт именно здесь.

| Что проверяют | Интерфейс | API |
|---|---|---|
| Отображение и вёрстка | да | нет |
| Доступность кнопок и полей | да | нет |
| Код ответа и заголовки | косвенно | да |
| Состав и типы полей JSON | нет | да |
| Права роли на операцию | через экран | напрямую |
| Сохранение данных в базе | через экран | запросом и повторным чтением |
| Обмен с внешней системой | почти нет | да |
| Скорость ответа под нагрузкой | заметно | измеримо |

Тест API дешевле и точнее интерфейсного в тех случаях, когда проверяется логика, данные или права. Он не заменяет интерфейсный тест, потому что не показывает, удобно ли пользователю и правильно ли отрисована ошибка. Но он находит дефект там, где интерфейс его скрывает.

В «Склад+» API обслуживает три основных сценария: список товаров и остатков, создание приёмки и отчёт по остаткам. У каждого сценария есть успешный ответ, ошибки ввода, ошибки доступа и ошибки сервера. Основной набор проверок API для этих сценариев занимает около 42 проверок, из них 8 входят в дымовой набор.

## Анатомия запроса и ответа

Чтобы проверить API, нужно разложить обмен на части. Каждая часть может быть источником дефекта.

| Часть | Пример | Что проверять |
|---|---|---|
| Метод | `GET`, `POST` | соответствует операции и не меняет данные у `GET` |
| Путь | `/api/products` | существует, не содержит лишних версий и опечаток |
| Параметры | `?site=Тверь` | обязательные, допустимые значения, кодировка |
| Заголовки | `Accept: application/json` | формат ответа, язык, версия API |
| Аутентификация | `Authorization: Bearer ...` | токен есть, не истёк, принадлежит нужной роли |
| Тело запроса | `{"supply_id": 505, "qty": 12}` | обязательные поля, типы, границы, лишние поля |
| Код ответа | `201` | соответствует результату операции |
| Заголовки ответа | `Content-Type: application/json` | формат совпадает с телом |
| Тело ответа | `{"id": 9001, "status": "создана"}` | схема, значения, отсутствие лишнего |
| Последствия | остаток вырос на 12 | данные изменились ровно один раз |

Последствия проверяют отдельно. Успешный код 201 ещё не значит, что приёмка создалась один раз и остаток вырос на нужное количество. После `POST` делают `GET` и смотрят, что документ появился, а повторный `POST` с теми же данными не создаёт дубль.

## Коды состояния и их причины

Код состояния это короткий ответ API о том, что произошло. Он входит в контракт так же, как тело. Клиент по коду решает, показать ошибку, повторить запрос или попросить пользователя войти заново.

| Код | Когда уместен | Пример в «Склад+» |
|---|---|---|
| 200 | запрос выполнен, тело содержит результат | список товаров, отчёт |
| 201 | создан новый объект | приёмка создана |
| 204 | операция выполнена, тела нет | приёмка отменена |
| 400 | клиент прислал неверные данные | количество строкой, нет обязательного поля |
| 401 | клиент не представился | нет токена, токен истёк |
| 403 | клиент известен, но прав нет | кладовщик просит отчёт менеджера |
| 404 | объект не найден | поставка с номером 999 |
| 405 | метод не поддерживается | `GET` на адрес создания приёмки |
| 409 | конфликт с текущим состоянием | повторная приёмка по той же поставке |
| 500 | ошибка на стороне сервера | сбой при формировании отчёта |
| 503 | сервис временно недоступен | перегрузка или обслуживание |

Разница между 400 и 500 принципиальна. 400 означает, что клиент может исправить запрос и повторить его. 500 означает, что запрос был допустим, но сервер не справился. Если API отвечает 500 на пустое поле, клиент не понимает, что исправлять, а команда получает ложную тревогу о сбое сервера.

Разница между 401 и 403 тоже важна. 401 говорит «представься», 403 говорит «ты известен, но тебе нельзя». Если API отвечает 401 на запрос кладовщика с отчётом менеджера, клиент попробует войти заново, хотя проблема в правах. Если API отвечает 403 на истёкший токен, клиент не догадается обновить сессию.

Иногда 404 используют вместо 403, чтобы не раскрывать существование чужого объекта. Это допустимое решение, но оно должно быть записано в контракте. Тест проверяет не «правильный на взгляд тестировщика» код, а соответствие контракту и здравому смыслу.

> [!PITFALL] Код 200 с ошибкой внутри
> API отвечает `200 OK` и телом `{"error": "нет прав"}`. Формально запрос выполнен, фактически операция запрещена. Клиент, который смотрит только на код, покажет успех. Такое поведение ломает и интерфейс, и мониторинг.

## Контракт: что API обещает

Контракт API описывает адреса, методы, параметры, коды, структуру успешного и ошибочного ответа. Его фиксируют в OpenAPI, JSON Schema, таблице или документе. Без контракта тестировщик проверяет догадку, а не обещание.

Хороший контракт отвечает на вопросы, которые возникают у клиента. Что обязательно в запросе? Какого типа поле? Может ли оно быть пустым? Какие значения допустимы? Что вернётся при ошибке? Есть ли пагинация? Меняется ли формат между версиями?

| Свойство контракта | Вопрос теста | Пример дефекта |
|---|---|---|
| Обязательные поля | что будет без поля | `qty` отсутствует, API отвечает 201 |
| Типы | что будет со строкой вместо числа | `"12"` принимается как 12 |
| Границы | что будет с нулём и отрицательным | `-3` создаёт приёмку |
| Перечисления | что будет с чужим значением | площадка `Саратов` проходит |
| Формат | что будет с датой и телефоном | дата `01.10.2026` вместо ISO |
| Пагинация | что будет со страницей за пределами | `page=999` возвращает всё |
| Ошибки | какой код и какое тело | 500 и HTML вместо JSON |
| Версия | что изменится в новой версии | поле переименовали без предупреждения |

Схема JSON проверяет структуру, а не бизнес-истину. Она скажет, что поле `stock` есть и оно целое, но не скажет, что остаток в Твери не должен быть нулевым при 1240 позициях на складе. Поэтому тест API сочетает схему и оракул: схема ловит форму, сравнение с данными ловит смысл.

Вот схема ответа списка товаров. Она требует массив `items`, число `total`, у каждого товара обязательные `sku`, `title`, `stock`, а остаток не может быть отрицательным.

```python
import jsonschema

schema = {
    "type": "object",
    "required": ["items", "total"],
    "properties": {
        "items": {
            "type": "array",
            "items": {
                "type": "object",
                "required": ["sku", "title", "stock"],
                "properties": {
                    "sku": {"type": "string", "pattern": "^SKU-\\d{4}$"},
                    "title": {"type": "string", "minLength": 1},
                    "stock": {"type": "integer", "minimum": 0},
                },
                "additionalProperties": False,
            },
        },
        "total": {"type": "integer", "minimum": 0},
    },
    "additionalProperties": False,
}

bad = {"items": [{"sku": "SKU-1001", "title": "Кабель UTP", "stock": -3}], "total": 1}
errors = sorted(jsonschema.Draft202012Validator(schema).iter_errors(bad), key=lambda e: list(e.path))
for error in errors:
    print("путь:", list(error.path), "|", error.message)
```

Проверка отрицательного остатка даёт конкретное сообщение с путём до поля.

```text
путь: ['items', 0, 'stock'] | -3 is less than the minimum of 0
```

Схема не заменяет тест-кейс. Она отвечает на вопрос «похож ли ответ на обещанный», но не на вопрос «правильные ли данные». Если API вернёт `total: 0` при 1240 позициях, схема пройдёт, а бизнес-проверка упадёт. Поэтому в наборе есть и проверка формы, и проверка значения.

## Прогон запросов на учебном API

Ниже небольшой учебный API «Склад+» на Flask. В нём три адреса: список товаров, создание приёмки и отчёт. Код показывает, как один и тот же сервис отвечает на успешные и ошибочные запросы.

```python
from flask import Flask, request, jsonify

app = Flask(__name__)
app.json.ensure_ascii = False

SUPPLIES = {505: {"id": 505, "warehouse": "Москва", "status": "ожидает"}}
ACCEPTANCES = {}
TOKENS = {"manager-token": "manager", "store-token": "storekeeper"}


@app.get("/api/products")
def products():
    site = request.args.get("site", "")
    if site not in {"Москва", "Тверь", "Тула", "Калуга"}:
        return jsonify({"code": "bad_site", "message": "неизвестная площадка"}), 400
    return jsonify({"items": [{"sku": "SKU-1001", "title": "Кабель UTP", "stock": 42}], "total": 1})


@app.post("/api/acceptance")
def acceptance():
    data = request.get_json(silent=True)
    if not isinstance(data, dict):
        return jsonify({"code": "validation_error", "fields": {"body": "ожидается JSON"}}), 400
    supply_id = data.get("supply_id")
    qty = data.get("qty")
    if not isinstance(supply_id, int) or not isinstance(qty, int) or qty <= 0:
        return jsonify({"code": "validation_error", "fields": {"qty": "ожидается целое число больше нуля"}}), 400
    if supply_id not in SUPPLIES:
        return jsonify({"code": "not_found", "message": "поставка не найдена"}), 404
    if supply_id in ACCEPTANCES:
        return jsonify({"code": "duplicate", "message": "приёмка уже создана"}), 409
    ACCEPTANCES[supply_id] = {"id": 9001, "supply_id": supply_id, "qty": qty}
    return jsonify({"id": 9001, "status": "создана"}), 201


@app.get("/api/report")
def report():
    header = request.headers.get("Authorization", "")
    token = header.removeprefix("Bearer ").strip()
    role = TOKENS.get(token)
    if role is None:
        return jsonify({"code": "unauthorized", "message": "нужен токен"}), 401
    if role != "manager":
        return jsonify({"code": "forbidden", "message": "нет прав на отчёт"}), 403
    return jsonify({"rows": 312, "file": "report.xlsx"})


client = app.test_client()
cases = [
    ("GET", "/api/products?site=Москва", None, {}),
    ("GET", "/api/products?site=Саратов", None, {}),
    ("POST", "/api/acceptance", {"supply_id": 505, "qty": 12}, {}),
    ("POST", "/api/acceptance", {"supply_id": 505, "qty": "12"}, {}),
    ("POST", "/api/acceptance", {"supply_id": 505, "qty": 12}, {}),
    ("POST", "/api/acceptance", {"supply_id": 999, "qty": 3}, {}),
    ("GET", "/api/acceptance", None, {}),
    ("GET", "/api/report", None, {}),
    ("GET", "/api/report", None, {"Authorization": "Bearer store-token"}),
    ("GET", "/api/report", None, {"Authorization": "Bearer manager-token"}),
]
for method, path, payload, headers in cases:
    response = client.open(path, method=method, json=payload, headers=headers)
    print(method, path, headers.get("Authorization", ""))
    print("  статус:", response.status_code, "| тип:", response.content_type)
    print("  тело:", response.get_data(as_text=True).strip())
```

Прогон показывает разные исходы одного API.

```text
GET /api/products?site=Москва
  статус: 200 | тип: application/json
  тело: {"items":[{"sku":"SKU-1001","stock":42,"title":"Кабель UTP"}],"total":1}
GET /api/products?site=Саратов
  статус: 400 | тип: application/json
  тело: {"code":"bad_site","message":"неизвестная площадка"}
POST /api/acceptance
  статус: 201 | тип: application/json
  тело: {"id":9001,"status":"создана"}
POST /api/acceptance
  статус: 400 | тип: application/json
  тело: {"code":"validation_error","fields":{"qty":"ожидается целое число больше нуля"}}
POST /api/acceptance
  статус: 409 | тип: application/json
  тело: {"code":"duplicate","message":"приёмка уже создана"}
POST /api/acceptance
  статус: 404 | тип: application/json
  тело: {"code":"not_found","message":"поставка не найдена"}
GET /api/acceptance
  статус: 405 | тип: text/html; charset=utf-8
  тело: <!doctype html>
<html lang=en>
<title>405 Method Not Allowed</title>
<h1>Method Not Allowed</h1>
<p>The method is not allowed for the requested URL.</p>
GET /api/report
  статус: 401 | тип: application/json
  тело: {"code":"unauthorized","message":"нужен токен"}
GET /api/report Bearer store-token
  статус: 403 | тип: application/json
  тело: {"code":"forbidden","message":"нет прав на отчёт"}

  статус: 200 | тип: application/json
  тело: {"file":"report.xlsx","rows":312}
```

Разбор этого прогона даёт несколько выводов.

Успешный список товаров возвращает 200, `application/json`, массив и общее число. Это хороший ответ: клиент может отрисовать таблицу и показать количество.

Неизвестная площадка возвращает 400 и машиночитаемый код `bad_site`. Клиент понимает, что ошибка в параметре, и может показать сообщение рядом с полем.

Создание приёмки возвращает 201, а не 200, потому что появился новый объект. Повторная отправка даёт 409, а не второй документ. Это проверка идемпотентности на уровне бизнес-правила.

Строка `"12"` вместо числа даёт 400 с указанием поля `qty`. Это хороший негативный ответ: ошибка не превращается в 500 и не проходит молча.

Неизвестная поставка даёт 404. Клиент понимает, что объект не найден, а не что сервер сломался.

Запрос `GET` на адрес создания приёмки даёт 405, но тело ответа приходит в HTML, а не в JSON. Это дефект контракта ошибок. Клиент, который ждёт JSON, не разберёт сообщение. Исправление простое: единый обработчик ошибок возвращает JSON с кодом и сообщением для всех 4xx и 5xx.

Отчёт без токена даёт 401, с токеном кладовщика 403, с токеном менеджера 200. Проверка прав не сводится к одному запросу: нужны все три исхода.

## Негативные проверки

Позитивный тест подтверждает, что API работает на правильных данных. Негативный тест проверяет, что API отказывает на неправильных и не ломается. Для «Склад+» набор негативных проверок строится вокруг денег, количества и доступа.

| Проверка | Запрос | Ожидание | Что ловит |
|---|---|---|---|
| Нет обязательного поля | `{"supply_id": 505}` | 400, поле `qty` | падение на `None` |
| Неверный тип | `{"supply_id": 505, "qty": "12"}` | 400 | приведение строки к числу |
| Ноль | `{"supply_id": 505, "qty": 0}` | 400 | нулевую приёмку |
| Отрицательное | `{"supply_id": 505, "qty": -3}` | 400 | уменьшение остатка |
| Верхняя граница | `{"supply_id": 505, "qty": 1000000}` | 400 или согласованный предел | переполнение и блокировку |
| Неизвестный объект | `{"supply_id": 999, "qty": 3}` | 404 | создание приёмки без поставки |
| Дубль | повторный `POST` | 409 | второй документ |
| Нет токена | `GET /api/report` | 401 | доступ без входа |
| Чужая роль | токен кладовщика | 403 | доступ к отчёту |
| Чужой объект | менеджер другой площадки | 403 или 404 | утечку данных |
| Неверный метод | `GET /api/acceptance` | 405, JSON | HTML в ошибке |
| Битый JSON | `{qty: 12` | 400 | падение парсера |
| Лишнее поле | `{"qty": 12, "role": "admin"}` | поле игнорируется или 400 | массовое присвоение |
| Спецсимволы | `site=Тверь' OR 1=1` | 400 или пустой список | инъекцию |
| Повтор с ключом | тот же `Idempotency-Key` | тот же результат | дубль при повторе |

Негативные проверки не нужно писать для каждого поля вручную. Достаточно выбрать по одному представителю от каждого класса ошибок и добавить границы для денег и количества. Для строковых полей проверяют пустую строку, максимальную длину, спецсимволы и юникод. Для числовых проверяют ноль, отрицательное, максимум и дробное. Для идентификаторов проверяют несуществующий, чужой и удалённый.

Отдельно проверяют поведение при сбое. Что вернёт API, если база недоступна? Что покажет клиент, если ответ идёт дольше 30 секунд? Можно ли повторить запрос без дубля? Эти проверки относят к надёжности, но контракт ошибок у них тот же: код, машиночитаемый признак и понятное сообщение.

## Аутентификация и права

Аутентификация отвечает, кто вы. Авторизация отвечает, что вам можно. В API обе проверки идут до бизнес-логики, иначе данные успевают измениться до отказа.

В «Склад+» три роли. Кладовщик создаёт приёмку и видит товары своей площадки. Менеджер видит остатки своих площадок и выгружает отчёт. Администратор управляет пользователями и справочниками, но не обязательно видит деньги. Матрица прав должна быть в контракте, а тест проверяет каждую клетку, где стоит запрет.

| Операция | Кладовщик | Менеджер | Администратор |
|---|---|---|---|
| Список товаров своей площадки | да | да | да |
| Список товаров чужой площадки | нет | нет | да |
| Создание приёмки | да | нет | да |
| Отчёт по остаткам | нет | да | да |
| Управление пользователями | нет | нет | да |

Проверка прав устроена как таблица: для каждой роли и каждой операции ожидается разрешение или отказ. Недостаточно проверить, что администратор может всё. Нужно проверить, что кладовщик не может отчёт, а менеджер не может приёмку. Именно запреты чаще всего забывают, и именно они дают утечку.

Токен передают в заголовке `Authorization`, а не в адресе. Адрес попадает в журналы, историю браузера и системы мониторинга, где токен увидят лишние люди. Тест проверяет, что токен с истёкшим сроком даёт 401, токен другой роли даёт 403, а отсутствие токена не открывает данные.

::/gate

::gate Какие дефекты API не видны на экране и как их найти?

## Типичные дефекты API

Дефекты API однообразны. Их список стоит держать перед глазами, потому что каждый пункт превращается в проверку.

| Дефект | Симптом | Что проверить |
|---|---|---|
| 200 вместо 201 | клиент не понимает, что объект создан | код создания |
| 500 вместо 400 | клиент не знает, что исправить | ошибки ввода |
| HTML вместо JSON | клиент не разбирает ошибку | `Content-Type` и тело 4xx |
| Неверный `Content-Type` | JSON приходит как `text/html` | заголовок ответа |
| Разные имена полей | `supply_id` и `supplyId` в одном API | схема и примеры |
| `null` вместо пустого массива | клиент падает на `null` | пустой список |
| Локализованная дата | `01.10.2026` вместо ISO | формат даты |
| Неверный `total` | пагинация показывает не то число | сумма и страницы |
| Дубль при повторе | две приёмки по одной поставке | повторный запрос |
| Стек вызовов в 500 | утечка внутренних путей | тело ошибки |
| Массовое присвоение | клиент меняет роль через тело | лишние поля |
| Нет проверки площадки | менеджер видит чужой склад | параметр и роль |
| Медленный ответ | список грузится 8 секунд | время и план запроса |
| Устаревший кеш | после изменения данные старые | повторное чтение |

Один дефект может проявляться сразу в нескольких строках. Пустой список в Твери это и отсутствие проверки площадки, и неверный фильтр, и слабый оракул в тесте. Поэтому API-тест проверяет не «работает ли адрес», а конкретное обещание: для площадки Тверь вернуть 1240 позиций, для чужой площадки вернуть отказ, для несуществующей площадки вернуть 400.

## Как строить набор проверок API

Набор начинают с контракта. Каждое обещание контракта превращают в одну или несколько проверок. Если контракт говорит, что `qty` целое больше нуля, проверок будет три: ноль, отрицательное, строка. Если контракт говорит, что менеджер видит только свои площадки, проверок будет столько, сколько площадок и ролей нужно проверить.

Дальше набор делят на уровни. Дымовой набор из 8 проверок подтверждает, что API отвечает и отдаёт список. Основной набор из 42 проверок закрывает успешные сценарии, ошибки ввода, права и повторную отправку. Расширенный набор добавляет нагрузку, таймауты, редкие роли и старые данные.

| Уровень | Проверок | Что закрывает | Когда запускают |
|---|---|---|---|
| Дымовой | 8 | список, приёмка, отчёт, вход | каждая сборка |
| Основной | 42 | успех, ошибки, права, дубли | ночь и приёмка |
| Расширенный | 70 | нагрузка, таймауты, старые данные | релиз |

Проверки должны быть независимыми. Если один тест создаёт приёмку, а второй ожидает, что её нет, порядок запуска становится частью теста. Данные готовят перед проверкой и удаляют после неё, либо используют уникальные номера поставок для каждого прогона.

Оракул строят на конкретных значениях. Проверка «код 200» слишком слабая. Проверка «код 200, `total` равен 1240, в `items` есть `SKU-1001`, остаток 42» ловит и пустой список, и неверный фильтр, и потерю поля. Если значение зависит от данных, его берут из подготовленного набора, а не из самой системы: иначе тест подтвердит любой ответ, который вернёт API.

Для списка товаров набор из четырёх проверок выглядит так.

| Проверка | Запрос по контракту «Склад+» | Ожидание |
|---|---|---|
| Своя площадка | `GET /api/products?site=Тверь` с токеном кладовщика | 200, `total` 1240, все `items` с площадкой Тверь |
| Пустой параметр | `GET /api/products?site=` | 400, код `bad_site` |
| Неизвестная площадка | `GET /api/products?site=Саратов` | 400, код `bad_site` |
| Чужая площадка | токен менеджера Твери, `site=Москва` | 403, код `forbidden` |

Четыре проверки закрывают один адрес, но проверяют разные обещания: данные, валидацию параметра и права. Если объединить их в одну проверку «список работает», при падении будет непонятно, что именно сломалось.

Найденный дефект фиксируют вместе с запросом и ответом. В отчёт попадают метод, адрес, заголовки без секретного токена, тело запроса, код и тело ответа, время, идентификатор запроса и версия стенда. Без этих данных разработчик не повторит дефект, а тестировщик после исправления не сможет доказать, что поведение изменилось.

> [!KEY]
> Хороший тест API проверяет три вещи одновременно: код состояния, форму тела и бизнес-значение. Код без тела пропускает пустой список, тело без значения пропускает неверные данные.

## Итоги

- API проверяют по контракту: метод, путь, параметры, заголовки, тело, код и последствия.
- Код состояния входит в контракт: 400 и 500 значат разное, 401 и 403 тоже.
- Схема JSON ловит форму ответа, но не заменяет проверку бизнес-значений.
- Негативные проверки закрывают пустые поля, типы, границы, дубли, права и чужие объекты.
- Права проверяют по матрице ролей, включая запреты, а не только разрешения.
- Типичные дефекты API: неверный код, HTML в ошибке, разные имена полей, дубли и утечка данных.
- Набор делят на дымовой, основной и расширенный, а проверки делают независимыми.

::quiz
Q: Что проверяет тест API в первую очередь?
+ Контракт: запрос, код ответа, тело и последствия операции
- Цвет кнопок и расположение полей
- Скорость набора текста пользователем
- Орфографию в подсказках интерфейса
! API-тест работает с границей систем, а не с отрисовкой экрана.

Q: Какой код уместен при создании новой приёмки?
+ 201
- 200
- 204
- 500
! Код 201 сообщает, что создан новый объект.

Q: Что означает код 403?
+ Клиент известен, но у него нет прав на операцию
- Клиент не представился
- Объект не найден
- Сервер не справился с запросом
! 401 говорит «представься», 403 говорит «тебе нельзя».

Q: Почему 500 вместо 400 на пустое поле считается дефектом?
+ Клиент не понимает, что исправить, а сервер получает ложную тревогу
- Потому что 500 всегда быстрее
- Потому что 400 запрещён в REST
- Потому что тело ответа не может быть JSON
! Ошибка ввода должна указывать на поле, а не выглядеть как сбой сервера.

Q: Что проверяет схема JSON?
+ Обязательные поля и типы
+ Форматы и допустимые значения
- Правильность бизнес-данных в базе
- Удобство интерфейса
! Схема отвечает за форму ответа, а не за смысл данных.

Q: Что останется незамеченным, если проверять только код 200?
+ Пустой список товаров при неверном фильтре площадки
- Неверный `Content-Type`
- Отсутствие обязательного поля
- Ошибка 500
! Код 200 может скрывать пустой или неверный ответ.

Q: Какой запрос проверяет запрет для кладовщика на отчёт?
+ Запрос отчёта с токеном кладовщика, ожидается 403
- Запрос отчёта без токена, ожидается 200
- Запрос отчёта с токеном администратора, ожидается 200
- Запрос списка товаров с токеном кладовщика, ожидается 200
! Запреты проверяют отдельно от разрешений.

Q: Что делать после успешного `POST` создания приёмки?
+ Прочитать приёмку повторно и проверить, что она создана один раз
- Считать проверку законченной по коду 201
- Удалить базу и начать заново
- Проверить только цвет кнопки
! Код ответа не доказывает, что данные сохранились правильно.

Q: Какой дефект выдаёт HTML в теле ошибки?
+ Клиент не может разобрать машиночитаемое сообщение
- Сервер работает быстрее
- Ошибка исчезает при повторе
- Тело ответа становится пустым
! Контракт ошибок должен быть единым для всех 4xx и 5xx.

Q: Какие проверки относятся к негативным?
+ Пустое обязательное поле
+ Отрицательное количество
+ Повторная отправка той же приёмки
- Успешное создание приёмки
- Просмотр списка товаров менеджером
! Негативные проверки подтверждают отказ на неверных данных и конфликтах.

Q: Какие свойства контракта нужно проверять?
+ Обязательные поля и типы
+ Коды ошибок и формат тела ошибки
+ Права роли на операцию
- Цвет логотипа на странице входа
- Шрифт заголовка отчёта
! Контракт описывает обмен данными и права, а не оформление.

Q: Что означает 409 при повторной приёмке?
+ Конфликт с уже существующим документом
- Ошибку сервера
- Успешное создание второго документа
- Отсутствие авторизации
! 409 сообщает о конфликте состояния, например о дубле.

Q: Почему проверки API должны быть независимыми?
+ Чтобы порядок запуска не влиял на результат и падение одной не скрывало другие
- Чтобы каждая проверка занимала больше времени
- Чтобы не требовалось готовить данные
- Чтобы можно было не проверять права
! Независимые проверки дают достоверный результат при любом порядке.

Q: Как называется правило, по которому тест решает, верен ли результат?
= оракул
= тестовый оракул
! Оракул задаёт ожидаемый результат, без него проверка превращается в наблюдение.

Q: Какой заголовок ответа показывает формат тела?
= content-type
= Content-Type
! По `Content-Type` клиент понимает, как разбирать тело ответа.
