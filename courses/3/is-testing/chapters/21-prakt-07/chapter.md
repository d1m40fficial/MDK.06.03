## Цель работы

Собрать коллекцию запросов к API ИС «Склад+» компании «Северный склад» так, чтобы её мог повторить другой человек на другом стенде. В коллекции будут папки по ресурсам, окружение с адресом и токенами, переменные для связанных запросов и сохранённые примеры ответов. Отдельно оформляется отчёт о проверке ответов.

Результат работы это пять связанных артефактов: коллекция Postman, окружение без секретов, README с порядком запуска, таблица наблюдений и отчёт. Коллекция без окружения работает только на машине автора, а отчёт без коллекции нельзя повторить.

## Краткие теоретические сведения

HTTP-запрос состоит из метода, адреса, заголовков и тела. Ответ состоит из кода состояния, заголовков и тела. Код 2xx сообщает об успехе, 4xx об ошибке клиента, 5xx об ошибке сервера. В «Склад+» успешный ответ и тело ошибки всегда приходят в JSON, поэтому проверяют не только код, но и заголовок `Content-Type`, и структуру тела.

| Код | Когда появляется | Пример в «Склад+» |
|---|---|---|
| 200 | запрос выполнен, тело содержит результат | список товаров, отчёт |
| 201 | создан новый объект | приёмка создана |
| 400 | клиент прислал неверные данные | количество строкой, неизвестная площадка |
| 401 | клиент не представился | нет заголовка `Authorization` |
| 403 | клиент известен, но прав нет | кладовщик просит чужую площадку |
| 404 | объект не найден | поставка с номером 999 |
| 409 | конфликт с текущим состоянием | повторная приёмка по той же поставке |
| 500 | ошибка на стороне сервера | сбой при формировании отчёта |

Коллекция хранит запросы, папки и порядок их запуска. Окружение хранит значения, которые меняются между стендами: адрес, токен, площадку. Переменная записывается в двойных фигурных скобках и подставляется перед отправкой. Если адрес вписан в каждый запрос, переезд стенда с порта 8080 на другой порт ломает всю коллекцию, и правки приходится искать по всему списку.

Связанные запросы передают данные через переменные коллекции. Создание приёмки возвращает номер `id`, и следующий запрос читает документ по этому номеру. Значение сохраняют скриптом в разделе Tests, потому что другого места, где ответ доступен, в Postman нет. В этой работе скрипт только передаёт номер, а проверки появятся на следующем занятии.

Проверка ответа без ожидаемого результата превращается в наблюдение. Ожидание берут из контракта: кода, схемы и бизнес-правила. Контракт этой работы задан кодом учебного API, который открыто лежит в проекте. Поэтому факт из ответа всегда можно сравнить с веткой кода, которая этот ответ сформировала.

Отчёт о проверке API фиксирует не только найденные дефекты. В нём видно, что именно проверено, на каком стенде, с какими данными и с каким результатом. Через неделю автор коллекции уже не помнит, почему запрос с площадкой Тверь вернул отказ. Отчёт и примеры ответов возвращают этот контекст без восстановления хода мыслей.

## Ход работы

### Шаг 1. Запустите учебный API

Ниже полный код учебного API. Он хранит данные в памяти, поэтому после перезапуска состояние возвращается к исходному: приёмки исчезают, остатки становятся прежними.

```python
from flask import Flask, request, jsonify

app = Flask(__name__)
app.json.ensure_ascii = False

TOKENS = {
    "store-token": {"role": "storekeeper", "site": "Москва"},
    "manager-token": {"role": "manager", "site": "Москва"},
    "admin-token": {"role": "admin", "site": None},
}
SITES = {"Москва", "Тверь", "Тула", "Калуга"}
SUPPLIES = {505: "Москва", 506: "Тверь", 507: "Тула"}
PRODUCTS = [
    {"sku": "SKU-1001", "title": "Кабель UTP", "site": "Москва", "stock": 42},
    {"sku": "SKU-1002", "title": "Розетка RJ-45", "site": "Москва", "stock": 120},
    {"sku": "SKU-2001", "title": "Коробка 400x300", "site": "Тверь", "stock": 64},
    {"sku": "SKU-2002", "title": "Стрейч-плёнка", "site": "Тверь", "stock": 18},
    {"sku": "SKU-3001", "title": "Стеллаж 2000x1000", "site": "Тула", "stock": 7},
    {"sku": "SKU-4001", "title": "Паллета EUR", "site": "Калуга", "stock": 0},
]
ACCEPTANCES = {}
NEXT_ID = 9000


def current_user():
    header = request.headers.get("Authorization", "")
    token = header.removeprefix("Bearer ").strip()
    return TOKENS.get(token)


@app.get("/api/products")
def products():
    user = current_user()
    if user is None:
        return jsonify({"code": "unauthorized", "message": "нужен токен"}), 401
    site = request.args.get("site", "")
    if site not in SITES:
        return jsonify({"code": "bad_site", "message": "неизвестная площадка"}), 400
    if user["role"] == "storekeeper" and site != user["site"]:
        return jsonify({"code": "forbidden", "message": "чужая площадка"}), 403
    items = [p for p in PRODUCTS if p["site"] == site]
    return jsonify({"items": items, "total": len(items), "site": site})


@app.post("/api/acceptance")
def create_acceptance():
    global NEXT_ID
    user = current_user()
    if user is None:
        return jsonify({"code": "unauthorized", "message": "нужен токен"}), 401
    if user["role"] not in {"storekeeper", "admin"}:
        return jsonify({"code": "forbidden", "message": "нет прав на приёмку"}), 403
    data = request.get_json(silent=True)
    if not isinstance(data, dict):
        return jsonify({"code": "validation_error", "fields": {"body": "ожидается JSON"}}), 400
    supply_id = data.get("supply_id")
    qty = data.get("qty")
    if not isinstance(supply_id, int) or not isinstance(qty, int) or qty <= 0:
        return jsonify({"code": "validation_error", "fields": {"qty": "ожидается целое число больше нуля"}}), 400
    if supply_id not in SUPPLIES:
        return jsonify({"code": "not_found", "message": "поставка не найдена"}), 404
    if supply_id in ACCEPTANCES:
        return jsonify({"code": "duplicate", "message": "приёмка уже создана"}), 409
    NEXT_ID += 1
    ACCEPTANCES[supply_id] = {"id": NEXT_ID, "supply_id": supply_id, "qty": qty, "status": "создана"}
    return jsonify(ACCEPTANCES[supply_id]), 201


@app.get("/api/acceptance/<int:supply_id>")
def read_acceptance(supply_id):
    if current_user() is None:
        return jsonify({"code": "unauthorized", "message": "нужен токен"}), 401
    document = ACCEPTANCES.get(supply_id)
    if document is None:
        return jsonify({"code": "not_found", "message": "приёмка не найдена"}), 404
    return jsonify(document)


@app.get("/api/report")
def report():
    user = current_user()
    if user is None:
        return jsonify({"code": "unauthorized", "message": "нужен токен"}), 401
    if user["role"] not in {"manager", "admin"}:
        return jsonify({"code": "forbidden", "message": "нет прав на отчёт"}), 403
    if request.args.get("fail") == "1":
        return jsonify({"code": "internal_error", "message": "отчёт временно недоступен"}), 500
    return jsonify({"rows": 4800, "file": "report.xlsx", "generated": "2026-10-31T10:00:00"})


if __name__ == "__main__":
    app.run(port=8080)
```

Сохраните файл как `.../api-testing/prakt-07/sklad_api.py` и запустите командой `python sklad_api.py`. В выводе появится адрес `http://localhost:8080`. Сервер останавливается сочетанием Ctrl+C в терминале.

Если установка Flask в общую папку Python запрещена, создайте виртуальное окружение в папке проекта командой `python -m venv .venv`, активируйте его через `.venv\Scripts\Activate.ps1` и установите Flask командой `python -m pip install flask`.

В API три токена. Они нужны, чтобы проверять не только успешные операции, но и отказы.

| Токен | Роль | Площадка | Что разрешено |
|---|---|---|---|
| `store-token` | кладовщик | Москва | список своей площадки, создание приёмки |
| `manager-token` | менеджер | Москва | список площадки, отчёт |
| `admin-token` | администратор | все | список любой площадки, приёмка, отчёт |

Проверьте, что API отвечает. Создайте в Postman запрос `GET http://localhost:8080/api/products?site=Москва` и добавьте заголовок `Authorization: Bearer store-token`. Ответ 200 должен содержать две позиции. Если пришёл 401, проверьте заголовок; если соединение не устанавливается, проверьте, что процесс API запущен и слушает порт 8080.

### Шаг 2. Создайте окружение

Создайте окружение `sklad-local` и заполните четыре переменные.

| Переменная | Значение | Зачем нужна |
|---|---|---|
| `baseUrl` | `http://localhost:8080` | адрес стенда |
| `storeToken` | `store-token` | запросы кладовщика |
| `managerToken` | `manager-token` | отчёт и проверка запретов |
| `site` | `Москва` | площадка по умолчанию |

Тип переменной оставьте `default`, а для токенов включите `secret`, чтобы значение скрывалось на экране и не попадало на снимки. Выберите окружение в правом верхнем углу. Без выбранного окружения Postman отправит запрос по адресу `{{baseUrl}}/api/products` буквально и вернёт ошибку соединения.

Проверка окружения простая. Наведите курсор на имя переменной в адресе: Postman покажет подставленное значение. Если подсказка пустая, переменная не найдена или окружение не выбрано.

### Шаг 3. Спланируйте папки коллекции

Создайте коллекцию `Склад+ API` и четыре папки. Папка группирует запросы по ресурсу, а не по порядку создания. Внутри папки сначала идёт чтение, затем запись, затем негативные случаи.

| Папка | Что проверяет | Запросов |
|---|---|---|
| Товары | чтение остатков и права на площадку | 3 |
|  |  |  |
|  |  |  |
|  |  |  |

Заполните таблицу до создания запросов: так проще заметить пропущенный случай. Всего в коллекции должно быть не меньше двенадцати запросов, по три на папку. Имена папок и запросов пишите по-русски, но метод и адрес оставляйте в имени запроса: `GET товары, своя площадка` понятнее, чем `request 7`.

Группировать запросы можно и по сценариям: «Приёмка целиком», «Отчёт и права», «Ошибки ввода». Для учебного набора удобнее ресурсы, потому что один и тот же запрос проверяет и успех, и отказ. Главное правило одно: у папки есть тема, а у запроса есть имя, по которому его найдёт человек, впервые открывший коллекцию.

### Шаг 4. Соберите запросы на чтение

Начните с папки «Товары». Создайте запрос `GET {{baseUrl}}/api/products`, добавьте параметр `site` со значением `{{site}}` и заголовок `Authorization: Bearer {{storeToken}}`. На вкладке Params должна быть одна строка. Если тот же параметр дописан ещё и в адрес, Postman отправит его дважды, и поведение будет зависеть от порядка разбора.

| Имя запроса | Метод | Адрес | Параметры | Ожидаемый код |
|---|---|---|---|---|
| GET товары, своя площадка | GET | `/api/products` | `site={{site}}` | 200 |
|  |  |  |  |  |
|  |  |  |  |  |

Добавьте ещё два запроса: список чужой площадки с токеном кладовщика и список с неизвестной площадкой. Для чужой площадки подставьте `Тверь` прямо в параметр этого запроса: отдельная переменная здесь не нужна, потому что значение относится к одной проверке.

### Шаг 5. Соберите запросы на запись

В папке «Приёмка» создайте `POST {{baseUrl}}/api/acceptance`. На вкладке Body выберите `raw` и тип `JSON`, затем вставьте тело.

```json
{
  "supply_id": 505,
  "qty": 12
}
```

Заголовок `Content-Type: application/json` Postman добавит сам при выборе типа JSON. Проверьте вкладку Headers: там не должно быть второго, вручную вписанного заголовка с другим значением. Если выбрать `form-data`, сервер получит поля формы, а не JSON, и вернёт 400.

Если API вернул 415, сервер не принял формат тела: проверьте выбранный тип и заголовок `Content-Type`. Если вернулся 400 с полем `body`, тело не разобралось как JSON, например из-за лишней запятой или одинарных кавычек.

Успешное создание возвращает 201 и тело с номером `id`. Код 201 означает появление нового объекта. Код 200 означал бы, что объект не создавался, и клиент не смог бы отличить создание от чтения.

| Имя запроса | Тело | Ожидаемый код | Что проверяет |
|---|---|---|---|
| POST приёмка, создание | `{"supply_id": 505, "qty": 12}` | 201 | создание документа |
|  |  |  |  |
|  |  |  |  |

Добавьте запросы: повторная приёмка по поставке 505, количество строкой `"12"`, количество 0, несуществующая поставка 999, приёмка с токеном менеджера. Каждый запрос сохраняет своё тело, поэтому не копируйте предыдущий запрос без правки.

### Шаг 6. Свяжите запросы переменной

После создания приёмки номер документа нужен запросу чтения. Откройте раздел Tests у запроса создания и добавьте строку.

```js
pm.collectionVariables.set("acceptanceId", pm.response.json().id);
```

Скрипт выполняется после ответа. `pm.response.json()` разбирает тело, `.id` берёт номер, `set` кладёт значение в переменные коллекции. В адресе чтения используйте `{{acceptanceId}}`.

Проверьте связку: отправьте создание, затем чтение. Если чтение вернуло 404, посмотрите значение `acceptanceId` в переменных коллекции. Пустое значение означает, что скрипт не выполнился или создание упало. При повторной отправке создания API вернёт 409, и номер не обновится. Для нового прогона перезапустите API или используйте другую поставку.

### Шаг 7. Проверьте ответы вручную

Отправьте каждый запрос и запишите наблюдение. Сравнивайте ответ с кодом API из шага 1, а не с догадкой. Таблица заполняется по факту, а не по ожиданию.

| Запрос | Код | Content-Type | Ключевые поля | Время, мс | Совпало с контрактом |
|---|---|---|---|---|---|
| GET товары, своя площадка | 200 | application/json | `items`: 2, `total`: 2 | 35 | да |
|  |  |  |  |  |  |
|  |  |  |  |  |  |

Проверьте не меньше восьми запросов, включая четыре негативных. Для каждого негативного ответа выпишите поле `code` из тела: `unauthorized`, `forbidden`, `bad_site`, `validation_error`, `not_found`, `duplicate`. Поле `code` нужно клиенту, чтобы отличить причины отказа без разбора текста сообщения.

Отдельно проверьте, что ошибки приходят в JSON, а не в HTML. Для этого смотрите `Content-Type` и первые символы тела. Если ошибка пришла в HTML, клиент не разберёт сообщение, даже когда код ответа верный.

### Шаг 8. Сохраните примеры ответов

Пример фиксирует ответ сервера и открывается без запуска запроса. Сохраните не меньше шести примеров: успешный список, список с нулевым остатком, создание, ошибка валидации, ошибка прав, ошибка сервера.

Имя примера должно содержать код и смысл: `200 своя площадка`, `403 чужая площадка`, `400 неверное количество`. Пример не заменяет проверку, но показывает новому человеку формат данных и помогает сравнить поведение после обновления.

Для нулевого остатка используйте площадку Калуга: там одна позиция с остатком 0. Для ошибки сервера отправьте `GET {{baseUrl}}/api/report?fail=1` с токеном менеджера. Параметр `fail=1` включает учебную ветку отказа, поэтому ошибка 500 воспроизводится по требованию, а не случайно.

### Шаг 9. Экспортируйте коллекцию и подготовьте README

Экспортируйте коллекцию в формате Collection v2.1 и окружение отдельным файлом. Перед экспортом окружения замените значения токенов на пустые строки или на текст `вставьте свой токен`: файл окружения уедет в общий репозиторий.

Проверьте экспорт поиском по файлу. Строк `store-token`, `manager-token` и `admin-token` быть не должно. Если токен попал в файл, отзовите его и выпустите новый, потому что история git сохранит старую версию.

README на пять-семь строк отвечает на вопросы нового человека: какое окружение выбрать, в каком порядке запускать папки, какие токены нужны, что считать успешным прогоном, какая версия API проверяется. README лежит рядом с файлами коллекции и окружения.

Коллекцию и окружение хранят в git вместе с README. Тогда изменение запроса видно в истории, а старую версию можно сравнить с новой. Большие выгрузки ответов и локальные адреса разработчиков в репозиторий не кладут: они быстро устаревают и мешают читать diff.

### Шаг 10. Оформите отчёт

Отчёт собирается в Word. Структура: цель, стенд и версия API, состав коллекции, таблица наблюдений, найденные расхождения, вывод.

В отчёт вставьте снимки: дерево коллекции с папками, окружение со скрытыми токенами, ответ на успешный запрос и ответ на негативный запрос. На снимке ответа должны быть видны код, заголовок `Content-Type` и тело.

Расхождением считается не только неверный код. Если API вернул 200 с пустым списком, если `total` не совпал с числом элементов, если ошибка пришла в HTML, это тоже расхождение. Каждое расхождение описывается строкой: запрос, факт, ожидание по контракту, предполагаемая причина.

Вывод отвечает на вопрос, можно ли передавать коллекцию другому тестировщику: выбрано ли окружение, нет ли секретов в файлах, все ли запросы воспроизводимы с нуля.

## Требования к отчёту

Отчёт в DOCX объёмом пять-восемь страниц. Формат: A4, поля 3 см слева, 1,5 см справа, 2 см сверху и снизу, Times New Roman 14 пт, интервал 1,5, отступ первой строки 1,25 см. Заголовки Heading 1 и Heading 2, таблицы Table Grid с шапкой по центру, название таблицы под таблицей.

В отчёте есть титульный лист с названием работы и фамилией, цель, стенд, состав коллекции, таблица наблюдений, список расхождений и вывод. Код API в отчёт не копируется, вместо него указывается версия и адрес стенда. Каждая таблица получает номер и название под таблицей, на каждую таблицу есть ссылка в тексте.

## Что сдать

- коллекцию `Склад+ API.postman_collection.json` с четырьмя папками и не менее чем двенадцатью запросами;
- окружение `sklad-local.postman_environment.json` без токенов;
- README с порядком запуска и выбора окружения;
- таблицу наблюдений по восьми запросам;
- отчёт в DOCX с расхождениями и выводом.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: четыре папки и не менее двенадцати запросов, адрес и токены вынесены в окружение, связка `acceptanceId` работает, проверено восемь запросов с четырьмя негативными, сохранено шесть примеров, секретов в файлах нет, README и отчёт согласованы с коллекцией.
- **4**: работа выполнена полностью, но один адрес вписан в запрос напрямую, сохранено меньше шести примеров или в таблице наблюдений нет времени ответа.
- **3**: коллекция собрана частично, окружение не используется, негативные запросы отсутствуют, отчёт пересказывает запросы без наблюдений.
- **2**: работа не выполнена.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
