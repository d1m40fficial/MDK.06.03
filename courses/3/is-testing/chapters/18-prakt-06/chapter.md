## Цель работы

Научиться собирать регрессионный набор под конкретное обновление и подтверждать прогоном, что старые функции не сломались. Работа идёт на учебном стенде «Склад+» версии 2.8: вы разберёте описание изменений, построите карту влияния, отберёте проверки из банка, добавите проверки на новое поведение, прогоните набор и оформите отчёт о готовности версии.

Результат работы это не список всех проверок, а обоснованный набор, который укладывается в бюджет прогона и закрывает зоны риска. Отчёт должен показать, что именно проверено, что найдено и что осталось непроверенным.

## Краткие теоретические сведения

Регрессия это ухудшение поведения, которое раньше работало. Она появляется после изменения кода, данных, настроек или внешнего окружения. Регрессионная проверка отвечает на вопрос «не сломали ли мы старое», а повторная проверка дефекта отвечает на вопрос «исправлено ли найденное». Это разные работы, и у них разные наборы.

Анализ влияния переводит описание изменений в зоны риска. Для каждого изменения выписывают модули, требования и общие данные, которые оно задевает. В «Склад+» 18 требований `R-01`...`R-18`, четыре площадки, 120 сотрудников и 4800 позиций товара. Одна функция расчёта суммы используется в приёмке, отгрузке, отчёте и обмене с бухгалтерией, поэтому изменение в одном месте может проявиться в четырёх.

Риск оценивают по двум величинам: вероятность, что изменение задело код, и цена ошибки для бизнеса. Закрытый документ, сумма в накладной и права на чужую площадку дают высокий риск. Текст сообщения или логотип дают низкий. Оценка риска нужна не для красоты таблицы, а для решения, какие проверки войдут в набор при ограниченном времени.

Регрессионный набор делят на уровни. Дымовой набор проверяет, что система жива и ключевые пути открываются. Целевой набор собирают под конкретное изменение. Ядро покрывает все требования в обычном режиме. Полный набор включает редкие случаи, старые данные и границы. На практике сначала запускают дымовой набор, затем целевой, а ядро и полный набор оставляют для ночной сборки и релиза.

Оракул это правило, по которому вы решаете, верен ли результат. Слабый оракул проверяет только код ответа или факт открытия экрана. Сильный оракул сверяет сумму, количество, состав полей, права роли и состояние данных после операции. Регрессия часто пропускает дефект именно потому, что проверка формально прошла, а оракул смотрел не туда.

### Шаг 3. Добавьте проверки на новое поведение

Банк содержит старые проверки. Новое поведение версии 2.8 ими не закрыто, поэтому для каждого изменения `C-1`...`C-4` нужна хотя бы одна новая проверка. Шаблон проверки: идентификатор, требование, предусловие, шаги, ожидаемый результат.

Образец заполнения дан на изменении `C-5`, которое не влияет на данные.

| Поле | Значение |
|---|---|
| Идентификатор | TC-201 |
| Изменение | C-5 |
| Предусловие | стенд 2.8 открыт, пользователь не авторизован |
| Шаги | открыть страницу входа, обновить страницу |
| Ожидаемый результат | отображается логотип версии 2.8, форма входа работает |

Для `C-1` проверьте не только создание новой приёмки, но и открытие документа, созданного до обновления. Для `C-2` проверьте состав столбцов и число строк в выгрузке. Для `C-3` проверьте права менеджера каждой площадки и ответ API. Для `C-4` проверьте пустое количество, нулевое, отрицательное и текстовое значение. Готовых ожидаемых результатов не дано: их нужно вывести из требований и описания изменения.

### Шаг 4. Соберите дымовой и целевой наборы

Разделите отобранные проверки на два набора и проверьте бюджет. Удобно вести список в файле `regression.csv` с колонками `id,set,minutes`, где `set` принимает значение `дымовой` или `целевой`. Тогда сумму можно посчитать одной командой.

Пример файла:

```text
id,set,minutes
TC-014,дымовой,6
TC-021,дымовой,4
TC-033,целевой,8
TC-041,целевой,7
```

Скрипт читает файл и печатает число проверок и минут по каждому набору.

```python
import csv
from collections import defaultdict

total = defaultdict(int)
count = defaultdict(int)

with open("regression.csv", encoding="utf-8") as f:
    for row in csv.DictReader(f):
        total[row["set"]] += int(row["minutes"])
        count[row["set"]] += 1

for name in sorted(total):
    print(f"{name}: проверок {count[name]}, минут {total[name]}")
```

На примере выше команда печатает:

```text
дымовой: проверок 2, минут 10
целевой: проверок 2, минут 15
```

Этот пример показывает только формат файла, а не готовый набор. Создайте свой файл, подставьте свои проверки и проверьте, что дымовой набор укладывается в 20 минут, а целевой в 60. Если не укладывается, вернитесь к отбору и объясните в отчёте, что исключили и почему.

### Шаг 5. Прогоните набор на стенде

Сначала выполните дымовой набор. Если он падает, дальше не идите: сначала выясните, открывается ли система и работает ли вход. Затем выполняйте целевой набор по порядку, от высокого риска к низкому.

Для каждой проверки заполняйте журнал. Первая строка дана как образец формата.

| Проверка | Ожидаемый результат | Фактический результат | Статус | Минуты | Чем подтверждено |
|---|---|---|---|---|---|
| TC-014 | приёмка сохраняется и видна в списке | приёмка сохранена, строка появилась | пройдена | 6 | список приёмок, номер 9001 |
|  |  |  |  |  |  |
|  |  |  |  |  |  |

Фиксируйте не только «пройдена» или «не пройдена», но и что именно вы увидели: сумму, количество, имя площадки, код ответа, текст сообщения. Если проверка упала, сохраните снимок экрана с фактическим результатом и укажите, на каком шаге это произошло. Для проверок API сохраните код ответа и тело.

Базовый результат версии 2.7: все 20 проверок банка проходили. Это важно для вывода: любое падение на версии 2.8, которого не было раньше, похоже на регрессию, но окончательный вывод делают после разбора.

### Шаг 6. Разберите расхождения

Для каждой упавшей проверки заполните таблицу. Тип расхождения определяйте по связи с изменением: если проверка относится к требованию, которое затронуто обновлением, это может быть новая ошибка в изменённом коде. Если проверка относится к соседнему требованию, которое не меняли, это похоже на регрессию.

| Проверка | Требование | Ожидание | Факт | Тип | Серьёзность | Блокирует выпуск |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |

Серьёзность оценивайте по последствиям, а не по громкости сообщения. Ошибка в сумме закрытого документа, потере данных и доступе к чужой площадке считается высокой. Ошибка в тексте сообщения считается низкой. Если сомневаетесь, задайте вопрос: что потеряет склад, если дефект попадёт в работу на неделю.

## Критерии оценки

Оценка выставляется по шкале от 1 до 5.

- **5**: карта влияния заполнена для всех изменений, набор укладывается в бюджет, все требования зон риска закрыты, новые проверки опираются на требования, журнал содержит фактические результаты, вывод обоснован и учитывает непроверенное.
- **4**: работа выполнена полностью, но одно изменение описано без требования или в наборе не хватает одной проверки соседнего модуля, при этом вывод остаётся корректным.
- **3**: карта влияния заполнена частично, набор собран без учёта времени, новые проверки повторяют старые, журнал содержит только статусы без фактических результатов.
- **2**: работа не выполнена.
- **1**: работа выполнена с использованием ИИ или скопирована полностью или частично, 1 балл без возможности исправления.
